# NSC-9871C0E9964 — 192.168.1.124 (the EPoX EP-8RDA)

Windows XP SP3, **AMD Athlon XP 1800+** (x86 family 6 model 8 stepping 1), 511 MB
RAM, **EPoX EP-8RDA** (nForce2; every onboard device reads `SUBSYS_10001695`, and
`0x1695` is EPoX's PCI vendor id), Phoenix-Award BIOS v6.00PG. 6.0 GB C: with
~3.7 GB free, floppy at A:.

| | |
|---|---|
| Boot disk | **Quantum Fireball CR6**, 6,448,619,520 bytes, on the **Promise card** — not the onboard IDE |
| Storage controller | **Promise Ultra 66** (`PCI\VEN_105A&DEV_4D38&SUBSYS_4D33105A&REV_01`), driver `ultra.sys`, enumerates as a SCSIAdapter |
| Onboard IDE | `PCI\VEN_10DE&DEV_0065` → "Standard Dual Channel PCI IDE Controller" (Microsoft's driver, **not** `nvatabus`) |
| 2D / display | **NVIDIA GeForce2 GTS/Pro** (`VEN_10DE&DEV_0150&SUBSYS_40161043` — ASUS), 800×600 |
| Network | **Intel PRO/100+ Management Adapter** (`VEN_8086&DEV_1229`), `e100b325.sys` |
| Agent | 1.79.4 |
| Image | slim PXE profile (`OemPreinstall = No`) — see [case study 003](../case-studies/003-epox-nforce2-xp-pxe-0x7b.md) |

## Its address is contested — trust the hostname, not the IP

This box answered on **192.168.1.124** when it was scanned, but that address is
already rostered to a different machine: `scripts/fleet/fleet-roster.txt:23`
expects `NSC-CABE14B7486` there (the dual-boot XP/Win98 box, Intel ~845 MHz,
Voodoo 3 removed 2026-08-11), and `docs/fleet-inventory.md` carries that record
too.

Both cannot hold the lease. This machine was `192.168.1.173` throughout its
install and moved to `.124` afterwards, so the most likely explanation is that it
took the address while the other box was off. **Resolve this before either box is
relied on** — a static reservation for one of them is the durable fix.

Identify this machine by hostname (`NSC-9871C0E9964`) or by its NIC
(`00:d0:b7:40:96:a9`), not by its address. Note the hostname itself is
disposable: `[UserData] ComputerName = *` makes XP generate a new random one on
every reinstall, so it changes each time this box is imaged.

## It only boots because the disk is NOT on the onboard IDE

This box took four installs to get right. Three completed and then failed to
boot — the last two with **STOP 0x0000007B INACCESSIBLE_BOOT_DEVICE** — while the
disk was on the onboard nForce2 IDE controller. Adding a **Promise Ultra 66 PCI
IDE card**, moving the disk to it, and disabling the onboard IDE in BIOS is what
made it boot.

Do not "tidy this up" by moving the disk back onto the motherboard. The full
reasoning, and the one-line change that would let the onboard controller work,
is in [case study 003](../case-studies/003-epox-nforce2-xp-pxe-0x7b.md).

The Promise binding is far closer to stock than the onboard one: `ultra =
ultra.sys,4` and `PCI\VEN_105A&DEV_4D38&CC_0180 = "ultra"` are both in
`I386/txtsetup.sif.preinject`, whereas the nForce2 binding appears nowhere in it.
It is not *purely* stock, though — the injector added a bare `DEV_4D38` id and a
second `ultra.sys` binary (35,538 B, from the driverpacks) alongside the stock
one inside `ULTRA.SY_` (36,736 B). Which of the two is installed here has not
been checked.

## nvatabus is still installed here, and that is fine

Worth knowing before someone "fixes" it: on this working machine all four
storage miniports are boot-start, `nvatabus` included.

```
HKLM\SYSTEM\CurrentControlSet\Services\ultra     Start = 0x0
HKLM\SYSTEM\CurrentControlSet\Services\nvatabus  Start = 0x0
HKLM\SYSTEM\CurrentControlSet\Services\atapi     Start = 0x0
HKLM\SYSTEM\CurrentControlSet\Services\pciide    Start = 0x0
```

`Start = 0x0` is `SERVICE_BOOT_START` and is normal for everything listed in
`txtsetup.sif`'s `[SCSI.Load]`. The fix was never "remove nvatabus" — it was to
put the **boot disk** on a controller `nvatabus` does not own.

Note also that the installed OS binds the onboard `DEV_0065` to Microsoft's
"Standard Dual Channel PCI IDE Controller", not to `nvatabus`. PnP in the
installed system matches on INFs, and the slim profile ships no NVIDIA IDE INF —
which is a different code path from the `[HardwareIdsDatabase]` lookup that
text-mode setup uses.

```
[boot loader]
default=multi(0)disk(0)rdisk(0)partition(1)\WINDOWS
```

## Two devices have no driver, by design

`DRIVERS` reports exactly two problems, both **error 28** (no driver installed):

| device | id |
|---|---|
| SM Bus Controller | `PCI\VEN_10DE&DEV_0064` |
| Multimedia Audio Controller | `PCI\VEN_10DE&DEV_006A` |

`AUDIOINFO` confirms `wave_out_count: 0` — there is no sound on this box yet.

This is expected, not a fault: it was imaged with the **slim** profile, which
sets `OemPreinstall = No` and therefore never copies the `$OEM$` tree — no
`C:\D` driver packs, no `cmdlines.txt`, no `retroagent.reg`. Two consequences
that will surprise someone later:

- **It does not answer ping.** No `retroagent.reg` means no firewall-off, and
  XP's firewall blocks ICMP by default. The agent on TCP 9898 answers fine.
  Use that, or ARP, to check whether the box is up — never ping alone.
- **Auto-login is not permanent.** `[GuiUnattended] AutoLogon = Yes` without the
  registry merge is a one-shot. See the `AutoLogonCount` note in
  `scripts/pxe/make-xp-source.sh`.

To finish provisioning this box, push the driver packs and the agent config over
the network rather than reimaging.

## Reading its hardware

The agent has no `PCILIST` / `HWINFO` / `SYSINFO`-style hardware command beyond
`SYSINFO`; the PCI inventory comes from `DRIVERS`, which returns 105 device
records as JSON.

```python
from client.retro_protocol import RetroConnection
c = RetroConnection("192.168.1.124", 9898)
await c.connect(os.environ.get("RETRO_AGENT_SECRET", "retro-agent-secret"))
devs = json.loads(await c.command_text("DRIVERS", timeout=90))
[d for d in devs if d["hardware_id"].startswith("PCI")]
```

`HELP` is not a command and returns `Unknown command`; the authoritative command
list is the string table in `agent/`.
