THE FINDING: a same-mode CDS_RESET does not build a new display surface
-----------------------------------------------------------------------
First design: apply Diag\Accel2D* with ChangeDisplaySettingsEx(current mode,
CDS_RESET). The vcr-kmd flight recorder (`vcrctl log`) after that Apply:

  82  DrvGetModes
  83  DrvAssertMode        a=0 b=1
  84  PHASE mode set
  85  mode 154: 1024x768x32@60
  86  pll 65000 kHz -> 65028 kHz, refresh 60028 mHz
  89  mode set done
  91  DrvAssertMode        a=1 b=1

Only DrvAssertMode(FALSE)/(TRUE) on the SAME PDEV - no DrvEnablePDEV, no
DrvEnableSurface - so VcrDd2dInit (vcrdd_2d.c, called from DrvEnableSurface)
never re-read IOCTL_VCR_INFO and the switches were never read.

Second design (shipped): pass through another listed mode at the same
resolution and back, two switches through tools/vcr_pace.h:

  96  DrvEnablePDEV mode 155            (495602 ms)
  99  mode 155: 1024x768x32@70
 106  DrvEnableSurface 1024x768x32      <- new surface, flags re-read
 126  DrvDisableSurface / 127 DrvDisablePDEV
 129  DrvEnablePDEV mode 154            (498667 ms: 3.065 s later - the pace floor)
 132  mode 154: 1024x768x32@60
 139  DrvEnableSurface 1024x768x32      <- back at the original mode, new surface

Summary line of that Apply: "[OK] display passed through 32-bit 70 Hz and is
back at 1024x768 32-bit 60 Hz (paced, read back)" (vm_apply_2d_bounce.png).
The driver in the bed predates the 2D report, so the panel said
[UNCONFIRMED] for the switch itself - which is the honest answer there.
