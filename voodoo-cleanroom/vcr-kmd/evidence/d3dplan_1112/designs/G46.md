- **Lane:** clean-room `vcr-kmd` (`vcrmp.sys` + `vcrdd.dll`), the Voodoo 5 6000 in `.124`, Direct3D only.
- **Kind:** needs-investigation. **Priority P1.** This is the measurement that comes before the performance work.
  UT2003 runs at 9.4 fps and UT2004 at 4-6 fps, and Halo's timedemo had not finished after 485 s, so all three are
  unplayable. **Effort M.** That is G46's own share. It becomes L if G46 also has to build the d3dprobe perf modes

- **Works with:** G04 (the heartbeat), G76 (the ring) and G52/G55/G59 (measured here, fixed there). It decides the
  order of G47-G51, G53, G54, G56, G57 and G58.

    §12 P9 (`runtime-24`);
  - the code, and the vendor H5 source;
  - a **host-side re-analysis of the committed UT2003 stats CSV and ring** (§1.2), done for this design.
- **How it was produced:** design only. Nothing was built, deployed or run on a box, and no box was contacted. The
  only things run were host scripts over committed evidence, in the scratchpad.

## 0. Verdict

1. **The gap is real, and the evidence on file cannot settle it.**
   - The game's own counter, `Hardware DrawPrimitive`, covers two things at once: the runtime's software vertex
     processing and clipping, and our HAL's DP2 walk and PIO.
   - Re-analysed here (§1.2), the two cannot be separated from the data. Per frame, the primitive count and the
     software-processed vertex count correlate at **0.994**.
   - The driver kept **no frame count** for any game session: all four logged `flips of 0`, because the flip counters
     count vsync'd flips only.
2. **What the host re-analysis already shows, without box time:**
   - **95 % of the UT2003 frame is inside DrawPrimitive.** The game outside it costs 6.3 ms a frame.
   - Each submitted primitive costs **3.75 µs** (median).
   - **18,586 triangles a frame reach the HAL**, which is 63 % of what the game submits, in 29.9 DP2 calls.
     DrawPrimitive's 116.7 ms therefore bounds the HAL at **6.28 µs per triangle**.
   - That matches the PIO model in the perf report: 36-45 uncached writes and 3 status reads per triangle
     (4.6-9.8 µs, perf §4.1).
   - UT2004 run 1 at 1280x960 shows roughly **2x that cost per HAL triangle**. Halo may show more. If the frame
     counts inferred from the clears hold, fill makes up a large share at 1280x960. **The split differs per title
     and per resolution.**
3. **The design is a staged investigation.** Each stage costs more than the one before and runs only if the last
   one leaves the question open.
   - **S0:** host analysis, done here.
   - **S1:** no driver change. The game thread's kernel/user CPU time plus the game's own statistics, which give
     the HAL-versus-runtime split directly.
   - **S2:** a log-only counter set in the driver (`Diag\D3DStats`) and d3dprobe microbenchmarks. They give the
     unit costs and the split inside the HAL. S2 also adds resolution scaling, a breadth pass over every D3D title,
     and UT99 D3DDrv against the vendor HAL's 69-70 fps.
   - **S3:** a one-boot "triangles not sent" switch (`Diag\D3DPerfTest` = 1, 3dfx's own `TRI_NULL`). It gives the
     frame-rate ceiling that any transport fix can reach.

   A decision table (§5) maps the measured split onto the fix order. A what-if model predicts each fix's gain before
   it is built.
4. **Expected outcome (inferred, to be replaced by the measurement):**
   - UT2003 at 640x480 is transport-bound: about 85-90 % of the frame is in the kernel, at about 3 status reads per
     triangle.
   - At 1280x960, waiting on the raster adds a large share.
   - **Likely fix order:**
     - G48 + G58: cheap, about 30-45 % off the HAL's time (model);
     - G49: autostrip, worth it only if the op histogram shows enough shared edges;
     - G50 (2PPC) for 1280x960;
     - **G47 CMDFIFO**, the 5-10x on transport (model);
     - G51 SLI, where fill remains the limit.
5. **No instrument here changes what a fresh install draws.**
   - `D3DStats` is default OFF. When armed it is log-only, plus six reads of chip 0's statistics registers per frame.
   - `D3DPerfTest` is a diagnostic. The miniport clears it again at the boot that honours it.
   - Every proven register sequence is unchanged and pinned by tests (§8).

### 1.2 S0: the committed data, re-analysed on the host (done for this design)

A throwaway script read the UT2003 stats CSV. Its numbers are the ones `tools/ue2stats.py` (§3.1) must reproduce.
It parses the header of 174 columns, where a duplicated name is (count, ms).

- **DrawPrimitive is 94.9 % of the frame.**
  - Outside it: 6.26 ms mean, 5.46 ms median. That is all the game's CPU (logic, visibility, scripts, Karma)
    together.
  - So **the frame rate is decided inside DrawPrimitive**, which holds both the runtime and the HAL.
- **Cost per submitted primitive:** 3.75 µs median (mean 3.74, p5 2.23, p95 4.83). It is stable across the run:
  4.06 / 3.98 / 3.88 µs in the first tenth, the middle 80 % and the last tenth of the frames.
- **Fit:** DP ms ≈ -28.6 + 0.00495 × primitives, R² 0.953.
  - Primitives alone explain 95 % of the frame-to-frame variance at 640x480.
  - The slope, 4.95 µs at the margin, is above the mean, so heavier frames cost more per primitive.
  - That fits large on-screen triangles adding raster waits, or a culled fraction that varies (inferred).
- **The runtime and the HAL cannot be split from this file.**
  - The primitive and software-vertex counts correlate at **0.994**; vertices per primitive are 1.19 ± 0.12.
  - The 3-variable fit (4.77 µs/primitive, 0.89 µs/vertex, -0.12 ms/call) is ill-conditioned. **No conclusion may
    be drawn from it.**
- **What reaches the HAL.** UT2003 clears twice a frame (CSV `Hardware Clear` = 1.99), so the context's 3985 clears
  ≈ 1992.5 frames ≈ the CSV's 1998. Per frame that gives:
  - **18,586 HAL triangles**, i.e. 63.3 % of the game's primitives. The rest are dropped by the runtime before DP2:
    off-screen trivial rejects, inferred;
  - **29.9 DP2 calls**, about 9.6 game DrawPrimitive calls per DP2 call (the runtime batches them);
  - an upper bound of **6.28 µs per HAL triangle**, if the runtime cost nothing.
- **The slow frames carry the run.** Frames over 150 ms are **49.7 %** of the run time; none is under 11.76 ms, and
  61 are under 23.5 ms. The worst frames are the ones with the most primitives (up to 70K).
- **UT2004 run 1** clears once a frame (inferred from 1069 clears in about 180 s at the stat-fps rate):
  - about 14.2K HAL triangles a frame at about 168 ms a frame;
  - **≤ 11.8 µs per HAL triangle at 1280x960**, about 1.9x UT2003's cost at 640x480 on the same map.

  Either the fill wait is not hidden at 4x the pixels, or the 8 bots cost CPU. **Unproven**, because the frame count
  is inferred.
- **UT2004 run 2's totals fit neither assumption.**
  - At one clear a frame they give 3.1K triangles a frame, which cannot take 170-250 ms at UT2003's per-triangle
    cost. **The driver must count frames**; that is §3.3.
  - **Halo** has the same problem: 764 clears in about 450 s of rendering would mean about 34K triangles and
    0.59 s a frame.
- **Logging volume.**
  - The ring's sequence moved from 97,382 to 207,568 between the end of UT2004 run 1 and the end of UT2003, about
    110K events in 424 s. That is at most about 55 a frame, if all fell in the 1998 frames.
  - At 5-15 µs per `VcrDd` IOCTL (perf-07, inferred) that is about **0.3-0.8 ms a frame: under 1 %**. G52 is not the
    bottleneck. Its cost is measured in S2, not assumed.
- **Texture traffic is negligible in this run:** 42 texture flushes in the whole session, and `Hardware Lock`
  0.012 ms a frame.

### 1.3 Where the time can go

| # | component | where | unit cost (all inferred until S2) | fixed by |
|---|---|---|---|---|
| C1 | the game outside D3D | game, user mode | 6.3 ms a frame, **measured** (§1.2) | not ours |
| C2 | the runtime's software vertex processing, clipping and DP2 build | `d3d8.dll`, user mode | 0.1-0.5 µs a vertex; 1-5 µs a clipped triangle | G57 (guard band: fewer clipped triangles); otherwise a hardware limit (G83) |
| C3 | system-call and dxg transitions, about 30 DP2 calls a frame | kernel | 5-20 µs a call | not needed |
| C4 | the HAL's CPU: walk, `compute_regs`, colour/UV maths, FPU save | `vcrdd_d3d.c`, `vcrdd_3d.c` | 0.1-0.3 µs a triangle; 1-3 µs per state change | G53, G60 |
| C5 | uncached writes: 27/36/45 per triangle, plus state | `vcrdd_3d.c:24-27`, `:183-239` | 45-150 ns each, posted | G58, G49, then G47 |
| C6 | status reads: `VcrDdRoom` before every vertex, 3 or more per triangle | `vcrdd_2d.c:92-108` | about 1 µs each, plus draining every posted write ahead of it | G48, then G47 |
| C7 | waiting for the chip to rasterise: `VcrDdRoom` spinning on a full FIFO | `vcrdd_2d.c:101-105` | (pixels a frame) / (166.8 MHz x px/clk), and only partly hidden | G50, G51; overlap with G47 |
| C8 | drains: `VcrDd2dSync` at Flip, Lock and TEXBLT | `vcrdd_ddraw.c:334`, `:658`; `vcrdd_d3d.c:1513`, `:1532` | the tail of the queued work, 1 µs or more | G54, G56 |
| C9 | log IOCTLs | `vcrdd_log.c:20-39` | 5-15 µs each, about 55 a frame or fewer (§1.2) | G52 |
| C10 | state and target re-sent at every DP2 call and change | `vcrdd_d3d.c:1322-1365` | 19-30 writes plus 2-4 reads | G53 |

**One more consequence (inferred, general NT DDI).** dxg calls the DP2 and DirectDraw callbacks with the display
device lock held. If the HAL's time really is most of the frame, the game holds win32k's display lock for most of
every frame, and every other GDI user waits:
- the agent's `SCREENSHOT`;
- `vcrctl fbshot`.

That is the "normal-priority work crawled" and "fbshot blocked on the display lock" of the Max Payne record (G04).
`D3DStats` reports that share directly as "HAL time / frame time".

## 2. Hypotheses and how each would show

| id | hypothesis | S1 shows | S2/S3 show | means |
|---|---|---|---|---|
| **H1** | **transport-bound**: the HAL's uncached writes and status reads (C5+C6) | the game thread at ≥ 70 % kernel time | most of the HAL time on writes and reads; few extra spins; d3dprobe `setup` µs/triangle times HAL triangles ≈ HAL time | G48 + G58 first, then G47 |

| **H3** | **runtime-bound**: software VP or clipping (C2) | user time ≥ 50 % of DrawPrimitive | the S3 ceiling barely rises; `fan_imm` share high if it is clipping | G57 if clipping; otherwise a hardware limit (G83) and detail settings |
| **H4** | **HAL CPU-bound** (C4, C9, C10) | kernel-heavy | HAL time well above (reads x t_r + writes x t_w); many `compute_regs`/re-sends or log IOCTLs | G52, G53, G60 |
| **H5** | **drain-bound** (C8) | kernel-heavy | Flip/Lock time ≥ 5 % of the frame | G54, G56 |
| **H6** | **game-bound** (C1) | user time in the game's own modules | already ruled out for UT2003: 6.3 ms of 123 (§1.2) | not ours |

H1 and H2 are expected to mix, weighted by resolution. The point of S2 is the weights.

## 3. Instruments

### 3.1 S0: `KMD/tools/ue2stats.py` (host; prototyped for this design)

- **Input:** a UE2 `stats-*.csv[.gz]` from UT2003 or UT2004 `-benchmark`.
  - The first header row starting `Frame Frame` is the column list. A name that repeats is (count, ms).
  - Optionally also: the session's `context N gone` line from a decoded ring, `--clears-per-frame`, and a
    `cputimes` CSV (§3.2).
- **Output:** JSON.
  - frames, fps from the frame times, frame-ms percentiles;
  - DrawPrimitive ms and share, game ms (frame minus DrawPrimitive);
  - primitives, software-processed vertices and calls a frame, µs per primitive, the one-variable fit with R², and
    the primitive/vertex correlation (which states that the split is impossible from this file);
  - given the ring: HAL triangles and DP2 calls a frame, and the µs-per-HAL-triangle bound;
  - given cputimes: the kernel and user milliseconds a frame (§3.2).
- **Test:** §8.1. The committed UT2003 CSV must reproduce §1.2's numbers.

### 3.2 S1: `KMD/tools/cputimes.c` → `out/cputimes.exe` (user mode, no driver change)

```
cputimes.exe <image name> <out.csv> [--period-ms 1000] [--max-s 1200]
```

- **What it does:**
  1. Waits for the process to appear (Toolhelp32 snapshot).
  2. Every period writes one row: QPC seconds, the process's user and kernel ms (`GetProcessTimes`), the busiest
     thread's id, user and kernel ms (`OpenThread(THREAD_QUERY_INFORMATION)` + `GetThreadTimes`), the thread
     count, and the system's busy share (`GetSystemTimes`, XP SP1+).
  3. Exits when the process does.
- **Why the split is direct:**
  - DP2, Clear2, Flip and Lock run synchronously in the calling thread, in kernel mode (win32k → dxg → `vcrdd.dll`),
    so our HAL's time, spins included, is that thread's **kernel** time.
  - The D3D8 runtime's vertex processing and clipping run in `d3d8.dll`, i.e. **user** time (inferred, general NT).
  - Together with §3.1's per-frame numbers this splits DrawPrimitive's 116.7 ms into "HAL + transitions"
    (kernel) and "runtime" (user minus the game's 6.3 ms).
- **Accuracy.** XP charges thread time in clock ticks (15.6 ms, inferred). Over a 245 s flyby the per-second
  medians are good to a few per cent. The analysis uses the seconds where the process held ≥ 90 % of the CPU (the
  steady state), not the loading.
- **Safety:**
  - it needs only query rights;
  - no GDI, no escape, no display lock;
  - it is not a `vcrctl`/ExtEscape tool, so the rule against those during a game does not apply.
- **Build:** `-O2 -Wall -march=i586 -DWINVER=0x0501 -D_WIN32_WINNT=0x0501 -static`, kernel32 only; listed under
  `LABS` in `KMD/Makefile` (as at `:97-106`).

### 3.3 S2: `Diag\D3DStats` – the driver's own split (log-only, default OFF)

This is the counter set the gap text assigns to G78 ("the driver counters (G78)"). G46 states what it needs.
- If G78's design defines the header and switch first, G46 uses them and adds only what is missing from this list.
- Otherwise G46 lands `KMD/include/vcr_d3dperf.h`, and G78 adds its vsync-on headroom accounting (refresh-unit
  buckets, on-time rate, perf §6.2) to the same struct.

**`KMD/include/vcr_d3dperf.h`** (new). Win32-free, integer-only (the display DLL is `-mgeneral-regs-only` except
`vcrdd_3d.c`) and host-tested, in the pattern of `include/vcr_flip.h`.

- `vcr_d3dperf` holds the per-PDEV accumulators below, with these functions:
  - `vcr_perf_frame(s, tsc_now)`, called at a frame boundary;
  - `vcr_perf_chip(s, regs[6])`, which accumulates each statistics register as `(now - last) & mask` with
    `mask` = (1 << `VCR_PERF_CTR_BITS`) - 1, default 24 bits (open question 1);
  - `vcr_perf_tsc_hz(dtsc, dqpc, qpf)`;
  - `vcr_perf_us(ticks, hz)`, 64-bit, no floating point;
  - `vcr_perf_any`;
  - `vcr_perf_reset`.

**Counted:** exact integers, one compare-and-add per event.

| group | counters |
|---|---|
| frames | **every** successful `Dd_Flip`, vsync'd or `DDFLIP_NOVSYNC` (the existing `vcr_flip_state.flips` counts vsync'd flips only, `include/vcr_flip.h:142-143`, and so read 0 for all four game sessions), plus every `Dd_Blt` whose destination is the primary (the D3D8 COPY swap effect presents by blit) |
| DDI calls | DP2 calls and command bytes; Clear2 calls and rectangles; Locks, and Locks whose `VcrDd2dSync` had to wait; TEXBLTs and bytes |
| triangles by DP2 op | TRIANGLELIST, STRIP, FAN, INDEXEDTRIANGLELIST, INDEXEDTRIANGLELIST2, INDEXEDSTRIP/FAN, **TRIANGLEFAN_IMM** (what the runtime's clipper emits, inferred: the G57 measure); skipped lines and points (shared with G16/G76) |
| triangles by stage count | 0, 1 or 2 textures (27/36/45 writes, `vcrdd_3d.c:183-239`) |
| register traffic | 3D writes, computed per call from the formulas (`tri()`: 3 x (8 + 3·t0 + 3·t1) + 3), so `vcrdd_3d.c` is untouched; `VcrDdRoom` calls (one status read each) and **extra reads** (the loop index `i` at its return, `vcrdd_2d.c:101-105`: FIFO-full spins); `VcrDd2dSync` calls that waited and their reads |
| state | `compute_regs` calls, state re-sends (`VcrDd3dState`), target re-sends (`VcrDd3dTarget`), texture flushes |
| logging | `VcrDd` calls that reached the IOCTL (a global in `vcrdd_log.c`, diffed per session) |
| hazard | DP2/Clear2 into `pd->flip_from` within one refresh of a vsync'd flip (perf-10, measured for G55) |

**Timed:** TSC, read after a `cpuid`.

- The TSC is read at entry and exit of `D3d_DrawPrimitives2`, `D3d_Clear2`, `Dd_Flip`, `Dd_Lock` and `Dd_Blt`, and
  at each frame boundary. That is about 70 reads a frame.
- **Why the `cpuid`:** `rdtsc` is not serialising on the Athlon XP (inferred). A bare one can retire before an
  uncached load ahead of it has returned, and would under-measure exactly the status reads in question.
- The TSC rate is taken against `EngQueryPerformanceCounter` at session start and at each log point. UT2003 itself
  reports 2006.73 MHz (`UT2003.log` CPU Speed).
- **Fine mode** (`D3DStats` bit 1, off by default) also brackets every `VcrDdRoom`, `VcrDd2dSync`, `VcrDd` and
  `compute_regs` call. It costs about 3-5 % (model) and is reported as such. It is for calibrating the coarse model,
  not for game runs.

**Per frame**, between two frame boundaries:
- a histogram of the frame time (ms buckets: < 12, < 24, < 48, < 96, < 192, < 384, < 768, ≥ 768);
- a histogram of the **HAL share**, in deciles: (DP2 + Clear2 + Flip + Lock + Blt time) / the frame time.

The HAL-share histogram is also the display-lock hold share (§1.3).

**Chip counters** (VSA-100 only, D3DStats only, never while `pd->exclusive_pid` is set):
- what is read: chip 0's `fbiPixelsIn` 0x14c, `fbiChromaFail` 0x150, `fbiZfuncFail` 0x154, `fbiAfuncFail` 0x158,
  `fbiPixelsOut` 0x15c and `fbiTrianglesOut` 0x25c (3D offsets).
- how they were derived: from `GL5/incsrc/h3regs.h:365-411` and cross-checked against `include/vcr_3dregs.h`
  (`V3D_C1` 0x148, `V3D_FOGTABLE` 0x160, `V3D_SSETUPMODE` 0x260).
- when they are read: in `Dd_Flip` **after** its existing `VcrDd2dSync` (`vcrdd_ddraw.c:334`), so the chip is idle
  and each frame's totals are exact.
- cost: six uncached reads, about 6-12 µs a frame.
- what they give: pixels a frame, overdraw, Z and alpha rejects, and a raster estimate.
- reset: never. Glide resets them with `nopCMD` = 1 (`GL5/glide3/src/gsst.c:3492-3499`) and the HAL writes
  `nopCMD` = 0 only, so the driver takes differences.

**Logged:** a new 5xx display event, `VCR_EV_DD_D3DPERF`. It takes the next free code at implementation, because
514 is claimed by both G02 and G04. It goes out as INFO lines at the points the flip counters already use:
- context gone (`ctx_free`, `vcrdd_d3d.c:1210`);
- "mode off";
- "DD local gone" (`vcrdd_ddraw.c:277-313`).

Each session is logged once (`vcr_perf_any`, as `vcr_flip_stats_any`). The lines carry:
- frames, session ms, DP2 calls, triangles;
- the HAL µs split (DP2, Clear2, Flip, Lock);
- reads (room calls, extra reads, sync calls, sync reads);
- triangles per op, and per stage count;
- writes (K);
- state (compute_regs, re-sends, target re-sends, flushes);
- chip pixels in and out (K), Z and alpha fails, triangles out;
- the two histograms;
- log IOCTLs, draws into `flip_from`, and the TSC MHz.

`tools/vcrlog.py` names the event from the X-macro on its own (`include/vcr_events.h` header). The summaries land at
session end, so they survive in the last 1024 ring entries that the on-box tools already fetch after each game
(onbox §6). Per-frame data never goes to the ring (G76).

**Live reading (optional, with G04).** If G04's heartbeat (`Diag\Live\D3DBeat`, a volatile registry value written
once a second) lands, the same IOCTL also writes a second value, `Diag\Live\D3DPerf`, with this second's counters.
The agent's `REGREAD` can then watch a running game with no escape and no display lock.

**Switch:** `Diag\D3DStats` (DWORD): bit 0 is the counters, bit 1 the fine timing. Absent means 0, i.e. off.
- **When it is read:** at every `IOCTL_VCR_INFO`, as `Accel2DText` and `DdHeapFloor` are (`miniport/vcrmp.c:447-466`).
  A game's own mode switch, which makes a new PDEV, picks it up.
- **How it reaches the DLL:** a new field appended to `vcr_info`, `d3d_perf`, which also carries the PerfTest level
  below. Bit 0x8000 of the flag word is already claimed by five other designs.
- **Older miniport:** `VcrDd2dInit` (`display/vcrdd_2d.c:443`) reads the field only when `info.size` covers it, so
  an older miniport means off.
- **Armed:** the DLL logs INFO "armed: D3D counters (Diag\D3DStats), log-only".
- **Off:** one predictable branch per DDI entry point. No `cpuid`/`rdtsc`, no statistics read, no event.

**Cost when on (model):**
- about 70 `cpuid`/`rdtsc` pairs and 6 uncached reads a frame;
- a few integer adds per triangle (op and stage bins, write formula), well under 1 % at today's ~6 µs per triangle.

§8.2 measures it with a d3dprobe A/B and sets a 1 % budget.

### 3.4 S3: `Diag\D3DPerfTest` = 1 – triangles not sent (3dfx's own `TRI_NULL`)

**Precedent.** The vendor HAL had build-time performance modes:
- `PCI_NOP` 1, `PCI_NULL` 2 and `TRI_NULL` 3 (`VH5/D3GLOBAL.H:731-734`). `TRI_NULL` makes the DP2 triangle
  handlers return before any work (`VH5/D6TRI2I.C:256-280`, `VH5/D6FANI.C:208-233`, `VH5/D6STRIPI.C:257-281`).
  `PCI_NULL`/`PCI_NOP` replace every packet write with nothing or a FIFO NOP (`VH5/D6TRI2I.C:218-231`).
- a `NULLDRIVER` build with per-area overrides "for doing wb99 performance analysis" (`VH5/D3TXTR.C:330-338`,
  `VH5/D3INIT.C:1955-1975`, `VH5/D3GLOBAL.H:1488-1495`).
- per-entry-point call-count, total-time and queue-time instrumentation (`VH5/DXINS.H:74-140`, used at
  `VH5/D6DP2.C:1221-1237`).

`D3DStats` is our version of that instrumentation, and `D3DPerfTest` = 1 is our `TRI_NULL`.

**Behaviour:**
- `tri()` and `imm_tri()` (`vcrdd_d3d.c:1367-1381`) count the triangle per op and stage, then return **before**
  `prepare()`. There is no `compute_regs`, register write, status read or flush for triangles.
- The walk, state tracking (`set_rs`), Clear2 (the fastfill), TEXBLT, Lock and Flip run as always.
- The screen shows only the clear colour.
- A game's frame rate then holds everything except the HAL's per-triangle work: game + runtime + walk.
  **This is the frame-rate ceiling any transport fix (G47/G48/G49/G58) can reach.**

**Values 2 and 3** are reserved for `PCI_NULL` and `PCI_NOP`. They are not built in this design. The counts times
the S2 unit costs (§5.2) give the bus/CPU split inside the HAL. Build them only if that model fails to reconcile
with the S1 kernel time to within 10 %. That needs a second emitter, and the proven one stays untouched.

**A one-boot switch:**
- The miniport reads `D3DPerfTest` at boot, next to `D3DBigTex` (`miniport/vcrmp.c:244`), and accepts only 1.
- It writes the value back to 0 at once and flushed, with `VcrDiagSet`, as the boot bookkeeping does at
  `vcrmp.c:95-112`.
- It logs a WARN at boot.

So an arm that is forgotten costs one boot of undrawn Direct3D, never more.

**Loud:**
- `VcrDd2dInit` logs a WARN: "D3DPerfTest 1: Direct3D triangles are NOT drawn this boot".
- `D3d_ContextCreate` logs the same WARN for every context.
- d3dprobe `render` fails visibly, every triangle check, as in the stale-FIFO case.

**Never default.** Diagnostic only; it is never in the game library's or the battery's normal state.

### 3.5 d3dprobe perf modes (code owned by G74/G78; specified here)

`d3dprobe perf --mode M` keeps today's scene as `--mode classic`, the default, for continuity with
`silicon_battery.py:256-258`. Every mode uses `--full --novsync` and runs a timed loop, then **one verification frame**
whose back buffer is locked and checked against analytic values. A run that drew nothing therefore never reports a
speed.

| mode | draws | reports | verification (reference value) |
|---|---|---|---|
| `setup` | `--tris N` (default 20,000) tiny primitives from a static `D3DPOOL_SYSTEMMEM` vertex buffer. Each cell is a 2x1-pixel quad, (x-0.5, y-0.5)-(x+1.5, y+0.5) in XYZRHW, so with the HAL's 0.5 centre it covers exactly pixels (x, y) and (x+1, y). Drawn as `--prim list\|strip\|fan\|ilist` with `--tex 0\|1\|2` (MODULATE, point sampled); `D3DRS_CLIPPING` FALSE, Z off, cull none. | µs per triangle, triangles/s, frames | lit pixels == 2 x quads, exactly; a triangle missing or doubled moves the count |
| `fill` | `--layers L` full-screen quads (2 triangles), `--tex 0\|1\|2`, `--blend` | Mpix/s, px/clk (core clock from `vcrctl clock` read before the run, never during) | every pixel == the last layer's colour; **with `D3DStats` on, Σ `fbiPixelsIn` over the timed frames == W x H x L x frames** (the analytic reference that settles the counters' width and meaning, open question 1) |
| `xform` | the `setup` cells as untransformed XYZ with an identity view and a projection onto the same pixels; software vertex processing; `--light 0..8` | µs per vertex for the runtime's transform (user time) | the same lit-pixel count as `setup` |
| `clip` | `xform` with every cell straddling a viewport edge | µs per clipped triangle; the HAL sees `TRIANGLEFAN_IMM` | the inside part of each cell is lit, the outside is not |
| `game` | a fixed synthetic UE2-like frame: about 20K indexed triangles in 30 `DrawIndexedPrimitive` calls from static VB/IB, untransformed, perspective, 2 stages (MODULATE), Z on, about 400 state and 60 texture changes, 30-80 px triangles, one clear | fps (novsync): the stable before/after benchmark for G47-G51 | 16 probe pixels against analytically computed colours of the Z-ordered layers |

`d3dprobe_run.py` passes `--mode/--prim/--tex/--tris/--layers/--light` through, keeping its monitor gate and pace.

### 3.6 Optional: `KMD/tools/procprof.c` (only if S1 shows ≥ 40 % user time)

This is an outside-the-process cousin of the ICD's render-thread sampler (`voodoo-cleanroom/CHANGELOG.md:292-311`,
`fxprof.c`).
- A TIME_CRITICAL thread suspends the game's busiest thread about once a millisecond, records `EIP` with
  `GetThreadContext`, and resumes it.
- A sample in kernel mode shows as `ntdll!KiFastSystemCallRet`, so the histogram by module also gives the kernel
  share independently.
- It names the hot spots inside `d3d8.dll`, transform against clipping. That matters only for H3.

### 3.7 `KMD/tools/d3dperf.py`: the split, the verdict, the what-if

- **Input:** a decoded ring (or `vcrlog.py fetch` output), plus optionally `ue2stats.py` JSON and a `cputimes` CSV.
- **Output:** the table of §5.1, a verdict per §5.3, and the what-if column of §5.2.
- Pure Python, host-tested (§8.1).

### 5.2 Unit costs and the what-if model

**From `setup`.** The time per triangle at 27/36/45 writes gives the cost per write as the slope.
- All three shapes read status 3 times per triangle (confirmed by the counters), so the intercept holds
  3·t_r + the HAL's CPU.
- S3's `setup` under `D3DPerfTest` = 1 gives the CPU part, and so t_r.
- Caveat: a status read waits for every posted write ahead of it (PCI ordering, inferred). So t_w and t_r are
  **effective** values for this access pattern, which is the one the fixes change.
- `strip` versus `list` shows today's expansion costs nothing extra per triangle. That is the baseline G49 is
  measured against.

**From `fill`.** Textured px/clk at 0/1/2 stages; G50's question.

**From `xform` and `clip`.** The runtime's µs per vertex and per clipped triangle; the H3 terms.

**The what-if column (model).** `d3dperf.py` applies each candidate fix to the measured per-frame counts:

| fix | change applied to the counts |
|---|---|
| G48 credit-based room checks | status reads per triangle from today's to about writes/31 |
| G58 packed colour + no duplicate `sOow1` | -9 writes per triangle (-12 with 2 stages) |
| G49 strip/fan continuation + autostrip | for the op share that can continue, writes per triangle from 3x(v+1) to (v+1) |
| G53 shadows | state re-send writes x (1 - redundant share); this needs the fine mode's re-send diff |
| G52 log gate | -log IOCTLs |
| G57 guard band | -clipped triangles x the runtime's clip cost |
| G50 2PPC | 0/1-stage raster halved; only the un-hidden part (FIFO-full spins) counts |
| G47 CMDFIFO | reads → ~0; writes at the write-combined rate measured by `upload`/TEXBLT, or 100-200 MB/s (model); frame ≈ max(CPU, GPU) instead of their sum |
| G51 SLI | raster ÷ 3.4 (the measured Glide scaling, perf §3.3) |

It prints the predicted frame time after each fix, cumulatively, in the order §6 proposes. That makes the order a
number, not a preference.

## 6. The likely fixes, in the expected order (each owned by its own gap)

The order is inferred and stays so until §5 is measured. Gains are model numbers for UT2003 at 640x480.

1. **G52** log gate (trivial, ~0.5 ms) and **G48 + G58** (packed `sARGB`, one status read per FIFO fill, no
   duplicate `sOow1`).
   - Both are direct-path changes behind their own switches (perf P1/P3).
   - Model: HAL 6.3 → about 3.5-4.5 µs per triangle. **UT2003 9.4 → about 13-17 fps.**
2. **G50:** 2PPC, band and column band. About 2x single-texture fill. This matters at 1280x960 and is small at
   640x480.
3. **G47:** command FIFO + packet 3 (XL; perf P6, host-tested GBK code to reuse).
   - Model: HAL about 0.5-1 µs per triangle, with CPU and chip overlapped.
   - **UT2003 → about 30-45 fps; ceiling = S3.**
   - G49 and G54/G56 then ride the FIFO.
4. **G51** SLI for D3D where fill remains the limit (1280x960 titles). Supervised; last.
5. **G57** guard band, if `fan_imm` is significant; **G53** shadows when state becomes a visible share after G47.

**Hardware limit (G83).** The Athlon XP's software vertex processing is a floor no driver change removes. S1 and S3
measure it, and §5's verdict says when it is the limit.

## 9. Risks to proven paths

- **The default 16 bpp path and fresh installs.** With both switches absent nothing changes:
  - no register traffic and no read;
  - one predictable branch per DDI call;
  - an integer add at `VcrDdRoom`'s and `VcrDd2dSync`'s returns;
  - `vcrdd_3d.c` untouched (§8.1-2).
- **Glide/OpenGL coexistence.**
  - The statistics reads are skipped while `pd->exclusive_pid` is set.
  - They happen only inside a DirectDraw `Dd_Flip`, which a Glide game does not call.
  - `D3DPerfTest` affects only `tri()`/`imm_tri()`.
- **SLI state.** D3D is single-chip; only chip 0 is read. An SLI-enabled board (not reachable from D3D today) would
  read chip 0's share.
- **The flip path.** Six reads after the existing drain delay the start-address write by about 6-12 µs. That is far
  inside a refresh, and the vsync'd completion rule (`vcr_flip.h`) is unchanged.
- **Measurement perturbation.**
  - `cpuid` and `rdtsc` at entry points: about 70 a frame.
  - The fine mode is reported as 3-5 % and used only for calibration.
  - `cputimes` samples once a second.
  - `procprof` costs about 1 % (the ICD sampler's figure) and is optional.
- **`D3DPerfTest` forgotten:** one boot of undrawn D3D at most (it clears itself), and WARN lines everywhere.
- **Box stability.** The runs are the kind made on 11-12, which had no hang in 13 probes and 4 games.
  - UT2004's `-benchmark` never ends at these rates, so use the console `exit`.
  - Halo is capped at 300 s.
  - Max Payne only attended.
  - A Glide session in between voids the baseline (§4).

## 10. Open questions

1. **Are `fbiPixelsIn`/`Out`, `ZfuncFail`, `AfuncFail` and `TrianglesOut` 24-bit on the VSA-100?**
   - Do fastfill clears count in `fbiPixelsIn`?
   - Does anything but `nopCMD` bit 0 reset them?

   `perf --mode fill` (L = 0, 1, 8) settles all three against W x H x L.
2. **Is the `cpuid`-serialised TSC at the entry points accurate enough?** S1's kernel time against D3DStats' HAL

   scaling has to use UT2004 or UT99.

   once G65 changes the staged one.
5. **Does UT99 436's D3DDrv run on vcr-kmd on silicon?** It is needed for the vendor comparison. Unreal Gold's ran
   on 86Box.
6. **How many frames did UT2004 run 2 and Halo actually render?** The clear-based counts in §1.2 contradict each
   other. The frame counter answers it at the next run.
7. **Is the runtime's processor-specific geometry pipeline active on the Athlon XP?**
   `HKLM\Software\Microsoft\Direct3D\DisablePSGP` should be absent. This decides how large H3 can be; `procprof`
   shows it.
8. **Will the operator take S3** (one more boot, all D3D undrawn for it), or the per-PDEV `D3DStats` changes between
   titles without a reboot?
9. **A UT2003 flyby on the vendor HAL** would be the cleanest reference. It needs a driver-stack swap on `.124` and
