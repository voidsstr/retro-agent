## 0. Verdict

1. **The code gap is real.**
   - `prim_caps` advertises `D3DPTEXTURECAPS_TRANSPARENCY` (`KMD/display/vcrdd_d3d.c:2034-2035`).
   - Nothing in `vcrdd_d3d.c` or `vcrdd_3d.c` reads `D3DRENDERSTATE_COLORKEYENABLE`, `DDRAWISURF_HASCKEYSRCBLT` or `ddckCKSrcBlt`.
   - `V3D_CHROMAKEY` and `FZ_CHROMAKEY` are defined (`KMD/include/vcr_3dregs.h:32, 107`) but never used.
   - Keys exist only for DirectDraw blits (`KMD/display/vcrdd_ddraw.c:431-434, 536-539`).
   - So a DX5/6/7 application that keys a texture gets its key-colour texels drawn opaque.
2. **The hardware does it in one pass.** The FBI chroma key (`fbzMode[1]` plus the `chromaKey` register) runs after the texture lookup and before the colour combine and fog (SPEC L3224, L3520).
   - The same compare is most likely already exercised on `.124` under our Glide: the UE1 Glide renderers of Unreal Gold, UT 436 and Deus Ex import `grChromakeyValue`/`grChromakeyMode` (`i686-w64-mingw32-objdump -p` on `LIB/UnrealGold/System/GlideDrv.dll`, `LIB/UnrealTournament436/System/GlideDrv.dll`, `LIB/DeusEx/System/GLIDEDRV.DLL`). That they enable it for masked surfaces during play is inferred.
   - The known limit is that the test runs after the bilinear filter.
3. **The visual evidence cited for this gap (visual-07) does not show a colour-key failure.** `FBS/thief2_c2.png` (Thief II's DX6 path, 640x480x16), brightened 8x:
   - The tree beside the wall is an organic, pixel-accurate leaf-and-twig cut-out, and the wall and slab show through between its branches.
   - The bushes on the right are polygonal meshes.
   - Both are filled with a flat (0,0,8).
   - A key the HAL ignores draws the key-coloured texels **as solid rectangles around every leaf billboard**. Here the transparent texels are correctly dropped; only the colour inside is wrong.
   - That fits a combine fault (a `SELECTARG1(TFACTOR)` stage or an alpha-only texture pass: G12/G14) or vertex fog at full density (G32) far better than G09.
   - The Dark engine's own docs call its "chroma key" textures **1-bit alpha** (`LIB/Thief2/doc/new_config_vars.txt:191-201`), and `THIEF.EXE` (Thief Gold) holds no colour-key string at all.
   - So visual-07 should be re-routed (section 9, Q5), and it is not evidence for this design.
4. **Which titles really key textures is unmeasured.** The best leads are string evidence:
   - **Aliens vs Predator**: its texture loader has the error context "setting the colour key" next to `awtexld.cpp`, and its caps dump prints "Does %s support texture transparency". The likely behaviour is that it keys textures exactly because we advertise the cap (inferred).
   - **Rainbow Six**: `Surface::SetTransparentValue`, `colorkey`.
   - **Jedi Knight and MotS**: only the generic `DDERR_COLORKEY*` name table, which is not evidence.
   - Shogo has no colour-key string. Hidden & Dangerous Deluxe is D3D8, which has no colour keys.
5. **Recommendation.** Implement it the way 3dfx's V5 HAL meant to, avoiding the bug that made 3dfx's version unreachable (section 1.4):
   - single pass on the FBI chroma key;
   - behind a default-off `Diag\D3DFeat` bit;
   - with usage counters that run even while the bit is off, so the first boot of this build measures exposure at zero risk.
   - **Priority P1:** a likely visible defect in AvP and Rainbow Six, plus an advertised cap that steers AvP's loader. Escalate to P0 if the counters show keyed draws in common scenes.

## 1. What was read, and what it settles

### 1.1 Direct3D semantics (W2K DDK `d_grafx.chm`, page `D3DRENDERSTATE_COLORKEYENABLE`)

- "Color-key is enabled with the AND of the render state enable and the DDRAWISURF_HASCKEYSRCBLT bit in the surface ... it needs to be okay for apps to leave the render state true all the time and still selectively use color-key for a subset of a frame's textures ... It is up to the driver to correctly handle this behavior."
- `D3DRENDERSTATE_COLORKEYBLENDENABLE` (144) "pertains only to devices which accelerate transform and lighting". We are not one, so it is ignored and counted only.
- The NT DDK header names the surface-local field "color key for source blt **and texture use**" (`KMD/out/ddi/ddrawint.h:743`, `DD_SURFACE_LOCAL.ddckCKSrcBlt`). The key format is the texture's own pixel format.

### 1.2 Hardware (SPEC, plus the 86Box model as a cross-check)

- **SPEC L3224:** fbzMode bit 1: "any source pixel matching the color specified in the chromaKey register is not written ... The chroma-key color compare is performed immediately after texture mapping lookup, but before the color combine unit and fog".
- **SPEC L3520-3527:** the alpha component is ignored by the match. `chromaKey` holds blue in [7:0], green in [15:8] and red in [23:16].
- **SPEC L3530-3547 (`chromaRange`):**
  - bit 28 turns the key into a range test;
  - bits 30:29 = 3 together with `combineMode[30]` = 0 is the TMU's **texture** chroma substitution (SPEC L2825, L3534);
  - `combineMode[30]` must be set for the new combine units, after which substitution is unavailable (SPEC L6248).
- **86Box** (`86B/voodoo_render.c:1089-1120`):
  - The compare is against `c_other`, the colour-combine unit's RGB-select output. With `rgbselect = TMU` that is the texel coming out of the TMU.
  - A match jumps to `skip_pixel`, which is before the depth write (`:1349-1364`). So a keyed pixel writes neither colour nor Z (inferred for silicon).
  - 16-bit texels are expanded by MSB replication (`86B/vid_voodoo.c:1267-1279`), which is the same rule 3dfx's HAL uses for the key (`VH5/D3TRI.H:231` `_imgMSBReplicate`).
- **Chip field:** `SST_CHIP(sst, n)` = n*0x400 (`GL/incsrc/h3defs.h:2087`), with `eChipFBI = 1` (`GL/glide3/src/fxcmd.h:585`). An FBI-only PIO write is therefore at 3D offset `0x400 + reg`. Our HAL already uses the TMU0/TMU1 forms, 0x800 and 0x1000 (`KMD/include/vcr_3dregs.h:17-18`).

### 1.3 What our HAL does today

- `compute_regs` (`vcrdd_d3d.c:921-1029`) builds:
  - `fbzMode` = RECTCLIP | RGBWRITE, plus dither and depth bits;
  - single stage: TMU0 `REPLACE` (`:962`) and the stage-0 op in the FBI CCU, with the texel on the CCU's "other" input whenever the op uses the texture (`color_path`, `:676-745`);
  - two stages: TMU1 samples stage 0, TMU0 combines stage 1 (`:950-960`), so the FBI's "other" is the stage-1 result.
- `ctx_defaults` zeroes `rs[]` (`:1128`), so COLORKEYENABLE starts FALSE. `set_rs` stores state 41 and marks the context dirty (`:1393-1406`).
- The register writer (`vcrdd_3d.c:74-129`) sends 8 FBI registers broadcast (chip field 0), then the fog table, then TMU0/TMU1.

### 1.4 3dfx's own HAL: the recipe, and a bug that made it unreachable

- **The recipe** (`VH5/D6DP2.C:6815-6967`):
  - when `pRc->colorKeyEnable` and the texture handle's `dwFlags & DDRAWISURF_HASCKEYSRCBLT`, the key's low value is expanded to xRGB888 per texture format;
  - it is written to the **FBI only**: "Only set the FBI. Don't write the TMU chromakey (its used for texturefactor)" (`:6943`, packet chip mask 0x1 on Napalm);
  - then `SST_ENCHROMAKEY` is set (`:6958`), and it is cleared when not texturing (`:6965`).
- **Single stage only:** "2 stage 'trilinear' or 'chromakey' isn't possible" (`VH5/D6MT.C:603`). PRS 12611 moved single-stage ops into the FBI CCU so the key sees the texel (`VH5/D6MT.C:80-82`).
- **Default and history:**
  - `colorKeyEnable = TRUE` at context init (`VH5/D3RSTATE.C:3709`).
  - The cap was removed for Napalm, "Napalm doesn't support texture chroma key" (`VH5/D3INIT.C:143-145`). That most likely refers to the TMU texture-space key, which the new combine mode disables (SPEC L6248, inferred).
  - It was re-enabled "for whql" (`VH5/D3INIT.C:99-100`).
- **The bug: the DX7 path could not fire.**
  - `ddiCreateSurfaceEx` fills `TXTRHNDL.dwFlags` from the **pixel format**: `pTxtrHndl->dwFlags = pDDSLcl->lpGbl->ddpfSurface.dwFlags` (`VH5/D7D3D.C:389`; also `W9X/DX/D3D/D7D3D.C:372`).
  - `D6DP2.C:6824` then tests `DDRAWISURF_HASCKEYSRCBLT` (0x800) against it.
  - In `DDPIXELFORMAT.dwFlags`, 0x800 is `DDPF_PALETTEINDEXED1` (`~/retro3dfx-toolchain/devtools/dx8ddk/inc/ddraw.h:3982`), which no texture this card offers ever carries.
  - The key is also captured only once, at CreateSurfaceEx (`VH5/D7D3D.C:402-403`), so a key set later is stale.
  - So "3dfx shipped FBI keying" says nothing about it ever running under the DX7 DDI. **Do not copy the cached flags. Read the surface local.**

### 1.5 Microsoft's NT sample (the documented pattern)

- `DDK/src/video/displays/3dlabs/driver/d3d.c:376-383` copies `lpSurf->dwFlags`, the **surface** flags, and the key from `ddckCKSrcBlt` at CreateSurfaceEx.
- `d3d.c:2195-2235` hooks `DdSetColorKey` (`DDHAL_SURFCB32_SETCOLORKEY`, `dd.c:1412-1413`) to refresh a key set after creation.
- The enable is the AND rule (`d3dhw.c:760-767`). Chroma keying starts off (`d3d.c:240`), and render states start zeroed.
- The sample also carries a disabled "alpha mapping to improve bilinear chroma keying" (`d3dhw.c:823`). The bilinear-fringe problem was known.

## 2. Approach

### 2.1 What is implemented

A draw is keyed when **all** of the following hold. The decision is one Win32-free function so it can be tested on the host:

| # | condition | where it comes from | reason code when it fails |
|---|---|---|---|
| 1 | `rs[D3DRENDERSTATE_COLORKEYENABLE]` != 0 | the DP2 render state (default FALSE, as now and as the MS sample) | `VCR_CK_NO_STATE` (not counted: the app did not ask) |
| 2 | the bound stage-0 texture's **surface local** has `DDRAWISURF_HASCKEYSRCBLT` | `t->dwFlags`, read live; never `ddpfSurface.dwFlags` (the 3dfx bug) | `VCR_CK_NO_KEY` |
| 3 | stage 0 is textured and sampled (`tex`) | `compute_regs` | `VCR_CK_NO_TEX` |
| 4 | one stage (`!two`) | the FBI sees TMU0's output, which with two stages is the stage-1 result | `VCR_CK_TWO_STAGE` |
| 5 | the colour path's "other" is the texel: `(fbzColorPath & 3) == CP_RGBSEL_TMU` | `color_path` | `VCR_CK_NOT_TEXEL` |
| 6 | the texture format can be matched: RGB565, ARGB1555, ARGB4444, ARGB8888 (and later RGB332, ARGB8332, I8/L8, AI44/A4L4, AI88/A8L8 when G34 offers them) | `textureMode` format field; compressed (`TM_COMPRESSED`) and palettized are refused | `VCR_CK_FORMAT` |
| 7 | `Diag\D3DFeat` bit CKEY is armed | `pd->d3d_ckey` | `VCR_CK_OFF` (counted as "would have keyed") |

**Key value:**
- `t->ddckCKSrcBlt.dwColorSpaceLowValue`, expanded to the xRGB888 the TMU emits:

  | format | expansion |
  |---|---|
  | 565 | r5 -> `r<<3 \| r>>2`, g6 -> `g<<2 \| g>>4`, b5 like r |
  | 1555 | 5-bit replicate per channel; the alpha bit is ignored, as the hardware ignores alpha |
  | 4444 | nibble x 0x11 |
  | 8888 | `key & 0xffffff` |
  | 332 and 8332 | 3/3/2-bit replicate, as `VH5/D6DP2.C:6864-6872` |
  | L8, AI88, AI44 | luminance replicated into R=G=B; masks `L8_LMASK` 0xFF, `LA16_LMASK` 0x00FF, `LA8_LMASK` 0x0F nibble-doubled (`VH5/D3GLOBAL.H:987-992`) |

- A colour-space key (high != low) uses the low value, as 3dfx did, and is counted and logged once. The exact range via `chromaRange` is a later option (Q7).

### 2.2 Register traffic

When a draw is keyed, and only then:

| step | register | value |
|---|---|---|
| 1 | `fbzMode` (broadcast, as now) | the usual bits **\| `FZ_CHROMAKEY` (bit 1)** |
| 2 | `chromaKey`, **FBI chip field**: offset `0x400 + 0x134` = `0x534` | xRGB888 key |
| 3 | `chromaRange`, **FBI chip field**: `0x400 + 0x138` = `0x538` | `0`: range off, so the test is an exact key, whatever a Glide session left in bit 28 |

- **Never broadcast.** Chip field 0 would also write both TMUs' `chromaKey`. That would disturb a stale texture-chroma substitution today (G03), and it would clobber TFACTOR once G14 keeps TFACTOR in the TMU `chromaKey`/`chromaRange` registers (3dfx's layout, `VH5/D6DP2.C:6943`).
- **Not keyed:** no new write, and `FZ_CHROMAKEY` stays clear. That is the current sequence, write for write.
- **Optional sub-bit CKEY_POINT** (default off even when CKEY is armed): a keyed draw clears `TM_MINFILTER | TM_MAGFILTER`. That gives exact, fringe-free keying at the price of blocky magnification (Q4).

### 2.3 Code changes, file by file

1. **`KMD/include/vcr_ckey.h`** (new, Win32-free, integer only):
   - `vcr_ckey_xrgb(unsigned textureMode, unsigned key, unsigned *xrgb)` returns 1 when keyable;
   - `vcr_ckey_why(rs_on, has_key, textured, two_stage, rgbsel, textureMode)` returns the reason codes above;
   - `#define VCR_CK_*`, `VCR_CK_WHY_MAX`.
2. **`KMD/include/vcr_3dregs.h`:** `#define V3D_FBI 0x000400u` (chip field: FBI only), `#define V3D_CHROMARANGE 0x138`.
3. **`KMD/include/vcr_3dseq.h`:** `#define VCR_3D_CKEY_MAX 2` and `vcr_3d_ckey_seq(unsigned xrgb, vcr_regw *w)`, which returns the two FBI writes of 2.2. It sits beside `vcr_3d_target_seq`, so the native test pins it write for write.
4. **`KMD/display/vcrdd_3d.h`:** `vcr3d_regs` gains `ULONG keyed, chromaKey;`.
5. **`KMD/display/vcrdd_3d.c` `VcrDd3dState`:**
   - right after the 8 base writes, add `if (r->keyed) { n = vcr_3d_ckey_seq(...); if (!VcrDdRoom(pd, n + 4)) return FALSE; write n }`;
   - the `+ 4` keeps room for TMU0's four writes, which follow without a check today (`:113-118`);
   - with `keyed == 0` nothing is added.
6. **`KMD/display/vcrdd_d3d.c`:**
   - **`compute_regs`:**
     - read `c->ck_has = tex && (t->dwFlags & DDRAWISURF_HASCKEYSRCBLT)` and `c->ck_lo = t->ddckCKSrcBlt.dwColorSpaceLowValue`;
     - `why = vcr_ckey_why(...)` with `v0.textureMode` (stage 0's format);
     - `r->keyed = why == VCR_CK_ON && c->pd->d3d_ckey`, and set `FZ_CHROMAKEY` and `r->chromaKey`;
     - apply CKEY_POINT;
     - count (2.4).
   - **`prepare`:** in the branch that drops texturing because the vertex lacks the coordinate set (`:1351-1356`), also clear `FZ_CHROMAKEY` and `regs.keyed`. With no texel, "other" is undefined.
   - **`D3d_DrawPrimitives2`:** before `walk()`, add `ckey_recheck(c)`:
     - when COLORKEYENABLE is on and a stage-0 handle is bound, `handle_get` the surface and compare its live `HASCKEYSRCBLT` and low key with `ck_has`/`ck_lo`; on a difference set `c->dirty = 1`;
     - an app's `SetColorKey` between two DP2 calls changes no render state, so nothing else would re-run `compute_regs`;
     - it uses `handle_get`, not the cached `c->tex_surf0`, which can dangle after a DestroySurface (`VcrDdD3dSurfaceGone`, `:148-160`, clears `rt`/`zb` only; that is noted for G43).
   - **`tri()` / `imm_tri()`:** `if (c->regs.keyed) c->ck_tris++`.
   - **Optional:** add `(r->fbzMode & FZ_CHROMAKEY)` to the `log_combo` hash and line, so a LogLevel 2 run lists keyed combinations.
7. **The Diag switch** (shared with the other D3DFeat items; whichever lands first creates it):
   - `KMD/miniport/vcrmp.c` reads `x->d3dfeat = VcrDiagGet(L"D3DFeat", 0)` **at boot**, like D3DBigTex.
   - It maps bit CKEY to `VCR_INFO_F_D3DCKEY` (0x8000, the next free flag) and CKEY_POINT to `VCR_INFO_F_D3DCKEYPT` (0x10000) in `fill_info`'s `v->flags` (`KMD/miniport/vcrmp.c:444-449`).
   - These are positive flags: an older miniport never arms them.
   - `KMD/include/vcr_ioctl.h` holds the defines.
   - `KMD/display/vcrdd_2d.c` `VcrDd2dInit` (`:442-467`) sets `pd->d3d_ckey` / `pd->d3d_ckey_point` and logs an "armed (Diag\D3DFeat)" event, like 513/18.
   - This works on any chip. The FBI key exists on Banshee/Voodoo3 too, so the 86Box bed can test it.
   - If D3DFeat later moves to an appended `vcr_info` field, `VcrDd2dInit` must `memset` the struct before the IOCTL. It is not zeroed today (`:436-443`).
8. **`KMD/include/vcr_events.h`:** document 513 `a=24` (colour key: b=handle c=key d=xRGB) and `a=25` (per-context colour-key totals).

### 2.4 Measurement that runs with the switch off

The decision runs on every `compute_regs`, armed or not. Counters live in `vcr_d3dctx`:
- `ck_state` (COLORKEYENABLE ever set);
- `ck_why[VCR_CK_WHY_MAX]`, counted only when the state is on;
- `ck_tris`;
- `ck_cspace` (high != low);
- `ck_blend` (COLORKEYBLENDENABLE set).

They are logged:
- **513/24 (INFO):** once per distinct (texture format, key) per context, at most 16, like `log_combo`.
- **513/25 (INFO):** at "context gone", beside the existing totals (`vcrdd_d3d.c:1212-1215`).

So the first boot of this build, with the bit **off**, tells which staged titles key textures. The register traffic is identical to today. This is the G09 slice of G76.

### 2.5 Caps

- **No change.** `TRANSPARENCY` stays advertised whether the bit is on or off, so the caps a DX5-7 application reads are byte for byte today's, and the switch only changes behaviour.
- D3D8/9 do not expose the cap and have no colour keys, so D3D8/9 titles are untouched by construction.
- No DirectDraw `DDCKEYCAPS` change; that is G61.
- **Rejected alternative:** withdraw the cap while the bit is off. It would be honest, and AvP's loader might then pick alpha formats. But it moves the default caps of every DX5-7 title without proof. It is kept as an experiment (Q8).

### 2.6 Single pass; what stays unkeyed (v1)

- **Two stages with a keyed stage 0** (`VCR_CK_TWO_STAGE`) draws unkeyed, as today, and is counted.
  - The FBI only ever sees the TMU0 combine, so this is impossible in one pass (3dfx said the same).
  - A two-pass emulation is out of scope unless the counters show a staged title doing it.
  - G15 should then answer `D3DERR_CONFLICTINGRENDERSTATE` for that combination; `vcr_ckey_why` is the shared rule.
- **The texel is not the CCU's "other"** (for example `SELECTARG1(DIFFUSE)` with a keyed texture bound): unkeyed and counted.
- **Not used:**
  - the TMU texture-space key (substitution), which disappears under `combineMode[30]=1`, the bit G12/G14 need (SPEC L6248), and is unproven on Napalm;
  - conversion of keyed texels to alpha 0 (a shadow-texture project; NewDark's `chroma_key_to_alpha` is the precedent);
  - P8 keys through the palette (G38).

### 2.7 The old path

With the bit off (the default): keys are ignored exactly as today, the cap is still advertised, and every register write is unchanged. The only addition is CPU-side counting in `compute_regs` (a few compares) plus one `handle_get` per DP2 call while COLORKEYENABLE is on.

## 3. Gating

- **Default-OFF** behind `Diag\D3DFeat` bit CKEY: read at boot, a positive flag, one Diag change per clean boot. CKEY_POINT is a second bit for the fringe A/B only.
- **When on, the proven paths are still unchanged.** A draw changes only if the application set COLORKEYENABLE **and** keyed the bound texture. No D3D8/9 title can do either, and DX5-7 titles that never key are untouched.
- **Not safe to land default-on yet:**
  - the FBI-only chip-field write (0x400) is new to this HAL;
  - whether XP keeps the kernel surface local's key current after `SetColorKey` is unproven (Q1).
- **Good candidate to flip default-on** right after one supervised clean boot passes the d3d7probe colour-key suite and one keying title confirms. Nothing outside keyed draws moves. That flip is a `MOVED_DIAG` entry with evidence (`REPO/tests/python/test_vcr_kmd_integration.py:86-91`).

## 4. The probe test (DX7: d3d7probe, from G75)

D3D8 has no colour keys, so the check lives in the DX7-interface probe G75 adds (`tools/d3d7probe.c`).

**Setup:**
- `DirectDrawCreateEx`, `IDirect3D7`, `IDirect3DDevice7` on `IID_IDirect3DHALDevice`;
- fullscreen 640x480x16 paced through `vcr_pace.h`, and 1024x768x32 when D3D32 is armed;
- readback by `Lock(DDLOCK_READONLY)` of the back buffer, top-left 256x256, the `expand()`/`expect()` scheme of `KMD/tools/d3dprobe.c:273-343`;
- `RESULT {json}`;
- build: `-lddraw -ldxguid -lgdi32 -luser32` (mingw has `d3d.h`/`d3dtypes.h` with `D3DRENDERSTATE_COLORKEYENABLE = 41`).

**Common scene:**
- clear to B = 565 (8,16,24), dithering off, Z off unless stated;
- a 16x16 texture in video memory over the 192x192 quad [32,224), 12 px per texel, 4x4-texel cells;
- cells K = key 0xF81F (expands to FF00FF), C = 0x07E0 (00FF00) and one near-miss cell N = 0xF81E (FF00F7);
- `SELECTARG1(TEXTURE)`, point filtering;
- every check is at the centre pixel of a cell.

| test | what changes | pass (reference) | old-buggy result |
|---|---|---|---|
| `colorkey` | key set at creation (`DDSD_CKSRCBLT`), COLORKEYENABLE TRUE | K centres = B exactly; C = 00FF00; **N = FF00F7** (exact compare, correct expansion) | K = FF00FF (key ignored) |
| `colorkey_modulate` | `MODULATE(TEXTURE, DIFFUSE)`, diffuse 0x808080 | K = B (the compare is before the combine); C = 008000 at d3dprobe `modulate`'s tolerance | K = 800080 |
| `colorkey_rsoff` | key set, COLORKEYENABLE FALSE | K = FF00FF (the AND rule) | same |
| `colorkey_default` | key set, render state never touched | K = FF00FF (DX7 default FALSE, our `ctx_defaults` FALSE) | same |
| `colorkey_late` | texture drawn once unkeyed (so it is named), then `SetColorKey(K)`, next frame | K = B (**answers Q1**) | K drawn |
| `colorkey_change` | frame 1 key K, frame 2 key C | frame 2: C cells = B, K cells = FF00FF (DP2 recheck) | frame 2 unchanged |
| `colorkey_remove` | after a keyed frame, `SetColorKey(NULL)` | K = FF00FF | n/a |
| `colorkey_z` | Z on, LESSEQUAL, write on: keyed quad at z=0.2, then a red quad at z=0.5 | K = FF0000 (keyed pixels wrote no Z); C = 00FF00 | K = FF00FF |
| `colorkey_1555`, `colorkey_4444`, `colorkey_8888` | same scene per format; keys 0xFC1F, 0xFA5A, 0xFF123456; near-miss one LSB off | K = B; N drawn | for 4444, a shift-only key (A050A0) would never match AA55AA: K drawn |
| `colorkey_filter` | 8x8 texels, MAG LINEAR, a 2x2 keyed block in the middle | the block's centre = B; pixels more than 1 texel from the block = C. Fringe pixels (neither B nor C) are **counted and reported**, not judged. With CKEY_POINT armed: fringe = 0. | centre = FF00FF |
| `colorkey_twostage` | stage 1 `MODULATE` with a white texture | v1: reported as `"limitation": "two-stage"`, neither pass nor fail. After G15: `ValidateDevice` fails. | n/a |

- Each test is **SKIPPED**, not failed, when its format is not offered.
- The RESULT carries `ckey_armed` from the HAL's armed event, so a run with the bit off is a deliberate reproduction of the old behaviour: the K cells drawn are the "before" values.
- **Leak check in d3dprobe (D3D8), same boot:** run `d3dprobe render --full` (the default 40-test matrix) right after the d3d7probe suite. It must stay 40/40. `fbzMode` is rewritten at every state flush, so a keyed state cannot leak into the next context; this pins that on silicon.

### 5.1 `REPO/tests/native/test_vcr_kmd_ckey.c` (new)

## 7. Risk to proven paths

| path | risk |
|---|---|
| **default 16 bpp D3D (bit off)** | none: identical register traffic; counting is CPU-only |
| **D3D8/9 titles (bit on)** | none by construction: no colour keys exist in D3D8/9; the leak check pins it |
| **DX5-7 titles that do not key (bit on)** | none: the AND rule stays false |
| **keyed draws (bit on)** | visual only, bounded to keyed textures: a wrong key either fails to kill (today's look) or kills texels of the key colour. A chroma kill is a plain pixel-pipeline reject, with no hang mechanism (inferred). Bilinear fringes are a known hardware limit (Q4). |
| **Glide/OpenGL coexistence** | Glide's open resets chroma mode, range and texture chroma (`GL/glide3/src/gsst.c:909-911`) and writes its own key when used (`distate.c:2226-2260`), so our leftover FBI values are harmless. The reverse (a stale FBI `chromaRange[28]` from Glide) is neutralised by our `chromaRange = 0` on keyed draws. A stale Glide `combineMode[31]` would re-route the CCU's "other" and so the compare's input; that is G03's baseline, and the reason for cold-boot testing. |
| **SLI** | D3D is single-chip today (G51). When G51 lands, the two FBI writes must reach every chip the same way its other 3D writes do. |
| **future combine work (G12/G14)** | G14 must write TFACTOR to TMU chip fields only; a broadcast write would clobber the FBI key. G12 must keep the "other is the stage-0 texel" rule in combineMode terms (`cc_otherselect` = texture RGB) for single-stage keyed draws, as 3dfx's CCU tables do (`VH5/D6MT.C:603`). |
| **flip path / 2D** | untouched |
| **kernel safety** | only documented `DD_SURFACE_LOCAL` fields of a surface found through the handle table (the same pattern `compute_regs` uses), with no new cached pointer |
| **CPU cost** | 2 PIO writes per keyed state flush (not per triangle); one hash lookup per DP2 while COLORKEYENABLE is on |

## 9. Open questions (each with the experiment that settles it)

1. **Q1: Does XP keep `DD_SURFACE_LOCAL.ddckCKSrcBlt` / `HASCKEYSRCBLT` current** after a `SetColorKey` on an already-named texture, and after `SetColorKey(NULL)`?
   - Settled by d3d7probe `colorkey_late`/`_change`/`_remove`.
   - If not: add a `DdSetColorKey` surface callback behind the same bit, as Microsoft's sample does (`DDK/.../d3d.c:2195-2235`). It records the key per handle entry, and the vendor's NOTHANDLED/`DD_OK` return (`VH5/DDSURF.C:2467-2479`) keeps the runtime's own handling.
2. **Q2: Do the DX5 execute-buffer titles (JK, MotS, R6) ever send COLORKEYENABLE?** Wine's ddraw starts it TRUE for version-1 devices (inferred, from memory of Wine's source), and 3dfx defaulted TRUE, but the runtime may never forward that initial value.
   - Settled by 513/25 `ck_state` in boot A, against `ck_why[NO_STATE]` with keyed textures bound.
   - If needed: a sub-bit that defaults the state TRUE for contexts that see a `D3DOP_EXIT` (the execute-buffer signature, `vcrdd_d3d.c:1773-1782`).
3. **Q3: Which staged titles key textures at all?** Boot A counters.
4. **Q4: Are the bilinear fringes acceptable?** A CKEY_POINT A/B on the same scene. The longer-term alternative is converting keyed texels to alpha, which is NewDark's approach.
5. **Q5: What draws Thief's DX6 trees as flat (0,0,8) cut-outs (visual-07)?** The LogLevel 2 `log_combo` lines for that scene in boot A will show:
   - `SELECTARG1(TFACTOR)` or an alpha-only texture pass points to G12/G14;
   - fog with D3DTLVERTEX specular alpha 0 points to G32;
   - keyed textures with 2 stages points to G09 with TWO_STAGE.
6. **Q6: Do DX7 managed textures (`DDSCAPS2_TEXTUREMANAGE`) carry the key to the driver's video-memory copy?** Add a `colorkey_managed` variant.
7. **Q7: Colour-space keys (high != low).** If the counters show them, use the exact per-channel range: `chromaKey` = low, `chromaRange` = high | enable | inclusive | intersection (SPEC L3530-3546). That needs its own probe case.
8. **Q8: Should TRANSPARENCY be withdrawn while the bit is off?** AvP's loader may then choose alpha formats, which draw with no fringes. The answer is an AvP A/B, once G71 lets it reach a device.
