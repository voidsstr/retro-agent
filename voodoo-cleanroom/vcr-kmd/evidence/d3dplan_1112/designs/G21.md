## 1. Verdict

**The gap is real and fixable, and most of the fix already runs on `.124` every day.** Both bugs are
confirmed by reading the code and by arithmetic. The second one is worse than the gap text says.

1. **Placement (verified).** `VcrDdD3dCreateMipChain`'s default branch places only
   `DDSCAPS_TEXTURE|DDSCAPS_MIPMAP` surfaces (`KMD/display/vcrdd_d3d.c:537-539`).
   - Every single-level texture is placed by DirectDraw's linear heap on a 4-byte boundary.
   - `texBaseAddr` keeps address bits 25:4 only (SPEC §8.79 L3966; `vcr_texlod.c:32` masks `0x00fffff0`).
   - So such a texture is sampled 4, 8 or 12 bytes early: rows shift by 2, 4 or 6 texels at 16 bpp.
   - The 11-08 fix (`481acfd`) lives only in `mipchain_ext` (`:381-391`), reached only with a
     `D3DBigTex` bit (`:532-533`).
   - Render-target textures (`DDSCAPS_3DDEVICE`) keep DirectDraw's placement on **both** paths (`:389-391`).
     The 3D engine also drops `colBufferAddr` bits 3:0 (SPEC §8.40, "must be 16-byte aligned"; hw Q12).
     So rendering into a misplaced one writes up to 12 bytes into the surface before it (inferred from
     the register definition).
   - A likely trigger on a fresh install: per-level mip calls are placed by the driver in 16-byte
     blocks of 8 bytes (2x2) or 2 bytes (1x1). That leaves DirectDraw's next single-level texture
     off the 16-byte grid (inferred; the heap's granularity is G07 open question 4).
2. **Address width (verified, larger than "16 MB lower").** `.124` runs the V5 6000 in its 256 MB VBIOS
   mode. Chip 0 has 64 MB, and the DirectDraw heap reaches `0x3ed3000`, about 63 MB
   (`ONBOX/ring_after_probe_i_decoded.txt` seq 24681; `0x3aff000` at 1280x1024x32,
   `ONBOX/ring_after_modeseq_decoded.txt` seq 25224).
   - The README's "heap is 0 - 27 MB" (`KMD/README.md:111, 496`) is stale.
   - With the default path's 24-bit field, a texture is sampled at its address **modulo 16 MB**:
     16, 32 or 48 MB low. That covers three quarters of the heap.
   - A texture in the first ~170 KB of the heap (350 KB at 32 bpp) has its would-be LOD-0 base "below
     zero". The 24-bit value then makes the TMU read it **16 MB high**.
   - SPEC L6091: "texbaseaddr can be set below zero, such that the offset to the texture wraps".
     With all 26 bits the wrap is correct (inferred: the TMU adder is 26 bits wide, L3966).
3. **Adjacent, same arithmetic (verified): a 16 bpp texture whose top is 1x1 is sampled 8 bytes early
   on BOTH paths.**
   - Its absent levels sum to 174760 bytes, which is 8 modulo 16. The 16-byte-aligned placement of
     `mipchain_ext` therefore reads 8 bytes before the texel.
   - Glide shifts the data by that remainder (`G5/glide3/src/ditex.c:1781-1787`, "the hw is still going
     to use the complete size computation, but it always starts from an aligned baseAddr").
   - 3dfx put 1x1 textures "8 bytes from vaddr0" (`VH5/D3TXTR.C:877-889`).
   - Of 273 power-of-two shapes (every kind, to 2048, aspect at most 8), only R5G6B5/1555/4444 1x1 has
     a non-zero phase (host check). A1R5G5B5/A8R8G8B8 1x1 needs none, so 3dfx's unconditional `+8`
     would be wrong for 32-bit textures.
   - G06 §10 and G07 §1.3 found this too. This design takes ownership of it; see §12.

**Chosen fix.** A new `Diag\D3DTexPlace`, default off. Its bit 0 makes the placement and addressing
half of the VSA-100 texture path independent of `D3DBigTex`'s format and size bits. It does this by
OR-ing into `pd->tex_ext`, which routes exactly four call sites:
- the allocator (`mipchain_ext`): every 16 bpp texture to 256 is placed 16-byte aligned;
- the TMU view (`tex_view_ext`/`ext_layout`): the 26-bit munged `texBaseAddr` on a VSA-100;
- the flush (`flush_written`): the proven texture-port write-back rule;
- `VcrDd3dTexFlush`'s `lin`.

Bit 0 also adds the 1x1 phase on every path. Bit 1 places render-target textures the same way.

No caps change. On a VSA-100, bit 0 writes **the same registers .124's daily `D3DBigTex = 7` path
writes** for every 16 bpp texture up to 256: 408 size×offset cases are identical (host check, §7).
A log-only counter, default on, names every bound texture the TMU reads from somewhere other than
its own address.

**Answering `GUID_GetHeapAlignment` (runtime-13) is not the primary fix.**
- It cannot fix the address width or the 1x1 phase.
- That XP honours it is inferred.
- It moves every DirectDraw surface.

It stays an evidence-gated investigation (§4.7).

**Defaulting `D3DBigTex` on (G20) is not a substitute.** That changes caps (2048, DXT, 8888) for
every title. G21 changes where textures live and nothing a game can see.

## 2. What the code does today (verified)

**Who places a texture.** `Dd_CreateSurface` (`KMD/display/vcrdd_ddraw.c:633-645`) calls
`VcrDdD3dCreateMipChain` (`vcrdd_d3d.c:522-584`):
- **With any `D3DBigTex` bit** (`pd->tex_ext`, set only on a VSA-100, `KMD/display/vcrdd_2d.c:463-466`):
  `mipchain_ext` (`:367-466`) places every `DDSCAPS_TEXTURE` surface that is not system memory and
  not `DDSCAPS_3DDEVICE`.
  - It uses `HeapVidMemAllocAligned(vm, total, 1, {16, 16})` (`:438-441`) with pitch `w × bytes`.
  - The surface is marked `MIP_TOP`/`MIP_LEVEL` in `dwReserved1` and freed by `VcrDdD3dFreeMipChain`
    (`:586-601`).
- **Without**: only `TEXTURE|MIPMAP`, 16 bpp (`:537-544`). Everything else returns
  `DDHAL_DRIVER_NOTHANDLED`, and dxg places it.
- `vmiData.dwTextureAlign = 16` (`vcrdd_ddraw.c:91`) is **not applied** by XP's linear heap. UT2003's
  textures sat at `0x91d6b4`, `0x93d6b4` and `0x71d6b4` (`SWP/sweep_1108/UT2003_combos_unaligned.txt`;
  `WT/docs/v56k-benchmark-plan.md:142-160`).
- XP asks `GUID_GetHeapAlignment` (42e02f16, 0x8c bytes = `DD_GETHEAPALIGNMENTDATA`,
  `~/retro3dfx-toolchain/devtools/dx8ddk/inc/dmemmgr.h:41-89`) at every enable. We decline it
  (`ONBOX/ring_after_probe_ii_decoded.txt` seq 24835; `vcrdd_ddraw.c:683-706`).

**How the TMU is pointed at it.** `view_of` (`:840-843`) picks `tex_view` (`:754-799`) or
`tex_view_ext` (`:806-837`):
- `tex_view` calls `vcr_texlod_compute` (`KMD/common/vcr_texlod.c:14-36`). Its base is
  `(offset − pre) & 0x00fffff0`, the Voodoo3 field.
- `tex_view_ext` → `ext_layout` (`:349-362`) → `vcr_texlod_compute_ext(..., ext_flags(pd))`
  (`vcr_texlod.c:94-146`). That gives `lin & 0x03fffff0` munged into `{bit1 = addr25, bits 24:4}`
  (`vcr_tex_munge`, `:79-82`; `G5/incsrc/h3defs.h:1074-1078`).
- `ext_flags` (`:331-334`) is always `VCR_TEXF_NAPALM | (tex_big ? BIG : 0)`.

**The flush.** `flush_written` (`:1287-1320`):
- The ext branch passes `vcr_tex_writeback_addr()`: a texture-port write only for RGB16, not TBIG,
  below 16 MB (`vcr_texlod.c:89-92`).
- The old branch passes the address, and `VcrDd3dTexFlush`'s range test (`KMD/display/vcrdd_3d.c:253-271`)
  makes the same decision (pinned by `WT/tests/native/test_vcr_kmd_texlod.c:337-369`).

`VcrDd3dTexFlush` takes `lin = pd->tex_ext ? vcr_tex_unmunge(base) : base` (`:255`).

**Exactly four places read `tex_ext`:** `vcrdd_d3d.c:532` (allocator), `:842` (view), `:1301` (flush),
and `vcrdd_3d.c:255` (port offset). Caps and formats read `tex_big`/`tex_dxt`/`tex_32` individually:
- `:2087-2098` (format list), `:2158` (max size);
- `VcrDdD3dFourCC` `:510`, `VcrDdD3dCreateTexSurface` `:476`;
- TEXBLT `:1510`, the Blt guard `vcrdd_ddraw.c:485`.

**What the TMU reads, today and fixed.** These are host-computed with `vcr_texlod.c` and the SPEC
L6089-6091 rule: the largest level is read at base + its absent levels, and the address wraps.
The VSA-100 interprets the register as 26 bits whichever path computed it.

| texture (R5G6B5 unless noted) | at | default path today: register → TMU reads (Δ) | bit 0: register → reads (Δ) |
|---|---|---|---|
| 64x64 | `0x0100000` | `0x00d8000` → `0x0100000` (0) | `0x00d8000` → same (0): **identical register** |
| 64x64, DirectDraw's 4-byte placement | `0x0100004` | `0x00d8000` → `0x0100000` (**−4**) | placed at `0x0100010` instead (0) |
| 64x64 | `0x1400000` (20 MB) | `0x03d8000` → `0x0400000` (**−16 MB**) | `0x13d8000` → `0x1400000` (0) |
| 64x64 | `0x2800000` (40 MB) | `0x07d8000` → `0x0800000` (**−32 MB**) | `0x07d8002` → `0x2800000` (0) |
| 64x64 at UT2003's real 11-08 address | `0x3d4f000` (61 MB) | `0x0d27000` → `0x0d4f000` (**−48 MB**) | `0x1d27002` → `0x3d4f000` (0) |
| 64x64, base "below zero" | `0x0010000` (64 KB) | `0x0fe8000` → `0x1010000` (**+16 MB**) | `0x1fe8002` → `0x0010000` (0) |
| 1x1, 16-aligned (today's BigTex placement too) | `0x0900000` | `0x08d5550` → `0x08ffff8` (**−8**) | placed at `0x0900008`: `0x08d5560` → `0x0900008` (0) |
| 1x1 A8R8G8B8 (BigTex path) | `0x0900000` | `0x08aaab0` → `0x0900000` (0) | no pad (0) |

**Silicon already uses bit 25.** UT2003 on the BigTex path sampled textures at `0x3c21ac0` (base
`0x1d21ac2`) and `0x3bc8570` (base `0x1bb8572`), with address bit 25 carried in register bit 1
(`SWP/sweep_1108/UT2003_combos_unaligned.txt`, combines 8 and 9). Its menu renders cleanly once
aligned (V-02). That the munge is right above 32 MB is therefore inferred from a working title, not
yet from a probe (`texhigh` fills only 20 MB, `KMD/tools/d3dprobe.c:861-912`).

**The vendor owns all of this.**
- 3dfx sends every `DDSCAPS_TEXTURE` surface, render targets included, to its own allocator
  (`VH5/DDSURF.C:345-364` → `TEXTURESURFACECREATE` → `TXTRMIPMAPALLOC`, `VH5/D3TXTR.C:1290`).
- That allocator gives linear heaps 16-byte start and pitch alignment (`VH5/DDMEMMGR.C:349-360`).
- It rounds bases to 16 (`txtrCalcBaseAddress`, `VH5/D3TXTR.C:3734-3765`), and moves 1x1 textures
  8 bytes in (`:877-889`).
- It warns on an unaligned download base (`:3349-3350`).

## 4. The design

### 4.0 Part 0: say where the TMU really reads (log only, register traffic unchanged, default ON)

It follows the hal §10 Phase-0 convention and lands default-on, pinned by a Python source test.
It measures the gap in every title on every configuration, and it is the in-game proof of the fix.

1. **A pure helper** in `KMD/include/vcr_texlod.h` / `KMD/common/vcr_texlod.c`:

   ```c
   /* The linear address the TMU reads the LARGEST level of a w x h texture of
    * `kind` from, when texBaseAddr holds `reg`: the register's base (unmunged
    * on a VSA-100 - VCR_TEXF_NAPALM in flags - the 24-bit field otherwise),
    * plus the levels before the texture's top (256 down to twice its size),
    * or minus its levels wider than 256 (TBIG); wrapped at the chip's address
    * width (SPEC L6091), 26 bits on a VSA-100, 24 on a Banshee/Voodoo3.
    * A texture whose fpVidMem differs is sampled from somewhere else. */
   vcr_u32 vcr_tex_read_at(vcr_u32 kind, vcr_u32 w, vcr_u32 h, vcr_u32 reg, vcr_u32 flags);
   ```

   - It is written beside `vcr_texlod_compute_ext`, which stays byte-identical (proven).
   - A native test cross-checks it against `vcr_texlod_compute_ext` for every shape (§7).
   - `flags` describes **the chip**, not the path: `pd->napalm ? VCR_TEXF_NAPALM : 0`. The VSA-100 reads
     the old 24-bit value as 26 bits too, which is what produces the −16/−32/−48 MB rows of §2.

2. **`tmu_view` gains `kind`.** `tex_view` sets `VCR_TEXK_RGB16`, and `tex_view_ext` takes it from `ext_layout`.

3. **The check, in `compute_regs`** (`:921`, after `view_of` for v0, and v1 when two stages are used).
   For each bound texture:

   ```c
   if (vcr_tex_read_at(v.kind, v.w, v.h, v.texBaseAddr, pd->napalm ? VCR_TEXF_NAPALM : 0)
       != (ULONG)t->lpGbl->fpVidMem) { c->tex_misaddr++; ... }
   ```

   - The first 8 distinct handles per context are logged at WARN:
     `texture %u at %x: the TMU reads it at %x (%d bytes off)`.
   - It is integer only, a loop of at most 11 levels, and runs only when state is recomputed, not per
     triangle (G52).

4. **Targets.** In `target_of` (`:1047`), when a target is accepted with `rt_off & 15` or (`z_on` and
   `z_off & 15`):
   - `c->rt_offgrid++`;
   - WARN once per context: `target %x / Z %x off the 16-byte grid: the 3D engine draws %u bytes
     before it`.
   - The target is not refused, so behaviour is unchanged.
   - This is the trigger for §4.7.

5. **Summary.** A new INFO line next to "context %u gone" (`ctx_free`, `:1210-1221`):
   `context %u textures: %u misaddressed binds (%u handles), %u target/Z off the grid`.
   It goes at the end, so it survives the ring wrap that loses per-draw events (G76).

**Event numbers.** Use the next free 513 `what` numbers when this lands. G05, G06 and G07 already
propose 24-27. Update the 513 row of `KMD/include/vcr_events.h:75`.

### 4.1 The switch: `Diag\D3DTexPlace` (DWORD bits, absent = 0)

**Where it is read.**
- **The miniport** reads it **at boot**, beside `D3DBigTex`: `x->d3dtexplace = VcrDiagGet(L"D3DTexPlace", 0)`
  in `VcrFindAdapter` (`KMD/miniport/vcrmp.c:244`). It shares `tex_ext` with `D3DBigTex`, so both
  latch at the same moment.
- **The flags.** `fill_info` (`:443-466`) maps bit 0 → `VCR_INFO_F_TEXPLACE` and bit 1 →
  `VCR_INFO_F_RTTPLACE`. These are two positive flags, so an older miniport never sets them.
- **Flag values.** Allocate the next two free bits when this lands. 0x8000 and 0x10000 are already
  claimed by the G01/G03/G05/G07/G08 designs. `test_the_switch_is_read_once_at_boot_and_absent_means_off`
  rejects a shared bit.
- **The field.** `VCR_EXT` gets `ULONG d3dtexplace;` (`KMD/miniport/vcrmp.h:153`).

**The display side,** in `VcrDd2dInit` (`KMD/display/vcrdd_2d.c:442-472`). It works on any chip, which
the 86Box Voodoo3 bed needs:

```c
pd->tex_place = (info.flags & (VCR_INFO_F_TEXPLACE | VCR_INFO_F_RTTPLACE)) ? 1 : 0;  /* bit 1 implies bit 0 */
pd->rtt_place = (info.flags & VCR_INFO_F_RTTPLACE) ? 1 : 0;
pd->tex_ext   = pd->tex_big | pd->tex_dxt | pd->tex_32 | pd->tex_place;
```

- Both new fields are reset with the others at `:442`.
- Event 513/18 keeps its text and fires only for `tex_big | tex_dxt | tex_32`.
- A new INFO event says `armed (Diag\D3DTexPlace %x): every texture placed where the TMU reads it%s,
  render-target textures %s`. The `%s` is "; 26-bit texture addresses" on a VSA-100.

`vcrdd.h:70-75`'s comment changes: `tex_ext` = "the texture path that places textures and reads
`ext_layout`", that is any `D3DBigTex` bit or `D3DTexPlace`.

**Supervised use** follows the usual process: one Diag change per clean boot, then
`safe-reboot.py` after the activation check.

### 4.2 Bit 0: every texture placed where the TMU reads it, on every path

**Code** (`KMD/display/vcrdd_d3d.c`):

1. **`ext_flags`** (`:331-334`):
   `return (pd->napalm ? VCR_TEXF_NAPALM : 0) | (pd->tex_big ? VCR_TEXF_BIG : 0);`
   - Unchanged wherever it runs today, since `tex_ext` implied `napalm` until now.
   - On a Banshee/Voodoo3 with bit 0 it gives flags 0, the Voodoo3 field.
2. **Nothing else changes in the four `tex_ext` sites.** With bit 0 and no `D3DBigTex` bit:
   - `pf_kind` (`:293-309`) yields `VCR_TEXK_RGB16` for 565/1555/4444 and `KIND_NONE` for everything else.
   - `vcr_texlod_compute_ext` refuses anything wider than 256.
   - So exactly the formats and sizes the caps already offer take the placing path.
   - `mipchain_ext` places single levels and per-level mip calls 16-byte aligned, with pitch `w×2`.
   - `tex_view_ext` writes the 26-bit base.
   - `flush_written`'s ext branch applies `vcr_tex_writeback_addr`: the port write only below 16 MB,
     the same decision the old range test made.
   - `VcrDd3dTexFlush` takes `lin` from `vcr_tex_unmunge`, which is the identity for any 24-bit value
     (bit 1 clear).
3. **The comment block** `:245-254` is rewritten to say the same.

**Differences of the ext allocator from the old default branch, for 16 bpp chains.** These are what
a fresh install with bit 0 gets in addition to the fix; each is benign or a fix:
- **Format source.** The surface's own `ddpfSurface` is read before the descriptor. This is the
  09-28 integration-review fix, `:392-410`.
- **Logging.** The placement event becomes 513/20 instead of 513/11.
- **Mipmapped render-target textures** are no longer packed by the driver: `mipchain_ext` excludes
  `3DDEVICE`. With bit 1 they are placed again (§4.4).

### 4.3 The 1x1 phase (bit 0)

**A pure helper,** with the name and meaning G07 §4.3 proposed, so either item can land first:

```c
/* bytes past a 16-byte boundary the TOP level of a w x h texture of `kind`
 * must start for the TMU (base 16-byte aligned, levels byte-exact) to read
 * it there: 8 for a 16 bpp 1x1, 0 for every other shape */
vcr_u32 vcr_tex_chain_pad(vcr_u32 kind, vcr_u32 w, vcr_u32 h);
```

- It is computed from the absent levels (`adj & 15`, or `−adj & 15` with TBIG), not hard-coded.
  The host check (§7) shows it is non-zero only for RGB16 1x1.

**In `mipchain_ext`,** with `pd->tex_place`:
- `pad = mip_level ? 0 : vcr_tex_chain_pad(kind, w0, h0)`.
  - `mip_level` is a per-level call for a sub-level of a chain: `DDSCAPS_MIPMAP`, with
    `DDSD_MIPMAPCOUNT` > 1 in the descriptor (measured: "seven calls for a 64x64 D3D8 texture,
    DDSD_MIPMAPCOUNT 7 on each", `WT/tests/python/test_vcr_kmd_d3d.py:106-114`), or a descriptor
    size larger than 1x1.
  - A chain's 1x1 *level* must sit right after its 2x2, not at a padded top. That is G07's
    contiguity problem, not this one, and this guard keeps G07's `mipdeep` measurement intact.
- The block is `total + pad`, and the top goes at `base + pad`.
- `SF_PAD8 0x8` is added to the surface-local `dwReserved1` flags (beside `SF_DIRTY 0x4`; the same
  flag G07 named).
- `VcrDdD3dFreeMipChain` (`:586-601`) frees `fpVidMem − (SF_IS(s, SF_PAD8) ? 8 : 0)`. The free path
  reads the surface's flag, never the switch.
- **Where it applies.** It applies on every path once bit 0 is set. On `.124` (`D3DBigTex = 7`)
  arming `D3DTexPlace = 1` changes only this. With `D3DTexPlace` clear, `D3DBigTex = 7` stays
  byte-for-byte today's path.

### 4.4 Bit 1: render-target textures (implies bit 0)

In `mipchain_ext`'s guard (`:389-391`) the exclusion becomes:
`(caps & SYSTEMMEMORY) || ((caps & 3DDEVICE) && !pd->rtt_place)`.

**What a render-target texture then gets:**
- the same 16-byte placement and pitch `w × bytes`. This is a 16-byte multiple for every R5G6B5
  texture at least 8 wide and every A8R8G8B8 at least 4 wide, at most 8192 bytes, inside the 14-bit
  stride (`vcr_rtfmt.h:124-164`);
- so it is both a legal 3D target (`colBufferAddr[25:4]`, stride 16-aligned; SPEC §8.40) and a
  samplable texture (pitch = width × bytes; hw Q12; SPEC §20.2 L6113).

**Smaller ones** keep a pitch under 16 and are refused as targets by `vcr_rt_rtcheck`. That is
exactly what DirectDraw's placement gives them today, since we ask DirectDraw for no pitch
alignment, so nothing regresses.

**Mipmapped render-target textures** are placed as chains, as the old default branch did.

**Which ones exist.** The runtime grants R5G6B5 render-target textures on PCI id `121a:0009`, and
A8R8G8B8 ones while `D3DBigTex` bit 2 lists the format (`reports/runtime.md` §4.3).

**What bit 1 does not fix:**
- **Coherency after rendering into a texture** is G37 (VcrDd3dTexFlush-style flush after the target
  changes away from it).
- **Render-to-texture as a feature** is G36.

**Bit 1 is G36's placement prerequisite.** Halo runs with `DisableRenderTargets`
(`/mnt/retro-share/Files/Games-Library/Halo/config.txt:115-118`).

### 4.5 Caps

**None change.**
- `dwMaxTextureWidth` stays `tex_big ? 2048 : 256` (`:2158`).
- The format list follows `tex_32`/`tex_dxt` (`:2087-2098`), and FOURCC follows `tex_dxt`.
- `TEXTURECAPS_POW2`, the aspect of 8 and `MinTextureWidth` 1 are untouched.
- A title can see no difference except its textures drawing right.

### 4.6 The old path (switch absent or 0)

- `tex_ext` is exactly today's: `tex_big | tex_dxt | tex_32`.
- `VcrDdD3dCreateMipChain`'s default branch, `tex_view`, the old flush branch, `ext_flags`' output for
  every VSA-100 and the caps are byte-for-byte today's.
- **Added:** the §4.0 counters and their WARN/INFO lines. They are log only.
- **Pinned by** `test_off_the_hal_is_the_proven_one` (`WT/tests/python/test_vcr_kmd_bigtex.py:70-104`),
  unchanged.

### 4.7 Part C, an investigation only: `GUID_GetHeapAlignment`

**Build it only if** one of these holds:
- (a) §4.0's target counter is non-zero in any staged title, meaning dxg put a back buffer, Z or
  render target off the grid;
- (b) a texture shape the allocator declines shows up misaddressed;
- (c) a windowed D3D title needs a width that is not a multiple of 8 pixels at 16 bpp.

**The design if built: `Diag\DdHeapAlign`,** read at every mode change like `DdHeapFloor`.
- **Where.** `DdGetDriverInfo` (`vcrdd_ddraw.c:683-706`) answers GUID
  `{0x42e02f16,0x7b41,0x11d2,{0x8b,0xff,0x00,0xa0,0xc9,0x83,0xea,0xf6}}`
  (`~/retro3dfx-toolchain/devtools/dx8ddk/inc/ddrawint.h:46`) with a `DD_GETHEAPALIGNMENTDATA` for heap 0.
- **The answer.** Set `ddsCaps` to the surface types it covers:
  - `ZBuffer`, `Offscreen` and `FlipTarget`: `{16, 16}`;
  - `Texture`: `{16, 4}`. The natural DWORD pitch, never 16 (§3 C); the value 4 is inferred to be
    today's pitch rule.
- **Measurement.** The §4.0 counters and 513/23 addresses show whether dxg honours it. d3dprobe
  windowed with a new `--size 250x250` shows whether an odd-width device now creates.
- **Outcomes.** Honoured: keep it as the backstop for surfaces the driver never places. Ignored:
  drop it.

## 5. Gating

- **Part 0** (counters) lands **default-on**. It writes no registers and allocates nothing. It is
  pinned by a Python source test.
- **Bit 0 lands default-OFF.** Absent, the driver is byte-for-byte today's.
  - **Is it safe to land default-on?** Almost: on a VSA-100 its register writes for every 16 bpp
    texture up to 256 equal what `.124` runs daily under `D3DBigTex = 7`. That is pinned over 408
    cases (§7).
  - It changes only what is mis-addressed today (−4/−8/−12 bytes, ±16/32/48 MB, 1x1).
  - **It is not landed default-on blind,** because on a fresh install it moves the allocation of
    every single-level texture from dxg to the HAL's single-pass allocator. That allocator has G63's
    offset-0 failure mode, unproven for this combination: a texture that is the first allocation
    after a mode set would get `DDERR_OUTOFVIDEOMEMORY`. D3D titles create their flip chain and Z
    first (inferred).
  - **Graduation.** After **one supervised clean boot** (§8 boot B) plus the bed run (boot 0), flip
    its default: `VcrDiagGet(L"D3DTexPlace", 1)`. Add a `MOVED_DIAG` entry in
    `WT/tests/python/test_vcr_kmd_integration.py:91` with the evidence path. Afterwards
    `D3DTexPlace = 0` is the kill switch.
  - The flip covers every chip, which is why the 86Box Voodoo3 bed run is part of the proof.
- **Bit 1 stays default-off** until G36's render-to-texture round trip (with G37's flush) passes on
  silicon. Its placement half is proven by `rtt_align` (§6) in boot D.
- **Part C** is not built unless §4.7's trigger fires.
- **One Diag change per clean boot.** `D3DTexPlace` is read at boot.

## 10. Risk to proven paths

**Switch off:** nothing.
- Register traffic, allocation and dxg's call pattern are today's.
- Part 0 adds an integer check per bound texture at state recompute and up to 8 WARN lines plus one
  INFO line per context. That is a few IOCTLs per context, not per draw (G52).

**Bit 0 on a VSA-100.**
- Registers for 16 bpp textures to 256 are identical to the daily BigTex path (§7). They differ from
  today's default path only where today's is wrong (§2).
- **Allocation** of every single-level texture moves from dxg to `HeapVidMemAllocAligned`:
  - the same calls `.124` has made for every texture since 11-08;
  - at most 12 bytes per texture are wasted to alignment, plus 8 for a 1x1;
  - G63's offset-0 block loss applies to a texture that is a fresh heap's first allocation
    (inferred rare). `DdHeapFloor` cures it.
- **Write-back** decisions are unchanged (the ext rule reproduces the old range test, pinned at
  `test_vcr_kmd_texlod.c:337-369`).

**Bit 0 on a Banshee/Voodoo3 (the 86Box bed):** placement only. The register is the Voodoo3 field.

**Bit 1:** render-target textures become driver-allocated.
- The target rules are unchanged.
- **The flip path** is untouched: flip chains and back buffers carry no `DDSCAPS_TEXTURE`.

**Glide/OpenGL coexistence:** none.
- No new register traffic, and DirectDraw heap surfaces only.
- Exclusive Glide ownership still draws nothing (`vcrdd_d3d.c:1859, 1887`).

**SLI state:** none. D3D is chip 0 only (G51). A future SLI D3D must replicate placed textures on
every chip, and that is unaffected by this item.

**The default 16 bpp path:** changed only behind the switch. After graduation, `D3DTexPlace = 0` is
the kill switch that restores it byte-for-byte.

  texture on `.124`, or if G20 keeps `D3DBigTex` default-off. In that case every fresh install
  renders shifted UI textures and garbage above 16 MB.

## 12. Open questions

1. **What is dxg's linear-heap granularity?** Does a 2-byte or 4-byte request advance the next
   block by 4, 8 or 16? `texalign`'s three phases assume 4 (UT2003's `...6b4` addresses). G07
   question 4 asks the same.
2. **Does XP honour a `GUID_GetHeapAlignment` answer for a linear heap?** (Part C, inferred.) And
   what `ddsCaps` bit marks `FlipTarget` valid in `HEAPALIGNMENT`?
3. **Is the VSA-100 TMU address adder exactly 26 bits** (64 MB wrap)? This matters only for "below
   zero" bases. SPEC L6091 says it wraps, without the width. Is the bit-25 munge right on this
   board above 32 MB? `texhigh40` answers it.
4. **Does any staged title bind a 16 bpp 1x1 texture or create R5G6B5/A8R8G8B8 render-target
   textures with Halo's switch off?** Part 0 answers it; it decides P1 versus P2.
5. **Pad ownership.** G06 §10, G07 §4.3 and this item all describe the 1x1 phase. It belongs with
   placement (single-level textures are this item's subject), so the proposal is `D3DTexPlace` bit 0.
   G07's whole-chain bit then needs no pad of its own: under atomic creation a 1x1 can only be a
   real top. The integrator should keep one switch for it.
6. **Should graduation flip bit 0 on Banshee/Voodoo3 too?** The 86Box bed is its only user. The
   design says yes, after boot 0.
7. **After graduation, should `target_of` refuse a target or Z that is off the 16-byte grid,** as it
   refuses an unaligned pitch (`vcr_rtfmt.h:105-130`)? Decide it on Part 0's counter. Refusing turns
   a 12-byte overwrite of a neighbour into a CreateDevice failure an application can handle.
