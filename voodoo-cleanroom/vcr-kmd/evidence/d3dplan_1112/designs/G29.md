## 1. Verdict

1. **The defect is real, and today it is honest.**
   - `blend_src` returns `BF_ONE` for SRCCOLOR and INVSRCCOLOR (default case, `KMD/display/vcrdd_d3d.c:643`,
     "ONE, and SRCCOLOR the chip cannot"). `blend_dst` returns `BF_ONE` for DESTCOLOR and INVDESTCOLOR
     (`:661`, "ONE, and DESTCOLOR the chip cannot").
   - The caps do not advertise them: `dwSrcBlendCaps` = `0x1f33`, `dwDestBlendCaps` = `0x003f`
     (`:2025-2031`; the D3D8 runtime reports the same on `.124`, `../caps_124.txt`).
   - So a title that reads the caps never sees a wrong pixel. A title that ignores the caps gets `ONE`.
2. **The VSA-100 does both natively, in one pass, with one register field.**
   - `alphaMode[11:8]` (RGB source factor) and `[15:12]` (RGB destination factor) take code 8 =
     `SST_A_SAMECOLOR` and 9 = `SST_AOM_SAMECOLOR` (1 - same colour) (`VINC/H3DEFS.H:915-930`, 925-926).
   - SPEC: *"When the value 0x8 is selected as the destination alpha blending factor (A_SAMECOLOR function),
     the destination pixel color is used as the destination blending factor. When the value 0x8 is selected as
     the source alpha blending factor, the source pixel color is used as the source blending factor"*. The
     change log says *"Added new alpha blending functions A_SAMECOLOR and AOM_SAMECOLOR to allow src*src and
     dst*dst blending calculations"* (`strings -n 5` lines 4301-4313 and 8586).
   - 3dfx's feature sheet: Napalm **Yes**, Voodoo3 **No**, for "source color" and "inverse source color" as
     source factors and "destination color" and "inverse destination color" as destination factors
     (`D3DXLS` rows 251-252, 271-272).
3. **"The chip cannot" is a Voodoo3 truth.** The mapping arrived in `56e0bc1` ("Direct3D HAL - d3dprobe render
   26/26 ... on the 86Box Voodoo3"). On a Banshee or Voodoo3 the codes 8/9 do not exist: 3dfx's own HAL draws
   SRCCOLOR there as `A_COLOR` under the comment *"Voodoo3: THIS is wrong!!!"* (`VH5/D3RSTATE.C:3081-3095`).
   The fix must therefore follow `pd->napalm`.
4. **The gap's game claim does not hold. No staged `.124` title was found that sends these factors.**
   - **Shogo** (`LIB/Shogo/d3d.ren`, md5 `072bc370...`). Disassembled:
     - it reads `dpcTriCaps.dwSrcBlendCaps & D3DPBLENDCAPS_SRCCOLOR` into a global (`0x10013e56`, stored at
       `0x10046064`);
     - that global is read only by the `LISTDEVICECAPS` console dump (`0x10013a4e`, inside `0x10013850`, which
       is called only at `0x10014624` after a string compare with `"LISTDEVICECAPS"`);
     - its "Lightmap capable" flag is SrcBlend ZERO plus DestBlend **SRCCOLOR** (`0x1001501a-0x1001503b`), and
       "Light add poly" is ONE/ONE (`0x10015045-0x10015064`). We already advertise both;
     - every `SetRenderState` (IDirect3DDevice3 vtable +0x58) for SRCBLEND/DESTBLEND sets SRCALPHA/INVSRCALPHA
       or ONE/ONE, or restores a saved value.

     The cap is printed, never used. Shogo renders nothing differently with this fix.
   - **Halo** (`LIB/Halo/halo.exe`, md5 `b7aa8f68...`) keeps its framebuffer blend functions in three
     `.rdata` arrays at `0x65dfbc`, `0x65dfe0` and `0x65e004`:
     - src = SRCALPHA, DESTCOLOR, DESTCOLOR, then ONE x5;
     - dst = INVSRCALPHA, ZERO, SRCCOLOR, ONE x4, INVSRCALPHA;
     - op = ADD x4, REVSUBTRACT, MIN, MAX, ADD.

     These are alpha blend, multiply, double multiply, add, subtract, min, max and alpha-multiply add. None uses
     SRCCOLOR as a source or DESTCOLOR as a destination.
   - **Fifteen more renderers**, byte-scanned for `push value; push SRCBLEND/DESTBLEND` call sites and DX5
     execute-buffer state writes: UT2003/UT2004 `D3DDrv.dll`, Max Payne `e2_d3d8_driver_mfc.dll`, `rf.exe`,
     `RainbowSix.exe`, `THIEF.EXE`, `Thief2.exe`, `JK.EXE`, `JKM.EXE`, `avp.exe`, `BF1942.exe`, H&D
     `igraph2.dll`/`i3d2.dll`, and the dormant UE1 `D3DDrv.dll`s. Every apparent hit was disassembled, and none
     was a render state:
     - four (UT2004, Halo, Max Payne, Thief Gold) are zlib's `zalloc(opaque, 19, 4)`;
     - Jedi Knight's and MotS's are the same table registration (`(key, value, 0)` calls, `JK.EXE 0x4d8476`,
       `JKM.EXE 0x527046`);
     - Red Faction's is a text draw at (20, 10);
     - AvP's and Rainbow Six's are unrelated data.
   - **What this cannot exclude:** engines that set blend states from variables (UE2's material code, NewDark,
     Max Payne, LS3D, Red Faction). Step 0's counter (4.1) answers that per title, from any sweep.
5. **The fix is the one the gap names, kept to the VSA-100 and gated:**
   - two mapping cases and the four caps bits;
   - moved into a Win32-free header, so that a host test executes the state-to-register translation (part of
     G77's goal);
   - a log-only blend-request counter;
   - a Glide-level silicon check that needs no driver change;
   - and d3dprobe `blendsq` / `blendsq_force`.
6. **Priority P3, effort S.** Raise it to P2 if the counter shows a staged title asking for these factors. It
   belongs with **G28**: the same two functions, the same two caps words, and the same probe matrix.

## 2. The defect, precisely

The D3D blend equation is `result = Cs·Fs + Cd·Fd` per channel. What is drawn for each of the four factors:

| request | D3D result (RGB) | `alphaMode` today | drawn today | armed | drawn armed |
|---|---|---|---|---|---|
| SRCBLEND = SRCCOLOR (3) | `Cs·Cs + Cd·Fd` | RGBSRC 4 (ONE) | `Cs + Cd·Fd` | RGBSRC **8** | `Cs·Cs + Cd·Fd` |
| SRCBLEND = INVSRCCOLOR (4) | `Cs·(1-Cs) + Cd·Fd` | RGBSRC 4 | `Cs + Cd·Fd` | RGBSRC **9** | exact |
| DESTBLEND = DESTCOLOR (9) | `Cs·Fs + Cd·Cd` | RGBDST 4 (ONE) | `Cs·Fs + Cd` | RGBDST **8** | exact |
| DESTBLEND = INVDESTCOLOR (10) | `Cs·Fs + Cd·(1-Cd)` | RGBDST 4 | `Cs·Fs + Cd` | RGBDST **9** | exact |

Unchanged, because they are already right:
- DESTCOLOR and INVDESTCOLOR as a **source** (`BF_COLOR`/`BF_INVCOLOR`, code 2/6 = the destination's colour,
  `:638-639`);
- SRCCOLOR and INVSRCCOLOR as a **destination** (code 2/6 = the source's colour, `:655-656`);
- BOTHSRCALPHA and BOTHINVSRCALPHA, which override the destination (`:648-652`);
- every other factor, and the out-of-range fallback to ONE.

**Not in scope (unchanged here):**
- The alpha channel is always `ASRC = ONE`, `ADST = ZERO` (`:997-998`). D3D's SRCCOLOR has alpha component `As`
  and DESTCOLOR has `Ad`; 3dfx wrote `SST_A_SRCALPHA` / `SST_A_DSTALPHA` into the alpha fields for them
  (`VH5/D3RSTATE.C:3084-3107`, `:3250-3272`). That only shows on a target with alpha, and it is **G28**'s.
- DESTALPHA substitution and SRCALPHASAT verification are **G28**'s. BLENDOP is **G91**'s.

## 3. What the hardware does

### 3.1 The field

`alphaMode` (`VINC/H3DEFS.H:904-936`; ours `KMD/include/vcr_3dregs.h:119-136`):

| bits | field | codes |
|---|---|---|
| [4] | `SST_ENALPHABLEND` | |
| [11:8] | RGB source factor | 0 ZERO, 1 SRCALPHA, 2 COLOR (the **destination's**), 3 DSTALPHA, 4 ONE, 5 1-SRCALPHA, 6 1-COLOR, 7 1-DSTALPHA, **8 SAMECOLOR (the source's own)**, **9 1-SAMECOLOR**, 0xA-0xE reserved, 0xF SATURATE |
| [15:12] | RGB destination factor | as above, but 2/6 is the **source's** colour, **8/9 the destination's own**, and 0xF is COLORBEFOREFOG |
| [19:16], [23:20] | alpha source / destination factor | separate table: ZERO/ONE at 15/16 bpp, plus SRCA, DSTA and the inverses at 32 bpp (SPEC "32 BPP alpha channel alpha blending modes") |

The nibble is 4 bits wide, so 8 and 9 fit and touch no other field.

### 3.2 Which colours

- **The source colour** is the pixel after the colour combine and fog.
  - The existence of the destination factor 0xF, "colour before fog", says the other factors see the fogged
    colour (SPEC, same paragraph).
  - D3D also fogs before it blends (inferred), so SAMECOLOR as a source is exactly D3D's SRCCOLOR.
- **The destination colour** is the frame-buffer pixel.
  - At 15/16 bpp it is expanded to 8 bits per channel before the blender (SPEC renderMode/fogMode dither
    paragraphs, `strings` lines 4612-4616).
  - Our HAL never enables dither subtraction, so the expansion is plain. Whether it is bit replication or zero
    fill is not stated; it moves a 16 bpp result by at most one 5-bit step (section 6).

### 3.3 Who already drives these codes

| user | where | on `.124` silicon in this project? |
|---|---|---|
| 3dfx's Napalm D3D HAL, NT and 9x | SRCCOLOR/INVSRCCOLOR as source and DESTCOLOR/INVDESTCOLOR as destination become `SST_A_SAMECOLOR`/`SST_AOM_SAMECOLOR` under `IS_NAPALM` (`VH5/D3RSTATE.C:3084-3107`, `:3250-3272`; identical in `W9X/D3RSTATE.C:3085-3098`, `:3251-3264`). The four caps are added under `IS_NAPALM` (`VH5/D3INIT.C:3132-3158`; the base caps without them are at `:2742-2775`, `:2945-2977`). The per-draw Napalm blend adjustment rewrites only DSTALPHA, 1-DSTALPHA, SATURATE and COLORBEFOREFOG, and **leaves 8/9 untouched** (`VH5/D6DP2.C:6234-6324`) | never measured |
| Glide 3 (h5) | `grAlphaBlendFunction` ORs `rgb_sf`/`rgb_df` straight into the fields (`G5/gglide.c:671-735`); `GR_BLEND_SAME_COLOR_EXT` 0x08 / `GR_BLEND_ONE_MINUS_SAME_COLOR_EXT` 0x09 (`G5/g3ext.h:155-156`); 3dfx's own test cycles them (`G5/../tests/test47.c:75-83`) | never measured |
| **our MesaFX ICD, shipped today** | `isNapalm` maps GL_SRC_COLOR / GL_ONE_MINUS_SRC_COLOR as a source and GL_DST_COLOR / GL_ONE_MINUS_DST_COLOR as a destination to `GR_BLEND_(ONE_MINUS_)SAME_COLOR_EXT` (`GLM/fxsetup.c:1522`, `:1576-1584`, `:1647-1656`), and advertises `GL_NV_blend_square` on Voodoo4/5 (`GLM/fxdd.c:1983`; `voodoo-cleanroom/README.md:358`) | **never measured**: no hit in FINDINGS.md, the plan docs or `tests/` (case-insensitive) |

I found no erratum. 3dfx's `Napalm_Validation_results.doc`, `Napalm_Validation_plan.doc`, `Post-Si Validation
plan.doc`, `Avenger_Validationplan.doc` and `napalmbswbringup.doc` contain no "same color", "src*src" or
"alpha blend" text at all (case-insensitive). That proves only that nobody wrote an erratum down. It is not proof
that the silicon works, which is why Step 1 (4.2) measures it.

## 4. Design

### 4.1 Step 0: measure which titles ask (log only, default on, can land first)

- **`vcr_d3dctx`** (`KMD/display/vcrdd_d3d.c:49-74`) gains `ULONG blend_req`:
  - bits 0-15: the SRCBLEND values seen;
  - bits 16-31: the DESTBLEND values seen;
  - one bit per D3DBLEND value 1-15. Any value above 15 sets bit 0 of its half, which no valid factor uses.
- **`compute_regs`** ORs both values in whenever `ALPHABLENDENABLE` is on (`:995-999`). That costs one OR per
  state change and nothing per triangle.
- **`ctx_free`** (`:1210-1216`) logs one extra event, `VCR_EV_DD_D3D` with the next free `what` (G05 proposes
  24/25; `KMD/include/vcr_events.h:75` is the arbiter), only if blending was ever on:
  `"context %u blend asked: src %04x dst %04x (SAMECOLOR: src 3/4, dst 9/10)"` (under the 95-character ring
  limit).
- **What it answers.** Any later sweep (`lan_sweep.py`, the plan's `--only` list at
  `docs/v56k-benchmark-plan.md:196`) then says, per title:
  - whether a game asks for src bits 3/4 or dst bits 9/10 (G29);
  - DESTALPHA 7/8 and SRCALPHASAT 11 (G28);
  - all from the `context N gone` tail that survives in the per-run `ring.txt`.
- **Who owns it.** If G76 lands its generic counters first, this mask becomes one of them.

### 4.2 Step 1: prove the silicon through Glide, with no driver change and no reboot

`glidelab` already late-binds `grAlphaBlendFunction` and `grLfbReadRegion` (`KMD/tools/glidelab.c:186-221`) and
reads pixels back for `bands`. A new mode **`blendsq`**:

1. Opens at `--res 640x480` (Glide's 16 bpp), dither off (`grDitherMode(GR_DITHER_DISABLE)`), and clears to
   `0x004080C0`.
2. Draws the twelve cells of 6.1:
   - each a flat quad in `grConstantColorValue(0x80C08040)`;
   - colour combine LOCAL_CONSTANT;
   - `grAlphaBlendFunction(rgb_sf, rgb_df, GR_BLEND_ONE, GR_BLEND_ZERO)`, with `GR_BLEND_SAME_COLOR_EXT` = 8 /
     `..._ONE_MINUS_...` = 9 for the SAMECOLOR cells and the classic tokens for the controls.
3. Reads the back buffer with `grLfbReadRegion` and compares each cell centre with the reference of 6.1,
   computed from the read-back background. Tolerance 12.
4. Ends with `RESULT {"mode":"blendsq","cells":[...],"pass":N,"fail":N}`.

Run it as `glidelab_run.py 192.168.1.124 blendsq --res 640x480 --cfg 0`, then `--cfg 5`. Cfg 0 is chip 0 alone,
which is what D3D uses. Cfg 5 is plain 4-chip SLI, which shows every chip's blender. Never use an AA cfg. The
mode is checked against the EDID by `glidelab_run.py`.

What each result means:
- **Pass:** A_SAMECOLOR works on this silicon. The HAL change is then a mapping onto a proven function. MesaFX's
  `NV_blend_square` is verified as a side effect.
- **Fail:** stop. Do not advertise. Record it in `retro-3dfx/FINDINGS.md`. Withdraw `GL_NV_blend_square` in the
  GL lane, where it is then a live bug. Close G29 as "not fixable on this silicon" (P3).
- **Ordering.** Run it **last** in a session, or before a clean reboot. A Glide close that is not idle can leave
  the command FIFO enabled, and every later D3D triangle vanishes (G01; recovery is in
  `../onbox/README.md` run #9).

### 4.3 Step 2: the HAL change

**New `KMD/include/vcr_blend.h`** (Win32-free, so `tests/native` compiles exactly what the HAL runs):

```c
#include "vcr_3dregs.h"
/* d3dtypes.h D3DBLEND_* values - vcrdd_d3d.c checks them against the DDK at compile time */
#define VCR_D3DBLEND_ZERO            1u
#define VCR_D3DBLEND_ONE             2u
#define VCR_D3DBLEND_SRCCOLOR        3u
#define VCR_D3DBLEND_INVSRCCOLOR     4u
#define VCR_D3DBLEND_SRCALPHA        5u
#define VCR_D3DBLEND_INVSRCALPHA     6u
#define VCR_D3DBLEND_DESTALPHA       7u
#define VCR_D3DBLEND_INVDESTALPHA    8u
#define VCR_D3DBLEND_DESTCOLOR       9u
#define VCR_D3DBLEND_INVDESTCOLOR   10u
#define VCR_D3DBLEND_SRCALPHASAT    11u
#define VCR_D3DBLEND_BOTHSRCALPHA   12u
#define VCR_D3DBLEND_BOTHINVSRCALPHA 13u
#define VCR_BLENDCAP(b)   (1u << ((b) - 1))   /* D3DPBLENDCAPS_x == 1 << (D3DBLEND_x - 1) */
#define VCR_BLEND_SRC_CAPS_BASE  0x1f33u      /* build 95678704: ZERO ONE SRCALPHA INVSRCALPHA DESTCOLOR
                                                 INVDESTCOLOR SRCALPHASAT BOTHSRCALPHA BOTHINVSRCALPHA */
#define VCR_BLEND_DST_CAPS_BASE  0x003fu      /* ZERO ONE SRCCOLOR INVSRCCOLOR SRCALPHA INVSRCALPHA */

/* same = 1 only on a VSA-100 with Diag\D3DFeat SAMECOLOR (pd->blend_same) */
static __inline unsigned vcr_blend_src(unsigned b, unsigned same)
{
    switch (b) {
    case VCR_D3DBLEND_ZERO:            return BF_ZERO;
    case VCR_D3DBLEND_SRCALPHA:        return BF_SRCALPHA;
    case VCR_D3DBLEND_INVSRCALPHA:     return BF_INVSRCALPHA;
    case VCR_D3DBLEND_DESTALPHA:       return BF_DSTALPHA;      /* G28 decides its fate */
    case VCR_D3DBLEND_INVDESTALPHA:    return BF_INVDSTALPHA;
    case VCR_D3DBLEND_DESTCOLOR:       return BF_COLOR;         /* a source factor's COLOR is the destination's */
    case VCR_D3DBLEND_INVDESTCOLOR:    return BF_INVCOLOR;
    case VCR_D3DBLEND_SRCALPHASAT:     return BF_SATURATE;
    case VCR_D3DBLEND_BOTHSRCALPHA:    return BF_SRCALPHA;
    case VCR_D3DBLEND_BOTHINVSRCALPHA: return BF_INVSRCALPHA;
    case VCR_D3DBLEND_SRCCOLOR:        if (same) return BF_SAMECOLOR;    break;
    case VCR_D3DBLEND_INVSRCCOLOR:     if (same) return BF_INVSAMECOLOR; break;
    }
    return BF_ONE;   /* ONE; SRCCOLOR/INVSRCCOLOR unarmed or on a Banshee/Voodoo3 (8/9 reserved there) */
}
static __inline unsigned vcr_blend_dst(unsigned b, unsigned src, unsigned same)
{
    if (src == VCR_D3DBLEND_BOTHSRCALPHA)    return BF_INVSRCALPHA;
    if (src == VCR_D3DBLEND_BOTHINVSRCALPHA) return BF_SRCALPHA;
    switch (b) {
    case VCR_D3DBLEND_ZERO:          return BF_ZERO;
    case VCR_D3DBLEND_SRCCOLOR:      return BF_COLOR;           /* a destination factor's COLOR is the source's */
    case VCR_D3DBLEND_INVSRCCOLOR:   return BF_INVCOLOR;
    case VCR_D3DBLEND_SRCALPHA:      return BF_SRCALPHA;
    case VCR_D3DBLEND_INVSRCALPHA:   return BF_INVSRCALPHA;
    case VCR_D3DBLEND_DESTALPHA:     return BF_DSTALPHA;
    case VCR_D3DBLEND_INVDESTALPHA:  return BF_INVDSTALPHA;
    case VCR_D3DBLEND_DESTCOLOR:     if (same) return BF_SAMECOLOR;    break;
    case VCR_D3DBLEND_INVDESTCOLOR:  if (same) return BF_INVSAMECOLOR; break;
    }
    return BF_ONE;   /* as build 95678704 for ONE and anything unknown */
}
static __inline unsigned vcr_blend_alphamode(unsigned s, unsigned d, unsigned same)
{
    return AM_BLEND | AM_RGBSRC(vcr_blend_src(s, same)) | AM_RGBDST(vcr_blend_dst(d, s, same)) |
           AM_ASRC(BF_ONE) | AM_ADST(BF_ZERO);      /* alpha channel: G28 */
}
static __inline unsigned vcr_blend_src_caps(unsigned same)
{
    return VCR_BLEND_SRC_CAPS_BASE |
           (same ? VCR_BLENDCAP(VCR_D3DBLEND_SRCCOLOR) | VCR_BLENDCAP(VCR_D3DBLEND_INVSRCCOLOR) : 0);
}                                                   /* 0x1f33 / 0x1f3f */
static __inline unsigned vcr_blend_dst_caps(unsigned same)
{
    return VCR_BLEND_DST_CAPS_BASE |
           (same ? VCR_BLENDCAP(VCR_D3DBLEND_DESTCOLOR) | VCR_BLENDCAP(VCR_D3DBLEND_INVDESTCOLOR) : 0);
}                                                   /* 0x003f / 0x033f */
```

**The old path.** The switch off, a Banshee/Voodoo3, and the 86Box bed (`pd->napalm` = 0) all give:
- the same `alphaMode` word for every one of the 256 (SRCBLEND, DESTBLEND) pairs;
- the same caps (`0x1f33`/`0x003f`) as build 95678704.

## 5. Gating

- **Switch:** `HKLM\SYSTEM\CurrentControlSet\Services\vcrmp\Diag\D3DFeat`, bit `VCR_D3DFEAT_SAMECOLOR`.
  - Take the next free bit when this lands; `vcr_d3dfeat.h` and its one-bit-each test are the arbiter.
  - Read at boot (FindAdapter), like `D3D32` and `D3DBigTex`. The blend caps an application reads at its desktop
    then match its fullscreen PDEV's.
  - **VSA-100 only** (`pd->napalm`). On a Banshee or Voodoo3 the codes are reserved.
- **Default OFF** (absent = 0).
- **Arming:** `REGWRITE HKLM SYSTEM\CurrentControlSet\Services\vcrmp\Diag D3DFeat REG_DWORD <bit>`, then
  `REGREAD` the key back (the value, not the `OK`). Then `scripts/fleet/safe-reboot.py` after the activation
  check. One Diag change per clean boot.

**Is it safe to land default-on?** Not on day one, though it is the safest kind of item in the plan.

- **For:**
  - the mapping changes only requests that are drawn wrong today;
  - the caps are honest in both states;
  - no proven matrix (40/40, 42/42, 83/0) sends these factors, so its register traffic is identical either way;
  - codes 8/9 select a blender input, so they cannot leave the engine busy (inferred).
- **Against:**
  - codes 8/9 have never been observed on this silicon (3.3);
  - the caps change can move a caps-checking title onto a path never seen on `.124`;
  - the project rule is default-off until one supervised boot proves it.

**Graduation.**
- **When:** Step 1 (Glide) passes, and Boot B (section 8) passes `blendsq` at 16 and 32 bpp with the default
  matrices unchanged.
- **How:** flip the default in a separate commit with its own test, by the plan's D3DFeat graduation convention
  (G05 §4.1: a default mask in the miniport, or a `D3DFeatOff` kill mask).
- **Fallback:** if a title regresses only because it now sees the caps, split the caps onto their own bit and
  keep the mapping.

## 6. d3dprobe tests (and the Glide twin)

### 6.1 `blendsq` and `blendsq_force` (new, in `run_test`, `KMD/tools/d3dprobe.c:914`)

**What it draws.**
- Clear to `Cd = 0x004080C0`. `untextured()`, ALPHABLENDENABLE on.
- For each cell: SRCBLEND = DESTBLEND = ZERO, then the cell's pair, then `quad_c` in `Cs = 0x80C08040` (A 0x80,
  RGB C0/80/40). Setting ZERO first means that a factor the runtime did not forward stays ZERO, which is
  visible as "dropped" below.
- The cells are 40x40 at x = 24 + 64·col and y = 24 + 56·row (cols 0-2, rows 0-3), inside the 256x256 readback.
- Afterwards restore ALPHABLENDENABLE FALSE and ONE/ZERO.
- Read each centre, plus the background at (8, 8). The background is the stored `Cd` that the reference uses.

**The reference.**
- Per channel: `v = min(255, round(s·Fs/255 + d·Fd/255))`, with `d` the measured background.
- Then the back buffer's quantisation: R5G6B5 truncate and expand by replication, which is d3dprobe's own
  `expand()`; X8R8G8B8 as is.
- **Tolerance 6 at 32 bpp and 12 at 16 bpp.**
  - Computed for this design, the chip's two plausible roundings (`/255` vs `(x·(f+1))>>8`) differ by at most 1
    at 32 bpp.
  - At 16 bpp the unknown destination expansion (replicate vs zero-fill, 3.2) moves a cell by at most 8.
  - Every SAMECOLOR cell's reference is at least 41 away from the pre-G29 value in some channel, at both
    depths, so the classes cannot overlap.

| row, col | SRCBLEND / DESTBLEND | D3D result | ref 32 bpp | ref 16 bpp (replicated `Cd`) | pre-G29 (ONE) 32 / 16 bpp |
|---|---|---|---|---|---|
| 0,0 | SRCCOLOR / ZERO | Cs² | `914010` | `944110` | `C08040` / `C68242` |
| 0,1 | INVSRCCOLOR / ZERO | Cs(1-Cs) | `2F4030` | `294131` | `C08040` / `C68242` |
| 0,2 | SRCCOLOR / ONE | Cs² + Cd | `D1C0D0` | `D6C3D6` | `FFFFFF` / `FFFFFF` |
| 1,0 | ZERO / DESTCOLOR | Cd² | `104091` | `10419C` | `4080C0` / `4282C6` |
| 1,1 | ZERO / INVDESTCOLOR | Cd(1-Cd) | `30402F` | `314129` | `4080C0` / `4282C6` |
| 1,2 | ONE / DESTCOLOR | Cs + Cd² | `D0C0D1` | `D6C3DE` | `FFFFFF` / `FFFFFF` |
| 2,0 | SRCCOLOR / DESTCOLOR | Cs² + Cd² | `A181A1` | `A582AD` | `FFFFFF` / `FFFFFF` |
| 2,1 | INVSRCCOLOR / INVDESTCOLOR | Cs(1-Cs) + Cd(1-Cd) | `5F7F5F` | `637D5A` | `FFFFFF` / `FFFFFF` |
| 2,2 | ONE / ZERO (control) | Cs | `C08040` | `C68242` | same |
| 3,0 | DESTCOLOR / ZERO (control, untested today) | Cs·Cd | `304030` | `314131` | same |
| 3,1 | ZERO / SRCCOLOR (control, untested today) | Cd·Cs | `304030` | `314131` | same |
| 3,2 | ONE / ONE (control, untested today) | sat(Cs + Cd) | `FFFFFF` | `FFFFFF` | same |

(The table is illustrative. The probe computes every value at run time from the measured background.)

**Classification of a SAMECOLOR cell:**
- `ref`: within tolerance of the D3D result;
- `old`: within tolerance of the pre-G29 drawing, with the factor replaced by ONE;
- `dropped`: within tolerance of the result with the unadvertised factor left at ZERO, which means the runtime
  did not forward it;
- `other`: anything else.

The 4 control cells use factors every Voodoo has and are always pass/fail. They also close part of
`../reports/history.md` §6.1, where DESTCOLOR as a source, SRCCOLOR as a destination and ONE/ONE have no check.

**Pass rules.**
- **`blendsq`** (caps-respecting):
  - a cell whose factors `g_caps.SrcBlendCaps` / `DestBlendCaps` advertise must be `ref` (counted pass/fail);
  - a cell with an unadvertised factor is **SKIPPED**, not drawn ("SrcBlendCaps lacks SRCCOLOR"), the
    d3dprobe convention;
  - on any driver, the 4 controls run.
- **`blendsq_force`**:
  - draws all 12 cells;
  - advertised cells are pass/fail as above;
  - an unadvertised cell is a **note** (`{"test":"blendsq_force","at":"src*src","class":"old"}`), neither pass
    nor fail, so the probe stays driver-neutral.

  It answers the question the caps cannot: what the HAL draws when a title ignores them.
- **Expected:**
  - off: `blendsq` = 4 pass + 8 skipped; `blendsq_force` = 4 pass + 8 notes of class `old`;
  - armed: 12/12 pass in both.
- **The default list.** Neither test joins the default list (`:1247`) until graduation. The recorded 40/40 and
  42/42 matrices then stay comparable, and `d3dprobe_run.py` fails a run whose explicit `--tests` list had a
  skip.

## 9. Risk to proven paths

| path | risk |
|---|---|
| default 16 bpp D3D (no D3D32/BigTex) | none off: identical words and caps, pinned pair by pair. Armed: only the four requests change, and they are drawn wrong today |

## 11. Side findings for other gaps

- **Halo (G17, G91).** Three of Halo's eight framebuffer blend functions are BLENDOP REVSUBTRACT, MIN and MAX
  (`halo.exe` `.rdata` `0x65e004`: 1,1,1,1,3,4,5,1). We do not advertise BLENDOP, and nothing in the HAL reads
  `rs[171]`, so those effects are presumably drawn as ONE/ONE ADD (inferred). That is worth checking when G17's
  "glow drawn as a translucent square" is chased.
- **MesaFX (GL lane).** `GL_NV_blend_square` ships on the V5 6000 and has never been measured. Step 1 verifies or
  refutes it.
- **Method.** A byte scan for `push imm; push 0x13` is unreliable on its own. zlib's `zalloc(opaque, 19, 4)`
  produces exactly that sequence in four of the staged renderers. Every hit needs disassembly.
