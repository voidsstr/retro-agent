## 0. Verdict

1. **Do not build a DX8-level DDI (`MaxStreams >= 1`).** On the VSA-100 it would add exactly two features no other
   route can give: BLENDOP (subtract and reverse subtract only) and per-channel COLORWRITEENABLE (§2.3). No staged
   title is known to need either. Its costs are the ones the gap lists: driver state blocks, the DX8 DP2 tokens,
   vertex/index-buffer handles, and every D3D8/9 title moving onto new code at once. 3dfx's own NT DX8 path could
   never have run, **even when compiled**: their NT HAL setup never sets the GetDriverInfo2 flag (§2.9).
2. **Most of the "DX8 gains" are already reachable from the DX7 DDI**, read from the runtimes:
   - **Caps2.** In the DX7 path d3d8 copies DirectDraw's `ddCaps.dwCaps2` into the device's Caps2. Its
     GetDeviceCaps keeps D3DCAPS2_DYNAMICTEXTURES (0x20000000), FULLSCREENGAMMA (0x20000) and CANRENDERWINDOWED
     (0x80000), and these values equal the DDCAPS2 bits (§2.5).
     - **CANRENDERWINDOWED is set by the runtime itself** for the primary display, in both paths.
     - **DYNAMICTEXTURES** is `DDCAPS2_DYNAMICTEXTURES` in our `DrvGetDirectDrawInfo`.
     - **FULLSCREENGAMMA** is `DDCAPS2_PRIMARYGAMMA` (we already implement `DrvIcmSetDeviceGammaRamp`).
   - **PresentationIntervals is recomputed by the runtime from Caps2 in both paths.** It is ONE, plus TWO/THREE/FOUR
     with `DDCAPS2_FLIPINTERVAL`, plus IMMEDIATE with `DDCAPS2_FLIPNOVSYNC` (§2.5). A driver-supplied
     PresentationIntervals is ignored.
   - **MaxPointSize:** a `MaxStreams = 0` driver must report 0, and the VSA-100 has no point sprites anyway.
   - **A8 is not needed by Halo.** G17 read `halo.exe`: it maps `a8`/`y8`/`ay8`/`a8y8` to "no D3D format", and no
     Halo map holds such a bitmap (`G17.md` §1 item 1). No other title on `.124` is known to want A8.
   - **DXVERSION is not per-application.** d3d8 sends 0x802; ddraw.dll and d3d9 both send 0x902 (§2.6). It cannot
     tell a DX5 title from a DX7 one, so it cannot scope G08's legacy-state work.
3. **What only GetDriverInfo2 can give is the format-operation list.** That means X8R8G8B8 (and any other)
   render-target textures by our choice, A8 textures, and our own Z operations, independent of the PCI-id table
   d3d8/d3d9 apply to `121a:0009`. **This does not need the DX8 DDI** (§2.1 to §2.4):
   - d3d8 and d3d9 put a driver on the DX8 DDI (type 6/7) **only when `D3DCAPS8.MaxStreams != 0`**
     (`GetDDIType`, d3d8 `0x6d9ee320`, d3d9 `0x4fe0fc80`). This settles runtime.md §14's open item.
   - With `MaxStreams = 0` the device keeps today's DDI class (3 or 4). That means the DX7 token stream,
     runtime-emulated state blocks (G40), and no VB/IB handles.
   - The runtime still takes the driver's D3DCAPS8 and, if any entry is `DDPF_D3DFORMAT`, the driver's format list
     instead of the legacy converter **and instead of the PCI table**.
   - It checks a `MaxStreams = 0` caps record against a "DX7 shape" first; a record that fails makes the HAL vanish
     (§2.3).
4. **The design (§4) is this "GDI2 hybrid", default-OFF, in two steps:**
   - **`GDI2` (identity).** Set `DDHALINFO_GETDRIVERINFO2`. Answer DXVERSION, GETD3DCAPS8, GETFORMATCOUNT and
     GETFORMAT with exactly what the runtime synthesises from our DX7 data today, so that nothing a D3D8/9
     application sees changes. This step proves the mechanism on silicon.
   - **`RTX8`.** Add `D3DFORMAT_OP_OFFSCREEN_RENDERTARGET` to X8R8G8B8. This is Halo's render-target route
     (`G36.md` §1 item 2: five of Halo's eight render targets are X8R8G8B8, which the DX7 DDI can never be granted).
   - DX5-DX7 titles are untouched: ddraw.dll uses the flag only to send DXVERSION and DEFERRED_AGP_AWARE (§2.6).
5. **Build it only when Halo's render targets are wanted through the driver.** That is G36's decision (Part D). The
   prerequisites are placement (G21 bit 1), coherency (G37's 3D half), X8R8G8B8 sampling with alpha forced to one
   (G17), and D3D32 (G20). Until then the identity step alone gains nothing visible.
6. **Priority P2, effort M** for the hybrid. The full DX8 DDI (tier 2, §5) is P3: do not build it unless a census
   shows a staged title needs BLENDOP or COLORWRITEENABLE.
7. **Side results** for other gaps:
   - **G10:** D3D8's CheckDepthStencilMatch never depth-checks D3DFMT_D16 for any driver, so X8R8G8B8+D16 is
     "match" by the runtime's own rule. Only Z promotion fixes G10; format operations cannot.
   - **G91:** no `MaxStreams = 0` driver can expose BLENDOP or COLORWRITEENABLE to D3D8/9. The caps-shape check
     rejects the HAL.
   - **G74 Q4:** dynamic textures do not need the DX8 DDI.
   - **runtime.md §3:** the MIPMAP texture cap comes from the mip-filter bits, not from DDSCAPS_MIPMAP.

   §13 lists these corrections.

## 2. What the XP SP3 runtimes do with a GetDriverInfo2 driver (read in the binaries)

### 2.1 d3d8's driver-data fetch (`0x6d9b4cb0`)

`-0x178(%ebp)` is `DD_HALINFO.dwFlags` (the HAL info sits at `-0x308`; `dwFlags` is at +0x190, after
`VIDEOMEMORYINFO` 0x4c and `DDNTCORECAPS` 0x13c). `testb $0x8` tests `DDHALINFO_GETDRIVERINFO2`.

| step | where | with the flag | without it (today) |
|---|---|---|---|
| second DdQueryDirectDrawObject, **with the DX7 texture-format buffer** | `0x6d9b4d82-0x6d9b4dd3` | **skipped** | done |
| DXVERSION (type 4, size 0x18, value **0x802**) | `0x6d9b4f41-0x6d9b4f72` | sent; the result is not checked | - |
| GETD3DCAPS8 (type 1, expected 0xd4) | `0x6d9b4fc0-0x6d9b4ff1` | if HANDLED and DD_OK: **`dwActualSize` must be exactly 0xd4 or the whole fetch fails** (`0x6d9b5002` → `0x6d9b52b0`, returns 0). Copies 0x35 dwords (`0x6d9b500f-0x6d9b501f`); then `Caps = ddCaps.dwCaps` (`0x6d9b5021-0x6d9b5027`), Caps2 gains 0x80000 (CANRENDERWINDOWED) for the primary display (`0x6d9b502a-0x6d9b5046`), and bit 0 of `+0xf8` marks "caps from the driver" | - |
| GETFORMATCOUNT (type 2, 0x18) and GETFORMAT (type 3, 0x34) per index | `0x6d9b50be-0x6d9b5255` | sizes checked exactly (`0x6d9b5104`, `0x6d9b51e5`). Each format goes into a DDSURFACEDESC with `dwFlags = DDSD_PIXELFORMAT` | - |
| if GETFORMATCOUNT is not handled | `0x6d9b525a-0x6d9b52aa` | re-query the DX7 texture list | - |
| **DX7 hwCaps copy and the D3DExtendedCaps query** (0x74 bytes) | `0x6d9b52c3-0x6d9b535c` | **never reached** | done |
| ZPixelFormats (0x3e4) | `0x6d9b5362-0x6d9b53ae` | done | done |
| DEFERRED_AGP_AWARE (type 0x18, size 0x10) | `0x6d9b5731-0x6d9b575f` | sent once | - |
| "DDI level" `0x4c` | `0x6d9b583f-0x6d9b5863` | **8 if MaxStreams (`caps+0xbc`) != 0, else 7** if the driver has DrawPrimitives2 | 7 |
| PCI-id table (KnownDriverFlags `0x104`) | `0x6d9b5872-0x6d9b599e` | consulted only below 8 | consulted |

**Consequence:** with the flag set, D3D8 never sees our D3DNTHAL_GLOBALDRIVERDATA caps or D3DExtendedCaps. Our
D3DCAPS8 must be complete, and it must always be answered.
- If GETD3DCAPS8 goes unanswered, the synthesis at `0x6d9af058-0x6d9af070` runs on DX7 buffers that this path never
  filled (inferred), and the HAL is lost.
- A wrong `dwActualSize` loses the HAL outright.

d3d9 does the same, with three differences (`0x4fe039ee-0x4fe03cea`; the non-flag path `0x4fe0438d`, which holds the
ExtendedCaps query at `0x4fe043d9`, is skipped):
- **DXVERSION** sends `DD_RUNTIME_VERSION` from the registry, defaulting to **0x902** (`0x4fe0379f-0x4fe037b8`).
- **GETD3DCAPS9 (type 0x10, 0x130 bytes)** is asked first. Only if it is answered does d3d9 ask GETDDIVERSION (0x23).
- **Otherwise it falls back to GETD3DCAPS8** (`0x4fe03c16-0x4fe03ce3`). It checks the size the same way, zeroes the
  first DX9-only field (`caps+0xd4`, `0x4fe03cd0`) and sets its "caps from the driver" flag.

Types 0x11, 0x12, 0x13, 0x21 and 0x22 are asked too. When one is answered, its size is checked exactly
(`0x4fe03fe7`, `0x4fe04271` → `0x4fe04c10`). When one is not answered, it is skipped.

**The rule for our handler:** answer only the types implemented here, always with the exact structure size, and
leave every other type at `DDERR_CURRENTLYNOTAVAIL`.

### 2.2 The DDI type: MaxStreams decides, and the hybrid keeps today's class

**d3d8 `GetDDIType` (`0x6d9ee320-0x6d9ee39d`)** is called from device init (`0x6d9eea75`), which stores the result in
device `+0x28` (`0x6d9eea86`). The device's copy of the driver caps sits at `+0x40`, so `+0x5c` is DevCaps and
`+0xfc` is MaxStreams. The function builds the type in steps:

| condition | type |
|---|---|
| `+0x16c` set | 3 (DX6) |
| then `+0x170` set | 4 (DX7) |
| then DevCaps HWTRANSFORMANDLIGHT (0x10000) | 5 |
| then **MaxStreams (`+0xfc`) != 0** | **6 (DX8)** |
| then HWTRANSFORMANDLIGHT as well | 7 |

**d3d9 (`0x4fe0fc80-0x4fe0fd32`)** applies the same steps to caps at `+0x140` (DevCaps `+0x15c`, MaxStreams
`+0x1fc`). It reaches 8/9 (DX9) only through `+0x214` = `caps+0xd4`, which the GETD3DCAPS8 fallback zeroes.

**The DDI factory** (d3d8 `0x6d9dbb93-0x6d9dbcc0`, jump table `0x6d9dbf90`) builds:

| type | object size | constructor |
|---|---|---|
| 3, 4, 5 | 0xf4 | `0x6d9e0d60`, `0x6d9e45b0`, `0x6d9e4870` |
| 6, 7 | 0x1f0 | `0x6d9ddb10`, `0x6d9e0cb0` |
| 10, 11 | 0x2c8 | - |

**So `MaxStreams = 0` keeps the DX6/DX7 DDI object vcrdd gets today.** That means:
- the same DP2 tokens;
- `EmulateStateBlocks` forced on for type ≤ 5 (d3d8 `0x6d9e8c05`/`0x6d9e8c32`, G40 §2.1);
- no vertex/index-buffer handles.

Which of 3 or 4 vcrdd gets is still unread (G40 open question 6), and the hybrid changes neither input.

**Hardware vertex processing (side result, read).** CreateDevice (`0x6d9c9d91-0x6d9c9e03`) refuses:
- HARDWARE_VERTEXPROCESSING without D3DDEVCAPS_HWTRANSFORMANDLIGHT;
- MIXED without it;
- PUREDEVICE without D3DDEVCAPS_PUREDEVICE.

Each refusal returns `8876086c`. This was runtime.md §14's first inferred item. No DDI level changes it, because the
VSA-100 has no T&L.

### 2.3 The "DX7 shape" check for a `MaxStreams = 0` caps record

d3d8 `0x6d9ac340` (called from the adapter-caps setup at `0x6d9ac4d1`, `0x6d9ac568` and `0x6d9aca6b`) and d3d9
`0x4fdf6d3c-0x4fdf6de6` (the same masks) require **TextureCaps != 0 and FVFCaps != 0**. When MaxStreams is 0, a
caps record must also satisfy **every** row below, or the function returns `8876086c` and the caps are not taken:

| field (D3DCAPS8 offset) | required |
|---|---|
| MaxPointSize (0xb0) | == 0.0 (`flds 0x6d9a1404` = 0.0f; `jp` = not equal). 3dfx's DX8 caps used 1.0, "Required for DX 8 support" (`VH5/D3INIT.C:3623`) |
| VertexShaderVersion (0xc4) / PixelShaderVersion (0xcc) | `0xfffe0000` / `0xffff0000` |
| MaxVolumeExtent (0x60), MaxVertexBlendMatrixIndex (0xac) | 0 |
| MaxVertexIndex (0xb8) | 0xffff (d3d9: also ≥ 0xfffe) |
| DevCaps (0x1c) | no bit of `0xfdf40000` |
| RasterCaps (0x24) | no bit of `0xffc00000` |
| PrimitiveMiscCaps (0x20) | no bit of `0xffffff89`. So **COLORWRITEENABLE (0x80) and BLENDOP (0x800) are forbidden** |
| TextureCaps (0x3c) | no bit of `0xfffcb200` |

Today's synthesised caps pass (MiscCaps 0x72). **Consequence for G91:** a DX7-DDI driver, and the hybrid, can never
offer BLENDOP or COLORWRITEENABLE to D3D8/9. Setting either in `dpcTriCaps.dwMiscCaps` would make the whole HAL
disappear. DX7 itself has no such render states. These two features are the only things a full DX8 DDI would add
on this silicon (§3).

### 2.4 The format list: a `DDPF_D3DFORMAT` entry switches the runtime to the driver's operations

d3d8's builder (`0x6d9af000` region) scans the list at `0x6d9af0f3-0x6d9af112` for any entry whose
`ddpfPixelFormat.dwFlags == DDPF_D3DFORMAT` (0x200000). d3d9 does the same at `0x4fdfbba0`.

| path | what it does |
|---|---|
| **DX8 list** (`0x6d9af1b0-0x6d9af24f`) | Drops the non-D3DFORMAT entries. Turns the old 0x20 flag into `3DACCELERATION` (0x800), and for a HAL adds `DISPLAYMODE` (0x400) as well (`0x6d9af224-0x6d9af242`). **It does not read KnownDriverFlags.** It does not convert the ZPixelFormats list either, so Z formats must be in our list. |
| **legacy list** (today) | Converts each DX7 DDPIXELFORMAT (`0x6d9b6850`; runtime.md §4.1). Adds render-target ops from the PCI table (`0x6d9af18a-0x6d9af319`). Converts the Z list (`0x6d9af3a9-0x6d9af47e`; D16 stays D16_LOCKABLE when table flag 0x80 is set). Adds display entries from `dwDeviceRenderBitDepth` (`0x6d9af484-0x6d9af6b5`). |
| **common tail**, both paths (`0x6d9af6b8-0x6d9af6f4`) | `OFFSCREEN_RENDERTARGET` (0x8) gains 0x110; `SAME_FORMAT_UP_TO_ALPHA` (0x100) gains 0x10; `ARBITRARY_COLOR_DEPTH` (0x80) gains `ZSTENCIL` (0x40). Then the 3DACCELERATION checks. |

**The legacy builder's display entries** are:
- a 16-bit display format with `SAME_FORMAT_RENDERTARGET`;
- X8R8G8B8 with `SAME_FORMAT_RENDERTARGET`, under a gate (`0x18c & 1`);
- one `DISPLAYMODE|3DACCELERATION` entry per DDBD bit (16 → the 16-bit format, 24 → R8G8B8, 32 → X8R8G8B8).

**The PCI table applies to the legacy list only.** Those are the ops runtime.md §4.3 decoded for `121a:0009 = 0x4580`:

| table bit | effect |
|---|---|
| 0x100 | R5G6B5 render target |
| 0x400 | A8R8G8B8 render target |
| 0x4000 | `OFFSCREEN_RENDERTARGET` instead of `SAME_FORMAT_UP_TO_ALPHA` |
| 0x80 | keep D16_LOCKABLE |

**The DDPIXELFORMAT layout for a D3DFORMAT entry** (`DDK8/ddraw.h`; the runtime reads entry `+0x50/+0x58/+0x5c`):

| offset | field |
|---|---|
| +8 | `dwFourCC` = D3DFORMAT |
| +0xc | `dwPrivateFormatBitCount` |
| +0x10 | `dwOperations` |
| +0x14 | `MultiSampleCaps` (wFlipMSTypes, wBltMSTypes) |

**MIPMAP correction:** `D3DPTEXTURECAPS_MIPMAP` (0x4000) is added to a `MaxStreams = 0` driver's TextureCaps whenever
TextureFilterCaps carries any mip bit (`0x3003c`; `0x6d9af848-0x6d9af884`). That is where `EV/caps_124.txt`'s
`00004007` gets its 0x4000. runtime.md §3 guessed DDSCAPS_MIPMAP.

### 2.5 Caps2 and PresentationIntervals in both paths

**DX7 path** (`0x6d9b4deb-0x6d9b4e29`):

| D3DCAPS8 field | taken from |
|---|---|
| Caps | `ddCaps.dwCaps` |
| Caps2 | `ddCaps.dwCaps2`, plus CANRENDERWINDOWED (0x80000) when the device is the primary display |
| Caps3 | `ddCaps.dwSVCaps` |

**GDI2 path:** Caps2 and Caps3 come from the driver's D3DCAPS8; only Caps is overwritten.

**GetDeviceCaps** (`0x6d9ad9f8-0x6d9ada62`, both paths):
- `Caps &= 0x02020000`;
- `Caps2 &= 0x220a0002` (plus CANMANAGERESOURCE 0x10000000 when allowed), plus CANCALIBRATEGAMMA (0x100000) when a
  device field at `+0x33d8` is set (inferred: a registered gamma calibrator, ddraw's `GammaCalibrator` key);
- `Caps3 &= 0x7fffffe0`;
- **PresentationIntervals = ONE (1); 0xf if the driver Caps2 has `DDCAPS2_FLIPINTERVAL` (0x200000); `|=` IMMEDIATE
  (0x80000000) if it has `DDCAPS2_FLIPNOVSYNC` (0x400000).**

**Consequences:**
- **Reachable from the DX7 DDI today, by DirectDraw caps alone:**
  - DYNAMICTEXTURES (`DDCAPS2_DYNAMICTEXTURES` 0x20000000, `DDK8/ddraw.h:3280`);
  - FULLSCREENGAMMA (`DDCAPS2_PRIMARYGAMMA` 0x20000; whether XP's ddraw sets it for our `GCAPS2_CHANGEGAMMARAMP`
    driver is unverified, and caps v2 prints Caps2);
  - PresentationIntervals TWO/THREE/FOUR (`DDCAPS2_FLIPINTERVAL`, with `DDFLIP_INTERVALn` honoured in `Dd_Flip`).
- These belong to G56/G74 (dynamic textures) and G54/G78 (flip intervals), not to a DDI change.
- **A trap for any GDI2 driver: its D3DCAPS8.Caps2 must carry `DDCAPS2_FLIPNOVSYNC`.** Otherwise D3D8 silently loses
  PRESENT_INTERVAL_IMMEDIATE. That is exactly the "--novsync = 85.0 fps" bug recorded at `vcrdd_ddraw.c:103-105`.
  3dfx's DX8 caps set Caps2 to CANRENDERWINDOWED only (`VH5/D3INIT.C:3384-3390`) and would have lost it.

### 2.6 DX5-DX7 titles: ddraw.dll uses the flag twice, d3dim700 never

**ddraw.dll** tests `DD_HALINFO.dwFlags & 8` in two places only:
- it records it as a DirectDraw-global flag (`0x7376987d-0x73769886`, `or [ebx+0x7],0x20`);
- it sends **DXVERSION 0x902** (`0x7376a106-0x7376a171`), and **discards the result** (`and [ebp-0x50],0`).

The recorded flag gates one generic GetDriverInfo2 helper (`0x73768c02`, test at `0x73768c20`). It is used for
DEFERRED_AGP_AWARE (type 0x18, size 0x10, `0x7376a180-0x7376a193`).

The DX7 object setup continues unchanged at `0x7376a198`. **d3dim700.dll does not contain the GUID** (searched as
bytes). DX5-DX7 titles (JK, MotS, R6, AvP, Thief Gold, SS2, Shogo, the UE1 D3DDrv renderers) therefore see the same
DX7 data as today, and one or two more GetDriverInfo queries per DirectDraw object.

### 2.7 dxg.sys marshalling: the outer `dwExpectedSize` is 0x18, and the copy-back is `dwActualSize`

dxg's GetDriverInfo thunk handles GetDriverInfo2 like this:
- It matches the GUID at `0x16836-0x16842` and sets the expected size to **0x18** (`0x16844`).
- It copies **6 dwords** of the caller's buffer into a kernel buffer at `ebp-0x464` (`0x16876-0x16882`): the GDI2
  header, the format index and one more dword.
- Its driver-call wrapper (`0x1318e`) presets `ddRVal = 0x88760028` (`DDERR_CURRENTLYNOTAVAIL`) and requires
  `GETDRIVERINFOSET`. On HANDLED plus DD_OK it returns the driver's **`dwActualSize`** (`0x1320c-0x1320f`).
- dxg then copies **that many bytes** from the kernel buffer back to the process (`0x168d3-0x168fd`, after a
  ProbeForWrite of the user range only).

Two rules follow:
- **Use the GDI2 header's `dwExpectedSize`, never `p->dwExpectedSize`.** The DDK says so (`DDK8/d3dnthal.h:1203-1206`),
  and dxg passes 0x18 there. Our `answer()` helper would copy 0x18 bytes of a 0xd4-byte D3DCAPS8 and report 0xd4.
  dxg would then hand the process 0xbc bytes of uninitialised kernel stack as caps.
- **Never report more than was written, and never more than 0x400** (the kernel buffer). Nothing in dxg bounds the
  copy-back.

### 2.8 CheckDepthStencilMatch (side result for G10)

d3d8's IDirect3D8 vtable is at `0x6d9a14c0`; slot 12 is `0x6d9ad790`. The Z format is depth-compared with the render
target (`0x6d9ad956-0x6d9ad973`; `0x6d9b5e10` returns each format's size, inferred from its use) **only when it is
"strict"**:
- D16_LOCKABLE (`0x6d9ad897`);
- formats 0x48-0x4f (the stencil and X8D24 family) that the table at `0x6d9abce0` marks;
- D32/D24X8 when the IDirect3D8 field `+0x34e0` exceeds 0x78 (`0x6d9ad8bc-0x6d9ad8cf`; inferred to be the SDK version
  the application passed to Direct3DCreate8, 120 for DX8.0).

`ZSTENCIL_WITH_ARBITRARY_COLOR_DEPTH` (0x80) on the Z entry clears strictness (`0x6d9ad917-0x6d9ad922`).
**D3DFMT_D16 (80) is never strict**, which explains `EV/caps_124.txt` "X8R8G8B8/D16 match 1" for every driver,
legacy or GDI2.
- G10 can only be fixed by making the pair render (Z promotion), not by format operations.
- The hybrid's identity step leaves the D16 answer unchanged.

### 2.9 3dfx: the NT DX8 path was unreachable, and its DX8 data has bugs not to copy

- **The flag is never set on NT.** `NTSpecificInit` assigns `pHalInfo->dwFlags = 0 | DDHALINFO_GETDRIVERINFOSET;`
  (`VH5/DDINIT.C:1643-1645`), and it runs on NT (`VH5/DDINIT.C:458-464`).
  - The only `DDHALINFO_GETDRIVERINFO2` in that file is in the `#ifndef WINNT` branch (`:214-250`).
  - Even there it comes **after** the statement's semicolon (`:235-241`), so it is a dangling expression.
  - The Win9x tree sets it correctly (`W9X/DDINIT.C:193-198`).
  - So 3dfx's NT GetDriverInfo2 handler (`VH5/DDFXNT.C:1067-1164`) was dead code **even in retro3dfx's DX=8 build**
    (`c34d62f`, which did not touch `DDINIT.C`). This adds to vendor-01.
- **Do not copy these from `BuildDX8TextureFormats` and `BuildD3DCaps8`:**
  - `OFFSCREEN_RENDERTARGET` on every 8- and 16-bit format in the list (`VH5/D3INIT.C:2310-2410`, `:2528-2540`).
    Of these, the VSA-100 colour buffer can be only 1555 (G93), and our HAL draws none of them. A4R4G4B4, X4R4G4B4,
    R3G3B2, A8R3G3B2, L8, A8, A4L4, A8L8, P8 and A8P8 are not render-target formats at all;
  - the FXT1 FourCC, which D3D8 has no name for (`:2487`);
  - `MaxStreams = 1`, "Indicates a DX 8 driver" (`:3633-3635`), which moves the driver onto the DX8 DDI;
  - `MaxPointSize = 1.f` (`:3623`), which fails the shape check if MaxStreams is 0;
  - Caps2 without `DDCAPS2_FLIPNOVSYNC` (`:3384-3390`);
  - a GETFORMAT handler that indexes its array with no bounds check (`VH5/DDFXNT.C:1129-1130`).

## 4. Design: the GDI2 hybrid

### 4.1 Switch and plumbing

- **Gate.** `Diag\D3DFeat` bit `GDI2` (the identity step) and bit `RTX8` (X8R8G8B8 render-target textures). Both are
  default OFF and positive flags. The bit numbers are assigned by whoever lands the `D3DFeat` carrier; until it
  exists, use a dedicated `Diag\D3DGdi2` DWORD with bit 0 = GDI2 and bit 1 = RTX8.
  - Read **at boot** by the miniport, like `D3D32`/`D3DBigTex` (`KMD/miniport/vcrmp.c:238-244`). The caps an
    application reads at its desktop must be the ones its fullscreen mode's PDEV has (the `D3DBigTex` comment at
    `:242-244`).
- **Miniport** (`vcrmp.c:445-466`): new `VCR_INFO_F_GDI2` and `VCR_INFO_F_GDI2_RTX8` bits in `vcr_info.flags`
  (`KMD/include/vcr_ioctl.h:110-140`; 0x8000 and 0x10000 are free today, and the integrator confirms). Set only on a
  Voodoo backend.
- **Display driver** (`vcrdd_2d.c:441-470`, beside `rt32`/`tex_*`):
  - `pd->gdi2 = pd->napalm && (flags & VCR_INFO_F_GDI2)`;
  - `pd->gdi2_rtx8 = pd->gdi2 && pd->rt32 && pd->tex_x8 && (flags & VCR_INFO_F_GDI2_RTX8)`. `tex_x8` is G17's
    X8R8G8B8-texture bit;
  - one INFO "armed" event in the 513/16-18 style: `armed (Diag\D3DFeat GDI2): D3D8/9 caps and formats answered by
    the driver (GetDriverInfo2, DX7 DDI kept: MaxStreams 0)%s`.
- **Never build with a higher `DIRECT3D_VERSION`.** `KMD/out/ddi/d3dnthal.h` defines the GDI2 structures only under
  `DIRECT3D_VERSION >= 0x0800`. Raising it pulls in the DX8 types and breaks the DX7 ones the HAL uses: compiling
  the build's headers with `-DDIRECT3D_VERSION=0x0800` gave 15 errors (`D3DLIGHTTYPE`, `D3DRENDERSTATETYPE`,
  `D3DPRIMITIVETYPE`, …). The new header therefore defines its own layout-identical structures (§4.3).

### 4.2 `DrvGetDirectDrawInfo` (`vcrdd_ddraw.c:112-114`)

```c
hal->dwFlags = DDHALINFO_GETDRIVERINFOSET;          /* unchanged line */
VcrDdD3dHalInfo(pd, hal);
/* Diag\D3DFeat GDI2: only where the D3D half was published (the same early-return
 * predicate as VcrDdD3dHalInfo), so the runtime never asks for caps we would not answer */
if (pd->gdi2 && hal->lpD3DGlobalDriverData)
    hal->dwFlags |= DDHALINFO_GETDRIVERINFO2;
```

`pd->gdi2_published` records the outcome. The GDI2 answers check the same predicate as `VcrDdD3dDriverInfo`
(`pjRegs && g2d_ok && !d3d_disabled`). If the HAL gives up between the two (G02), GETD3DCAPS8 goes unanswered and
D3D8 loses the HAL, which is the same outcome as today's give-up (§10).

### 4.3 The GetDriverInfo2 dispatcher, and a new Win32-free header

**`KMD/include/vcr_gdi2.h`** (new; compiled as is by the native test, like `vcr_rtfmt.h`):

```c
#define VCR_GDI2_MAGIC          0xFFFFFFFFul
#define VCR_GDI2_GETD3DCAPS8    1u
#define VCR_GDI2_GETFORMATCOUNT 2u
#define VCR_GDI2_GETFORMAT      3u
#define VCR_GDI2_DXVERSION      4u
#define VCR_GDI2_CAPS8_SIZE     0xd4u   /* sizeof(D3DCAPS8): d3d8 0x6d9b5002, d3d9 0x4fe03ca1 check it exactly */
#define VCR_GDI2_COUNT_SIZE     0x18u   /* DDNT_GETFORMATCOUNTDATA: d3d8 0x6d9b5104 */
#define VCR_GDI2_FORMAT_SIZE    0x34u   /* DDNT_GETFORMATDATA: d3d8 0x6d9b51e5 */
#define VCR_GDI2_DXVER_SIZE     0x18u   /* DDNT_DXVERSION */
#define VCR_GDI2_KBUF_MAX       0x400u  /* dxg.sys's kernel buffer (0x1687c); the copy-back is unbounded */

typedef struct { vcr_u32 reserved, magic, type, expected; } vcr_gdi2_hdr;    /* DDNT_GETDRIVERINFO2DATA */
typedef struct { vcr_u32 v[VCR_GDI2_CAPS8_SIZE / 4]; } vcr_caps8;            /* D3DCAPS8, by offset */
/* field offsets (checked with _Static_assert against DDK8/d3d8caps.h on mingw, 2026-11-12):
 * Caps 0x08 Caps2 0x0c Caps3 0x10 PresentationIntervals 0x14 CursorCaps 0x18 DevCaps 0x1c
 * PrimitiveMiscCaps 0x20 RasterCaps 0x24 ... TextureCaps 0x3c TextureFilterCaps 0x40 LineCaps 0x54
 * MaxTextureWidth 0x58 MaxVolumeExtent 0x60 MaxVertexW 0x70 GuardBandLeft 0x74 StencilCaps 0x88
 * FVFCaps 0x8c TextureOpCaps 0x90 MaxVertexBlendMatrixIndex 0xac MaxPointSize 0xb0
 * MaxVertexIndex 0xb8 MaxStreams 0xbc VertexShaderVersion 0xc4 PixelShaderVersion 0xcc */

typedef struct { vcr_u32 fmt, ops; } vcr_gdi2_fmt;   /* D3DFORMAT (or FOURCC), D3DFORMAT_OP_* */

/* copy length of an answer: the GDI2 header's expected size (NOT the outer one,
 * which dxg sets to 0x18), never more than the kernel buffer */
static vcr_u32 vcr_gdi2_copy_len(vcr_u32 size, vcr_u32 gdi2_expected);

/* the runtime's DX7 -> D3DCAPS8 synthesis (d3d8 0x6d9aeaf0-0x6d9aed31), as a function of
 * our DX7 data: in = the D3DDEVICEDESC_V1 and D3DNTHAL_D3DEXTENDEDCAPS bytes vcrdd publishes */
static void vcr_caps8_from_dx7(const vcr_u32 *devdesc_v1, const vcr_u32 *extcaps,
                               vcr_u32 dd_caps, vcr_u32 dd_caps2, vcr_u32 dd_svcaps, vcr_caps8 *out);
/* the DX7 shape a MaxStreams-0 record must have (d3d8 0x6d9ac35f-0x6d9ac3eb) - 1 = taken */
static int vcr_caps8_shape_ok(const vcr_caps8 *c);
/* the identity format list (+ RTX8), flags = VCR_GDI2_F_RT32 | _TEX32 | _TEXDXT | _TEXX8 | _RTX8 */
static unsigned vcr_gdi2_formats(unsigned flags, vcr_gdi2_fmt *out, unsigned max);
```

**`vcrdd_d3d.c`, `VcrDdD3dDriverInfo`**: a new branch before the final `return 0`. The GUID is `f828169c-a8e8-11d2-a1f2-00a0c983eaf6` (`DDK8/ddrawint.h:49`).

```c
if (pd->gdi2 && geq(&p->guidInfo, &gdi2)) {
    vcr_gdi2_hdr *h = (vcr_gdi2_hdr *)p->lpvData;
    if (h && h->magic == VCR_GDI2_MAGIC)      /* else a DDStereoMode query: not available */
        gdi2_answer(pd, p, h);                /* known types only; ddRVal stays CURRENTLYNOTAVAIL otherwise */
    return 1;
}
```

**`gdi2_answer`:**

| type | answer |
|---|---|
| **DXVERSION** | store `{pid = EngGetCurrentProcessId(), version}` in a 16-entry ring in the PDEV; INFO event once per pid; `dwActualSize = 0x18`, DD_OK |
| **GETD3DCAPS8** | build into a local `vcr_caps8` (§4.4); assert `vcr_caps8_shape_ok`, or answer nothing and WARN once; `memcpy(p->lpvData, &c, vcr_gdi2_copy_len(0xd4, h->expected))`; `dwActualSize` = the same length; DD_OK |
| **GETFORMATCOUNT** | `count` = `vcr_gdi2_formats(...)`; `dwActualSize = 0x18` |
| **GETFORMAT** | **bounds-check `dwFormatIndex`** (unanswered if out of range). Write a 32-byte DDPIXELFORMAT: `dwSize` 32, `dwFlags` DDPF_D3DFORMAT, `dwFourCC` = fmt, `dwOperations` (+0x10) = ops, every other dword 0 (no multisample). `dwActualSize = 0x34` |
| anything else | 0x10 (GETD3DCAPS9), 0x11-0x13, 0x18/0x19 (AGP), 0x21-0x23: **not answered** |

The existing per-query INFO log (`vcrdd_ddraw.c:703-704`) gains the GDI2 type and the actual size, so the ring shows
the whole exchange.

caps8 builder; `g_gd.hwCaps` is the device description. The app-visible result equals today's by construction. The
host test (§8) checks the construction against a port of the runtime's masks and against `EV/caps_124.txt`.

### 4.5 The format list: identity, then RTX8

**Identity list.** This is the legacy builder's output for our DX7 list and DDBD, with `121a:0009`'s table flags,
before the runtime's common tail. One entry per format, holding the union of its operations:

| D3DFORMAT | ops | condition | why (today's source) |
|---|---|---|---|
| R5G6B5 (23) | TEXTURE \| OFFSCREEN_RENDERTARGET \| SAME_FORMAT_RENDERTARGET \| DISPLAYMODE \| 3DACCELERATION | always | converter + table 0x100/0x4000 + 16-bit display entries |
| A1R5G5B5 (25), A4R4G4B4 (26) | TEXTURE | always | converter (table bits 0x800/0x1000 clear) |
| A8R8G8B8 (21) | TEXTURE \| OFFSCREEN_RENDERTARGET | `tex_32` | converter + table 0x400 |
| X8R8G8B8 (22) | SAME_FORMAT_RENDERTARGET, + DISPLAYMODE \| 3DACCELERATION with `rt32`, + TEXTURE with G17's `tex_x8` | 32 bpp modes exist (always on `.124`) | display entries; G17's DX7 entry |
| DXT1, DXT2, DXT3, DXT4, DXT5 (FOURCC) | TEXTURE | `tex_dxt` | converter |
| D16_LOCKABLE (70) | ZSTENCIL | always | Z list + table 0x80 |
| X8D24 (76), S8D24 (74) | ZSTENCIL | `rt32` | Z list (masks `0x00ffffff`, stencil `0xff000000`; the runtime maps them to the API's D24X8/D24S8, as measured today) |

- `MultiSampleCaps` is 0 everywhere: no anti-aliasing (campaign choice).
- **Mode independence:** the list never reads `pd->bpp` (runtime.md §11, the `4a9793b` lesson). It depends only on
  boot-latched bits.

**RTX8** (second step): X8R8G8B8 `|= TEXTURE | OFFSCREEN_RENDERTARGET`, only with `rt32 && tex_x8`. The runtime's
tail adds 0x110. Nothing else changes.

**Never** add a render-target op to a format outside {R5G6B5, X8R8G8B8, A8R8G8B8}. The 3D engine's colour buffer is
16 or 32 bpp RGB (`KMD/include/vcr_rtfmt.h`). 1555 targets are G93's business and come through the same table once
proven.

**A8** is designed but **not built**, because no title needs it (Halo is refuted by G17). If one ever does:
- A8 (28) `TEXTURE` behind its own bit;
- sampled as TMU format 2 (A8) with the TMU colour forced to 0 (`SST_TC_ZERO`, `G34.md:575`);
- with a d3dprobe `a8_decode` test.

### 4.6 What happens on the old path (both bits clear)

- `hal->dwFlags` is the same single assignment. `VcrDdD3dDriverInfo` reaches the new branch only with `pd->gdi2`, so
  GUID `f828169c` (never sent today) still falls through to "not available".
- Caps, formats, Z list, register traffic and DP2 handling are byte-for-byte unchanged.
- The `ext_caps()` refactor is a pure move; the host test compares its output with the old inline block for every
  combination of Diag bits.

### 4.7 Logging (no new hot-path cost)

The new events fire only at DirectDraw enable and process start: one "armed", one per GDI2 query (already the case for
every GetDriverInfo), and one DXVERSION per pid. Nothing is added to DrawPrimitives2. The new 513 sub-ids follow the
G40/G76 numbering; the integrator checks them against the other designs.

## 5. Tier 2, the full DX8 DDI: not recommended, and what it would take

Build it only if a census (open question 5) shows a staged title rendering wrongly **because** BLENDOP or
COLORWRITEENABLE are missing. It would need:
1. **`MaxStreams >= 1`.** The DDI becomes type 6, and DX8 tokens arrive: SETSTREAMSOURCE(UM), SETINDICES,
   DRAWPRIMITIVE(2), DRAWINDEXEDPRIMITIVE(2), CLIPPEDTRIANGLEFAN, SETVERTEXSHADER (an FVF handle), BUFFERBLT,
   VOLUMEBLT, ADDDIRTYRECT/BOX, MULTIPLYTRANSFORM (`DDK8/d3dnthal.h:553-576`).
2. **Vertex and index buffers.** Without `_NT_D3DDEVCAPS_HWVERTEXBUFFER/HWINDEXBUFFER` they stay in system memory as
   user-memory streams (3dfx `VH5/D8DP2.C:96-300` for the shape) (inferred).
3. **State blocks.** Either G40's Step 1 (record/execute/capture, plus the DX8 CREATE), or `EmulateStateBlocks=1`
   on the box as a stop-gap (read only above type 5, d3d8 `0x6d9e8c0b-0x6d9e8c2d`).
4. **D3D9 vertex-declaration conversions** for a DX8 driver ("Cannot convert vertex declaration for dx8 driver" in
   `d3d9.dll`), with new refusal paths.
5. **The BLENDOP and COLORWRITEENABLE mappings** themselves (G91).
6. **Effort XL**, with every D3D8/9 title on new DDI code at once and no proven reference: 3dfx's never ran (§2.9).

## 6. Gating

- **Default OFF**, two positive bits read at boot, **one Diag change per clean boot**:
  1. a boot with the new DLL and both bits clear (the byte-for-byte path);
  2. `GDI2` alone (identity);
  3. `GDI2|RTX8`, only after G17's `tex_x8`, G21 bit 1 and G37's 3D half are proven, each in its own earlier boot.
- **Not safe to land default-on.** Even in identity mode it changes *who* computes every D3D8/9 title's caps and
  formats. An error there removes the HAL (§2.1, §2.3); it does not mis-render.
  - Identity also brings nothing visible, so there is no reason to turn it on by default before RTX8 is wanted.
  - `GDI2|RTX8` may become the default only after a full D3D8/9 sweep (all deployed D3D8/9 titles, both depths)
    matches the both-clear boot, and Halo's render-target scenes are checked in game.
- **Kill switch:** clear the bits. The miniport reads them at boot, so a clean boot restores today's path exactly.

## 7. d3dprobe tests

## 10. Risk to proven paths

| path | risk | containment |
|---|---|---|
| default 16 bpp path (bits clear) | none: an unchanged assignment and an unreachable branch | python pins; boot A's golden |
| D3D8/9 with GDI2 | the driver now supplies every caps and format the runtime used to synthesise. An error **removes the HAL** (wrong size → fetch fails; a non-DX7-shaped record → `8876086c`; a missing display-mode op → no fullscreen device) | identity by construction, with tests 3, 6, 8 and 10; a zero-diff golden on silicon; clearing the bit restores today exactly |

| kernel safety | an over-reported `dwActualSize` leaks dxg kernel stack to the process | tests 1 and 2: the copy length is clamped and equals the bytes written |
| DX5-DX7 titles | ddraw.dll's extra DXVERSION and DEFERRED_AGP_AWARE queries only (§2.6) | one DX6 title in boot B |
| state blocks and tokens | would change only if MaxStreams were non-zero | test 7; "0 unparsed" and G40's tripwire on silicon |
| Glide/OpenGL coexistence, SLI state, the flip path, the miniport | not touched (DirectDraw caps data only). G01's stale-FIFO hazard is unchanged and must be handled before any boot (G01) | - |
| G02 give-up | if the HAL gives up after the flag was published, GETD3DCAPS8 is unanswered and D3D8 has no HAL until the next mode set: the same outcome as today's give-up | answers use the same predicate as the published flag |

## 12. Open questions

1. **d3d9 in GDI2 mode:** the fetch, DDI type, shape check and list scan were read; nothing was run. Settle it with
   `d3d9probe caps9` in boot B.
2. **The legacy builder's `0x18c & 1` gate** for an X8R8G8B8 `SAME_FORMAT_RENDERTARGET` entry. The identity list
   always carries it. It is identical at `.124`'s 32 bpp desktop (the boot-B golden proves it). A 16 bpp desktop was
   not checked, because no staged title starts from one.
3. **Does XP's ddraw add `DDCAPS2_PRIMARYGAMMA` itself** for a `GCAPS2_CHANGEGAMMARAMP` driver (then FULLSCREENGAMMA
   is already there)? caps v2's Caps2 answers it.
4. **D3DCAPS2_DYNAMICTEXTURES on the DX7 DDI:** the caps path copies `DDCAPS2_DYNAMICTEXTURES`. Does d3d8's resource
   code then create and Lock a DEFAULT dynamic texture on a type-4 device? Measure it with a DirectDraw-caps-only
   switch (G56/G74's item), before any GDI2 work. This answers G74 Q4 differently from its expectation.
5. **Does any staged D3D8/9 title use BLENDOP (D3DRS 171) or COLORWRITEENABLE (168)?** It is the only question that
   could justify tier 2.
   - It cannot be counted in the HAL: the runtime cannot hand those states to a DX7-DDI driver usefully (inferred).
   - It needs a runtime-side census: a logging `d3d8.dll`/`d3d9.dll` proxy, staged per title in the build VM, never
     on the box's system32.
6. **Halo's slot 1 and 2 (A8R8G8B8, back-buffer and half size, not powers of two)** are skipped under
   `DisableAlphaRenderTargets` (`G36.md` §3). Nothing else in this design needs non-power-of-two support, which the
   VSA-100 lacks.
7. **Which DDI class (3 or 4) vcrdd gets** (G40 open question 6). The hybrid leaves both inputs alone, so the answer
   is the same in every boot.
8. **FREE_DEFERRED_AGP (0x19):** does a non-AGP driver ever receive it after answering nothing to
   DEFERRED_AGP_AWARE? The ring in boot B shows it. It is harmless either way, because it is unanswered.

## Appendix: re-deriving the runtime evidence

```sh
d=$(mktemp -d) && cd "$d"                       # an empty directory of its own
for f in D3D8.DL_ D3D9.DL_ DDRAW.DL_ DXG.SY_; do
  7z x -y "/mnt/retro-share/Files/OS/XPSP3-FLEET/I386/$f" >/dev/null; done
md5sum d3d8.dll d3d9.dll ddraw.dll dxg.sys       # f099b129..., 0607cbc6..., a340cd71..., ac728056...
for f in d3d8.dll d3d9.dll; do i686-w64-mingw32-objdump -d "$f" > "${f%.dll}.dis"; done
i686-w64-mingw32-objdump -d -M intel ddraw.dll > ddraw.dis
i686-w64-mingw32-objdump -d -M intel dxg.sys   > dxg.dis
grep -n 'testb  $0x8,-0x178(%ebp)' d3d8.dis      # 0x6d9b4d82, 0x6d9b4ed5, 0x6d9b5731: the GETDRIVERINFO2 gates
grep -n 'cmpl   $0xd4,-0xc(%ebp)' d3d8.dis       # 0x6d9b5002: the caps size check
grep -n -A30 '^6d9ee320:' d3d8.dis               # GetDDIType: 3/4/5, then 6 only if 0xfc(%ecx) (MaxStreams) != 0
grep -n -A30 '^4fe0fc80:' d3d9.dis               # the d3d9 twin (0x1fc)
grep -n 'cmpl   $0xfffe0000\|testl  $0xffffff89' d3d8.dis d3d9.dis   # the DX7-shape check
grep -n 'cmpl   $0x200000,' d3d8.dis d3d9.dis    # the DDPF_D3DFORMAT list scan
grep -n -A12 '^6d9ada37:' d3d8.dis               # PresentationIntervals from Caps2 bits 0x200000/0x400000
grep -n 'movl   $0x902,' d3d9.dis                # DD_RUNTIME_VERSION default; d3d8: 'movl   $0x802,'
grep -n '0x737683f8' ddraw.dis                   # the GUID's three uses; flag tests: 'BYTE PTR \[e..+0x1b4\],0x8'
grep -n 'mov    edi,0x1f3dc' dxg.dis             # dxg's GetDriverInfo2 case (expected size 0x18 follows)
```

The D3DCAPS8 offsets and the GDI2 structure sizes were checked by compiling `_Static_assert`s with
`i686-w64-mingw32-gcc -I DDK8` against `d3d8caps.h`:
- D3DCAPS8 is 0xd4; MaxStreams is at 0xbc, Caps2 at 0x0c, MaxPointSize at 0xb0.
- D3DFMT X8R8G8B8 = 22, A8R8G8B8 = 21, R5G6B5 = 23, D16_LOCKABLE = 70, D16 = 80.
- `DDNT_GETFORMATCOUNTDATA` (0x18) and `DDNT_GETFORMATDATA` (0x34) follow from `DDK8/d3dnthal.h:1358-1376`. They could
  not be compiled against the build's headers without `DIRECT3D_VERSION 0x0800`, which breaks the DX7 types (§4.1).
