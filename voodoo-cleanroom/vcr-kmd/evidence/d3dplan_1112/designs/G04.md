# G04 design: the Max Payne freeze of 2026-10-04 (an investigation, not a guessed fix)

- **Lane:** clean-room, `vcr-kmd` (`vcrmp.sys` + `vcrdd.dll`), the Voodoo 5 6000 in `.124`.
- **Kind:** needs-investigation. **Priority P0. Effort L.**
- **Depends on:** G01, G02 (they hold the fixes for the leading hypothesis), G03, G76, G79.
- **Written:** 2026-11-12, from the reports `hal-30`, `hal-25`, `games-10/11`, `history-03..06` and `onbox-12`,
  the code, the 09-29, 10-04 and 11-12 evidence, and the staged Max Payne tree.
- **How it was produced:** design only. Nothing was built, run or deployed, and no box was contacted.

Path aliases: `KMD` = `voodoo-cleanroom/vcr-kmd`, `EV` = `KMD/evidence`, `ONBOX` = `EV/d3dplan_1112/onbox`,
`LIB` = `/mnt/retro-share/Files/Games-Library`, `HOSTEV` = `~/.retro-fleet/evidence/v56k-gametune_1001-fbshot_probe-20261004`,

"(inferred)" marks a statement that comes from general Windows/3dfx knowledge, not from a file read here.

---

## 0. Verdict

1. **The gap is real and its cause is still unproven.** This design changes no driver behaviour "for G04" on a
   guess. Instead it delivers three things:
   - the means to watch a frozen Direct3D session **without taking win32k's display lock** (section 3);
   - a short attended protocol that reproduces the two leading preconditions one at a time (section 4);
   - an outcome-to-fix map and the rule for lifting `.124`'s `blk` (sections 5-6).
2. **New evidence makes one hypothesis lead** (section 1.2): a stale Glide command FIFO left by the 4-chip Quake II
   session four minutes before Max Payne (G01), followed by the silent 2D give-up (G02). On 09-29 Max Payne ran
   after a cold boot with no Glide session before it, and did not freeze.
3. **Runner-up:** an escape (the default `vcrctl fbshot`) caught in a priority inversion behind a high-priority game
   thread. Something in Max Payne's process held the CPU above normal priority on 10-04. Nothing in the static read
   of the game explains that, so it must be measured.
4. **What G04 owns:** the instrumentation, the protocol and the `blk` decision. The likely fixes belong to G01 and
   G02 and are designed there.

### 1.2 New facts found for this design

1. **A Glide session ran just before the freeze. Before the clean run, none did.**
   - **10-04 (froze):** `fbab_quake2.json` (written 19:50) records a Quake II 4-chip SLI overlay session:
     `sli_chips 4`, `cfgSliLfbCtrl 1e0f0030`, 104 flips while it was read, so the attract demo was running.
     `fbab_maxpayne.json` follows at 19:54, in the same boot. How Quake II was closed is not recorded.
   - **09-29 (did not freeze):** the breaker trip at 13:16:55 cold-booted `.124` (`FIND`, 09-29 13:55 entry). The
     next captures are System Shock 2 at 13:34, Max Payne at 13:42 (menu with text; WM_CLOSE exited it), then the
     Glide titles Serious Sam TFE at 13:46 and TSE at 13:54 (file times in `EV/lan_20260929_sweep/`).
     No Glide session is recorded before Max Payne in that boot.
   - **Both days used the same blocked default fbshot** (`FIND:332`). So the escape alone did not freeze the game on
     09-29.
   - **The visual audit (V-05) finds the same correlation:** Red Faction, Shogo and H&D draw nothing, or lose their
     backdrop, after a Glide/OpenGL session in the same boot, and render fully in Glide-free boots.
   - **The mechanism was measured on 11-12 (`onbox-01`, `onbox-02`):**
     - a Glide close that takes h5 Glide's not-idle path leaves `cmdFifo0` enabled;
     - the miniport resets the engine at a mode set only when the chip reads BUSY (`miniport/vcrmp_hw.c:571-572`);
     - with the FIFO merely enabled, D3D clears worked and every triangle vanished;
     - a host write into the FIFO window made it busy (status `0xa1f`); 1.3 s later
       `512 ERR a=9 b=2 c=0xa1f "2D engine never went idle"` turned acceleration off for the PDEV;
     - from then on DrawPrimitives2/Clear2 answered `DD_OK` and drew nothing (`display/vcrdd_d3d.c:1859, 1887`), while
       `Dd_Flip` kept flipping (`display/vcrdd_ddraw.c:315-361`): the game stays alive behind a frozen picture.
2. **Glide's FIFO window is the bottom of our DirectDraw heap.**
   - Glide puts `cmdFifo0` at 96 KB .. ~1116 KB, i.e. 0x18000-0x117000 (`KMD/README.md:80-86`, `:712-716`; the
     11-12 registers: base 0x18 pages, size field 0xfe = 255 pages).
   - Our desktop sits at the top of video memory, and the DirectDraw heap runs from offset 0 up to it
     (`display/vcrdd_ddraw.c:45-60`, `heap_range`). So the first surfaces of every fullscreen D3D game land inside
     Glide's window.
   - On 11-12 the windowed device's target (0x40000), Z (0x80000) and texture (0xc0000) were all inside it.
   - On 10-04 Max Payne's scanned-out buffer was 0x4b0000-0x960000 (`fbab_maxpayne.json`: `start 004b0000`,
     `mb1_end 00960000`, i.e. 1280x960x4). Something allocated before it occupies 0x0-0x4b0000, which contains the
     whole window. Which surface that is (a second back buffer, the Z buffer or textures) is in the ContextCreate line
     at LogLevel 2.
   - A CPU write into that range (a Lock, a CPU texture upload, a HEL blit) is command data to a stale FIFO. The
     README records the first desktop layout hanging the engine (0xA5F) exactly that way.
3. **The crawl was CPU starvation, not the display lock.**
   - `wmic` and `taskkill` take no display lock; only the escape does. hal-25/R7's "fits the crawl" therefore explains
     the blocked escape, not the crawl.
   - The probe was only ~3x faster at `/high` (38 s against 120 s), and `taskkill /f` at `/high` still took ~3 s.
     That fits a runnable thread at priority 13 or higher, or a bus-level stall, with starved threads progressing only
     on XP's ~4 s anti-starvation boosts (inferred).
   - The 11-12 stale-FIFO state did not make the box crawl (the agent and `vcrctl` worked normally). So the crawl looks
     like a property of Max Payne's process, not of the FIFO (inferred).
4. **The static read of the staged binaries** (`LIB/MaxPayne`) explains no sustained hog:
   - `rlmfc.dll`'s CPU calibration (0x10025500-0x100255c4):
     - saves the priority class and thread priority;
     - sets `HIGH_PRIORITY_CLASS` (0x80) and `THREAD_PRIORITY_TIME_CRITICAL` (15);
     - busy-waits 0.5 s on `QueryPerformanceCounter` (loop at 0x10025450; constant 0.5 at 0x1002b048);
     - restores both.
   - `sndmfc.dll` sets its listener thread's priority from a static the game writes (`S_Listener::setThreadPriority`,
     default 0).
   - `MaxPayne.exe`'s real imports are hidden by SafeDisc (KERNEL32 lists only `GetProcAddress` and four others).
5. **`vcrctl` takes `GetDC(NULL)` for every command except `fbshot --probe`** (`tools/vcrctl.c:2101-2104`), so
   `probe-mem`, `probe-pci` and `probe-vga` touch USER/GDI before reading a register. Freeze-time reads must not.
6. **The record disagrees about where the blocked escape waits.** `FIND:332` (09-29) says "in user space ... killed
   cleanly"; `FIND:127` and the README (10-04) say "in the kernel ... no timeout ends it". A thread snapshot of a
   blocked `vcrctl` settles it.

## 3. Instrumentation, built before any box time (all log-only)

### 3.1 The Direct3D heartbeat ("beat"): `Diag\D3DBeat`, default OFF

**`KMD/include/vcr_beat.h`** (new, Win32-free, host-tested). It holds:

- **`vcr_d3d_beat`**, a fixed 96-byte record: magic `'VBT1'`, size, version.
  - Display fields:
    - `seq`, `where` (1 DP2, 2 Clear2, 3 Flip, 4 Lock, 5 ContextCreate, 6 context gone, 7 engine given up), `pid`;
    - the mode (w, h, bpp) and `ctxs`;
    - `dp2s`, `tris`, `clears`, `flips_ok`, `flips_still`, `locks`, `locks_in_glide_fifo`;
    - `g2d_ok`, `giveups`, `max_spin`, `exclusive_pid`.
  - Miniport fields:
    - `ms`, `boot`, `status`;
    - `fifo0_basesize`, `fifo0_readptr`, `fifo0_amin`, `fifo0_depth`, `fifo0_holes`;
    - `scan` (vidDesktopStartAddr).
- **`vcr_beat_due(now, last, period)`.** It is due when `last` is 0 and when the counter wraps or goes backwards.
- **`vcr_giveup_class(status, basesize, exclusive_pid)`**, which returns one of:
  - `STALE_CMDFIFO`: status bit 11 set, basesize bit 8 set, no Glide owner;
  - `GLIDE_OWNS`;
  - `ENGINE_BUSY`;
  - `FIFO_NEVER_DRAINED`.
- **`VCR_GLIDE_FIFO_LO`/`HI`** = 0x18000/0x117000, and `vcr_beat_in_glide_fifo(off, len)`. There is one definition,
  shared with G01's design.

**Display DLL (`vcrdd.dll`).**

- **Counters.** New per-PDEV counters in `display/vcrdd.h`, beside the existing `flip` state.
- **`VcrDdBeat(pd, where)`.** It goes in a new `display/vcrdd_beat.c`.
  - It is integer only, makes no register access, and is not called with the FPU state saved.
  - It returns at once unless `pd->beat_on` is set and `vcr_beat_due(EngQueryPerformanceCounter(), pd->beat_last,
    qpf)` holds (the period is one second).
  - Otherwise it sends `IOCTL_VCR_D3DBEAT`.
- **Call sites:**
  - `D3d_DrawPrimitives2`: right after the context check and **before** `w.drawable` is computed (`vcrdd_d3d.c:1859`);
  - `D3d_Clear2`: before `:1887`;
  - `Dd_Flip`: at entry, counting `DD_OK` and `DDERR_WASSTILLDRAWING` separately;
  - `Dd_Lock`: also counting a Lock whose surface overlaps the Glide FIFO window;
  - `D3d_ContextCreate` and `ctx_free`.

  A given-up PDEV therefore keeps beating. The old shape answered `DD_OK` in silence.
- **`VcrDdRoom` / `VcrDd2dSync`** (`display/vcrdd_2d.c:92-133`) record their loop count in `pd->max_spin`: one compare
  per call, no extra read.
- **`pd->beat_on`** comes from `IOCTL_VCR_INFO` flag `VCR_INFO_F_D3DBEAT` (0x8000, the next free bit, positive), read
  at `DrvEnableSurface` like `D3D32`.

**Miniport.**

- `IOCTL_VCR_D3DBEAT` (`VCR_CTL(0xa10)`) is handled by `VcrBeat()` in `miniport/vcrmp_log.c`.
  1. It checks the size and magic, and stamps `ms` and `boot`.
  2. It **reads** chip 0's status, the `cmdFifo0` block (0x80020-0x80048) and `vidDesktopStartAddr` (0xe4). It makes
     no writes.
  3. It stores the record as `...\vcrmp\Diag\Live\D3DBeat`: REG_BINARY in a `REG_OPTION_VOLATILE` subkey, never
     flushed. That keeps it out of the disk hive and gone at reboot.
  4. It logs a new event, `VCR_EV_DD_BEAT` 514, at INFO (a = where, b = dp2s, c = tris, d = flips_ok).
- Periodic beats are accepted only when `Diag\D3DBeat`=1, read at FindAdapter. `where` = 7 is always accepted
  (section 3.2).

**Reading it.**

- The agent's `REGREAD HKLM SYSTEM\CurrentControlSet\Services\vcrmp\Diag\Live` runs inside the agent: no child
  process and no display lock.
- The decoder is a new `tools/vcrbeat.py`, following the `vcrphases.py` pattern.

**Cost.**

- **On** (one-second period):
  - one QPC read per DP2/Clear2/Flip/Lock call;
  - per second, one IOCTL, one volatile registry write and 9 register reads.
- **Off:** one branch per call. No IOCTL and no register access.
- **Either way,** the drawing path's register traffic is identical (pinned, section 7).

### 3.2 A give-up names its cause: default ON (error path only)

- **What `give_up()` does** (`display/vcrdd_2d.c:83-89`), before `g2d_ok = 0`:
  - reads `cmdFifo0` baseSize, readPtr, aMin and depth, through the same `rd()` that `VcrDdGlideReset3d` already uses;
  - logs a second event, 512 a=10 "give-up detail", with the `vcr_giveup_class` verdict;
  - sends the beat record unthrottled with `where` = 7, whether or not `D3DBeat` is on.
- **What the miniport does with that record:**
  - writes it to `Diag\D3DGiveUp`, non-volatile and flushed;
  - records it as a phase (`VcrPhase`), so `vcrphases.py --prev` shows it even after a hard hang and a power cycle.
- **Why this can be default-on:** the proven path (no give-up) is byte-for-byte unchanged. At a give-up the box is
  already on its failure path, and the new work is register reads plus one 15-30 ms flush. The existing 512 a=9 event
  keeps its fields, so current decoders still work.

### 3.3 `vcrctl` (user mode)

- **No DC** for `probe-mem`, `probe-pci`, `probe-vga`, or for the two new commands below. Today only `fbshot --probe`
  skips `GetDC`.
- **New: `threads [--delta MS] <pid|image|all>`.**
  - It calls `NtQuerySystemInformation(SystemProcessInformation)` through `GetProcAddress`.
  - Per thread it prints: priority, base priority, state, wait reason, kernel and user ms, context switches, start
    address, and ticks in the current state.
  - `--delta` takes two snapshots and prints CPU ms per thread in the interval, highest first, plus the idle process.
  - It raises itself to `REALTIME_PRIORITY_CLASS` for this bounded work, so a hog cannot starve the measurement.
- **New: `probe-regs [--lat N] [--scan K]`.**
  - It finds the board with fbshot's discovery (`fb_probe_open`).
  - Through vcrprobe it reads: status, the 3D `intrCtrl`, the `cmdFifo0/1` blocks, `vidDesktopStartAddr` and
    `vidProcCfg`.
  - `--lat N` times N single status reads (min/avg/max microseconds).
  - `--scan K` CRC32s K 4 KB windows of the scanned-out buffer. That answers "is the picture changing?" with 1/1200 of a
    probe frame's reads.
- **Escape guard.** Escape commands refuse while `Diag\Live\D3DBeat` is under 3 s old with `ctxs` > 0, unless given
  `--force`. That turns the rule "no escapes under a D3D game" into a refusal (G79).

### 3.4 Host: `tools/d3dwatch.py <host> --exe MaxPayne.exe --out <dir>`

- **Every 2 s:** `PING`, `PROCLIST`, `REGREAD ...\Diag\Live`, then the classifier (a pure function, host-tested).
- **Triggers:** no new beat for 6 s while the game lives; `giveups` rising; or `fifo0_basesize` bit 8 with no Glide
  owner.
- **The freeze bundle** it then captures:
  - `threads --delta 1000 all`, twice;
  - `typeperf` (% Interrupt, % DPC, % Privileged, % User, Processor Queue Length, Context Switches/sec; 3 samples)
    through `cmd /c start "" /realtime /b /wait`;
  - `probe-regs --lat 1000 --scan 3`, twice, 2 s apart;
  - `WINLIST`.
- **After the bundle:**
  - It alerts and waits for the person. It never closes the game and never sends an escape while the game lives.
  - After the person has closed the game, it fetches `vcrctl log <seq>`, a `vcrctl reg` dump, `PROCLIST` and
    `DISPLAYCFG`.
  - Everything goes to the evidence directory, never the scratchpad.

### 3.5 Logging for the investigation boots

- **`LogLevel` = 2** drops the per-DP2 DEBUG events that wrap the ring in seconds.
- **`LogEntries` = 8192** (1 MB non-paged; the miniport accepts 64-16384, `miniport/vcrmp_log.c:282-283`).
- **Timing is unchanged by these settings:** `VcrDd()` formats and IOCTLs every event and the level is checked in the
  miniport (`display/vcrdd_log.c:20-39`, `vcrmp_log.c:326`; G52). So the experiment is not perturbed.

### 3.6 Optional fault injection: `Diag\D3DFault`, default off, read at boot

- **Trigger:** a per-run value read at the next beat.
- **Effect:** it clears `g2d_ok` exactly as `give_up()` does, with no register write.
- **Use:** it reproduces H-B's user-visible signature on any title, on demand. It also serves as G02's test hook.

## 4. The attended protocol

### 4.1 Before every boot

1. **Activation:** `LICSTATUS` (or `wmic path Win32_WindowsProductActivation get /value`).
2. **PXE hold for `.124`** (MAC `00:d0:b7:40:96:a9`, which is NOT in `never_offer`):
   `scripts/pxe/pxe_server.py --arm 00:d0:b7:40:96:a9`, checked with `--list-holds`. A hard hang is recovered by a
   power cycle, which boots from the network first.
3. **Reboot:** only through `scripts/fleet/safe-reboot.py`.

### 4.2 Before every session

1. **Board settings:** `SSTH3_SLI_AA_CONFIGURATION` = 5 and `Diag\SliAA` = 0 (no AA, the user's choice). The DAEMON
   Tools SafeDisc emulation must be on.
2. **No stray processes** in `PROCLIST`. On 10-02 a leftover Carmageddon 2 spun at 100 % for 14 h.
3. **Record the screensaver state.**
4. **Chip state:** `vcrctl reg 0` and `vcrctl reg 80024`, with no D3D application running. Expect status idle and
   `cmdFifo0.baseSize` 0.
5. **Probe check:** `d3dprobe render --tests beat` passes (section 7.1).
6. **Start `d3dwatch`.**
7. **Pacing:** `--pace 5000`, and at least 5 s between mode switches.

**The person's checklist,** written into the session log every minute and at any freeze:

- Does the cursor follow the mouse?
- Does a menu item highlight on hover?
- Is music or sound still playing?
- Does Num Lock toggle?
- Any flicker between two frames?
- When was the freeze first noticed?

### 4.3 E-ctl (optional, any time, no driver involved)

- Run Max Payne on `.133` (GeForce4 Ti) or `.123` at its menu for 5 minutes.
- Take `threads --delta 1000 MaxPayne.exe` at 1 and 4 minutes, close with WM_CLOSE.
- This tells whether a high-priority busy thread is simply how Max Payne runs (H-D as a game property).

### 4.4 Boot 1: instrumentation only (`LogLevel` 2, `LogEntries` 8192, `D3DBeat` 1; logging values, no behaviour switch)

The current build is 95678704, and **G01/G02 stay off.** That is the point of this boot: see the build as shipped, and
reproduce the 10-04 precondition without its cure.

1. **S0.** Run `d3dprobe render --full --res 1280x960 --bpp 32 --tests beat,clear,flat,tex`. It must pass.
2. **E0a, twice.**
   - Launch through the staged `Play Max Payne.bat`. On `.124` it opens 1280x960x32@85, with vsync on.
   - Leave it 10 minutes at the menu. The person moves the mouse once a minute.
   - At 2 minutes, take `threads --delta 1000 all` and `typeperf`. These are the baseline priorities.
   - At 5 minutes, run `probe-regs --scan 3` twice, 2 s apart.
   - Close with WM_CLOSE, then fetch `vcrctl log` and the registers.
   - In the second E0a, the person also plays the tutorial for 5 minutes. That is the first in-game look on this HAL
     (G73).
3. **E0b.** Hands off for 12 minutes, so the 10-minute screensaver timeout is crossed (H-I).
4. **E1.** Run `fbshot --probe` under `start /high` three times, 2 minutes apart (H-E).
5. **E2.** The default fbshot (escape) once, with an EXECW timeout of 25 s, then the same under `start /high` (H-C).
   - This deliberately breaks the "no escape under a D3D game" rule. Do it attended, and keep `taskkill /f` under
     `start /realtime` ready.
   - Before recovering, take a thread snapshot of the blocked `vcrctl`.
6. **E3: reproduce 10-04's precondition.** Make a Glide client end without disabling its FIFO, trying these in order
   and checking `vcrctl reg 80024` (bit 8) after each:
   1. `glidelab abandon --cfg 5` (exits without `grSstWinClose`, paced);
   2. Quake II 4-chip, attract demo for 60 s, `quit` from its console (as `lan_sweep` does);
   3. `glidelab fill --cfg 5 --frames 1000000` ended mid-run by `vcrctl pace-kill <pid>` (a killed Glide client).

   Then run Max Payne for 10 minutes, watched. Its outcomes:

   | result | meaning |
   |---|---|
   | (i) triangles blank, clears and CPU writes visible | H-A1 |
   | (ii) renders, then `g2d_ok` 0 with class `STALE_CMDFIFO` and a frozen picture | H-A2 + H-B: the 10-04 shape |
   | (iii) renders 10 minutes clean | H-A not sufficient for Max Payne |

   A control run: the same sequence after a Glide close that left the FIFO off. It separates "a Glide session before"
   from "the FIFO left on", and it is also the G03 (leftover 3D state) check.

   Recover with `taskkill /f` under `start /realtime` plus `vcrctl pace-mark`, then `vcrctl modeseq` (paced). On 11-12
   that ran the busy-at-mode-set reset. Then end the boot.

### 4.5 Boot 2 (one change: G01's switch, proposed `Diag\D3DSafe` bit 0)

- Repeat S0, then E3, then one E0a.
- **Expected:**
  - the FIFO is stopped at the mode set or at ContextCreate;
  - the beat's `fifo0_basesize` reads 0;
  - Max Payne renders for 10 minutes.

## 6. Exit criteria and the `blk` decision

- **Closed** when one of these holds:
  - **(a) The mechanism is shown:** E3 reproduces the 10-04 shape on 95678704, and Boot 2 shows G01's guard turning
    the same sequence into a clean 10-minute session. In addition, E0a x2 and E0b are clean with the beat continuous,
    the menu text visible in a `--scan` frame, and WM_CLOSE exiting.
  - **(b) Nothing reproduces:** E0-E3 and E-ctl all come out clean. Then G04 is closed as not reproduced, and
    `D3DBeat` stays armed on `.124` for supervised D3D sessions.
- **Honest statistics.** The freeze was seen once in about four sessions. So three clean E0 runs alone leave a 42 %
  chance (0.75^3) of missing a 1-in-4 event that is still there. Closure (a) rests on the mechanism, not on the count.
- **Lifting `blk`** (the user's decision): proposed once G01 and G02 are default-on, or armed on `.124`, and closure
  (a) or (b) holds.
  - D3D titles may rejoin readiness rounds with `d3dwatch` running: a stall captures the bundle and pages a person.
  - The rule "no escapes under a D3D game" stays, now enforced by the escape guard.
  - Update `KMD/README.md:156`, `PLAN:553-556` and `docs/lan-multiplayer-status.md:82-83` in the same commit.

## 7. Tests

### 7.1 d3dprobe: `beat` (explicit, never in the default list; fullscreen or windowed)

- **What it reads:** `Diag\Live\D3DBeat` through `RegQueryValueExA`. The d3dprobe link line gains `-ladvapi32`
  (`KMD/Makefile:102`). If the value is absent (switch off), the test is SKIPPED, not failed.
- **What it draws.** T = 100 untextured triangles (a 10x10 grid in the 256x256 window) plus a Clear, per frame, in this
  order:
  1. warm-up frame W1; sleep 1.2 s;
  2. W2, then read r0;
  3. F = 120 frames; sleep 1.2 s;
  4. trigger frame X; sleep 100 ms, then read r1.
- **Reference values,** computed rather than golden. The beat is taken at call ENTRY, so X's triangles are not yet
  counted:

  | check | expected |
  |---|---|
  | `r1.tris - r0.tris` | (F + 1) x T = 12,100, exactly |
  | `r1.flips_ok - r0.flips_ok` | F + 1 fullscreen, 0 windowed |
  | `pid` (r0 and r1) | d3dprobe's own |
  | `seq` | increased |
  | `ms` | +1000 or more |
  | `g2d_ok` | 1 |
  | `giveups` | unchanged |
  | `fifo0_basesize` bit 8 | clear: a stale FIFO fails the check, so it doubles as the stale-FIFO detector before any D3D test |
  | pixel | one triangle's centre reads its colour |

## 8. Risk

- **The instrumentation:**
  - With `D3DBeat` off, the register traffic is byte-identical. The always-on parts sit in the give-up error path
    (reads plus one flushed record) and in user-mode `vcrctl`.
  - With it on, the cost is one IOCTL and one volatile registry write per second from the game's own thread at
    PASSIVE_LEVEL, and 9 register reads in the miniport. There are no register writes.
  - The default 16 bpp path, Glide/OpenGL (no DP2 or Flip, so no beats), SLI (untouched) and the flip rule (its return
    values unchanged; `test_vcr_kmd_flip.c` unchanged) are not affected.
  - A videoprt-serialized IOCTL inside DP2/Flip once a second can add latency to that one call.
- **The experiments.** E3 creates a known-bad hardware state on purpose, and E2 sends escapes under a live D3D game.
  - Expected worst case: a frozen game, recovered as on 11-12.
  - Rare worst case: a hard hang and a power cycle. Hence the PXE hold and the activation check, and a person at the box
    throughout.
- **The CRT:** about 20 paced switches per boot. The D3D8 runtime's own unpaceable double switch only follows a refused
  CreateDevice, which Max Payne at 1280x960x32 does not hit.
- **AA:** cfg 5 only, with `SliAA` 0.
