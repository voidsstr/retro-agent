## 0. Verdict

**The gap is real and fixable. Its size is not quite what the brief says.**

**Smaller.** Nothing is broken on `.124` today.
- Both switches have been armed there explicitly since 2026-09-28: `D3D32` = 1, `D3DBigTex` = 7
  (`PLAN:619-620`). The ring confirms it on 11-12 (513/16, 513/18, `onbox.md` "The box during the run").
- What G20 protects is the **next install**:
  - a re-image of `.124`, which has happened before (`scripts/fleet/fleet-roster.txt:23`);
  - a deleted `Diag` key: the agent's `REGDELETE` of `Services\vcrmp\Diag` erases every switch at once
    (CLAUDE.md, REGDELETE);
  - a second VSA-100 box (`.143`'s V5 5500, if it ever moves to vcr-kmd).
- Any of these silently costs six titles until someone remembers to arm the switches again.

**Larger.** The record so far misses three things:

1. **Without `D3D32`, the D3D8 runtime answers "no" to every texture and Z format asked at `.124`'s
   32 bpp desktop format, R5G6B5 and D16 included, not only to 32 bpp ones.**
   - Measured on `.124` itself on 09-26: `vcrkmd-v5-5.jsonl`, step `d3d`, `desktop_fmt 22`:
     `tex565 0, tex1555 0, tex4444 0, z16 0`.
   - The 86Box Voodoo3 shows the same (`e1_caps_desk32.txt`). At a 16 bpp desktop the same HAL answers
     yes (`e4_caps_desk16.txt`).
   - A D3D8/9 title that validates formats against the desktop format before its 16 bpp switch therefore
     finds nothing to use (inferred consequence; no title is measured doing it).

2. **Flipping the default as the gap describes it would silently regress Thief II.**
   - Its staged launcher picks between NewDark's Direct3D 9 display and the DX6 fallback by reading the
     Diag **values** (`LIB/Thief2/Play Thief 2.bat:15-19`, generated by
     `scripts/fleet/stage-fleetres.py:847-878`).
   - With the default on and the values absent, it would move `cam_ext.cfg` aside and run DX6 at
     640x480, although the driver offers everything the D3D9 display needs.
   - The generator's own advice, "DELETE THIS BLOCK ... the day vcr-kmd offers those by default"
     (`stage-fleetres.py:845-846`), is also wrong: a box can still be running a miniport from before G20,
     where absent means off.
   - The fix: the miniport publishes, in a **volatile** registry key, what it put in force *this boot*.
     The launcher reads that key and falls back to the Diag values only when the key is absent.

3. **Of the blockers in `history.md` §7, only G10 really blocks D3D32** (§3):
   - The stale command FIFO (G01) is not specific to 32 bpp.
   - The 16 bpp stencil premise does not depend on the switch: a 16 bpp target's register sequence is
     the same whatever `D3D32` says (`KMD/include/vcr_3dseq.h:56-77`).
   - The LAN-party caution no longer applies: the party configuration *is* the armed one.
   - Rainbow Six is fixed (`be58b7d`), though on one image.

**3dfx shipped exactly this default on Napalm.** `32BPP_RENDERING` absent means on ("Enable the
possibility of 32bpp rendering by default", `VH5/D3INIT.C:1035-1039`). ARGB8888, DXT1-5 (plus FXT1) and
2048x2048 are unconditional on `IS_NAPALM` (`VH5/D3INIT.C:2169-2240`, `:3190-3196`).

**The design.**
- **Part 0:** correct the docs now.
- **Part 1:** the `InForce` record (miniport, no hardware traffic).
- **Part 2:** the Thief II launcher reads `InForce`.
- **Step 1:** `VcrDiagGet(L"D3DBigTex", 7)`. No prerequisite.
- **Step 2:** `VcrDiagGet(L"D3D32", 1)`, after G10.

How the defaults behave:
- An explicit value still decides: 0 turns a switch off, and `D3DBigTex` 1/2/4 picks single bits.
- The `vcr_info` flags stay positive and the display driver keeps gating them on `napalm`. So
  `vcrdd.dll` needs **no code change and no redeploy**, and a Banshee/Voodoo3, the 86Box bed and any
  older miniport see nothing new.
- Each step is proven in its own supervised clean boot before it lands on `master`.

**Priority P1** (§10). **Effort M.**

### 4.1 Part 1: the `InForce` record (miniport; lands with the first G20 `vcrmp.sys`, default on)

**What.**
- `HKLM\SYSTEM\CurrentControlSet\Services\vcrmp\InForce` is a key created **volatile**, so it is gone at
  every shutdown.
- It holds four `REG_DWORD`s, written at boot:

  | value | meaning |
  |---|---|
  | `D3D32` | 1 when this boot hands the display driver the 32 bpp D3D flag on a VSA-100, i.e. what `pd->rt32` becomes |
  | `D3DBigTex` | the BigTex bits handed over on a VSA-100 (`& 7`), else 0 |
  | `D3D` | the `Diag\D3D` kill switch in force |
  | `Boot` | the `BootCount` that wrote it |

**Why volatile.** A miniport from before G20 never writes the key. After a rollback (which needs a
reboot), the key is therefore gone, and every reader falls back to the Diag values with their old meaning
("absent = off"). So a reader can never mistake a previous driver's defaults for the current one's.

**Code.**
- **`KMD/miniport/vcrmp_log.c`.**
  - Build `g_inforce_buf` = RegistryPath + `L"\\InForce"` next to `g_diag_buf` (`:262-276`).
  - Add `void VcrInForceWrite(ULONG d3d32, ULONG bigtex, ULONG d3d, ULONG boot)`:
    - `ZwCreateKey(..., VCR_REG_OPTION_VOLATILE /* 1 */, &disp)`;
    - four `diag_write`s and `ZwClose`;
    - no `ZwFlushKey`: a volatile key never reaches the hive file.
  - A failed create logs **WARN** event 804 (ntstatus) and returns.
  - If `disp == REG_OPENED_EXISTING_KEY` (2) on the first write of the boot, the key existed before this
    boot, so it was created by hand and may not be volatile. Log **WARN** 804 d=2, and still write.
  - Success logs **INFO** 804 with the values.
- **`KMD/miniport/vcrmp.h`:** `#define VCR_REG_OPTION_VOLATILE 1`, `#define VCR_REG_OPENED_EXISTING_KEY 2`,
  and the prototype.
- **`KMD/miniport/vcrmp.c`**, in `VcrFindAdapter`, after `x->clut_read = ...` (`:250`), before
  `hwinfo(x)`:
  ```c
  {   /* G20: what the display driver arms THIS boot (vcrdd_2d.c VcrDd2dInit: a
       * VSA-100 - device 0x0009 - and the flag), for readers that cannot ask the
       * driver: the Thief II launcher, deploy_box.py, d3dprobe_run.py */
      ULONG v5 = x->backend == VCR_HW_VOODOO && x->device == 0x0009;
      VcrInForceWrite(v5 && x->d3d32 ? 1 : 0, v5 ? (x->d3dbigtex & 7) : 0,
                      x->d3d ? 1 : 0, VcrDiagGet(L"BootCount", 0));
  }
  ```
- **`KMD/include/vcr_events.h`:**
  `VCR_EVENT(VCR_EV_INFORCE, 804, "a=D3D32 b=D3DBigTex bits c=D3D d=0 created / 2 opened an existing key / ntstatus of a failed create")`.
  `tools/vcrlog.py` reads names from this table.

**Cost and risk.**
- No hardware access.
- **No new import:** `ZwCreateKey`, `ZwSetValueKey` and `ZwClose` are already in `out/vcrmp.sys`'s
  import table, so `tools/check_imports.py` is unaffected.
- It runs at PASSIVE_LEVEL, where `VcrDiagSet` already writes `BootCount`, `BootAttempts` and the phases.
- When it fails, every reader takes the conservative path (Part 2).

**Later.** When G01/G03/G10 graduate `Diag\D3DSafe` bits, the record gains `D3DSafe` the same way.

### 4.3 Step 1: `D3DBigTex` absent = 7 (no prerequisite)

`KMD/miniport/vcrmp.c:244`:

```c
    /* G20 (2026-11-xx): absent = 7, all three bits, on a VSA-100 (the display
     * driver arms them only there, vcrdd_2d.c). Verified on .124: 4ef226e
     * (09-28), 481acfd (11-08, 100/0), evidence/d3dplan_1112/onbox
     * d3dprobe_textures_{a,b} (11-12), armed daily since 09-28; the G20 boot B
     * (evidence/silicon/g20_defaults/) proved absent = 7. An explicit value
     * still decides: 0 = the proven 16 bpp/256 texture path, 1/2/4 = one bit.
     * The vcr_info flags stay POSITIVE: a miniport older than this never arms
     * them, whatever the display driver. Was 0. */
    x->d3dbigtex = VcrDiagGet(L"D3DBigTex", 7);
```

- No other code line changes.
- On a VSA-100 with no value, the HAL now runs the path `.124` has run since 09-28:
  - the 9-entry texture list and MaxTexture 2048;
  - FourCC DXT1-5 in DirectDraw's list;
  - `mipchain_ext` placing every texture 16-byte aligned;
  - the 26-bit base.
- **Side effect: G21 is fixed on the VSA-100.** The default path's 4-byte placement of single-level
  textures and its 24-bit texBaseAddr now remain only on a Banshee/Voodoo3, or on a VSA-100 with an
  explicit `D3DBigTex` = 0.

### 4.4 Step 2: `D3D32` absent = 1 (after G10)

- `KMD/miniport/vcrmp.c:238`: `x->d3d32 = VcrDiagGet(L"D3D32", 1);`, with a comment of the same shape

- **Preconditions:**
  1. **G10 is proven and in force wherever `D3D32` is.** A D16 made in a 32 bpp mode must draw, not be

## 9. Risks to proven paths

**The default 16 bpp path.**
- Step 2 does not touch it: the register sequence is pinned.
- Step 1 moves every texture onto the BigTex texture path, the path `.124`'s 16-bit titles (JK, MotS,
  Shogo, SS2, Thief Gold, R6) have run since 09-28.
- Below 16 MB the register values match the default path's. The differences are the driver's 16-byte
  placement, which is the G21 fix, and chains of every texture going through `mipchain_ext`.
- G07's per-level CreateSurface problem affects both paths equally.

**Glide/OpenGL coexistence.**
- The switches are D3D-only.
- G01's stale FIFO hits D3D at either depth. Step 2 makes the windowed 32 bpp route, which escalates to
  a 2D give-up, possible on fresh installs. It is already possible on `.124`.

**SLI and flips:** untouched. 32 bpp D3D flips measured 84.4 fps at 85 Hz on 11-12.

**What becomes the default on a fresh install** (all already true on `.124`):

| exposure | gap |
|---|---|
| D24S8 listed with its stencil never honoured (StencilCaps 0) | G35 |
| A8R8G8B8 render-target textures granted by the runtime but untested | G36 |
| dither left on at 32 bpp | G30 |
| alpha always blended ONE/ZERO where a destination alpha now exists | G28 |
| VRAM for 32 bpp buffers at high resolutions (1600x1200x32 triple-buffered is about 23 of 27 MB; FLEETRES picks 1280x960 on `.124`) | - |
| the configuration in which Max Payne froze | G04 |
| an R5G6B5 + D24X8 pick by a D3D8 title. The runtime refuses it, possibly after its mode set (G11 open question 1); no title is known to do it | G11 |

**The kernel.**
- The only new kernel work is a registry write at boot, with no new imports.
- A volatile-create failure is logged and makes the launcher conservative.
- A hand-made, non-volatile `InForce` could outlive a rollback. The first write of the boot detects it
  (804 d=2), and `deploy_box.py status` compares `Boot` with `BootCount`.

**Tools.** `deploy_box.py status` and the install verify print `InForce`. A missing key after the
reboot is a loud WARN.

## 11. Open questions

1. **The user's call.** The operator armed both switches for the party. The flip makes that the shipped
   default for every install (`games.md` §6.3). Confirm before step 1 lands.
2. **Compiled default plus `InForce` (recommended) or a package default?** The package default would be
   `HKR, Diag, D3D32, 0x00010003, 1` / `D3DBigTex ... 7` with NOCLOBBER in `inf/vcrkmd.inf`
   (`[vcr.Diag]`). §12(a) weighs the two. The INF lines can also be added on top.
3. **Does `CheckDeviceFormat` at a 32 bpp adapter format answer anything with `D3D32` off on the current
   build?** The only fixtures are 09-26 (`.124`) and the 86Box Voodoo3; both say all 0. The `--expect`
   rule relies on it.
4. **DXT2/DXT4 premultiplied semantics.** If the D3D8 reference rasterizer un-premultiplies DXT2/4 on
   decode (inferred: it may), `dxt4_decode1` deliberately does **not**. The reference is the hardware's
   and 3dfx's behaviour, and Halo's.
5. **After boot C:** leave `.124`'s values absent (recommended: it then runs the shipped default daily),
   or write them back explicitly (friendlier to a rollback past G20)?
6. **Should `InForce` also carry the D3DSafe bits** once G01/G03/G10 graduate, and should the 3dfx
   Control Panel's `/report` show it?
7. **Step 1 alone on a fresh install** gives `D3DBigTex` without `D3D32`: UT2003/UT2004 work, while
   H&D, Halo, Thief II's D3D9 display and Max Payne still need step 2. Is that intermediate state worth
   shipping, or should both steps ship in one release once G10 is in (still two proof boots)?

## 12. Alternatives considered

| alternative | why not (as the main route) |
|---|---|
| (a) **Package default**: the INF writes explicit values with NOCLOBBER | No binary change, and the launcher works unchanged. But a deleted Diag key or a manual install loses the values. The code's "absent" stays off, which gives two sources of truth. And it departs from how `Accel2DPattern`, `Accel2DLine`, `GdiGamma` and `SliAAVendorRecipe` graduated (compiled default plus `MOVED_DIAG`) |
| (b) **Invert the launcher** (absent ⇒ armed) | Wrong on any box running a pre-G20 miniport with no values: Thief II shows its own "video hardware is not supported" dialog |
| (c) **Materialise the default**: the miniport writes 1/7 when absent | Rollback-safe, but every box then carries values that look like operator choices, and a later change of default never reaches them |
| (d) **Delete the launcher block**, as its docstring says | Wrong for a pre-G20 miniport, and wrong after a rollback |
| (e) **Both flips in one boot** | Two Diag changes in one boot. Step 2 also has a hard prerequisite (G10) that step 1 does not |
| (f) **Have the display driver publish the record** | A display driver has no registry write; it would need a new IOCTL into the miniport. The miniport already knows everything the display driver will arm |
