# G56 design: every DirectDraw Lock and texture upload drains the engine; Halo's Bink intros run slow

- **Lane:** clean-room `vcr-kmd` (`vcrmp.sys` + `vcrdd.dll`), the Voodoo 5 6000 in `.124`. Direct3D, plus the
  DirectDraw calls the D3D runtimes make on its behalf.
- **Kind as filed:** fixable. **Finding of this design:** the drain is real but costs almost nothing on today's
  transport, and **it is not what makes Halo's intros slow.** The movie loop never queues engine work, so its Locks
  never wait. Its real cost is a stretched `StretchRect` that our `Dd_Blt` hands back, and the runtime then stretches
  on the CPU, reading video memory. So this item becomes a short investigation (Part A) that re-targets the Halo fix to
  G61, a small default-OFF fix (Part B) that G47 will need, and two later parts (C, D).
- **Priority P2. Effort M** (Parts A + B). Part C is L and lands with G47.
- **Written:** 2026-11-12. Read-only design. Nothing was built, deployed or run on a box, and no fleet box was
  contacted. The only things run were host-side reads of committed evidence, the staged library and the XP SP3
  runtime, all in the scratchpad.

## 0. Verdict

1. **The mechanism exists, and on today's transport it is nearly free.**
   - `Dd_Lock` calls `VcrDd2dSync` on every lock (`KMD/display/vcrdd_ddraw.c:658`), and both TEXBLT branches drain
     first (`KMD/display/vcrdd_d3d.c:1513`, `:1532`).
   - But `VcrDd2dSync` returns at once when nothing has been queued since the last sync (`KMD/display/vcrdd_2d.c:121-122`).
   - Every `Dd_Flip` drains before it flips (`vcrdd_ddraw.c:334`). So a Lock made between a Present and the next draw
     costs nothing.
   - A Lock made mid-frame waits for at most the tail of the PIO queue. Through the 31-entry PCI FIFO, that tail is one
     or two triangles or one clear, plus at least three status reads (`vcrdd_2d.c:125-128`; perf §1.2).
2. **The uploads are rare in every game measured on this HAL.**
   - The per-context `texture flushes` counter counts each bind of a texture written since its last use.
   - UT2003 flyby (245 s, ~2000 frames): **42**. UT2004 botmatch (~180 s): **63**. UT2004 `stat fps`: **22**. Halo
     timedemo (485 s): **77** (`ONBOX/games/*/ring_decoded.txt`, the `context 1 gone` lines).
   - So in those sessions the drains before uploads add up to milliseconds, not to frame time.
   - The 7-write TMU flush (`vcrdd_3d.c:253-270`) costs a few µs per uploaded texture (inferred). SPEC §20.3 requires
     it. It stays.
3. **Halo's intros are slow because of a software stretch, not the Lock path.** This was read from the staged binary
   (`LIB/Halo/halo.exe`, md5 `b7aa8f68…`, function `0x43ed20-0x43f003`; §2).
   - **Setup:** the movie player creates a **640x480 X8R8G8B8 `D3DPOOL_DEFAULT` offscreen plain surface** and gets
     render target 0.
   - **Each frame:**
     - `LockRect(flags 0)`;
     - `BinkCopyToBuffer(…, BINKSURFACE32)`;
     - `UnlockRect`;
     - **`StretchRect(surface → back buffer, D3DTEXF_NONE)`**;
     - `Present`.
   - **What our driver does with that:** at the staged `-vidmode 1280,960,85` the stretch is 2x. Our `Dd_Blt` hands
     every stretch back (`vcrdd_ddraw.c:529-532`, "stretch / format change: HEL").
   - **Yet the stretch happened:** the 09-28 frames show the movie stretched to 1280x960 (`FBS/halo_libdeploy_3.png`).
   - So the runtime stretched it with the CPU, and it read the source out of video memory through the write-combined
     user mapping (`KMD/miniport/vcrmp_dd.c:28-29`). Reads through that mapping are uncached (inferred).
   - **During the movie nothing else queues engine work.** Every Lock in the loop finds `g2d_busy` = 0 and does not
     wait at all.
4. **The measured rate fits the stretch and not the Lock.**
   - The three intros are 1,109 frames, 37.0 s at 30 fps (Bink headers, §2.3).
   - On 09-28 the menu came 11 min 9 s after the first captured frame, which was already in MGS (15:28:37 →
     15:39:46). FIND records them still playing "13 minutes after launch". The screenshot times bound Bungie +
     Gearbox (807 frames) to 6.5-9 min.
   - That is **0.48-0.67 s per frame, 14-20x slower**; FIND's "about 10x" understates it.
   - Reading 0.3-1.2 million uncached dwords per frame at roughly 0.45-1 µs each predicts 0.14-1.2 s (inferred unit
     cost). The Lock path predicts ~0.
5. **What follows for the plan:**
   - **Part A (do first, about one supervised session):** prove the cause with a replay of Halo's loop
     (`d3d9probe movie9`), a VRAM read benchmark and a 640x480 A/B of Halo itself.
   - **The Halo fix is G61's stretch blit,** the VSA-100 2D engine's screen-to-screen stretch (SPEC §7.3.2, "100
     Mpixels/Sec"), which 3dfx's own HAL used (`VH5/DDBLT32.C:1267-1270`, caps `VH5/DDINIT.C:256, 293, 339-342`).
     `-novideo` is dropped after that (Part D), not after anything in this item.
   - **Part B:** an in-flight span set, so that Lock and TEXBLT drain only when the surface may still be in use.
     - It is default OFF behind `Diag\D3DLockScope`; off, the proven path runs byte for byte.
     - On PIO it buys little. Its value is under G47: with a command FIFO, an unscoped drain waits for a whole frame
       of queued work.
     - It is measured in shadow mode first.
   - **Part C (with G47):** TEXBLT as CMDFIFO packet 5, and Lock fences by FIFO position. Interfaces only; it is
     designed with G47.

## 1. What the code does today

| step | code | cost on today's PIO transport |
|---|---|---|
| `Dd_Lock` | refuse `flip_from` while its flip is pending (`vcrdd_ddraw.c:652-657`), then `VcrDd2dSync(pd)` (`:658`), return NOTHANDLED (the runtime computes the pointer) | **0** if nothing was queued since the last sync (`vcrdd_2d.c:121-122`). Otherwise the raster tail of what the 31-entry FIFO holds (at most ~2 triangles or one clear), plus at least 3 status reads (`:125-128`) |
| `Dd_Unlock` | `VcrDdD3dTexWritten(s)` (`vcrdd_ddraw.c:676-681` → `vcrdd_d3d.c:606-614`): `SF_DIRTY` on the surface, global `g_tex_writes++` | a few stores |
| next draw that samples it | `prepare()` sees `g_tex_writes` moved (`vcrdd_d3d.c:1327-1334`), `flush_written()` runs `VcrDd3dTexFlush` (`vcrdd_d3d.c:1287-1320` → `vcrdd_3d.c:253-270`) | 7 PIO writes, 1 status read and 1 uncached texel read, written back through the texture port: a few µs (inferred) |
| DP2 TEXBLT | `VcrDd2dSync` (`vcrdd_d3d.c:1513` DXT, `:1532` other), `VcrDdD3dTexWritten`, then `memcpy` per level into the write-combined `pvRamBase` (`:1424-1449`, `:1456-1495`) | as Lock, plus the copy |
| `Dd_Flip` | `VcrDd2dSync` **before every flip** (`vcrdd_ddraw.c:334`) | the frame's raster tail. **This is why Locks after a Present cost nothing.** It belongs to G54 and is not changed here |

**What the vendor did.**
- 3dfx's `DdLock` drains for a texture **only** if a 2D blit into it is still in the FIFO (`BltToTxtrInFifo`) or the
  texture is also a render target (`VH5/DDSURF.C:1614-1620`). The unconditional drain of the line before is commented
  out (`:1605-1612`).
- So 3dfx let the CPU write a texture while queued triangles might still sample it (a write-after-read race). It
  downloaded TEXBLT data with packet 5, in order with the draws (`VH5/D3TXTR.C:3549-3560`), after flushing the TMU
  cache by writing an inverted `texBaseAddr` into the FIFO (`:2532-2540`).
- Part B below is stricter than the vendor: it waits on exactly that race.

**SPEC §20.1:** *"Texture downloads done through this port are guaranteed to be processed in-order with 3d rendering,
which alleviates the host from having to idle the chip before downloading."* That is true of the texture download port
(PIO at BAR0 + 0x600000, or packet 5). It is not true of the LFB path that `Lock` hands to the application: SPEC calls
that path *"non-synchronized"*.

### 2.1 The loop

`LIB/Halo/halo.exe` (md5 `b7aa8f68829a33a9f0b87ec81425f5db`) loads Bink by delay-load. Its IAT slots are

### 2.2 What our driver does with it

| call | path | waits? |
|---|---|---|
| `LockRect(offscreen, 0)` | `Dd_Lock`: not `flip_from`; `VcrDd2dSync` finds `g2d_busy` = 0 | **no**: the previous `Present`'s `Dd_Flip` drained, and nothing has drawn since |
| `BinkCopyToBuffer` | 1.2 MB of CPU stores through the WC view (`vcrmp_dd.c:28-29`) | about 6-12 ms at 100-200 MB/s (inferred) |

| `Present` | `Dd_Flip` | today's Halo timedemo logged no vsync'd flips (G46 §0 item 1: all four game sessions logged `flips of 0`, and the flip counters count vsync'd flips only), so no refresh wait (inferred) |

## 3. The design

### 3.1 Part A: settle the cause (no driver behaviour change)

**E0 (host, done in this design).** §2: the binary, the Bink headers, the frame times. **Result:** H1 fits, H0 does
not.

**E1: `d3d9probe movie9`, Halo's loop replayed call for call.**
- **Where it lives:** a mode of the D3D9 test program G36 specifies (`KMD/tools/d3d9probe.c`, `LoadLibraryA("d3d9.dll")`,
  no `-ld3d9`, `vcr_pace.h` for the mode switch). If G36 has not landed, this item creates the file with only
  `movie9` and `vramread9`.
- **Device:** `Direct3DCreate9`, `CreateDevice(HAL, SOFTWARE_VERTEXPROCESSING)`. Fullscreen `--res WxH`, X8R8G8B8,
  1 back buffer, refresh 85. `D3DPRESENT_INTERVAL_IMMEDIATE` by default, as Halo's flips were (§2.2); `--vsync` for
  ONE.
- **Setup:** `CreateOffscreenPlainSurface(640, 480, D3DFMT_X8R8G8B8, D3DPOOL_DEFAULT)`, then `GetRenderTarget(0)`.
- **Per frame** (`--frames 120`), each call timed by QPC:
  1. `LockRect(S, NULL, 0)`;
  2. 640x480 plain 32-bit stores of pattern P(f, x, y), with a distinct colour per 8x8 block;
  3. `UnlockRect`;
  4. `StretchRect(S, NULL, RT, NULL, D3DTEXF_NONE)`;
  5. `Present`.
- **Verification** (last frame, before its `Present`): `GetRenderTargetData` into a `D3DPOOL_SYSTEMMEM` surface;
  64 sampled pixels must equal P(x·640/W, y·480/H), ±1 source pixel for rounding (as `ddlab sdlddraw`'s `sdl_row_ok`).
- **RESULT** `{lock_ms, write_ms, unlock_ms, stretch_ms, present_ms}`, each as median/p95/max, plus `fps`, `stretch_hr`,
  `picture_ok` and `verdict`:
  - `software-stretch`: `stretch_ms` ≥ 20x the 640x480 control;
  - `engine-stretch`;
  - `failed:<hr>`.

**E1b: `d3d9probe vramread9`.**
- `LockRect(S, D3DLOCK_READONLY)`, then three timed passes:
  - sequential dword reads of all 640x480 (MB/s);
  - the same with every dword read four times in a 2x2 destination order (`--nn2x`: the naive per-destination-pixel
    stretch);
  - a write-only pass (MB/s).
- It gives t_read on this box. **Prediction (H1):** E1's `stretch_ms` at 1280x960 lies between the sequential and the
  `nn2x` read times, ±30 %.

**E2: Halo itself, A/B.** Supervised, one session, no Diag change.
- **How it is launched:** the staged tree, through a `.bat` that `cd`s to it (the Halo rules in CLAUDE.md), **without
  `-novideo`**:
  - (a) `-vidmode 1280,960,85`;
  - (b) `-vidmode 640,480,85`.
- **Paced:** at least 5 s between the runs' mode switches.
- **Capture:** agent `SCREENSHOT` every 10 s; never `vcrctl` while a D3D game runs.
- **End:** at the menu, or after 150 s, by `WM_CLOSE` (Halo exits cleanly on it).
- **Prediction (H1):**
  - (b) reaches the menu at about 37 s + load. A 640x480 back buffer makes `StretchRect` a same-size copy, which our
    `Dd_Blt` gives to the 2D engine (`vcrdd_ddraw.c:540-543`).
  - (a) is still in MGS or Bungie at 150 s.
- **If (b) is slow too:**
  - either d3d9 passes flags our `Dd_Blt` refuses even at 1:1 (`ok_flags`, `vcrdd_ddraw.c:472-482`);
  - or the cost is H0 after all.
  - E3 says which.

**E3: what the driver sees.** One boot with `Diag\LogLevel` = TRACE and `Diag\LogEntries` = 16384, then disarm.
- Run E1 at 1280x960 for 20 frames.
- Fetch the ring after the probe exits. It shows, per frame:
  - the `Blt` event (513 a=10) with its `dwFlags`;
  - the `Lock` events (a=9) on the offscreen surface and the back buffer;
  - the `Flip`.
- **Outcomes:**
  - **No `Blt` event for the StretchRect:** d3d9 never asked the driver for the stretch. G61 must report
    `DDCAPS_BLTSTRETCH` before d3d9 will send it.
  - **A `Blt`, then two `Lock`s:** the runtime's own CPU stretch (H1). G61 must handle that Blt.
  - **A `Blt` and no `Lock`:** the stretch went through GDI (`DrvStretchBlt`, `vcrdd_punt.c:648-652`). G61 or GDI work
    then covers it there.

**E4: counters (with G46's `Diag\D3DStats`).** These fields are added to G46's `vcr_d3dperf` struct; §3.5 lists them.
They name the titles whose movie or 2D paths stretch a video-memory source:
- `Blt` hand-backs by reason, each with "source in video memory" and pixel totals;
- Locks by surface kind;
- Locks that waited, and for how long.

**What each outcome means:**

| E1/E2 result | meaning | next step |
|---|---|---|
| `stretch_ms` ≫ (≥ 300 ms at 1280x960), `lock_ms` < 1 ms, (b) at speed | **H1** | the Halo fix is G61's hardware stretch (§3.4). Part B is not needed for Halo |
| `lock_ms` ≥ 10 ms | H0 holds partly: the engine was busy at the Lock | find what was queued (E3 ring); Part B becomes relevant to Halo |
| (b) slow and E3 shows a refused 1:1 Blt | flag handling | G61 accepts d3d9's StretchRect flags too |
| `vramread9` fast (≥ 50 MB/s) yet the stretch slow | the stretch path does more than read once | E3 ring plus `procprof` (G46 §3.6) on the probe |

### 3.2 Part B: scoped Lock and TEXBLT waits (the in-flight span set)

**Rule.** Drain before a CPU access to video memory only when the engine may still touch the bytes the CPU will touch:
- RAW: the CPU reads what the engine writes.
- WAR / WAW: the CPU writes what the engine reads or writes.

A read-only lock of a surface the engine only reads (a bound texture) needs no drain.

**`KMD/include/vcr_inflight.h` (new).** Win32-free, integer only, host-tested, in the pattern of `include/vcr_flip.h`.

```c
#define VCR_INFL_MAX 16
#define VCR_INFL_R   1u           /* the engine reads it  (a bound texture, a 2D source)        */
#define VCR_INFL_W   2u           /* the engine writes it (target, Z, a fill/copy/port write)   */
typedef struct { vcr_u32 lo, hi, rw; } vcr_infl_span;        /* [lo, hi) in video memory     */
typedef struct {
    vcr_infl_span s[VCR_INFL_MAX];
    vcr_u32 n, overflow;          /* overflow: unknown extent or full - everything in flight */
    vcr_u32 epoch;                /* bumped at every observed idle                          */
    vcr_u32 g2d_ops_at_idle;      /* pd->g2d_ops when the set was last emptied               */
} vcr_inflight;
void vcr_infl_idle(vcr_inflight *f, vcr_u32 g2d_ops);              /* empty it, epoch++    */
void vcr_infl_note(vcr_inflight *f, vcr_u32 lo, vcr_u32 hi, vcr_u32 rw);  /* merge or append;
                                                       hi <= lo or a full table -> overflow */
int  vcr_infl_must_wait(const vcr_inflight *f, vcr_u32 g2d_ops, vcr_u32 lo, vcr_u32 hi,
                        int cpu_writes);
     /* 1 if: overflow, or hi <= lo (unknown size), or g2d_ops != g2d_ops_at_idle (a 2D
      * operation ran since the last idle - 2D is not tracked by span), or any span overlaps
      * [lo,hi) and (cpu_writes || (span.rw & W)).  0 otherwise. */
vcr_u32 vcr_infl_surface_bytes(vcr_u32 pitch, vcr_u32 height, vcr_u32 linear_size);
     /* pitch*height; for a FOURCC surface the larger of its linear size and block size;
      * 0 (= unknown -> wait) on overflow */
```

**Why ranges and not per-surface flags:**
- A range covers aliasing: a mip level inside its chain's block, and a surface freed and re-created at the same
  address.
- It covers G07's split chains: the TMU reads `base + chain offset(k)` whoever owns those bytes.
- It needs no field in `DD_SURFACE_LOCAL`: `dwReserved1` is taken by `SF_*`, `vcrdd_d3d.c:204-212`.

**Where spans are noted.** All of it is in `vcrdd_d3d.c`, and only when `pd->lock_scope` (or shadow mode, §3.5) is on.

| site | spans |
|---|---|
| `prepare()` (`vcrdd_d3d.c:1322-1365`), after `VcrDd3dTarget` + `VcrDd3dState` succeed; and on its fast path whenever `w->infl_epoch != pd->infl.epoch` (one compare per triangle) | target `[rt_off, rt_off + rt_pitch·height)` W; Z `[z_off, z_off + z_pitch·height)` W if `z_on`; for each bound stage, the **TMU's** span `[lin_base, lin_base + chain bytes)`. - **2D work is not tracked by span.** Every 2D operation already bumps `pd->g2d_ops` (`vcrdd_2d.c:218, 245, 332, 374`).

**`Dd_Lock` with the switch on.** Inserted after the `flip_from` check (`vcrdd_ddraw.c:652-657`), which is unchanged:

```c

    if (s->ddsCaps.dwCaps & DDSCAPS_SYSTEMMEMORY)
        return DDHAL_DRIVER_NOTHANDLED;                /* the engine never touches it */

    if (!vcr_infl_must_wait(&pd->infl, pd->g2d_ops, lo, hi, !(p->dwFlags & DDLOCK_READONLY))) {
        pd->lock_scoped++;  return DDHAL_DRIVER_NOTHANDLED;

VcrDd2dSync(pd);                                       /* the proven line, unchanged */
```

**TEXBLT** (`vcrdd_d3d.c:1510-1548`). Both `VcrDd2dSync` calls go through the same rule:
- the destination: every level the copy loop will write, each level's own `[fpVidMem, + bytes)` with `cpu_writes`;
- a video-memory source (CPU reads), each level likewise.

Any level that must wait drains once. Under a Glide owner (`exclusive_pid`) the old unconditional drain stays.

**What the rule never relaxes:**
- a Lock of the render target, the Z buffer or a texture still bound (WAR);
- anything after a 2D operation;
- anything of unknown size;
- anything once the table is full;
- anything while Glide owns the chip.

The whole d3dprobe render matrix reads the back buffer with a Lock right after drawing. That matrix is therefore the
RAW test of the rule.

**Not changed by Part B:**
- every register write and every caps bit;
- the `flip_from` refusals in Lock and Blt;
- the drain in `Dd_Flip` (G54's) and the GDI punt syncs (`vcrdd_punt.c:38`);
- `ctx_free`, `Dd_Blt`'s CPU fallbacks, Reset3D and the TMU flush (G37's).

**Expected gain on PIO.** Small: (mid-frame texture Locks + TEXBLTs) × (raster tail + 3 µs). §0.2 says that is tens
per session in UT2003/UT2004/Halo. Shadow mode (§3.5) measures it per title before the switch is ever armed. **The
reason to build it now is G47:** once a command FIFO lets the CPU run up to a frame ahead, an unscoped drain at a
mid-frame upload costs the whole queued frame. Part C then swaps the empty-at-idle clearing for FIFO-position fences.

### 3.3 Part C: packet-5 TEXBLT and FIFO-position fences (after G47; interfaces only)

- **C1: TEXBLT through the CMDFIFO**, behind `Diag\D3DTexPkt5` bit 0. It is effective only with G47's `D3DCmdFifo` and
  `D3DLockScope` both armed. Per level and rectangle:
  1. a 2D NOP (pixel flush, SPEC §20.3 rule 1);
  2. packet 5 (`VINC/H3GDEFS.H:252-265`), at most 0x4000 dwords per packet, an `sfence` per chunk
     (`VH5/D3TXTR.C:3491-3503`, "Never ... more than 64k of the fifo ... fence to keep the hole counting working");
  3. then, in the FIFO, `texBaseAddr` written inverted and rewritten, with a `nopCMD` between (both TMUs, as
     `VcrDd3dTexFlush` does), and a 2D NOP (SPEC §20.3 rules 3-4; vendor `VH5/D3TXTR.C:2532-2540`).

  **Space:**
  - LFB space (`SSTCP_PKT5_LFB`) with the linear address first. It is absolute, so no `texBaseAddr` juggling, and it
    works above 16 MB and for TBIG.
  - The vendor's TEXPORT form (base `0x3a00000` + offset on Napalm, SPEC §13.1.8) is the fallback. It is the
    vendor-proven one.

  The source is copied into the FIFO, so there is no wait at all. A video-memory → video-memory TEXBLT (rare) goes to
  the 2D engine instead, which orders itself behind pending 3D: SPEC `miscInit1` bits 16/17 default 0 (G37 §1).
- **C2: Lock fences.** Each span also keeps the FIFO serial of its last use.
  - **Why `readPtr` is not enough:** fetched is not finished.
  - **The candidate fence:** at the end of each DP2 call, each Clear2 and each flip, the HAL emits a 2D NOP (pixel
    flush), then a packet-5 LFB write of a 32-bit serial into a driver-reserved dword. A span retires when that dword
    reads ≥ its serial (one uncached read). Each wait is bounded by `SPIN_CAP` and falls back to the full sync and
    give-up rule.
  - This replaces the per-idle clearing, which stops being frequent once G54 removes the drain at each flip.
- **C3:** Lock-based uploads (D3D8/9 managed textures) cannot use packet 5. They keep Part B's rule with C2's fences.

**PIO alternative, considered and rejected.** Writing TEXBLT texels through the texture download port by PIO (BAR0 +
0x600000, in order with rendering, SPEC §20.1) needs no drain at all. But it is uncached single-dword PCI writes behind
FIFO-room checks: 27-90 MB/s (inferred) against 100-200 MB/s for a WC `memcpy`. It is not worth a second upload path
before G47.

### 3.4 Part D: drop `-novideo` (after G61 and Part A)

  - an unclipped, video-memory → video-memory, same-format (32 bpp X8R8G8B8 here) SRCCOPY with the flags E3 records;
  - a 640x480 → 1280x960 stretch, top-down;
  - on the 2D engine's screen-to-screen stretch blt (SPEC §7.3.2, command 2, `srcSize`/`dstSize`, `bresError0/1`

## 5. Probe tests

**d3dprobe (D3D8; managed textures, so the runtime's own upload Lock is what reaches `Dd_Lock`).** Both are named,
never in the default list.

**`lockwar`** (write-after-read: the race Part B must never open).

On PIO, what is still queued when a DP2 call returns is the tail the 31-entry FIFO holds: the last one or two
triangles (§1). d3dprobe reads back only the top-left 256x256 (`readback()`, `tools/d3dprobe.c:291-322`; G74). So the
geometry puts a long, late-rasterized triangle tail inside that window:
1. Texture T: managed, 256x256 R5G6B5, solid **red 0xF800**.
2. Draw three opaque, Z-off, full-screen quads sampling T (bilinear). Then the **last** big draw: a quad over rows
   0-255 at full width, mapped so that each row samples a different texture row. Its last-rasterized rows (about
   150-255, about 1.6 ms of raster at about 1 px/clk at 1024 wide, inferred) are the ones still queued at step 3.
3. `LockRect(T)`, fill it **green 0x07E0**, `UnlockRect`. The runtime flushes the pending DP2 here or at step 4
   (inferred).
4. Draw one 16x16 quad at (0, 240)-(16, 256) sampling T. Before this draw the runtime uploads T's video-memory copy:
   `Dd_Lock` on it, then a 128 KB copy (about 1 ms), while the tail of step 2 may still rasterize.
5. `EndScene`, then `readback()`. d3dprobe already locks the back buffer right after drawing, before `Present`.
- **Pass:**
  - 32 sample points of rows 0-239, rows 200-239 included, read **exactly red**;
  - the small quad reads **exactly green**;
  - run at 640x480x16 and 1024x768x32.
- **Old code:** passes (it always drains).
- **Part B armed:** must pass (T is in flight as R and the Lock writes, so it drains).
- **Proof mode (bit 1):** expected to **FAIL** (green in the late rows). That shows the test detects the race.
- **If proof mode does not fail:** the window is too small. Widen the last quad or use G74's full-surface readback
  before trusting a pass.

**`lockfar`** (the scoped skip):
- As `lockwar`, but the big quads sample texture **A** (blue) and the upload is to an unrelated texture **B**.
- **Pass:** the big area is exactly blue and the small quad exactly green.
- **The ring's per-session counters must show:**
  - armed: ≥ 1 scoped Lock and 0 waited for this test's context;
  - off: shadow ≥ 1 would-skip.
- **Informational:** the QPC time of the small quad's `DrawPrimitive` call, which contains the upload. It is
  A/B'd across the two boots: armed, about µs; off, about the remaining raster.

**`perf --mode upload`** (the mode G74/G78 frame; specified here):
- `--tex-kb S --per-frame K`: K managed textures of S KB re-filled and drawn per frame.
- It reports MB/s and µs per upload, with `--novsync` and with vsync.

**d3d9probe (new modes; tool from G36):** `movie9 --res 1280x960|640x480 [--vsync] [--frames N]` and
`vramread9 [--nn2x]`, as in §3.1. They measure and do not gate. After G61, `movie9 --res 1280x960` gates:
`stretch_ms` median ≤ 15 ms and `picture_ok`.

## 8. Risk to proven paths

- **Default 16 bpp path and every unarmed box:** none. With `lock_scope` = 0 there is no bookkeeping, and the drains,
  registers and caps are byte for byte today's.
- **Armed:**
  - **The risk is a missed span.** The CPU writes a texture while queued triangles still sample it, or reads a target
    before the engine has finished it: torn texels or a wrong readback. It cannot hang: no wait is added, only skipped.
  - **What bounds it:**
    - the completeness test (§6);
    - waiting by default on overflow, unknown sizes and 2D;
    - the full drain under a Glide owner;
    - `lockwar` with its proof-mode negative.
- **CPU LFB writes overlapping engine work.**
  - 3dfx's HAL did this routinely: texture Locks without a busy wait (`VH5/DDSURF.C:1614-1620`).
  - SPEC §21.2 warns of a "potential deadlock condition ... when determining if the Napalm subsystem is idle" after LFB
    accesses, and asks for a NOP before polling. Our `VcrDd2dSync` polls without a NOP today, and the CPU already
    writes the LFB between syncs.
  - Part B raises how often the two overlap, so **watch item:** any boot-B stall or give-up (`2D engine never went
    idle`) is a stop, and is handed to G04.
- **Glide/OpenGL coexistence:** unchanged. With `exclusive_pid` set, the full drain runs as today. Glide's own command
  FIFO never touches our set. G01's stale FIFO is a precondition, not an interaction.
- **SLI:** D3D is single-chip; offsets are chip 0's. If G51 adds D3D SLI later, spans stay valid as offsets (inferred).
- **Flip path:** not touched. G54 owns the drain in `Dd_Flip`. When G54 removes it, Part B's set is emptied less often
  and needs C2's fences. That dependency is recorded.
- **Part C:** inherits G47's risks (a FIFO wedge, hole counting, WC fencing) and adds the fence-ordering question.
- **Part D:** a library change. The same purge → GAMESYNC → screenshot loop as any staged-game fix.
