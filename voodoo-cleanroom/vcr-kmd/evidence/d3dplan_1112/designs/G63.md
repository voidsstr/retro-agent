## 0. Summary

- **Verdict: real, fixable, and most of the fix already exists.** The block at offset 0 has two silicon measurements.
  One is new: it comes from today's rings, which nobody had linked to G63.
  - `ddlab vidmem` on 09-27, desktop 1024x768x32: 120 surfaces where 121 fit, the lowest at +512 KB
    (`KMD/evidence/silicon/256mb/ddlab_vidmem.txt`).
  - **New:** the 11-12 fullscreen probe at 1024x768x32 got heap `0-3cff000`. Its back buffer landed at **0x300000**,
    which is exactly its own size, the Z at 0x600000 and the first texture at 0x900000
    (`ONBOX/ring_after_probe_ii_decoded.txt` seq 24821, 24848-24853, 24873). The block at 0, the size of the first
    allocation, was handed out as "0", read as a failure, and placed again by DirectDraw's second pass. **3 MB of the
    heap was never used.** The windowed probe on the same day shows the same signature at 256 KB: target 0x40000, Z
    0x80000, texture 0xc0000 (`ONBOX/ring_after_probe_windowed_decoded.txt` seq 25029-25051).
- **A correction to the gap.** A single-pass `DDERR_OUTOFVIDEOMEMORY` cannot hit the fullscreen titles the gap lists
  (UT2003, UT2004, Halo):
  - Their flip chain is always the first allocation of the fresh heap, and DirectDraw places it in two passes.
  - For them the cost is **capacity**: one back buffer per mode set. That is 4.7 MB at the staged 1280x960x32 and 3 MB
    at 1024x768x32.
  - The single-pass failure needs a **driver-placed block as the first allocation of a fresh heap**. That means a
    texture with `D3DBigTex`, or any mipmap chain. It has never been shown on silicon. `ddlab texfirst` (new, §7.2)
    makes the failure on demand.
- **The binaries on `.124` already carry the switch.**
  - `LIVE/vcrmp.sys` (fda1b8c9) contains the UTF-16 name `DdHeapFloor`.
  - `LIVE/vcrdd.dll` (95678704) contains "`(Diag\DdHeapFloor: the heap starts off offset 0)`".
  - So **Phase A needs no driver build.** It needs one registry value and one supervised clean boot. Only the lab
    tools are rebuilt: `out/ddlab.exe` dates from 09-28 00:15, before `sdlddraw` existed (e25b0a9, 10:08), and
    contains no `sdlddraw` string.
- **The design, in four phases:**
  1. **Phase A, the investigation.** Build two lab tools: `ddlab texfirst` and d3dprobe `heapfill`. Then run one clean
     boot, control first, then `DdHeapFloor = 1`, with every number registered in advance (§4).
  2. **Phase B, the driver change.**
     - A value table in `vcr_ddheap.h`. Value 1 is one page. Value 2 is above Glide's command-FIFO window, at
       **0x118000** on a VSA-100.
     - One allocator for every driver-placed block. It retries once when the heap starts at 0. Nothing else changes
       on the default path, so it lands default-on.
     - Counters in `VCR_ESC_DD_STATS` (§5).
  3. **Phase C.** Value 2 and the retry on silicon (§9).
  4. **Phase D.** Promotion: `DdHeapFloor` absent means 2 (§6).
- **Priority P2. Effort M.** Phase A alone is S and worth doing in the first supervised `.124` session, for three
  reasons:
  - it costs no build;
  - it settles the one hypothesis G62 has;
  - it can deliver the fix that same day, by leaving the value armed.

## 2. The mechanism: the DDK's own contract, and the measurements

- **`HeapVidMemAllocAligned` returns 0 for failure.**
  - DDK page `gdifncs_8dnr.htm`: "returns the FLATPTR offset of the resulting allocation upon success. Otherwise, it
    returns zero".
  - On NT, `fpVidMem` is an offset into the frame buffer. A heap whose `fpStart` is 0 therefore hands out its first
    block **at** 0, and the caller cannot tell that block from failure.
  - The heap manager is first-fit and ascending, with no per-block overhead (measured: `G07.md` §2, the 0x900000 and
    0x902000 placements). The block leaves the free list and is never freed, so it stays lost until the heap is rebuilt
    at the next mode change.
- **DirectDraw survives because it tries twice.**
  - DDK `ddraw_10dj.htm` (§3.3.2.1 Memory Heap Allocation): "DirectDraw's heap manager makes two passes through the
    VIDEOMEMORY structures when attempting to allocate memory in response to a surface creation or restoration."
  - Our one heap is eligible on both passes, so the second pass takes the next block. That is why ddlab's first surface
    was created at +512 KB, and why the 11-12 back buffer landed at 0x300000.
- **The driver's own allocators try once.** `mipchain_ext` and `VcrDdD3dCreateMipChain` answer
  `DDHAL_DRIVER_HANDLED` + `DDERR_OUTOFVIDEOMEMORY` when they get 0. dxg then returns that error to the application;
  it does not run a second pass of its own.
- **When the first allocation is a driver-placed block** (reachable now, measured never), the application's call fails:
  - **Not in a fullscreen D3D8 game (measured).** The flip chain comes first: the 11-12 ring shows CreateSurface
    `1000601c` (back buffer), then `00024000` (Z), then ContextCreate, then the textures. A DX5-7 game builds its
    flip chain before its textures too (inferred).
  - **Possible** for a windowed DirectDraw 7 application that makes a video-memory texture or mipmap before its render
    target (inferred: rare).
  - **Possible** for a D3D8 managed texture whose video copy is the first allocation of a fresh heap. The runtime's
    evict-and-retry would then succeed on its second call (inferred).
  - **Exactly what `ddlab texfirst` does on purpose** (§7.2).
- **What it costs today, per mode change.** The cost is the first allocation's size. In a fullscreen game that is the
  back buffer:

  | mode | block lost today |
  |---|---|
  | 640x480x16 | 600 KB |
  | 1024x768x32 | 3.0 MB (seen 11-12) |
  | 1280x960x32 (UT2004; Halo's `-vidmode 1280,960,85`) | 4.7 MB |
  | 1600x1200x32 | 7.3 MB |

  The heap is 59-62 MB on `.124` in the 256 MB VBIOS mode. The ring reads `heap 0-3cff000 (62460 KB)` at 1024x768x32
  and `0-3aff000 (60412 KB)` at 1280x1024x32. **The README's "`.124`'s heap is 27 MB" (`KMD/README.md:111`, `:496`)
  and d3dprobe's `texhigh` comment (`KMD/tools/d3dprobe.c:863`) are stale** (G80).
- **The vendor never starts its heap at 0.** 3dfx's NT driver for this chip lays memory out like this:
  1. its own command FIFO at offset `CMDFIFO_START_OFFSET`. On NT4 that is one page up (0x1000), on NT5 it is 0
     (`VH5/ENABLE.C:1074-1077`). The FIFO is 64 KB to 1 MB, 512 KB by default (`:1240-1254`);
  2. then the hardware cursor (`:1284`, `:1319`);
  3. then the linear DirectDraw heap, from `ulScreenOffset` (`VH5/ENABLE.C:2307-2308`, `:2651-2652`;
     `VH5/DDINIT.C:1148-1149`);
  4. the desktop at the end of memory (`:2290`).

  That is our layout, except for the reserved bottom. Our h5 Glide likewise keeps everything but its FIFO above
  0x117000: a 96 KB "out of the way of VGA" pad, then `MAXFIFOSIZE_16MB` 0xff000, then texture memory
  (`GL5/minihwc/minihwc.c:1043-1044`, `:2566-2592`).

## 3. Why the floor should end up above Glide's window on a VSA-100 (value 2), not one page up

Value 1 (one page, the code that exists) cures the lost block. Value 2 also does four further things. All four point
the same way:

1. **It closes the escalation path of the 11-12 incident.** This item is inferred from G01's fact 3; the escalation
   itself was measured.
   - The windowed probe's first texture was CPU-written at 0xc0000. That is inside the stale `cmdFifo0` window
     0x18000-0x117000.
   - `aMax` read about 0xc0000 + 128 KB afterwards, and the chip went `0xa1f` busy.
   - The desktop PDEV then lost 2D acceleration and the D3D HAL until the next mode set (`ONBOX/session_log.md`
     10:03:23; `G01.md` §2 rows 1-3).
   - With value 2 the same run puts its RT at 0x118000 and its texture at 0x198000. No host write can reach the window.
     A stale FIFO still eats the triangles (G01's own fix), but the box keeps its HAL.
   - Value 1 does not help here: the RT would be at 0x1000. In fullscreen it adds a little exposure, because the
     back buffer and Z (rarely CPU-written) now land in the window where today's lost block covered it.
2. **No texture base can wrap.**
   - A texture smaller than 256 is based before itself, at its address minus the levels it lacks. The largest such
     distance is 0x2AAA8 for a 16-bit 1x1 and **0x55550** for an ARGB8888 1x1.
   - A texture placed lower wraps: `(offset - pre) & 0x3fffff0` (`KMD/common/vcr_texlod.c:134-141`). The default
     path's 24-bit field wraps to 16 MB, which samples 16 MB high on a 64 MB VSA-100. The row "wraps in the 16 MB
     field" is pinned at `WT/tests/native/test_vcr_kmd_texlod.c:82`.
   - With a wrapped base the texture-port write-back is also skipped (§1).
   - Whether the 26-bit TMU adder wraps correctly has never been measured. Value 2 (0x118000 > 0x55550) makes the
     question unreachable. Value 1 does not.
3. **It clears the VGA pad.** Glide keeps out of [0, 0x18000) "to get out of the way of VGA". Nothing writes VGA
   memory while a DirectDraw surface is alive, because a console or VGA switch is a mode change that loses every
   surface (inferred). Value 2 makes that a non-question.
4. **It is G47's mandatory floor, and it matches the desktop rule.** G47's command ring lives exactly in Glide's
   window and needs the heap above 0x118000 while armed (`G47.md` §3.1). G01 §3.5 proposed "`DdHeapFloor = 2`" for
   the same window. The miniport already refuses any mode whose desktop would reach below 0x118000.

**The cost of value 2:** 1,146,880 bytes (1.09 MB), against what the lost block costs today:

| mode (fullscreen) | lost today | value 2 vs today |
|---|---|---|
| 640x480x16 | 0.59 MB | -0.51 MB |
| 800x600x16 | 0.92 MB | -0.18 MB |
| 640x480x32 | 1.17 MB | +0.08 MB |
| 1024x768x16 | 1.50 MB | +0.41 MB |
| 1024x768x32 | 3.00 MB | +1.91 MB |
| 1280x960x32 (UT2004, Halo) | 4.69 MB | +3.59 MB |
| 1600x1200x32 | 7.32 MB | +6.23 MB |

The titles that run at 640x480x16 (Thief Gold, System Shock 2, UT2003's G19 fallback) use a few MB of textures out of
58 MB, so the 0.5 MB is immaterial there. On a Banshee or Voodoo3, value 2 means the page floor: h3 Glide puts its FIFO
under the colour buffers, not at the bottom (`.../glide3x/h3/minihwc/minihwc.c:1520`, `:1538`:
`fifoStart = fbOffset - fifoSize`).

8. **Armed: repeat steps 3, 4 and 5.** The fullscreen run's own switch builds an armed PDEV, and so does the desktop's

    - the two 11-12 texture lists at `--full --res 1024x768 --bpp 32` (`ONBOX/README.md` runs 11-12);

    - `ddlab_run.py ... flip --res 800x600 --bpp 16 --frames 120`;

    - UT2004, DM-Antalus spectator botmatch, staged 1280x960x32, 60 s (`ONBOX/gamerun.py`, as 11-12 run 15). Then

    - Optionally Halo's `-timedemo` (`-novideo`, staged config) at its staged mode.

## 5. Phase B: the driver change

### 5.1 `KMD/include/vcr_ddheap.h` (Win32-free, host-tested)

```c
#define VCR_DD_HEAP_FLOOR        0x1000u    /* bit 0: one page - no block at offset 0 (existing) */
/* bit 1, VSA-100 only: above h5 Glide's command-FIFO window [0x18000, 0x117000) (minihwc.c: 96 KB
 * VGA pad + MAXFIFOSIZE_16MB) plus a guard page - the miniport's caps.fb_reserved, where no desktop
 * may lie either. Also above the largest base-before-the-texture (0x55550, a 1x1 ARGB8888), so no
 * texBaseAddr can wrap. G47's ring floor (VCR_CF_HEAP_FLOOR) is this constant. */
#define VCR_DD_HEAP_GLIDE_FLOOR  0x118000u

/* the floor, in bytes, for Diag\DdHeapFloor on this chip: 0 = the layout of every silicon run to
 * 2026-11-12; any other value keeps every block off 0; bit 1 on a VSA-100 lifts it above Glide's window */
static inline vcr_u32 vcr_dd_heap_floor(vcr_u32 diag, vcr_u32 napalm)
{
    if (!diag)
        return 0;
    if ((diag & 2u) && napalm)
        return VCR_DD_HEAP_GLIDE_FLOOR;
    return VCR_DD_HEAP_FLOOR;
}

/* a 0 from HeapVidMemAllocAligned on a heap that starts at 0 may be the block AT 0, handed out and
 * lost: one retry tells them apart (DirectDraw's own second pass does the same). A heap with a floor
 * never retries: its 0 is always "no memory". */
static inline vcr_u32 vcr_dd_heap_retry(vcr_u32 heap_start)
{
    return heap_start == 0;
}
```

`vcr_dd_heap_range` stays as it is. It already takes the floor in bytes and rounds it to a page.

### 5.2 Miniport and flag

- **`KMD/miniport/vcrmp.c` `fill_info`.** Read `DdHeapFloor` **once** into a local, `hf = VcrDiagGet(L"DdHeapFloor", 0)`,
  and emit two positive flags: `(hf ? VCR_INFO_F_DDHEAPFLOOR : 0) | ((hf & 2) ? VCR_INFO_F_DDHEAPGLIDE : 0)`.
  - A pre-G63 DLL with the new miniport and value 2 still gets the page floor.
  - The new DLL with today's miniport fda1b8c9 gets the page floor for any non-zero value, because that miniport maps
    every non-zero value to 0x1000.
  - No pairing is ever worse than value 1.
- **`KMD/include/vcr_ioctl.h`:** `VCR_INFO_F_DDHEAPGLIDE` on the next free bit.
  - Several designs already claim 0x8000-0x20000 (G01, G03, G05, G07, G08, G09, G16, G39). The integrator picks the
    bit.
  - `test_vcr_kmd_abi.c::every_vcr_info_flag_owns_one_bit` and the uniqueness assert in `test_vcr_kmd_ddraw.py` catch a
    clash.

### 5.3 Display DLL plumbing

- **`vcrdd_2d.c` `VcrDd2dInit`.**
  - Add `pd->dd_heap_floor = 0` to the reset before the IOCTL, so an older miniport arms nothing.
  - After `pd->napalm` is set (`:451`), the field becomes **bytes**:
    `pd->dd_heap_floor = vcr_dd_heap_floor(((flags & F_DDHEAPFLOOR) ? 1u : 0u) | ((flags & F_DDHEAPGLIDE) ? 2u : 0u), pd->napalm);`
- **`vcrdd_ddraw.c` `heap_range`.**
  - Pass `pd->dd_heap_floor` straight through, and store the result in `pd->dd_heap_start`/`dd_heap_end` for the
    escape.
  - The INFO line's suffix names the floor: "`(Diag\DdHeapFloor 1: off offset 0)`" or
    "`(Diag\DdHeapFloor 2: above Glide's command FIFO)`".
  - **G47 hook:** when `pd->cf.on` it passes `max(pd->dd_heap_floor, VCR_DD_HEAP_GLIDE_FLOOR)`, not a second
    constant.
- **`vcrdd.h`:** the `dd_heap_floor` comment becomes "bytes (vcr_dd_heap_floor)". Add `dd_heap_start` and
  `dd_heap_end`.

### 5.4 One allocator for every driver-placed block (`vcrdd_d3d.c`, exported in `vcrdd.h`)

```c
static ULONG g_dd_zero_answers, g_dd_zero_recovered;     /* since the DLL loaded: survive PDEVs */

FLATPTR VcrDdHeapAlloc16(VCR_PDEV *pd, VIDEOMEMORY *vm, ULONG bytes)
{
    vcr_surfalign al;
    LONG pitch = 0;
    FLATPTR base;
    memset(&al, 0, sizeof al);
    al.dwStartAlignment = 16;
    al.dwPitchAlignment = 16;
    base = HeapVidMemAllocAligned(vm, bytes, 1, &al, &pitch);
    if (!base && vcr_dd_heap_retry((vcr_u32)vm->fpStart)) {
        g_dd_zero_answers++;
        base = HeapVidMemAllocAligned(vm, bytes, 1, &al, &pitch);
        if (base) {
            g_dd_zero_recovered++;
            /* WARN 513/<next free>: "heap block at offset 0 lost (Diag\DdHeapFloor off): %u bytes placed at %x" */
        }
    }
    return base;
}
```

- `mipchain_ext` (`:437-441`) and `VcrDdD3dCreateMipChain` (`:558-562`) call it instead of building
  `vcr_surfalign` themselves. Their OOM branches stay as they are.
- **It is the only `HeapVidMemAllocAligned` call site in `display/`.**
  - G07 (chain reservation), G10 (`VcrDdD3dCreateZSurface`, whose own two-try loop this replaces), G18, G21 (the
    single-level and render-target placement) and G36 must call it.
  - Every new driver-placed block then inherits the cure.
- **The retry runs only after a 0 answer on a heap at 0.** It can recover at most one block per heap, the one at 0. In a
  real out-of-memory it makes one extra call that also returns 0.

### 5.5 Visibility

- **`VCR_ESC_DD_STATS`** (`vcrdd_escape.c:367-374`) grows from 4 to 8 ULONGs, appended: `[4]` heap start and `[5]`
  heap end (this PDEV), `[6]` `g_dd_zero_answers`, `[7]` `g_dd_zero_recovered`.
  - A caller that asks for 4 still gets 4, as `VCR_ESC_2D_STATS` does.
- **`vcrctl info`** prints `"dd_heap":{"start":..,"end":..,"zero_answers":..,"recovered":..}`, or `null` from an older
  DLL. The armed state can then be read on the box without decoding the ring, between runs only.

### 5.6 The old path (switch absent)

- The heap starts at 0 exactly as today. `the_default_layout_is_unchanged_and_starts_at_zero` keeps pinning that.
- Every allocation that succeeds at the first call is unchanged, call for call.
- The single behaviour change is in the failing path: a 0 answer on a heap at 0 is retried once.
- Nothing touches a register.

## 6. Gating and promotion

| part | gate | why |
|---|---|---|
| lab tools (`texfirst`, `heapfill`), host tests | none | they are tools |
| `VcrDdHeapAlloc16` and its retry | **lands default-ON** | every successful allocation is unchanged; only a call that today returns a spurious `DDERR_OUTOFVIDEOMEMORY` changes outcome, and the outcome it gets (a block at a non-zero offset) is what DirectDraw's second pass does for every surface every day. Shown on silicon by `texfirst` in Phase C's control half |
| value 1 (page) | `Diag\DdHeapFloor = 1`, default OFF | it moves every surface; arming it on `.124` after Phase A is the operator's decision |
| value 2 (Glide window) | `Diag\DdHeapFloor = 2`, default OFF until Phase D | new layout; VSA-100 only |

**Phase D, the promotion.** Conditions:

1. Phase C passes (§9).
2. A week of daily use with value 2 armed, covering UT2004, UT2003, Halo, Thief II (NewDark D3D9), JK DF2 and one GL
   or Glide title in the same boot, with no D3D regression against the 11-12 or 11-08 frames.
3. `vcrctl info` shows `recovered` = 0 throughout.

Then:

- change the miniport's default: `VcrDiagGet(L"DdHeapFloor", 2)`. A Banshee or Voodoo3 gets the page floor; an
  explicit 0 restores today's layout;
- move the switch from `NEW_DIAG` to `MOVED_DIAG` with the evidence (`WT/tests/python/test_vcr_kmd_integration.py:76`,
  `:91`);
- update the README row.

The promotion needs a new `vcrmp.sys` and should ride on G01's miniport deploy. **It is not safe to land the layout
default-on before then.** It moves every DirectDraw and D3D surface on every box, and the low-offset behaviour has
never run on the card.

## 7. Lab tests

### 7.1 d3dprobe `heapfill`: an explicit test, never in the default list, and the only test of its run

- **What it does.**
  1. Right after CreateDevice, it creates a DirectDraw 7 object through `LoadLibrary("ddraw.dll")`, so no link change
     is needed. It reads `GetAvailableVidMem(DDSCAPS_VIDEOMEMORY)` **total** = T and releases the object.
     - On vcr-kmd T is `dwVidMemTotal = he - hs`. ddlab's `vidmem_total` 63,959,040 is exactly 0x3cff000.
     - If DirectDraw cannot be created, the test computes T with `vcr_dd_heap_range` and says so.
  2. One SYSTEMMEM 256x256 R5G6B5 source. For i = 0, 1, ...:
     - fill the source with a unique 565 colour c_i;
     - `CreateTexture(256, 256, 1, 0, R5G6B5, D3DPOOL_DEFAULT)`. Each texture is exactly 131,072 bytes. With
       D3DBigTex it goes through `mipchain_ext`; without, DirectDraw places it;
     - `UpdateTexture(src, t_i)`. DEFAULT textures cannot be locked: `ONBOX` run 12's `*_def` refusals. The
       `_upd` path passed there;
     - stop at the first failure, which must be `8876017c`. n = i.
  3. Draw a 32x32 grid of 8x8-pixel quads, cell i textured with t_i (SELECTARG1 TEXTURE, point sampling), into the
     256x256 readback window. Lock the back buffer and read every cell's centre.
  4. Release everything.
- **Pass:**
  - **every one of the n cells equals c_i exactly**, with 565 to 888 expansion at 32 bpp. That catches any placement
    overlapping another texture, the RT or the Z;
  - **and** the fill ended on `8876017c`;
  - **and**, fullscreen on vcr-kmd (adapter driver `vcrdd.dll`): **slack = T - B - Z - n x 131,072 < 131,072**, with
    B and Z = W x H x bytes of the device's back buffer and depth. In other words, no block the size of a texture is
    missing from the heap.
- **Reported:** `n`, `T`, `B`, `Z`, `slack` and `wrong_cells`. Windowed, or on another driver, the slack is reported
  but not judged (that heap is not fresh).
- **Reference values (§4.3):**

  | mode | old-buggy (floor off) | value 1 | value 2 |
  |---|---|---|---|
  | 1024x768x32 | slack 3,272,704 = the lost 3 MB back buffer + 126,976 | n 439, slack 122,880 | n 431, slack 28,672 |
  | 640x480x16 | slack 643,072 | n 497, slack 114,688 | n 489, slack 20,480 |

### 7.2 `ddlab texfirst [--single|--mip]`: the single-pass failure on demand (DirectDraw 7 is the only API that can make a texture a heap's first allocation)

- **Steps.**
  1. Exclusive fullscreen, with a paced `SetDisplayMode` to a mode other than the desktop's. That gives a new PDEV and
     a fresh heap.
  2. The primary, locked for its address. The primary is not taken from the heap.
  3. **The first heap allocation:** `CreateSurface(DDSCAPS_TEXTURE | DDSCAPS_VIDEOMEMORY, 64x64, R5G6B5)`.
     - `--single` reaches `mipchain_ext` on a D3DBigTex box.
     - `--mip` adds `MIPMAP | COMPLEX`, 2 levels, which reaches `VcrDdD3dCreateMipChain` on the default path.
  4. A second, identical texture.
  5. The paced restore.
- **RESULT** `{"mode":"texfirst","res":..,"kind":"single|mip","hr1":..,"from_primary1":..,"hr2":..,"from_primary2":..}`.
- **Runner:** `ddlab_run.py` adds `texfirst` to `FULLSCREEN` and `SWITCHES["texfirst"] = 2`.
- **Reference values:** §4.3. The old-buggy value is `hr1 = 8876017c`. With the retry and no floor, `hr1 = 0` at
  0x2000; with value 1 at 0x1000; with value 2 at 0x118000.

## 8. Host regression tests (each asserts the fixed AND the old-buggy value)

### 8.1 `WT/tests/native/test_vcr_kmd_ddheap.c` (extended; it also includes `common/vcr_texlod.c`)

- **A model of the heap manager's contract.**
  - `m_alloc`: first-fit, ascending, 16-byte start, no overhead; returns 0 for no memory, **and a block at 0 is
    handed out as 0**.
  - `m_dxg`: two passes.
  - `m_driver_old`: one pass.
  - `m_driver_new`: one pass plus `vcr_dd_heap_retry`.
- **`TEST(a_fresh_heap_at_zero_loses_its_first_block)`.** The 11-12 fullscreen ring: with the floor off,
  `m_dxg(3 MB)` = **0x300000**, then 0x600000, then a texture at 0x900000. With value 1: 0x1000 / 0x301000 / 0x601000.
  With value 2: 0x118000 / 0x418000 / 0x718000.
- **`TEST(a_single_pass_block_first_in_a_fresh_heap)`.**
  - Old: `m_driver_old(8192)` = **0**, which is DDERR_OUTOFVIDEOMEMORY, and the next one = 0x2000.
  - New, floor off: 0x2000, with `vcr_dd_heap_retry(0)` = 1.
  - Floor 1: 0x1000, with `vcr_dd_heap_retry(0x1000)` = 0, so there is never a retry.
- **`TEST(ddlab_vidmem_on_124s_desktops)`.**
  - At 1280x1024x32: 116 off and 117 with value 1 (lowest +512 KB against +4 KB); 115 with value 2.
  - At 1024x768x32: 120 against 121, the silicon number, with value 2 at 119.
- **`TEST(the_floor_table)`.** `vcr_dd_heap_floor(0, 1)` = 0 (today), `(1, x)` = 0x1000, `(2, 1)` = 0x118000,

    not wrap.

## 10. Risk to proven paths

| path | risk | mitigation |
|---|---|---|
| default 16 bpp path | none with the switch absent, apart from the retry in the failure path. Armed: every surface moves down by the lost block's size, so more textures sit below 16 MB, which only helps G21's above-16 MB bug | the full d3dprobe matrix at 16 bpp (640x480x16 fullscreen) in Phase A |
| texture base wrap | value 1 lets a driver- or runtime-placed small texture sit below its 256-level offset when the first allocations are tiny (a small window). That is the same class as today's windowed case. The default path's 24-bit field then samples 16 MB high, and the write-back is skipped | value 2 rules it out (0x118000 > 0x55550, host-tested) |
| Glide/OpenGL coexistence | value 1 puts a fullscreen back buffer and Z inside Glide's FIFO window, where today's lost block often covered it. Host writes there under a stale FIFO escalate to a 2D give-up (G01) | Phase A and C start from a cold boot; value 2 removes the exposure, and the promotion target is value 2 |
| SLI/AA state | none: the heap is chip 0's DirectDraw bookkeeping; no register is touched | — |
| flip path | back buffers at new offsets (0x1000 or 0x118000), each 4 KB-aligned. Flip completion takes no address (`vcr_flip.h`). Whether `vidDesktopStartAddr` needs any alignment above 16 bytes for a linear surface is unmeasured | `ddlab flip`, d3dprobe `perf` and the fullscreen matrix in both phases |
| VGA pad [0, 0x18000) | value 1 places live surfaces there (inferred harmless) | value 2 avoids it |
| heap capacity | value 2 costs 1.09 MB: a net loss against today of 0.51 MB at 640x480x16 and 0.18 MB at 800x600x16, and a net gain wherever the first allocation is larger than 1.09 MB | §3 table |
| `Diag\DesktopOffset` pinned low | with value 2 a desktop below 0x119000 leaves no heap, so DirectDraw falls back to the HEL | a debug override, unset on `.124`; the native test pins "empty, never reversed" |
| binary pairings | new DLL with old miniport, or old DLL with new miniport: value 2 degrades to value 1, never further | §5.2 |

   set in the staged titles' environment on `.124`.

   and forces one with `vcrctl modeseq` if not.
