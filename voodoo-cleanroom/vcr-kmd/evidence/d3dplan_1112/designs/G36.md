## 1. Verdict

**The gap has two halves, and they have different answers.**

1. **Render-to-texture on our HAL is real, untested and fixable.** Two defects are verified by reading the
   code; neither has been seen on silicon because nothing has ever rendered into a texture here.
   - **Placement.** A render-target texture (`DDSCAPS_TEXTURE|DDSCAPS_3DDEVICE`) is excluded from
     `mipchain_ext` (`KMD/display/vcrdd_d3d.c:389-391`), so DirectDraw's linear heap places it on a 4-byte
     boundary, as it did UT2003's fonts at `0x91d6b4`.
     - `colBufferAddr` and `texBaseAddr` both drop address bits 3:0 (SPEC §8.40 L3568 "Must be 16-byte
       aligned"; §8.79 L3966).
     - The 3D engine then renders up to 12 bytes before the surface, into the tail of whatever DirectDraw
       placed in front of it. The TMU samples from the same truncated base, so the round trip looks right,
       while the CPU and the 2D blitter see the image shifted by 2, 4 or 6 texels (inferred from the
       register definitions).
     - `target_of` checks the target's pitch (`vcr_rt_rtcheck`, `KMD/include/vcr_rtfmt.h:124`), never its
       base.
     - **The fix exists as a design:** G21's `Diag\D3DTexPlace` bit 1 places these textures 16-byte
       aligned with pitch = width × bytes (`designs/G21.md` §4.4). G36 consumes it and supplies the
       round-trip proof.
   - **Coherency.** Nothing marks a texture "written" when the 3D engine renders into it. The TMU cache
     is flushed only for surfaces flagged by `Unlock`/TEXBLT (`VcrDdD3dTexWritten`, `vcrdd_d3d.c:606-614`;
     `flush_written`, `:1287-1320`), so a texture rendered after it was last sampled can be read stale.
     SPEC §20.3 (L6183-6189): "Napalm needs explicit software intervention to maintain cache coherency."
     Fixing it naively adds a **second** defect: the existing flush writes the texture's first dword back
     through the texture port (`KMD/display/vcrdd_3d.c:263-267`). It reads that dword through the LFB
     with the CPU, and an LFB read is not ordered after the rendering still queued in the engine (SPEC
     §20.1: LFB access is "non-synchronized"). So a flush right after rendering would put **stale** texels
     back at (0,0) and (1,0).
     - This is G37's 3D half. G37 has no design yet, so Part B below specifies it.
2. **Halo cannot get its render targets from any fix inside the DX7 DDI.** This is read from its binary
   (§3) and from XP's runtime (§2.3).
   - Halo 1.10 creates eight render-target textures in one loop and raises FATAL 105 when any
     `CreateTexture` fails. **Five of them are `D3DFMT_X8R8G8B8`** (128² ×3, 64² ×2).
   - XP's d3d8/d3d9 grant a DX7 driver render-target texture formats **only** from their built-in PCI-id
     table. The entry for `121a:0009` is `0x4580`, which lacks the X8R8G8B8 bit `0x200`; the registry can
     only switch flags off (`ForceDriverFlagsOff`; d3d9.dll has no "on" string).
   - On `.124` (`D3DBigTex` bit 2 armed) Halo first tries a **back-buffer-sized A8R8G8B8** target
     (1280x960, not a power of two). The POW2 caps refuse that too (inferred; §4 E3 measures it).
   - So the plan's step 3, "retry Halo without `DisableRenderTargets`", reproduces FATAL 105 whatever the
     HAL does. **Do not spend a supervised boot on it.**
   - The only routes are G94 (a DX8-level DDI that publishes its own format ops) or a Halo-local `d3d9.dll`
     shim that turns the X8R8G8B8 targets into A8R8G8B8 ones. Either one needs `DisableAlphaRenderTargets`
     staged in place of `DisableRenderTargets`. That is the user's decision (§6).

**What this design delivers:**
- **Part 0:** a log-only census of render-target textures, default on.
- **Part A:** placement, which is G21 bit 1 and needs no new code here.
- **Part B:** coherency for 3D-written textures, behind a switch.
- **Part C:** the probes that turn every remaining "inferred" into a measurement: `d3dprobe rtt*`, plus a
  new `d3d9probe` with `caps9`, `halort9` (Halo's exact sequence, replayed) and `rtt9`.
- **Part D:** the Halo decision, with a guard test so nobody removes the staged flag by mistake.

**Halo outcome.** This item alone unblocks no title. Halo's render-target effects follow only from G94 or
the shim. Thief II's distortion and Max Payne's render targets follow only if the census shows they use
granted formats.

## 2. What happens today (verified)

### 2.1 Creating a render-target texture (D3D8/D3D9 → our DDI)

- **`Dd_CanCreateSurface` accepts every `TEXTURE|3DDEVICE` surface** (`KMD/display/vcrdd_ddraw.c:610-631`).
  It refuses only non-16-bit Z buffers without D3D32. 3dfx accepted only 565, plus 8888 and 1555 on Napalm
  (`VH5/DDSURF.C:158-195`).
  - XP's d3d8/d3d9 never ask us for anything but R5G6B5 and A8R8G8B8 (§2.3). Only a DX7 application could
    create a 4444 or 1555 render target, and `vcr_rt_format` would draw it as 565. That bug belongs to G93
    (`designs/G28.md` §3.8).
- **`Dd_CreateSurface` → `VcrDdD3dCreateMipChain`** (`vcrdd_ddraw.c:633-645`).
  - Default path: places only `TEXTURE|MIPMAP` chains (`vcrdd_d3d.c:537-539`).
  - BigTex path: `mipchain_ext` places every texture except `SYSTEMMEMORY|3DDEVICE` (`:389-391`).
  - Either way a render-target texture returns `DDHAL_DRIVER_NOTHANDLED`, and dxg places it in the linear
    heap.
  - **Measured for dxg's placement:** back buffers `pitch 4096` for 1024 px x 32 bpp (`EV/onbox/session_log.md`,
    10:02 entry), so pitch = width × bytes. Textures at 4-byte offsets `0x91d6b4`/`0x93d6b4`
    (`KMD/evidence/d3dtune_1014/sweep_1108/UT2003_combos_unaligned.txt`). That render-target textures get
    the same is inferred (same allocator).
- **`CreateSurfaceEx` names it** (`name_surface`, `vcrdd_d3d.c:1921-1949`). That is the first point at
  which its `fpVidMem` is known to us; it is logged at DEBUG only.

### 2.2 Rendering into it, and sampling it

- **DP2 `SETRENDERTARGET`** (`vcrdd_d3d.c:1725-1753`) → `target_of` (`:1047-1088`):
  - `vcr_rt_format` takes 16 bpp, or 32 with `rt32`;
  - `vcr_rt_rtcheck` requires pitch ≥ a row, a multiple of 16 and ≤ 0x3fff;
  - `vcr_rt_zcheck` checks the Z;
  - **nothing checks `fpVidMem & 15`.**
  - `vcr_3d_target_seq` writes `colBufferAddr = rt_off` as is (`KMD/include/vcr_3dseq.h:71`). The chip
    ignores bits 3:0.
- **Clear2 / DP2 CLEAR** fastfill the same target (`clear_rects`, `:1408-1421`).
- **Sampling.** `compute_regs` → `view_of` → `tex_view` (`:754-799`) or `tex_view_ext` (`:806-837`).
  Both require pitch = w × bytes and a power-of-two size (`KMD/common/vcr_texlod.c:19, 107`), and
  both mask the base to 16 bytes.
  - A target dxg gave a 4-aligned address is therefore sampled from the same truncated base it was rendered
    at.
  - A target whose pitch is not w × bytes is refused for sampling: WARN 513/7 "texture %u refused", caps
    `…3000`.
- **Coherency.** `prepare` (`:1322-1365`) flushes only bound textures whose `SF_DIRTY` is set, and only when
  the global `g_tex_writes` counter has moved since this context last looked (`:1327-1334`).
  - Rendering never sets `SF_DIRTY`.
  - The flush itself is `VcrDd3dTexFlush` (`KMD/display/vcrdd_3d.c:253-271`): 2D NOP, `texBaseAddr` set to
    its inverse and back with a nopCMD, 2D NOP. That is exactly SPEC §20.3's five steps.
  - It is followed by the 86Box-oriented texture-port write-back. That writes back a dword the CPU reads
    through the LFB (`:263-267`), gated by `Diag\TexPortFlush` (default 1, `KMD/miniport/vcrmp.c:235`).
- **A second hole in the same mechanism (verified by reading, affects CPU uploads too).** A dirty texture
  that is not bound at the first triangle after the counter moves is never flushed later:
  - the counter is consumed by that triangle;
  - when the texture is bound later, `prepare` sees no counter change;
  - safety then depends on `texBaseAddr` changing value, which flushes the cache by itself (SPEC §20.3
    step 3).
  - Untextured draws do not write `texBaseAddr` (`vcrdd_3d.c` `VcrDd3dState`). So
    "sample A → render into A untextured or by Clear → untextured HUD → sample A" is stale even after G37
    marks A (inferred sequence; `rtt_stale` in §8 builds it).
- **3dfx's HAL** sidesteps all of this. It flushes the TMU cache (inverse base, then base) at **every**
  texture state send (`VH5/D6DP2.C:6709-6713`), and its `SetRenderTarget` does nothing extra
  (`VH5/D7DP2.C:68-142`).

### 2.3 What the XP runtime will create for us (verified in `D3D9`; d3d8 carries the same table and code)

- **Driver-flag table.** The entry for `121a:0009` sits at file offset `0x1410`:
  `{0x121a0009, 0, 0, 0x4580}` (read back this session).
- **Per-format builder.** For each texture format the DX7 driver lists, it tests one flag bit per format at
  `0x4fdfbe19-0x4fdfbe4b`:

  | format | flag bit |
  |---|---|
  | R5G6B5 | `0x100` |
  | X8R8G8B8 | `0x200` |
  | A8R8G8B8 | `0x400` |
  | A1R5G5B5 | `0x800` |
  | A4R4G4B4 | `0x1000` |
  | X1R5G5B5 (`0x4fdfbc3f`) | `0x2000` |

  When the bit is set it ORs a render-target op into **that texture entry**. The op is
  `OFFSCREEN_RENDERTARGET` (8) with flag `0x4000`, else `SAME_FORMAT_UP_TO_ALPHA` (`0x100`)
  (`0x4fdfbc2a-0x4fdfbc3a`).
- **Normalisation** (`0x4fdfc240-0x4fdfc264`). An entry with 8 gains `0x110`, so OFFSCREEN implies both
  same-format variants. With `0x4580`, R5G6B5 and A8R8G8B8 (when listed) become texture + every
  render-target op.
- **The X8R8G8B8 render-target op lives in an entry with no TEXTURE op.** The builder adds stand-alone
  `SAME_FORMAT_RENDERTARGET` entries for the display format and for X8R8G8B8 (`0x4fdfbfb0-0x4fdfc057`).
  They carry no `OP_TEXTURE`.
- **`IDirect3D9::CheckDeviceFormat`** (`ret $0x1c`, required ops built at `0x4fdf8b93-0x4fdf8bce`):
  - for `D3DUSAGE_RENDERTARGET` it requires `SAME_FORMAT` (`0x10`) when the format equals the adapter
    format, `SAME_FORMAT_UP_TO_ALPHA` (`0x100`) when they are equal after stripping alpha, otherwise
    OFFSCREEN (8);
  - it then looks for **one entry** holding all required ops (`(ops & req) == req`, loop
    `0x4fdf8c22-0x4fdf8c4c`), with no OR across entries.
- **Consequences:**
  - an X8R8G8B8 render-target texture at an X8R8G8B8 adapter needs TEXTURE|`0x10` in one entry. No such
    entry exists, and none can: listing X8R8G8B8 as a texture (G34) gives it TEXTURE alone, because
    `0x200` is not in our flags;
  - R5G6B5 is granted at any adapter format;
  - A8R8G8B8 is granted while `D3DBigTex` bit 2 lists it;
  - A1R5G5B5, A4R4G4B4 and X1R5G5B5 render-target textures are never granted.
  - **This settles runtime-06's open alternative: X8R8G8B8 render targets are impossible through our DDI.**
  - `CreateTexture` validating through the same lookup is inferred. §4 E2 measures it.

## 3. Halo 1.10, read from its binary (verified, static)

**The creation function** is `0x52ca20`. It is called from `0x517339` (device creation) and `0x515f40`
(inferred: device reset). The table is 9 slots of 20 bytes `{w, h, fmt, surface, texture}` at `0x69d358`
(.data, file offset `0x29d358`).
- Slot 0 is always the back buffer.
- `0x52ccc0` = `SetRenderTarget(slot)` and `0x52cdd0` = `SetTexture(stage, slot)` index it.
- The loop (`0x52cafc-0x52cb75`) calls `IDirect3DDevice9::CreateTexture(w, h, 1, D3DUSAGE_RENDERTARGET, fmt,
  D3DPOOL_DEFAULT)` (vtable `0x5c` at `0x52cb43`). It runs for slots 1-8 whose surface is still NULL, and
  stops at the first failure.
- If the texture pointer stays NULL it calls `0x57ea70(0x69, 0x72, 1)` (`0x52cb51-0x52cb57`).
- `0x69` = **105**. The English `Strings.dll` text: *"Your computer's video driver is known to have serious
  issues with the game…"*; `0x72` = 114 is the support URL.

| slot | static {w, h, fmt} (`0x69d36c…0x69d3fc`) | at run time |
|---|---|---|
| 1 | 640, 480, **A8R8G8B8** | overwritten with the **back buffer's W x H** and A8R8G8B8 (`0x52cab3-0x52cad6`); or **the back buffer itself** when alpha targets are off |
| 2 | 320, 240, A8R8G8B8 | overwritten with **W/2 x H/2** (`0x52cae0-0x52cae5`); skipped when alpha targets are off |
| 3 | 128, 128, **X8R8G8B8** | created |
| 4 | 128, 128, **X8R8G8B8** | created |
| 5 | 64, 64, **X8R8G8B8** | created |
| 6 | 64, 64, A8R8G8B8 | skipped when alpha targets are off |
| 7 | 64, 64, **X8R8G8B8** | created |
| 8 | 128, 128, **X8R8G8B8** | created |

No other code writes slots 3-8's formats (searched for every address).

**The flags.** The config handlers are `0x57d180` (`DisableRenderTargets` → `0x722b70`) and `0x57d190`
(`DisableAlphaRenderTargets` → `0x722b74`), registered in the table at `0x69fe80`. They map as follows:
- `DisableRenderTargets` sets `0x69c689` **and** `0x69c68a` (`0x516e87-0x516e96`). `0x69c689` skips the
  whole loop (`0x52caeb-0x52cafa`).
- `DisableAlphaRenderTargets` sets `0x69c68a` only (`0x516e9d-0x516ea5`).
- **Halo also sets `0x69c68a` itself** when `IDirect3D9::CheckDeviceFormat(adapter, HAL, X8R8G8B8,
  D3DUSAGE_RENDERTARGET, D3DRTYPE_SURFACE, A8R8G8B8)` fails (`0x517201-0x51723a`).

**What that means on `.124`** (`D3D32` + `D3DBigTex=7`, `-vidmode 1280,960,85`):
- A8R8G8B8 is listed, so Halo's alpha check passes (A8R8G8B8 at an X8R8G8B8 adapter needs `0x100`, which
  the normalisation supplies).
- `0x69c68a` therefore stays 0, and slot 1 is **1280x960 A8R8G8B8**: not a power of two. That is refused,
  because TextureCaps says POW2 without NONPOW2CONDITIONAL (`EV/caps_124.txt` TextureCaps `0x4007`; that
  D3D9 enforces it is inferred). FATAL 105 at slot 1.
- Without `D3DBigTex` bit 2 the alpha check fails, Halo turns alpha targets off by itself, and FATAL 105
  comes at slot 3 (X8R8G8B8).
- **With `DisableAlphaRenderTargets` staged and X8R8G8B8 targets available,** Halo would create only the five
  power-of-two X8R8G8B8 targets (224 KB). That is the end state worth aiming for.

**The staged entry.** `LIB/Halo/config.txt` is 22,709 bytes against the 1.10 patch's 22,678
(`LIB/Halo/NOTES-halo.txt`). The 31 bytes are exactly `\tDisableRenderTargets\r\n\tbreak\r\n` inserted under
`0x0009 = "Voodoo 4 and 5"`. In the stock file that device falls through to `UnsupportedCard` with the rest
of the 3dfx list. So the project added the flag and the `break`, as `FINDINGS.md:435-442` implies.

## 5. The design

### 5.0 Part 0: say which titles render into textures (log only, default ON)

This follows the hal §10 Phase 0 convention and G52's rule: no IOCTL per draw.

1. **In `name_surface`** (`vcrdd_d3d.c:1921`), for a surface with both `DDSCAPS_TEXTURE` and
   `DDSCAPS_3DDEVICE` in video memory, one INFO line:
   `render-target texture %u: %ux%u %u bpp (R %x A %x) at %x pitch %u%s`. The suffix is one of:
   - " - OFF the 16-byte grid: the 3D engine draws %u bytes before it" (`fpVidMem & 15`);
   - " - pitch is not width x bytes: the TMU cannot sample it";
   - " (driver-placed)" when `SF_MIP_TOP` is set (G21 bit 1).

   It fires once per creation, which is rare. A per-PDEV counter `pd->rtt_created` is incremented.
2. **In the `SETRENDERTARGET` case** (`:1725`), when the new target is a texture:
   - `c->rtt_sets++`;
   - an INFO line for the first 8 distinct surfaces per context only:
     `context %u renders into texture %u (%ux%u, %u bpp, z %u bits)`.
3. **In `ctx_free`** (`:1210`), next to "context %u gone", a summary that survives the ring wrap (G76):
   `context %u render targets: %u texture targets set, %u marked for the TMU, %u flushed, %u off the grid;
   %u render-target textures created on this PDEV`.
4. **Events.** These are the next free 513 `what` numbers when this lands; 24-27 and up are claimed by the
   G05/G06/G07/G21 designs. Update the 513 row in `KMD/include/vcr_events.h:75`.
5. **No register writes, no new IOCTL on the drawing path.** Pinned by
   `test_the_render_target_census_writes_no_register`.

### 5.1 Part A: placement = G21 `Diag\D3DTexPlace` bit 1 (no new code here)

**G21 §4.4 already specifies it.** `mipchain_ext` keeps `3DDEVICE` textures only when `!pd->rtt_place`. With
bit 1 they get `HeapVidMemAllocAligned(…, {16, 16})` and pitch = w × bytes, which is a multiple of 16 for
R5G6B5 ≥ 8 wide and A8R8G8B8 ≥ 4 wide, and at most 8192 (SPEC §8.41 L3577: stride ≤ 16383, 16-aligned).

**G36's additions:**
- **The acceptance proof** for bit 1 is `rtt_copy` plus G21's `rtt_align` (§8).
- **The non-goal.** A render-target texture narrower than 8 px at 16 bpp keeps a pitch under 16. It stays
  refused as a target (`vcr_rt_rtcheck`) and is logged by Part 0. That is no regression: dxg gives it the
  same pitch today.
- **Risk inherited from G63.** The placement uses the single-pass allocator. A render-target texture that is
  the first block of a fresh heap would get `DDERR_OUTOFVIDEOMEMORY` while `Diag\DdHeapFloor` is off
  (`KMD/include/vcr_ddheap.h`). Device creation allocates the flip chain and Z first (inferred), so
  `rtt_copy` runs after one.

### 5.2 Part B: TMU coherency for textures the 3D engine wrote (G37's 3D half)

**Implement it once.** Use G37's switch if G37's design covers the 3D half; otherwise use
**`Diag\D3DRtt` bit 0**. It is read at boot in `VcrFindAdapter` beside `D3DBigTex`, as
`x->d3drtt = VcrDiagGet(L"D3DRtt", 0)`, and reaches `VcrDd2dInit` as a new positive `VCR_INFO_F_RTTSYNC`
bit, giving `pd->rtt_sync`. That bit is the next free one at landing; G21 records that `0x8000` and
`0x10000` are already claimed by other designs. It applies on every chip; the Voodoo3 branch below exists
for the 86Box bed.

**A Win32-free decision header `KMD/include/vcr_rtt.h`** (host-tested):

```c
/* the 3D engine wrote this surface (it was the render target and was drawn or
 * cleared): mark it for the TMU when rendering leaves it - a texture only, in
 * video memory; never a flip-chain buffer (not a texture) */
static __inline unsigned vcr_rtt_mark(unsigned is_texture, unsigned in_vidmem, unsigned drawn)
{ return is_texture && in_vidmem && drawn; }

/* the texture-port write-back address for a flush (VcrDd3dTexFlush's `addr`):
 * a texture the 3D ENGINE wrote gets none on a VSA-100 - SPEC 20.3's flush
 * (2D NOP, texBaseAddr away and back, 2D NOP) is complete without it, and the
 * write-back would put back a dword the CPU read through the LFB before the
 * queued rendering landed (SPEC 20.1: LFB access is not synchronized) */
static __inline unsigned vcr_rtt_writeback(unsigned napalm, unsigned rt3d, unsigned addr)
{ return (rt3d && napalm) ? ~0u : addr; }

/* a Banshee/Voodoo3 (the 86Box bed, whose texture cache watches only the
 * port) keeps the write-back for a 3D-written texture, after an idle */
static __inline unsigned vcr_rtt_needs_idle(unsigned napalm, unsigned rt3d)
{ return rt3d && !napalm; }
```

**In `vcrdd_d3d.c`:**

1. **`SF_RT3D 0x10u`.** It is the next free bit after G21's `SF_PAD8 0x8`, beside `SF_DIRTY 0x4`
   (`:209`). It means "written by the 3D engine since the TMU last looked".
2. **The context gets `ULONG rt_drawn, rtt_sets, rtt_marks, rtt_flushes`.**
   - `rt_drawn = 1` is set in `prepare`'s full path, after `VcrDd3dTarget` succeeds (`:1361`). That is once
     per state send, not per triangle.
   - It is also set in `clear_rects` after a successful fastfill (`:1416-1418`).
3. **`rt_leave(c)`.** If `pd->rtt_sync && vcr_rtt_mark(caps & TEXTURE, in_vidmem(c->rt), c->rt_drawn)`, then:
   - `VcrDdD3dTexWritten(c->rt)` (sets `SF_DIRTY` and moves `g_tex_writes`);
   - `c->rt->dwReserved1 |= SF_RT3D`;
   - `c->rtt_marks++`;
   - and finally `c->rt_drawn = 0`.

   It is called:
   - in the `SETRENDERTARGET` case before `c->rt = rt` (`:1735`), when `rt != c->rt`;
   - in `ctx_free` before the `memset` (`:1210-1221`): another context may sample the texture later.
4. **`flush_written`** (`:1287-1320`) collects `rt3d` alongside `dirty` (any level with `SF_RT3D`) and
   clears both flags. On the ext path it passes
   `vcr_rtt_writeback(pd->napalm, rt3d, vcr_tex_writeback_addr(...))`; on the old path it passes
   `vcr_rtt_writeback(pd->napalm, rt3d, fpVidMem)`. When `vcr_rtt_needs_idle` holds it calls `VcrDd2dSync`
   first. Then `c->rtt_flushes++` when `rt3d`.
5. **Flush on bind** (closes the hole of §2.2). In `prepare`'s full path, after `compute_regs` (`:1337`),
   with `pd->rtt_sync`: `flush_written(c, c->tex_surf0); flush_written(c, c->tex_surf1);`.
   - `flush_written` returns at once when no level is dirty: a loop of at most 12 flag reads per bound
     texture.
   - The flush's `texBaseAddr` writes are queued before `VcrDd3dState` writes the real state, so the order
     is the one SPEC §20.3 asks for.
   - With the switch this also closes the same hole for CPU uploads. That is G37's other half; say so in
     the commit.
6. **Feedback watch.** When a bound texture is the current target (`c->tex_surf0 == c->rt` or `tex_surf1`),
   log one WARN per context, "texture %u is sampled while it is the render target (undefined in D3D)".
   Nothing else changes.

**Single pass, no new register.** The flush is the proven `VcrDd3dTexFlush` sequence. The only change in
register traffic is that, for a 3D-written texture on a VSA-100, the one texture-port write is left out.
That write was the bed's accommodation and is not required by the SPEC.

## 7. Gating

- **Part 0 (census):** default ON. It writes no register, adds no IOCTL per draw, and is pinned by a source
  test.
- **Part A:** G21's `D3DTexPlace` bit 1, default off, graduating on G21's rules plus `rtt_copy` passing.
- **Part B:** default OFF behind `Diag\D3DRtt` bit 0, or G37's switch.
  - **Off, it is byte-for-byte today's path.** On, register traffic changes only inside contexts that
    render into a texture (an extra proven flush) and in the rare CPU-upload case of §2.2 (a flush that
    should have happened).
  - **Graduation:** after **one supervised clean boot** where `rtt_stale`, `rtt565`, `rtt8888`, `rtt_z` and
    `rtt9` pass, and the default lists stay 40/40 / 42/42.
  - **Default-on is plausible and does not need a separate game run,** because no title uses this path
    successfully today. Still, it is new traffic in titles not yet censused (Thief II, Max Payne, UE2). So
    flip the default only after E6's census shows which titles exercise it and a frame check of each shows
    no regression.
  - The flip needs a `MOVED_DIAG` entry (`WT/tests/python/test_vcr_kmd_integration.py:86-91`).
- **One Diag change per clean boot:** `D3DTexPlace` and `D3DRtt` are both read at boot. Each boot goes
  through `safe-reboot.py` after the activation check.
- **Tools (Part C):** no gate. They run under the usual lab rules: paced switches ≥ 5 s apart, never while a
  D3D game runs, never `vcrctl`/ExtEscape during a D3D title.
- **Part D:** no staged change without the user's decision and a supervised proof.

## 11. Risk to proven paths

- **Default 16 bpp path:**
  - Part 0 adds rare log lines.
  - Parts A and B are off by default. With them on, a title that never renders into a texture issues the
    identical register stream, because both act only on `TEXTURE|3DDEVICE` surfaces.
  - The only shared-path change is the flush-on-bind for a dirty CPU-uploaded texture, which runs only when
    `SF_DIRTY` is still set, i.e. a flush that should already have happened.
- **Glide/OpenGL coexistence:** no new register is written. The flush sequence is the one D3D already uses
  for uploads. Probes still need G01's clean engine, or every triangle reads as a FAIL for an unrelated
  reason.
- **SLI:** none today, because D3D renders on chip 0 with `sliCtrl` 0 (`KMD/include/vcr_3dseq.h:189`).
- **Hand-off to G51:** under SLI a target is split across the chips by y′ packing (SPEC §8.29 L3427), so a
  texture rendered with SLI on is incomplete on every chip (hw Q12, inferred). G51 must either drop SLI for
  any context whose target is a texture (sliCtrl 0 with broadcast writes, so every chip renders the whole
  texture into its own replicated copy), or keep render-to-texture on chip 0 and broadcast nothing. Add
  `rtt565`/`rtt_stale` to G51's gate.
- **Flip path:** none. A flip-chain buffer is not a texture, and `rt_leave` ignores it.
- **Memory and allocation:** G21 bit 1 moves render-target textures into the single-pass allocator (G63's
  offset-0 case, §5.1).
- **Performance:**
  - one flush (7 register writes and two 2D NOPs) per render-target texture per switch away. Halo's set
    would be at most about 8 per frame;
  - one dirty-flag loop per state recompute;
  - no idle on the VSA-100.
- **86Box bed:** the Voodoo3 branch keeps the write-back after an idle. Whether the emulator's texture cache
  sees pipeline writes at all is unknown, so `rtt_stale` is a **silicon** verdict, and on the bed it is
  recorded but not gated.

## 13. Open questions

1. Does D3D9 (and D3D8) refuse a non-power-of-two `D3DUSAGE_RENDERTARGET` texture under POW2 without
   NONPOW2CONDITIONAL? E2, E3, `rtt_np2`. The runtime check was not located in the disassembly.
2. Does the runtime's `CreateTexture` validation use the same per-entry op lookup as `CheckDeviceFormat`?
   E2 versus E1.
3. Does the VSA-100's 2D engine read a surface before the 3D pixels in flight land, without a 2D NOP first?
   E5.
4. Is the SPEC §20.3 flush without the texture-port write-back enough on silicon?
   - for 3D-written textures: `rtt_stale` with Part B;
   - for CPU uploads: never isolated. One boot with `Diag\TexPortFlush = 0` and the default list (`tex2add`)
     would settle it.
5. Which `.124` titles render into textures, in which formats and sizes, and which are refused by the
   runtime unseen (E6, E7)? NewDark's distortion is a likely screen-sized, non-power-of-two target
   (inferred).
6. Which Halo effects use which render target? The binary is stripped. A/B frames against `.240` with
   render targets on are the only practical map.
7. With option 2, does any Halo pass read the alpha of a former X8R8G8B8 target (its sampled alpha would no
   longer be 1)?
8. Does 86Box's Voodoo texture cache see pipeline writes, and does the bed's `rtt_stale` mean anything?
9. Does Halo's render-target path then need more: destination alpha (G28), COLORWRITEENABLE (G91; the
   alpha-only pass at `0x520806` per `designs/G28.md`), or Z bias (G22)?
