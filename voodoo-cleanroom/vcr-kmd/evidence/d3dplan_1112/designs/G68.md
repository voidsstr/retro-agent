## 0. Verdict

- **The gap is a real evidence gap. A HAL regression cannot hide in it.** No commit between the
  09-29 build (`bfdf2cd`, 09-29 01:00) and the first 11-08 fix (`76d36e7`) touched `display/` or
  `common/`, so the D3D, DirectDraw and 2D code that drew the black frame on 09-29 is the code that
  drew the menu on 11-08 00:48 (F1). The difference is the **boot's history**, not the driver.
- **The leading explanation is the stale Glide state G01/G03 describe. It is circumstantial, not proven.**
  - On 09-29 Red Faction started two minutes after a 4-chip SLI GLQuake session through MesaFX and our
    h5 Glide, which ended with a console quit.
  - The frame was written uniformly black and stayed so for more than 60 s (F2).
  - Everything Red Faction shows is a Direct3D triangle: Bink movie tiles, in-engine text and the menu (F3).
  - "Clears work, triangles vanish" (G01, measured 11-12) and "triangles drawn through MesaFX's last
    extended combine" (G03) each give exactly that frame.
  - The same sweep recorded the same signature twice more (F5).
  - No ring, no register read and no reproduction exist.
- **Two of the record's own explanations do not hold up.**
  - "Game not focused" is the sweep's artifact. Its own WM_CLOSE took the focus, as fixed in
    `lan_sweep` `fe2a23c` on 2026-10-03 (F4).
  - "Needs its disc mounted" is not a blocker. The staged launcher mounts Red Faction's own image (F6).
- **New facts from the binary that the rest of the plan depends on (F7-F10):**
  - `rf.exe` reads its video settings from **HKCU**, which answers G66's and G10's open question.
  - It asks for **D16 on every 3dfx adapter at any depth**, with an **A8R8G8B8** back buffer at 32 bpp
    (G10, G11).
  - The staged `Vsync`=0 gives IMMEDIATE presents (G65).
  - It picks its own "Voodoo mode" from vendor id 0x121a.
  - After every device it writes `rfd3d.id`, a free record of what it decided on our HAL.
  - It has a built-in benchmark: `-timedemo` / `-frameratetest`.
- **The investigation is one supervised session on the deployed build (`vcrdd` 95678704) with no driver
  or behaviour-switch change.** In order:
  1. **B0** reads what is already on the box;
  2. **B2** shows the no-disc screen on a healthy HAL;
  3. **B1** runs three clean controls;
  4. **B3** replays the 09-29 chain (GLQuake → Red Alert 2 → Red Faction), with `cmdFifo0` read between
     titles, then reproduces the state deterministically;
  5. **B4** is the first in-game look: timedemo, frameratetest and attended play at 640x480x16@85.

  **B5** (1280x960x32) waits for G10 + G66.
- **Code G68 lands is tooling and tests only:**
  - a black-frame verdict and Glide-FIFO attribution in `lan_sweep.py`;
  - a Red Faction device preset and two explicit tests in d3dprobe;
  - `gamerun.py` promoted to `KMD/tools/`, with a timedemo parser;
  - a binary-contract test that also guards the G66-before-G10 ordering hazard.
- **Priority P1** (a prerequisite measurement for the P0 cures G01/G03/G10, and the in-game check of a staged
  title). **Effort M.**

### 1.2 Facts this reading adds

**F1: the D3D HAL did not change between 09-29 and 11-08 00:48.**
- `git diff --stat bfdf2cd 76d36e7^ -- display common include miniport compat` lists only:
  - `include/vcr_aaguard.h`, `vcr_events.h`, `vcr_fbshot.h`, `vcr_sli.h`;
  - `miniport/vcrmp.c`, `.h`, `_log.c`, `_multi.c`, `_sli.c`.

  These are the SLI/AA auto-disarm and AA READ_EN work, and log plumbing.
- **Nothing in `display/` or `common/` changed:** not the DP2 walker, not the 2D engine or its give-up,
  not DirectDraw.
- The 09-29 build is `bfdf2cd` (PLAN, 09-29 05:40 resume point). `b63ea6a5` ran "from the end of September
  until 11-08" (`reports/history.md` §2).
- So hypothesis H6 below ("a HAL bug fixed in between") is excluded.

**F2: a uniformly black frame was WRITTEN black.**
- A mode set does not clear video memory (G39). AvP's 640x480x16 session showed the old desktop as garbage
  for its whole run (V-04), and UT2004's 09-29 30 s frame shows the desktop at 1280x960x16
  (table above).
- So a 640x480 frame with every pixel exactly 0, in GDI at 30 s and 60 s and in the scan-out at
  ~40 s, was painted black by something. Either:
  - Red Faction's D3D `Clear` (fastfill); or
  - GDI erasing Red Faction's fullscreen popup window (`rf.exe` imports `GetStockObject` and
    `RegisterClassExA`; a black class brush is inferred).
- Either way Red Faction's window and mode were up. **For more than 60 s nothing Red Faction draws became
  visible.**

**F3: everything Red Faction draws is a Direct3D triangle.**
- **Bink movies** (`data\movies\thqlogo.bik` plays first) take this path:
  - `CreateImageSurface(640, 480)` (device vtable +0x6c at 0x52048e);
  - per frame: `LockRect`, `BinkCopyToBuffer`, `UnlockRect` (0x5204ca, 0x520553, 0x52056c);
  - `CopyRects` into a texture's level 0 (+0x70 at 0x5206e3, after `GetSurfaceLevel` at 0x5205b7);
  - textured quads, scaled to the screen.
- **The menu and the "Insert Red Faction CD #2 (ESC exits game)" message** are in-engine bitmaps/text
  (`RFL/README-DISC.txt:4-5` calls it an "in-engine message"). That they are textured quads is inferred.
- So both Glide-left states can produce F2's frame:
  - G01's (PIO triangles lost while fastfill works, measured `ONBOX` 10:02);
  - G03's (the FBI/TMU still running MesaFX's last extended combine, from source).
- A missing disc or a missing focus alone would not do it: the text or the movie would show.

**F4: "close keys withheld - game not focused" is the sweep's own artifact.**
- Before `lan_sweep` `fe2a23c` (2026-10-03: "games DO get the keyboard - its own WM_CLOSE took it") two
  things held:
  - no sample recorded the foreground;
  - the only focus check ran **after** the sweep's WM_CLOSE, which takes the game's window
    (`scripts/benchmarks/lan_sweep.py:243-246` comment).
- The same flag sits on Yuri's Revenge, SiN software, SoF2 MP and Unreal Gold, all of which rendered.
- So nothing in the record says Red Faction lacked focus on 09-29. history-34's explanation should be withdrawn.

**F5: the same sweep shows the signature twice more, and one counter-example.**
- **UT2004 after a killed Unreal Gold:** the stale desktop at 30 s (mode already set), then a black frame. That
  is the README's "a KILLED Glide client still needs a cold boot before a 32 bpp D3D test" (`KMD/README.md:112`).
- **Shogo after RTCW MP:** 2D text present, 3D backdrop missing. In the 11-12 stale state, 2D and fastfill
  worked and triangles did not.
- **Thief II after TFC's console quit:** a full menu.
- This fits G01's fact 6: the close-time idle wait ORs all four chips. In 4-chip SLI the not-idle close
  path, which skips `cmdFifo0.baseSize = 0`, is taken only when a slave is still busy
  (`GL5/minihwc/minihwc.c` `hwcRestoreVideo`, the `[retro3dfx]` not-idle branch). It is common, but not
  every time.
- GLQuake on 09-29 ran 4-chip SLI.

**F6: the disc state on 09-29 is unknowable, and does not matter.**
- `Play Red Faction.bat` has `REQUIREDISC=1` (`:69`). With no mounter installed it calls `:fail`, then
  `:theend`, and never starts the game (`:103-108`, `:462-486`).
- `rf.exe` was running on 09-29, so a mounter existed at 04:44. PLAN records DAEMON Tools 3.47 installed
  on `.124` that day.
- Whether the mount succeeded cannot be recovered: `mount-error.txt` is deleted at every launch (`:71`).
  If it failed, `:anydisc` may have started the game "against an unrelated disc" (`:186-210`).
- Without its disc Red Faction stops on the in-engine message above (`README-DISC.txt:4-5`, seen on
  `.145`/`.240`/`.246`). A working HAL draws that message, so even the no-disc case needs F3's explanation.
- Today the launcher mounts `_disc\RedFaction_Disc2.cue` itself, over whatever D: holds.
  onbox-15's blocker ("D: holds the SoF image") disappears when the title is started the way a person
  starts it.

**F7: `rf.exe` reads its video settings from HKCU.**
- The registry helper at 0x52b2a0 takes `HKEY_CURRENT_USER` as the root when its subkey argument is NULL:
  `bd 01 00 00 80`, `mov ebp,0x80000001`, at 0x52b2b3. A non-NULL subkey must spell out a `"hkey..."` prefix.
- The four reads at 0x4b1480-0x4b14ed pass NULL. Their defaults:
  - **16** for `Resolution Bit Depth`;
  - **640** for `Resolution Width`;
  - **480** for `Resolution Height`;
  - **-1** for `Resolution Backbuffer Format`.
- `Vsync` is read the same way (0x54463a).
- The launcher writes HKLM (`Play Red Faction.bat:56-58`). So the measured 640x480x16 is `rf.exe`'s
  built-in default, and every FLEETRES value is dead. This settles G66's question and the one G10 left
  to it.

**F8: the device Red Faction asks for** (0x5444b0-0x5447e6; matches G10 §2).

| field | value |
|---|---|
| swap effect | FLIP |
| `Flags` | `LOCKABLE_BACKBUFFER` |
| back buffer | R5G6B5 at 16 bpp; **A8R8G8B8** at 32 (`24 fe 83 c0 17` at 0x5446b0). Inferred: a `Resolution Backbuffer Format` ≥ 0 overrides it (0x544664) |
| presentation interval | `Vsync` ? ONE : IMMEDIATE (`81 e1 01 00 00 80 81 c1 00 00 00 80` at 0x544668). `install.reg` stages `Vsync`=0, so presents are IMMEDIATE |
| vertex processing | `D3DCREATE_SOFTWARE_VERTEXPROCESSING` |
| depth format | **`D3DFMT_D16` for vendor 0x121a at any depth** (`3d 1a 12 00 00` at 0x544756, then 0x5446f6). NVIDIA ≥ 0x100 gets D24S8 at 32 bpp, Matrox D32 |

At 32 bpp on today's HAL that is G10's refused pair, and it brings G11's double CRT switch.

**F9: what Red Faction decides from our caps.**
- After `CreateDevice` (0x544860 onward) it **requires**:
  - MODULATE;
  - SRCALPHA or BOTHSRCALPHA, and INVSRCALPHA or BOTHINVSRCALPHA;
  - `GetAvailableTextureMem` ≥ 0x500000.
- It **sets these flags:**
  - `D3Dmt` (multitexture), if stages ≥ 2 and simultaneous textures ≥ 2: **1** on us;
  - `D3Dm2x` from `TextureOpCaps` MODULATE2X: **0** on us, so G05 does not reach Red Faction;
  - `D3Dp2t` and `D3Dst` from POW2 and SQUAREONLY;
  - vertex-fog mode from `RasterCaps` FOGVERTEX: yes on us, so G32 matters;
  - DITHERENABLE at 16 bpp;
  - inferred: `D3Dbgb` when the reported guard band does not cover the screen. Ours reports none (G57).
- **For vendor 0x121a with device id ≠ 5 it takes a "Voodoo mode":**
  - `D3Dvm` = 1 and `D3Drhw` = 0.001;
  - inferred: a projection near/far of 1.0/10.001 instead of 0.001/1.001 (0x543a09-0x543a34).

  `-voodoo3` and device id 5 set the Voodoo3 flags instead. The README's `-voodoo` / `-voodoo3` switches
  are therefore not needed on the V5.
- **Then it sets** MIN/MAG LINEAR on stages 0-1, GOURAUD, and SPECULARENABLE FALSE (0x544d52-0x544dfa).
- **It writes `rfd3d.id`** (mode `"w"`, 0x544ee0, called at 0x5447eb after every successful `CreateDevice`):
  - adapter, driver, vendor/device ids;
  - the chosen texture formats;
  - the flags `D3Dsc/bgb/vm/v2m/zm/rhw/st/p2t/mt/m2x`.

  `C:\Games\RedFaction\rfd3d.id` on `.124` should hold the 11-08 run's copy today.

**F10: Red Faction has a benchmark.**
- `-timedemo <level>`: "Player is created at start of level and spins around once. stats ... displayed in
  the console and in a text file". `-frameratetest <level>`: the same spin at every node, per node and
  overall (`RFL/README.TXT:144-151`).
- The `rf.exe` strings include `timedemo.txt` and "Nav point: %d Average frames per second: %.2f min: %.2f
  max: %.2f".
- Levels:
  - `L1S1` … `L6S3`, `train01/02` (`levels1.vpp`);
  - `dm01`-`dm20`, `ctf01`-`07`, `glass_house` (`levelsm.vpp`).
- `reports/perf.md` §6.3 lists Red Faction among the "titles without a timedemo". That is wrong.

## 3. The investigation (one supervised session, no driver change)

### 3.0 Rules

- **Box state.** `vcrdd.dll` 95678704 and `vcrmp.sys` fda1b8c9 as deployed, with `D3D32`=1 and `D3DBigTex`=7
  as armed. No behaviour-switch change.
- **Start clean.** Start from a cold boot with no Glide session.
  - Before it: activation check (`LICSTATUS` WPA), then `scripts/fleet/safe-reboot.py`.
  - **Share G04's boot 1** (`Diag\LogLevel`=2, `LogEntries`=8192, logging only). At LogLevel 3 the 1024-entry
    ring loses Red Faction's `ContextCreate` line, with its target/Z offsets, within seconds (`ONBOX/README.md`).
  - If no reboot is possible, the precondition instead is: `vcrctl reg 0` = 0x1f, `reg 80024` bit 8 clear, and
    `d3dprobe render --full --res 640x480 --bpp 16` = 40/40. H2's state cannot be read that way.
- **Tool timing.** No `vcrctl`/ExtEscape while a D3D game runs. `vcrctl reg` and `tools/vcrlog.py fetch` run only
  between titles.
- **Frames during a run.** Agent `SCREENSHOT 0` (GDI works for Red Faction at 640x480x16; both 11-08 sweeps) plus
  `WINLIST` and `PROCLIST` per shot. This is what `ONBOX/gamerun.py` does.
- **Mode switches** are the games' own, at least 5 s apart. **Never start Red Faction at 32 bpp before G10**
  (F8, G11).
- **Closing a game.**
  - Kill by PID, never by image name. Red Faction ignores WM_CLOSE, so: WM_CLOSE by PID, 20 s, then
    `taskkill /f` by PID, verified.
  - At the no-disc screen, use its own ESC.
  - Afterwards `DISPLAYCFG get` must read 1280x1024x32@85.
- **Evidence** goes to `KMD/evidence/redfaction_<yyyymmdd>/` (repo tree, never the scratchpad). Push it
  at each checkpoint.

### 3.1 B0: read what is already on the box (read-only; can run before the boot)

- `DIRLIST C:\Games\RedFaction`.
- `DOWNLOAD` `rfd3d.id`, and also `errorlog.txt`, `mount-error.txt`, `timedemo.txt` and `console.txt`
  where they exist.
- `REGREAD HKCU Software\Volition\Red Faction` and the same under HKLM: confirms F7 and the staged `Vsync`=0.
- `EXEC cmd /c vol D:`: is D: `RF_2`? That decides whether B2 needs a mount change.

**Expected.** `rfd3d.id` from 11-08 02:14 shows:
- vendor 4634, device 9;
- driver version 6.14.1.1 (`3753b5f`);
- `D3Dmt` 1, `D3Dm2x` 0, `D3Dvm` 1, `D3Drhw` 0.001.

A difference corrects F8/F9 before any game runs.

### 3.2 B2: the no-disc screen (only if D: is not `RF_2`; clean engine)

- Use `gamerun.py` with a wrapper that runs `rf.exe` directly, not the launcher: shots at 10, 20 and 30 s,
  then `UIKEY ESCAPE` while Red Faction is focused.
- **Text on black:** H3 is out. A black 09-29 frame then needs a HAL-side cause, whatever the disc did.
- **Pure black:** H3 stays possible, the 09-29 frame proves nothing on its own, and B3 decides.
- If D: already holds `RF_2`, skip B2. Do not unmount: a locked DAEMON Tools unit raises a modal
  (`Play Red Faction.bat` `:domount` notes).

### 3.3 B1: control ×3 (clean engine; the staged launcher, which mounts `RF_2`)

- Shots at 15, 30, 45, 60 and 90 s.
- After each run:
  - `DOWNLOAD rfd3d.id`;
  - ring fetch: `ContextCreate` (format, target and Z offsets), the "context N gone" counters, the 511/12-13
    flip summary, any 512/513 WARN/ERR;
  - `vcrctl reg 0`, `80024`.
- **Pass:** the THQ logo or 3D intro by 30 s and the menu by 60 s, as on 11-08. 0 unparsed, no refusal, FIFO off.
- **A black run here is H5, or a regression on 95678704 against 11-08's `13256e46`.** Stop and investigate
  with the ring before going on.

### 3.4 B3: the 09-29 chain, with the FIFO read between titles

1. The `Quake` desktop shortcut (GLQuake 1280x960, MesaFX + our Glide, 4-chip SLI, as on 09-29). Run 60 s, then
   the sweep's console quit (TILDE, `TEXT:quit`, RETURN) with GLQuake focused.
2. `vcrctl reg 0`, `80024`, `8002c`, `80034` (status, baseSize, readPtrL, aMin). Fetch the ring: is there a
   `HWCRLSEXCLUSIVE`? Was it "SLI/AA off: display reset" or "Glide asked"? Fetch `retrogl.log` if it is present.
3. `Red Alert 2 - Yuri's Revenge` for 60 s, closed as on 09-29 (WM_CLOSE, then force by PID).
4. The same four reads, and the ring.
5. Red Faction through the staged launcher. Shots at 15/30/45/60/90 s; close; reads, ring and `rfd3d.id`.
6. If Red Faction was black:
   - `vcrctl modeseq 6000 1024 768 32 85` (the 11-12 recovery, paced);
   - reads: expect FIFO off and 0x1f;
   - `d3dprobe render --full --res 640x480 --bpp 16` must be 40/40;
   - Red Faction again: expect the menu.
7. **If the FIFO read off after step 2** (a clean GLQuake close):
   - repeat 1-2 up to three times. That is G01's E0 frequency measurement, for GLQuake;
   - if it never reads on, use G01's deterministic producer (E1): a **1-chip** `glidelab fill` killed by PID
     mid-run, or `glidelab orphan` if G01 has landed it;
   - then the reads, then Red Faction directly (skip Red Alert 2), with the same logic.

## 7. d3dprobe tests

Both compare the locked back buffer with values computed in d3dprobe, its usual analytic method. Point sampling,
`DITHERENABLE` FALSE, `ZFUNC` ALWAYS, `ZWRITEENABLE` FALSE. Run as
`d3dprobe render --app redfaction --bpp 16 --res 640x480`.

### 7.1 `lockbb`: CPU writes into the lockable back buffer, then 3D on top

**Why.** Red Faction asks for `D3DPRESENTFLAG_LOCKABLE_BACKBUFFER` (F8). d3dprobe only ever locks the back buffer
`READONLY` to read it back (`readback()`, `:292`); nothing writes it.

**What it draws:**
1. Clear the target to black.
2. Lock the back buffer (flags 0) and write two blocks:
   - **K**: x 16..79, y 16..79, R5G6B5 0xFC00 (R31 G32 B0);
   - **W**: x 96..127, y 16..47, white.
3. Unlock.
4. Draw an untextured quad **Q**, x 48..111, y 32..63, diffuse (0,0,255), alpha 0x80, SRCBLEND SRCALPHA,
   DESTBLEND INVSRCALPHA.
5. Read back.

**Pass.** Expanded 8-bit RGB per pixel. Exact cells have tolerance 4; blended cells have tolerance 12.

| pixel | content | expected |
|---|---|---|
| (20,20) | K | (255,130,0) |
| (60,40) | K + Q | ≈ (127,65,128) |
| (88,40) | Q over black | ≈ (0,0,128) |
| (104,40) | Q over W | ≈ (127,127,255) |
| (120,20) | W | (255,255,255) |
| (200,200) | untouched | (0,0,0) |

**Old-bug signatures:**
- K or W reads black: the CPU write was lost behind a late clear (Lock not ordered).
- (60,40) reads (0,0,128): the blend read a stale destination.
- (60,40), (88,40) and (104,40) all unchanged: triangles lost. This is the G01 stale-FIFO state, so the test
  is also a canary for it.

At 32 bpp (only after G10) the same geometry is used in A8R8G8B8, with tolerance 3 for exact cells and 4 for
blended cells.

### 7.2 `rgb565_256_recopy`: Red Faction's movie path, copied twice into one texture

**Why.** This is F3's per-frame Bink path. Nothing tests the copy **after** the texture has been sampled. That
is the G37 hazard: the TMU cache is not flushed after a Blt into a texture.

**What it does:**
1. Create a 640x480 R5G6B5 image surface with `CreateImageSurface` (system memory), as Red Faction does.
2. Fill it with pattern A: 32-texel red (0xF800) / blue (0x001F) cells.
3. `CopyRects` the source rectangle (192,112)-(448,368) into a 256x256 R5G6B5 `D3DPOOL_DEFAULT` texture. The
   source offset tests the pitch.
4. Draw a 256x256 quad at 1:1, half-pixel correct (the 11-08 fix), and read back.
5. Refill the image surface with pattern B (green 0x07E0 / white), `CopyRects` again into the **same** texture,
   draw and read back.

**Pass:** all 64 cell centres equal A after step 4 and B after step 5 (tolerance 4).

**Old-bug signature:** any cell still showing A after B was copied (a stale TMU cache, G37).

The time for each copy and draw is logged for information (G56).

### 7.3 `caps` → `"rf"`

**Pass:** `fs_565_565` = 1 (Red Faction's working pair).

The 32 bpp answers are recorded:
- `zmatch_a8_d16` is expected to be 1, which is the runtime's "match" that G10 is about;
- `fs_x8_a8` is to be measured.

They are reported as `"g10_open": true` until G10's capability is reported by the box.
