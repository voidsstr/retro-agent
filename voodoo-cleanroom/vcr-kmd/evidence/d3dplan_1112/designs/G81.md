## 1. Verdict

1. **Max Payne's edge was the pixel half, and nothing else.**
   - The 10-04 frame from `.124` (pre-fix build b63ea6a5) is the NVIDIA reference frame of the same menu at the same
     1280x960, **moved by (+0.50, +0.50) px**.
   - Over the text-free right half the match is 0.16 luma mean absolute difference (MAD) at that shift, against
     0.33-0.40 at ±0.125 px. Unshifted, the MAD is 4.7.
   - The best fit, interpolated, is (+0.498, +0.493) px.
   - One model, "our pixel = the reference half a pixel further on", predicts:
     - the last two columns row by row, with MAD under 0.1 luma;
     - the row means of the picture's first and last two rows to within 0.1.
2. **A correct driver must NOT make Max Payne's column 1279 equal column 1278.** On the NVIDIA reference, Max
   Payne's own last column is **exactly half** its neighbour in every row: 8.7 against 17.3 luma, median ratio 0.500.
   - The gap text quotes "column 1279 mean luma 4.2, against 12.4 in column 1278". Read naively, that invites a
     "the last column should match its neighbour" check, and that check would fail a correct HAL.
   - The pass target is the reference frame (section 9, V4).
3. **The texel half needs no offset, and the vendor's `textureCenter` is not a half texel.**
   - **Max Payne's fit.** The fit above includes the texel half: the backdrop is bilinear-filtered, and a texel-centre
     error would add a displacement that is not exactly half a pixel. The fit leaves no room for one beyond about
     0.01 px.
   - **G45's fit.** It reached the same answer on a different path: UT2004's DXT5 menu edge at 0.8 texel/pixel and
     16 bpp, right to about 0.05 texel.
   - **The vendor's value.** 3dfx adds `textureCenter[log2 size]` = 1/2^(slog+1) **after** scaling S by 256
     (`VH5/D6TRI2I.C:958-984`). That is **1/512 of a texel** on the wider side, and 2^aspect/512 on the narrower side
     (at most 1/64 at 8:1). It is a tie-break nudge for samples that fall exactly on a texel edge. Their 1998 log says
     "half a texel" (`VH5/D3RSTATE.C:379`). **Copied as a real half texel, it would re-create the `rgb565_decode1`
     failure on every 1:1 texture.**
4. **One vendor detail nobody had recorded.** 3dfx's later Win9x HAL moved the pixel offset to **0.5 + 1/32**
   (`W9X/D3RSTATE.C:3851-3855`, with the 0.5 line commented out). That value is compiled into the Win9x retail
   listing (`W9X/RETAIL/D3RSTATE.COD:8645`). There is no log entry giving the reason.
   - If the setup unit truncates x/y to 12.4 fixed point, as 86Box models it, +1/32 turns truncation into rounding.
   - If it rounds half-up, +1/32 breaks every exact pixel edge.
   - So it may only be tried after the `pixsnap` measurement (section 7.7). It is a candidate, not a plan.
5. **What is genuinely unproven on silicon:**
   - the fill rule exactly on a pixel centre: the 0.5 bias puts every integer D3D edge exactly on a Voodoo pixel
     centre;
   - the setup unit's float-to-12.4 conversion;
   - point sampling exactly on a texel edge. This is where "naive" 0..W quads land after the 11-08 fix, and where
     the vendor's nudge matters;
   - the sub-texel centre on TMU1, on TBIG levels and on DXT1 in a second stage.

   d3dprobe has no test for any of these. This design adds them.
6. **Decision.** Land the tests and the documentation. Change no driver behaviour. Each of three small corrections
   lands only if a measurement asks for it (F1-F3, section 5.2), default OFF behind `Diag\D3DCentre`. **Priority P2.**

### 2.2 The 11-08 before/after pairs (ours against ours)

| title | best fit "pre-fix = post-fix shifted by" | reading |
|---|---|---|
| Red Faction 60 s | (+0.5, +0.5) px, MAD 2.40 (neighbours 2.70-2.79) | bilinear menu art: the fix moved the image exactly half a pixel |
| Hidden & Dangerous 60 s | (+0.5, +0.5) px, MAD 4.74 (a shallow minimum: live 3D backdrop) | the same |
| Thief II 60 s (NewDark, D3D9) | **(+1.0, +1.0) px**; `pre(x, y) == post(x+1, y+1)` exactly for **89.6 %** of pixels (`pre == post`: 54.7 %) | point-sampled 1:1 UI: pre-fix every pixel showed texel (x+1, y+1). That is `rgb565_decode1`'s 1024/1024 failure, in a game |

Four of the five G81 titles (Red Faction, Thief II, UT2003, UT2004) lost their last column and/or row pre-fix. That
loss is the signature of **D3D-correct full-screen quads**, drawn from -0.5 to W-0.5:
- pre-fix, the right edge at W-0.5 fell exactly on the Voodoo centre of pixel W-1, and was excluded;
- a "naive" 0..W quad would have covered that column pre-fix.

So those four draw the D3D way, and the fixed build is right for them: none of them sends a pixel or texel sample
onto an exact edge.

**Max Payne is the exception.**
- Its column 1279 and rows 108/849 were *drawn* pre-fix: each reads the reference half a pixel on, row by row (§2.1).
- So its backdrop's right edge lies at or beyond x = 1280, as a naive 0..W quad's would (inferred; the geometry was
  not read from the game).
- If the left edge is at x = 0, the 0.5 bias now puts it exactly on pixel 0's centre. Max Payne's column 0 after the
  fix is then a silicon reading of the left-edge tie rule (V4 (d)).

### 2.3 The first column and row after the fix

In every `S08F` frame, column 0 matches column 1 and row 0 matches row 1 (Appendix A, `edges.py`):

| title | col 0 / col 1 | row 0 / row 1 |
|---|---|---|
| Red Faction | 144.7 / 145.2 | 89.1 / 89.9 |
| Hidden & Dangerous | 78.4 / 78.3 | 143.8 / 143.5 |
| Shogo | 15.3 / 15.3 | 15.5 / 17.1 |

- **No title lost a first column or row to the bias.** A lost one reads near 0 against its neighbour.
- **Caveat: this says little about the tie rule.** A -0.5 quad's edges land on Voodoo pixel *boundaries* after the

  - Four of the five G81 titles are not naive (§2.2).
  - Which of the other `S08F` titles are naive is not known.
  - The tie rule is unproven (§4, Q1). Max Payne's column 0 after the fix is the one game reading in reach (V4 (d)).

### 2.4 Silicon facts already on file

- **Point sampling at 1:1** (D3D-correct geometry, texel centres) is exact.
  - `rgb565_decode1`, `dxt1_decode1` and `dxt5_decode1` are 0 of 1024 wrong, and so is `dxt5_big_c@992,480` (a
    1024x512 TBIG DXT5, far corner).
  - Source: `../onbox/d3dprobe_textures_b_1024x768x32.txt` (11-12, 1024x768x32, build 95678704).
- **Magnified bilinear, DXT5 alpha, 16 bpp** (G45 §2.4-2.5): UT2004's menu edge matches the D3D model, and the
  "TMU without the half-texel subtraction" model is rejected.
  - The residual is about +0.045 texel at 0.8 texel/pixel. That is about the size of a 4-bit bilinear-weight
    quantisation (1/16 = 0.0625) (inferred).

## 3. The conventions, side by side

### 3.1 Ours (`KMD/display/vcrdd_3d.c`)

| what | code | value |
|---|---|---|
| pixel centre | `VcrDd3dDrawInit` `:295-307`; `vertex()` `:190-191` | `sVx = x + xy_bias`, `sVy = y + xy_bias`, `xy_bias = 0.5f` (76d36e7; pinned by `test_vertices_get_the_half_pixel_centre_offset`, `WT/tests/python/test_vcr_kmd_d3d.py:735-743`) |
| S/T scale | `VcrDd3dTexScale(1)` `:273-285` | the wider side spans 256, the narrower one 256·h/w. TBIG keeps 256 too (`KMD/include/vcr_texlod.h` header comment, after h5 Glide `grTexSource`) |
| texel centre | `vertex()` `:213-214` (TMU0), `:219-220` (TMU1) | `S/W = u · s_scale · oow`, **no additive term** |
| stage to TMU | `compute_regs` (`KMD/display/vcrdd_d3d.c:947-966`), `prepare` (`:1339-1350`) | one stage: TMU0. Two stages: **TMU1 samples D3D stage 0 and TMU0 samples stage 1**, each with its own size and texcoord set |

### 3.2 3dfx's W2K/XP HAL (vendor-25, vendor-12)

- **Pixel.** `pixelOffset = 0.5` when `PIXELCENTER` (default 1, `VH5/D3INIT.C:1911-1914`) is set
  (`VH5/D3RSTATE.C:3832-3835`). It is added to every vertex (`VH5/D6TRI2I.C:1131`, `VH5/D6STRIPI.C:1168`). Points
  are ±0.5 quads plus the offset (`VH5/D6POINT.C:259-365`).
- **Texel.**
  - `textureCenter[12]` = {1/2, 1/4, ... 1/4096} is indexed by log2 of each side (`VH5/D3TXTR.C:804-808`,
    `:2209-2218`).
  - It is added **after** the scale: `s = (u · scaleS + centerS) · w` (`VH5/D6TRI2I.C:958-984`, `:1034-1056`), with
    `scaleS` = `MAX_TEXTURE_SIZE_U` = 256 on the wider side (`VH5/D3TXTR.C:1846-1908`; `VH5/D3GLOBAL.H:925`).
  - One texel is 256/W S-units. So the offset is:

    | texture | wider side | narrower side | a literal half texel would be |
    |---|---|---|---|
    | 256x256, 64x64, 2048x2048 | 1/512 texel | 1/512 texel | 0.5 texel (0.5 S-units at 256, 2 at 64, 0.0625 at 2048) |
    | 256x64 | 1/512 texel | **4/512** texel | |
    | 512x64 (8:1) | 1/512 texel | **8/512 = 1/64** texel | |

  - The revision log reads "Added 0.5 to every vertex x,y and half a texel to s,t" (`VH5/D3RSTATE.C:379`, 1998).
    1/(2W) is half a texel in *normalised* u. Added after the ×256, it is a 1/512-texel nudge. Whether that was
    meant or an accident, the driver 3dfx shipped samples at +1/512 texel, and a nudge that small only decides
    samples that land exactly on a texel edge.

### 3.3 3dfx's later Win9x HAL: `pixelOffset = 0.5 + 1/32`

`W9X/D3RSTATE.C:3851-3855`:
```c
  if( _D3( pixelCenter ) )
//    pRc->sst.pixelOffset = 0.5f;
    pRc->sst.pixelOffset = 0.5f + 1/32.0f;
```
- It is in the retail compiler listing (`W9X/RETAIL/D3RSTATE.COD:8645`), so it shipped. Nothing in the log explains
  it.
- On the 1/16-pixel vertex grid, +1/32 is half a subpixel step. Run on paper (Appendix B), for an edge at
  `40 + j/64`:

| setup-unit conversion | bias 0.5 | bias 0.5 + 1/32 |
|---|---|---|
| exact (ideal) | transitions (1, 1) = D3D | (-1, -1): **exact edges broken** |
| truncation to 1/16 (86Box's model: `(int32_t)(sVx * 16.0f)`, `86B/voodoo_setup.c:154-159`) | (4, 4); exact edges right | **(2, 2)**; exact edges right: effectively rounding |
| round half up | (2, 2); exact edges right | (0, 0): **pixel 40 lost, pixel 60 gained at j = 0** |
| round half even | (3, 3); exact edges right | (1, 1) = D3D |

  "Transitions" are `pixsnap`'s two numbers (§7.7), and D3D's rule gives (1, 1).
- So +1/32 is good on a truncating chip and on a half-even one, and destructive on a round-half-up chip. **Only the
  silicon can say which it is.**

### 3.4 Other references on the same chip, and the emulator

- **MesaFX** (`MFX/fxtris.c:52-61`): `TRI_X_OFFSET`/`TRI_Y_OFFSET` = 0.0, "to ensure precise rasterization.
  Otherwise, we'll fail a bunch of conformance tests".
  - OpenGL's pixel centres are at +0.5, so the Voodoo samples at +0.5, and D3D needs exactly our 0.5.
  - S/T = u · 256 with no texel term (`MFX/fxddtex.c:676-740`, `MFX/fxvbtmp.h:208-212`). OpenGL and D3D9 share the
    texel convention (centres at (i + 0.5)/W), so ours is the convention our own ICD already renders conformantly
    with.
- **86Box** (inferred model):
  - the setup unit **truncates** to 12.4 (`86B/voodoo_setup.c:154-159`);
  - coverage is D3D's top-left rule on the 1/16 grid: rows by `(y + 7) >> 4` (`86B/voodoo_render.c:1531-1532`),
    columns by `(x + 0x7000) >> 16` with the right edge pulled in one pixel (`:846-852`);
  - bilinear subtracts half a texel (`tex_s -= 1 << (3 + tex_lod)`, `:315-320`), so texel centres sit at
    half-integers;
  - point sampling truncates S with no offset (`:366-369`).

  Silicon may differ. That is what §7 measures.

## 5. Fixes

### 5.1 Default: none

- No caps change, no register change, no change to the DP2 walker, the default 16 bpp path, the BigTex path, Glide
  or OpenGL coexistence, SLI or the flip path.
- **The rule to write down instead:** do not add a texel-centre offset, and do not copy `textureCenter` as a half
  texel. Do not copy the Win9x `0.5 + 1/32` without §7.7's measurement. Do not "fix" Max Payne's or UT2004's darker
  last column or row; both reference GPUs draw them (§2.1, G45).

### 5.2 Conditional corrections (only on measured evidence; none is expected)

**One switch for all three: `HKLM\SYSTEM\CurrentControlSet\Services\vcrmp\Diag\D3DCentre`**, a DWORD read at boot,
absent = 0 = today.

- It is read where `D3DBigTex` is: `x->d3dcentre = VcrDiagGet(L"D3DCentre", 0)` (`KMD/miniport/vcrmp.c:244`
  pattern).
- It is passed to the display driver as a new `vcr_info` field, or as `VCR_INFO_F_*` bits. 0x8000 and up are free
  at the time of writing (`KMD/include/vcr_ioctl.h:109-143`); the integrator allocates them alongside G16's
  `D3DFeat`.
- `vcrdd_2d.c` copies it into `pd->d3d_centre` beside `pd->tex_big` (`KMD/display/vcrdd_2d.c:453-469`), and logs
  event 513 with the next free `what` when it is armed.

| bit | name | what changes | condition to arm | proof |
|---|---|---|---|---|
| 0 | **F1** texel tie-break | `VcrDd3dTexScale`/`VcrDd3dTexScale1` also set `d->s_nudge = 0.5f / w`, `d->t_nudge = 0.5f / h` (S/T-units: exactly the vendor's `textureCenter[log2 size]`). `vertex()` writes `(uv[0] * d->s_scale + d->s_nudge) * oow` **only when the nudge is non-zero**; otherwise the existing expression, so the register values are bit-identical when off | Q3 finds texels picked at i−1 | `texc_naive` point: 0 at i−1. `texc1`, `texc_phase*` and every `*_decode1` unchanged (\|Δδ\| ≤ 1/256 texel) |
| 1 | **F2** snap rounding | after `VcrDd3dDrawInit` (`KMD/display/vcrdd_d3d.c:1862`): `if (pd->d3d_centre & 2) w.d.xy_bias += 1.0f / 32.0f;` | Q2 = (4,4) truncation **and** a title shows an attributable artefact (none known). **Forbidden** if Q2 = (2,2) | `pixedge` all D3D. `pixsnap` (2,2) with j = 0 still D3D. `texc1` within tolerance |
| 2 | **F3** measured residual | per TMU, a constant `d->s_off` = −δ · s_scale / w added like F1's nudge (δ from §7.4 on silicon) | Q4/Q5 measures \|δ\| > 1/16 texel on a path | that path's `texc_phase` \|δ\| ≤ 1/64; the others unchanged |

Each lands with its regression test (§8.3), one bit per clean boot, and stays default OFF until a supervised run
proves it. **F2 alone touches every triangle's coverage.** F1 and F3 touch only texture coordinates.

## 6. Gating

- **The default deliverables change no driver behaviour.** They are d3dprobe tests, a reference header, host tests
  and documentation, so they need no Diag switch and no reboot, and are safe to land at once.
  - The new d3dprobe tests are **explicit-only**, as the BigTex tests are: never in the default `--tests` list until
    a supervised `.124` pass and a reference-GPU pass (V1-V3).
  - After those passes, `texc1` and `pixedge` join the default list. They are cheap and guard the 11-08 fix on every
    run.
- **F1-F3** are default OFF behind `Diag\D3DCentre`. Off, the path is unchanged write for write (§5.2). One bit per
  clean boot, supervised. Activation is checked before any reboot, and `safe-reboot.py` is used.
- **Not safe to land default-on without silicon:** F2 in particular. Its effect depends on an unmeasured rounding
  mode, and the wrong guess removes a column or row from every naive full-screen quad.

## 7. d3dprobe tests (`KMD/tools/d3dprobe.c`, explicit-only)

**Shared setup.**
- All of these fit d3dprobe's 256x256 readback window (G74 is not needed).
- Each clears to black. Z, blending, alpha test and fog are off, and `D3DRS_DITHERENABLE` is FALSE.
- Stage 0's COLOROP/ALPHAOP are SELECTARG1(TEXTURE) unless stated otherwise, with MIP NONE.
- Textures are MANAGED, filled by Lock, and R5G6B5 unless stated otherwise (offered on every path, the default path
  included).
- The expected values are D3D9's: pixel centres at integers; texel coordinate c = u·W − 0.5; bilinear between
  floor(c) and floor(c)+1 with weight frac(c); point = texel floor(u·W).
- **Shared reference code.** These go in G74's `KMD/include/vcr_d3dref.h` (`vcr_ref_bilinear`, `vcr_ref_covers`).
  G81 adds `vcr_ref_snap` and `vcr_ref_ramp_area`. If G74 has not landed, G81 creates the header with only these.
- **Results.** Every result goes into the RESULT JSON. The per-texel tests use `test_dxt_decode`'s shape
  (`rgb_wrong`, …, `ok`); the measurements add a `note`.
- **Overlaps, kept apart on purpose:**
  - G74's `bilinear` is a three-point model classifier;
  - G08's `bilinear` is the DX5 legacy filter states (**the two share a name, which the integrator must resolve**);
  - G45's `edgeblend` is UT2004's composite.

  G81's tests measure the residual on every TMU path and gate the exact-edge cases. None duplicates those three.

### 7.1 `texc1`: bilinear at 1:1, D3D-correct geometry

- **Draws:** a 32x32 one-texel checkerboard (black/white), CLAMP, MAG/MIN LINEAR, at `(Q0 − 0.5) .. (Q0 + 32 − 0.5)`
  with u, v 0 → 1. This is `*_decode1`'s geometry.
- **Reference:** pixel (Q0+i, Q0+j) = texel (i, j) **exactly**: black or white.
- **Pass:** all 1024 pixels within ±24 per channel. That allows one 1/16 bilinear step plus 565 rounding. The RESULT
  carries `max_dev` and the mean of the should-be-black pixels (the bleed).
- **Old values:**
  - pre-11-08 build (`xy_bias` 0): **1023/1024 wrong**, mid-grey; only (31,31) is exact, through CLAMP;
  - a literal half texel added to S/T: 1024/1024 grey;
  - a TMU without the half-texel subtraction: grey.

### 7.2 `texc_naive`: the same at 1:1 with **naive** geometry (Q0 .. Q0+32, no −0.5)

- **Point part.** `rgb565_decode1`'s random 565 texture. Each pixel is classified as texel i (refrast's
  floor(u·W) = i), texel i−1, or other, separately in x and y.
  - **Pass (the gate):** `other` = 0.
  - **Note:** the counts {i, i−1}. This is Q3, the case that decides F1.
  - Pre-11-08 build: every pixel sampled a texel centre and read texel i: "0 at i−1", accidentally.
- **Bilinear part.** `texc1`'s checkerboard.
  - **Reference:** c = i − 0.5 in x and j − 0.5 in y, so every pixel blends two checker texels in at least one axis
    and reads 128 ± 24. The exception is (0,0), which is texel (0,0) through CLAMP in both axes.
  - **Pass:** all 1023 other pixels grey.
  - This is the mirror of `texc1`: the pre-11-08 build drew this crisp. **A naive title's UI that looked sharper
    before 11-08 and softer after is now drawn as every D3D9 GPU draws it.**

### 7.3 Why both: the two tests pin the convention from both sides

`texc1` alone cannot tell "right" from a compensating pair of errors. `texc1` exact **and** `texc_naive` grey can only
be the D3D convention.

### 7.4 `texc_phase`, `texc_phase_t`: the sub-texel centre, measured

- **Draws:** a 2x2 texture, column 0 black and column 1 white (`_t`: rows), CLAMP, LINEAR.
  - It is magnified to 64 px a texel: the quad runs x `63.5 .. 191.5`, u 0 → 1.
  - **16 one-row strips** (rows 40-55). Strip i has its u range offset by **i/256 texel** (δu = i/512), which dithers
    out a 4-bit weight quantiser.
- **Reference:** strip i's area A_i = Σ v/255 over k = 16..111 (k = pixel − 64) is **48 + i/4** (ramp from k = 32 to
  95).
- **Estimate:** δ = mean_i (A_i − 48 − i/4) / 64 texels.
  - Positive means we sample further along +S. Appendix B checks it: δ = 0 gives 48, 0.045 gives 50.9, 0.5 gives 78.
  - Also recorded: `levels` (distinct values in strip 0's ramp: 16-17 for 4-bit weights) and `monotonic`.
- **Pass:** |δ| ≤ 1/16 texel. Expected about 0, or up to −1/32 if the weights truncate (that shows in `levels` and in
  the step alignment).
- **What it can and cannot see:**
  - a literal half texel, or no TMU subtraction, reads δ ≈ 0.47-0.5 and fails;
  - the pre-11-08 pixel half reads δ = 0.008 and passes. At 64 px a texel, half a pixel is invisible in texel units;
    `texc1`/`pixedge` catch that one.

### 7.7 `pixsnap`: the 12.4 conversion (Q2), a measurement

## 10. Risk

- **To proven paths: none from the default deliverables.**
  - User-mode test code runs only when named.
  - Host tests and documentation.
  - V1 switches no mode. V2 adds one paced switch pair on the 1998 CRT. V4 adds no launch to G04's session.
- **Max Payne (G04).** V4 rides on a session G04 already runs attended. Using GDI capture only removes the one
  action correlated with the 10-04 freeze (G04 §0.3).
- **Conditional fixes:**
  - **F2 is the dangerous one.** On a round-half-up chip it drops the first column and row of every naive quad.
    Hence the §6 rule: never before `pixsnap`, and never default-on.
  - F1/F3 move texture coordinates by at most 1/64 texel (F1) or by a measured δ (F3). Visible only at exact texel
    edges, which is their purpose.
- **Glide/OpenGL coexistence.**
  - Unchanged.
  - One interaction: a leftover Glide **AA** state (`aaCtrl` jitter offsets, README `SliOffAaCtrl` row; G03) would
    move D3D's sample points by a sub-pixel amount. `pixsnap` would read as "a constant offset", which is the
    diagnosis.
  - The user runs without AA, so this is unlikely.
- **SLI (G51) and two-pixels-per-clock (G50).** When either lands, re-run `pixedge`/`pixsnap`/`texc1`. Interleaved
  bands with a per-chip y error, or 2PPC column pairing, would show as edge failures on alternate rows or columns.
  These tests are the cheap guard.
- **The vertex-path rewrites ahead** (G16, G25, G47, G48, G49, G58 all restructure `vertex()`). §8.1 test 5 and
  `texc1`/`pixedge` are what keep the 11-08 fix from silently regressing. That is the main value of landing this
  item.
