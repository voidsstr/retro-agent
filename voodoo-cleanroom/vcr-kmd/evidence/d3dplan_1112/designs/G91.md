## 0. Verdict

- **The hardware half of the gap is right.**
  - `fogMode[11:8]` gives ADD, SUBTRACT and REVSUBTRACT, separately for RGB and alpha.
  - `renderMode[20:17]` masks R, G, B and A at 32 bpp.
  - `fbzMode[9]` masks all of RGB at every depth.
  - MIN and MAX do not exist.
  - hal-35's "BLENDOP and separate alpha blending are hardware limits" is wrong for everything except MIN/MAX.
- **The DDI half is settled offline, and the answer is no.** I read it from the XP SP3 runtime binaries:
  - Both runtimes **copy** a DX7 driver's misc caps into D3DCAPS8/9. They clear only MASKPLANES and
    CONFORMANT. So `D3DPMISCCAPS_COLORWRITEENABLE` (0x80) and `D3DPMISCCAPS_BLENDOP` (0x800) set in our DX7
    caps **would be reported** to D3D8 and D3D9 applications.
  - Both runtimes **never send** `D3DRS_COLORWRITEENABLE` (168) or `D3DRS_BLENDOP` (171) to a DX6 or DX7 DDI
    driver. `CD3DHal::SetRenderState` stores the value and calls the DDI only when the state number is below
    `m_dwMaxRenderState`. For the DX6 and DX7 DDI classes that limit is **0x88 = 136**: render states 0 to
    WRAP7 (135).
  - The D3D9 separate-alpha states (206 to 209) and `COLORWRITEENABLE1-3` (190 to 192) are dropped in the
    same way.
  - Only a DX8-level DDI gets them. d3d8 forwards states below 172 (or 256 with a flag), d3d9 below 256.
- **So the gap's proposed experiment would give a false positive.** "Set the misc-cap bits in a test build and
  read them back with d3dprobe caps" would show `PrimitiveMiscCaps 0x8f2`, and nothing would work. It must not
  be used to decide.
- **Consequence: G91 cannot be fixed through the DX7 DDI.** The caps must stay `0x72`. The only route is G94
  (a DX8-level DDI). This design specifies the register mapping for that day (§6) so G94 does not re-derive it.
- **What lands now is small (effort S):**
  - a host test that pins the caps and rejects `0x8f2`;
  - one diagnostic line in the context summary: the highest render-state number the HAL ever received. It
    turns §3 into a silicon measurement at the next deploy, with no reboot of its own;
  - two d3dprobe tests, `blendop` and `cwmask`. Today they report `dropped`. They become real pass/fail checks
    the day a DDI that receives the states arrives;
  - corrections to the reports and the README.
- **Halo is the staged title this matters to.**
  - `halo.exe` calls `SetRenderState(COLORWRITEENABLE)` at 63 sites and `SetRenderState(BLENDOP)` at 54 sites.
    It never tests the caps.
  - Its "subtract" framebuffer blend and its "darken" screen flash are REVSUBTRACT. On `.124` today they draw
    as ADD: they brighten instead of darken.
  - Its depth-only (mask 0) and alpha-only (mask 8) passes write colour there, if they run on `.124`'s
    fixed-function path. One alpha-only pass is gated on pixel shader 1.1 (G28). For the rest it is not known.
  - Halo's own `MinMaxBlendOpIsBroken` flag changes only its MIN/MAX uses (§11.4).
- **Priority P3 for G91 as filed.** In this DDI there is nothing to implement beyond the guard. The Halo
  evidence is an input to G94's priority and to G67's gameplay check.

## 2. Hardware facts (confirmed; nothing here changes them)

| function | field | values | source |
|---|---|---|---|
| RGB blend op | `fogMode[8]` order, `[9]` subtract | 00: `S·a + D·b`; bit 9: `S·a − D·b`; bits 8+9: `D·b − S·a`; bit 8 alone: `D·b + S·a` (= add) | SPEC §8.22 L2853-2854, §8.23.2 L2924-2931; `VINC/H3DEFS.H:851-852` (`VH5/H3DEFS.H:836-837`) |
| alpha blend op | `fogMode[10]`, `[11]` | the same four on the alpha channel | L2855-2856, L2946 |
| result range | — | negative results become 0 and overflow becomes 255, per channel | `CSIM/FBI.C:1410-1440` (3dfx's chip model). The SPEC text says nothing; §8 quad 3 checks it on silicon. |
| MIN / MAX | none | no field compares S with D | §8.22 and §8.23.2 list only add/subtract; the revision log adds only "reversal of operations and subtraction" (L6562) |
| RGB factors | `alphaMode[15:8]` | all 13 D3D factors, SAMECOLOR included (G29) | L2955-2972 |
| alpha factors | `alphaMode[23:16]` | 32 bpp: ZERO, SRCA, DSTA, ONE, 1−SRCA, 1−DSTA. 15/16 bpp: ZERO/ONE, and only with the aux buffer as alpha. | L2976-2994 |
| per-channel write | `renderMode[17]` R, `[18]` G, `[19]` B, `[20]` A | "Only used when 32BPP rendering is enabled". Each needs `fbzMode[9]` set. | L3295-3298, L3310, L3312; `VINC/H3DEFS.H:139-142` |
| RGB write | `fbzMode[9]` | every depth. At 15 bpp it also gates the 1-bit alpha. At 32 bpp, with the bit clear, no plane is written. | L3211, L3256 |
| register cost | `fogMode`, `alphaMode`: not sync. `fbzMode`, `renderMode`: sync. | | the register table, L2304-2306, L2333 |

- **What follows for a target.**
  - SUBTRACT and REVSUBTRACT are exact on RGB at every depth.
  - The alpha op matters only where alpha is stored (32 bpp).
  - On an R5G6B5 target there is no alpha. The masks 0x0, 0x7, 0x8 and 0xF are therefore exact through
    `fbzMode[9]` alone. Only partial RGB masks (1-6, 9-14) cannot be done at 16 bpp.
  - On an X8R8G8B8 target the masks 0x7 and 0xF are the same, and so are 0x8 and 0x0.
- **Glide on the same registers.**
  - `grAlphaBlendFunctionExt` piggybacks the op bits on `grFogMode` (`GL5/gglide.c:3981-4020`): SUB → bit 9,
    REVSUB → bits 8+9.
  - `grColorMaskExt` writes `renderMode[20:17]` (`GL5/distate.c:2366-2384`).
  - `_grRenderMode` rewrites `renderMode` from Glide's own shadow at every open (`GL5/gsst.c:4166-4223`).
- **3dfx's own D3D never exposed either feature.**
  - Both caps are commented out in its DX8 caps builder (`VH5/D3INIT.C:3426`, `:3430`; `W9X/D3INIT.C:3516`,
    `:3520`).
  - Its only per-channel use is a DEBUG toggle (`VH5/D6DP2.C:6177-6205`).
  - No DP2 in the H5 tree handles `D3DRS_BLENDOP` or `COLORWRITEENABLE` (case-insensitive grep of the tree).

## 3. What the XP SP3 runtimes do with the two states (the decisive evidence)

### 3.1 The caps pass through

- **d3d8.** `0x6d9aeaf0` builds D3DCAPS8 from the DX7 global driver data:
  - `0x6d9aeb01: mov 0x6c(%ecx),%edx` / `0x6d9aeb04: mov %edx,0x20(%eax)` copies
    `hwCaps.dpcTriCaps.dwMiscCaps` (offset 4 + 0x68) into `PrimitiveMiscCaps` (0x20).
  - The fix-up after it is `0x6d9af0b7: and $0xfffffff6,%eax`. It clears only MASKPLANES (0x1) and
    CONFORMANT (0x8).
  - The same block clears SUBPIXEL, SUBPIXELX, STIPPLE and the AA bits from RasterCaps
    (`0x6d9af0c6: and $0xfff7f19f`). That is the "dropped SUBPIXEL" `REP/runtime.md` §3 measured, which
    confirms this is the path our caps take.
  - `CAPS` reads `PrimitiveMiscCaps 00000072`, exactly our `prim_caps` value (`vcrdd_d3d.c:2017-2018`).
- **d3d9.** The same pattern: the copy at `0x4fdfb231`/`0x4fdfb234` (function `0x4fdfb220`), the mask
  `and $0xfffffff6` at `0x4fdfb822`. The later fix-up at `0x4fdfbaf4` adds bits and clears none of 0x80, 0x800
  or 0x20000.

So a test build with `D3DPMISCCAPS_COLORWRITEENABLE | D3DPMISCCAPS_BLENDOP` would read back `0x8f2` in both
runtimes.

### 3.2 The states never reach a DX6/DX7 DDI

- **d3d8, the API path.** `IDirect3DDevice8::SetRenderState` of the HAL device class (`CD3DHal`) is
  `0x6d9d2940`: slot 50 of its vtable at `0x6d9a82f8` (135 entries: the 97 interface methods, then internal
  virtuals).
  - It takes the device lock.
  - While a state block is being recorded, it records the state there (`0x6d9e5df0`), with a "below the
    maximum" flag.
  - Otherwise it calls the internal setter in slot 98, `0x6d9d4890` (`0x6d9d2a0e: call *0x188(%edx)`).

  That setter runs as follows:
  1. It compares the value with the stored one and stops if it is the same.
  2. It calls `0x6d9d35a0`. That helper has a jump table for states 9 to 167 only. Every state from 168 up
     is only stored in the array at `0x908(%esi)`, apart from the WRAP0-7 special case (`0x6d9d3d95`).
  3. It calls the DDI only when the state is below the device's maximum:
     ```
     6d9d499a: cmp  0x390(%esi),%edi     ; state >= m_dwMaxRenderState ?
     6d9d49a0: jge  6d9d49b5             ;   then the driver never hears of it
     6d9d49af: call *0xd4(%edx)          ; m_pDDI->SetRenderState(state, value)
     ```
- **Every other d3d8 caller has the same gate:**
  - the internal setter in slot 129, `0x6d9d49f0` (`0x6d9d4a14`);
  - the state-block apply loop (`0x6d9e70ff`), which matters because D3D8 emulates state blocks for this DDI
    (`REP/runtime.md` §0.8);
  - the helper `0x6d9da930` (`0x6d9da938`).
- **Where the maximum comes from.** At device init `0x6d9d8005: call *0x68(%eax)` asks the DDI object, and
  `0x6d9d800e` stores the answer at `0x390`.
  - The DX7 DDI class (vtable `0x6d9a91e8`; constructor `0x6d9e45b0` stores type 4) answers with
    `0x6d9e2110: b8 88 00 00 00 c3` (`mov $0x88,%eax; ret`). So does the DX6 class (vtable `0x6d9a8ff8`).
  - 0x88 = 136 = `D3DRENDERSTATE_CLIPPING`, the first T&L state (`DDK8/d3dtypes.h:1254-1257`). A non-T&L
    driver gets 0 to 135. `D3DRS_COLORWRITEENABLE` = 168 and `D3DRS_BLENDOP` = 171
    (`DDK8/d3d8types.h:392, 394`) stay in the runtime.
- **d3d9 does the same:**
  - its setters gate the DDI call (`call *0xe4`) with `cmp 0x209c(…),…; jge`. Checked at seven sites:
    `0x4fe678e6`, `0x4fe67965`, `0x4fe5784d`, `0x4fe66136`, `0x4fe6e16f`, `0x4fe6e1b4` and `0x4fe5921b`.
    A pure-device path like d3d8's (§3.4) is assumed and was not looked for;
  - `0x209c` is filled from the DDI at `0x4fe59266`;
  - the DX7 class (vtable `0x4fde8490`; constructor `0x4fe7b10a` stores type 4) answers `0x4fe79010: mov $0x88`;
  - the helper `0x4fe665a0` again has a jump table for 9 to 167 only (`cmp $0x9e` after `lea -0x9`), and its
    default only stores (`0x4fe66cf0`-`0x4fe66d54`).
- **Neither runtime special-cases these numbers.** No instruction in either `.text` compares a state with
  0xa8 or 0xab. Nothing translates them into PLANEMASK or anything else.

### 3.3 The DDI classes, side by side

| DDI class (type) | d3d8 vtable → max state | d3d9 vtable → max state | 168 / 171 reach the driver? |
|---|---|---|---|
| DX6 | `0x6d9a8ff8` → 0x88 | `0x4fde8280` → 0x88 | no |
| **DX7, no T&L (4): vcrdd today** | `0x6d9a91e8` → **0x88** | `0x4fde8490` → **0x88** | **no** |
| DX7 T&L (5) | `0x6d9a9310` → 0x99 | `0x4fde8600` → 0x99 | no |

| DX9 (9) | n/a | `0x4fde7bd0` → 0x100 | yes, incl. SEPARATEALPHABLEND* (206-209) |

**Cross-checks that the reading is right:**
- **DDI-only states the runtime does send.** `D3DRENDERSTATE_EVICTMANAGEDTEXTURES` (61) and `SCENECAPTURE` (62)
  are defined at `DDK8/d3dnthal.h:953-954`. Both are below 136, and d3d8 sends them unconditionally:
  `0x6d9db109 push $0x3d`, `0x6d9e16ab push $0x3e`.
- **A DDI-only state above the limit.** `D3DRS_DELETERTPATCH` (169, `d3dnthal.h:1171`) is sent only from a
  patch path (`0x6d9d7685`) (inferred: RT patches need a DX8 driver).
- **The caps.** Our `0x72` comes back unchanged, and our SUBPIXEL is dropped. Both match §3.1.

### 3.4 What is still inferred

- **`.124`'s own `system32` copies were not read.** That is a read-only md5 check, §10 step 1.
- **The DDI class vcrdd gets.** It is DX7 (type 4) because we report DRAWPRIMITIVES2EX without
  HWTRANSFORMANDLIGHT (`REP/runtime.md` §0.1). It makes no difference: DX6 and DX7 both answer 0x88.
- **Pure devices.** The other device vtable, at `0x6d9a88c8` (`CD3DBase`, inferred), has in slot 50 a
  `SetRenderState` (`0x6d9d9be0`) that calls the DDI with no gate. A pure device needs hardware vertex processing, which a HAL without HWTRANSFORMANDLIGHT never grants
  (inferred from the D3D8 rules). So every title on `.124` goes through the gated `CD3DHal`, which software
  vertex processing requires anyway.

## 4. Consequences, and the alternatives rejected

1. **No change to the HAL can make BLENDOP or COLORWRITEENABLE work for a D3D8/D3D9 application through this
   DDI.** DX5, DX6 and DX7 applications cannot ask for either: their render-state enumeration ends at 152 and
   has no such state.
2. **Setting the cap bits would make a lying driver.**
   - An application that tests them would pick a technique, and the HAL would silently draw it as ADD with
     full writes.
   - An application that does not test them, such as Halo (§11), gains nothing.
   - This is the project's "reported success and was believed" failure shape.
3. **Rejected: read the runtime's state array through DP2's `lpdwRStates`.**
   - The HAL already *writes* that array (`vcrdd_d3d.c:1398-1399`). The DDK calls it "a pointer to the
     internal render states array".
   - Even if it is the same array the runtime stores 168 and 171 in (not verified), the driver could only see
     the **last** value set before the flush.
   - `SetRenderState(BLENDOP)` makes no DP2 token and no flush, while one DP2 buffer carries many draws. Halo's
     pattern of set op, draw, reset op would then apply the reset value to the whole batch.
   - It would also mean a kernel driver reading user memory it does not own.
4. **Rejected: PLANEMASK (state 13).**
   - The runtimes never translate COLORWRITEENABLE into it.
   - d3d8 sends its own stored PLANEMASK with the other legacy states (the 87-state table at `0x6dab10d8`,
     sent by `0x6d9d2110`, includes 13).
   - No staged title is known to use it.
5. **The only route is a DX8-level DDI (G94).** §6 is written for that day.

## 5. Design: what lands in the DX7 lane now (effort S)

### 5.1 The caps stay `0x72`, and say why

There is no code change to the value. Add a comment in `prim_caps` (`vcrdd_d3d.c:2013-2018`), so the next reader
does not "fix" it:

```c
    /* NOT COLORWRITEENABLE (0x80) or BLENDOP (0x800), although the VSA-100
     * has per-channel write enables at 32 bpp and subtract / reverse-subtract
     * blending (fogMode[11:8]): XP SP3's d3d8/d3d9 copy these caps through to
     * applications but never pass D3DRS_COLORWRITEENABLE (168) or
     * D3DRS_BLENDOP (171) to a DX6/DX7-DDI driver - it receives render states
     * below 136 only (CD3DDDIDX7::GetMaxRenderState = 0x88, G91 design §3).
     * Advertised here they are a promise the HAL can never keep. They need a
     * DX8-level DDI (G94). Pinned by test_vcr_kmd_d3d.py. */
```

### 5.2 One diagnostic line: the highest render state received (default on, logging only)

- **`vcr_d3dctx`** gains `ULONG rs_max, rs_hi`: the highest state number received, and how many tokens carried
  a state of 136 or above.
- **`set_rs`** counts every token before its `st >= RS_MAX` return (`vcrdd_d3d.c:1396`):
  ```c
      if (st > c->rs_max) c->rs_max = st;
      if (st >= VCR_DX7_MAX_RS) c->rs_hi++;        /* 136: never, on XP SP3 (G91) */
  ```
- **`ctx_free`** logs one extra event, `VCR_EV_DD_D3D` 24. Code 24 is free: `KMD/display/` uses 1-23.
  The message is `"context %u states: highest %u, %u at or above 136"`. It is once per context, at teardown,
  and never on the drawing path.
- **What it does not change:** no register write, no cap, no allocation. If G76 (per-context counters) lands
  first, these become two fields of its block instead.
- **Why it is worth having:** it turns §3 into a silicon fact at the next deploy, and it will catch the day a
  different runtime or a DX8 DDI changes the answer.

### 5.3 Two d3dprobe tests that report "dropped" today

`blendop` and `cwmask` (§8). They go into `KMD/tools/d3dprobe.c`'s default list after `blend`.
- With the cap absent and no `--want`, each is **SKIPPED, never failed**. The JSON names its verdict
  (`honoured`, `dropped` or `wrong`). This follows the probe's existing rule for features the HAL does not offer.
- With no edit, they become real checks once a build arms the DX8-era feature (§7).

### 5.4 Documentation to correct

## 6. The fix G94 makes possible (specified now)

Everything in this section lands only with a DX8-level DDI. It sits behind `Diag\D3DFeat` bits, default OFF (§7).

### 6.1 `KMD/include/vcr_blendop.h` (new; integer only, Win32-free; the native test compiles it)

```c
#define VCR_BO_ADD          1u      /* D3DBLENDOP (DDK8/d3d8types.h:226-230) */
#define VCR_BO_SUBTRACT     2u
#define VCR_BO_REVSUBTRACT  3u
#define VCR_BO_MIN          4u
#define VCR_BO_MAX          5u
#define FM_RGB_BLEND_REVERSE (1u << 8)  /* SPEC §8.22: order D*b op S*a */
#define FM_RGB_BLEND_SUB     (1u << 9)  /* op = subtract */
#define FM_A_BLEND_REVERSE   (1u << 10)
#define FM_A_BLEND_SUB       (1u << 11)

typedef struct vcr_bo {
    unsigned fog;                   /* fogMode[11:8] */
    unsigned force;                 /* 1: the factors below replace the application's */
    unsigned src, dst, asrc, adst;  /* alphaMode factor codes (BF_*), when force */
    unsigned inexact;               /* MIN/MAX: an approximation */
} vcr_bo;

static __inline vcr_bo vcr_bo_map(unsigned op)
{
    vcr_bo r = { 0, 0, 0, 0, 0, 0, 0 };
    switch (op) {
    case VCR_BO_SUBTRACT:    r.fog = FM_RGB_BLEND_SUB | FM_A_BLEND_SUB; break;          /* 0xa00 */
    case VCR_BO_REVSUBTRACT: r.fog = FM_RGB_BLEND_REVERSE | FM_RGB_BLEND_SUB |
                                     FM_A_BLEND_REVERSE | FM_A_BLEND_SUB; break;        /* 0xf00 */
    case VCR_BO_MIN:         /* S*D ("multiply"): <= min, equal when S or D is 0 or 1 */
        r.force = 1; r.src = BF_COLOR; r.dst = BF_ZERO; r.asrc = BF_DSTALPHA; r.adst = BF_ZERO;
        r.inexact = 1; break;
    case VCR_BO_MAX:         /* S + D*(1-S) ("screen"): >= max, equal when S or D is 0 or 1 */
        r.force = 1; r.src = BF_ONE; r.dst = BF_INVCOLOR; r.asrc = BF_ONE; r.adst = BF_INVSRCALPHA;
        r.inexact = 1; break;
    default: break;          /* ADD, and anything unknown: D3D's default */
    }
    return r;
}
```

- **The alpha op follows the RGB op.** D3D8 has one op for all four channels. D3D9's `BLENDOPALPHA` under
  `SEPARATEALPHABLENDENABLE` sets `[11:10]` alone, together with G28's alpha factors.
- **The MIN/MAX degrades use factors the chip has:**
  - RGB factor 2 as source is the destination colour; factor 6 as destination is `1 − source colour` (SPEC
    L2966-2967).
  - Alpha factors 3 (DSTA) and 5 (1−SRCA) are in the 32 bpp alpha table (L2985).
  - Both degrades are exact when either operand is 0 or 1 in a channel. Their largest error is
    `min·(1 − max) ≤ 1/4`, at S = D = ½.

```c
/* the colour write mask (D3DRS_COLORWRITEENABLE: R=1 G=2 B=4 A=8 - the same
 * order as renderMode[17..20]) on a target of fmt (VCR_RT_16/32) that does or
 * does not store alpha */
typedef struct vcr_cw { unsigned rgbwrite, rm_wmask, inexact; } vcr_cw;
static __inline vcr_cw vcr_cw_map(unsigned mask, unsigned fmt, unsigned rt_alpha)
{
    vcr_cw r = { 1, 0, 0 };
    unsigned have = rt_alpha ? 0xfu : 0x7u, m = mask & have;
    if (m == 0)        { r.rgbwrite = 0; return r; }   /* fbzMode[9] off: exact everywhere */
    if (m == have)     return r;                        /* everything: the target's renderMode */
    if (fmt == VCR_RT_32) { r.rm_wmask = m << 17; return r; }
    r.inexact = 1;     return r;                        /* 16 bpp: RGB is all or nothing */
}
```

- **Halo's masks cost no extra register write.** On X8R8G8B8 and R5G6B5, 0xF and 0x7 keep the default, and
  0x8 and 0x0 clear `fbzMode[9]`, which is written at every flush already.
- **Only partial masks at 32 bpp write `renderMode`.** That register is a sync register.

### 6.2 HAL changes (every one behind its bit; with the bits off the register stream is today's, byte for byte)

| where | change |
|---|---|
| `ctx_defaults` (`vcrdd_d3d.c:1126-1137`) | `rs[168] = 0xF`, `rs[171] = D3DBLENDOP_ADD`. **Today both are 0 from the memset.** Under the feature, a mask of 0 would draw nothing until the application first set it. |
| `compute_regs` (`:995-999`, `:1002-1003`) | With ALPHABLENDENABLE, `r->fogMode \|= bo.fog`, and `bo.force` replaces the four factors. Then the mask: `rgbwrite == 0` clears `FZ_RGBWRITE`, and `rm_wmask != 0` sets `r->renderMode` to the composed value (otherwise 0, meaning "the target's"). |
| `VcrDd3dState` (`vcrdd_3d.c:74-81`) | Writes `renderMode` only when the composed value differs from what is live (`pd->rm_live` shadow, set by the target sequence too). `fogMode` is already written whole at every flush (`:81`). |
| `VcrDd3dClear` (`vcrdd_3d.c:136-176`) | D3D9's documentation of the state says it "does not affect the clear operation" (inferred: D3D8 the same). | `vcrdd_3d.h` `vcr3d_regs` | gains `renderMode` (0 = the target's). |
| counters (G76) | count draws with `inexact` (partial masks at 16 bpp, MIN/MAX), logged once per context |

### 6.3 Caps policy

- **COLORWRITEENABLE (0x80): advertise it**, with its own bit, after the `cwmask` probe passes.
  - It is exact for every mask on a 32 bpp target.
  - On R5G6B5 it is exact for 0x0, 0x7, 0x8 and 0xF. Partial RGB masks there are drawn as full writes and
    counted.
- **BLENDOP (0x800): honour it, do not advertise it.**
  - D3D8/9 have one cap for all five ops, and MIN/MAX here are approximations.
  - The gate is the DDI class, not the cap (§3.2), so the state reaches the driver either way (inferred for
    the DX8 class: the same `CD3DHal` path).
  - Halo, which never tests the cap, still gets exact SUBTRACT and REVSUBTRACT and close MIN/MAX.
  - Revisit this if a title is found that tests the cap and has no fallback.
- **D3D9 SEPARATEALPHABLEND (0x20000)** is G28's, on top of this mapping.

### 6.4 Traps (each pinned by a test, §9.2)

- **The context defaults** above (168 = 0xF, 171 = ADD).
- **Clear ignores the mask.**
- **`renderMode` is a sync register.** Shadow it. Halo's masks never need it.
- **One `renderMode` composer, shared with G50 and G57.** G50 puts the 2 ppc band in `renderMode[24:22]`
  (G50 design, `vcr_ppc_rendermode`). G57 puts the guard band in `[21]`. A mask write must keep both.
  `fogMode[19:12]` (dither rotation, G30) shares a register with the op bits: compose, never assign.
- **SLI (G51).** `fogMode` and `renderMode` are per-chip FBI registers. Write them under the same chip mask as
  the rest of the state.
- **15 bpp targets (G93).** `fbzMode[9]` gates RGB and the 1-bit alpha together (L3256). Only 0x0 and 0xF are
  exact on A1R5G5B5, and 0x0, 0x7 and 0xF on X1R5G5B5.

## 11. Halo: what it asks for, what `.124` draws today, and the investigation

### 11.1 What `halo.exe` asks for (static; `IDirect3DDevice9::SetRenderState` is vtable `0xe4`, device at `0x71d174`)

- **COLORWRITEENABLE**, 63 sites: 0xF ×9, **0x7 ×43** (RGB only, keeping destination alpha), **0x8 ×5** (alpha
  only), **0x0 ×4** (no colour), from a register ×2.
- **BLENDOP**, 54 sites: ADD ×47, **REVSUBTRACT ×1**, **MIN ×2**, **MAX ×2**, from a register ×2.
  - One register site is the framebuffer-blend setter `0x5185d0`. It reads three tables, at `0x65dfbc` (SRC),
    `0x65dfe0` (DEST) and `0x65e004` (OP):

    | index | SRC | DEST | OP | Halo's name (inferred: matches its shader enum order) |
    |---|---|---|---|---|
    | 0 | SRCALPHA | INVSRCALPHA | ADD | alpha blend |
    | 1 | DESTCOLOR | ZERO | ADD | multiply |
    | 2 | DESTCOLOR | SRCCOLOR | ADD | double multiply |
    | 3 | ONE | ONE | ADD | add |
    | 4 | ONE | ONE | **REVSUBTRACT** | subtract |
    | 5 | ONE | ONE | **MIN** | component min |
    | 6 | ONE | ONE | **MAX** | component max |
    | 7 | ONE | INVSRCALPHA | ADD | alpha-multiply add |

## 12. Risk to proven paths

- **Now.**
  - No register write, cap or allocation changes.
  - `set_rs` gains a compare and an increment per state token.
  - One log event per context lifetime.
  - No risk to the default 16 bpp path, to Glide/OpenGL coexistence, to SLI or to the flip path.
- **G94 era, path by path:**
  - **16 bpp default.** With the bits off, nothing changes. With BLENDOP on, `fogMode` gains bits only for a
    blended draw with a non-ADD op. With CWMASK on, `fbzMode[9]` is cleared only for masks with nothing to
    write.
  - **Glide/OpenGL coexistence.**
    - `fogMode` is rewritten whole by D3D at every flush (`vcrdd_3d.c:81`) and by Glide's state validation.
    - `renderMode` is rewritten whole by D3D's target sequence (`vcr_3dseq.h:65`) and by Glide's
      `_grRenderMode` at every open.
    - A D3D client killed with a partial mask live leaves `renderMode` masked until either of those runs
      (G03's reset family).
  - **SLI.** Broadcast with the rest of the state (§6.4).
  - **Flips.** Untouched.
  - **Performance.** `renderMode` sync writes happen only for partial masks at 32 bpp. Halo's masks need none.

    `0x100042b3`); the values are not known. It too is only reachable through G94.
  - UE2 resets BLENDOP to ADD only.
  - Thief II NewDark sets COLORWRITEENABLE = 0xffffffff (`Thief2.exe` `0x5f4711`, `0x5f595f`, `0x5f6f7e`).
  - None of these is unblocked through the DX7 DDI.
- **Priority: P3** for G91 as filed. Nothing can be implemented in this DDI, and no staged title is blocked
  by the caps. §11.3's outcome feeds G94's priority.
