## 1. Verdict

**The gap is real and fixable. It is a pure transport change: the HAL keeps every register value it writes today and
only changes how the values reach the chip. Priority P2, effort L.**

- **Today** every 3D register write is one uncached store into chip 0's 31-entry PCI FIFO: 27/36/45 stores per
  untextured/1-texture/2-texture triangle, plus a `status` read before every vertex (`KMD/display/vcrdd_3d.c:24-27`,
  `:183-239`; `KMD/display/vcrdd_2d.c:92-108`). 31 entries hold about 2.5 vertices, so the CPU waits through each
  triangle's set-up and the chip idles while the CPU does the runtime's software T&L.
- **What it costs, measured.** The UT2003 flyby at 640x480x16 spends 116.7 ms of its 123 ms frame in "Hardware
  DrawPrimitive", at 29.4k triangles a frame: about **237k triangles/s end to end**
  (`REP/onbox.md` §UT2003, `ONBOX/session_log.md` 10:23). That is the PIO path's modelled ceiling of 120-220k/s
  (`REP/perf.md` §4.1). The split between our DP2 and the runtime's software vertex processing is unmeasured (G46).
- **The fix: chip 0's `cmdFifo0`, programmed exactly as our own h5 Glide programs it on this board** - base 0x18000,
  0xff000 bytes, hole counting on, the values read back on silicon (`ONBOX/regs/regs_after_windowed_1009.txt`:
  `0x80020 = 0x18`, `0x80024 = 0x1fe`) - filled through the display driver's write-combined LFB view:
  - triangles as **packet 3**, one packet a triangle, colour as the four floats `vertex()` sends today;
  - target, state and clears as **packet 1**, in today's order, consecutive registers merged into one run;
  - locked-op fences (Glide's `P6FENCE`) around the wrap jump, every 64K dwords, before any read-pointer wait and
    at the end of each DDI call;
  - the read pointer read only when the cached room runs out;
  - every wait bounded by `SPIN_CAP`; on any failure the stream is stopped, the proven engine reset runs, and the PDEV
    goes on with the direct path.
- **What it is not.** No packed colour (G58), no strip/fan continuation (G49), no register shadows (G53), no swap
  queue (G54, perf P7), no packet-5 uploads (G56, P8), no SLI (G51). Each of these builds on this ring and is cheap
  once it exists. Packet 6 and every AGP path are out: the 6000's chips sit on PCI-66 behind a bridge (`REP/hw.md`
  §2.4, Q13).
- **Why P2 and not higher.** By the plan's rubric this is "performance with a measurable gain". It is the largest
  single lever for the 4-9 fps measured in UT2003/UT2004, but those titles also render wrong (G05, G06, G18). Making
  a wrong picture faster is not the first job, and this is the riskiest change in the performance lane.

## 3. The design

### 3.0 Switch and plumbing

- **`Diag\D3DCmdFifo`** (DWORD, absent = 0), read **at boot** in `VcrFindAdapter` beside `D3D32`/`D3DBigTex`
  (`vcrmp.c:234-244`) into `x->d3dcmdfifo`:

  | bit | what |
  |---|---|
  | 0 (1) | arm the Direct3D command FIFO on a VSA-100. **The only bit a normal run sets.** |
  | 1 (2) | allow it on a Banshee/Voodoo3 too: the 86Box bed, for a pre-silicon pass. Never on a fleet box. |
  | 2 (4) | phase 1b, later: the texture-cache flush goes through the FIFO, with no disarm (§3.4.4) |
  | 3 (8) | paranoid, for diagnosis: a fence after every packet, and a range check on every read-pointer poll |
  | 4 (16) | bisect: drain at the end of every DP2/Clear2 call (no run-ahead across calls). This separates "the ring is wrong" from "asynchrony is wrong". |

- `fill_info` sets **positive** `vcr_info.flags` bits `VCR_INFO_F_D3DCMDFIFO` (bit 0) and `VCR_INFO_F_D3DCMDFIFO_V3`
  (bit 1), plus one each for bits 2-4 when they land. An older miniport never sets them. **The bit numbers are not
  fixed here.** G01, G08, G09 and G16 each proposed 0x8000/0x10000, and G15 proposes an appended word. Take the next
  free bits at landing time; `test_d3d32_is_a_default_off_switch` already fails when two flags share a bit.
- `VcrDd2dInit` (`vcrdd_2d.c:432-502`) sets `pd->cf.on` = (`napalm` && bit 0) || (`!napalm` && bit 1). It caches
  `pd->cf.sli_chips` from the same `vcr_info` and logs **"armed: Direct3D command FIFO at 0x18000, 1020 KB
  (Diag\D3DCmdFifo)"** once. That line is what tells a ring decode the switch was on, as 513/16 and 513/18 do today.
- **A new event `VCR_EV_DD_CMDFIFO`** takes the next free code in the 51x display block. G02 and G04 both claim 514,
  so 515 is the first unclaimed code today. `tools/vcrlog.py` reads the table from `vcr_events.h` itself.

  | what | level | when | a..d |
  |---|---|---|---|
  | 1 | INFO | the first arm of a PDEV | base, size, `baseSize` read back |
  | 2 | WARN | an arm refused, once per PDEV per reason | why (§3.2 `VCR_CF_R_*`), `cmdFifo0.baseSize`, `cmdFifo1.baseSize` / status |
  | 3 | ERROR | a FIFO failure | why, `readPtrL`, status |
  | 4 | ERROR | the failure's fingerprint, logged right after what 3 | `aMin`, `aMax`, `depth << 16 \| holeCount` (16 bits each), `wofs` |
  | 5 | WARN | after a failure: engine reset, then the direct path | reset result, failures this PDEV |
  | 6-8 | INFO | the counters, at the last context gone, `DrvAssertMode(FALSE)` and `VcrDd2dTerm` | arms / disarms / drains; wraps / fences / polls; packet-3 triangles / KB / refusals; DP2 µs / spin µs (RDTSC) |

  Nothing is logged per frame, per arm or per packet. The ring wraps within seconds of a game already (G76), and
  every `VcrDd` is an IOCTL (G52).
- **PDEV state** (`vcrdd.h`, in `VCR_PDEV`):

  ```c
  typedef struct VCR_CF {
      ULONG on;            /* Diag\D3DCmdFifo for this PDEV's chip                     */
      ULONG armed;         /* cmdFifo0 is OURS and enabled                              */
      ULONG failed;        /* a failure this PDEV: the direct path until the next one   */
      ULONG staging;       /* w3() collects instead of storing (vcrdd_3d.c)              */
      ULONG stage_n, stage_bad;
      vcr_regw stage[VCR_CF_STAGE_MAX];   /* 64 */
      ULONG smode;         /* the state's sSetupMode: packet 3's cull bits              */
      ULONG gen;           /* bumped by a failure: prepare() re-sends                   */
      ULONG sli_chips;     /* cached from vcr_info; refreshed at release and re-assert  */
      ULONG refused_seen;  /* VCR_CF_R_* bits already logged                            */
      vcr_cf_ring ring;    /* the pure state, include/vcr_cmdfifo.h                     */
      volatile ULONG *ring_va;            /* pvRamBase + base                           */
      ULONG cnt[VCR_CF_NCOUNT];           /* arms, disarms by reason, wraps, ...         */
      ULONGLONG t_dp2, t_spin;            /* RDTSC                                      */
  } VCR_CF;
  ```

### 3.1 Memory layout: Glide's window, carved out of the DirectDraw heap

- **The ring is `[0x18000, 0x117000)`**: `VCR_CF_BASE` 0x18000 and `VCR_CF_SIZE` 0xff000, so `baseAddrL` 0x18 and
  `baseSize` 0xfe | 0x100. This is the byte-for-byte geometry our Glide runs on `.124` (fact 3, and the silicon
  readback quoted in §1). It
  keeps the 96 KB under it clear for VGA, as Glide's own comment asks. It is in the lower 16 MB (fact 7). No desktop
  mode can reach it (`fb_reserved` 0x118000, `vcr_modes.c:177`).
- **Glide and the D3D ring share the window and never run at once.** Glide reaches the chip only after
  `GETLINEARADDR`/`HWCSETEXCLUSIVE`, where the DLL disarms (§3.5). Glide's `hwcInitFifo` idles first, writes
  `baseSize` = 0 and re-initialises the window itself (GL5 `minihwc.c:2816-2900`).
- **The heap floor is mandatory with the switch on.** A DirectDraw surface inside the window would be counted by the
  hole logic as command data (fact 13; G01 fact 3). `heap_range()` (`vcrdd_ddraw.c:51-57`) passes
  `VCR_CF_HEAP_FLOOR` = 0x118000 as `floor` to `vcr_dd_heap_range()` when `pd->cf.on`, and otherwise what it passes
  today (`dd_heap_floor ? VCR_DD_HEAP_FLOOR : 0`). It is read at `DrvGetDirectDrawInfo`, after `VcrDd2dInit` has set
  `cf.on` (`vcrdd_2d.c:455-457`). It is fixed for the life of the PDEV: arming and disarming never move it.
  - The cost is 1.1 MB of heap. On `.124`'s 1280x1024x32 desktop that is 26.9 -> 25.8 MB.
  - A side effect is that G63's "a block at offset 0 is lost" cannot happen while the switch is on.
- **The ring is written only while armed, and only through `pd->ring_va`.** Writes are `volatile ULONG` stores, one
  dword at a time, in address order. Never `memcpy` or `memset`: SPEC L4794 allows only 32-bit words in a CMDFIFO.
  Nothing reads the ring.

### 3.2 Pure logic: `KMD/include/vcr_cmdfifo.h` (Win32-free, host-tested)

This is GBK's `gbk_fifo.c` and `gbk_packet.c`, ported and corrected. Integer only, C89, no CRT.

```c
#define VCR_CF_BASE         0x18000u      /* Glide's: 96 KB pad, minihwc.c */
#define VCR_CF_SIZE         0xff000u      /* MAXFIFOSIZE_16MB: 255 pages   */
#define VCR_CF_HEAP_FLOOR   0x118000u     /* == miniport caps.fb_reserved  */
#define VCR_CF_END_ADJUST   32u           /* FIFO_END_ADJUST: the JMP fits */
#define VCR_CF_MARGIN       4u            /* never write onto the read ptr */
#define VCR_CF_FENCE_DW     0x10000u      /* the hole counter's 64K rule   */
#define VCR_CF_MAX_REQ      4096u         /* bytes; one lap is 1,044,448   */
#define VCR_CF_THRESH       ((0xfu << 5) | 0x8u)   /* Glide, non-Banshee   */
#define VCR_CF_SPIN_CAP     2000000u      /* = vcrdd_2d.c SPIN_CAP, not GBK's 10M */
#define VCR_CF_STAGE_MAX    64u
#define VCR_CF_VERTEX_MAX   14u
/* CMDAGP offsets in BAR0 (h3regs.h SstCRegs, computed): cmdFifo0 at +0x20 */
#define VCR_CF_BASEADDR0    0x80020u
#define VCR_CF_BASESIZE0    0x80024u
#define VCR_CF_READPTRL0    0x8002cu
#define VCR_CF_READPTRH0    0x80030u
#define VCR_CF_AMIN0        0x80034u
#define VCR_CF_AMAX0        0x8003cu
#define VCR_CF_DEPTH0       0x80044u
#define VCR_CF_HOLES0       0x80048u
#define VCR_CF_BASESIZE1    0x80054u      /* cmdFifo1 at +0x50 */
#define VCR_CF_THRESHREG    0x80080u      /* cmdFifoThresh */
```

- `unsigned vcr_cf_init_seq(unsigned base, unsigned size, vcr_regw w[10])`: fact 4's ten stores, in order. Hole
  counting is on: neither `SST_CMDFIFO_DISABLE_HOLES` (bit 10) nor AGP (bit 9).
- **Ring state and room**, Glide's model:

  ```c
  typedef struct vcr_cf_ring {
      unsigned base, size, wofs, rofs, since_fence, jmp, laps;
      int room_end, room_read;      /* bytes */
  } vcr_cf_ring;
  void vcr_cf_reset(vcr_cf_ring *r, unsigned base, unsigned size); /* wofs = rofs = 0;
                         room_end = size - 32; room_read = room_end - 4; jmp precomputed */
  enum { VCR_CF_OK, VCR_CF_STALL, VCR_CF_WRAP, VCR_CF_TOOBIG };
  int  vcr_cf_check(const vcr_cf_ring *r, unsigned nbytes);  /* NO read pointer: OK / STALL / WRAP / TOOBIG */
  void vcr_cf_update_read(vcr_cf_ring *r, unsigned readptrl); /* credit what the chip consumed (+1 lap if behind) */
  int  vcr_cf_readptr_sane(const vcr_cf_ring *r, unsigned readptrl); /* base <= p < base + size, dword aligned */
  void vcr_cf_wrap(vcr_cf_ring *r);       /* after the JMP was stored at wofs: room_read -= room_end */
  void vcr_cf_advance(vcr_cf_ring *r, unsigned nbytes);       /* by what WAS written, never by a reservation */
  int  vcr_cf_fence_due(const vcr_cf_ring *r, unsigned ndw);  /* since_fence + ndw > 0x10000 */
  int  vcr_cf_drained(const vcr_cf_ring *r, unsigned readptrl); /* readptrl == base + wofs */
  ```

  The vendor's infinite loop (fact 11) cannot happen here. A check only asks whether n bytes fit, and the ring advances
  by the dwords actually stored. A request larger than `VCR_CF_MAX_REQ` is `TOOBIG` before anything is touched. The
  largest real requests are a full stage of 64 register writes (at most 128 dwords, 512 bytes, §3.4.1) and a
  2-texture triangle (172 bytes); the 32-word fog table packs into one 33-dword run.
- **Packets** (headers only; the 2D bit, chip field and register number are those of facts 8 and 9):
  - `vcr_cf_pk1(off, n, inc)`: `off` is a 3D offset as the HAL already spells it, e.g. `V3D_TMU0 + V3D_TEXTUREMODE`.
    The register is `off & 0x3fc` and the chip field `(off >> 10) & 0xf`. A chip field of 8 or more, or a register
    beyond 0x3fc, returns 0, and 0 is never a valid header: the caller fails rather than emit an ambiguous packet.
    The examples:

    | register | header |
    |---|---|
    | `fbzMode` (0x110) | 0x00010221 |
    | TMU0 `textureMode` | 0x00011601 |
    | the TMU0\|TMU1 `nopCMD` | 0x00013241 |
    | a 32-word increment run at `fogTable` | 0x002082c1 |

  - `vcr_cf_pk3(setupmode, nverts, cmd)` = `((setupmode >> 16) & 0xf) << 22 | (setupmode & 0xff) << 10 | nverts << 6 |
    cmd << 3 | 3`. Packed colour (bit 28) is clear. For one texture with no culling it is 0x0000fcc3; with CCW culling
    (`SM_CULL | SM_CULL_NEGATIVE`) it is **0x0180fcc3**.
  - `vcr_cf_jmp(base)` = `(base << 4) | 0x18`, which is 0x00180018 for 0x18000.
  - `unsigned vcr_cf_vertex_dwords(unsigned mask)`: X Y, then R G B (3) for `SM_RGB`, A (1), Z, Wfbi, W0, S T (2),
    W1, S T (2). That is **8, 11 or 14**.
  - `static const unsigned vcr_cf_vertex_regs[14]` = `sVx, sVy, sRed, sGreen, sBlue, sAlpha, sVz, sOowfbi, sOow0,
    sSow0, sTow0, sOow1, sSow1, sTow1`. This is the order `vertex()` writes (`vcrdd_3d.c:190-221`) and the order
    packet 3 carries (fact 8). The host test pins one against the other.
- **Packer:** `unsigned vcr_cf_pack(const vcr_regw *w, unsigned n, vcr_u32 *out)` emits packet 1 per write, and
  merges a run of consecutive registers on one chip, in ascending order, into one packet-1 increment run. Merging only
  ever joins writes that were already adjacent and ascending, **so the order of the writes is exactly the input's**.
  `vcr_cf_pack_size()` gives the size first, so the reserve is exact.
- **Arm decision:** `unsigned vcr_cf_arm_why(on, failed, excl_pid, sli_chips, g2d_ok, bs0, bs1, idle_run)` returns
  0 to arm, or one of:

  | code | meaning |
  |---|---|
  | `VCR_CF_R_OFF` | the switch is off |
  | `VCR_CF_R_FAILED` | an earlier failure this PDEV |
  | `VCR_CF_R_OWNER` | Glide holds the chip |
  | `VCR_CF_R_SLI` | an SLI session is live (snooping would broadcast the ring) |
  | `VCR_CF_R_ENGINE` | the 2D engine was given up |
  | **`VCR_CF_R_FOREIGN`** | `cmdFifo0` or `cmdFifo1` has `SST_CMDFIFOEN` and it is not ours: G01's state |
  | `VCR_CF_R_BUSY` | not idle three reads in a row (`vcr_idle_run`, `vcr_3dseq.h:160-171`) |

  **A foreign stream is never re-initialised by this item.** Clearing it is G01's job, with G01's owner check; doing
  it here would kill an alt-tabbed live Glide game's stream (G01 §2 row 7).

### 3.3 Transport: `KMD/display/vcrdd_cmdfifo.c` (new, integer only, `-mgeneral-regs-only` like the rest)

- **`BOOL VcrDdCfArm(pd)`**:
  1. `VcrDd2dSync(pd)` if `g2d_busy`. This is the direct path's own bounded drain; a give-up means no arm.
  2. Read `cmdFifo0.baseSize` and `cmdFifo1.baseSize`, then the idle rule (three `status` reads: `SST_BUSY` clear and
     the PCI FIFO back at `g2d_fifo_full`).
  3. Call `vcr_cf_arm_why`. A refusal is logged once per reason per PDEV and means the direct path.
  4. The ten stores of `vcr_cf_init_seq`, in order, through `pjRegs`. **Verify** with a twice-stable `readPtrL` ==
     0x18000, `depth` == 0 and `baseSize` == 0x1fe; on a mismatch, `baseSize` = 0, `failed` = 1 and event 3 (the
     same rule as Glide's "Initial fifo state is incorrect", `gsst.c:2853-2862`). The verifying reads also make sure
     the stores reached the chip before any ring write.
  5. `vcr_cf_reset`, `armed` = 1, and the arm is counted.
- **`volatile ULONG *VcrDdCfBegin(pd, ndw)`**: one check, `vcr_cf_check`. The fast path is two compares; with room it
  returns `ring_va + wofs/4`. Otherwise it goes to `make_room`:
  1. **fence** (the chip must see everything already written before we wait on its read pointer);
  2. while the room is short: a twice-stable `readPtrL`, a sanity check (out of the ring = failure), then
     `vcr_cf_update_read`. **One budget for every read in the call: `VCR_CF_SPIN_CAP`** (GBK's design note, with
     `vcrdd_2d.c`'s bound);
  3. if `WRAP`: fence, store the JMP at `wofs`, fence, then `vcr_cf_wrap`, at most once per call;
  4. if the 64K rule is due, fence.

  `TOOBIG`, an exhausted budget or an insane read pointer go to `VcrDdCfFail` and return NULL.
- **`void VcrDdCfEnd(pd, ndw)`**: `vcr_cf_advance` by exactly `ndw`; `g2d_busy` = 1; under bit 3, a fence.
- **The fence** is one locked instruction, Glide's `P6FENCE`: `__asm__ __volatile__("xchgl %%eax,%0" : "+m"(dummy) ::
  "eax", "memory")`. A locked operation drains the write-combining buffers on P6 and K7. It needs no SSE: the DLL is
  built `-march=i686`, and the Athlon XP has no SSE2 `mfence`.
- **`BOOL VcrDdCfDrain(pd)`** (the ring stays armed):
  1. fence;
  2. a bounded twice-stable `readPtrL` until it equals `base + wofs`;
  3. then the idle rule (three reads), bounded.

  On success `g2d_busy` = 0. A timeout is a failure.
- **`BOOL VcrDdCfDisarm(pd, why)`**: drain, then `baseSize` = 0 (one uncached store), `armed` = 0, the disarm counted
  under `why`.
- **`void VcrDdCfFlush(pd)`**, at the end of DP2 and Clear2: a fence if anything was written since the last one, so a
  frame's tail is not left in a write-combining line while the chip waits on a hole.
- **`void VcrDdCfFail(pd, why)`**:
  1. events 3 and 4 with the fingerprint;
  2. `baseSize` = 0;
  3. `IOCTL_VCR_RESET_ENGINE`, the proven reset (fact 16);
  4. then `armed` = 0, `failed` = 1, `fog_valid` = 0 (G41) and `gen++`. If the reset reports idle, the PDEV carries on
     with the direct path (event 5); if not, `give_up(pd, 3, status)`, which is today's outcome for a wedge.

  If G02 has landed, its recovery replaces step 3, so one code path recovers both transports.
- **`void VcrDdQuiesce(pd, why)`** = `if (armed) VcrDdCfDisarm(pd, why); VcrDd2dSync(pd);`.

### 3.4 Emitters (`KMD/display/vcrdd_3d.c`)

#### 3.4.1 Target, state and clears: the same code, staged

- `w3()` (`:24-27`) gains one branch: `if (pd->cf.staging) { VcrDdCfStage(pd, off, v); return; }`.
- The three bodies' `VcrDdRoom(...)` calls become `room3(...)`, which is `pd->cf.staging ? !pd->cf.stage_bad :
  VcrDdRoom(pd, n)`.
- The bodies are renamed `target_regs`, `state_regs` and `clear_regs`; **their write sequences are untouched**.
- The public functions become wrappers:

  ```c
  BOOL VcrDd3dState(VCR_PDEV *pd, const vcr3d_regs *r)
  {
      BOOL ok;
      if (!VcrDdCfStageBegin(pd))          /* off, refused or failed: the proven path, as before */
          return state_regs(pd, r);
      ok = state_regs(pd, r);              /* the same writes, collected in order */
      pd->cf.smode = r->setupMode;
      return VcrDdCfStageEnd(pd, ok);      /* packed, reserved exactly, written; or dropped */
  }
  ```

- `VcrDdCfStageBegin` returns FALSE at once when `!cf.on`. Otherwise it arms if needed (`VcrDdCfArm`) and starts the
  staging; `VcrDdCfStageEnd` stops it.
- **There is one source of truth for what is written.** The fog table (`:86-101`), the compressed-texture nopCMD
  (`:107-112`), TMU0 and TMU1, the 32 bpp stencil pair from `vcr_3d_target_seq`, and the clear's fbzMode/c1/zaColor,
  per-rectangle clip and fastfill and clip restore all reach the ring in the order they reach the PCI FIFO today.
- **Sibling items keep working.** Every later gap that adds a state write (G05 `combineMode`, G22 zaColor, G50 2PPC,
  ...) is carried by the FIFO with no extra work. G22's rule, that zaColor is clobbered by every clear, holds because
  the clear's writes are the same and `clear_rects` still sets `dirty` and `prepared` = 0 (`vcrdd_d3d.c:1419-1420`).
- **Stage overflow:** `VcrDdCfStage` packs and writes what it has once 64 entries are collected, and carries on. Every
  packet is complete by itself, so this is correct. A DP2 CLEAR with many rectangles is the only caller that gets near
  the limit. A failure in the middle marks `stage_bad`, so the remaining `room3` calls return FALSE, and the function
  returns FALSE as the direct path does when `VcrDdRoom` gives up.

#### 3.4.2 Triangles: packet 3

```c
BOOL VcrDd3dTriangle(VCR_PDEV *pd, const vcr3d_draw *d, const UCHAR *a, const UCHAR *b, const UCHAR *c)
{
    if (VcrDdCfWant(pd))                                  /* armed, or armed now */
        return tri_pk3(pd, d, a, b, c);
    /* ... the existing body, unchanged ... */
}
static BOOL tri_pk3(VCR_PDEV *pd, const vcr3d_draw *d, const UCHAR *a, const UCHAR *b, const UCHAR *c)
{
    ULONG mask = SM_RGB | SM_A | SM_Z | SM_WFBI | (d->textured ? SM_W0 | SM_ST0 : 0) |
                 (d->textured1 ? SM_W1 | SM_ST1 : 0);
    ULONG nv = vcr_cf_vertex_dwords(mask), n = 1 + 3 * nv;
    volatile ULONG *p = VcrDdCfBegin(pd, n);
    if (!p)
        return FALSE;
    *p++ = vcr_cf_pk3(mask | (pd->cf.smode & (SM_FAN | SM_CULL | SM_CULL_NEGATIVE | SM_NO_PINGPONG)),
                      3, VCR_PK3_INDEPENDENT);
    p = vertex_words(p, d, a);
    p = vertex_words(p, d, b);
    p = vertex_words(p, d, c);
    VcrDdCfEnd(pd, n);
    return TRUE;
}
```

- **The header and the payload come from one mask**, built from the same `d->textured`/`d->textured1` that decide what
  `vertex_words` stores. A header that disagrees with its payload would desynchronise the stream and hang the engine,
  and this rules it out by construction. The cull bits come from the state's `sSetupMode`, exactly as the setup unit
  sees them today. `prepare()` keeps `setupMode` and `d` consistent (`vcrdd_d3d.c:1338-1356`).
- **`vertex_words()` stores exactly what `vertex()` writes, in its order.** It uses the same expressions: the xy bias,
  colour as four floats 0-255, `z * z_scale`, the fog ramp's synthetic 1/W, `uv * scale * oow`, and `sOow1` = `sOow0`.
  That is 8, 11 or 14 dwords. `vertex()` itself is left byte for byte as it is: it is the hottest proven code, and a
  host mirror test pins the two functions' expression lists to each other (§6). Folding `vertex()` onto
  `vertex_words()` belongs in the commit that flips the default.
- **Size:** 25, 34 or 43 dwords (100, 136 or 172 bytes) a triangle. That replaces 27/36/45 uncached single-dword
  stores plus at least 3 `status` reads.
- **One packet per triangle.** Batching up to five triangles a packet saves 1 dword in 34, under 3 %. It would mean
  writing the header after the vertices (a deliberate hole) or a staging copy. It is deferred to G49, which knows its
  counts in advance.
- **No `status` read and no `VcrDdRoom` on this path.** The read pointer is read only when the ring is short (G48 is
  fixed for this path).
- **The ring holds copies of the vertices.** Nothing refers back to the runtime's command or vertex buffers after DP2
  returns, so the runtime may reuse them at once, as it does today.

#### 3.4.3 What stays direct (phase 1a)

- **`VcrDd3dTexFlush`** (`:253-270`) stays direct. It contains a raw 2D NOP and a texture-port write-back. Its
  `VcrDdRoom(pd, 7)` triggers the disarm (§3.5), so it runs exactly as proven.
- This costs nothing extra. A texture write is always preceded by a Lock or a TEXBLT, and both drain the ring anyway.
- The next state write re-arms (ten stores and three reads, about 5 µs, inferred). The counters show how often this
  happens per frame.

#### 3.4.4 Phase 1b (bit 2, after phase 1a is proven)

The texture flush goes in the ring instead:

- the 2D NOP as a 2D packet 1 (0x000140e1);
- `texBaseAddr` pointed away, `nopCMD` and `texBaseAddr` back as packet 1. This is how 3dfx flushes in the FIFO
  (VH5 `D3TXTR.C:2532-2540`);
- the port write-back as a one-word packet 5 to the texture port.

That removes the arm/disarm churn for titles that stream textures. It is measured against phase 1a by the
arms-per-frame counter.

### 3.5 Who drains and who disarms

**Two levels.** A CPU access to video memory needs the chip to have finished with it: that is a **drain**, and the ring
stays armed. A direct register write, Glide, a mode change or a tool needs the stream stopped: that is a **disarm**
(drain, then `baseSize` = 0). **Direct and FIFO writes are never mixed.**

### 3.6 What does not change

- **The caps.** Nothing reported to the runtime changes.
- **The DDI answers** and the state-to-register mapping.
- **The flip:** `Dd_Flip` still drains before `IOCTL_VCR_DDFLIP`, honours `DDFLIP_NOVSYNC`, and answers
  `DDERR_WASSTILLDRAWING` as now. Vsync stays on (the user's choice).
- **The render-after-flip behaviour (G55):** the first draws after a flip start at once, today and with the ring.
- **The fog shadow**, which is only invalidated by a failure.
- **The 16 bpp, 32 bpp, D3D32 and D3DBigTex paths:** the same writes arrive in the same order.
- **DirectDraw-only and Glide/OpenGL titles.** They never arm the ring. Their only change is the heap floor while the
  switch is on.

### 3.7 Expected effect (inferred until measured)

- **Per 1-texture triangle on the HAL side:** 136 bytes of write-combined stores (bursts of 64 bytes on PCI-66, at
  about 100-200 MB/s) and no uncached reads. That is **about 0.7-1.4 µs, or 0.7-1.4 M triangles/s**, against
  4.6-8.4 µs (120-220k/s) today (`REP/perf.md` §4.1). Packed colour (G58) and strips (G49) are the next factors.
- **Within a frame** the CPU and the chip overlap, so a frame is about max(CPU work, chip work) plus the tail. Across
  frames they do not, because the flip still drains; that is G54.
- **UT2003 flyby (640x480x16; transport-bound, since its 237k triangles/s is the PIO ceiling, §1): about 2x
  avgfps**, so roughly 9.4 -> 18. The bound is the runtime's software T&L and clipping share, which only G46 can
  measure.
- **UT2004 and Halo at 1280x960** move roughly 50-90k triangles/s by their 11-12 ring counters (UT2004 15.2M
  triangles in a 242 s session, Halo 26.1M in 498 s, loading included; `ONBOX/session_log.md` 10:16 and 10:29).
  They are likely bound by something else as well: fill on one chip at 1 px/clk (G50, G51), texture uploads (G56) or
  the runtime. G47 alone may give them much less, and the counters in §7 say which.

## 4. Gating

- **Default OFF** behind `Diag\D3DCmdFifo` bit 0. With the switch off:
  - every hook tests `pd->cf.armed` or `pd->cf.on`, and both stay 0;
  - `w3()` stores as before; the staged wrappers fall straight into the old bodies;
  - the DirectDraw heap range is today's.

  **The register traffic and the memory layout are byte for byte today's.** `test_vcr_kmd_d3dseq.c` and
  `test_vcr_kmd_d3d.py` keep pinning that.
- **Nothing arms at boot or at a mode set.** Arming happens only at the first Direct3D draw. A box that hangs with the
  switch armed therefore comes back to its desktop after a power cycle and is disarmed remotely: `REGWRITE ... Diag
  D3DCmdFifo REG_DWORD 0`, then a clean boot.
- **One Diag change per clean boot** (the plan's rule): arm, cold boot, run, disarm. Never together with another new
  switch.
- **Not safe to land default-on.** It is a new hardware transport that has never run from this driver. Flip the default
  only after:
  - the 86Box bed;
  - one supervised `.124` boot with the whole §7 matrix;
  - the in-game runs;
  - a 30-minute soak with 0 FIFO failures;
  - the user's decision.

  In that commit, fold `vertex()` and `VcrDd3dState` onto the shared builders and retire the mirror test.

## 5. d3dprobe tests (`KMD/tools/d3dprobe.c`)

These are explicit tests, outside the default list, so the 40/40 and 42/42 baselines keep their meaning. **They are
path-agnostic: they also pass on the direct path, and boot A records that.**

1. **`fifolap`: three-plus laps, pixel-exact.**
   - **What it draws:** untextured, Z off, dither off, into the top-left 256x256 of the back buffer (the readback
     window, G74). There are 4 layers of 64x64 tiles of 4x4 pixels, each tile a quad of 2 triangles: **32,768
     triangles a frame**. That is 3.28 MB of packets, more than **3 laps** of the ring and 12 or more 64K fences.
   - **Colour:** tile (tx, ty) of layer k is r5 = tx & 31, g6 = ty, b5 = 8 \| (tx >> 5) \| k << 1, replicated to 888.
     Every tile is unique within a layer, every layer differs, and the value is exactly representable in 565, so the
     expected pixel is the same at 16 and 32 bpp.
   - **Batching:** `DrawPrimitiveUP` in batches of 1,024 triangles, toggling `ALPHABLENDENABLE` (ONE/ZERO, which does
     not change the picture) between batches. That forces a state packet before every batch, so state packets cross
     the wraps too.
   - **Pass:** all 16,384 tile-interior pixels (the 2x2 centre of every tile) equal layer 3's colour, **0 wrong**.
     The RESULT gives `checked`, `wrong` and the first wrong pixel. A lost, duplicated or reordered packet at a wrap or
     a fence shows as an earlier layer's colour or the clear colour.
   - Optional `fifolap_tex`: the same with one white 8x8 texture MODULATE, so 34-dword packets.
2. **`fifosync`: the drain at Lock, and the flush.**
   - **What it does:** one MANAGED 8x8 R5G6B5 texture, point-sampled, `SELECTARG1(TEXTURE)`. 64 times in **one**
     frame: `LockRect`, fill with colour T_i (565-exact: r5 = i & 31, g6 = (5i) & 63, b5 = 16 \| i >> 5),
     `UnlockRect`, then draw a 32x32 quad at cell i of an 8x8 grid.
   - **Pass:** the centre of every cell shows its own T_i, **0 wrong cells**.
   - **Why it works:** the D3D8 runtime uploads a managed texture by Lock and CPU copy (`retro-3dfx/FINDINGS.md:
     1214-1215`). Our `Dd_Lock` must therefore wait for quad i-1, still queued in the ring, before the CPU overwrites
     the texture. A missing drain shows quad i-1 in a later colour, and a missing flush shows the stale one. It also
     makes the arm/disarm cycle run 64 times a frame.
3. **`perf --scene setup [--tex 0|1] [--tris N]`** (default 20,000 a frame).
   - **What it draws:** N small (3-pixel) triangles at deterministic pseudo-random positions, one Clear and one
     Present a frame. The existing `perf` scene is fill-bound and cannot see the triangle path (`REP/perf.md` §3.2).
   - **What it reports:** `tris_s` and fps. Run it `--novsync` (the HAL and setup number, diagnostic only) and with
     vsync (the campaign's mode).
   - This is the minimum G47 needs. G78 owns the full set of perf scenes.
4. **`d3dprobe_run.py --expect-fifo on|off`.**
   - **What it does:** after the probe has exited (never during it), reads the ring with `vcrctl log`.
   - **Requires when on:**
     - event 515 what 1 (armed);
     - for `fifolap`, at least 3 wraps a frame;
     - 0 failures (what 3) and 0 refusals (what 2).
   - **Requires when off:** no event 515 at all.
   - **Why:** a probe pass on the direct path proves nothing about the FIFO. This is "verify the post-condition, not
     the return value".

- **Mirror.** The value expressions of `vertex_words()` equal those of `vertex()`, in order, after normalisation.
- **The ring is outside the heap.** `VCR_CF_HEAP_FLOOR` == `VCR_CF_BASE + VCR_CF_SIZE` rounded up to a page ==
  0x118000 == the miniport's `caps.fb_reserved`, and `heap_range` applies it when `pd->cf.on`.
- **No status read per vertex.** `tri_pk3`/`vertex_words` contain no `rd(`, no `VcrDdRoom` and no `pjRegs`.
- **Fence and stores.** The fence is a locked `xchg`/`lock`, never `mfence`, `sfence` or an empty macro. The ring
  writer has no `memcpy`/`memset`.
- **The hook points exist.** Disarm at `DrvAssertMode(FALSE)`, `VcrDd2dTerm`, `GETLINEARADDR`, `HWCSETEXCLUSIVE` and
  the harness escapes; a drain only at `Dd_Lock`, `Dd_Flip` and TEXBLT.
- **Every wait is bounded** by `VCR_CF_SPIN_CAP` (2,000,000).

## 8. Risk to proven paths

| path | risk | why |
|---|---|---|
| the default 16 bpp path, switch off | **none** | register writes, room reads and the heap layout are unchanged; pinned by tests |
| any path, switch on | transport bugs: wrap, fence, room, arm, drain | engine wedge, caught by bounded waits -> reset -> direct; a corrupt packet could write any 3D register (e.g. a wrong `colBufferAddr` draws into the desktop until the next frame). Mitigated by: the exact Glide programming proven on this silicon, pure packers decoded by a model, header and payload from one mask, a 4 KB request cap, `fifolap`/`fifosync`, the bed first |
| PCI bus | a hard bus hang if the chip stops taking writes | not new. Ring writes are memory writes that drain into the frame buffer whatever the 3D engine is doing. A wedged engine stops the read pointer, and the room wait (bounded) catches it. A wedged memory controller would hang texture uploads today too |
| Glide/OpenGL | Glide reuses the same window | the disarm comes first at every hand-off; Glide re-initialises the FIFO itself after an idle wait. A killed Glide client leaves its stream on: refused here, G01 clears it |
| SLI | snooped ring writes reaching the slaves | arming is refused while `sli_chips` != 0; D3D stays chip 0 only |
| the flip | none in behaviour | it still drains before the flip IOCTL. A longer queue only moves the CPU's wait to the flip; a frame's total work is unchanged |
| DirectDraw/GDI | an extra disarm/re-arm per windowed Present and per accelerated GDI call while a D3D context is live | windowed mode loses some overlap with the 2D Present blit. Fullscreen flips do not disarm |
| memory | 1.1 MB less DirectDraw heap with the switch on | matters only for texture-heavy titles at 1280x960x32 (UT2004). An open question for the ring size |
| CPU | an extra branch in `w3()`, `VcrDdRoom` and `VcrDd2dSync` on a field that is 0 | negligible |
| G43 | a stale PDEV pointer in a context now also reaches the ring state | same class as today's `pjRegs`; G43's fix covers both |

## 10. Open questions

1. **Does XP's kernel `P6CACHE` mapping really give `pvRamBase` write-combining on `.124`?** It depends on an MTRR or
   PAT entry. If not, the ring still works, ordered and uncached, but slower. `perf --scene setup` will show it; a
   one-shot MTRR read (a probe-driver addition) would settle it.
2. **Does `SST_BUSY` read clear with the FIFO armed, drained and hole-free?** Glide's `grFinish` relies on it
   (inferred). Log `status` at the first drain.
3. **`cmdFifoThresh`:** Glide's 0x1e8 (proven on this board) against 3dfx's Napalm D3D value (0x14 << 5) \| 8 = 0x288.
   Does the high-water mark change fetch efficiency? A/B later, one boot each.
4. **The ring size:** Glide's 1020 KB against the vendor's 512 KB D3D default. A smaller ring returns 0.5 MB of heap;
   one frame of UT2003 is about 4 MB of packets at 34 dwords a triangle. Measure the stall spins.
5. **How often does an Unreal Engine 2 frame disarm** (texture writes, then a direct flush)? If it is dozens of times,
   do phase 1b (§3.4.4) before measuring further.
6. **Are the CMDAGP register writes ordered through the PCI FIFO or applied at once?** The design is safe either way
   (it idles before arming and drains before disarming), but the answer decides whether the arm's idle wait could be
   relaxed.
7. **Batching** five triangles per packet-3 header (a header written last into a deliberate hole): is it worth the 3 %?
   Defer to G49.
8. **A boot guard like `SliAALive`**, so a boot that died with the ring armed disarms itself. Probably not needed,
   since nothing arms at boot, but it is one flushed registry write per PDEV if wanted.

## 11. Notes for sibling items

- **G01:** as in §9. Its guard should run before G47's arm decision, so a stale stream is cleared and the ring then
  arms.
- **G02:** `VcrDdCfFail` calls G02's recovery when present. A FIFO failure is "a give-up" in G02's sense.
- **G03, G05, G12-G14, G22, G25-G30, G35, G50:** add state writes to `state_regs`/`target_regs` as usual. The FIFO
  carries them with no change.
- **G41:** `fog_valid` must also be invalidated by `VcrDdCfFail`'s reset.
- **G49:** packet-3 codes 001/010 (strip start and continue), with counts known per opcode. The ring and the header
  builder are already here.
- **G53:** shadows must also be invalidated on a FIFO failure (`cf.gen`).
- **G54:** `swapbufferCMD` and the overlay address go in the ring. Pending swaps are counted by FIFO position (Glide's
  `bufferSwaps[]`) or by `status[30:28]`, capped at 6 (`VH5/D3GLOBAL.H:749`).
- **G56:** per-surface "last used at FIFO position" fences need a monotonic position. The ring keeps `laps` and
  `wofs`, plus an arm epoch, for that.
- **G51:** SLI would need the ring snooped to every chip and room taken from the slowest chip's read pointer (Glide
  `fifo.c:1017-1041`). Not before G47 is proven single-chip.
- **G58:** packed colour is bit 28 plus one word in place of four, behind its own switch. The floats test flips under
  that switch only.
