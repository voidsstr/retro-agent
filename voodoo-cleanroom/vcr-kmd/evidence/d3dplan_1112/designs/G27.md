## 0. Summary

- **Three of the four parts are real gaps, and the hardware does all three natively. SETTEXLOD is not a gap.**
  - `D3DTSS_MIPMAPLODBIAS` (19) and `D3DTSS_MAXMIPLEVEL` (20) are stored and never read.
  - `D3DPRASTERCAPS_MIPMAPLODBIAS` is not reported (live RasterCaps `00100191`).
  - The TMU picks a mip level by **truncating** its LOD, while D3D's point mip filter asks for the **nearest** level. So every mipmapped draw on this HAL samples up to a whole level too sharp: half a level on average.
  - `D3DDP2OP_SETTEXLOD` is sent only to a driver that manages textures itself (DDK). We do not claim that (`DDCAPS2_CANMANAGETEXTURE` is not set), so the runtime does the work. It stays parsed and is now counted. It is not applied.
- **The fix is one integer function that composes tLOD bits 17:0 for a mipmapped draw** (`KMD/common/vcr_texlod.c`, host-tested):
  - LODMIN = top + MAXMIPLEVEL (clamped to the chain) + 0.5;
  - LODBIAS = the application's bias, rounded to quarters, + 0.5, clamped to the 4.2 field;
  - LODMAX is unchanged.
- **The +0.5 also goes on LODMIN, not only on LODBIAS.** The VSA-100 picks the magnification filter when the biased LOD is clamped at LODMIN (SPEC L3857, L3931). Raising both by the same half level keeps that choice at the unbiased LOD 0. 3dfx put +0.5 on the bias only, which moves the min/mag threshold by half a level.
- **It is called once, in `view_of`.** That covers both texture paths (default and D3DBigTex) and both stages. Each stage's own values follow its texture to the TMU that samples it (stage 0 on TMU1, stage 1 on TMU0). That avoids two vendor bugs: crossed stage biases, and stage 0's MAXMIPLEVEL used for both TMUs.
- **Gating.**
  - The register change and the cap go behind `Diag\D3DFeat` bit `LODCTRL` (proposed bit 10, 0x400; the integrator assigns it). It is read at boot and default OFF. With it off, register traffic and caps are byte-identical.
  - It graduates to default-on after one supervised boot passes. It is a pure correctness fix with a d3dprobe proof.
  - Logging is default-on: a one-shot line per distinct LOD stage-state value, and a SETTEXLOD counter.
- **Who sends these states.** This comes from a static disassembly of the staged binaries (section 4):
  - Red Faction: stage 0 bias −0.75 always, and −1.5 on its detail-texture stage.
  - Battlefield 1942: a bias per stage, from its settings.
  - UT2003/UT2004: −0.5 at device set-up. The per-texture path then passes the bias through `_ftol2`, which makes it the integer 0.
  - Halo, Max Payne, H&D, Thief, Thief II and System Shock 2 set neither state, so they get the rounding only.
- **d3dprobe tests.**
  - `lodbias`: 16 analytic cases, judged against D3D's rule.
  - `lodscan`: measures where the silicon switches levels.
  - `setlod`: shows that the runtime, not the driver, honours SetLOD.
  - `lodscan` and `setlod` can run on today's deployed build, with no driver change, before any HAL code is written (section 9, step 0).
- **P2, effort M.** No staged title is blocked. Arming it in game waits for G07 (mip chains packed right): the rounding samples smaller levels sooner.

## 1. What the HAL does today (verified)

- **The texture view.** Both views build tLOD with LODMIN = LODMAX = the texture's top LOD:
  - the default path: `vcr_texlod_compute`, `KMD/common/vcr_texlod.c:14-36`;
  - D3DBigTex: `vcr_texlod_compute_ext`, `:94-146`.
  - The lodbias field (bits 17:12) is always 0.
- **Mipmapped draws.** A chain the driver placed (`SF_MIP_TOP`), drawn with `MIPFILTER > D3DTFP_NONE`, gets LODMAX = its smallest level. Nothing else changes (`KMD/display/vcrdd_d3d.c:777-786` default path, `:814-824` D3DBigTex). So `MIPFILTER` POINT and LINEAR both sample floor(LOD).
- **Two stages** (`compute_regs`, `:949-960`):
  - TMU1 samples stage 0 with `v0.tLOD`; TMU0 samples stage 1 with `v1.tLOD`.
  - Each view is built from its own stage's TSS array (`view_of(c->pd, c->tss, …)` and `view_of(c->pd, c->tss1, …)`, `:927-929`). So a per-view change maps stages to TMUs correctly by construction.
- **The two stage states.**
  - `D3DTSS_MIPMAPLODBIAS` and `D3DTSS_MAXMIPLEVEL` are stored (`TSS_MAX` 32, `:1591-1611`) and mark the state dirty. Nothing reads them.
  - `ctx_defaults` zeroes both (`:1128-1129`), which matches D3D's defaults: bias 0.0, maxmip 0.
  - The legacy render state `D3DRENDERSTATE_MIPMAPLODBIAS` (46) is stored in `rs[]` only. G08 mirrors it into TSS 19 of stage 0, as the 3dlabs DDK sample does (`REP/runtime.md` §6.2).
- **SETTEXLOD** is skipped by its record size (`rec_size`, `:1564`).
- **Caps.**
  - `prim_caps` RasterCaps = DITHER | ZTEST | SUBPIXEL | FOGVERTEX | FOGTABLE | WFOG (`:2019-2020`). D3D8 reports `00100191` (`KMD/evidence/d3dplan_1112/caps_124.txt`).
  - There is no MIPMAPLODBIAS (`0x2000`, `DDK8/d3d8caps.h:203`).
  - `dwCaps2` is `DDCAPS2_FLIPNOVSYNC` only (`KMD/display/vcrdd_ddraw.c:105`), so there is no `DDCAPS2_CANMANAGETEXTURE`.
- **The register write.**
  - TMU0's tLOD is written whole on every state send of a textured draw (`KMD/display/vcrdd_3d.c:115`); TMU1's in two-stage draws (`:123`).
  - So a new tLOD value is a new value in a register the HAL already writes. There is no new register, no new write and no new ordering.
- **No float arithmetic is allowed where the change goes.**
  - `vcrdd_d3d.c` and `common/vcr_texlod.c` are built with `-mgeneral-regs-only` (`KMD/Makefile:26`, `:43-45`).
  - `WT/tests/python/test_vcr_kmd_d3d.py::test_floats_live_in_one_object_behind_the_fpu_bracket` forbids the token `float` in `vcrdd_d3d.c`.
  - So the bias (an IEEE float in a DWORD) must be decoded with integer operations. 3dfx's `CalcBias42` does the same.
- **The truncation has never been tested.** The existing d3dprobe mip checks pick LODs where floor and round agree on purpose:
  - `mip` uses LOD −1.58, 1.0 and 2.0 (`KMD/tools/d3dprobe.c:982-1030`);
  - `mip2048` uses LOD n + 0.26, "floor and round agree" (`:802-856`).
  - Both pass on silicon (`ONBOX/d3dprobe_textures_a_1024x768x32.txt`: mip 3/3, mip2048 5/5). The rounding difference is invisible to them by design.

## 2. Hardware and reference facts

### 2.1 tLOD (SPEC §8.77 L3911-3936; `GL5/incsrc/h3defs.h:715-733`)

| bits | field | format | used here |
|---|---|---|---|
| 5:0 | lodmin | 4.2 unsigned | top level + MAXMIPLEVEL + rounding |
| 11:6 | lodmax | 4.2 unsigned | smallest placed level (unchanged) |
| 17:12 | lodbias | 4.2 **signed**, −8.0 … +7.75 | app bias + rounding |
| 18, 19, 23 | lod_odd, lod_tsplit, lod_zerofrac | | kept (G26 trilinear) |
| 20, 22:21 | s_is_wider, aspect | | kept |
| 28, 29 | tmirrors, tmirrort | | kept (G33) |
| 30 | tbig | | kept (LODs count from 2048) |

- *"lodbias is added to the calculated LOD value, then it is clamped to the range [lodmin, min(8.0, lodmax)]. Note that whether the LOD is clamped to lodmin is used to determine whether to use the minification or magnification filter"* (L3931). With tbig the upper bound is 11.0 (L3936).
- *"tminfilter is referenced when LOD>=LODmin, otherwise tmagfilter is referenced"* (§8.76 L3857).
- *"tloddither … adds an average of 3/8 (.375) to the LOD value and needs to compensated in the amount of lodbias"* (L3861). This design does not set `tloddither`. G26 may set it.
- Our header already names the two 4.2 fields with integer helpers: `TL_LODMIN(l) = l << 2`, `TL_LODMAX(l) = l << 8` (`KMD/include/vcr_3dregs.h:178-179`). The lodbias field has no macro yet.

### 2.2 How the TMU picks a level, and what D3D asks for

- **The TMU truncates.** 3dfx's own table comment: *"include the LOD bias for each flavor below … The thinking is that end users expect the hardware to round to the closest LOD"* (`VH5/D6MT.C:5507-5510`, `LB_HALF = 2 << SST_LODBIAS_SHIFT`). With bias 0 a point-mipped pixel at LOD 1.85 samples level 1.
- **D3D asks for the nearest level.** `D3DTFP_POINT`: *"The nearest mip level is selected"* (`W2KDDK` D3DTEXTUREMIPFILTER page); `DDK8/d3dtypes.h:1737` `D3DTFP_POINT = 2, // nearest`.
  - On a truncating unit, nearest = floor(LOD + 0.5). OpenGL's NEAREST_MIPMAP rule is the same rounding (inferred, from general knowledge).
- **How the D3D8 runtime hands the filter over.** It passes MIPFILTER to this DX7 DDI in DX7 values: `D3DTEXF_POINT` arrives as `D3DTFP_POINT` (2). The `mip` test proves it on silicon, because `tex_view` tests `> D3DTFP_NONE` (1) and the chain is sampled.
- **Section 9, step 0 measures the truncation directly** (`lodscan`) before any HAL change. If the silicon already rounds, the +0.5 is dropped (section 12, Q1).

### 2.3 What the two stage states mean

- **`D3DTSS_MIPMAPLODBIAS`** is a float in a DWORD (`DDK8/d3dtypes.h:1615`, "D3DVALUE Mipmap LOD bias"). Its unit is one mip level.
  - **Positive means blurrier (smaller levels).** That is the hardware's sign (*"added to the calculated LOD"*), Glide's, and 3dfx's (`CalcBias42` keeps the sign).
  - The W2K DDK help page states the opposite (*"A positive bias causes the use of larger mipmap levels"*, d_grafx.chm D3DTEXTURESTAGESTATETYPE). We read that as a documentation error (inferred).
  - UE2 uses −0.5 to sharpen (`LIB/UT2004/System/UT2004.ini` `DefaultTexMipBias=-0.5`), which fits positive = blurrier.
  - The probe's cases C and D settle the sign on silicon, and a reference-driver run settles it for D3D (section 7.5).
- **`D3DTSS_MAXMIPLEVEL`** is the *"LOD index of largest map to use (0 == largest)"* (`DDK8/d3dtypes.h:1616`), counted from the top of the chain.
  - The W2K DDK help also says *"the maximum dimension is 2^MAXMIPLEVEL"*. That contradicts its own next clause (*"zero indicates that there is no limit"*) and the header.
  - 3dfx implemented it as an index from the top and passed WHQL DCT 262 "Mip Filter Point & Linear - MaxMipLevel" with it (`W9X/DX/D3D/D6DP2.C` revision notes 25 and 27).
  - Values past the chain clamp to its smallest level. 3dfx added that clamp for F-22 Lightning 3, *"only one LOD per texture"*, PRS 12046 (`VH5/D6DP2.C:6660-6671`).
- **With `MIPFILTER` NONE** the DDK says nothing about either state.
  - 3dfx uses a no-mip tLOD (LODMIN = LODMAX = top, no bias; `VH5/D6MT.C:5621-5626`). Its MAXMIPLEVEL clamp then falls back to the top (`VH5/D6DP2.C:6690-6698`), so both states are ignored.
  - This design keeps that. Probe case H pins it; section 12 Q7 asks what real D3D hardware does.

### 2.4 Glide's conversion: same field, two traps not to copy

- `grTexLodBiasValue` (`GL5/glide3/src/gtex.c:2439-2484`) converts with `_grTexFloatLODToFixedLOD`, defined as `(int)((v + .125F) / .25F) & 0x3F` (`GL5/glide3/src/fxglide.h:3324-3325`).
  - **Trap 1.** C truncates toward zero, so a negative half comes out a quarter short: −0.5 becomes −0.25 and −0.75 becomes −0.5.
  - **Trap 2.** The value is masked to 6 bits *before* the clamp to −0x20…0x1f (`gtex.c:2453-2459`). So +7.9 wraps to −8.0, and +100 wraps to +4.0.
- **Side effect on the OpenGL lane (not this item).** `GLSRC/fxsetup.c:558-572` defaults `FX_LOD_BIAS` to −0.5. Through trap 1 that is programmed as −0.25. `WT/docs/v56k-benchmark-plan.md:1270` still measured that sharper bias as costing up to 9 % in GPU-bound RtCW on this board.

## 5. Design

### 5.1 The arithmetic: `KMD/include/vcr_texlod.h` + `KMD/common/vcr_texlod.c`

These are pure integer functions, beside the texture-address arithmetic they extend. They are compiled `-mgeneral-regs-only`, and a native test compiles the same file.

```c
/* ---- LOD control: D3DTSS_MIPMAPLODBIAS / D3DTSS_MAXMIPLEVEL and D3D's nearest
 * level (G27, Diag\D3DFeat LODCTRL). tLOD bits 17:0 are three 4.2 fields (h5
 * h3defs.h SST_LODMIN/LODMAX/LODBIAS, SPEC 8.77): the TMU adds lodbias to its
 * LOD, clamps the sum to [lodmin, lodmax], takes the level by TRUNCATION, and
 * uses the magnification filter when the sum was clamped at lodmin. */
#define VCR_LOD_NEAREST_Q   2u      /* +0.5 in quarters: nearest level on a truncating TMU */

/* a D3D LOD bias (the float's IEEE bits - no FPU here) in quarters of a
 * level, rounded to the nearest (ties away from zero), clamped to the 4.2
 * field -32..31; NaN, zero and denormals are 0, +-inf the ends */
int vcr_lod_bias_q(vcr_u32 bits);

/* the tLOD of a mipmapped draw. tlod is a texture view's (lodmin = the top,
 * integer; lodmax = the smallest level sampled; bias 0). maxmip levels come
 * off the top (clamped to the chain); lodmin and the bias both get round_q, so
 * the min/mag choice stays at the unbiased LOD 0; the app's bias is added.
 * A tlod whose lodmax is not above its lodmin (one level sampled) comes back
 * unchanged. Bits 18-31 are kept. */
vcr_u32 vcr_tlod_lodctl(vcr_u32 tlod, vcr_u32 maxmip, vcr_u32 bias_bits, vcr_u32 round_q);
```

```c
int vcr_lod_bias_q(vcr_u32 bits)
{
    vcr_u32 e = (bits >> 23) & 0xffu, m = (bits & 0x7fffffu) | 0x800000u, sh;
    int neg = (int)(bits >> 31), q;
    if (e == 0xffu)
        return (bits & 0x7fffffu) ? 0 : neg ? -32 : 31;     /* NaN: no bias; inf: the end */
    if (e == 0)
        return 0;                                          /* zero and denormals */
    if (e >= 130)
        return neg ? -32 : 31;                             /* |bias| >= 8.0 */
    sh = 148 - e;                                          /* bias * 4 = m >> sh, sh 19..147 */
    q = sh >= 32 ? 0 : (int)((m + (1u << (sh - 1))) >> sh);
    q = neg ? -q : q;
    return q > 31 ? 31 : q < -32 ? -32 : q;
}

vcr_u32 vcr_tlod_lodctl(vcr_u32 tlod, vcr_u32 maxmip, vcr_u32 bias_bits, vcr_u32 round_q)
{
    vcr_u32 lodmin = tlod & 0x3fu, lodmax = (tlod >> 6) & 0x3fu, below;
    int q;
    if (lodmax <= lodmin)
        return tlod;                    /* one level: nothing to choose between */
    below = (lodmax - lodmin) >> 2;     /* levels the chain has under its top */
    if (maxmip > below)
        maxmip = below;                 /* past the chain: its smallest level (F-22 rule) */
    lodmin += (maxmip << 2) + round_q;
    if (lodmin > lodmax)
        lodmin = lodmax;                /* never lodmin > lodmax */
    q = vcr_lod_bias_q(bias_bits) + (int)round_q;
    q = q > 31 ? 31 : q < -32 ? -32 : q;
    return (tlod & ~0x3ffffu) | lodmin | (lodmax << 6) | (((vcr_u32)q & 0x3fu) << 12);
}
```

Also add `#define TL_LODBIAS(q) (((unsigned)(q) & 0x3fu) << 12)` to `KMD/include/vcr_3dregs.h`, beside `TL_LODMIN`/`TL_LODMAX` (`:178-179`), and say there that the fields are 4.2.

**Why the rounding goes on LODMIN too.** Let H be the TMU's own LOD (its units put the texture's top level at `top`), D = H − top the D3D LOD, b the app's bias and k the maxmip.
- Hardware level = floor(clamp(H + b + 0.5, top + k + 0.5, lodmax)). Relative to the top that is round(D + b), clamped to [k, smallest]: D3D's nearest level.
- Magnification is chosen when H + b + 0.5 < top + k + 0.5, i.e. D + b < k.
- With k = 0 that is "biased LOD below 0", as D3D defines it (inferred: D3D applies the bias before the min/mag choice, as OpenGL does).
- 3dfx's bias-only rounding magnified only below D + b = −0.5. With mag and min filters that differ (e.g. MAG LINEAR, MIN POINT), the band [−0.5, 0) was drawn with the wrong filter. Probe case K tests this.
- **For k > 0 there is an inherent deviation.** One register field both clamps the top level and decides the filter, so the band [0, k) is magnified on the VSA-100, where D3D would minify. That only shows when the two filters differ. 3dfx had the same.

### 5.3 The HAL: `KMD/display/vcrdd_d3d.c`

1. **`view_of` (`:840-843`) is the only call site.**
   ```c
   static BOOL view_of(VCR_PDEV *pd, const DWORD *tss, PDD_SURFACE_LOCAL s, tmu_view *v)
   {
       BOOL ok = pd->tex_ext ? tex_view_ext(pd, tss, s, v) : tex_view(tss, s, v);
       /* Diag\D3DFeat LODCTRL (G27): this stage's MIPMAPLODBIAS and MAXMIPLEVEL and
        * D3D's nearest level, into THIS view's tLOD - each stage's values follow
        * its texture to its TMU (two stages: stage 0 on TMU1, stage 1 on TMU0) */
       if (ok && (pd->d3dfeat & VCR_D3DFEAT_LODCTRL) && tss[D3DTSS_MIPFILTER] > D3DTFP_NONE)
           v->tLOD = vcr_tlod_lodctl(v->tLOD, tss[D3DTSS_MAXMIPLEVEL],
                                     tss[D3DTSS_MIPMAPLODBIAS], VCR_LOD_NEAREST_Q);
       return ok;
   }
   ```
   - It works on the tLOD the view already produced. So G07's guard, which lowers LODMAX to the levels really packed, is honoured with no coordination: it runs inside the view.
   - `tex_view` and `tex_view_ext` are not touched.
2. **`prim_caps` (`:2013-2046`)** takes the flag: `prim_caps(D3DPRIMCAPS *c, ULONG lodctl)`.
   - When the flag is set it adds `D3DPRASTERCAPS_MIPMAPLODBIAS`, for TriCaps and LineCaps both (`:2071-2072`).
   - Nothing else in the caps changes. The live RasterCaps becomes `00102191`.
3. **The one-shot LOD-state log (default-on, log only).**
   - In the `TEXTURESTAGESTATE` case (`:1605-1608`), when stage 0/1 changes state 19 or 20 to a non-zero value not seen before in this context, the HAL logs one INFO event, 513 with a new what (`lodstate`): stage, state, value, quarters, and "LOD control on/off".
   - At most 8 per context. A `c->lodstate_sets` count goes into a second ctx_free line (the first is full at 95 characters), together with the SETTEXLOD count.
   - This measures the section 4 question (raw −0.5 or `_ftol2` 0) on any build, armed or not. A wrapped ring keeps the ctx_free line (G76).
4. **SETTEXLOD gets its own case before `default:`, with the parse unchanged.**
   - `NEED(n * sizeof(D3DNTHAL_DP2SETTEXLOD)); c->settexlod += n;`
   - Then one WARN per context: "SETTEXLOD handle %u lod %u: not applied - sent only to a driver that manages textures". Then `p += …`.
   - Its line in `rec_size` (`:1564`) goes, because the explicit case replaces it.
5. **Nothing in `compute_regs`, `vcrdd_3d.c`, the flip path or the target path changes.**

### 5.4 `MIPFILTER` LINEAR until G26

- Today LINEAR is drawn as nearest-level (truncated). Trilinear is G26.
- The design passes `VCR_LOD_NEAREST_Q` for LINEAR as well. The single level closest to a trilinear blend at LOD L is round(L), not floor(L) (inferred).
- When G26 lands, it chooses the LINEAR value in one place: 0 for true trilinear, or a dither-compensated quarter count for LOD dither. `vcr_tlod_lodctl`'s `round_q` parameter is that seam. G26's two-TMU split keeps `lod_odd`/`lod_tsplit` (bits 18-19), which the function leaves alone.

### 5.5 SETTEXLOD: why it is not implemented

- **The DDK says so.** *"Used only for driver managed textures. … dwLOD controls the maximum miplevel loaded into video memory."* (`W2KDDK` d_grafx.chm, `D3DNTHAL_DP2SETTEXLOD`.) Driver management is opted into with `DDCAPS2_CANMANAGETEXTURE` (d_grafx.chm, driver-managed textures page). Our `dwCaps2` does not set it (`KMD/display/vcrdd_ddraw.c:105`).
- **XP's d3d8.dll agrees.** `IDirect3DBaseTexture8::SetLOD` is at `XPRT/d3d8.dll` `0x6d9fb860` (read from the binary, not executed):
  - it clamps the LOD to the level count;
  - if the texture has a resource-manager object (`+0x24`; that meaning is inferred), it calls the manager (`0x6d9fb889` → `0x6d9ef3c0`);
  - only a `D3DPOOL_MANAGED` texture *without* one reaches the driver wrapper (`0x6d9fb8b0` → `0x6d9d7f70` → DDI slot `0xe0` → `0x6d9e3150`, which writes opcode `0x2b` = SETTEXLOD).
  - On a HAL without driver management every managed texture has a manager object (inferred). So the runtime keeps the LOD by what it gives the driver.
- **This is cheap to confirm on silicon.** The `setlod` check (section 7.3) must draw the right level with no driver change, and the new counter must stay 0.
- **If SETTEXLOD ever arrives**, the runtime thinks we manage textures. It may then have loaded only levels ≥ dwLOD into a full-size chain. The WARN says so. That would be a new gap, not this one.

### 5.6 Plumbing: `Diag\D3DFeat`

- **Follow the sibling designs' shape** (G15 §5.3, G08, G16):
  - the miniport reads `x->d3dfeat = VcrDiagGet(L"D3DFeat", 0)` at boot (`KMD/miniport/vcrmp.c`, beside `:238-244`);
  - `vcr_u32 d3dfeat` is appended to `vcr_info` (`KMD/include/vcr_ioctl.h`), size-checked by the reader;
  - `VcrDd2dInit` (`KMD/display/vcrdd_2d.c:442-471`) sets `pd->d3dfeat` (0 from an older miniport) on every chip;
  - one "armed" INFO line.
- **Whichever D3DFeat item lands first adds the word.** This item adds only `#define VCR_D3DFEAT_LODCTRL 0x400u`.
  - Bit 10 is proposed. The siblings use 0 (G15), 1 (G08), 4 (G16) and 6-8 (G05/G12/G13). The integrator assigns the number.
- **Read at boot**, because the bit changes caps. A D3D8 application reads RasterCaps at the desktop's PDEV and must see the same at its fullscreen PDEV. That is the D3D32/D3DBigTex rule (`REP/runtime.md` §2: the runtime re-reads caps at every DirectDraw enable).
- **The bit is chip-independent.** The three tLOD fields are the Voodoo family's: the Banshee/Voodoo3 header has the same `SST_LODBIAS` field at bits 17:12 (`WT/voodoo-cleanroom/build/retro3dfx-glide/glide3x/h3/incsrc/h3defs.h:269-270`). Only the VSA-100 can verify it, though: 86Box gets LOD selection wrong (`KMD/tools/d3dprobe.c:47-51`).

### 5.7 The old path (switch off)

- `vcr_tlod_lodctl` is not called, and `prim_caps` gets 0. So tLOD, RasterCaps and every other register are byte-identical to today on both texture paths and on every chip.
- The SETTEXLOD case parses exactly what `rec_size` parsed (`n * 8` bytes).
- The new logging is INFO/WARN only, at most 8 + 1 lines per context.

## 6. Gating

- **Default OFF** behind `Diag\D3DFeat` bit `LODCTRL` (0x400 proposed). It is latched at boot, and armed alone (one Diag change per clean boot).
- **Not default-on at landing**, for three reasons:
  - It changes what every mipmapped title samples, by half a level softer where no bias is sent.
  - It adds a cap that games test.
  - The fractional LODMIN it relies on has never run on VSA-100 silicon: 3dfx always used integer LODMIN.
- **Graduates to default-on after one supervised boot** (section 9, Boot B) in which `lodbias`, `lodscan` and `setlod` pass and the default gate is unchanged. It is a pure correctness fix with a probe proof.
  - The mechanism is the D3DFeat owner's call (section 12 Q9).
  - A plain "absent value means LODCTRL on" default would silently drop LODCTRL on any box that sets D3DFeat for another bit. So a per-feature kill bit (for example `Diag\D3DFeatOff`) is the safer shape.
- **Default-on from the first build:** the one-shot `lodstate` log, the SETTEXLOD counter and WARN. These are log-only and pinned by a Python test, like Phase 0 of the plan (`REP/hal.md` §10).

## 7. d3dprobe tests (`KMD/tools/d3dprobe.c`)

- **These are explicit-only checks, like `mip`**: silicon only, because 86Box's LOD is wrong (`d3dprobe.c:47-51`). The default list at `:1247` does not change.
- **Each check draws one frame and reads the quad's centre pixel `(128,128)`** with `expect(…, tol 12)` (`:328-344`).
- **The scene is analytic**:
  - a 256x256 R5G6B5 `D3DPOOL_MANAGED` chain of 9 levels, each level one solid colour: L0 red, L1 green, L2 blue, L3 yellow, L4 magenta, L5 cyan, L6 white, L7 grey, L8 orange;
  - 256x256 works on both texture paths (`VcrDdD3dCreateMipChain` places a 16-bit chain up to 256 without D3DBigTex);
  - quads cover [32, 224) with `quad_t` (`:260-266`) and uv = 0.75 · 2^LOD, so the texel:pixel ratio sets the LOD;
  - MIN, MAG and MIP are POINT unless a case says otherwise.
- **LODs use fractions .15 and .85, never .5.**
  - A piecewise-linear log2, the cheap hardware approximation, puts 1.15 at 1.11 and 1.85 at 1.80 (inferred model).
  - So each expected level holds with ≥ 0.3 of margin on either side whatever the silicon's approximation is. `lodscan` measures the real one.

### 7.2 `lodscan` (the measurement that decides the rounding)

- **What it draws.** Chain 1, POINT everywhere, bias 0. LOD runs from −0.5 to 3.0 in steps of 1/32: 113 frames.
  - Each frame's centre pixel is classified as the nearest level colour. A distance above 40 counts as "garbage" and fails.
- **What it reports.** The first LOD showing level ≥ 1, ≥ 2 and ≥ 3 (`"transitions":[…]`), next to D3D's `[0.5, 1.5, 2.5]` and the truncating `[1.0, 2.0, 3.0]`.
- **Pass:** every transition within ±0.15 of D3D's, and the levels monotonic.
- **On today's build** it should fail at about [1.0, 2.0, 3.0]. That is the first-ever measurement of the truncation, and section 9 step 0 runs it before any code exists.
- **The offset of the transitions from the ideal values is the silicon's LOD-approximation error.** It confirms the margins used by `lodbias`.

| J1 | `IDirect3DTexture8_SetLOD(tx, 1)`, MIP NONE | −1.0 | L1 green |
| J2 | `SetLOD(2)`, MIP POINT | 0.15 | L2 blue |
| J3 | `SetLOD(1)` + MAXMIPLEVEL 2, MIP POINT | 0.15 | L2 blue (D3D: the larger of the two) |

- J1 and J2 must pass on any build: they show the runtime's resource manager hands the driver a chain that starts at the LOD. The new SETTEXLOD counter must read 0.

## 10. Risk to proven paths

- **The default 16 bpp path, and every path with the switch off:** none. There is no tLOD, caps or register change. Only the parse-equivalent SETTEXLOD case and the INFO/WARN logs are new. A Python test pins this.
- **Switch on, rendering.**
  - Only tLOD bits 17:0 change, and only for driver-placed chains with ≥ 2 levels drawn with MIPFILTER > NONE.
  - A wrong encoding samples the wrong level (visible, recoverable). It cannot hang or corrupt anything: there is no new write, no new register, no FIFO change, no new ordering, and texBaseAddr and textureMode are unchanged.
  - The fractional LODMIN is new to this silicon. Case K verifies it, and the fallback is one line.
- **Switch on, looks.**
  - Titles that send no bias get distant textures about half a level softer than today. That is D3D-correct and is what 3dfx shipped (`LB_HALF`).
  - The user may perceive it as blurrier. Red Faction's −0.75 and UE2's raw −0.5 give back roughly today's sharpness.
- **G06/G07 exposure.** Smaller mip levels get sampled sooner. A chain whose small levels are misplaced (G07) shows its garbage more. So in-game arming waits for G07's guard.
- **Glide/OpenGL coexistence:** unchanged.
  - The HAL already overwrites TMU0's whole tLOD (and TMU1's in two-stage draws) today. Only the value differs.
  - Glide writes tLOD from its shadow in `grTexSource` before it textures (inferred from the h5 `gtex.c` register group), so a D3D bias cannot leak into Glide.
  - The reverse already holds: MesaFX's −0.25 never reaches D3D.
- **SLI:** none today (D3D is one chip). Under G51 the same tLOD goes to every chip. 3dfx's per-chip bias offsets need AA, which is off by the user's choice.
- **The flip path:** untouched.
- **Performance.**
  - Neutral to slightly positive: the rounding uses smaller levels sooner, so fewer texels are fetched. A game's negative bias costs a little. The sharper MesaFX bias measured up to 9 % in GPU-bound RtCW (`WT/docs/v56k-benchmark-plan.md:1270`).
  - D3D on `.124` is transport-bound today (UT2003 flyby 9.41 fps), so this is unlikely to show.
- **Caps.** Reporting MIPMAPLODBIAS may switch a game onto a path that uses the bias (UE2 prints "Supports LOD biasing"). That path then works. It does not draw anything new.

## 12. Open questions

1. **Does the VSA-100 truncate the LOD for point mip?** 3dfx's comment says yes; `lodscan` in step 0 measures it. If it already rounds, set `round_q` to 0.
2. **Is a fractional LODMIN honoured for the min/mag choice (case K)?** If not, fall back to integer LODMIN, and the threshold moves by half a level when MAG ≠ MIN.
3. **How large is the silicon's LOD-approximation error?** It is the offset of `lodscan`'s transitions from 0.5, 1.5 and 2.5.
4. **Which bias does UE2 actually send in game?** Raw −0.5 at device set-up, or `_ftol2` → 0.0 per texture state? The Boot A ring answers it.
5. **Does XP's D3D8 runtime forward `D3DTSS_MIPMAPLODBIAS` to a HAL that does not report the cap?** Boot A's probe bias cases plus the `lodstate` log answer it.
6. **After `SetLOD`, does the runtime rebase MAXMIPLEVEL for its smaller device copy (`setlod` J3)?** If not, the HAL cannot correct it. No staged title is known to combine the two.
7. **What does real D3D hardware do with MAXMIPLEVEL and bias under MIPFILTER NONE (case H)?** Run it on a reference driver. This design follows 3dfx: inert.
8. **The W2K DDK help reverses the bias sign and calls MAXMIPLEVEL "2^n".** The headers, 3dfx, Glide and the hardware say otherwise. Probe cases C, D, F and G settle it on silicon, and section 7.5 settles it for D3D itself.
9. **The D3DFeat bit number and the graduation mechanism** are the integrator's. Prefer a per-feature kill bit over changing the DWORD's absent-value default.
10. **Should LINEAR keep the +0.5 until G26?** This design says yes. The G26 owner may choose LOD dither as the stand-in instead.
11. **Does the DX7 runtime (`d3dim700`, DX6/DX7 titles) ever send SETTEXLOD to a non-managing driver?** d3d8.dll does not (section 5.5). The counter will show it for the others.
12. **A user-tunable global D3D LOD bias** (3dfx's registry `LOD_BIAS`) is not proposed: the user chose stock settings.

## 13. Related observations for other gaps (not in this item's scope)

- **An idle TMU.** 3dfx parks an unused TMU at LODMIN = LODMAX = 8 (a 1x1 level) "for performance reasons" (`VH5/D6MT.C:5663-5670`). Our single-texture draws leave TMU1 with whatever textureMode and tLOD it last had (`KMD/display/vcrdd_3d.c:119-126` writes TMU1 only in two-stage draws). That is a candidate for G46/G53 measurement.
- **The OpenGL lane.** `FX_LOD_BIAS`'s documented −0.5 default is programmed as −0.25 through Glide's conversion (section 2.4). If the benchmark decision on that bias (`WT/docs/v56k-benchmark-plan.md:1285`) is revisited, the value actually in effect is −0.25. This belongs in the clean-room OpenGL notes, not here.
