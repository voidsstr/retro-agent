## 1. Verdict

**The gap is real, fixable, and small. It also has a third hole the gap text does not name, and the fix
must avoid one hazard it would otherwise create.** Everything below was verified by reading the code.

| # | hole | where | status today |
|---|---|---|---|
| 1 | A `Dd_Blt` into a video-memory texture is never marked dirty. This covers the 2D-engine copy and fill, `clipped_blt`, and **`Dd_Blt`'s own CPU fallbacks** (`memset`/`memmove` after `VcrDd2dSync`, `vcrdd_ddraw.c:510-520, 546-557`). The fallbacks write video memory with no Unlock, so nothing marks them either. | `vcrdd_ddraw.c:408-466` (exit `:463`), `:468-565` (exit `:562`) | named in the gap; the CPU fallback is new |
| 2 | Rendering into a texture is never marked: triangles, DP2 `CLEAR` and `Clear2` fastfills into a `DDSCAPS_TEXTURE\|3DDEVICE` target. | `SETRENDERTARGET` `vcrdd_d3d.c:1725-1753`; `clear_rects :1408-1421`; `D3d_Clear2 :1873-1900` | named in the gap |
| 3 | **Dirty while not bound.** `prepare()` consults the dirty flags only when the global write counter moved, and only for the textures bound at that moment (`vcrdd_d3d.c:1327-1335`). If the next draw is untextured, the counter is consumed with nothing to flush. Untextured draws write no TMU register (`vcrdd_3d.c:113-130`), so TMU0 keeps the old texture's `texBaseAddr`. Re-binding that texture then writes the same value, which does not flush (row "SPEC" below). Its cached texels stay stale. **This applies to CPU writes (Unlock, TEXBLT) as well.** | `vcrdd_d3d.c:1322-1336` | **new**; G18 §4.2 noticed the same shortcut for its own surfaces |
| 4 | **A hazard the fix itself must avoid.** `VcrDd3dTexFlush` reads one dword of the texture with the CPU and writes it back through the texture port, so that 86Box's cache sees a write (`vcrdd_3d.c:263-267`). It reads **without waiting for the engine**. For a texture the 2D or 3D engine is still writing, it can read the old dword and write it back over the new texels. Today it only ever runs after CPU writes, which have already landed. Marking engine writes would expose it. | `vcrdd_3d.c:253-270` | latent until holes 1-2 are marked |

**What the hardware requires (SPEC §20.3, L6182-6190):** *"Napalm needs explicit software intervention to
maintain cache coherency."* The sequence is:
1. a 2D NOP "pixel flush";
2. *"explicitly flush the texture cache, by **changing** the value of texBaseAddr … write the inverse …
   then re-write texBaseAddr with a correct value"*;
3. another 2D NOP.

Our `VcrDd3dTexFlush` is exactly that sequence, plus a 3D `nopCMD` between the two writes, as Glide does
(`vcrdd_3d.c:258-262`; `G5/fxglide.h:1600-1611`, `G5/gsst.c:1384-1399`).

**Writing the same value is not a flush.** Glide says so for download coherency: *"it is perfectly legal to
source once and download over and over again … Unconditionally flush"* (`G5/gtexdl.c:1650-1662`). Our HAL
re-sends `texBaseAddr` at the first triangle of every DP2 call (`w.prepared = 0`). That re-send writes the
same value whenever the same texture stays bound, so it does not save us (inferred from SPEC's wording and
Glide's comment; **measured in boot A, §7**).

**The engines order themselves; only the cache needs software.** SPEC `miscInit1` bit 16: *"2D will not wait on pending 3D operations"* when set;
bit 17: *"3D will not wait on pending 2D operations"* when set. Both default to 0 (L5836-5837). Our
miniport only read-modify-writes `miscInit1` (`miniport/vcrmp_hw.c:189-195, 574`;
`miniport/vcrmp_sli.c:380-449`), so a triangle after a blit waits for the blit (inferred: nothing sets
those bits). The hazard is the **TMU cache**, not the ordering of memory writes. SPEC also has a silicon debug knob,
`trexInit1` bit 29 `always_cache_inv` ("always cache invalidate each triangle", L4009). It is **not used**
here: `trexInit1` also holds FIFO stall levels and clock-delay fields (L3983-3993), and a
read-modify-write from the display driver could wedge the TMU interface.

**What 3dfx's HAL did (vendor-30):**
- It flushes **both TMUs at every texture-state send** (`VH5/D6DP2.C:6709-6714, 6762-6767`; per-chip at
  `:6571-6573`; added "for PC99 TextureSizes & MultiTexture failures", `:256-258`).
- `SetRenderTarget` sets `_D3(lastContext) = 0` (`VH5/D7DP2.C:138`), which re-sends all texture state with
  that flush at the next draw (`VH5/D6DP2.C:6373-6386`). So render-to-texture was covered.
- Unlock of a texture flushes (`VH5/DDSURF.C:2001-2012`, "fix for Texture Load - Video failures").
- A 2D `Blt` into a texture only sets `BltToTxtrInFifo` (`VH5/DDBLT32.C:444-450, 2468-2472`). That flag
  makes the next `Lock` drain the engine (`VH5/DDSURF.C:1612-1620`); it flushes no TMU. So the vendor
  closed holes 2 and 3 by brute force and left hole 1 to chance.

**Why not copy the vendor's rule** (flush at every texture-state send):
- On our PIO transport, every register write is an uncached store into a 31-entry PCI FIFO (G47/G48).
  A flush is 7 such writes plus two 2D NOPs, per TMU.
- We re-send state at every DP2 call and every change (G53). Flushing there would add roughly 14 writes
  per state send, and the TMU would refetch every texel after each one.
- 3dfx paid that over a command FIFO. We would pay it in CPU time, in a HAL that already spends 116.7 ms
  of a 123 ms UT2003 frame in DrawPrimitive (G46).
- So the fix is targeted. The vendor rule is kept only as a **debug bit** (§3.8), for diagnosis.

**86Box (the Voodoo3 test bed) fails the old path every time, which makes the bed a real proof.**
- Its texture cache is decoded, looked up by base address (`86B/voodoo_texture.c:530-547`).
- It is invalidated only by texture-port writes (`:641-651`), CMDFIFO packet 5
  (`86B/vid_voodoo_fifo.c:710-720`) and `agpMoveCMD` (`86B/vid_voodoo_banshee.c:1709-1717`).
- No 2D blit, 3D render, LFB write or base change invalidates it.
- So on the bed, today's path shows stale texels for holes 1-3, every time. The flush's one-dword
  port write-back is what makes the fix visible there. That write-back is also why hazard 4 must be
  handled, not dropped.

**How often it bites on silicon is unknown, and probably not often.** Most frames bind other textures in
between, and every base *change* flushes. The window is a texture that stays bound, or comes straight
back, across its own modification. Examples: a texture-target cleared or drawn untextured and then sampled; a
vidmem→vidmem `Blt` into the last-bound texture; a font page updated during untextured HUD draws. Which
staged titles hit it is unmeasured. The always-on counters in §3.5 answer it.

## 2. What the code does today

- **Marking.** `VcrDdD3dTexWritten(s)` (`vcrdd_d3d.c:603-614`) sets `SF_DIRTY` (0x4) in the surface-local
  `dwReserved1` (magic `SF_MAGIC`) and bumps the global `g_tex_writes`. It has exactly three callers:
  `Dd_Unlock` (`vcrdd_ddraw.c:679`) and both TEXBLT branches (`vcrdd_d3d.c:1514, 1533`). A HEL blit and a
  GDI `GetDC` on a texture reach it through Unlock. vcrdd implements no `DrvDeriveSurface`, so dxg locks
  and unlocks the surface for GDI.
- **Checking.** `prepare()` runs at every triangle. When `g_tex_writes != c->tex_writes_seen`
  (`:1327`), it recomputes the bound set if state is dirty and calls `flush_written` on
  `tex_surf0`/`tex_surf1` (`:1331-1332`).
- **Flushing.** `flush_written` (`:1287-1320`) walks up to 12 levels through `next_mip`. If any level is
  dirty, it clears the flags and calls `VcrDd3dTexFlush(base, addr)`:
  - the default path passes `addr = fpVidMem`;
  - the VSA-100 path passes `vcr_tex_writeback_addr()`, which is `~0` (no write-back) except for a 16 bpp
    texture of at most 256 below 16 MB (`include/vcr_texlod.h:93-103`, `common/vcr_texlod.c:89-92`).
- **The flush.** 2D NOP; `texBaseAddr` = `~base` broadcast to both TMUs; `nopCMD`; `texBaseAddr` = `base`;
  2D NOP. Then, unless `Diag\TexPortFlush = 0` (`no_texport`), **a CPU read of the dword at `addr` and its
  write through the texture port** (`vcrdd_3d.c:253-270`).
- **The proven ground.** All of this is the 09-26 `8c190d3` fix. `d3dprobe tex2add` went grey → green on the
  86Box Voodoo3 (`reports/history.md:119`). Since then the flush has run on `.124` for every managed-texture
  upload (Lock/Unlock) and TEXBLT.

## 3. The fix

### 3.1 One switch: `Diag\D3DFeat` bit TEXCOH

- **Bit 5 (`0x20`, `VCR_D3DFEAT_TEXCOH`).** hal.md §10 numbers Phase 2 as bits 0-5, and item 6 (alignment
  and coherency) is bit 5. G21 took its alignment half onto its own switch (`D3DTexPlace`), so bit 5 is
  free. Siblings: G15 bit 0, G08 bit 1, G22 bit 2, G25 bit 3, G16 bit 4. The plan owner fixes the number in
  `include/vcr_d3dfeat.h`.
- **All chips.** The cache rule is the same on Banshee, Voodoo3 and VSA-100 (SPEC §3.7, L662: "additional
  flushing code required around texture downloads"; Glide's h3 and h5 share `GR_TEX_FLUSH_*`). So
  `pd->texcoh` is **not** gated on `pd->napalm`. That is what lets the 86Box Voodoo3 bed prove it first.
- **Read at boot**, as a positive flag (absent = off). It uses the shared `D3DFeat` plumbing: the
  `vcr_info.d3dfeat` word appended after the last field (G05 §4.2). Whichever D3DFeat item lands first
  creates that plumbing.

### 3.2 Marking: one entry point for engine writes

A new function sits beside `VcrDdD3dTexWritten`, which stays as it is:

```c
/* vcrdd_d3d.c (G37): a video-memory texture the 2D engine (Dd_Blt / clipped_blt, or Dd_Blt's own
 * CPU fallback) or the 3D engine (a texture as the render target) wrote. Counted always; marked
 * only with Diag\D3DFeat TEXCOH - unarmed, nothing changes but a counter. */
void VcrDdD3dTexEngineWritten(VCR_PDEV *pd, PDD_SURFACE_LOCAL s, ULONG who);
```

- **It does nothing for a surface that is not a video-memory texture.** It checks `DDSCAPS_TEXTURE` and
  `in_vidmem`, as `VcrDdD3dTexWritten` does. That covers the back buffer, the primary, Z, offscreen plain
  surfaces and system memory, so flips, windowed presents and 2D-only DirectDraw titles never reach the
  rest.
- **Armed,** it sets `SF_DIRTY | SF_ENGINE`, adding the magic if absent, exactly as `VcrDdD3dTexWritten`
  does. Then it bumps `g_tex_writes`.
- **New surface flag `SF_ENGINE 0x10u`:** *the dirty write was the engine's.*
  - Taken values: `SF_MIP_TOP` 0x1, `SF_MIP_LVL` 0x2, `SF_DIRTY` 0x4. G07/G21 plan `SF_PAD8` 0x8.
  - A compile-time check pins `SF_DIRTY == VCR_TC_DIRTY` and `SF_ENGINE == VCR_TC_ENGINE` (§3.6).

**Call sites (four, all after the write was issued):**

| hole | call | where |
|---|---|---|
| 1 | `VcrDdD3dTexEngineWritten(pd, d, VCR_TW_BLT)` before `pd->dd_blts++` | `clipped_blt` (`vcrdd_ddraw.c:463`) and `Dd_Blt` (`:562`). Those are the only two `DDHAL_DRIVER_HANDLED` + `DD_OK` exits. The flip-pending `DDERR_WASSTILLDRAWING` exit (`:500-503`) writes nothing and is not marked. A `NOTHANDLED` blit goes to the HEL, whose Unlock marks it already. |
| 2 | `VcrDdD3dTexEngineWritten(c->pd, c->rt, VCR_TW_RENDER)` when a `SETRENDERTARGET` **switches away** from a texture (`c->rt && c->rt != rt`, before `c->rt = rt;`) | `vcrdd_d3d.c:1735`. The mark lands inside the same DP2 walk, so the next `prepare` that samples the old target flushes it. This covers the D3D8/9 pattern "render into T, switch back, bind T, draw" when it all sits in one command buffer. |
| 2 | the same call for the **current** target at the end of `D3d_DrawPrimitives2` (after `walk`, `:1867`) and of `D3d_Clear2` (after its loop) | This covers a target that is never switched away from: a DX7 title that creates a second device on a texture surface (inferred), and a context that is rendered into while another samples. It costs one caps test per call. The common target is the back buffer, which returns at once. |

**Why mark at switch-away and at call end, not per triangle.** No sampling of a texture is defined while it
is the target. So the first point where a stale cache matters is after a switch, or in another context.
Marking per triangle would add a store to the hottest path for nothing.

### 3.3 The flush syncs first when the engine wrote the texture (hazard 4)

In `flush_written`, the level walk ORs each level's `SF_DIRTY | SF_ENGINE` into `fl` and clears both. Then,
after `addr` is computed as today (both branches):

```c
if (vcr_texcoh_plan(fl, !c->pd->no_texport && addr != ~0u) & VCR_TC_SYNC)
    VcrDd2dSync(c->pd);         /* the engine's write lands before the CPU reads texel 0 back */
VcrDd3dTexFlush(c->pd, base, addr);     /* unchanged */
```

- **When `VcrDd2dSync` is called.** It is called only when an engine write is pending AND the flush will
  read a texel back with the CPU.
- **What it costs.** `VcrDd2dSync` is status reads only, and it returns at once when nothing is queued
  (`vcrdd_2d.c:118-131`).
- **When there is no sync.** The VSA-100 path does no write-back for a 32-bit, DXT, TBIG or above-16 MB
  texture. There the flush is the documented `texBaseAddr` flip alone, and the hardware's own 2D NOP pixel
  flush orders it after the engine's write (SPEC §20.3 rule 1).
- **`VcrDd3dTexFlush` is not touched.**
- **Unarmed, `SF_ENGINE` is never set,** so `plan` is FLUSH whenever the texture is dirty. That is today's
  behaviour, write for write.

### 3.4 Dirty-at-bind (hole 3)

In `prepare`'s state-send path, right after `compute_regs(c)` and before `VcrDd3dTarget`/`VcrDd3dState`:

```c
compute_regs(c);
if (c->pd->texcoh) {            /* G37: a texture written while it was not bound */
    flush_written(c, c->tex_surf0);
    flush_written(c, c->tex_surf1);
}
```

- **When it runs.** At every state send while armed: the first triangle of each DP2 call, and every
  state change. That is never per triangle.
- **When it costs nothing.** A texture with no dirty level costs only the level walk (12 levels at most).
- **After a flush.** `VcrDd3dState` writes the correct per-TMU bases right after it, so the broadcast
  writes the flush makes to both TMUs (`vcrdd_3d.c:259-261`) are put right.
- **The counter path at `:1327-1335` is left exactly as it is.** It still catches a write while a texture
  stays bound and no state is re-sent, such as a TEXBLT in the middle of a walk.
- **Cheaper variant, if a measurement ever asks for it:** remember the bound surfaces of the last state
  send per context, and walk only when they change.

### 3.5 Counters and logs: observation even when unarmed

- **Counted always, with no hardware access and no new log event:**
  - `g_tex_blt2d`: blits into video-memory textures, since boot;
  - per context `c->rt_away`: switches away from a texture render target.
- Both are appended to the existing "context %u gone" INFO line (`vcrdd_d3d.c:1212-1215`). The line's event
  arguments do not change, and no tool parses its text (checked: no match under `WT/tests`, `KMD/tools`,
  `WT/scripts`).
- **The point:** an ordinary, unarmed play session tells us which staged titles exercise holes 1 and 2.
  This is the measurement the priority (§9) waits on, and the per-gap counter G76 asks for.
- **Armed only, rate-limited** to the first 16 per boot, because G52 says every `VcrDd()` is an IOCTL:
  event 513 with a new sub-code. It is provisionally **30**: 21-23 are `log_combo`, and 24-29 are contended
  by G05/G16/G24. The arguments are `b` = who (1 blt, 2 render), `c` = `fpVidMem`, `d` = `w<<16|h`. The
  armed boot then names its surfaces.
- **The armed line.** Boot logs the D3DFeat line (the shared "armed" event), with "texture coherency after
  2D blits and render-to-texture".

### 3.6 The decision header: `include/vcr_texcoh.h` (new, Win32-free, host-tested)

It follows `vcr_rtfmt.h`'s pattern: `static __inline` functions, integer only, compiled as is by the HAL and
by `tests/native`.

```c
#define VCR_TC_DIRTY   0x4u    /* == SF_DIRTY: written since the TMU last looked */
#define VCR_TC_ENGINE  0x10u   /* == SF_ENGINE: the 2D/3D engine wrote it */
#define VCR_TW_CPU     0u      /* Unlock (runtime, HEL, GDI), TEXBLT's memcpy */
#define VCR_TW_BLT     1u      /* Dd_Blt / clipped_blt, incl. Dd_Blt's CPU fallback */
#define VCR_TW_RENDER  2u      /* triangles or a fastfill into a texture target */
#define VCR_TC_FLUSH   1u
#define VCR_TC_SYNC    2u

/* the flags a write sets; 0 = none. Unarmed only the CPU marks (8c190d3) */
static __inline unsigned vcr_texcoh_mark(unsigned who, int vidmem_texture, int armed)
{
    if (!vidmem_texture) return 0;
    if (who == VCR_TW_CPU) return VCR_TC_DIRTY;
    return armed ? VCR_TC_DIRTY | VCR_TC_ENGINE : 0;
}

/* before a draw samples it: from the OR of its levels' flags, and whether the flush will read a
 * texel back with the CPU (TexPortFlush on and an address the write-back takes) */
static __inline unsigned vcr_texcoh_plan(unsigned levels_or, int writeback_reads)
{
    if (!(levels_or & VCR_TC_DIRTY)) return 0;
    return VCR_TC_FLUSH | ((levels_or & VCR_TC_ENGINE) && writeback_reads ? VCR_TC_SYNC : 0);
}
```

### 3.7 Caps, passes, and the old path

- **Caps: none change.** This is coherency, not a feature. No D3D caps change, no DirectDraw caps change,
  and there is no format change.
- **Passes: single pass.** It adds no register field. It reuses the proven flush sequence at new trigger
  points, plus one `VcrDd2dSync` before an engine-written texture's write-back.
- **Unarmed (the default):**
  - `vcr_texcoh_mark` returns 0 for BLT/RENDER, so no surface flag is set and `g_tex_writes` does not move;
  - the dirty-at-bind check is not compiled into the path (`if (c->pd->texcoh)`);
  - `plan` never yields SYNC;
  - the flush runs for exactly the textures, at exactly the points, it does today.
  - The only difference is two numbers appended to the context-gone log text.

### 3.8 Optional debug bit: 3dfx's rule, for diagnosis only

- **The switch.** `VCR_D3DFEAT_TEXFLUSHALL` is a debug bit allocated from the top, provisionally bit 31.
  It never graduates and it does not depend on TEXCOH.
- **What it does.** In `prepare`'s state-send path, for each textured TMU in `c->regs`, it calls
  `VcrDd3dTexFlush(pd, texBaseAddr[01], ~0u)`. That is the `texBaseAddr` flip only, with no write-back, so
  there is no CPU read and no sync.
- **Silicon only.** 86Box's decoded cache ignores base flips.

**What it is for:**
- **Validating TEXCOH.** A probe that passes under FLUSHALL but fails under TEXCOH means some writer is not
  marked.
- **A one-boot A/B for the "stale texels" hypotheses** of G06 (its §3.4 step 5, "TMU cache staleness"), G17
  and G18. If UT2004's block noise changes under FLUSHALL, the cache is involved. If it does not, the cache
  is ruled out at the cost of one boot.
- **Its cost:** about 7-14 PIO writes per state send. Measure fps in that boot, but do not ship it.

## 4. Gating

- **Default OFF**, behind `Diag\D3DFeat` bit 5 (TEXCOH), read at boot. With the bit off, the proven path
  is unchanged in register traffic, allocation and flush points (§3.7).
- **Arming:** `REGWRITE HKLM SYSTEM\CurrentControlSet\Services\vcrmp\Diag D3DFeat REG_DWORD 32`
  (OR it into any bits already set). Read it back with `REGREAD` on the **key**. Then check activation and
  reboot with `scripts/fleet/safe-reboot.py`. One Diag change per clean boot.
- **Is it safe to land default-on? Not on day one, but it is the clearest graduation candidate in Phase 2.**
  - **The case for:** it is a pure correctness fix. Its only hardware actions are the flush sequence that
    has run on `.124` since 09-26, at new trigger points, and a status-read idle wait. No caps change. Every
    D3D title benefits, at a cost bounded by how often textures are written by the engine.
  - **The case against:** a `VcrDd2dSync` inside the DP2 walk at a new point, on silicon, has not run. It
    is the same wait every `Lock` and TEXBLT already does, but the project rule is one supervised clean
    boot first.
  - **Graduation:** after boot B (§7) passes, flip the default in its own commit, with its test, using the
    plan's shared D3DFeat convention (a default mask or a `D3DFeatOff` kill mask, G05 §4.1). TEXCOH then
    becomes a kill switch.
- **The debug bit (§3.8)** is never armed together with another change and never graduates.

## 5. d3dprobe tests (`KMD/tools/d3dprobe.c`)

**Shared rules for all of them:**
- **Texture shape.** Each texture is 16x16 R5G6B5, small enough that its 512 bytes fit any plausible TMU
  cache (inferred), so stale lines survive the whole interval.
- **How it is drawn.** The quad covers `[Q0,Q1) = [32,224)` (`:149-151`), so each texel is 12x12 pixels.
  Sampling is SELECTARG1 TEXTURE, POINT/POINT/NONE, CLAMP.
- **Probe texels.** The whole first row (texels 0..7 at y = 38, x = 38, 50, …, 122) plus (8,7) and (14,14).
  Row 0 is where the flush's write-back lands. It lands at texel `(fpVidMem & 15)/2`, not 0, when the
  surface is misplaced (G21), so the whole row is checked.
- **Expected values.** Red 0xf800 → `0xff0000`, green 0x07e0 → `0x00ff00`, ±12 per channel (`expect`,
  `:328-343`).
- **Round 1 is the cold read.** A texel that is wrong there is reported `placement` (G21/G36's business)
  and excluded from the coherency verdict, so misplacement can never pass as, or hide, a coherency result.
- **Round 3 is the ground truth.** `CopyRects` copies the tested texture into a fresh DEFAULT texture F that
  was never sampled. F is then sampled cold: a new base on silicon, and an undecoded base on 86Box.
- **Verdict per texel:**
  - `ok`: round 2 = round 3 = green;
  - **`stale`**: round 2 red, round 3 green. **This is G37.**
  - **`stale_wb`**: only row-0 texels stale while the rest of the texture is green. The flush ran without
    the sync, which is hazard 4.
  - `premise`: round 3 not green. The write never landed, so this says nothing about coherency.
- **RESULT JSON.** Each test reports `ok`/`fail`/`skipped` and these verdict counts.
- **Lists.** All of these are explicit tests, never in the default list until graduation.
  `d3dprobe_run.py` fails a run in which a named test was skipped (`WT/tests/README.md:261` (c)). So
  `rtt_clear8888` is named only on silicon with `D3DBigTex` bit 2.

| test | what it draws | pass | today (expected) |
|---|---|---|---|
| **`blt2tex`** (hole 1) | D: DEFAULT texture filled red by `UpdateTexture` (TEXBLT, marked). S: a 16x16 R5G6B5 `CreateRenderTarget` surface, cleared green through `SetRenderTarget(S, NULL)` + `Clear`. ## 8. Risk to proven paths

- **Default 16 bpp path, unarmed:** no change (§3.7).
- **Armed:**
  - extra flushes only for textures written by the engine, or rebound after a write while unbound;
  - one `VcrDd2dSync` per such texture before a write-back, a status-read idle wait that every `Lock`
    already does;
  - no caps or allocation change.
- **Glide/OpenGL coexistence:** none.
  - Marking writes only system memory (the surface local and a counter).
  - The flush runs inside `prepare`, which returns at once when `w->drawable` is false, and it is false
    while a Glide process owns the chip (`exclusive_pid`, `vcrdd_d3d.c:1325-1326, 1859-1860`).
  - Like every D3D path, it relies on G01's FIFO state being sane.
- **SLI:** none today, since Direct3D runs on one chip. **When G51 lands:**
  - `VcrDd3dTexFlush` must reach every chip's TMUs (a chipMask broadcast);
  - a render-target texture needs SLI off for that target (hw Q12: a texture rendered under SLI is
    incomplete on every chip);
  - a 2D blit into a texture must reach every chip's copy.
  G51's design must carry those three.
- **The flip path:** none. Flip-chain surfaces are not textures; the marking function returns at the caps
  test.
- **Performance:**
  - cost at most one engine drain plus 7 writes per engine-written texture per bind-after-write;
  - a ping-pong post-process chain pays one per pass;
  - compared with G46's 123 ms frames this is noise (inferred; boot B's perf and the game fps confirm).
- **Failure mode under a wedged chip:** `VcrDd2dSync` can give up and turn acceleration off, exactly as a
  `Lock` can today. That is G02's silent give-up, not a new mode.
- **Use-after-free (G43):** the new calls use `c->pd`, as the rest of the walk does. There is no new
  exposure; G43 covers it.
- **Future work that must keep this:**
  - **G53** (register shadowing) must invalidate its `texBaseAddr` shadow after a flush, which writes
    other values to both TMUs, and must never shadow the flush away.
  - **G47** (CMDFIFO) must emit the flush as packets and keep "sync before the write-back" (or drop the
    write-back on the VSA-100, Q3).
  - **G56** (conditional Lock drain) should reuse `SF_ENGINE`. It is exactly 3dfx's `BltToTxtrInFifo`
    (`VH5/DDSURF.C:1612-1620`): "the engine wrote this, drain before the CPU touches it".

## 10. Open questions

1. **Does a same-value `texBaseAddr` write flush the VSA-100 cache?** SPEC says "changing", and Glide's
   comment implies not. Boot A measures it.
   - If it does flush, today's per-DP2 re-send masks holes 1-3 on silicon.
   - That masking ends with G53's shadowing, so this item should land before G53.
2. **Does D3D8 `CopyRects` with a render-target-surface source reach `DdBlt`?** No TEXBLT can carry a
   non-texture source, so it should (inferred). The bed's unarmed `blt2tex` FAIL, and the armed 513/30
   "who = 1" line, confirm it.
3. **Is the write-back needed on silicon at all?** It exists for 86Box's cache. On the VSA-100 the
   inverted-base flip is the documented mechanism. Dropping it for engine-written textures when
   `pd->napalm` would remove the sync too. That is a perf refinement for G46/G47 to decide with
   measurements, and it would make the bed and silicon run different code.
4. **Which staged titles exercise holes 1-2?** The counters answer it (§3.5); priority follows.
5. **The D3DFeat bit number, the debug-bit convention, and the graduation mechanism** are plan-level, shared
   with G05/G08/G12/G15/G16/G22/G25.
6. **Does the runtime's PCI-id table grant the 86Box Voodoo3 (`121a:0005`) an R5G6B5 render-target
   texture?** `reports/runtime.md` §4.3 measured only `121a:0009`. If not, the bed proves holes 1 and 3,
   and holes 2 and 3-with-render are proven on `.124` only.
7. **DX7-only routes:** `DDBLT_COLORFILL` into a texture through `IDirectDrawSurface7::Blt`, and a D3D7
   device created on a texture surface. D3D8 cannot send them. They are covered by the `Dd_Blt` fill mark
   and the DP2-end mark, and proven only once G75's DX7 probe exists (`blt2tex_fill`, `rtt_dev2`).
