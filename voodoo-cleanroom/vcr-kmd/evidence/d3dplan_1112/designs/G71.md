## 0. Verdict

1. **The gap is real, and it is wider than the title says.** AvP's Direct3D path has never been seen working on
   **any** box. On `.124` it has never even been reached.
   - AvP's front end is DirectDraw only. It loads every menu graphic with `AwCreateSurface` into a 16-bit 565
     DirectDraw surface (`RDY/fix-avp/LOGFILE_133.TXT:153-799`).
   - The texture loader's D3D entry point, `AwSetD3DDevice(%p) called` / `AwSetD3DDevice() OK`
     (`avp.exe` strings), appears in **none** of the eight AvP logs on record. Those are `RDY/fix-avp/LOGFILE_133.TXT`
     and `RDY/scout-AliensVsPredator/LOGFILE_{123,124,133,143,171,184,240}.TXT`.
   - The 2026-11-12 "seven boxes reach the menu" proof (`RDY/fix-avp/fleet/AliensVsPredator.json`) therefore
     proves the decoded library tree and DirectDraw. It does not prove Direct3D on those boxes either.
2. **On `.124` today AvP still dies on game data, not on our driver.**
   - `.124`'s tree read `fastfile\ffinfo.txt` **OBFUSCATED** on 11-11 16:32 (`RDY/scout-AliensVsPredator/boxreads.json`,
     entry 192.168.1.124).
   - `.124` was left out of the 11-12 push: `scripts/fleet/lanparty_titles.json` lists AvP's boxes without 124.
     That follows the readiness policy that marks `.124` `blk` for Direct3D titles after the Max Payne freeze
     (G04, `WT/docs/lan-multiplayer-status.md:71`).
   - Step 1 is therefore the staged-game loop: purge, GAMESYNC, verify. The tree is 308 MB in 561 files
     (`du` on `LIB/AliensVsPredator`), about 6-10 minutes at `.124`'s measured 0.55-0.83 MB/s SMB rate
     (`FIND:496-499`).
3. **Static analysis of `avp.exe` predicts what AvP will send our HAL** (Appendix A; md5 `91bb8e75...`):
   - **Opcodes:** an execute-buffer stream of `D3DOP_STATERENDER` (8), `D3DOP_TRIANGLE` (3) and `D3DOP_EXIT` (11),
     behind one `PROCESSVERTICES COPY` the runtime consumes.
     - All three opcodes have explicit cases in `walk()` (`KMD/display/vcrdd_d3d.c:1585`, `:1643`, `:1773`).
     - The single `D3DOP_LINE` (2) site is in a function nothing calls.
     - There is no POINT, SPAN, TEXTURELOAD, SETSTATUS or BRANCHFORWARD.
   - **Render states written:** the legacy `TEXTUREMAG`/`TEXTUREMIN` (NEAREST or LINEAR), `TEXTUREMAPBLEND = MODULATE`
     (written once), `TEXTUREPERSPECTIVE` 0/1, seven SRCBLEND/DESTBLEND pairs, ZFUNC LESSEQUAL/ALWAYS, ZWRITE,
     DITHER, SHADEMODE GOURAUD, FILLMODE, and CULLMODE NONE in its hardware draw mode.
   - **Never written:** `COLORKEYENABLE`, `SPECULARENABLE`, `FOGENABLE`, `ALPHATESTENABLE`, any `TEXTUREADDRESS*`,
     and any texture-stage state.
4. **Expected result: the device comes up and the stream parses. What goes wrong will be known HAL gaps:**
   - **Device and stream.**
     - Our DX5 device description carries the same flags and device caps as 3dfx's own V5 HAL
       (`vcrdd_d3d.c:2063-2070` against `VH5/D3INIT.C:2598-2634`).
     - Mysteries of the Sith, the other execute-buffer title, ran 7,014 DP2 with 0 unparsed (`PLAN:674`).
   - **Point-sampled textures where AvP asks for bilinear:** G08, high confidence. AvP sends `TEXTUREMAG/MIN = LINEAR`,
     and `set_rs` only stores them (`:1393-1406`).
   - **Vertex-alpha translucency drawn opaque on RGB565 textures:** G08's legacy-MODULATE alpha rule, medium
     confidence.
   - **Colour-keyed cut-outs and missing specular light:** G09 and G25, but **only if** XP's `d3dim.dll` gives a
     legacy device `COLORKEYENABLE`/`SPECULARENABLE` = TRUE. AvP never sets them, its loader does set a colour key
     ("setting the colour key"), and it writes a computed specular colour on some vertex paths. Unknown, and
     measurable.
   - **New, not in the gap list:** `TEXTUREPERSPECTIVE` is ignored; the HAL always samples perspective-correct
     (`TM_PERSPECTIVE` at `:787`, `:825`). 3dfx honours it (`VH5/D3RSTATE.C:2344-2362`). It is probably harmless
     for AvP, which writes one rhw per polygon on its perspective-off path (Appendix A.4).
5. **What G71 delivers:**
   - the attended investigation protocol, with an outcome-to-fix map;
   - a control run on a GeForce box (the first in-game AvP reference anywhere on the fleet);
   - three small pieces of tooling: `tools/avplog.py`, `tools/ebscan.py` with a committed static profile, and a
     d3dprobe `avpstate` check;
   - one host test file;
   - the records.
   **G71 changes no driver behaviour.** The defects it finds land under their own gaps (G08, G09, G25, G10, G39,
   G55, G56, G59). One optional log-only line is described in section 5.3.

## 4. The investigation

### 4.0 Rules for every on-box step

These come from the project rules and from what AvP has already done to `.124`.

- **The `.124` sessions are attended.** A person watches the CRT and drives AvP's keyboard menus. D3D titles on
  `.124` stay out of unattended runs until G04 closes.
- **Close AvP gracefully:** its own menu Quit, then `taskkill /pid` (WM_CLOSE), then `taskkill /f /pid` only after
  20 s, then `vcrctl pace-mark`. Never ALT+F4, and never a key sent unless `WINLIST`'s foreground pid is `avp.exe`
  (`FIND:473-484`). Never kill by image name.
- **No `vcrctl` and no ExtEscape while AvP runs.** That includes `log`, `reg` and `fbshot`. Frames come from the
  agent's GDI `SCREENSHOT 0` and from AvP's own `SCREENSHOT` console command. Registers and the ring are read
  after AvP exits.
- **Mode switches at least 5 s apart.** AvP's switches are driven by the person (launch, level start, quit), so
  the spacing holds. Change AvP's video mode **only in the main menu, never in game**: a context living across a
  mode change is G43's possible use-after-free. No alt-tab and no Windows key, for the same reason.
- **No Glide or OpenGL program runs in the boot before AvP.** A stale command FIFO makes every D3D triangle vanish
  (G01, `ONBOX` run #5). Before each AvP launch, check `vcrctl reg 0` (expect `0x1f`) and `vcrctl reg 80024` (bit 8
  clear).
- **Every reboot:** check activation first (`LICSTATUS` or `wmic path Win32_WindowsProductActivation`), arm the PXE
  hold for `.124` (`scripts/pxe/pxe_server.py --arm 00:d0:b7:40:96:a9`, then `--list-holds`), and reboot only
  through `scripts/fleet/safe-reboot.py`.
- **Evidence goes in the repo tree:** `KMD/evidence/avp_<yyyymmdd>/`, never the scratchpad.

### 4.1 Phase A: on the host (no box)

1. **Commit the static profile.** `tools/ebscan.py` (Appendix A.5) is run over `objdump -d -M intel` of
   `LIB/AliensVsPredator/avp.exe`. It writes `KMD/evidence/d3dplan_1112/avp/avp_static_profile.json`: the opcodes,
   the (state, value) pairs, the never-written set, and the binary's md5 `91bb8e752f42d35f594fc06feabd49cf`.
2. **`tools/avplog.py`**: a parser of AvP's three logs into one JSON (section 5.2), with its verdict rules.
3. **d3dprobe `avpstate`** (section 9), built into `out/d3dprobe.exe`.
4. **`tests/python/test_vcr_kmd_avp.py`** (section 10). It is green before any box is touched.

### 4.2 Phase B: `.124`'s tree (no Direct3D, can run unattended)

1. **Read before changing anything** (the method of `RDY/scout-AliensVsPredator/avp_boxread.py`):
   - `DIRLIST C:\Games\AliensVsPredator`;
   - `DOWNLOAD` of `fastfile\ffinfo.txt` (decoded or obfuscated by its first bytes);
   - `DOWNLOAD` of `LOGFILE.TXT`, `dx_error.log` and `ConsoleLog.txt`, all small (N4).
   `dx_error.log` has never been read. If it names a DirectX failure from an earlier run, that is a lead before
   any D3D run.
2. **Staged-game loop** (CLAUDE.md "Fixing a Staged Game"):
   - `rd /s /q C:\Games\AliensVsPredator`, then a `DIRLIST` to verify it is gone;
   - `GAMESYNC RESET` + `START`;
   - wait for `state=done` AND `failed_files == 0` AND `titles_done == titles_total` AND `titles_total` equal to the
     library's count for `.124`'s profile.
3. **Verify the post-condition, not the sync:**
   - `DOWNLOAD fastfile\ffinfo.txt` gives md5 `8011119b8456329457f0872037b22243`;
   - `DOWNLOAD avp_huds\Disk.RIF` gives `fe9a1f4e5caab35e38aabdbbb445aabc` (`decoded_manifest.tsv`);
   - `HKLM\SOFTWARE\Fox Interactive\Aliens vs Predator\1.00\Source Path` reads `C:\Games\AliensVsPredator\`
     (`install.reg`).

### 4.3 Phase C: the control run (attended or agent-driven, on a GeForce box)

`.184` (GeForce2 GTS, the V5's generation) or `.133` (GeForce4 Ti 4600). Same title, same library tree.

1. **One injected-key test.** At "Select User Profile", send `UIKEY RETURN` with AvP focused. Does DirectInput
   take the agent's keys? (open question 3). If it does, the rest of this phase can be agent-driven, which matters
   for later unattended sweeps elsewhere.
2. **The route:**
   - New Profile, name `fleet`;
   - main menu, Options, Video: note the offered modes, including whether 32-bit modes appear;
   - back to the main menu: start the Marine campaign, first mission;
   - 2 minutes in game: look around, fire, throw a flare (Marine), toggle the image intensifier;
   - console: `SHOWFPS`, `SHOWPOLYCOUNT`, `SCREENSHOT`;
   - menu Quit.
3. **Collect:**
   - `LOGFILE.TXT`, `dx_error.log`, `ConsoleLog.txt`, `AvP_Video.cfg` and the `*.bmp` screenshots (`DIRLIST *.bmp`);
   - GDI frames at the menu and at 30/60/90 s in game.

**What this settles:**
- whether the decoded library loads a level at all: no other data defect, and a P0 for the library rather than
  for us if it does not;
- the reference picture of the first mission;
- AvP's device and format choices on a contemporary driver;
- the format of `AvP_Video.cfg`.

**Do it before the `.124` boot,** so `.124`'s result can be compared on the spot.

### 4.4 Phase D: the `.124` boot (attended)

**Boot setup.** One Diag change for this boot: `Diag\LogEntries` = 16384, read at boot (`miniport/vcrmp_log.c:282-284`;
`LogLevel` at `:279`).
`LogLevel` stays at its default of 3 (DEBUG), so device creation, CreateSurface and texture placement are all
logged. AvP's per-frame DEBUG volume is small: it uses no texture-stage TEXTUREMAP events, so roughly one
target-change event per flip (inferred). That keeps a short session whole. Read the value back, then go through
§4.0's reboot steps.

## 9. d3dprobe test: `avpstate`

D3D8 cannot send execute buffers or `TEXTUREMAPBLEND` (that is G75). `avpstate` checks the half of AvP's pipeline
that D3D8 can express, with AvP's own vertex format, before the game meets it.

- **Device:** the probe's usual one. Dither off and CULLNONE, as `main()` sets (`KMD/tools/d3dprobe.c:1492-1495`).
  Run at 640x480x16 (AvP's mode) and at 1024x768x32.
- **Vertices:** `D3DFVF_TLVERTEX` = XYZRHW | DIFFUSE | SPECULAR | TEX1 (0x1c4, stride 32), AvP's exact layout.
  `specular = 0x00404040` with `D3DRS_SPECULARENABLE` FALSE (the D3D8 default). So every cell also checks that
  `fvf_layout` finds the texture coordinates after the specular slot (`vcrdd_d3d.c:1254-1284`), and that a disabled
  specular adds nothing.
- **Texture:** a 64x64 R5G6B5, solid white (`checker(64, 0xffffffff, 0xffffffff)`), point-sampled.
- **Stage 0:**
  - `COLOROP MODULATE (TEXTURE, DIFFUSE)`;
  - `ALPHAOP SELECTARG2` with `ALPHAARG2 DIFFUSE`. That is what DX5's legacy MODULATE means for a texture with no
    alpha, and the combine G08 maps it to (`color_path`: `CP_ASEL_ITER` with a textured colour path).
  - Stage 1 is DISABLE.
- **Inputs:**
  - Background: clear `0x406080`.
  - Diffuse `0x80c0a040`: source colour S = (0xc0, 0xa0, 0x40), source alpha As = 0x80.
- **Cells:** eight 24x24 cells, one per AvP pair, at fixed positions inside the 256x256 window. One more cell is
  left at the clear colour; its pixel is read back as the destination D. Using the read-back value cancels the
  565 quantisation of the clear.

| cell | state | reference value (computed in the probe from S, As, D) | 32 bpp example |
|---|---|---|---|
| `off` | ALPHABLENDENABLE FALSE | S | c0a040 |
| `normal_valpha` | SRCALPHA / INVSRCALPHA | S x As + D x (1 - As) | 808060 |
| `normal_talpha` | the same blend with `ALPHAOP SELECTARG1(TEXTURE)` | S: an RGB565 texel's alpha is 1.0. This is what AvP gets today without G08 | c0a040 |
| `glowing` | SRCALPHA / ONE | D + S x As | a0b0a0 |
| `colour` | ZERO / SRCCOLOR | D x S / 255 | 303c20 |
| `invcolour` | ZERO / INVSRCCOLOR | D x (255 - S) / 255 | 102460 |
| `darkening` | INVDESTCOLOR / ZERO | S x (255 - D) / 255 | 906420 |
| `justsetz` | ZERO / ONE, Z write on at z 0.2; then an opaque red quad at z 0.5 with LESSEQUAL | D (colour untouched, the red quad hidden). Skipped under `--noz` | 406080 |

- **Pass:** every channel of every cell is within **16** at 16 bpp (two 565 quantisations and 8-bit factors) and
  within **6** at 32 bpp.
- **Reference:** D3D's blend equation. The same `--tests avpstate` run on `.133`/`.184` (GeForce, any driver)
  confirms the tolerance against a shipping D3D driver before the `.124` run.
- **Reported as:** explicit `--tests avpstate`, not in the default list (that keeps the 40/42 counts comparable).
  An explicitly named test that is skipped fails the run (`KMD/tools/d3dprobe_run.py:202-216`).
- **Expected today:** a pass. If a cell fails, that factor is wrong on silicon. That is a G71 finding in
  `blend_src`/`blend_dst`, and it would hit AvP's matching translucency mode.
- **Culling is deliberately not in it.** AvP sends CULLMODE NONE on hardware (N7). A cull-sign cell belongs to
  G74's general coverage.

## Appendix A: `avp.exe`, static execute-buffer profile

**Binary:** `LIB/AliensVsPredator/avp.exe`, 2,169,856 bytes, md5 `91bb8e752f42d35f594fc06feabd49cf`, linked against
DirectX 6.0 headers ("Compiled with DirectDraw Version 6.0"). Imports `DDRAW` (`DirectDrawCreate`,
`DirectDrawEnumerateA`) and `DINPUT`. `DirectDrawEnumerateExA` is named as a string (dynamic).

**Method:** `i686-w64-mingw32-objdump -d -M intel --no-show-raw-insn`, then a scan for `D3DINSTRUCTION` headers.
MSVC compiles AvP's macros to three stores: `mov BYTE PTR [r],op`, `mov BYTE PTR [r+1],bSize` (via
`[r-3]` after `add r,4`) and `mov WORD PTR [r+2],wCount`. A header counts only when `bSize` is that opcode's
record size (TRIANGLE 8, STATERENDER 8, PROCESSVERTICES 16, LINE 4, EXIT 0). For STATERENDER, the DWORD stores
that follow are paired as (type, arg), following `add r,8` and the shared tail at 0x4cf981 for the second
state of a two-state block. This is heuristic: JK's binary writes its states another way (2 states found), and
Rainbow Six none. For AvP the counts below were checked by reading the code around each site.

### A.3 Vertices

`D3DTLVERTEX` (sx, sy, sz, rhw, color, specular, tu, tv). Specular at +0x14 is `0xff000000` (black, no fog) on
several paths (for example 0x4d1077) and a computed value on others (`mov [ebx+0x14],edx/eax`). AvP lights in
software and carries a specular term (inferred: its renderer's SpecularR/G/B).

### A.4 The perspective-off path

0x4d0ea8-0x4d1199 writes per vertex sx, sy, sz, `rhw = [esp+0x14]` (0x4d100a-0x4d1012: one value moved as an integer,
so the same for every vertex of the polygon, inferred), colour `0xc8c8c8` with specular `0xff000000`, then sets
`TEXTUREPERSPECTIVE = 0` (0x4d1130). With one rhw per polygon, perspective-correct and affine interpolation give
the same texels. That is why N9 is expected to be harmless for AvP.

### A.5 `tools/ebscan.py` (to be committed; the design's copy lived only in the session scratchpad)

The scanner is about 150 lines of Python over the `objdump` text:

1. Parse `address: mnemonic operands`.
2. For each `mov BYTE PTR [r(+k)],op` with op in 1..14, find the bSize store at relative offset +1 within 8
   instructions, tracking `add r,imm`. Accept the header only when bSize equals the opcode's record size.
3. For op 8, collect the following `mov DWORD PTR [r±k],v` stores relative to the header until the next header,
   a non-arithmetic instruction or an unconditional `jmp`. For a `jmp`, follow it once to collect the shared
   tail.
4. Pair offsets 4+8i (type) and 8+8i (arg).
5. Emit `{binary, md5, opcodes{op: sites}, states[{state, values}], dead_sites[]}`. `dead_sites` lists sites whose
   enclosing function has no `call`/`jmp` reference and no stored pointer.
