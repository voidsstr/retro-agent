- **New rows.** The text below is draft wording; every fact in it is from the code above.

  | value | read | what it does |
  |---|---|---|
  | `D3D` | at boot (FindAdapter) | **A kill switch, default ON (absent = 1; 0 = off).** 0 withdraws the Direct3D HAL. It sets `vcr_info.flags` 0x4 (NO_D3D), which becomes `pd->d3d_disabled`. `VcrDdD3dHalInfo` and the D3D GetDriverInfo answers return nothing, the HAL leaves mip chains and DXT sizing to DirectDraw, and `Reset3D` does not run ("not reset - Direct3D is off"). A D3D8/9 title then cannot create a HAL device; a DX5-7 title may fall back to the runtime's software rasterizer (inferred). DirectDraw, GDI acceleration, Glide and OpenGL are unchanged. It takes D3D off a box whose D3D titles misbehave without uninstalling the driver. A reboot applies it. |
  | `TexPortFlush` | at boot | **A kill switch, default ON (absent = 1; 0 = off).** After a CPU write into a texture, the HAL flushes the TMU texture cache with Glide's coherency sequence (`VcrDd3dTexFlush`). It then writes one dword back through the texture port at the first texel, which is the write 86Box's texture cache watches. That write-back fires only for a 16 bpp texture no wider than 256, below 16 MB (`vcr_tex_writeback_addr`). 0 (flags 0x8, NO_TEXPORT) keeps the sequence and drops the port write; use it for an A/B on a texture-upload fault. |
  | `Accel2D` | at boot | **A kill switch, default ON (absent = 1; 0 = off).** 0 (flags 0x2, NO_ACCEL2D) draws GDI and DirectDraw blits in software. **The Direct3D HAL goes with it**, because the HAL needs the engine: `VcrDdD3dHalInfo` and GetDriverInfo require `g2d_ok`. This is the same state an engine give-up leaves for the rest of a PDEV (512 a=9; G02). |
  | `LogLevel` | at boot (DriverEntry) | The flight recorder's level, **default 3** (0 ERROR, 1 WARN, 2 INFO, 3 DEBUG, 4 TRACE). An event above it is not recorded; the display DLL's events are filtered in the miniport too. At 3, a game's per-draw DEBUG events (513 what 8, 14) overrun the ring: UT2004 alone logged about 67,000 events (`ONBOX/README.md`). At 2 the ring keeps the INFO events (513/1-2 contexts, 21-23 combine set-ups) and drops those. It changes only what the ring keeps. |
  | `LogEntries` | at boot | The ring's size in 128-byte entries, **default 1024 (128 KB)**. Values from 64 to 16384 are honoured (16384 is 2 MB of non-paged pool); anything else is ignored. Set it with `LogLevel` before a session whose ring must survive (G04), and delete it afterwards. |
  | `DbgPrint`, `DebugPort` | at boot | Mirror every recorded event to DbgPrint, or to an I/O port (0xE9 QEMU debugcon, 0x3F8 COM1); see "The debug harness". Default 0. |

**A4. `tools/d3dprobe_run.py` keeps the result** (a new helper, `tools/labrecord.py`, so `ddlab_run`,
`glidelab_run` and `lab_run` can adopt it later).

- **Where.** Every exit path that prints a RESULT writes one record, the `--no-save` path excepted. That
  includes refusals (rc 2), errors and timeouts. The default file is
  `KMD/evidence/d3dprobe/<YYYYMMDD>/<HHMMSS>_<host>_<mode>_<WxHxBPP>_<full|win>[_<label>].json`,
  in the worktree the runner runs from and never in a scratchpad. Beside it go
  `<same>.log` (the downloaded d3dprobe log) and `<same>.ring.tsv.gz`.
- **The record.**
  - `record` 1, `result` (the printed RESULT, verbatim) and `exit_code`;
  - `started` and `ended` (ISO, host time), `host`, `port`;
  - `argv`, `lab_args` and `label`;
  - `d3dprobe_exe` (md5 and code-md5 of `out/d3dprobe.exe`), `repo` (HEAD and whether
    `tools/d3dprobe.c` is dirty);
  - `box`:
    - `vcrdd` and `vcrmp`: the md5 and the code-md5 of the files on the box, through `REGREAD`
      SystemRoot, then `DOWNLOAD %SystemRoot%\system32\vcrdd.dll` and `...\drivers\vcrmp.sys`;
      about 240 KB, read-only. A failure is recorded as `unreadable: <error>` and does not fail the
      run.
    - `vcrctl_info` (the raw JSON, or "not vcr-kmd");
    - `in_effect`: `flags` decoded into the switches this boot really applies (D3D32, D3DBigTex bits,
      NO_D3D, NO_TEXPORT, NO_ACCEL2D, RESET3D, DDHEAPFLOOR...). That is the truth for this boot,
      where a REGREAD of Diag only shows the next boot's.
    - `log_next_seq` before and after.
- **Code-md5** is the md5 of the PE with the COFF TimeDateStamp and the optional-header CheckSum
  zeroed, so a record can be matched to a source build.
- **Ring slice.** After the run, `vcrctl log <seq before>` is saved, but only when the probe is gone:
  no reap was needed, or the reap confirmed it. Otherwise the record says `ring: not read (probe
  still running)`, under the rule "never run vcrctl while a D3D app runs".
- **Flags.**
  - `--save-dir DIR` overrides the location; `silicon_battery.py` passes
    `--save-dir evidence/silicon/<label>/` so its records sit beside its jsonl.
  - `--label TEXT`.
  - `--no-save` prints a boxed `RESULT NOT SAVED - this run is not evidence` banner.
- **The last line printed** is `record: <path> (+ .log, .ring.tsv.gz) - commit it with the change
  it verifies`.
- **Call order.** The provenance calls are made at the same point as the existing fullscreen gate's
  `vcrctl info`, before the upload. Nothing is sent to the box while d3dprobe is running.

**A5. Named checks must account for themselves** (runner first; d3dprobe as well).

  code to 1.
- **d3dprobe.c.**
  - The unknown-test branches (`:1189`, `:1241`) become `failed(t, "unknown test", 0)`, so the

  - A `--tests` list longer than the buffer is refused with a RESULT error instead of being

  - The three `*_def` checks are **removed** (`:1172-1182`, and the dead `g_cells_pool`
    DEFAULT branch). They cannot pass under D3D8. The DEFAULT pool stays covered by
    `*_upd`/`*_copy`.

## 7. Risk

- **The default 16 bpp path, Glide/OpenGL coexistence, SLI state and the flip path:** none. No
  driver code changes, and the identical-image check proves it.
- **The runner.**
  - It adds about 3 s and about 240 KB of reads a run.
  - `vcrctl info` and `vcrctl log` are escapes, and the rule is never to run them while a D3D game
    runs. The runner calls them only before its own probe starts, and after the probe is confirmed
    gone. If the reap could not confirm that, the ring is skipped and the record says why.
  - `DOWNLOAD` of a loaded driver file is a read. If XP refuses it, the record says `unreadable`
    and the run is not failed.
  - Nothing is written to the box beyond what the runner already writes.
- **Doc tests can be brittle.** They key on table rows by their first cell, on the code-list syntax
  of the event table, and on a short fixed phrase list. Each failure message names the file, the
  line and the expected form.
- **Repository growth.** A record is about 10-30 KB of JSON, up to about 25 KB of log and about
  20 KB of gzipped ring. That is about 1-2 MB for a 20-run session.
- **Shared index files.** Before editing `WT/tests/README.md`, run
  `git -C <worktree> status --short` on every live worktree, and append in a separate region. None
  had it modified on 2026-11-12.
- **Overlap with G20's Part 0, G11 §4.4, G19, G21 and G63.** §2 Part B sets the boundary. Whichever
  lands second rebases its doc edits; the doc-truth tests catch a stale result.

## 12. Open questions

1. **Tier 2 Diag documentation.** Should every one of the 57 Diag values get a README row, or is a
   `Diag\Name` mention enough for the boot-safety, monitor, SLI and mode-math values? This design
   requires rows for tier 1 only.
2. **The `*_def` checks.** Remove them (proposed), or turn them into an expected-refusal check?
   Removing assumes the D3D8 runtime refuses `LockRect` on a non-dynamic DEFAULT-pool texture before
   the HAL is asked. To confirm, run once at `LogLevel` 4: no 511/9 Lock for that surface.
3. **Part D.** The transcript is private session data on the dev host. Is a recovered,
   clearly-labelled partial record wanted in the repo, or should those values stay in commit
   messages?
4. **Should `ddlab_run.py`, `glidelab_run.py` and `lab_run.py` adopt `labrecord.py` too?** They have
   the same prose-only risk. `lab_run.py` runs d3dprobe without the runner, so its runs would not be
   recorded.
5. **A build identity in the binaries.** For example, git hash and dirty flag in `vcr_info`, or a
   resource string. A record could then name its source without a code-md5 search. That changes
   every build's bytes, so it belongs to the next driver release, not to this item.
6. **The VBIOS mode in the docs.** `.124` has run the 256 MB VBIOS mode since 2026-09-27, and the
   switch is physical. The docs will state both heap sizes. Should the README also give the mode the
   box is in, or leave that to `vcrctl info` (`fb_per_chip`)?
7. **202's double what 2** (I/O BAR at boot, and the register view for the display driver) is a
   miniport-lane fix. It needs a new code, and the doc test could then cover the miniport's
   what-events too.
