# G11: a CreateDevice that fails after the runtime's mode set flaps the CRT

Design for one item of the Direct3D plan for the Voodoo 5 6000 on `.124` (vcr-kmd HAL).
Written 2026-11-12. It reads code, docs and committed evidence only; no fleet box was contacted.

Path shorthands: `KMD` = `voodoo-cleanroom/vcr-kmd`, `WT` = the `v56k-bench` worktree root,
`ONBOX` = `KMD/evidence/d3dplan_1112/onbox`, `E86` = `KMD/evidence/86box_v3/int_20260927/04_d3d`,
`VH5` = 3dfx's H5 W2K display driver source (guidance only), `FIND` = `retro-3dfx/FINDINGS.md`.
"Measured" means it comes from a ring, a log or a probe result. "Inferred" means it does not.

---

## 0. Verdict

The gap is real. It is not a pacing problem the driver should solve at the mode set. It is a
**contract problem**: the D3D8 runtime sets the fullscreen mode before three of its own steps:
creating the depth buffer, checking the depth format, and calling our `ContextCreate`. Whatever
fails at those steps reaches the monitor. The cure has four parts:

1. **Remove the one refusal games can reach after the mode set (G10).** Today that is
   X8R8G8B8/A8R8G8B8 + D16.
2. **Pin the contract in a test.** Every (back buffer, Z) pair that the runtime accepts must be one
   that `ContextCreate` draws, in every listed mode. Without this test, any later caps or format
   change can bring the flap back.
3. **Make every remaining ContextCreate refusal loud.** Two of the three are silent today.
4. **Give the tools a way to refuse, and to count, the re-syncs they would cause.** The
   on-box run of 11-12 was a deliberate refusal probe, and nothing stopped it or counted it.

**No pacing or hold in the kernel.** That design is worked through in §4.5, and it is the
wrong trade here.

Three facts this design adds to the brief:

- **It is four timing changes, not two.** Every mode change on vcr-kmd goes through XP's
  `DrvAssertMode(FALSE)` → `IOCTL_VIDEO_RESET_DEVICE` → `VcrHwResetToVga`, which drops the
  monitor to VGA text (31.5 kHz) before the new mode (`KMD/display/vcrdd.c:570-614`,
  `KMD/miniport/vcrmp.c:677-695`; FIND 2026-09-26: "every switch dips to VGA text (31.5 kHz) and
  back ... two sync changes per switch"). So the refusal on 11-12 put this sequence on the cable
  in about 170 ms: 91.1 → 31.5 → 43.3 → 31.5 → 91.1 kHz.
- **The runtime's *own* depth-format refusal also comes after its mode set.** On the 86Box
  Voodoo3 bed, the runtime set and then reverted the mode with no driver refusal at all (§2, E86 `e7`).
  So "make the runtime say no" is not flap-free for a Z format. Only a back-buffer format the
  HAL does not offer, or a HAL that is not offered at all, is refused before the mode set.
- **Two of the three `ContextCreate` refusals are silent.** All 32 contexts in use, and no FPU
  save area: both return `DDERR_OUTOFMEMORY` with no log line
  (`KMD/display/vcrdd_d3d.c:1170-1173`, `:1178-1181`). Each of them costs a fullscreen D3D8/9
  CreateDevice the same mode flap.

## 2. Where a D3D8 CreateDevice fails, relative to its mode set

| failure | decided by | mode set first? | evidence |
|---|---|---|---|
| no HAL offered (`GetDeviceCaps(HAL)` 8876086a) | runtime, up front | **no** | ONBOX 10:11:03 (`d3dprobe_render_1024x768x32_after_reset.txt`; ring: only DrvGetModes + DestroyDDLocal) |
| back-buffer format without 3D (32 bpp on a Voodoo3 / without D3D32) | runtime, after `SetCooperativeLevel(EXCLUSIVE)` | **no** | E86 `e3`, `e5`: `DirectDraw exclusive 1` → `exclusive 0`, no 300/303 rows |
| depth format not in the driver's Z list | runtime, after the mode set **and** the primary chain | **yes** | E86 `e7` (V3, 640x480x16 + D24S8): pid 1144 `DrvEnablePDEV mode 75` 2087.281 s, `mode 75: 640x480x16@60` 2087.451 s, primary chain created, **no Z CreateSurface and no ContextCreate**, `DrvEnablePDEV mode 80` 2087.681 s, `mode 80` 2087.772 s (321 ms, 86Box clock), CreateDevice 8876086c, no driver refusal logged |
| (target, Z) refused by our `ContextCreate` | driver | **yes** | §1 |
| runtime's pairing check (CheckDepthStencilMatch-type; R5G6B5 + D24X8 → 8876086a) | runtime | **unknown** | 11-08, `WT/docs/v56k-benchmark-plan.md:172-174`; no ring was kept |
| out of video memory for the chain or the Z at the chosen mode | runtime / DirectDraw | yes (inferred from the order above) | — |

D3D9 is assumed to order CreateDevice the same way, because it has the same legacy-driver
machinery (`reports/runtime.md` §3-4). That is inferred. DX5-7 applications set the mode
themselves, so a refusal there is the application's to handle: it may fall back on the same mode,
or exit.

**What this means for the plan.** A refusal costs the CRT nothing only when it is a back-buffer
format the HAL does not list, or a HAL that is not offered. Anything about the depth buffer costs a
flap, whoever refuses it. So the driver must accept every Z pairing the runtime accepts.

## 3. Our refusals after that mode set, and whether a game can reach them

`D3d_ContextCreate` (`KMD/display/vcrdd_d3d.c:1163-1208`):

| refusal | logged? | reachable from a fullscreen D3D8/9 CreateDevice? |
|---|---|---|
| 513/12 size pair (`vcr_rt_format`, `KMD/include/vcr_rtfmt.h:79-87`) | WARN | **Yes: X8R8G8B8/A8R8G8B8 + D16.** The runtime matches it (`caps_124.txt` zmatch X8R8G8B8/D16 = 1/1, and on 09-28 too). Not reachable: 32 bpp without D3D32 (the runtime refuses that up front), R5G6B5 + D24X8/D24S8 (no runtime match) and 16-over-32 (draws since be58b7d). |
| 513/17 target pitch (`vcr_rt_rtcheck`) | WARN | **No** for listed modes: every `vcr_timings` width is a multiple of 8, so pitch = w×2 or w×4 is 16-aligned. The test in §7 pins this for every timing. Windowed clients cause no mode switch. |
| 513/15 Z (`vcr_rt_zcheck`) | WARN | **No** for the automatic Z: it is in video memory and has the back buffer's size and pitch. A Z that cannot be allocated fails earlier, in CreateSurface (runtime). |
| all `MAX_CTX` = 32 contexts in use | **silent** | only with a context leak (none known); same flap if it happens |
| FPU save area (`EngAllocMem`) failed | **silent** | only under pool exhaustion; same flap |

`Dd_CreateSurfaceEx` always answers `DD_OK`: a full handle table is logged, not refused
(`vcrdd_d3d.c:95-116`, G42). So it is not a flap source.

## 4. Approach

### 4.1 The contract: every pair the runtime accepts is drawn (G10 implements it, this item pins it)

- **Caps stay as they are.** D16 stays listed at every desktop. 4a9793b dropped it at the 32 bpp
  desktop and broke the proven 16 bpp fullscreen device, because the runtime reads the Z list at the
  desktop mode (`vcr_rtfmt.h:179-191`). E86 `e7` shows that a runtime-side Z refusal flaps anyway.
- **G10 makes X8R8G8B8 + D16 draw.** The recommended way is the vendor's: a 16-bit Z requested
  while the primary is 32 bpp gets 32-bit storage (`VH5/DDSURF.C:592-626`: "Napalm cannot handle a
  different depth zbuffer and primary"). After the fix, `surf_zbits` reads 32 and the existing 32/32
  rule draws it. 3dfx itself took the depth-mismatch error out of its `ContextCreate` on
  2000-04-06 (`VH5/D3CONTXT.C`, revision 12).
- **Why the primary depth is the right input.**
  - For a D3D8/9 fullscreen device, the mode is set *before* the Z is created (ring order in §1).
  - For a windowed device, the back buffer must be the desktop format.
  - So in every CreateDevice case, primary depth = back-buffer depth.
  - G10 owns the choice between this and a hidden aux buffer. This item needs only "matched ⇒ drawn".
- **The invariant becomes a host test** (§7) over three axes: render depths offered
  (`DDBD_16`, plus `DDBD_32` with rt32), × the Z list (`vcr_rt_zlist`), × the runtime's
  *measured* matching table, × every `vcr_timings` mode:
  - with G10's switch **on**, no matched pair is refused;
  - with it **off**, exactly one matched pair is refused, (32, 16). That is today's state, pinned so
    that any *new* post-mode-set refusal fails the suite.

### 4.2 Loud refusals (a HAL change, failure path only)

In `KMD/display/vcrdd_d3d.c`:

- Log the two silent refusals as **513 what 24**, WARN:
  - `ContextCreate refused: all 32 contexts in use (pid N)` (b=1, c=MAX_CTX, d=pid);
  - `ContextCreate refused: no memory for a N-byte FPU save area (pid N)` (b=2, c=bytes, d=pid).
- When the render target is a flip chain (`lpDDSLcl->ddsCaps.dwCaps & DDSCAPS_FLIP`), add one
  suffix to the 12/15/17/24 text: `- a fullscreen flip chain: its mode is already set, and a refusal
  here makes the runtime restore the desktop (two mode changes on the monitor)`.
  - The D3D8 fullscreen back buffer carries DDSCAPS_FLIP: caps 0x1000601c at handle 2 in §1.
    A windowed back buffer is a plain offscreen surface.
  - Leave the a..d fields alone, so old decoders keep their meaning.
- `KMD/include/vcr_events.h` 513 description: append
  `24 context refused: b=1 no free context (c=MAX_CTX) 2 no FPU save area (c=bytes) d=pid`.
  The code is appended, never renumbered. 1-23 are in use.

### 4.3 Tools that refuse to cause re-syncs, and count the ones that happen

**`KMD/tools/d3dprobe.c`**

- **`caps` gains `"hal"` per zmatch cell.** Where the cell's back-buffer format equals the desktop
  format, create a hidden 64x64 *windowed* device with that auto Z, release it, and report 1/0.
  Otherwise report `null` ("not askable without a switch").
  - A cell with `match:1, hal:0` is a FAIL line: "the runtime promises this pair, the HAL refuses
    it - a fullscreen CreateDevice would switch the monitor and fail". rc 1.
  - This shows G10's bug on `.124` with zero mode switches. It also states the §4.1 invariant on
    silicon at the cost of a caps run.
- **A fullscreen pre-flight**, `static HRESULT preflight(...)`, in its own function and windowed
  only. `test_a_switch_in_is_recorded_even_when_it_failed`
  (`WT/tests/python/test_vcr_kmd_monitor_safety.py:393-411`) requires every `IDirect3D8_CreateDevice`
  in `main` to be followed by `vcr_pace_after_switch`, so a windowed CreateDevice must not sit there.
  It runs before `vcr_pace_before_switch()` (`d3dprobe.c:1464`) and checks:
  1. `CheckDeviceFormat(HAL, bbfmt, DEPTHSTENCIL, SURFACE, zfmt)`. This catches E86 `e7`.
  2. `CheckDepthStencilMatch(HAL, bbfmt, bbfmt, zfmt)`.
  3. If `bbfmt == desktop format`, the same windowed 64x64 device as `caps` with that Z. This
     catches 11-12.

  It skips steps 1 and 2 with `--noz`, and logs "HAL pairing not askable without a switch" when
  the formats differ.

  A failure ends the run **before anything switches**:
  `RESULT {"mode":..,"error":"preflight: <step> <hr>","preflight":"refused"}`, rc **3**.
- **`--expect-refusal`** is the only bypass, for the one attended refusal probe. The pre-flight still
  runs and logs its prediction; then the fullscreen CreateDevice proceeds as today.
- **A new render test, `zpair`**. It is explicit only, not in the default list. It is specified in §6.

**`KMD/tools/d3dprobe_run.py`**

- `--expect-refusal` is refused in `arg_refusal()` (`:100`) unless `--i-am-at-the-box` is given.
  That is the phrase `vcrctl sliaa` already uses. With both, the runner prints the plan before it
  connects: "this run will switch the monitor and have the device refused: 2 mode changes =
  4 timing changes within ~0.2 s".
- `--pace` defaults to 5000 for `--full`. That is the campaign rule; the 11-12 session needed the
  `ONBOX/d3dprobe_paced.py` wrapper for it. The EXECW budget is computed from it.
- rc 3 is reported as `PREFLIGHT REFUSED - nothing switched`, which is neither a pass nor a crash.
- **Re-sync accounting.** Read `REGREAD HKLM SYSTEM\CurrentControlSet\Services\vcrmp\Diag` before
  and after the run. `PhaseLog` holds 64 × {ms, code, a, b} and is flushed at every phase
  (`KMD/miniport/vcrmp_log.c:141-158`); every mode set writes MODESET_BEGIN (a=w<<16|h,
  b=bpp<<16|Hz) and MODESET_DONE (a=mode index) (`KMD/miniport/vcrmp_hw.c:670`, `:719`). Take
  the phases with index in (PhaseCount_before, PhaseCount_after], and add these RESULT fields:
  - `mode_sets`;
  - `timing_changes` (2 per mode set: the RESET_DEVICE dip, as the monitor-safety docstring already
    counts it);
  - `quick_resyncs` (a mode set whose BEGIN is < 5000 ms after the previous DONE);
  - `min_dwell_ms`;
  - `reverts`: a quick set back to the mode before the previous one (A→B→A).

  `quick_resyncs > 0` without `--expect-refusal` prints `UNPLANNED RE-SYNC` and gives rc 1.
  A window over 64 phases, or a reboot between the reads (`BootCount` differs, or the count goes
  down), gives **`"unknown"` and fails**. It never reports 0. The PhaseLog survives ring wraps,
  which matters because a game wraps the 1024-entry ring in seconds (G76).

**`KMD/tools/vcrphases.py`**

- Add pure functions `mode_sets(entries)` and `resyncs(sets, floor_ms=5000, mode_before=None)`.
  Both the runner and the sweep call them.
- Add `--resyncs`, which prints a table: mode, dwell ms, quick, revert.

**`WT/scripts/benchmarks/lan_sweep.py`** (the D3D title sweep that wrote `KMD/evidence/d3dtune_1014/*/run.out`)

- Do the same before/after read per title, and write `mode_sets`, `quick_resyncs`, `reverts` and
  `refusals` into `sweep.json`. `refusals` is the 513/12/15/17/24 entries, when the per-title ring
  is fetched.
- Classify: a quick revert with a refusal inside it is **FLAP (refusal)** and fails the title. A
  quick set without one is **app re-set**: recorded, not failed. An example already in the ring is
  the OpenGL session of pid 1892 setting 1280x960x32@60 and then @85, 2.3 s apart
  (`ONBOX/ring_start_decoded.txt` seq 23787 / 23924). Normal titles must not fail on their own
  behaviour.

### 4.4 Docs (each one is wrong today)

- **`KMD/README.md:565-567`** says a 16 bpp device with D24S8 is "refused by the D3D8 runtime,
  cleanly, with no mode set". That holds windowed (`e6`). Fullscreen (`e7`), the runtime set 640x480
  and restored 800x600 321 ms later. Correct it.
- **`KMD/README.md:474-477`**: "before the driver sees them" is true of the driver, not of the
  monitor.
- **`KMD/include/vcr_rtfmt.h:187-191`** ("costs nothing on the chip: ContextCreate refuses it ...
  expected to answer no ... unverified"): measured, the runtime answers *yes* for X8R8G8B8 + D16.
  Add that the refusal costs the monitor two mode changes, i.e. four timing changes.
- **`WT/tests/native/test_vcr_kmd_d3dseq.c:299`** ("offering both sizes is safe because ContextCreate
  asks vcr_rt_format"): safe for the chip, not for the CRT. Point to the new test.
- **`d3dprobe.c` caps comment** (`:1337-1347`): its "expected MATCH" table is wrong. State the
  measured one.
- Also update:
  - the KMD README Tools row (preflight, `hal`, `zpair`, `--resyncs`);
  - the `WT/tests/README.md` fix→test rows;
  - the `WT/docs/v56k-benchmark-plan.md` D3D status;
  - a newest-first `FIND` entry: "A D3D8 CreateDevice that fails on its depth buffer has already
    switched the CRT - four timing changes in ~0.2 s; only back-buffer/HAL refusals are free".

### 4.5 Considered and not recommended

- **A kernel hold of the revert** (e.g. `Diag\ResyncHoldMs`: wait in RESET_DEVICE until N ms after
  the previous mode set when the HAL flagged a refusal at this mode). Rejected:
  - It holds win32k's display lock and the USER lock for the whole wait, so the desktop freezes.
  - It cannot see the runtime's own Z refusals (`e7`), because nothing arms it.
  - A blanket rate limit would also pace normal titles. The GL lane's 60→85 Hz double set is
    2.3 s apart.
  - It does not reduce the number of switches; it only spreads them.
  - After G10 the only things that would arm it are leaks and pool exhaustion.

  Build it only if the accounted sweep shows a staged title flapping that G10 does not explain,
  and only on the user's decision. It would then be default-off, armed by an IOCTL from the
  refusal sites, capped at 5000 ms, PASSIVE_LEVEL only, logged as an appended event 309.
- **Deferring the physical timing change until the first present.** Rejected:
  - GDI draws the new PDEV at once, so the new layout would be scanned at the old timing.
  - It would change the proven mode-set path (123/123 modes verified).
- **Skipping the RESET_DEVICE VGA dip.** That would halve the timing changes of *every* mode
  change. It was rejected before, because RESET_DEVICE is also the VgaSave hand-off
  (`vcrmp.c:678-693`, FIND 2026-09-26). It is out of scope; listed under open questions.
- **Accepting the pair and drawing without Z.** Rejected: a wrong picture with no error is worse
  than a refusal (`vcr_rtfmt.h:117-123`).

## 6. d3dprobe checks

1. **`caps` → `zmatch.<bb>.<z>.hal`.** On the 32 bpp desktop it creates windowed devices only, so
   there are **zero mode switches**.
   - Pass: every cell with `match:1` and `hal != null` has `hal:1`.
   - Reference: today (95678704) `X8R8G8B8.D16` = `{format:1, match:1, hal:0}` → FAIL; D24X8 and
     D24S8 = hal 1; R5G6B5 cells = hal `null`.
   - After G10: all hal 1.
2. **`zpair` (render test, explicit).** For each D ∈ {D16, D24X8, D24S8}:
   - **Skip** D (named) unless `CheckDeviceFormat(DEPTHSTENCIL)` and `CheckDepthStencilMatch` accept
     it for the back buffer.
   - With the device's own target and Z, clear the colour to the sentinel magenta 0xff00ff.
   - Create a depth surface D at the back-buffer size (`CreateDepthStencilSurface`), then
     `SetRenderTarget(bb, zD)`, then clear Z only (1.0).
   - Draw the `ztest` scene (`d3dprobe.c:1132-1149`): green z 0.25 full quad, red z 0.75 full quad,
     blue z 0.10 left half, ZFUNC LESSEQUAL.
   - Read back: (180,128) must be **0x00ff00** ±8 ("far quad hidden") and (64,128) **0x0000ff** ±8
     ("near quad drawn").
   - Restore the original Z.
   - Old-buggy value: a target the HAL refuses at SETRENDERTARGET draws nothing, the Z clear
     included, so both points read the **sentinel 0xff00ff**. The sentinel stops a stale frame from
     an earlier test passing.
   - Windowed on `.124` this exercises X8R8G8B8 × {D16, D24X8, D24S8} with **zero mode switches**,
     plus the SETRENDERTARGET path (`vcrdd_d3d.c:1725-1749`, runtime report §5.1 case c).
   - Today: D16 FAIL (sentinel; ring `SETRENDERTARGET (not drawn) refused`), D24X8 and D24S8 PASS.
     After G10: 3/3.
3. **The fullscreen pre-flight.**
   - Pass: `render --full --res 640x480 --bpp 32 --zfmt d16` on today's build ends with rc 3,
     `"preflight":"refused"` and **0 mode sets** in its PhaseLog window. The reference value is the
     2 mode sets with a 109 ms dwell of 11-12 10:01:28.
   - After G10: the pre-flight passes and the run is 40/40.

## 7. Regression tests

**`WT/tests/native/test_vcr_kmd_rtmatch.c`** (new; it includes `vcr_rtfmt.h` and
`common/vcr_modes.c`, as `test_vcr_kmd_modes.c` does).

- `runtime_matches(rt, z)` is a table of the **measured** cells only, with its source cited
  (`caps_124.txt` 2026-11-12, `silicon/d3d32_step16/d3d32_caps_.txt` 2026-09-28): X8R8G8B8 matches
  D16, D24X8 and D24S8; R5G6B5 matches D16 only.
- `every_pair_the_runtime_matches_is_drawn_at_every_listed_mode`. For rt32 ∈ {0,1}, every offered
  depth and every listed Z the runtime matches:
  - `st = <G10 storage rule>(rt32, primary = rt, z)`;
  - check `vcr_rt_format(rt32, rt, st) != VCR_RT_REFUSED`;
  - for every `vcr_timings[i]`, check `vcr_rt_rtcheck(fmt, w, w*rt/8) == VCR_RT_OK` and
    `vcr_rt_zcheck(fmt, w, h, 1, 1, w*st/8, w, h) == VCR_RT_OK`.
- With G10's switch **off**: exactly one matched pair is refused, and it is (32, 16). With it
  **on**: zero.
- `the_x8r8g8b8_d16_pair_was_refused_after_the_mode_set` asserts both values:
  - **old**: `vcr_rt_format(1, 32, 16) == VCR_RT_REFUSED` with the Z kept at its requested
    16 bits;
  - **fixed**: the stored Z is 32, and `vcr_rt_format(1, 32, 32) == VCR_RT_32`;
  - unchanged: 16 bpp + D16 stays 16, no rt32 stays 16, and (1, 16, 32) stays 16 (be58b7d).

**`WT/tests/python/test_vcr_kmd_resync.py`** (new: the analyzer in `vcrphases.py`)

- The 11-12 window, given as PhaseLog phases (83009831 BEGIN 640x480x32@85, 83009862 DONE 144,
  83009971 BEGIN 1280x1024x32@85, 83010002 DONE 159), must give `mode_sets=2`,
  `timing_changes=4`, `quick_resyncs=1`, `min_dwell_ms=109` and `reverts=1`. The old tools
  reported no figure for this window: d3dprobe_run.py's RESULT had no such field.
- A paced d3dprobe window (dwell ≥ 5000) gives quick 0.
- The GL double set (75242015 → 75244317, same size, other refresh) gives quick 1, revert 0,
  classified "app re-set".
- More than 64 phases, or a BootCount change, gives `None` ("unknown"), never 0.

**`WT/tests/python/test_vcr_kmd_monitor_safety.py`** (additions)

- In `main`, `preflight(` comes before `vcr_pace_before_switch()` in the fullscreen path, and
  `g_expect_refusal` is its only bypass.
- The `preflight` function sets `Windowed = TRUE`, contains no `D3DSWAPEFFECT_FLIP` and no
  `vcr_pace_` calls, and so cannot switch.
- `caps`' `hal` device is windowed too.
- `d3dprobe_run.py` refuses `--expect-refusal` without `--i-am-at-the-box`.
- `d3dprobe_run.py` and `lan_sweep.py` both call `vcrphases.resyncs`.

**`WT/tests/python/test_vcr_kmd_d3d.py`** (addition)

## 9. Risk to proven paths

- **16 bpp default path, flip path, SLI, Glide/OpenGL coexistence: untouched.** No register write,
  cap, format or mode-set step changes in A or B.
- **The pre-flight and `caps` `hal`** create small windowed devices on the desktop PDEV. That is
  the proven windowed path (42/42). They draw nothing. The one known hazard is G01's stale Glide
  FIFO: surfaces low in VRAM inside the FIFO window plus host writes caused the 2D give-up. The
  pre-flight writes nothing, and step 1a checks the FIFO first.
- **The accounting** reads the registry through the agent: `REGREAD`, no ExtEscape, no vcrctl. It
  runs before and after a title, never during one.
- **False failures.** Normal titles re-set modes, as the GL lane's 60→85 Hz pair shows. Only a
  quick revert with a refusal inside it fails a run; the rest is recorded.
- **Dependency risk (G10, not this item).** A D16 stored at 32 bits means that an application which
  *locks* a D16 (the runtime exposes it as D16_LOCKABLE for 121a:0009, `reports/runtime.md` §4.2-4.3)
  reads a 32-bit layout. No staged title is known to lock Z.
- **G02 interplay.** If G02 makes `ContextCreate` refuse on a dead engine, that is a new refusal
  after the mode set. The §7 matrix does not cover it, because it is not about formats. It must log
  through 513/24-style WARN with the flip-chain suffix. Where it can, the give-up should be expressed
  before the mode set, as "HAL not offered" on the desktop PDEV; 10:11 shows that path switches
  nothing.
