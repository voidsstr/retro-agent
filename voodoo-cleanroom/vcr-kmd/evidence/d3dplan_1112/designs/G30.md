# G30: dithering is left on for 32 bpp targets

Design for one item of the Direct3D plan for the Voodoo 5 6000 on `.124` (vcr-kmd HAL).
Written 2026-11-12 from code, docs, the vendor source and committed evidence. No fleet box was contacted.

Path shorthands:
- `KMD` = `voodoo-cleanroom/vcr-kmd`; `WT` = the `v56k-bench` worktree root.
- `H5` = `retro-3dfx/3dfx Driver Code/H5`; `VH5` = `H5/W2K/Src/Video/Displays/H5` (3dfx's W2K display driver and D3D HAL).
- `CSIM` = `H5/CSIM` (3dfx's C simulator of the chip).

## 0. Verdict

**The gap is real, and the fix is one line of policy.**
- `compute_regs` sets fbzMode bit 8 whenever `D3DRENDERSTATE_DITHERENABLE` is non-zero, at every target depth (`KMD/display/vcrdd_d3d.c:978-980`).
- SPEC §8.25 says *"fbzMode bit(8) must be cleared when 32-bit color rendering is selected (renderMode[1:0]=0x2)"* (L3254).
- Our own h5 Glide clears it at 32 bpp (`G5/gglide.c:3905-3908`).

**What the chip does with the bit at 32 bpp has never been measured, and the evidence leans towards "nothing".** Two points support that:
- 3dfx's C model of the chip skips the whole dither stage for a 32 bpp pixel: `if (bpp != SST_RM_32BPP) { // if 32bpp just skip all this crap!` (`CSIM/FBI.C:1455`).
- 3dfx's shipped D3D HAL set the bit on 32 bpp targets with no depth check. A case-insensitive search of `H5/W2K` and `H5/Win9x` finds no other place that clears it (§2.3).

The spec still says "must", and it uses the softer word "ignored" for the neighbouring bit 19 in the same register description (L3268). The fix therefore makes our output independent of a chip behaviour nobody has measured. It costs one compare per state computation.

**No staged title is known to send the bit to a 32 bpp target today** (static scan, §3):
- UT2003 and UT2004 turn dithering on unconditionally, but they render at 16 bpp until G19 is fixed.
- Halo turns it off.
- Red Faction turns it on only when its colour depth is 16, and never on an ATI adapter.
- Max Payne very probably dithers only at 16 bpp.
- Thief II (NewDark), H&D and the DX5/6 titles are unknown. A once-per-context event counts them on the box (§4.3).

The gap's list "Halo, Thief II, H&D, Max Payne" is the list of titles that run at 32 bpp. It is not a list of titles that dither.

**Design:**
- A Win32-free helper `vcr_fbz_dither(fmt, enable)` returns no dither bits whenever the target programs renderMode[1:0] = 2. `compute_regs` takes its fbzMode dither bits from it.
- There is no new Diag switch. A 32 bpp target exists only with `Diag\D3D32 = 1`, which is default OFF, so a fresh install is byte-for-byte unchanged.
- Two d3dprobe tests: `dither32` is the fix and also the measurement of the old behaviour; `dither16` is the 16 bpp control.
- A native host test.
- The "2x2 plus subtraction at 16 bpp" idea is kept apart as an optional, default-OFF step 2 (§4.5). It has no correctness reason, it would change the proven 16 bpp lane, and the vendors' reason for 2x2 does not carry over to vcr-kmd.

**Priority P2.** The fix is spec compliance and the visible effect is unknown. Raise it to **P1** if the probe on the *current* build (step A in §8) shows the chip honours the bit at 32 bpp. In that case G30 becomes a prerequisite of G19: once UE2 renders at 32 bpp, it would otherwise keep its dither pattern on a 32 bpp frame.

**Correction to `reports/hw.md` Q17.** The report says Glide "forces 2x2 + dither-subtract". Glide forces 2x2, but subtraction is on only when `SSTH3_ALPHADITHERMODE` = 3 ("Smoother"). The default is 1 ("Optimal": no subtraction; `G5/gpci.c:1837-1846`). 3dfx's D3D HAL behaves the same way (§2.3).

## 1. The code today (read 2026-11-12)

**How fbzMode is built and written:**
- `compute_regs` (`KMD/display/vcrdd_d3d.c:921-1029`) starts from `r->fbzMode = FZ_RECTCLIP | FZ_RGBWRITE;`, then runs `if (c->rs[D3DRENDERSTATE_DITHERENABLE]) r->fbzMode |= FZ_DITHER;` (`:978-980`). It never looks at the target's depth.
- The dither bits:
  - `FZ_DITHER` is bit 8 (`KMD/include/vcr_3dregs.h:111`).
  - `FZ_DITHER2X2` (bit 11, `:114`) is defined but never set, so the matrix is always 4x4.
  - Bit 19 (dither subtraction) has no define and is never set.
- `VcrDd3dState` writes fbzMode exactly as computed (`KMD/display/vcrdd_3d.c:79`).
- `prepare` calls `compute_regs` at the first triangle of every DrawPrimitives2 call and after any state change (`vcrdd_d3d.c:1322-1365`).

**`compute_regs` already depends on the target.** Depth testing is enabled only when `c->target.z_on` (`:986`). The target is current whenever `compute_regs` runs:
- it is re-read at every DP2 and Clear2 call (`target_of`, `:1849-1855`, `:1884`);
- SETRENDERTARGET sets `c->dirty = 1; w->prepared = 0;` (`:1741-1742`);
- a clear sets `dirty` too (`:1419`).

**Which targets exist.** A 32 bpp target exists only on a VSA-100 with `Diag\D3D32 = 1` (`pd->rt32`, `vcr_rt_format`, `KMD/include/vcr_rtfmt.h:79-87`). The switch is armed on `.124` and off by default.

**Clears never dither.**
- `VcrDd3dClear` writes its own `fbzMode = FZ_RECTCLIP | FZ_RGBWRITE [| FZ_ZAWRITE]` (`vcrdd_3d.c:139-158`).
- On SDRAM, a fastfill's dithering follows fbzMode[8] alone (SPEC L2701), and the 6000 uses SDRAM (`reports/hw.md` §2.3).
- So 16 bpp clears are truncated today and stay so.

**Default state.**
- `c->rs` is zeroed at ContextCreate (`:1128`), and the whole context is zeroed before that (`:1176`).
- D3D's own default for DITHERENABLE is FALSE.
- Only an application that sets the state gets the bit.

**Caps.** They advertise `D3DPRASTERCAPS_DITHER` (`:2019`), and that stays correct (§4.4).

**Nothing has ever tested this bit.**
- d3dprobe sets `D3DRS_DITHERENABLE FALSE` once after CreateDevice (`KMD/tools/d3dprobe.c:1495`), and no test turns it on.
- Every 32 bpp probe result on silicon ran with dither off. That includes windowed at the 32 bpp desktop: `KMD/evidence/silicon/d3d32_step16/d3d32_render___bpp_32_.txt`, fmt 22 = X8R8G8B8, zfmt 77.

## 2. What the hardware and the references say

### 2.1 The spec

| field | text | SPEC |
|---|---|---|
| fbzMode[8] | enable dithering | L3210 |
| fbzMode[11] | 0 = 4x4 ordered, 1 = 2x2 ordered | L3213 |
| fbzMode[19] | alpha-blending dither subtraction | L3220 |
| fbzMode[8] at 32 bpp | *"must be cleared when 32-bit color rendering is selected (renderMode[1:0]=0x2)"* | L3254 |
| fbzMode[19] at 32 bpp | *"is ignored when 32-bit color rendering is selected"* | L3268 |
| 32 bpp storage | *"the data is stored directly into the frame buffer with no dithering applied"*. This is in §3.3, which opens "horribly out-of-date ... ignore this section" (L539). | L582 |
| dither rotation | renderMode[25] with fogMode[19:12]: *"disable dither rotation for 32BPP rendering"*. A hardware bug breaks it for FASTFILL and 3D LFBs. | L3301, L3318, L3346, L3356, L6254 |
| SLI | *"Dithering does not work properly when the 'band' height is 1"* | L6244 |

The spec states a rule and does not say what breaks if the rule is not followed.

### 2.2 3dfx's C model of the chip (CSIM)

- **Pipeline order.** Dithering is the last step before the write masks: *"8) dither (always do this last)"* (`CSIM/FBI.C:125-137`).
- **32 bpp skips it.** At `CSIM/FBI.C:1455`, `if (bpp != SST_RM_32BPP) { // if 32bpp just skip all this crap!` encloses both the ordered dither (`:1459-1491`) and the plain truncation to 565/555. A 32 bpp pixel is stored with the 8-bit channels as blended, whatever fbzMode[8] says.
- **The 32 bpp blend path has no dither subtraction.** An error for it, *"You've gone bonkers! Why dither in 32bpp?"*, is commented out (`:1386-1387`). That reads as: driver command streams replayed through the model carried the bits (inferred).
- **The 16 bpp arithmetic.**
  - A per-channel normalise-and-add is at `CSIM/RGBFMT.C:252-264` (`_sstDit5`, `_sstDit6`).
  - The matrix is #0 (`CSIM/FBI.C:152-157`), the same as SPEC's "Matrix #0 (default)" (L3322-3326).
  - The 2x2 matrix is the top-left 2x2 of #0, with the low normalisation bits masked.
  - §6.3 builds the probe's reference from this model.
- **SLI and dithering.** The band height must be at least the matrix height: 2 lines for 2x2, 4 for 4x4 (`CSIM/GO.C:1136-1150`). That is stricter than SPEC's "not 1".
- **Fog dither is a different feature.** It adds the 4x4 matrix to the fog-table interpolation at *every* depth (`CSIM/FBI.C:1167`).

### 2.3 Our Glide and 3dfx's D3D HAL

**h5 Glide, `_grDitherMode` (`G5/gglide.c:3874-3918`):**
- It clears ENDITHER | DITHER2x2 | ENDITHERSUBTRACT (`:3890`).
- For both GR_DITHER_2x2 and GR_DITHER_4x4 it sets all three, *"Forcing dither rendering matrix to 2x2"* (`:3885`, `:3898`).
- It removes the subtraction when `disableDitherSub` is set (`:3900`).
- **At 32 bpp it clears all three** (`:3905-3908`).
- `disableDitherSub` is TRUE unless `SSTH3_ALPHADITHERMODE` = 3. The default is 1, OPTIMAL (`G5/gpci.c:1837-1846`).
- Init calls `grDitherMode(GR_DITHER_2x2)` (`G5/gsst.c:977`).
- **Glide's 16 bpp default is therefore 2x2 without subtraction.**

**3dfx's D3D HAL, `ditherEnable` (`VH5/D3RSTATE.C:3488-3534`):**
- DITHER2x2 is always set (`:3500`, and in `initNewRC` at `:3758-3761`).
- ENDITHER follows DITHERENABLE (`:3506`).
- Subtraction is on only for ALPHADITHERMODE 3. `VH5/REGKEYS.H:158-163` reads *"1: Optimal (default)- No dither subtraction ... 3: Smoother"*; the value is read at `VH5/DDINIT.C:833-835`.
- Both bits are cleared when dithering is off (`:3530`).
- **There is no depth check.** `grep -r -i ENDITHER` over `H5/W2K` and `H5/Win9x` finds only these lines, and no `fbzMode &=` anywhere in `VH5/*.C` touches bit 8 (case-insensitive). 3dfx's retail D3D HAL therefore wrote fbzMode[8] on every 32 bpp target whose application enabled dither. It did so on every V5, and 32 bpp rendering was on by default (`VH5/D3INIT.C:1036-1044`, `32BPP_RENDERING` = 1).

**What follows.** The retail HAL shipped the bit at 32 bpp, and the C model ignores it. Both suggest the silicon ignores it too (inferred). The fix is correct either way: it is what the spec requires and what our Glide does, and a pixel-format rule should not rest on an unmeasured "probably".

### 2.4 Out of scope, left as is

- **fogMode bit 6, `FM_DITHER`** (`vcr_3dregs.h:140`, set together with fog at `vcrdd_d3d.c:1006`).
  - SPEC calls it *"fogdither control, dither the fog blending component"* (L2851).
  - It dithers the fog factor's interpolation. CSIM applies it at every depth (`FBI.C:1167`), and 3dfx's D3D sets it at every depth (`VH5/D3FOG.C:218-226`, `ENFOGGING | ... | FOG_DITHER`).
  - L3254 does not cover it. G31 and G32 own the fog path.
- **Dither rotation** (renderMode[25], fogMode[19:12]).
  - Glide's AA paths program the rotation selects (`G5/distate.c:2483-2504`).
  - D3D writes renderMode whole at every target setup (`vcr_3d_target_seq` → `vcr_rt_rendermode`, bit 25 = 0). It writes fogMode whole at every state emit (`vcrdd_3d.c:81`), so bits 19:12 = 0.
  - A Glide session's rotation therefore never reaches a D3D draw. Keep it that way: AA is off by user choice, and rotation must stay off for 32 bpp and for fastfill.
- **The 16 bpp matrix and subtraction** are covered by §4.5.

## 3. Which staged titles send DITHERENABLE, and at what depth

**Method.** A static scan of the staged binaries, disassembled with objdump (the copies in this session's shared scratchpad). It looks for an immediate `0x1a` (D3DRS_DITHERENABLE = 26) pushed into SetRenderState through the device vtable: D3D8 `+0xC8`, D3D9 `+0xE4`, or the title's own render-state wrapper. It sees direct calls only. Table-driven, state-block and DX5 execute-buffer paths are invisible to it.

| title (API, binary) | site (measured) | what it sets | reaches a 32 bpp target? |
|---|---|---|---|
| UT2003 (D3D8, `System/D3DDrv.dll`) | `0x10010831`: `push 1; push 0x1a; call [vtbl+0xC8]` | TRUE, unconditionally | yes once it renders 32 bpp. Today it renders 16 bpp (G19, `reports/visual.md` V-08) |
| UT2004 (D3D8, `System/D3DDrv.dll`) | `0x10011f45`: the same | TRUE, unconditionally | the same |
| Red Faction (D3D8, `rf.exe`) | `0x544c02-0x544c37` | TRUE iff its colour-depth global `[0x17c7b48]` == 16 and the adapter vendor `[0x1cd4288]` ≠ 0x1002 (ATI); otherwise FALSE | no |
| Max Payne (D3D8, `e2driver/e2_d3d8_driver_mfc.dll`) | `0x1002875a-0x10028774`, through its state-cache method `+4` | TRUE iff a device field `[+0x10]` < 3; otherwise 0 (`ebx`, zeroed at `0x10028623`) | probably not: the field is plausibly the bytes per pixel (inferred) |
| Halo (D3D9, `halo.exe`) | `0x516458`: `push 0; push 0x1a; call [vtbl+0xE4]` | FALSE, at its only site | no |
| Thief II NewDark (D3D9, `Thief2.exe`) | `0x6035c7`, from a saved state block; `0x605cf7`, from per-draw flags `((f >> 21) & 1) && (f & 0x40)` | conditional | unknown: count it on the box |
| H&D (`Bin/igraph2.dll`), System Shock 2 (`shock2.exe`), Thief Gold (`thief.exe`), AvP, BF1942 | no direct site found | none found | unknown |

**What this means:**
- **UE2 is the case that matters.** It always asks for dithering, and V-08 already sees *"an ordered-dither pattern visible on the menu backdrop's dark gradients"* at 16 bpp. When G19 moves UE2 to 32 bpp, that backdrop must come out clean. If the chip honours fbzMode[8] at 32 bpp, a G19 fix without G30 would keep a dither pattern on a 32 bpp frame.
- **Windowed clients.** Any windowed D3D client on `.124`'s 32 bpp desktop takes a 32 bpp target, for example DX8 SDK samples, which enable dithering (inferred).
- **Unrelated items:**
  - V-12, the Halo square with *"4 dithered colours"* (`reports/visual.md`), is a DXT block's four colours. Halo sets DITHERENABLE FALSE.
  - Max Payne's freeze (G04) is not expected to involve this bit, since Max Payne very probably does not dither at 32 bpp.

## 4. Design

### 4.1 The rule, in one Win32-free header: `KMD/include/vcr_dither.h` (new)

The header is integer only and Win32-free, and it includes `vcr_rtfmt.h`. Three code bases compile it:
- the display driver (built with `-mgeneral-regs-only`: no floats here);
- d3dprobe;
- `WT/tests/native/test_vcr_kmd_dither.c`.

```c
/* fbzMode's dither bits for a Direct3D draw into a target of format fmt
 * (VCR_RT_*), with D3DRENDERSTATE_DITHERENABLE = enable (any non-zero value
 * is TRUE, as compute_regs has always read it).
 * SPEC 8.25 L3254: "fbzMode bit(8) must be cleared when 32-bit color
 * rendering is selected (renderMode[1:0]=0x2)"; bit 19 is ignored there
 * (L3268); h5 Glide _grDitherMode clears 8, 11 and 19 at 32 bpp.
 * Keyed on the renderMode the target itself programs (vcr_rt_rendermode),
 * so a future 32 bpp format (G10's promoted Z keeps VCR_RT_32) inherits the
 * rule, and a 1555 target (G93, renderMode 1) dithers as it should. */
static __inline unsigned vcr_fbz_dither(unsigned fmt, unsigned enable)
{
    if (!enable || (vcr_rt_rendermode(fmt) & 3u) == RM_32BPP)
        return 0;
    return FZ_DITHER;           /* 4x4, no subtraction: the proven 16 bpp value */
}

/* the matrix height a dithering fbzMode needs from an SLI band (CSIM GO.C
 * 1136-1150; SPEC L6244): G51 asserts band lines >= this. 0: no dither. */
static __inline unsigned vcr_fbz_dither_rows(unsigned fbz)
{
    return !(fbz & FZ_DITHER) ? 0u : (fbz & FZ_DITHER2X2) ? 2u : 4u;
}
```

The same header carries the 16 bpp reference model that d3dprobe's `dither16` check and the native test use (§6.3).

`KMD/include/vcr_3dregs.h` gains `#define FZ_DITHERSUB (1u << 19)`, which is h3defs.h `SST_ENDITHERSUBTRACT`. Nothing sets it in step 1. Step 2 and the 32 bpp invariant test use it.

### 4.2 `compute_regs` (`KMD/display/vcrdd_d3d.c:978-980`)

```c
-    r->fbzMode = FZ_RECTCLIP | FZ_RGBWRITE;
-    if (c->rs[D3DRENDERSTATE_DITHERENABLE])
-        r->fbzMode |= FZ_DITHER;
+    /* dithering at 16 bpp only: SPEC 8.25 L3254 (include/vcr_dither.h) */
+    dith = vcr_fbz_dither(c->target.fmt, c->rs[D3DRENDERSTATE_DITHERENABLE]);
+    r->fbzMode = FZ_RECTCLIP | FZ_RGBWRITE | dith;
+    if (c->rs[D3DRENDERSTATE_DITHERENABLE] && !dith && !c->dither32_noted) {
+        c->dither32_noted = 1;                  /* once per context (4.3) */
+        VcrDd(VCR_LV_INFO, VCR_EV_DD_D3D, 24, c->rs[D3DRENDERSTATE_DITHERENABLE],
+              c->target.rt_off, c->dp2s,
+              "DITHERENABLE %u on a %u bpp target: not dithered (fbzMode[8] clear)",
+              c->rs[D3DRENDERSTATE_DITHERENABLE], c->target.fmt);
+    }
```

- `vcr_d3dctx` gains `ULONG dither32_noted;`. The context is zeroed at creation (`:1176`).
- `#include "../include/vcr_dither.h"` is added beside the other includes.
- **Nothing else changes.** The write count and order in `VcrDd3dState` are the same. Clears, the target sequence, fog and the caps are untouched.

### 4.3 One INFO event per context: event 513, `what` 24

The event uses the next free `what` code: 24 at the time of writing, since 1-23 are used.
- Fields: b = the DITHERENABLE value, c = the target offset, d = the DP2 count.
- Add the code to the 513 description in `KMD/include/vcr_events.h`. Adding a `what` code renumbers nothing.
- **Purpose.** During step C (§8), it tells which titles send dither to a 32 bpp target: Thief II, H&D and the DX5/6 titles the static scan cannot see.
- **Cost.** One flag test per `compute_regs`. Nothing per triangle. The event is not a DEBUG trace, so it does not add to G52.

### 4.4 Caps, passes and the old path

**Caps: no change.**
- `D3DPRASTERCAPS_DITHER` stays. Dithering is honoured wherever the target has fewer bits per channel than the pipeline.
- At 32 bpp there is nothing to dither to. That is how drivers of the period treated DITHERENABLE on 8-bit-per-channel targets (inferred).
- The runtime does not validate the state against the cap.

**Passes.** Single pass. The register writes are the same in count and order. No multipass.

**The old path.**
- With `Diag\D3D32` off, which is a fresh install, the only formats `compute_regs` ever sees are `VCR_RT_16` and `VCR_RT_REFUSED`, and nothing draws into a refused target.
- For both, `vcr_fbz_dither` returns exactly what the two removed lines produced: `FZ_DITHER` for any non-zero value, 0 for zero. The register stream is byte-for-byte unchanged, which the native test pins (§7).
- A Banshee or Voodoo3 renders 16 bpp only and is unchanged for the same reason.

### 4.5 Step 2 (optional, separate change, P3, default OFF): the 16 bpp matrix

The gap suggests "consider 2x2 plus subtraction at 16 bpp". The recommendation is **not to change the default**:

1. **No correctness issue.** D3D defines no dither matrix. 4x4 without subtraction is a valid D3D dither.
2. **It would change the proven lane.** Every 16 bpp title that dithers would get different pixels: UE2 and Red Faction today, and Max Payne at 16 bpp.
3. **The vendors' reason does not apply to vcr-kmd.** 3dfx's 2x2 belongs with its *overlay* video filter. vidProcCfg[17:16] = 1 is *"2x2 dither subtract followed by 2x2 box filter (for 3d only)"* (SPEC L4244-4247), and `OVERLAYMODE` "Optimal" uses that filter below 1024x768 (`VH5/REGKEYS.H:153-157`). vcr-kmd shows D3D frames on the desktop surface, because flips move `vidDesktopStartAddr` (G54), so no filter ever sees the pattern.
4. **Subtraction was opt-in in both vendor stacks** (§2.3).

**If the user wants the vendor look anyway:**
- **Switch.** Add `Diag\D3DDither`, read at boot like `D3D32`, through the next free `VCR_INFO_F_*` bits. Values:

  | value | matrix | subtraction | note |
  |---|---|---|---|
  | absent or 0 | 4x4 | no | today |
  | 1 | 2x2 | no | 3dfx's D3D HAL and our Glide |
  | 2 | 2x2 | yes | the vendors' "Smoother" |
  | 3 | 4x4 | yes | |

- **Helper.** `vcr_fbz_dither` gains a `mode` argument. At 32 bpp every mode still returns 0, as Glide clears 8, 11 and 19.
- **Decision.** By eye on the CRT, at UT2004 16 bpp (V-08's backdrop), one value per clean boot. `dither16` (§6.2) names the matrix the chip actually used.

**SLI.** When G51 brings SLI to D3D, its band height must be at least `vcr_fbz_dither_rows(fbzMode)`: 4 lines for 4x4, 2 for 2x2. 3dfx's SLI bands are 16 or 32 lines (`VH5/DDFXNT.C:3017`), so either matrix fits. A 32 bpp target never dithers after this fix, which takes it out of that constraint.

## 5. Gating

**No new Diag switch for step 1. Safe to land default-on inside the `D3D32` gate.**
- **Reachability.** The change is reachable only through a 32 bpp target, and a 32 bpp target exists only with `Diag\D3D32 = 1`, which is default OFF. With the switch off, the HAL's register stream is byte-for-byte the proven one (native test).
- **Effect with D3D32 armed.** It removes one bit the spec requires clear. The condition is taken from the same `vcr_rt_rendermode` value the target writes.
- **No kill switch.** A switch that put a forbidden bit back would be a kill switch for a spec violation, and G80 is already about undocumented ones.
- **Proof.** One supervised clean boot runs `dither32` on the new build (§8). G30 must be proven **before G20 makes `D3D32` default-on**, so the 32 bpp lane becomes the default only once it follows the spec.
- **Deploy rules.** A driver deploy is a vcrdd.dll swap plus `safe-reboot.py` after an activation check, and step 1 is one driver change with no Diag change in that boot. Prefer a build whose only change from 95678704 is G30. If it is batched, batch it only with items that are themselves default-OFF.
- **Step 2.** Behind its own default-OFF `Diag\D3DDither`, one value per clean boot.

## 6. d3dprobe tests (`KMD/tools/d3dprobe.c`)

**Placement.** Both tests are explicit, like the D3DBigTex tests, and stay out of the default list, so the documented pass counts do not move. `d3dprobe_run.py` fails a run in which an explicitly named test was SKIPPED. So run `dither32` only on a 32 bpp target and `dither16` only on a 16 bpp one.

**Shared rules for both:**
- They draw untextured (`untextured()`).
- DITHERENABLE is set to TRUE only around the draw and back to FALSE afterwards, the probe's global default from `:1495`.
- They use a new helper `expect_block(test, what, x0, y0, w, h, want_fn)`. It compares every pixel of a block with tolerance 0 and writes ONE check record. The record has the existing `test, at, x, y, got, want, ok` fields, with x, y, got and want taken from the first wrong pixel (or the block origin when all are right), plus `"wrong": <count>`.
- The block is 16x16 at (64,64)-(79,79). It lies inside the quad `[Q0, Q1)` = `[32, 224)`, away from the edges, and starts at a multiple of 4, so every phase of both matrices appears 16 or 64 times.
- Build: d3dprobe gains `-Iinclude`, and `include/vcr_dither.h` becomes a prerequisite of `$(OUT)/d3dprobe.exe` (`KMD/Makefile:101-102`).

### 6.1 `dither32`: the fix, and a measurement of the current build

**Condition.** The test is skipped unless the back buffer is `D3DFMT_X8R8G8B8` or `A8R8G8B8`. Windowed on `.124` it uses the 32 bpp desktop and needs no mode switch.

**Draws:** the same scene four times, as separate frames.
1. A flat quad with all four vertices `0xff868281`, DITHERENABLE TRUE.
2. The same quad with DITHERENABLE FALSE.
3. A horizontal ramp `quad_c(Q0,Q0,Q1,Q1, 0.5, 0xff000000, 0xffffffff, 0xff000000, 0xffffffff)`, DITHERENABLE TRUE.
4. The same ramp with DITHERENABLE FALSE.

**Checks, all with tolerance 0:**
- *"flat 868281, dither on"*: every pixel of the 16x16 block reads `0x868281`.
- *"flat 868281, dither off"*: the same.
  - This is the control: the colour path itself is exact on this target.
  - It also catches a void run. If G01's stale Glide FIFO swallows every triangle, this check fails as well, and the result is "not a G30 result".
- *"ramp, dither on"*: on row y = 128, x ∈ [33, 222]:
  - every pixel is grey (R = G = B);
  - the row never decreases;
  - every step is ≤ 2.
  
  The ramp is 255 levels over 192 pixels, so steps are 1 or 2. A 565 quantisation shows as R ≠ G (6-bit green against 5-bit red) and as steps of about 8.
- *"ramp, dither on = off"*: the two rows are identical, pixel for pixel. This is the decisive A/B. It needs no assumption about the chip's interpolation.

**Pass.** All four checks pass.

**What the result means on each build:**
- On the new build: all four must pass.
- On the *current* build, 95678704, which sets the bit, the result is the first measurement of the silicon:
  - PASS: the chip ignores bit 8 at 32 bpp, so the bug was latent.
  - FAIL: the chip dithers or quantises at 32 bpp. Record the first wrong pixel and the count, and go to P1 (§0).

### 6.2 `dither16`: the 16 bpp control

**Condition.** The test is skipped unless the back buffer is `D3DFMT_R5G6B5`.

**Draws:** the same flat `0xff868281` quad, with DITHERENABLE FALSE and then TRUE.

**Checks:**
- *"flat, dither off"*: the block equals the truncation model, `0x848284` at every pixel. SPEC L3254 says a disabled dither converts by truncation.
- *"flat, dither on"*: the block is classified against the VSA-100 models from §6.3. The record carries `"matrix": "4x4" | "2x2" | "none" | "other"`.

**Pass.** The dither-off block is exact, and the dither-on block matches the 4x4 or the 2x2 model exactly. The probe also serves other drivers as a reference, so it does not insist on one matrix.

**What vcr-kmd must show.** "4x4" while there is no `Diag\D3DDither`. **The G30 regression criterion is that the blocks and `matrix` are identical on the old and the new build.** That is the on-silicon proof that the 16 bpp lane did not change.

If the chip's arithmetic differs from the model (`"other"`), the chip is the truth. Record the block and correct the model. The old-equals-new criterion holds either way.

### 6.3 The reference model (in `vcr_dither.h`)

The model is our own code, written from the arithmetic in 3dfx's C model.
- **Validation.** During this design it was compiled and compared with that arithmetic over every n ∈ 0..255 and every threshold d ∈ 0..15, for both channel widths and both matrices: **0 mismatches**.
- **Provenance.** The shipped test pins literal values only (§7). No vendor code is copied.

```c
#define VCR_DM_OFF  0u      /* truncation (fbzMode[8] clear) */
#define VCR_DM_4X4  1u      /* fbzMode[8] */
#define VCR_DM_2X2  2u      /* fbzMode[8] + [11] */
static const unsigned char vcr_dm0[4][4] = {         /* SPEC "Matrix #0", L3322-3326 */
    { 0, 8, 2, 10 }, { 12, 4, 14, 6 }, { 3, 11, 1, 9 }, { 15, 7, 13, 5 } };

/* one channel: 0..255 normalised onto (2^bits - 1) * 16 + 15, threshold added,
 * integer part kept; the 2x2 matrix masks the low normalisation bits */
static __inline unsigned vcr_dith_ch(unsigned n, unsigned bits, unsigned d, unsigned two)
{
    unsigned sh = bits == 6 ? 2u : 1u, top = bits == 6 ? 6u : 7u;
    unsigned lo = two ? (bits == 6 ? ~3u : ~1u) : ~0u;
    return ((((n << sh) | ((n >> top) & lo)) - ((n >> 4) & lo)) + d) >> 4;
}

/* the RGB565 word a 16 bpp target stores for colour rgb at (x, y) */
static __inline unsigned vcr_dither_565(unsigned rgb, unsigned x, unsigned y, unsigned how)
{
    unsigned r = rgb >> 16 & 255, g = rgb >> 8 & 255, b = rgb & 255, d, two = how == VCR_DM_2X2;
    if (how == VCR_DM_OFF)
        return (r >> 3) << 11 | (g >> 2) << 5 | b >> 3;
    d = two ? vcr_dm0[y & 1][x & 1] : vcr_dm0[y & 3][x & 3];
    return vcr_dith_ch(r, 5, d, two) << 11 | vcr_dith_ch(g, 6, d, two) << 5 |
           vcr_dith_ch(b, 5, d, two);
}
```

**Expected readback for `0x868281`.** Values are as d3dprobe's `expand()` returns them. Rows are y & 3 and columns are x & 3, from a block origin at a multiple of 4.

| model | y=0 | y=1 | y=2 | y=3 |
|---|---|---|---|---|
| off | `848284` ×4 | `848284` ×4 | `848284` ×4 | `848284` ×4 |
| 4x4 | `84827b 848284 84827b 848284` | `8c8284 84827b 8c8684 848284` | `84827b 8c8284 84827b 848284` | `8c8684 848284 8c8284 848284` |
| 2x2 | `84827b 848284 84827b 848284` | `8c8284 84827b 8c8284 84827b` | as y=0 | as y=1 |

All three channels move with the threshold, and the 4x4 and 2x2 models differ at 6 of the 16 phases, so the classification is unambiguous. At 32 bpp, every one of these values is ≠ `0x868281`, so `dither32` detects any 565-style treatment.

## 7. Regression tests

**`WT/tests/native/test_vcr_kmd_dither.c` (new).** `run_all.sh` picks up `tests/native/test_*.c` on its own. The file includes `munit.h` and `../../voodoo-cleanroom/vcr-kmd/include/vcr_dither.h`. The old rule is spelled out as it was: `static unsigned old_rule(unsigned fmt, unsigned enable) { return enable ? FZ_DITHER : 0; }`, from `vcrdd_d3d.c:979-980` in vcrdd.dll 95678704.

**Tests:**
- **`a_32bpp_target_never_gets_the_dither_bit`.** For enable ∈ {1, 2, 0xffffffff}:
  - `vcr_fbz_dither(VCR_RT_32, e) == 0` (fixed);
  - `old_rule(VCR_RT_32, e) == 0x100` (the defect: fbzMode[8] on a 32 bpp target);
  - `vcr_rt_rendermode(VCR_RT_32) & 3 == 2` (the condition L3254 names).
- **`every_other_target_keeps_the_proven_value`.** For fmt ∈ {`VCR_RT_16`, `VCR_RT_REFUSED`} × enable ∈ {0, 1, 2, 0xffffffff}, the helper equals `old_rule`. `vcr_fbz_dither(VCR_RT_16, 1) == 0x100`: 4x4, bit 11 clear, bit 19 clear.
- **`no_format_that_programs_32bpp_dithers`.** For every fmt in 0..255 whose `vcr_rt_rendermode(fmt) & 3 == RM_32BPP`, bits 8, 11 and 19 of the result are all clear. This guards against a future format or a step 2 mode re-introducing the bug.
- **`the_probe_reference_model`.**
  - The §6.3 table for `0x868281`: off, 4x4 and 2x2, all 16 phases, after `expand()`.
  - Endpoints: `vcr_dith_ch(0, w, d, m) == 0` and `vcr_dith_ch(255, w, d, m) == 2^w - 1` for every d and both matrices.
  - These are literal values, so a broken model would make d3dprobe fail a correct chip.
- **`dither_rows_for_sli`.** 0 → 0, `FZ_DITHER` → 4, `FZ_DITHER | FZ_DITHER2X2` → 2. This is the hook for G51.

**`WT/tests/python/test_vcr_kmd_d3d.py`: one new test, `test_dither_is_cleared_on_32bpp_targets`.**
- `func(D3D, "static void compute_regs(")` contains `vcr_fbz_dither(c->target.fmt, c->rs[D3DRENDERSTATE_DITHERENABLE])`, and no longer contains `r->fbzMode |= FZ_DITHER;`.
- `FZ_DITHER` appears nowhere else in `vcrdd_d3d.c`, so there is no second writer.
- `VcrDd3dClear` in `vcrdd_3d.c` never ORs a dither bit.
- The SETRENDERTARGET case still sets `c->dirty = 1`, so the decision follows a re-target.
- `d3dprobe.c` has `dither32` and `dither16` branches, and each sets DITHERENABLE back to FALSE.
- The Makefile builds d3dprobe with `-Iinclude` and lists `include/vcr_dither.h` as its prerequisite.

**Extend `test_the_register_offsets_are_computed_from_the_gpl_header`.** It already compiles the GPL `h3defs.h` from the Glide clone together with our headers. Add `FZ_DITHER == SST_ENDITHER`, `FZ_DITHER2X2 == SST_DITHER2x2` and `FZ_DITHERSUB == SST_ENDITHERSUBTRACT` (`glide3x/h5/incsrc/h3defs.h:759, 762, 768`).

**Docs.**
- `WT/tests/README.md`: one row in the fix→test table, giving the date, the spec line, the native and Python tests, and the `d3dprobe --tests dither32` / `dither16` checks.
- `KMD/README.md`: the tools table gets the two tests; Findings gets the silicon outcome from §8.

## 9. Risk to proven paths

| path | risk | why |
|---|---|---|
| default 16 bpp lane (D3D32 off or on) | none | `vcr_fbz_dither` returns the old value for every non-32 target (native test); `dither16` must be identical before and after on silicon |
| 32 bpp lane (D3D32 armed) | very low | one bit fewer in fbzMode, same writes in the same order. A visual change only if the chip honoured the bit, and then towards correct. A bit the spec requires clear cannot plausibly hang the engine, and 3dfx's HAL wrote both values |
| clears | none | fastfill writes its own fbzMode without dither (`vcrdd_3d.c:139-158`) |
| Glide/OpenGL coexistence | none | D3D writes fbzMode whole at every state emit; Glide keeps its own shadow and clears dither at 32 bpp itself |
| SLI | none today | D3D is single-chip. For G51, a 32 bpp target never dithers, so only 16 bpp needs band ≥ matrix rows (`vcr_fbz_dither_rows`) |
| flip path | none | fbzMode is 3D state. Flips move `vidDesktopStartAddr` |
| performance | none | one compare per `compute_regs`, nothing per triangle |
| a game that relied on a 32 bpp dither artefact | negligible | no plausible case |

## 11. Open questions

1. **Does the VSA-100 ignore fbzMode[8] at 32 bpp?** The C model and the shipped vendor HAL say yes; the spec says "must be cleared". Step A answers it with one windowed probe and no mode switch.
2. **Which staged titles send DITHERENABLE to a 32 bpp target?** Thief II NewDark's flag path, H&D's LS3D, and the DX5/6 titles (JK, MotS, Shogo, SS2, Thief Gold, AvP) cannot be settled statically. The 513/24 event in step C settles them.
3. **Is Max Payne's field `[+0x10]` the bytes per pixel,** which would mean dither only at 16 bpp? The step C event answers that as well.
4. **Does the chip's 16 bpp dither match the C model exactly?** `dither16` reports `"other"` if not. The model then follows the chip. The G30 criterion (old block = new block) holds either way.
5. **Should 16 bpp move to 2x2 and/or dither subtraction (step 2)?** Only as a by-eye choice by the user. There is no correctness reason, and the vendors' reason (the overlay's 2x2 box filter) does not apply to vcr-kmd's desktop-surface flips.
6. **Is fog dither (fogMode[6]) visible at 32 bpp?** It is left as is: it is not covered by L3254, CSIM and 3dfx's D3D apply it at every depth, and G31/G32 own the fog path.
