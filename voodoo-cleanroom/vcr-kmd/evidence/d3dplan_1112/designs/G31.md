## 0. Verdict

- **The gap is real.** `vcr_fog_table` evaluates every entry at a W from 1 to 52428.8 (`KMD/common/vcr_fog.c:36-62`).
  A FOGSTART/FOGEND pair in device-Z units (at most 1) therefore puts every entry at full fog. A host prototype
  linked against the real `vcr_fog.c` gives **64 of 64 entries = 255** for LINEAR 0.2..0.8, and the same for D3D's
  default pair (0, 1). Every pixel of such a draw is the fog colour.
- **3dfx did not draw this fog; it turned it off.** 3dfx's PXLFOGLIN guard (`VH5/D3FOG.C:178`, `:376-395`) zeroes
  the table when `start < 1 && end <= 1` ("which is wrong but ... the lowest risk solution", PRS 13517, Centipede).
  We can draw it correctly with the registers we already use.
- **The fix: the same table, indexed by Z.** The detection is 3dfx's exact test, and it applies to LINEAR only. When
  it fires, each vertex sends `Wfbi = 1 - (1 - 2^-17.68)·sz` instead of its rhw. That is an affine map of its device z,
  and the setup unit iterates it exactly as it iterates Z. The 64-entry table is then built at the z each entry stands
  for. The fog unit still does a W lookup, but the value it looks up is z.
  - fogMode stays `0x41` (`ENFOGGING | FOG_DITHER`).
  - The register set, the write order and the counts are all unchanged. No caps change. Single pass.
  - In a Z table, a step between entries above 63 **saturates** instead of wrapping (SPEC §8.46, below).
- **Accuracy (host model of SPEC §8.22's lookup).** LINEAR Z fog comes out within 1/255 of D3D's per-pixel Z fog
  when FOGSTART/FOGEND fall on table entries, and within about 13/255 near a kink that does not. The second error is
  the one every W table already has.
- **Gating.** It goes behind `Diag\D3DFeat` bit **FOGZ** (provisionally bit 10, `0x400`), default OFF. With the bit
  off, the register stream is byte-identical to `95678704`.
  - On substance it qualifies for default-on: no new registers, Wfbi values in the range the proven vertex-fog path
    already sends, and the only draws that change currently render as solid fog colour.
  - By the campaign's convention it is promoted after one supervised clean boot of `fogtable_z` and `fogtable_zgrad`
    at 16 and 32 bpp.
- **Exposure: no staged `.124` title is known to send a Z range** (static scan of every D3D renderer, §3):
  - Shogo, Thief Gold, Thief II NewDark, UT2003, UT2004 and BF1942 use W-unit table fog.
  - Red Faction, Halo, Max Payne, Rainbow Six and Hidden & Dangerous use vertex fog.
  - JK and MotS have no fog.
  - Undetermined: AvP (execute buffers; it never reaches a D3D device on `.124`, G71) and System Shock 2 (game code
    encrypted in its SafeDisc v1 `.ICD`).
  - Thief II NewDark converts its fog to **device-Z units whenever a device does not report WFOG**. That is the one
    staged engine with a Z-fog code path, and the reason WFOG must stay advertised.
- **Priority P3, effort S.** Escalate to P1 or P0 the moment the in-game fog counter (§4.1) shows a title with a Z
  range.

So W is the only index. Any LINEAR pair with `end <= 1` puts every entry at or beyond `end` (w is at least 1), and
the draw is solid fog colour. EXP/EXP2 with a density meant per unit of z (the DX5 DDK suggests 0..1) is the same
failure in a milder form (§4.4). Nothing in today's code can tell the two units apart.

## 2. Reference behaviour

### 2.1 What Direct3D says the units are

- **DX5/DX6 DDK** (`DDK98`, page "Pixel fog", `dd3ddk_57s4.htm`):
  > "the hardware does a table look-up on the depth value interpolated at each pixel ... ZFront/ZBack can be 0 to 1
  > ... fStart is determined by the render state D3DRENDERSTATE_FOGTABLESTART and is in the range [0, 1]."
- **W2K DDK** (`DDK2K`, `d3denum_0ilj.htm`, `d3denum_5auf.htm`): FOGTABLESTART is "a position with a value between
  0.0 and 1.0 ... for example 0.3"; FOGTABLEEND "could be set to 0.8"; defaults 0.0 and 1.0. WFOG is "Used for w based
  fog", and ZFOG means "the device supports z based fog". No page says how a WFOG driver tells a Z range from a W range.
- **The application side (inferred, DirectX 7/8 SDK "Eye-Relative vs. Z-based Depth").** W-based fog is used when the
  device reports WFOG and the projection is W-friendly; otherwise fog is Z-based. A non-T&L HAL has no documented
  way to learn the projection:
  - the runtime transforms the vertices itself (inferred);
  - SETTRANSFORM is a T&L op, which our walk skips by size (`vcrdd_d3d.c:1561`);
  - WINFO is documented only for W-buffering (`d3dstrct_56hz.htm`: "Cards that do not support this feature should
    ignore and skip over these instructions").

  So a WFOG-only driver can only infer the units from the values.
- **So the driver must decide from the range.** 3dfx did: `start < 1 && end <= 1` means Z
  (`VH5/D3FOG.C:387`). Its revision log (`:25-39`) records why both halves are needed:
  - 03 Apr 2000: the workaround for PRS 13517 ("V5: Centipede, no textures - only overlays appear once game starts").
  - 04 Apr 2000: narrowed to `nearZ < 1.0F and farZ <= 1.0F`, "otherwise the W Fog - Linear test where nearZ = 1.0F
    and farZ = 1.0F fails". **A pair of 1.0/1.0 must stay W.**

### 2.2 The hardware (SPEC, `reports/hw.md` Q15)

- **§8.22 fogMode (L2867):**
  > "the MSBs of a normalized floating point representation of (1/W) is used to index into the 64-entry fog table ...
  > 8 lower order bits of the floating point (1/W) are used to blend between multiple entries of the lookup table"
  - Entry i stands for `w_i = 2^(3+i/4)/(8-i%4)` (Glide's `guFogTableIndexToW`, `VH5/D3FOG.C:192-200`).
  - Within an octave the four entries are **equally spaced in 1/W**: `1/w_i = 2^-k (1 - j/8)` for `i = 4k + j`. So the
    blend between two entries is linear in the iterated 1/W, which is linear in screen space.
  - (inferred from the index curve and the SPEC wording; 86Box's Voodoo model computes the index and blend the same
    way. `fogtable_zgrad`'s mid-segment column measures it, §7.)
- **§8.46 fogTable (L3644):**
  > "the difference between successive fog blending factors cannot exceed 63 ... the sum of each fog blending factor
  > and Δ fog blending factor pair must not exceed 255."
  - The delta is 6.2. `vcr_fog_reg`'s `& 0xff` turns a step of 64 into a delta of 0, and 100 into 36.
- **The Wfbi iterator** is the FBI's own 1/W (`sOowfbi`, setup bit 3). Texture perspective uses the TMU Ws (`SM_W0`,
  `SM_W1`), which `compute_regs` always sets for a textured stage. Depth uses the Z iterator (no W-buffer yet, G23).
  **Wfbi feeds only the fog unit today.** That is what the proven vertex-fog path already relies on: it sends a
  synthetic 1/W per vertex, and it passes on silicon at 16 and 32 bpp (`KMD/evidence/d3dplan_1112/onbox/`
  `d3dprobe_render_640x480x16.txt`, `d3dprobe_render_1024x768x32_clean.txt`,
  `d3dprobe_render_windowed_desktop32_clean.txt`: `fogvertex` 3/3 in each).

### 2.3 The vendor reference: what to take, and what not

- **Take the detection** (`D3FOG.C:387`): LINEAR only, `start < 1.0F && end <= 1.0F`. 3dfx shipped it in its last
  V5 drivers (from April 2000, on Win9x and W2K alike: revision 7) against the period library, with the 1.0/1.0
  exclusion it gained for the WHQL W-fog test.
- **Do not take:**
  - **the outcome.** Zeroing the table loses the fog the application asked for. 3dfx's own comment calls it wrong.
  - **its packing** (`:447-455`). The deltas are not masked: a step of 64 or more spills into the neighbouring
    entry's byte, and a decreasing step corrupts the whole word.
  - **its EXP/EXP2 normalisation** (`:298-299`, `:333-334`). It scales the table so the last entry is 255, which is
    not D3D's function. Ours is unscaled (`vcr_fog.c:46-51`) and stays so.
- **The Centipede fix is this item.** No other fog workaround in the vendor tree concerns Napalm
  (`reports/vendor.md` §12).

## 4. Design

### 4.1 Step 0: measure exposure (log only, default-on)

This is the Phase 0 instrumentation (G76), so it belongs to G76's counter set. If G76 has not landed, it is
G31's to add. Both forms are log-only, with no register change, and are default-on as Phase 0 allows.

- **G76 counters** (per context, reported in the "context gone" event): table fog with a Z range
  (`FOGTABLEMODE == LINEAR && vcr_fog_zrange_bits(start, end)`); table fog EXP/EXP2 with `density >= 0.5f` (a
  Z-unit suspect, §4.4); FOGTABLEMODE != NONE at all; WINFO seen (with the last `dvWNear`/`dvWFar` bits);
  SETTRANSFORM seen (with its transform type). The last two are skipped by size today (`vcrdd_d3d.c:1556`, `:1561`).
- **Stand-alone form:** event 513 with a new `what` (the next free code at landing; 24 and 25 are claimed by both
  G03 and G10, and 26 by G08). INFO, logged in `compute_regs` when the table key `fog_table[0..3]` differs from the
  last one logged. At most 4 per context; later changes are only counted. Text:
  `"fog table %u: mode %u start %x end %x density %x zrange %u drawn %s"`, with drawn being "W" or "Z".

This step is what turns "unmeasured" into a row per title during the G73 in-game sweep, and it decides any
escalation.

### 4.2 Step 1: the Z-indexed table (behind `Diag\D3DFeat` bit FOGZ)

**Detection** (`compute_regs`, `vcrdd_d3d.c:1007-1013`). The HAL is built `-mgeneral-regs-only`, so the test
runs on the float bit patterns the render states already carry:

```c
/* include/vcr_fog.h - integer only, so the HAL may call it */
/* 3dfx's PXLFOGLIN range (VH5/D3FOG.C:387): FOGSTART < 1 and FOGEND <= 1, i.e.
 * D3D table fog in DEVICE-Z units (the DX5 DDK's 0..1). On the IEEE-754 bits:
 * a set sign is below 1; a clear one compares as an unsigned integer. inf and
 * NaN are never a Z range. 1.0/1.0 is NOT one (3dfx, 04/04/00: the WHQL W-fog test). */
static __inline int vcr_fog_zrange_bits(unsigned start, unsigned end)
{
    if ((start & 0x7f800000u) == 0x7f800000u || (end & 0x7f800000u) == 0x7f800000u)
        return 0;
    return ((start & 0x80000000u) || start < 0x3f800000u) &&
           ((end & 0x80000000u) || end <= 0x3f800000u);
}
```

```c
/* compute_regs, inside the existing LINEAR/EXP/EXP2 branch, after fog_table[0..3] are set */
c->fog_z = 0;                                   /* beside c->fog_vertex = 0 (:1003) */
...
if (tm == D3DFOG_LINEAR && (c->pd->d3dfeat & VCR_D3DFEAT_FOGZ) &&
    vcr_fog_zrange_bits(r->fog_table[1], r->fog_table[2])) {
    r->fog_table[0] |= VCR_FOG_ZINDEX;          /* part of the cache key: a Z table never passes for a W one */
    c->fog_z = 1;
}
```

`prepare` (`:1358`) adds `w->d.fog_z = c->fog_z;`. The `dp2walk` is zeroed per call (`:1835`), so the field starts
at 0. `vcr_d3dctx` gains `ULONG fog_z`, and `vcr3d_draw` (`vcrdd_3d.h:46-58`) gains `ULONG fog_z`.

**The map and the table** (`KMD/common/vcr_fog.c`, the FPU object; `vcr_fog_table` and `vcr_fog_reg` stay untouched):

```c
#define VCR_FOG_ZINDEX   0x10                       /* or'd into the table's mode word */
#define VCR_FOG_OOW_MIN  (5.0f / 262144.0f)          /* 1/w of entry 63; exact in a float */

/* the Wfbi a vertex at device z sends: affine in z, so the setup unit iterates
 * it as it iterates Z; z 0 -> 1/W 1 (entry 0), z 1 -> 1/W of entry 63 */
float vcr_fog_z_oow(float z)
{
    if (!(z > 0.0f))                                /* also NaN */
        z = 0.0f;
    if (z > 1.0f)
        z = 1.0f;
    return 1.0f - z * (1.0f - VCR_FOG_OOW_MIN);
}

/* the device z entry i stands for under that map: 0 ... 1 */
float vcr_fog_index_z(int i)
{
    return (1.0f - 1.0f / vcr_fog_index_w(i)) / (1.0f - VCR_FOG_OOW_MIN);
}

/* vcr_fog_table's three functions, evaluated at vcr_fog_index_z(i) instead of
 * vcr_fog_index_w(i) - same clamps, same rounding, same "end <= start" step */
void vcr_fog_table_z(int mode, float start, float end, float density, unsigned char out[64]);

/* vcr_fog_reg with the delta SATURATED to 0..63 (SPEC §8.46: a step "cannot
 * exceed 63"); used for Z tables only, so W tables keep their bytes */
unsigned vcr_fog_reg_sat(const unsigned char t[64], int n);
```

**The load** (`VcrDd3dState`, `vcrdd_3d.c:86-101`): two dispatches on the flag. A key without it takes exactly
today's calls:

```c
if (r->fog_table[0] & VCR_FOG_ZINDEX)
    vcr_fog_table_z((int)(r->fog_table[0] & ~VCR_FOG_ZINDEX), fbits(r->fog_table[1]), fbits(r->fog_table[2]),
                    fbits(r->fog_table[3]), t);
else
    vcr_fog_table((int)r->fog_table[0], ...);                       /* unchanged */
...
w3(pd, V3D_FOGTABLE + 4 * i, (r->fog_table[0] & VCR_FOG_ZINDEX) ? vcr_fog_reg_sat(t, (int)i)
                                                                 : vcr_fog_reg(t, (int)i));
```

**The vertex** (`vertex`, `vcrdd_3d.c:202-209`): one more branch, and the same single `sOowfbi` write:

```c
if (d->fog_vertex) {
    ...                                             /* unchanged: the ramp */
} else if (d->fog_z) {
    /* table fog in device-Z units (G31): Wfbi carries the vertex's z, and the
     * table is built over z (vcr_fog.h) */
    wf(pd, V3D_SOOWFBI, vcr_fog_z_oow(p[2]));
} else {
    wf(pd, V3D_SOOWFBI, oow);                       /* unchanged */
}
```

**Registers, before and after, for one Z-range LINEAR draw:**

| register | today (and with the bit off) | with FOGZ armed |
|---|---|---|
| `fogMode` (`0x108`) | `0x41` | `0x41` |
| `fogColor` | FOGCOLOR | FOGCOLOR |
| `fogTable[0..31]` (`0x160+`) | all `0xff00ff00` (every entry 255, delta 0) | D3D's Z fog at `z_i`, deltas saturated |
| `sSetupMode` | `... \| SM_WFBI \| ...` | unchanged |
| `sOowfbi` per vertex | rhw | `1 - (1 - 5·2^-18)·sz`, in [`1.9e-5`, 1] |
| writes per vertex, VcrDdRoom counts | 9 / 12 / 15 | identical |

**Why the result is exact for LINEAR.** Device z is affine in screen space over a triangle, and so is
`vcr_fog_z_oow(z)`. The chip iterates that value and blends between entries linearly in 1/W (§2.2), so a table
holding `f(z_i)` gives `f(z)`'s piecewise-linear interpolant over z. For LINEAR that interpolant is exact except
in the segment that contains each clamp kink. EXP/EXP2 tables built this way (`vcr_fog_table_z` accepts them) get
64 breakpoints that are dense near z = 1, where perspective depth bunches up.

**Prototype numbers.** The host build used the real `vcr_fog.c` plus the functions above, with a model of the
SPEC §8.22 lookup (index from 1/W, blend linear in 1/W, 6.2 delta from the register):

| check | result |
|---|---|
| `vcr_fog_zrange_bits` against `isfinite && s < 1.0f && e <= 1.0f` | 0 mismatches: hand-picked edges (±0, denormal, 0.999, 1.0, nextafter(1), 5, 2000, ±inf, NaN) plus 2,000,000 random bit pairs |
| `vcr_fog_index_z` at entries 0 / 2 / 3 / 4 / 8 / 12 / 28 / 63 | 0 / 0.250005 / 0.375007 / 0.500010 / 0.750014 / 0.875017 / 0.992206 / 1.000000 |

A Z table hits the 63 limit in its coarse low-z segments (each 0.125 or 0.0625 wide). That is why the saturating
delta is part of this item. Without it, the probe's own gradient reads 64 at the ramp's midpoint instead of 128.

**With the bit off:** `fog_z` is never set and `VCR_FOG_ZINDEX` never appears in a key. `vcr_fog_table` and
`vcr_fog_reg` are untouched, so every register value is today's: Z ranges still draw as solid fog colour, and W
ranges, EXP, EXP2 and vertex fog are unchanged.

### 4.3 Interactions

- **W-buffer (G23).** Wfbi carries depth there, so a W-buffered context must never set `fog_z`. G23 adds `&& !wbuf`
  to the detection, and for a Z range it falls back to **no table fog** (fogMode 0, 3dfx's PXLFOGLIN outcome), never
  the all-255 table. The Z iterator is free under W-buffering, and FOG_Z could carry a linear Z fog there. That is
  G23's or G32's call, and it needs the `FOG_Z|FOG_ALPHA` silicon question settled first (`reports/vendor.md` §7.4).
- **Vertex fog (G32)** never reaches `fog_z`: `fog_vertex` needs FOGTABLEMODE NONE, and `fog_z` needs LINEAR.
  Whatever G32 does to the vertex-fog carrier leaves this path alone.
- **Lines and points (G16):** drawn through `vertex()`, so they get the Z index automatically.
- **Fog-table cache (G41):** the flag is part of `pd->fog_loaded`'s key, so the first Z table after any W table
  (or after a Glide session) is always reloaded. G41's stale-W-table case is unchanged; it is neither better nor worse.
- **SLI (G51):** fog state rides whatever state broadcast G51 adds. Nothing here is per-chip.
- **WINFO:** still skipped. Nothing in G31 reads it (see §4.4).

### 4.4 Deliberately not in this item

- **EXP/EXP2 in Z units.** There is no start/end to test, and density alone does not separate the units (Thief
  Gold's W density 0.025; the DX5 DDK's "0 to 1" in Z units). 3dfx did not guard it either.
  - A rule would need WINFO: by the projection algebra a non-perspective projection gives
    `dvWNear == dvWFar == 1` (inferred).
  - It would also need proof that XP's D3D8/9 runtimes send WINFO to a non-T&L DX7 driver.
  - Step 0's WINFO counter and G23's parse are the measurement. No staged title needs this rule (§3).
- **Saturating W-table deltas.** `vcr_fog_reg`'s wrap also mis-interpolates a steep W ramp (a step above 63 between
  entries). Fixing it changes proven bytes, so it gets its own probe (`fogtable_steep`: LINEAR 1..2, whose steps
  are 68 and 102) and its own boot. It is listed under open questions.
- **Advertising ZFOG** (§5).
- **3dfx's sub-unit WSCALE for W tables** (`D3FOG.C:402-405`) belongs to the W-buffer (G23).

## 5. Caps

**Unchanged.** RasterCaps keeps `FOGTABLE | WFOG | FOGVERTEX`.

- WFOG stays: 3dfx shipped it (`VH5/D3INIT.C:2926`), it is what every staged W-unit title expects, and NewDark keys
  its fog units on it (§3).
- ZFOG stays off. It would invite an application to choose Z units for EXP/EXP2 too, which this design cannot
  detect. A D3D8/9 application that reads it could take a path no staged title has exercised on this HAL.
- Because the caps do not change, no application takes a different code path when FOGZ is armed. Only the pixels of
  a Z-range LINEAR draw change.

## 6. Gating and promotion

- **`Diag\D3DFeat` bit FOGZ**, provisionally **bit 10 (`0x400`)**:
  - after G12's bits 6-8 and the W-buffer's expected 9; bits 0, 1 and 4 are taken by G15, G08 and G16;
  - the D3DFeat allocation (`reports/hal.md` §10) fixes the final number;
  - a positive flag, absent = off;
  - plumbing as G15 specifies: `VcrDiagGet(L"D3DFeat", 0)` at boot, the appended `vcr_info.d3dfeat` word,
    `pd->d3dfeat`. Whichever D3DFeat item lands first adds the word.
- **Chip-independent.** The Banshee, Voodoo3 and VSA-100 share the fog unit, so the 86Box Voodoo3 bed can run the
  probes first (16 bpp).
- **One Diag change per clean boot:** boot A without the bit, boot B with it (§9).
- **Promotion to default-on** comes in the build after boot B, if `fogtable_z` and `fogtable_zgrad` pass at 16 and
  32 bpp, windowed and fullscreen, and the default probe sets are unchanged.
  - It needs no game evidence: no staged title draws a Z range, so promotion changes nothing in any of them.
  - Promoting means the code stops testing the bit, and a documented kill switch replaces it (the Accel2DPattern
    pattern, "Diag = 0 turns it back off"). The mechanism is the plan-level choice G05, G08, G15 and G16 also wait on.
  - The probe tests then join d3dprobe's default list in the same commit.
- **Safe to land default-on?** On substance, yes: no caps change, no new registers, Wfbi in the proven range, and a
  byte-identical stream for every non-Z-range draw. It still lands default-OFF to keep the campaign's single rule;
  the cost is one supervised boot pair.

## 7. d3dprobe tests (`KMD/tools/d3dprobe.c`)

A helper draws a quad with per-side z and rhw (FVF `XYZRHW | DIFFUSE`, the existing `VC`):
`quad_zr(x0, y0, x1, y1, z0, z1, rhw0, rhw1, c)`. A second helper builds the expected colour:
`fog_rb(a) = ((255 - round(255a)) << 16) | round(255a)`, red fogged toward blue by amount `a`. Both tests use red
quads (`0xffff0000`), fog colour blue (`0xff0000ff`), FOGTABLEMODE LINEAR and FOGVERTEXMODE NONE, and are untextured
(`untextured()`). Expected values are **computed in the probe** from D3D's formula
`a = clamp((z - start)/(end - start), 0, 1)`. Tolerance is 12 per channel at 32 bpp and 16 at 16 bpp (the existing
W `fogtable` half-fog reads `7b0084` at 16 bpp, `7e0080` at 32). Both tests are **explicit** (`--tests ...`) until
promotion.

### `fogtable_z`: the units

Six quads, 32x128, at `x0 = 8 + 40i`, `y 64..192`, sampled at `(x0 + 16, 128)`, every one at **rhw constant**. A
W-indexed table cannot separate them by depth; only a Z index can.

| i | z | rhw | FOGSTART, FOGEND | want | old build / bit off | 3dfx's zero table |
|---|---|---|---|---|---|---|
| 0 | 0.10 | 1 | 0.2, 0.8 | `ff0000` (no fog) | `0000ff` FAIL | `ff0000` |
| 1 | 0.50 | 1 | 0.2, 0.8 | `7f0080` (half) | `0000ff` FAIL | `ff0000` FAIL |
| 2 | 0.65 | 1 | 0.2, 0.8 | `4000bf` (three quarters) | `0000ff` FAIL | `ff0000` FAIL |
| 3 | 0.90 | 1 | 0.2, 0.8 | `0000ff` (all fog) | `0000ff` | `ff0000` FAIL |
| 4 | 0.50 | 1 | 0.999, 1.0 (a Z range at the edge) | `ff0000` | `0000ff` FAIL | `ff0000` |
| 5 | 0.50 | 0.5 | 1.0, 1.0 (**not** a Z range: W, w 2) | `0000ff` (W: all fog behind end) | `0000ff` | `0000ff` |

**Pass: 6/6.** The table shows the test tells all three behaviours apart: the old path fails 4 checks and the vendor's
zero table fails 3. Quad 5 pins 3dfx's 1.0/1.0 exclusion on silicon, and quad 4 pins `end <= 1` as inclusive. The
model reads 127.8 and 191.4 for quads 1 and 2.

### `fogtable_zgrad`: per-pixel interpolation

One quad, `x 32..224`, `y 64..192`, with **z 0 at the left and 1 at the right**. rhw runs from 1 at the left to 0.25
at the right, so any use of rhw by the fog would move every column. LINEAR **0.25..0.75**, whose two kinks fall on
table entries 2 and 8. Sampled at `y = 128`, `z = (x - 32)/192`:

| x | 56 | 80 | **92** | 104 | 128 | 152 | 176 | 200 |
|---|---|---|---|---|---|---|---|---|
| z | 0.125 | 0.25 | 0.3125 | 0.375 | 0.5 | 0.625 | 0.75 | 0.875 |
| want | `ff0000` | `ff0000` | `df0020` | `bf0040` | `7f0080` | `4000bf` | `0000ff` | `0000ff` |
| model, saturated delta | 0.0 | 0.0 | 31.3 | 62.8 | 126.8 | 190.9 | 254.9 | 255 |
| model, wrapping delta | 0.0 | 0.0 | **0.0** | **0.0** | **64.0** | 190.9 | 254.9 | 255 |

**Pass: 8/8.**

- Columns 92, 104 and 128 fail if the deltas wrap: their Z steps are 64.
- Column 92 sits mid-segment, so it is the silicon check that the blend is linear in 1/W (§2.2).
- On the old build or with the bit off every column is blue, so 6 of 8 fail.

### Optional: `fogtable_ztex`

The `tex` checker texture on one quad, at Z half-fog, rhw 1. It shows the Z index combining with a textured stage

## 10. Risk to proven paths

- **The default 16 bpp path and every W-table, EXP/EXP2, vertex-fog and no-fog draw:** none. With the bit off the
  register stream is today's. `vcr_fog_table` and `vcr_fog_reg` are not edited (golden-pinned, §8.1), and the bit
  test is pinned by §8.2. With the bit on, only LINEAR draws with `start < 1 && end <= 1` change, and today those are
  solid fog colour.
- **Wfbi values:** in [1.9e-5, 1]. That is the same range the proven ramp sends (`vcr_fog_ramp_oow` spans
  `1/w_63 ... 1`), so there is no new iterator range, and texture perspective (TMU W0/W1) is not involved.
- **Glide/OpenGL coexistence:** no new interaction. A Z key always forces a table reload; G41's stale-W case is
  unchanged.
- **SLI and flip path:** untouched.
- **An application that meant sub-unit eye distances** (`start < 1, end <= 1` in W): it gets Z fog instead. The W
  table cannot index W below 1 anyway (entry 0 is w = 1), so it was already wrong. 3dfx accepted the same trade.
- **A Z ramp narrower than the entry spacing at its depth** is banded: the interpolant is limited to 63 a segment
  near z = 0, where segments are 0.125 wide. This only affects draws that are solid fog today.
- **Future W-buffer (G23):** must not combine with `fog_z` (§4.3). Until G23 exists, nothing W-buffers.

## 12. Open questions

1. **Do AvP and System Shock 2 send a Z range in game?** Statically undetermined (execute buffers; encrypted
   `.ICD`). H&D has about 18 unresolved register-state sites. The answer comes from step 0 / G76 during the G73 sweep
   (AvP only after G71).
2. **EXP/EXP2 in Z units.** Does XP's D3D8/9 runtime send `D3DDP2OP_WINFO` to a non-T&L DX7 driver, and is it (1, 1)
   for a non-perspective projection? Does `D3DDP2OP_SETTRANSFORM(PROJECTION)` arrive at all (our walk skips it by size,
   `vcrdd_d3d.c:1561`)? Either would give a second rule that covers EXP/EXP2. Measure with step 0's WINFO and
   SETTRANSFORM counters and G23's parse; d3dprobe would need a `SetTransform(PROJECTION)` variant (ortho against
   perspective).
3. **Is the in-segment blend linear in 1/W on silicon?** SPEC, Glide's index curve and 86Box say yes.
   `fogtable_zgrad` column 92 measures it. If it is linear in W instead, the error inside a 0.125-wide segment is
   below 2/255, so the design still holds.
4. **Should W tables saturate too?** `vcr_fog_reg`'s wrap mis-interpolates any W ramp with a step above 63 (LINEAR
   1..2 has steps of 68 and 102). That needs a `fogtable_steep` probe and its own boot. It is a small, separate gap.
5. **What should `start == end` mean?** We keep the step (no fog in front of `end`, all fog behind). 3dfx produced a
   0/0 at entry 0, and wined3d says "everything fogged". No title is known to depend on it.
6. **D3DFeat:** bit number 10 is provisional, and the graduation mechanism (a dedicated kill switch) is a plan-level
   decision shared with G05, G08, G15 and G16.
7. **WFOG:** keep it. NewDark's Z conversion (`0x602cb0`) proves a period engine honours it. Withdrawing it is not on
   any plan and would need EXP-in-Z (question 2) first.

## Appendix A. The prototype (to rebuild the §4.2 numbers)

- A C file that `#include`s `KMD/common/vcr_fog.c` and adds the four functions of §4.2 verbatim.
- A model of the lookup:
  - entry i where `1/w_{i+1} < oow <= 1/w_i`;
  - `frac = (1/w_i - oow)/(1/w_i - 1/w_{i+1})`, quantised to 8 bits;
  - amount = `e_i + (delta_i/4)·frac`, with `e_i` and `delta_i` read back out of the packed register words.
- A sweep of z from 0 to 1 in steps of 1e-5, compared with `255·clamp((z - s)/(e - s))`.
- Built with `gcc -O1 -std=c99 ... -lm` on the host. The prototype lived in the session scratchpad, which is
  deleted at session end; this appendix and §4.2 are its record.
