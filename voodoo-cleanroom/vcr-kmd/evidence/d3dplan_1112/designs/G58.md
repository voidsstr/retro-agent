## 0. Verdict

1. **The gap is real, and it has two halves.**
   - **Correctness (latent).** `vertex()` sends the diffuse colour as four floats to `sRed`..`sAlpha`. SPEC's
     register table lists them as stored by the **FBI only** (L2361-2364). Only the packed `sARGB` is "FBI+TREX*"
     (L2360). A TMU combine that selects iterated colour or alpha (`SST_CM_TC_*SELECT_IRGB/IA`) therefore never
     sees D3D's diffuse. **No pixel is wrong today**, because no TMU stage of ours selects iterated colour. It
     becomes wrong the moment G12 bit 8 does.
   - **Performance.** Each vertex carries three colour writes too many. A two-stage vertex also carries a
     duplicate `sOow1` that 3dfx never sends.
2. **Three pieces of evidence make the fix far less speculative than the gap assumed.**
   - **Packed `sARGB` has already run through this HAL on this silicon.** Battery `vcrkmd-v5-2` (2026-09-26 12:12)
     was the sARGB build. `vcrkmd-v5-3` (12:23) was the float build, 11 minutes later. Both were before PARMADJUST.
     They failed **the same two checks with byte-identical values** (gouraud `fffb00`/`ff00ff`) and passed the same
     34, `tex2mod` and `tex2add` included (§2.4). Over 36 checks the two transports were indistinguishable. The
     fault was PARMADJUST (`d716d6f`).
   - **Our own OpenGL stack sends packed colour and no per-TMU W on `.124` in every frame.**
     - MesaFX defaults to `FX_PACKEDCOLOR 1` (`MFX/fxglidew.h:41-42`, `fxglidew.c:128-133`). Our Glide then sets the
       packet-3 packed-colour bit (`GL5/gglide.c:5771-5777`, `6258-6259`).
     - MesaFX disables `GR_PARAM_Q0`/`Q1` (`MFX/fxglidew.c:139-144`). It asks for a per-TMU W only for projective
       texture formats (`MFX/fxvbtmp.h:370-380`). So Glide's `_grUpdateParamIndex` sets up neither W0 nor W1
       (`GL5/gglide.c:4558-4630`), and both TMUs take their W from the broadcast Wb.
   - **The spec says it outright.** The packet-3 parameter words are named "Wbroadcast", "W0 Tmu 0 & Tmu1 W",
     "S0 Tmu0 & Tmu1 S" and "W1 Tmu 1 W" (L4875-4879). The register table has "sWtmu0: TREX0 & TREX1 W" and
     "sWtmu1: TREX1 only W" (L2367, L2370). So "TMU1 takes W0 when SM_W1 is clear" is documented, and proven on this
     silicon through packet 3. It is unproven only on our direct-register transport.
3. **Design.** This item owns two bits of `Diag\D3DFastSetup`, the switch perf.md P3 named and G48's design
   allocated: **bit 0 (0x01) packed `sARGB`**, and **bit 4 (0x10) TMU1 takes W from W0** (SM_W1 clear, no `sOow1`).
   - **Optional Part C, bit 7 (0x80).** It applies Glide's own parameter pruning, which G48 handed to this item's
     designer: the TMUs take W from Wb, Z is not set up when nothing reads it, and Wfbi is not set up when nothing
     reads it.
   - **One owner.** A new integer header, `KMD/include/vcr_vtxplan.h`, turns `compute_regs`' `sSetupMode` into the
     parameter bits a draw really sets up. `vertex()` writes exactly what those bits say. The `sSetupMode` the chip
     is given and the payload it receives therefore cannot disagree, on today's direct path or in G47's packet 3.
4. **Effect.** Writes per triangle go from 27/36/45 (0/1/2 stages) to 18/27/33 with bits 0+4. With Part C they go
   to 15/24/30 (depth on, no vertex fog) and 12/21/27 (depth off). No pixel changes. G12 bit 8 becomes possible.
5. **Gating.**
   - It lands **default-OFF**. With the bits off, the register traffic is byte-for-byte today's: a frozen sequence
     in a native test pins it, and boot A proves it.
   - Proof is one supervised clean boot per bit (B, C, optionally D).
   - It is the strongest **graduate-to-default-on** candidate in the performance lane, given the evidence in
     point 2. Graduate in a follow-up commit once boots B and C pass.
6. **Priority P2. Effort M.** Parts A and B alone are S once G48's `D3DFastSetup` plumbing exists.

## 2. What the hardware and the references say

### 2.1 SPEC

- **Register table** (L2357-2374). Colour:
  - `sARGB` 0x26c: **FBI+TREX\***.
  - `sRed`/`sGreen`/`sBlue`/`sAlpha` 0x270-0x27c: **FBI**.

  The W registers:
  - `sWb` 0x284: FBI+TREX\*.
  - `sWtmu0` 0x288: "TREX0 & TREX1 W".
  - `sWtmu1` 0x294: "TREX1 only W".

  Even the legacy start registers carry colour to the FBI only (`startR` L2239 "FBI"). `startW` is "FBI+TREX\*"
  (L2246).
- **Chip field 0 writes "FBI + all TREX chips"** (§8, the chip-field table above L2220). That is how `vertex()`
  writes, so an `sARGB` write reaches both TMUs.
- **§8.59 `sSetupMode`** (L3718-3735): "When a Bit is set, that parameter will be calculated in the setup process,
  otherwise the value is not passed down to the triangle, and the previous value will be used." Bits 0-7 are RGB,
  A, Z, Wb, W0, ST0, W1, ST1. **There is no packed-colour bit in the register interface.** In direct mode `sARGB`
  and `sRed`..`sAlpha` are two ways of loading the same vertex colour (inferred from v5-2 against v5-3, §2.4).
- **§8.61 `sARGB`** (L3747-3754): bits 31:24 A, 23:16 R, 15:8 G, 7:0 B. This is **D3DCOLOR's own layout**, so the
  raw `D3DCOLOR` dword is the register value. 3dfx sends it unchanged (§2.2).
- **§8.67** (L3780-3783): "a global 1/W that is sent to both the FBI and all TMUs". **§8.68** (L3785-3786): "all
  the TMUs local 1/W". **§8.71** (L3799-3800): "TMU1's local 1/W".
- **Packet 3** (§13.1.6, L4833-4882):
  - Bit 28 means "packed color data follows the X and Y values".
  - Parameter mask [21:10] = `sSetupMode` [7:0].
  - The words: word 3 "Red / Packed ARGB", word 8 **"Wbroadcast"**, word 9 **"W0 Tmu 0 & Tmu1 W"**, word 10
    "S0 Tmu0 & Tmu1 S", word 12 **"W1 Tmu 1 W"**.

  This is the hierarchy G58 relies on. Wb reaches every unit. W0 then reaches both TMUs. W1 then reaches TMU1 alone.
- **The subpixel-correction note** (L2767-2769): PARMADJUST corrects the start values passed into the setup unit,
  and a parameter not passed down for a new triangle is corrected twice. This matters only for Part C, which prunes
  **only parameters nothing reads** (§3.8).

### 2.2 3dfx's NT V5 HAL

- **Packed colour, always.**
  - Direct path: `SETPD(cmdFifo, ghw0->sARGB, aColor)` for each vertex, under `setupFlag & (SST_SETUP_RGB |
    SST_SETUP_A)` (`VH5/D6TRI2I.C:1133-1134`, `1169-1170`, `1205-1206`, `1248-1249`).
  - `aColor` is the raw `pA[FVFO_COLOR]` (`:778`, `:803-805`, `:814-816`), or white when there is no diffuse
    (`:822-824`).
  - FIFO path: `CMDFIFO_BUILD_PK3(cmd, n, setupFlag, 1)`, where the last argument is bit 28 (`VH5/FIFOMGR.H:91-93`;
    `VH5/D6DP2.C:2185-2193`).
- **SST_SETUP_W1 is never set.**
  - `H3DEFS.H:993` defines it.
  - Every other hit **clears** it (`D6TRI2I.C:1381`, `1525`; `D6STRIPI.C:1426`, `1579`; `D6FANI.C:1133`, `1272`;
    `D6DP2.C:2190`, `2194`).
  - Two-stage draws set `SST_SETUP_ST1` alone (`VH5/D6MT.C:6013`). The vertex code writes `sSow1`/`sTow1` and never
    `sOow1` (`D6TRI2I.C:1155-1159`).
  - TMU1's S/T are computed with the same RHW as TMU0's (`D6TRI2I.C:1032-1048`; the W values themselves at
    `:861-919`).
- **Diffuse inside the TMUs.** The stage tables route "Diff" to `SST_CM_TC_OTHERSELECT_IRGB`, `LOCALSELECT_IRGB`,
  `MSELECT_7_IRGB` and the `IA` equivalents (`VH5/D6MT.C:748-857`). Untextured Napalm draws still program both
  TMUs' `textureMode` "because Napalm sometimes uses the TCUs for getting iterated data to the CCU"
  (`VH5/D6DP2.C:6975`). The vendor's iterated-colour model depends on `sARGB` reaching the TMUs.

### 2.3 Our own stack on `.124`: packed colour and inherited W in every OpenGL frame

| fact | where |
|---|---|
| `FX_PACKEDCOLOR` defaults to 1, so the layout is `GR_PARAM_PARGB` | `MFX/fxglidew.h:41-42`, `MFX/fxglidew.c:128-133` |
| our Glide sends one packed dword per vertex for a `GR_U8` colour, and sets packet-3 bit 28 | `GL5/gglide.c:5771-5777`, `6258-6259`; `GL5/fxcmd.h:1561-1576` |
| `GR_PARAM_Q0` and `GR_PARAM_Q1` disabled; `ST1` on only through the `ST_DIFF_TMU1` hint | `MFX/fxglidew.c:136-144`, `MFX/fxsetup.c:1109-1110` |
| a per-TMU W is hinted only for projective formats | `MFX/fxvbtmp.h:370-380` |
| Glide prunes W_TMU0/W_TMU1 without that hint, Z without depth or Z fog, and Wfbi without texture, fog or a W-buffer | `GL5/gglide.c:4448-4716` (`_grUpdateParamIndex`) |

So every triangle our MesaFX ICD draws through our h5 Glide on the V5 6000 has these properties:
- its colour is packed;
- multitextured triangles have `SM_ST1` set and `SM_W0`/`SM_W1` clear: both TMUs take W from Wb;
- the HUD has no Z.

That includes the proven Quake II runs (146.8 fps on one chip, 201.3 on four; `CLAUDE.md`, `KMD/README.md`). **Bits
0, 4 and 7 add no new hardware behaviour.** They are the setup-unit behaviour our OpenGL lane already depends on,
moved to our direct-register transport.

## 3. The design

### 3.1 The switch (shared with G48; whichever lands first creates it)

- **`HKLM\SYSTEM\CurrentControlSet\Services\vcrmp\Diag\D3DFastSetup`** (DWORD) is read **at boot**:
  `x->d3dfastsetup = VcrDiagGet(L"D3DFastSetup", 0)` in `VcrFindAdapter`, beside `D3DBigTex`
  (`KMD/miniport/vcrmp.c:238-244`, `vcrmp.h`).
- It travels to the display driver whole, in an **appended** `vcr_u32 d3d_fastsetup` at the end of `vcr_info`
  (`KMD/include/vcr_ioctl.h:63-108`). It goes after `mon_src`, or after a `d3dfeat` word if one has landed. This is
  G48 §4.6's ABI, pinned by `WT/tests/native/test_vcr_kmd_abi.c`.
- **`VcrDd2dInit`** (`KMD/display/vcrdd_2d.c:432-475`):
  - `memset(&info, 0, sizeof info)` before the IOCTL. Today the struct is not zeroed (`:436-443`); an older
    miniport's shorter struct must read as 0.
  - Then `pd->d3d_fast = pd->g2d_ok ? info.d3d_fastsetup & VCR_FS_IMPLEMENTED : 0`.
  - One arming event, the next free `DD_D3D` code at implementation:
    `armed (Diag\D3DFastSetup %x): packed colour %s, TMU1 W from W0 %s, setup pruning %s` (merged with G48's credit
    line if that exists).
- **The bits** (perf.md P3's order, G48 §4.6's table):

  | bit | value | name | owner |
  |---|---|---|---|
  | **0** | **0x01** | **`VCR_FS_PACKED`: one `sARGB` per vertex** | **G58 Part A** |
  | 1 | 0x02 | FIFO credit | G48 |
  | 2, 3 | 0x04, 0x08 | strip/fan continuation, autostrip | G49 |
  | **4** | **0x10** | **`VCR_FS_W1SHARE`: SM_W1 clear, no `sOow1`** | **G58 Part B** |
  | 5, 6 | 0x20, 0x40 | credit verify, no reserve | G48 |
  | **7** | **0x80** | **`VCR_FS_PRUNE`: Glide's parameter pruning** | **G58 Part C (optional)** |

- **Chip-generic.** Banshee, Voodoo3 and VSA-100 share the setup unit and `sARGB` (0x26c in the GPL `h3regs.h`). So
  the switch is not gated to `napalm` (G48's choice), and the 86Box Voodoo3 bed can exercise bit 0. The original HAL
  drew 26/26 there with `sARGB` (`56e0bc1`). 86Box's model of W inheritance is not known, so the bed is advisory
  for bits 4 and 7.
- **G12's `pd->packed_argb`** is `(pd->d3d_fast & VCR_FS_PACKED) != 0`.

### 3.2 The rule, in one Win32-free header: `KMD/include/vcr_vtxplan.h` (new, integer only)

```c
/* Which triangle-setup parameters a Direct3D vertex carries, and in which registers.
 * ONE owner for the sSetupMode parameter bits VcrDd3dState writes and the payload
 * vertex() (and G47's packet 3) sends: they cannot disagree. Integer only and
 * Win32-free: display/vcrdd_d3d.c prepare() and display/vcrdd_3d.c vertex() use it;
 * tests/native/test_vcr_kmd_vtxplan.c compiles the same header. */
#define VCR_FS_PACKED   0x01u   /* sARGB (FBI+TREX, SPEC L2360), not sRed..sAlpha (FBI, L2361-2364) */
#define VCR_FS_W1SHARE  0x10u   /* TMU1 takes W0 ("W0 Tmu 0 & Tmu1 W", L4876) */
#define VCR_FS_PRUNE    0x80u   /* Glide's _grUpdateParamIndex: W from Wb, unused Z/Wb not set up */
#define VCR_SM_PARAMS   0xffu   /* sSetupMode [7:0]; [19:16] (strip/cull) stay the caller's */

typedef struct vcr_vtx_facts {
    unsigned wfbi_is_rhw;   /* the Wfbi sent IS the vertex's rhw: no vertex-fog ramp (vcr_fog.h), no W remap */
    unsigned z_used;        /* fbzMode DEPTH or ZAWRITE, or any fog/alpha path that reads iterated Z */
    unsigned wfbi_used;     /* fog (table or vertex), a W-buffer, or an alpha select of iterated W */
    unsigned tmu_own_w;     /* a TMU needs a W of its own (projected textures, G92): never share */
} vcr_vtx_facts;

/* compute_regs' sSetupMode -> what this draw really sets up */
static __inline unsigned vcr_vtx_setup(unsigned sm, unsigned fast, const vcr_vtx_facts *f)
{
    unsigned p = sm & VCR_SM_PARAMS, rest = sm & ~VCR_SM_PARAMS;
    if ((fast & VCR_FS_W1SHARE) && (p & SM_W1) && (p & SM_W0) && !f->tmu_own_w)
        p &= ~SM_W1;                                    /* TMU1 takes W0 */
    if (fast & VCR_FS_PRUNE) {
        if ((p & SM_W0) && (p & SM_WFBI) && f->wfbi_is_rhw && !f->tmu_own_w)
            p &= ~(SM_W0 | SM_W1);                      /* every TMU takes Wb ("Wbroadcast") */
        if (!f->z_used)
            p &= ~SM_Z;
        if (!(p & (SM_ST0 | SM_ST1)) && !f->wfbi_used)
            p &= ~SM_WFBI;                              /* untextured, and nothing reads W */
    }
    return rest | p;
}

/* dwords one vertex carries, without its command: X Y, colour, Z, Wb, W0, S0 T0, W1, S1 T1 */
static __inline unsigned vcr_vtx_words(unsigned sm, unsigned packed);
/* the registers in that order: the order vertex() writes and packet 3 carries (SPEC L4867-4882).
 * The colour is 0x26c when packed, else 0x270-0x27c */
static __inline unsigned vcr_vtx_layout(unsigned sm, unsigned packed, unsigned reg[14]);
/* packet 3 word 0 for this payload, for G47: mask [21:10] = sm[7:0], bit 28 = packed colour present */
static __inline unsigned vcr_vtx_pk3_bits(unsigned sm, unsigned packed);
```

- **Fallback rule, ready if U3 fails.** If `tex2persp_fogv` shows TMU1 takes Wb rather than W0 when Wfbi ≠ rhw, the
  W1SHARE condition gains `&& f->wfbi_is_rhw`. That is one line, plus the native test case that pins it.
- **Colour pruning is deliberately not here.** Dropping `sARGB` when no unit reads iterated colour (Glide's
  `IT_DRGB` pruning) would remove one more word from UT2003's `SELECTARG1(TEXTURE)` world. Whether any unit reads
  the colour is, however, the combine compiler's knowledge (G12's `vcr_cmb_out.needs`). It belongs to G12
  (open question 4).

### 3.3 `prepare()`: one place decides the parameters and the transport (`KMD/display/vcrdd_d3d.c`)

The new block goes after the texture-coordinate and vertex-fog edits (`:1338-1360`), and immediately before
`VcrDd3dTarget`/`VcrDd3dState` (`:1361`):

```c
    {   /* G58: the parameters this draw sets up, and how its colour travels (include/vcr_vtxplan.h) */
        vcr_vtx_facts f;
        ULONG fast = c->pd->d3d_fast;
        f.wfbi_is_rhw = !w->d.fog_vertex;
        f.z_used = (c->regs.fbzMode & (FZ_DEPTH | FZ_ZAWRITE)) != 0;
        f.wfbi_used = (c->regs.fogMode & FM_ENABLE) || (c->regs.fbzMode & FZ_WBUFFER);
        f.tmu_own_w = 0;                                    /* G92 (projected textures) sets it */
        c->regs.setupMode = vcr_vtx_setup(c->regs.setupMode, fast, &f);
        w->d.sm = c->regs.setupMode & VCR_SM_PARAMS;        /* exactly what VcrDd3dState sends */
        w->d.packed = (fast & VCR_FS_PACKED) != 0;
        w->d.vwords = vcr_vtx_words(w->d.sm, w->d.packed);
    }
```

- **Why it holds.**
  - Every state send goes through this block, because `prepare()` always calls `compute_regs()` before it (`:1335`,
    `:1337`).
  - Within one DP2 walk, `w->d` and the last state sent change together.
  - A clear sets `prepared = 0` and `dirty` (`:1419-1420`), so the next triangle re-runs it.
- **`vcr3d_draw`** (`KMD/display/vcrdd_3d.h:46-58`) gains three integer fields, `ULONG sm, packed, vwords;`. They are
  written by the integer HAL and only read by the FPU file, which is the same rule its other `ULONG` fields follow.
- **With `fast = 0`.** `vcr_vtx_setup` returns its input. `sm` is today's bits, `packed` is 0, and `vwords` is
  8/11/14, so the room count stays at 9/12/15.

### 3.4 `vertex()`: write exactly what `d->sm` says (`KMD/display/vcrdd_3d.c:183-223`)

```c
static BOOL vertex(VCR_PDEV *pd, const vcr3d_draw *d, const UCHAR *v)
{
    const float *p = (const float *)v;          /* x, y, z, rhw: D3DFVF_XYZRHW */
    float oow = p[3];
    ULONG sm = d->sm;                           /* the sSetupMode VcrDd3dState sent (prepare) */
    ULONG argb = d->diff_off ? *(const ULONG *)(v + d->diff_off) : 0xffffffffu;
    if (!VcrDdRoom(pd, d->vwords + 1))          /* + the sBeginTriCMD / sDrawTriCMD after it */
        return FALSE;
    wf(pd, V3D_SVX, p[0] + d->xy_bias);
    wf(pd, V3D_SVY, p[1] + d->xy_bias);
    if (d->packed) {
        /* D3DCOLOR is sARGB's own layout (A R G B, SPEC 8.61); sARGB is FBI+TREX
         * (L2360): the TMUs' iterated colour - sRed..sAlpha reach the FBI only */
        if (sm & (SM_RGB | SM_A))
            w3(pd, V3D_SARGB, argb);
    } else {                                    /* the proven path, as 3dfx's h5 Glide */
        if (sm & SM_RGB) {
            wf(pd, V3D_SRED, (float)((argb >> 16) & 0xff));
            wf(pd, V3D_SGREEN, (float)((argb >> 8) & 0xff));
            wf(pd, V3D_SBLUE, (float)(argb & 0xff));
        }
        if (sm & SM_A)
            wf(pd, V3D_SALPHA, (float)(argb >> 24));
    }
    if (sm & SM_Z)
        wf(pd, V3D_SVZ, p[2] * d->z_scale);
    if (sm & SM_WFBI) {
        if (d->fog_vertex) { /* unchanged: the fog ramp's synthetic 1/W */ }
        else wf(pd, V3D_SOOWFBI, oow);
    }
    if (sm & SM_W0)
        wf(pd, V3D_SOOW0, oow);
    if (sm & SM_ST0) { /* sSow0, sTow0: unchanged expressions */ }
    if (sm & SM_W1)
        wf(pd, V3D_SOOW1, oow);
    if (sm & SM_ST1) { /* sSow1, sTow1: unchanged expressions */ }
    return TRUE;
}
```

- **What the old path writes.** Every expression is today's, and they are written in today's order. With
  `fast = 0`, `sm` is `RGB|A|Z|WFBI` plus `W0|ST0` exactly when `d->textured`, plus `W1|ST1` exactly when
  `d->textured1` (§3.3). The writes are therefore the same registers, values and order: **byte for byte**. §6
  pins this.
- **Integration with sibling designs.**
  - **G48** splits `vertex()` into `vertex_seq` (builder) and `emit`. These branches go into `vertex_seq` unchanged.
  - **G16/G25** add `vertex_at(..., x, y [, argb, tmus])`. The transport branches go into `vertex_at`. G25's
    specular pass 2 must take its parameter bits from `vcr_vtx_setup` applied to its own pass-2 `sSetupMode`.
- **No hang mode on this path.** A direct register write cannot desynchronise anything. A wrong parameter bit gives
  wrong pixels, which the probes catch. That is unlike packet 3, where a header that disagrees with its payload
  desynchronises the stream (G47 §3.4.2). Under G47, `vcr_vtx_pk3_bits(d->sm, d->packed)` must be the header's mask
  and bit 28, because one owner rules that out.

### 3.5 Counters and evidence the HAL keeps itself

- **A per-context payload counter.**
  - `vcr_d3dctx` gains `ULONG vwords` (`vcrdd_d3d.c:49-74`).
  - `tri()` and `imm_tri()` (`:1367-1381`) add `3 * (w->d.vwords + 1)` after a successful `VcrDd3dTriangle`. The
    add saturates at 0xffffffff; Halo's 26 M triangles × 45 = 1.17 G still fits.
  - `ctx_free` (`:1210-1215`) logs a **second** event, because a ring message holds 95 characters:
    `context %u payload: %u setup words for %u triangles (D3DFastSetup %x)`.
  - The host divides. No 64-bit division is needed in the display DLL.
- **Why this counter matters.** It is the post-condition, not the switch. A single-test d3dprobe session must read
  exactly 2 × 3 × (vwords + 1) per quad, for example `tex2mod` at 90 / 72 / 66 / 60 for 0 / 0x01 / 0x11 / 0x91
  (§7). A box whose ring says 0x11 is armed while it sends 90 words a quad is telling us the arming is broken.

### 3.6 Caps, passes, formats

**No caps change, single pass, no format change.** G58 changes only how the same values reach the setup unit.

### 3.7 With the switch off (the old path)

Byte for byte: the same registers, values, order, room counts and status reads as today. The code paths that
change are:
- the four new lines in `prepare()`, an identity with `fast = 0`;
- `vertex()` keyed on `d->sm`, which is equivalent by construction;
- `VcrDd2dInit`'s `memset`.

G48 made the same choice, one function with switchable branches over a second copy of `vertex()` (its §4.2): G16,
G25, G32, G23, G49 and G92 all change what a vertex sends, and two copies would drift.

## 4. Gating

- **Default OFF** behind `Diag\D3DFastSetup` bits 0x01, 0x10 and 0x80, read at boot as positive bits. With them
  absent, the register traffic is today's, write for write (§3.7, §6).
- **One Diag change per clean boot.** The order is A (baseline), B (+0x01), C (+0x10), and optionally D (+0x80).
  Each runs on top of whatever `D3DFastSetup` value G48 has already proven.
- **Safe to land default-on?** **No, not at landing.** It changes the bus traffic of every Direct3D vertex, and the
  project rule wants a supervised silicon proof first.
- **Graduate after one boot per bit.** It is the best-evidenced change in the performance lane (§2.3-§2.4):
  - Bits 0 and 4 can become default-on in the commit after boots B and C pass, together with their test change.
  - **Convention proposed for this word:** absent → `VCR_FS_DEFAULT` (0x11 after graduation); any value present →
    exactly its bits; `0` → the proven float path. This is the `Accel2DPattern` precedent applied to a bit field
    (plan-level choice, open question 3).
  - Bit 7 graduates separately after boot D.
- **Fresh installs.** These are 16 bpp only, with textures up to 256. After graduation they get packed colour too,
  because the switch is chip-generic.

## 7. On-box verification (`.124`, supervised, one Diag change per clean boot)

**Before every boot:**
- the activation check (`LICSTATUS`; `safe-reboot.py` reads WPA);
- `D3D32 = 1` and `D3DBigTex = 7` stay armed, as on `.124` today;
- no Glide or OpenGL program in the boot before the D3D steps (G01). If one ran, run `vcrctl modeseq`, then confirm

**Decision rules:**
- **B fails anything A passed:** bit 0 stays off. Compare the `iterexact` per-pixel diff with boot A. Because v5-2 and

## 8. Risk to proven paths

| path | risk | why acceptable |
|---|---|---|
| **default 16 bpp / fresh install** (bits absent) | none in traffic | Writes are byte for byte today's: the frozen native sequence, the Python pins and boot A's 40/40 pin them. The only off-path code change is the `sm`-keyed `vertex()`, which is equivalent because `prepare()` already keeps `d.textured` ⇔ W0\|ST0 and `d.textured1` ⇔ W1\|ST1 (`vcrdd_d3d.c:1340-1356`). |
| **armed, wrong rule** | wrong pixels, never a hang | On the direct path a register write cannot desynchronise the engine (§3.4), and the probes name the parameter. Under G47 the one-owner header rules out a header that disagrees with its payload. |
| **Glide/OpenGL coexistence** | the TMU colour latch now holds D3D's last colour; a stale Glide TMU `combineMode` (G03) sees D3D's diffuse instead of a stale colour | Glide and MesaFX send colour whenever one of their combines reads it (`GL5/gglide.c:4507-4525`). | **SLI** | none | D3D is chip 0 only, with snooping off (`KMD/include/vcr_3dseq.h:97-99`). A future G51 broadcast of `sARGB` is an ordinary FBI+TREX write. |
| **flip path** | none | untouched |
| **2PPC (G50)** | none | Writes to one TMU go to both; `sARGB` and W0 are broadcast anyway. |

## 9. Optional experiment: do the TMUs see iterated colour from the floats? (U4, `glidelab itrgb`)

**Why.** This decides whether G12 bit 8 **needs** G58, or merely benefits from it. The register table says the TMUs
see iterated colour only through `sARGB`. That is the gap's premise, and it is inferred from the chip column.

**What.** A new `KMD/tools/glidelab.c` mode, run on our h5 Glide, needs no D3D. It draws one gouraud triangle (red,
green and blue corners) twice:
- (a) with `GR_PARAM_RGB` + `GR_PARAM_A` floats;
- (b) with `GR_PARAM_PARGB`.

The combine is set up as follows:
- TMU0: `grTexColorCombineExt(GR_TMU0, GR_CMBX_ITRGB, X, GR_CMBX_ZERO, X, GR_CMBX_ZERO, c_invert TRUE, GR_CMBX_ZERO,
  FALSE, 0, FALSE)`, so out = iterated RGB (`GL5/gtex.c:1499-1975`). Bind a dummy 8×8 texture.
- FBI: `grColorCombineExt(GR_CMBX_TEXTURE_RGB, …)`, so out = TMU RGB.

Read back with `grLfbReadRegion` at the three corners.

**Outcomes:**
- **(b) right and (a) black or stale:** the table holds. G12 bit 8 requires G58.
- **Both right:** the floats reach the TMUs too. G58 is performance only, and G12 can drop its `packed_argb`
  condition.

**Rules for running it:**
- Last in a boot, after every D3D step, or followed by `vcrctl modeseq`. A Glide close that is not idle leaves
  `cmdFifo0` on (G01).
- One paced mode switch, single chip, no AA.

## 11. Open questions

1. **U4.** Do the TMUs see iterated colour only through `sARGB`? Settled by G12 bit 8's cells or §9. If the floats
   also reach the TMUs, G12 bit 8 does not need to wait for G58.
2. **U3.** With vertex fog, does TMU1 take W0 or Wb when `SM_W1` is clear? `tex2persp_fogv` decides. The fallback
   rule is ready (§3.2).
3. **Graduation convention** for the `D3DFastSetup` word: "absent = default mask, present = exact", or a separate
   kill mask. This is a plan-level choice shared with G48/G49 (and G05's `D3DFeat` question).
4. **Colour pruning.** Dropping `sARGB` when no combine unit reads iterated colour or alpha would save one more word
   on `SELECTARG1(TEXTURE)` geometry, such as UT2003's BSP world. It needs a `needs_iterated` output from G12's
   combine compiler. Who owns it: G12, or a later G58 follow-up?
5. **Part C's home.** Keep it in G58 (bit 7) or give it its own gap id? It shares only the header and the switch.
6. **Bit-exactness.** Is the packed path's iterated colour bit-identical to the float path's? Expected yes (bytes
   0-255 are exact floats); the `iterexact` CRC in boot A against boot B answers it. If not, how large is the LSB
   difference?
7. **Bus versus setup time.** Does a shorter vertex also shorten the setup unit's per-triangle time (7 or 16 clocks
   with subpixel correction, L2767), or only the bus? The boot A/B/C `perf --mode setup` deltas, divided by Δwrites,
   say whether a write costs more than t_w alone.
8. **Allocation.** The final `DD_D3D` event codes (the arming line and the payload line), and whether the bit numbers
   stay 0/4/7. G48's table reserves 0 and 4; 7 is the first free bit after G48's 5 and 6.
