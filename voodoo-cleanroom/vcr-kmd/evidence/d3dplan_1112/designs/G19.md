# G19: UT2003/UT2004 run at 16 bpp, and UT2003 at 640x480, on `.124`

This is the design for one item of the Direct3D plan for the Voodoo 5 6000 on `.124` (vcr-kmd HAL).
Written 2026-11-12. It reads the staged game binaries, our code, the docs and the committed evidence
only. No fleet box was contacted. The game binaries were read from the read-only mount
`/mnt/retro-share` and disassembled on the host with `pefile` and `capstone`.

## 0. Verdict

**The gap is real, but the driver is not at fault.** Both symptoms are policies inside the games.
Both are keyed on the PCI vendor id the D3D runtime reports, `0x121a`, and the staged binaries
contain both. vcrdd reports that id honestly (`UT2003.log:50-51`).

1. **16 bpp: `D3DDrv.dll` forces it on every 3dfx card.**
   - Both builds read the vendor id at device init. For vendor `0x121a`, at **any** device id, they
     set an unregistered `URenderDevice` flag: `+0x64` in UT2003 and `+0x70` in UT2004.
   - `SetRes` then overwrites the requested colour depth with 2 bytes. That sets `Use16bit = 1`,
     which gives an R5G6B5 back buffer and a D16 depth buffer.
   - So the ini's `Use16bit=False` never takes effect. `Diag\D3D32` cannot change the outcome,
     because the driver is never asked for 32 bpp.
   - The same flag also removes the Specular and SpecularityMask layers of Shader materials, and it
     replaces environment-map texture generation with world coordinates.
   - Epic's own command-line switch **`-nodeviceid`** skips the vendor detection, so the flag stays 0.
2. **UT2003's 640x480: `UT2003.exe` runs its first-run auto-configuration at every launch.**
   - The staged `UT2003.ini` and `Default.ini` carry `[FirstRun] FirstRun=0`. The exe runs its
     hardware auto-configuration whenever that value is 0.
   - For vendor `0x121a` it writes `FullScreenViewportX/Y = 640/480`, `Projectors=False` and
     `NoDynamicLights=True` into the in-memory config, after the launcher has written 1280x960.
     It also lowers detail on video-memory and capability grounds.
   - UT2004.exe contains the identical 3dfx branch. It never runs, because the staged `UT2004.ini`
     says `FirstRun=3369`.
   - The signature in the log is the line `Init: D3D Device: Video memory on board: 58`. It is
     printed only by that auto-configuration, and it is at `UT2003.log:23`.

**Leads this rules out:**
- **The X8R8G8B8 + D16 refusal (G10).** UE2 picks D16 only together with a 16-bit back buffer. At
  32 bpp its first choice is D24X8 (read).
- **`MenuViewportX/Y=640x480`.**
  - The only script that switches to 640x480 does so when the current mode is *below* 640x480
    (`XInterface.u` `GUIPage.CheckResolution`).
  - UT2004 has the same value and runs at 1280x960.
- **The history report's "UT2004 at 1280x960x32"** (`reports/history.md:599`). That cannot happen on
  vendor `0x121a` without `-nodeviceid`. It is a documentation error (G80).

**What to do:**
- **(A)** Fix the library: `FirstRun=2225` in the staged UT2003 inis, with a validator check and a
  regression test. This is a correctness fix. It makes the staged configuration the one the game
  actually uses.
- **(B)** Keep 16 bpp as UE2's colour depth on `.124` for now:
  - It is Epic's path for this vendor, and it is what a real Voodoo 5 ran.
  - The VSA-100 renders two pixels per clock (2PPC) **only at 15/16 bpp**.
  - Measure 32 bpp once with `-nodeviceid`. If the user wants it, ship it as a per-box,
    registry-gated launcher block.
- **(C)** Add a `d3dprobe ue2fmt` replay of UE2's format negotiation, so that no HAL change can
  silently break either depth for UE2.
- **(D)** Open a new plan item for the 16 bpp image-quality levers 3dfx used:
  - a 2x2 dither matrix;
  - the overlay-promotion scan-out filter, 3dfx's "22-bit" output.

  No gap in G01-G97 covers them.

### 2.2 The `URenderDevice` fields

Read from `URenderDevice::StaticConstructor`. Each `UBoolProperty` is constructed with its C++ offset
pushed after the property name.

| field | UT2003 (`E03` 0x1038dbf3-0x1038de63) | UT2004 (`E04` 0x103e9d46-0x103e9e61) |
|---|---|---|
| `UseStencil` | +0x54 | +0x60 |
| **`Use16bit`** | **+0x58** | **+0x64** |
| `Use16bitTextures` | +0x5c | +0x68 |

| `LowQualityTerrain` | +0x68 | +0x74 |

The flag sits between registered properties but is not one itself, so **no ini key can set or clear
it**.

### 2.3 D3DDrv: vendor detection

The detection runs once per device init.

- **Where:**
  - UT2003: `D03` 0x1000f985-0x1000fdad.
  - UT2004: `D04` 0x100111b0-0x100115f5.
- **Defaults first.** Both flags are cleared (UT2003 at 0x1000f99b/0x1000f99e; UT2004 at
  0x100111b8/0x100111bb).
- **`-nodeviceid`.** `ParseParam(appCmdLine(), "nodeviceid")`:
  - UT2003 at 0x1000f9b3, UT2004 at 0x100111f9.
  - It logs `D3D Detected: -nodeviceid specified, 3D device identification skipped` and jumps past
    every vendor branch. **The flags stay 0.**
- **Vendor `0x121a`** (UT2003 at 0x1000fa1f, UT2004 at 0x10011265; bytes `3d 1a 12 00 00`). It logs
  `D3D Detected: 3dfx video card`, then:

  ```
  ; UT2003, D03 0x1000fa3b                    ; UT2004 does the same at 0x10011281 with +0x70/+0x6c/+0x68
  mov ecx, [ebx+0x463c]      ; DeviceId
  cmp ecx, 9
  mov eax, 1
  mov [ebx+0x64], eax        ; the 3dfx flag: EVERY 3dfx device
  jae done                   ; DeviceId >= 9 (VSA-100 = 9): nothing else
  mov [ebx+0x60], eax        ; Banshee/Voodoo3 only
  mov [ebx+0x5c], eax        ;   Use16bitTextures = 1
  mov [0x1003f070], 4        ;   a global (purpose not read)
  ```

  Our DeviceId is 9, so only the flag is set.
- **Other vendors that get the same flag** (UT2003 0x1000fbe8-0x1000fc19 and 0x1000fc6d-0x1000fd8c;
  UT2004 0x10011430-0x100115d5):
  - Matrox `0x0521`, `0x0525` and `0x2527`;
  - 36 S3 device ids (Savage family, read from the compare chain).

  So this is Epic's flag for low-end cards, not a 3dfx bug workaround (inferred).

### 2.4 What the flag does (three effects)

**(1) `SetRes` forces 16 bpp.**

- **Where:** UT2003 at `D03` 0x1000ff48-0x1000ff8c; UT2004 at `D04` 0x10011785-0x100117c1.
- **The caller.** WinDrv's `TryRenderDevice` calls
  `SetRes(Viewport, FullscreenViewportX, FullscreenViewportY, Fullscreen, ColorBytes=0, 1)`
  (UT2003 `WinDrv.dll` 0x11104b0a-0x11104be7, reading `UClient` +0x68/+0x6c).
  - With the flag clear, `ColorBytes=0` leaves `Use16bit` as the ini set it.
  - With the flag set, it becomes 2:

  ```
  ; UT2004, D04 0x10011785
  cmp  [esi+0x70], edi       ; the 3dfx flag
  mov  eax, 2
  jne  have                  ; flag set: ColorBytes := 2
  mov  eax, [ebp+0x18]       ;   else the caller's ColorBytes (0 from WinDrv)
  have: 2 -> [esi+0x64] (Use16bit) = 1 ; 4 -> Use16bit = 0 ; anything else -> unchanged
  bits = (Use16bit && !GIsEditor) ? 16 : 32
  ```

- **Formats** (UT2004 `D04` 0x10011ba4-0x10011c5d, fallback 0x1001230e-0x1001234d; UT2003
  `D03` 0x100103bf-0x100104a3):
  - **Back buffer:** `22 + (bits != 32)`, that is X8R8G8B8 (22) or R5G6B5 (23).
  - **The back-buffer check:** `CheckDeviceFormat(adapter, HAL, modeFmt, RENDERTARGET, SURFACE, bb)`.
    A failure gives `CheckDeviceFormat failed`, which is fatal.
  - **Depth, first choice:**
    - `Use16bit` gives D16 (80);
    - otherwise `UseStencil` gives D24S8 (75);
    - otherwise D24X8 (77).
  - **Depth fallbacks**, up to three tries: D32 (71), then D24S8 (75). With `UseStencil` it is D24X4S4
    (79) twice. Then `CheckDepthStencilMatch failed.` is fatal.
  - **Each try** asks `CheckDeviceFormat(DEPTHSTENCIL)` and
    `CheckDepthStencilMatch(adapter, HAL, fmt, bb, z)`.
  - **A fatal error** goes to the handler at `D04` 0x1000e990, which shows `Error setting display
    mode: %s (%s). Please delete your UT2004.ini file if this error prevents you from starting the
    game.` UT2003's text is the same (`D03` string at 0x10031ba8).
- **So UE2 never pairs D16 with a 32-bit back buffer.** With 32 bpp it asks for D24X8 first, which
  vcrdd lists and matches when `Diag\D3D32` is armed (`caps_124.txt` `zmatch`).

**(2) `FD3DRenderInterface::ApplyTexModifier` downgrades environment mapping.**

- **Where:** UT2003 at `D03` 0x100089f7; UT2004 at `D04` 0x1000a0d7.
- **What:** with the flag, a texture-coordinate source of 10 or 11 becomes 8. The names are inferred
  from UE2's enum order: `TCS_WorldEnvMapCoords` and `TCS_CameraEnvMapCoords` become
  `TCS_WorldCoords`.
- **Also:** a non-projected modifier gets `D3DTSS_TEXTURETRANSFORMFLAGS = COUNT2`. The field is
  identified from its values (inferred): it takes 2/3/4 and is ORed with 0x100 = `D3DTTFF_PROJECTED`.

**(3) `FD3DRenderInterface::SetShaderMaterial` drops the specular layers.**

- **Where:** UT2003 at `D03` 0x10004fe1; UT2004 at `D04` 0x1000605e.
- **What:** with the flag, two fields of the `UShader` are cleared. From the code that reads them and
  the adjacent log strings (`SpecularityMask must be a simple bitmap`,
  `No room for SpecularityMask in multipass specular`), they are **Specular** and
  **SpecularityMask** (inferred).

`-nodeviceid` therefore changes three things on `.124`, not only one:
- the colour depth;
- environment-mapped texture coordinates;
- shader specular passes.

The second and third are new paths on our HAL, and nothing has exercised them yet (§9).

### 2.5 UT2003.exe: the first-run auto-configuration

**The gate** (`X03` 0x1090d80d-0x1090d842):

```
FirstRun = 0; GConfig->GetInt("FirstRun", "FirstRun", FirstRun);
if (GIsClient && FirstRun == 0) AutoConfigure();          ; call 0x10905ec0
```

**`AutoConfigure`** (`X03` 0x10905ec0) measures the machine, logs what it found and writes
`GConfig->SetString(...)` to the in-memory config, **before the engine and the viewport load it**:

- **What it measures and logs:**
  - CPU MHz from `GSecondsPerCycle`;
  - `Physical Memory: %i MByte`;
  - the minimum of three `GetAvailableVidMem` totals: `D3D Device: Video memory on board: %i`, which
    is `UT2003.log:23`;
  - the device caps.
- **The rules that fire on `.124`.** The box has 58 MB, 2007 MHz, `MaxSimultaneousTextures` 2, no
  hardware T&L, and vendor `0x121a`:

| rule (address) | setting it writes on `.124` |
|---|---|
| D3D caps read, `MaxSimultaneousTextures` < 4 (0x1090623a) | `DetailTextures=False` |
| 32 < VRAM <= 64 MB tier (0x109069cb-0x10906aea) | texture detail Normal for Interface, Terrain, WeaponSkin, World and Lightmap; Lower for PlayerSkin and RenderMap; `UseTrilinear=False`; `SuperHighDetailActors=False` |
| CPU >= 1500 MHz (0x10906f0b) | nothing more |
| **vendor `0x121a` (0x10906fcb)** | **`FullScreenViewportX=640`, `FullScreenViewportY=480`, `Projectors=False`, `NoDynamicLights=True`** |

**Other tiers that do not fire on `.124`:**
- under 8 MB: 320x240;
- 8-16 MB: 512x384;
- 16-32 MB: `Use16bit=True`;
- if `CheckDeviceFormat(X8R8G8B8 adapter, DXT3 texture)` fails, the measured VRAM is halved first.
  That happens with `D3DBigTex` bit 1 off, and probably also with `D3D32` off (inferred), so on a
  default install the 16-32 MB tier (`Use16bit=True`) would fire too;
- NVIDIA device rules (`DecoLayers=False`).

**After it.** `InitEngine` (`X03` 0x10908e95-0x10908ebe) raises `FirstRun` to 2225 and calls
`SetInt`. That reaches the ini only when the config is flushed at a clean exit.

**Why it repeats on `.124`:**
- The staged ini says 0.
- `GAMERES` adjusts this very file: rules `agent/shared/gameres.h:1018-1020`.
- The game rewrites the file at exit, so the next `GAMESYNC` finds a file that matches neither ledger
  entry and copies the library's `FirstRun=0` back (CLAUDE.md, "GAMESYNC and GAMERES must not undo
  each other").
- The tree was captured from the build VM before the game had ever exited.

**UT2004.exe has the same code** (gate at `X04` 0x1090f11c, 3dfx branch at 0x10907f40). Its InitEngine
raises `FirstRun` to 3369 (0x10909307). It is dormant only because the staged ini says 3369.

**A blind spot.** `GAMERES VERIFY` reads the file, which says 1280x960 whenever FLEETRES or GAMERES
last wrote it. The override happens in memory at launch, so VERIFY can call a 640x480 run "ok". This
is the project's "reported success" shape.

### 2.6 The `MenuViewport` candidate, checked

- **Where the fields are:** `UClient` registers `WindowedViewportX/Y` at +0x60/+0x64,
  `FullscreenViewportX/Y` at +0x68/+0x6c and `MenuViewportX/Y` at +0x70/+0x74
  (`E03` 0x1038c8db-0x1038ca6e).
- **The startup mode** comes from `FullscreenViewportX/Y` (`WinDrv.dll` 0x11104b0a/0x11104b35).
  The one WinDrv site found writing the `MenuViewport` offsets is `-defaultres`
  (0x11101640-0x1110166b), which sets all three pairs to 640x480. That switch is on none of these
  command lines.
- **The script side.** The only 640x480 switch is in `XInterface.u` `GUIPage.CheckResolution`
  (UnrealScript source is embedded in the package):
  `if ( ( (x<640) || (y<480) ) && (bRequire640x480) ) ... ConsoleCommand("TEMPSETRES 640x480")`.
  It raises a resolution below 640x480 and never lowers one.
- **The control:** UT2004 has the same `MenuViewport=640x480` and runs at 1280x960.

## 3. Is 16 bpp the right answer for UE2 on this card?

**For 16 bpp:**
- **It is the era-correct path.** Every Voodoo 4/5 owner ran UT2003/UT2004 in D3D at 16 bpp, whatever
  driver they had, because the decision is in `D3DDrv.dll`.
- **It is the VSA-100's fast path.**
  - 2PPC "should only be enabled for 15/16 bpp rendering modes" (SPEC, via `reports/hw.md` §2.2).
  - 3dfx's HAL enables 2PPC only in a 15/16 bpp mode (`VH5/D6MT.C:4411-4414`).
  - 16 bpp also halves colour and Z traffic.
  - At 1280x960, one chip at 1 pixel per clock is about 18 ms of fill for a frame. With 2PPC it is
    about 9 ms (`reports/perf.md`, the fill table, overdraw 2.5 inferred).
- **It matters little today.** 116.7 of the 123 ms UT2003 frame is inside DrawPrimitive
  (`ONBOX/session_log.md:19`). Colour depth will matter after G46-G53.

**Against 16 bpp:**
- 565 quantisation with the 4x4 ordered dither, which is visible in every UE2 frame (V-08).
- **D16 precision on large outdoor maps** such as DM-Antalus (inferred). Running the same scene at
  32 bpp with D24X8 also tests whether depth precision contributes to G06 (block noise) or G18 (white
  sky). That is a cheap discriminator for those gaps.

**What 3dfx did about 16 bpp quality** (out of G19's scope, item D):
- **Dither:** the D3D HAL always used the **2x2** dither matrix: "D3D won't let you chose the dither
  matrix size so hardcode something" (`VH5/D3RSTATE.C:3500-3531`). Dither subtraction for blending was
  off by default. Ours uses the 4x4 matrix: `FZ_DITHER` only, without `FZ_DITHER2X2`
  (`KMD/display/vcrdd_d3d.c:979-980`, `KMD/include/vcr_3dregs.h:111-114`).
- **Scan-out:** at fullscreen flip, 3dfx promoted the primary to the **video overlay** with
  `vidProcCfg` filter bits [17:16] set to 2x2 below 1024 pixels wide and 4x4 at 1024 and above
  (`SST_OVERLAY_FILTER_*`, `INCLUDE/H3DEFS.H:1185-1190`), and with `vidMaxRGBDelta = 0x1F0F1F`
  (`VH5/DDFXNT.C:2552-2700`).
  - The filter is off in AA modes.
  - In SLI modes only the 4x4 filter or point sampling is allowed.
  - This is the "22-bit" output 3dfx marketed (inferred).
  - vcr-kmd uses none of it (no filter field in `KMD/miniport`, `KMD/include`).

**Recommendation:**
- Keep UE2 at 16 bpp on `.124` by default.
- Run the 32 bpp A/B once (§8, E3). If the user wants 32 bpp after seeing the numbers and frames,
  enable the launcher block in §4.3.
- In either case, open item D. It improves every 16 bpp D3D and Glide title, not only UE2.

## 4. Approach

### 4.1 (A) UT2003's resolution: fix the library

1. **The fix.** In `\\192.168.1.122\files\Files\Games-Library\UT2003\System\UT2003.ini` **and**
   `Default.ini`, line 18: `FirstRun=0` becomes `FirstRun=2225`.
   - 2225 is the value the game writes itself.
   - The file grows by 3 bytes, so GAMESYNC's size+mtime test sees the change, even through
     `smbclient`'s 2007 timestamps.
   - Publish through `scripts/fleet/libwrite.py` / `sharewrite.py`, one file at a time, each read back
     through `/mnt` (CLAUDE.md, "WRITING TO THE SHARE").
   - Do not bump `_deploy_generation.txt`.
   - Nothing else in the tree changes.
2. **How it reaches a box.** `UT2003.ini` is a GAMERES-ledger file. A library change breaks the ledger
   match, so the next sync copies the new file and GAMERES re-applies its viewport keys
   (`agent/shared/grledger.h` contract). No agent change is needed.
3. **The effect on `.124`:**
   - the launcher's 1280x960 holds;
   - the staged detail returns: `DetailTextures`, `Projectors`, dynamic lights, `UseTrilinear` (still
     drawn as nearest-mip, G26), `SuperHighDetailActors`, Lightmap UltraHigh;
   - colour depth stays 16 bpp (§2.4).

   UT2004 already runs on `.124` this way: staged detail, 1280x960, 4-6 fps.
4. **The effect on other boxes:**
   - The per-launch auto-tuning of detail stops. Slow or low-memory boxes get the staged high
     settings, as they already do for UT2004.
   - The latent overrides end: 3dfx gets 640x480, a box under 16 MB of VRAM gets 320x240 or 512x384.
   - Today's UT2003 rows at 1280x960 and 1920x1080 were recorded on NVIDIA/ATI boxes, where the
     auto-configuration does not touch the resolution, so their resolution does not change. Their
     detail does. Re-verify each box in the push step (§8, E5).

Option B, a per-box `FirstRun` written only where vcr-kmd runs, is in §4.7. It is not recommended.

### 4.2 Make it visible: validator and test

- **Where:** `scripts/validate-staged-library.py`, inside `ue2_config_problems()` (now at :347-377).
  It is a WARN, the same severity as the other `ue2-config` findings. It does not block deployment.
- **The rule:** in any UE2 `System\` dir, a `[FirstRun] FirstRun` of `0`, empty or missing in
  `UT2003.ini`, `UT2004.ini` **or `Default.ini`** gives:
  `"<ini> [FirstRun] FirstRun=0 - the exe's first-run auto-configuration runs at EVERY launch and
  overrides the fleet's resolution (a 3dfx card gets 640x480; under 16 MB of VRAM 320x240/512x384)
  and the staged detail; set the build number (UT2003 2225, UT2004 3369)"`.
- **`Default.ini` matters too**, because the engine copies it over a missing `<game>.ini`.
- **The test** is in §7.

### 4.3 (B) The colour depth: a measured opt-in, not a default

No change ships until E3 (§8) has numbers and frames, and the user has chosen. If 32 bpp is chosen:

- **Generator.** A block `ue2_vcrkmd_depth()` in `scripts/fleet/stage-fleetres.py`, modelled line for
  line on `newdark_display_swap()` (:767-897) and `halo_novideo()` (:748-765). It is anchored on
  `cd /d "%~dp0System"`, so the existing `UE_USERINI` and FLEETRES blocks stay intact.

  ```
  rem ---- per-box UE2 COLOUR DEPTH - see stage-fleetres.py ue2_vcrkmd_depth ----
  set UE2_DEVID=
  set UE2_VCR=0
  set UE2_D3D32=0
  sc query vcrmp 2>nul | find /i "RUNNING" >nul && set UE2_VCR=1
  reg query "HKLM\SYSTEM\CurrentControlSet\Services\vcrmp\Diag" /v D3D32 2>nul | findstr /r /i /c:"0x1$" >nul && set UE2_D3D32=1
  if "%UE2_VCR%"=="1" if "%UE2_D3D32%"=="1" set UE2_DEVID=-nodeviceid
  if defined UE2_DEVID if exist "%~dp0FLEETRES.EXE" "%~dp0FLEETRES.EXE" -ini "%~dp0System\UT2004.ini" D3DDrv.D3DRenderDevice Use16bit False
  ```

  - `"fix"` replaces `start "" "UT2004.exe"` with `start "" "UT2004.exe" %UE2_DEVID%`.
  - The block goes in `Play UT2004.bat`, in `Join fleet UT2004 server.bat` and, with `UT2003.ini`, in
    `Play UT2003.bat`.
  - The `Use16bit False` write is needed because a clean exit on the 3dfx path may have saved the
    forced value. E0 checks whether it does.
- **Gate:**
  - It applies only where the vcr-kmd miniport is **RUNNING**, not merely where its key exists: a
    rollback leaves the key behind.
  - It needs `Diag\D3D32`=1. Without it, `CheckDeviceFormat(X8R8G8B8)` fails and UE2 shows its fatal
    "Error setting display mode" dialog (§2.4).
  - If the switch is armed but the box has not rebooted, the same visible dialog appears. That is the
    caveat Thief II documents, and it is never silent.
  - A box where detection cannot run (no `sc.exe`) keeps the library's behaviour.
  - It is two-way: a box that loses vcr-kmd or D3D32 gets the 3dfx path back at its next launch.
- **Delete the block** the day item D or the performance work makes the user prefer 16 bpp, or the
  day D3D32 is the default and 32 bpp has been measured as better.

| option | why not |
|---|---|
| Spoof the vendor id in the driver | `GetAdapterIdentifier` reports the PnP device's PCI id, not a DDI answer. Changing it would mean changing the device's identity. ## 6. d3dprobe test: `ue2fmt`

**What it does** (no draw, no device). It reports what Unreal Engine 2 (D3DDrv 2225/3369) will do on
this adapter:

1. **Identify.** `IDirect3D8_GetAdapterIdentifier` gives `vendor`, `device` and
   `ue2_3dfx_path = (VendorId == 0x121a)`. When the last is true, UE2 renders 16 bpp unless it is
   started with `-nodeviceid`.
2. **Mode.** `EnumAdapterModes`: is `--res` (default 1280x960) listed at R5G6B5 and at X8R8G8B8? It
   also reports the refresh UE2's best-match would take: with `DesiredRefreshRate` at 60 or below and
   no override, the last equal-score entry wins. This is informational, for G65.
3. **Replay UE2's DetermineFormats** for three cases, with `adapter = bb`, exactly as fullscreen
   `SetRes` does:
   - `d16`: bb R5G6B5, Z order **{D16, D32, D24S8}**;
   - `d32`: bb X8R8G8B8, Z order **{D24X8, D32, D24S8}**;
   - `d32_stencil` (`UseStencil=True`): Z order **{D24S8, D24X4S4, D24X4S4}**.

   - **The back buffer:** `CheckDeviceFormat(0, HAL, bb, D3DUSAGE_RENDERTARGET, D3DRTYPE_SURFACE, bb)`.
   - **Each Z:** `CheckDeviceFormat(DEPTHSTENCIL)` plus `CheckDepthStencilMatch(0, HAL, bb, bb, z)`.
   - **Recorded:** `z_try` = the `[fmt, format_ok, match_ok]` of each try up to the first success, and
     `z` = the format UE2 ends with, or 0 for its fatal `CheckDepthStencilMatch failed.`.
4. **Output:**

   ```
   RESULT {"mode":"ue2fmt","vendor":"121a","device":"0009","ue2_3dfx_path":1,
           "desktop_fmt":22,"res":"1280x960",
           "d16":{"listed":1,"refresh":85,"rt":1,"z_try":[[80,1,1]],"z":80},
           "d32":{"listed":1,"refresh":85,"rt":1,"z_try":[[77,1,1]],"z":77},
           "d32_stencil":{"rt":1,"z_try":[[75,1,1]],"z":75},
           "ue2_renders":16,"nodeviceid_renders":32}
   ```

**Pass criterion, against `.124` today** (`caps_124.txt`, D3D32=1, D3DBigTex=7):

| field | expected |
|---|---|
| `vendor` / `device` | `121a` / `0009` |
| `ue2_3dfx_path` | 1 |
| `d16.z` | 80 on the first try |
| `d32.rt` | 1 |
| `d32.z` | 77 on the first try |
| `ue2_renders` | 16 |
| `nodeviceid_renders` | 32 |

- **On a default install** (D3D32 off): `d16.z` = 80, and `d32.rt` = 0 is the **expected** refusal.
  `nodeviceid_renders` then reads `"fatal"`, which is why the §4.3 gate requires the switch.
- **Fail:**
  - any `d16.z` other than 80 on the first try: a HAL change broke every UE2 title's default device;
  - `d32.z` other than 77 with D3D32 armed;
  - any `z_try` in `d32` that contains 80. That would mean the replay no longer matches UE2, whose
    32-bit list never contains D16.

**Device-level companions** use existing modes, paced at least 5 s apart, after a clean boot (G01):
- `render --full --res 1280x960 --bpp 16 --zfmt d16`: 40/40;
- `render --full --res 1280x960 --bpp 32 --zfmt d24x8`: 40/40.

These are UE2's exact device pairs at the staged mode.

## 9. Risk to proven paths

- **The driver:** none. No vcrdd or vcrmp change, so the default 16 bpp path, Glide/OpenGL
  coexistence, SLI state and the flip path are untouched.
- **(A) on `.124`:**
  - 4x the pixels, plus the staged detail (dynamic lights, projectors, detail textures,
    SuperHighDetailActors), so expect lower fps than today's 9.41 at 640x480.
  - More VRAM: 1280x960x16 front + back + D16 is about 7.4 MB, against 1.8 MB at 640x480. There is
    less room for managed textures.
  - The resolution follows the fleet's per-box policy. The per-title remedy for speed is the
    performance work, not a hidden auto-configuration.
- **(A) on other boxes:** the per-launch detail tuning stops, so slow boxes get the staged high detail,
  as UT2004 already does everywhere. The E5 re-verification covers it.
- **(B), if adopted:**
  - **A new path on our HAL:** 32 bpp UE2 with D24X8, shader specular passes, and env-map texgen with
    `D3DTTFF_COUNT3`. `fvf_layout` already sizes 1/2/3/4-float texcoord sets and samples (s,t)
    (`KMD/display/vcrdd_d3d.c:1254-1283`), but no game has exercised it.
  - **Blends:** extra additive passes may hit G28/G29.
  - **32 bpp state:** dither at 32 bpp (G30); the stale CMDFIFO after a Glide session (G01).
  - **Cost:** twice the frame-buffer traffic, and no 2PPC.
  - **A D3D32-off box** would show the fatal dialog. The registry gate prevents that, and an
    armed-but-not-rebooted box shows the dialog visibly.
- **(C):** a tool, with no device and no switch.
