## 0. Verdict

### The HAL half of the gap is real

`vertex()` sends each TMU `W = rhw`, `S = s·rhw` and `T = t·rhw` (`KMD/display/vcrdd_3d.c:210-221`).
- A third or fourth coordinate in the vertex is never read.
- `D3DTSS_TEXTURETRANSFORMFLAGS` (TSS 24) is stored in `c->tss[]`/`c->tss1[]` by the generic TSS case (`KMD/display/vcrdd_d3d.c:1591-1609`) and is read nowhere.

A stage whose coordinates reach the HAL as (s, t, q) with PROJECTED is therefore drawn with q ignored.

### What it costs today is unknown, because nobody has measured what the XP runtime sends

The HAL does not advertise `D3DPTEXTURECAPS_PROJECTED` (`KMD/display/vcrdd_d3d.c:2034-2035`; `caps_124.txt` TextureCaps `00004007`). Three behaviours are possible, and they predict very different pictures:

| | the runtime... | the HAL sees | today's picture |
|---|---|---|---|
| (a) | divides per vertex itself. The DX8.1/DX9 SDK text says the runtime does this when the cap is absent (inferred: quoted from memory) | a 2-float set | right at the vertices, warped inside triangles where q varies |
| (b) | passes (s, t, q) and the flag through | a 3/4-float set + PROJECTED | **unprojected**: wrong everywhere |
| (c) | strips q or the flag without dividing | a 2-float set, undivided | unprojected, and the HAL cannot see it |

### UE2 sends PROJECTED, and never asks whether the HAL can do it (measured from the binaries)

Read in both `LIB/UT2004/System/D3DDrv.dll` (md5 `b6bb4d87…`) and `LIB/UT2003/System/D3DDrv.dll` (md5 `04c412ca…`).

**What the projector code does.** `FD3DRenderInterface::SetProjectorMaterial` builds its projected stages as follows:
- `TexCoordIndex = 0x20000` (`D3DTSS_TCI_CAMERASPACEPOSITION`);
- `TTFF = 3` (`COUNT3`);
- a 4x4 texture matrix;
- then `TTFF |= 0x100` (`D3DTTFF_PROJECTED`) when a flag of the projector material is set.

UT2004 addresses: `0x1000459d-0x100045f7` and `0x100052c3-0x10005319`. UT2003 addresses: `0x100035ec-0x10003646` and `0x100042e5-0x10004332`.

**It does not check the cap.** The only read of `DeviceCaps8.TextureCaps` in UT2004's D3DDrv tests `0x800` (CUBEMAP) and `0x10000` (MIPCUBEMAP) (`0x10010bae-0x10010bc7`). No test of `0x400` was found (§3.1). UE2 therefore sends PROJECTED whatever the HAL says.

### The hardware mechanism is documented, and our own OpenGL lane already uses it

The hardware side:
- each TMU divides by its own iterated 1/W: `sWtmu0` "TREX0 & TREX1 W", `sWtmu1` "TREX1 only W" (SPEC L2367, L2370, L3785-3800);
- `tclampw` "is used when projecting textures to avoid projecting behind the source of the projection" (SPEC L3859).

Our MesaFX ICD + h5 Glide implement exactly this mapping for OpenGL's q: TMU W = q·oow, S = s·oow·scale (`MFX/fxvbtmp.h:204-226`, `GL5/fxcmd.h:1606-1631`).

It has **never been shown on silicon**: no title on `.124` is known to use projective OpenGL texturing (inferred).

### Design: three parts, and no new register

**Part A: counters (log-only, default ON).** Per context, the HAL counts projected stages by kind:
- divided;
- not divided because the switch is off;
- pre-divided by the runtime;
- 1-D;
- bad q.

It also buckets the q ratio inside each triangle, which tells whether per-vertex vs per-pixel would even be visible. This answers "does a title send it, and in which form" in any in-game session (G73's census key `tex.transform.projected`).

**Part B: the per-pixel divide** (`Diag\D3DFeat` bit `PTEX`, default OFF). For a TMU whose set carries q under PROJECTED, `vertex()` sends:

    W = q·k·rhw,   S = s·scale·rhw·k,   T = t·scale·rhw·k

Here k is a per-triangle power of two with `max|q|·k ∈ (½, 1]`.
- The registers, `sSetupMode` bits and write counts are unchanged; only the values sent to `sWtmu0/1`, `sS/W*` and `sT/W*` change, and only on those draws.
- k is exact in IEEE arithmetic. It keeps the TMU's W within the triangle's own largest rhw, which is the range the proven path already sends.

**Part C: the cap** (`D3DFeat` bit `PTEXCAPS`, default OFF, needs PTEX). It adds `D3DPTEXTURECAPS_PROJECTED`. Under (a), the runtime then stops dividing per vertex and hands the raw (s, t, q) to Part B.

### Gating

- **Part A:** default on, because it changes no register.
- **Parts B and C:** default OFF. They graduate to default-on in a follow-up commit after one supervised clean boot each on `.124` (§8).
- **With both bits clear,** every register write is today's, byte for byte (pinned by §7).

### Priority and effort

**Priority P2.** Raise it to **P1** if U1 finds (b), the raw pass-through: every perspective projector UE2 draws in every UT2003/UT2004 match is then wrong today. Lower it to **P3** if U1 finds (a) and the Part A q-ratio buckets show UE2's triangles barely vary in q.

**Effort M** (A: S; B: S-M; C: S; the probe tests: M).

## 2. What Direct3D asks for

**D3D's definition.** A stage with `D3DTTFF_PROJECTED` samples `(s/q, t/q)`, where q is the COUNT-th element of its set (`d3dtypes.h`: "texcoords to be divided by COUNTth element"; `dx8ddk/inc/d3dcaps.h:224-228`: "Device can divide transformed texture coordinates by the COUNTth texture coordinate").
- `COUNT3|PROJECTED` divides by the third element.
- `COUNT4|PROJECTED` divides by the fourth.
- With the cap, the divide happens per pixel (inferred: SDK text).

**The interpolation D3D requires.** Let λ be a pixel's screen-space barycentrics and ρ = rhw. Then:

    u_D3D = (Σ λᵢ ρᵢ sᵢ) / (Σ λᵢ ρᵢ qᵢ)

**What the TMU does.** It iterates S/W, T/W and 1/W linearly in screen space and divides per pixel: `u_hw = (Σ λᵢ Sᵢ)/(Σ λᵢ Wᵢ)`.

| mapping | u_hw | |
|---|---|---|
| **today** (`Sᵢ = sᵢρᵢ·scale`, `Wᵢ = ρᵢ`) | `scale·(Σλρs)/(Σλρ)` | q ignored |
| **Part B** (`Sᵢ = sᵢρᵢk·scale`, `Wᵢ = qᵢρᵢk`, one k > 0 per triangle) | `scale·(Σλρs)/(Σλρq)` | **D3D's own value, for any k** |
| a runtime per-vertex divide, (a) | `(Σ λρ (s/q)ᵢ)/(Σλρ)` | exact at the vertices only |

**What is out of scope:**
- `COUNT1|PROJECTED` and `COUNT2|PROJECTED`: 1-D projection. Counted, not drawn differently.
- Back-projection where q < 0: `TM_CLAMPW` returns texel (0,0) there, as the spec intends. D3D's reference would mirror (inferred). Applications clip projectors to their frustum; UE2 does (`bClipBSP`, inferred).
- Cube, volume and 3-D coordinates (G84).

## 3. Evidence

### 3.1 UE2 sends COUNT3|PROJECTED with camera-space texgen, unconditionally (measured)

**UT2004 `D3DDrv.dll`** (`b6bb4d877e833530270098f50ba05a87`).

The function is identified by the wide strings at `.rdata`:
- `FD3DRenderInterface::SetProjectorMaterial` at `0x1005e2b8`, pushed by the guard at `0x10005f6f`, after the function's `ret $0x90` at `0x10005f55`;
- "No stages left for projected texture" at `0x1005e528`, pushed at `0x10004b70`;
- "Either projected texture or base material must be simple." at `0x1005e4b0`.

Two stage set-ups inside that function:

```
1000458f  rep movsl                      ; 16 dwords -> stage+0x80 (a D3DMATRIX: the texture transform)
1000459d  movl $0x1,0x7c(stage)          ; texture transform on
100045b1  movl $0x20000,0x74(stage)      ; TexCoordIndex = D3DTSS_TCI_CAMERASPACEPOSITION
100045c5  movl $0x3,0x78(stage)          ; D3DTTFF_COUNT3
100045d0  mov 0xb8(material),%ecx ; test ; je   ; the projector material's flag
100045f1  or  $0x100,%ecx ; mov %ecx,0x78(stage)    ; |= D3DTTFF_PROJECTED

100052cc  movl $0x3,0x78(...)  100052e0  movl $0x20000,0x74(...)  100052f6  mov %edx,0x7c(...)
100052fa  test %dl,0xd4(%ecx) ; je ; 10005313  or $0x100,%esi   ; the second projected stage
```

**UT2003 `D3DDrv.dll`** (`04c412ca1e2c280740579e42a2a0e97c`) has the same two set-ups, with the stage struct shifted by 4:
- `0x100035ec`/`0x10003600`/`0x10003614` and `or $0x100` at `0x10003640`;
- `0x100042e5`-`0x10004332`.

**The caps.** `DeviceCaps8` sits at `UD3DRenderDevice+0x4194`. The proof is the assertion "RenDev->DeviceCaps8.MaxPrimitiveCount > (UINT)NumPrimitives" (`.rdata 0x100633ec`) pushed after `cmp %edi,0x4248(%eax)` at `0x100172e5`; MaxPrimitiveCount is at `+0xb4` in `D3DCAPS8`.
- `TextureCaps` is therefore `+0x41d0`. It is read once, at `0x10010bae`, and tested for `0x800` (`test $0x8,%ah`) and `0x10000`.
- The neighbouring RasterCaps read (`+0x41b8 & 0x4000`) is UE2's "Supports Z biasing" (G22).
- A pattern search found no `test $0x400`, no `testb $0x4` on a stack copy, and no `and $0x400` (`objdump` of the whole `.text`).

So UE2 sends PROJECTED whether or not the cap is there, as far as a pattern search can show.

**Staged settings make projectors common:**
- `LIB/UT2004/System/UT2004.ini:150` and `:191`: `Projectors=True`;
- `LIB/UT2003/System/User.ini:333`: `bPlayerShadows=True`;
- `LIB/UT2004/System/DefUser.ini:265`: `bVehicleShadows=True`.

Which projector classes are perspective, and how much q varies inside their triangles, is what Part A's q-ratio buckets measure (U6). Two candidates (inferred):
- player and vehicle shadow projectors, which are also render targets (G36);
- decal projectors (scorch marks), whose FOV may be 1°, i.e. nearly constant q.

### 3.2 The XP runtime (not measured)

- `.124` runs D3D8 titles through XP SP3's `d3d8.dll` 5.03.2600.5512 (`xpsp.080413-0845`; the image source's copy, md5 `f099b129022170f2df9e1c0185c9bcfb`, `/mnt/retro-share/Files/OS/XPSP3-FLEET/I386/D3D8.DL_`).
- Every D3D8 title uses software vertex processing, because VertexShaderVersion is 0 (`caps_124.txt`; G83).
- Halo and NewDark go through `d3d9.dll` instead (`reports/games.md:127, 135`).

**What the documentation says.** The DX8.1 and DX9 SDK text for `D3DPTEXTURECAPS_PROJECTED` says, from memory and inferred: "If this capability is not present, but the projective divide needs to occur anyway, then it is performed on a per-vertex basis by the Direct3D runtime."

**What the code shows.** `d3d8.dll`'s retail strings name none of this. Four `test $0x100` sites were found in its 358k-line disassembly; the one inspected (`0x6d9df91a`) tests an internal state word, not TTFF, and the other three were not read. The static route was abandoned as too costly against an experiment that answers it in minutes (U1).

**One piece of real evidence that TTFF reaches an NT DX6/7 HAL at all.** 3dfx's NT parser revision 96 is "Fix for PRS 14997 and 14904 - Support for TEXTURETRANSFORMFLAGS 2d texture coords" (`VH5/D6DP2.C:59-60`). That PRS only makes sense if the runtime forwarded TTFF to the driver.

### 3.3 The hardware (SPEC)

- **Register table** (L2357-2374):
  - `sWb` 0x284 "Global W" (FBI+TREX);
  - `sWtmu0` 0x288 "TREX0 & TREX1 W";
  - `sS/W0`, `sT/W0` "TREX0 & TREX1";
  - `sWtmu1` 0x294 "TREX1 only W";
  - `sS/Wtmu1`, `sT/Wtmu1` "TREX1 only".
- **§8.59 `sSetupMode`** (L3718-3735): bit 4 "Setup W0", bit 6 "Setup W1". "When a Bit is set, that parameter will be calculated in the setup process".
- **§8.67-8.73** (L3780-3810):
  - Wb is "a global 1/W that is sent to both the FBI and all TMUs";
  - sWtmu0 is "all the TMUs local 1/W";
  - sWtmu1 is "TMU1's local 1/W".
- **textureMode bit 3 `tclampw`** (L3830): "force S=0, T=0 when W is negative".
- **L3859:** "tclampw bit of textureMode is used when projecting textures to avoid projecting behind the source of the projection ... it is not necessary to set this bit when doing projected textures."

  The chip's designers wrote down projective texturing through the TMU W as an intended use.
- **Packet 3** (L4875-4879), for G47: words "Wbroadcast", "W0 Tmu 0 & Tmu1 W", "W1 Tmu 1 W". Part B's values travel in the same words.
- **LOD.** The SPEC gives no formula. Any sane LOD formula is homogeneous of degree 0 in (S/W, T/W, 1/W), since the texture coordinate itself is. So the per-triangle k cannot change the LOD.
  - On the derivative: the usual approximation `|d(S/W)/dx| / (1/W)` drops the `dW/dx` term, exactly as it already does for ordinary perspective (inferred).

### 3.4 Our own OpenGL lane does exactly this

**MesaFX.** A projective set (OpenGL q, `tc_size == 4`) gets the following in `MFX/fxvbtmp.h:204-226`:
- `tmuvtx[n].sow = s·uscale·oow` and `tow = t·vscale·oow`;
- `tmuvtx[n].oow = oow · q`.

The vertex format asks Glide for a per-TMU W only for these formats (`GR_STWHINT_W_DIFF_TMU0/1`, `:370-380`; layout `MFX/fxglidew.c:139-172`).

**Our h5 Glide** turns that into the TMU W word, `q0 · oow` / `q1 · oow` (`GL5/fxcmd.h:1606-1631`, `STATE_REQUIRES_W_TMU0/1`). S and T are `_oow · s_scale` (`:1616-1618`).

**Part B is the same mapping**, with one addition: a per-triangle exact rescale. MesaFX sends raw `q·oow`. Whether the raw form ever overflows the TMU's W iterator is open question 5. The rescale makes the question moot for D3D.

### 3.5 3dfx never offered it, and its NT parser has a bug not to copy

- **Never offered:**
  - DX7 caps: `D3DPTEXTURECAPS_PROJECTED` is commented out (`VH5/D3INIT.C:3037`);
  - DX8 caps: commented out too (`:3469`); D3DXLS row 310.
  - Their Win9x software T&L leaves the divide out ("This wasn't in the procprim.c in the refrast, but the sdk says for projected you divide ... (LEAVE IT OUT!)", `W9X/K3DTNL.C:1393-1399`). That code is in a block compiled out, `#if 0 // UNUSED` at `:1063` to `#endif //0` at `:1500`.
- **The bug, vendor-31.** The NT DP2 parsers store the TTFF value into `ADDRESSU` and `ADDRESSV`:
  - `VH5/D6DP2.C:1508-1511`;
  - `VH5/D7DP2.C:1620-1623`, `1750-1753`.

  Win9x revision 100 calls that "wrong" and fixes it (`W9X/D6DP2.C:58-62`). A title that sets COUNT3|PROJECTED on 3dfx's NT driver had its stage switch to an undefined address mode.

  Ours stores TTFF in its own slot. §7's Python test pins that it never reaches the address modes.

## 5. The design

### 5.1 Part A: counters (log-only, default ON, no register change)

**In `vcr_d3dctx`** (`KMD/display/vcrdd_d3d.c:49-74`), add:
- `ULONG ptex[9]`, triangle counts:
  - divided per pixel;
  - not divided because the switch is off;
  - pre-divided (the set holds no q);
  - 1-D (COUNT1/2);
  - bad q, drawn unprojected;
  - four q-ratio buckets;
- `ULONG ptex_shape[8], nptex_shape` for the once-per-shape log.

**In `prepare()`,** for each TMU's stage, compute `vcr_ptex_kind(ttff, set_n, &q)` (§5.2.1). The first time a context sees a (stage, TTFF, set size, kind) shape, it logs one event with the next free `VCR_EV_DD_D3D` what code; 24+ are contested by sibling designs and the integrator assigns. The message stays under 95 characters, the ring's limit:

    ctx %u stage %u TTFF %x set %u fl: %s

where `%s` is one of:
- `per pixel`;
- `NOT divided: D3DFeat PTEX off`;
- `pre-divided`;
- `1-D, not divided`.

The numbers go in a/b/c for the census parser.

**Per triangle:** one increment in `tri()`/`imm_tri()` keyed on the draw's precomputed kind. The q-ratio bucket and the bad-q count are taken in `VcrDd3dTriangle` through `d->ptex_cnt`, a `ULONG *` into the context. The FPU file increments integers only.
- The ratio is computed **only for triangles whose TMU set carries q** (kind `DIVIDE`, whatever the switch).
- So with PTEX clear the register values are unchanged; the FPU file only reads three floats more.

**In `ctx_free()`** (`:1210-1215`): when any `ptex[]` is non-zero, log two INFO events beside 513/2, one with the five counts and one with the four buckets. Or they become fields of G76's per-context record when that lands. Contexts that never projected log nothing new, so no ring pressure.

**Census mapping** (G73 §3.2): `tex.transform.projected` is the sum, with sub-keys `.drawn`, `.ignored`, `.predivided`, `.1d`, `.badq` and `.qratio.<bucket>`.
- G73's calibration cell c21 sends `COUNT2|PROJECTED`, so it lands in `.1d`. Its expected table must say so, or the cell should use `COUNT3|PROJECTED` with a 3-float set; that is G73's choice.

### 5.2 Part B: the per-pixel divide (`Diag\D3DFeat` bit PTEX, default OFF)

#### 5.2.1 The rule, in one Win32-free header: `KMD/include/vcr_ptex.h` (new, integer only)

```c
/* vcr_ptex.h - projected texture coordinates (D3DTTFF_PROJECTED, G92) on the Voodoo TMUs.
 * D3D samples (s/q, t/q) per pixel, q the set's COUNT-th coordinate. Each TMU divides its
 * iterated S/W, T/W by its OWN iterated 1/W per pixel - sWtmu0 (both TMUs), sWtmu1 (TMU1
 * only; SPEC L2367, L2370, 8.68-8.73) - so S = s*rhw*k, T = t*rhw*k, W = q*rhw*k gives
 * D3D's own value for any k > 0 fixed over the triangle. tclampw is the spec's guard for
 * "projecting behind the source" (L3859), and every textureMode we write has it.
 * Integer half: the HAL (-mgeneral-regs-only) uses it; common/vcr_ptex.c has the floats. */
#define VCR_TTFF_COUNT_MASK   0xffu
#define VCR_TTFF_PROJECTED    0x100u      /* d3dtypes.h D3DTTFF_PROJECTED */

#define VCR_PTEX_NONE         0u          /* no PROJECTED on the stage this TMU samples */
#define VCR_PTEX_DIVIDE       1u          /* the set carries q: the TMU divides per pixel */
#define VCR_PTEX_PREDIVIDED   2u          /* PROJECTED, but the set holds no q (the runtime's divide) */
#define VCR_PTEX_1D           3u          /* COUNT1/COUNT2|PROJECTED: a 1-D projection, not handled */

/* nset: the set's floats per the FVF (1..4); *qidx: q's float index when DIVIDE */
static __inline unsigned vcr_ptex_kind(unsigned ttff, unsigned nset, unsigned *qidx)
{
    unsigned n = ttff & VCR_TTFF_COUNT_MASK;
    *qidx = 0;
    if (!(ttff & VCR_TTFF_PROJECTED) || nset < 1 || nset > 4)
        return VCR_PTEX_NONE;
    if (n == 1 || n == 2)
        return VCR_PTEX_1D;
    if (n == 0 || n > nset)               /* no count, or one the vertex does not carry */
        n = nset;
    if (n < 3)
        return VCR_PTEX_PREDIVIDED;       /* never divide twice */
    *qidx = n - 1;
    return VCR_PTEX_DIVIDE;
}
```

The rule's table, which §7's native test asserts:

| TTFF | set floats | kind | q index |
|---|---|---|---|
| `0x103` (COUNT3\|PROJ) | 3 | DIVIDE | 2 |
| `0x104` | 4 | DIVIDE | 3 |
| `0x100` (no count) | 3 / 4 | DIVIDE | 2 / 3 |
| `0x104` | 3 | DIVIDE | 2 |
| `0x103` | 2 | PREDIVIDED | none |
| `0x102`, `0x101` | any | 1D | none |
| `0x003` (no PROJECTED) | 3 | NONE | none |

#### 5.2.2 The floats: `KMD/common/vcr_ptex.c` (new; built with the x87 like `common/vcr_fog.c`, and natively by the test)

```c
/* k for one triangle: a power of two with max|q|*k in (1/2, 1] - exact in IEEE arithmetic,
 * so the TMU's W never exceeds the triangle's largest rhw and |S/scale| never exceeds what an
 * ordinary coordinate of value s/q would send. 0: a q is NaN, 0, or beyond 2^+-60 at a vertex -
 * the triangle is drawn as today (W = rhw), and counted. No CRT: no fabs, no frexp. */
float vcr_ptex_scale(float qa, float qb, float qc);

/* one vertex of one TMU: out[0] = W (sWtmu*), out[1] = S/W, out[2] = T/W.
 * q == 1 and k == 1 give today's values bit for bit: (s*s_scale)*rhw*1, (1*1)*rhw. */
void vcr_ptex_vertex(float s, float t, float q, float rhw, float s_scale, float t_scale,
                     float k, float out[3]);
```

How `vcr_ptex_scale` works:
- It rejects NaN explicitly (`q != q`), because `max()` would drop a NaN silently.
- It takes `m = max(|qa|,|qb|,|qc|)` by sign-bit masking, and requires `2^-60 ≤ m ≤ 2^60`.
- It builds `k = 2^-(e)` from m's biased exponent, `e + 1` when the mantissa is non-zero. The result is `k` with bits `(254 - e) << 23`.

Examples:
- m = 4 → 0.25;
- m = 3 → 0.25;
- m = 1 → 1;
- m = 0.3 → 2;
- m = 4000 → 2⁻¹².

#### 5.2.3 Plumbing the set sizes and the per-TMU decision (`KMD/display/vcrdd_d3d.c`)

- **`fvf_layout`** (`:1254-1283`) also returns `set_n[i]`: the floats of set i (`sz == 0 ? 2 : sz == 1 ? 3 : sz == 2 ? 4 : 1`). `dp2walk` gains `ULONG set_n[8]` beside `set_off[8]` (`:1251`), and `D3d_DrawPrimitives2` passes it through (`:1837`, `:1866`).
- **`vcr3d_draw`** (`KMD/display/vcrdd_3d.h:46-58`) gains integer fields only. The FPU file reads them; the HAL writes them, as it does every other `ULONG` there.

  ```c
  ULONG ptex;        /* bit 0: TMU0 divides by its set's q, bit 1: TMU1 (D3DFeat PTEX) */
  ULONG ptex_seen;   /* the same bits for kind DIVIDE whatever the switch (Part A's ratio) */
  ULONG q0, q1;      /* q's float index in TMU0's / TMU1's set */
  ULONG *ptex_cnt;   /* the context's Part A counters */
  ```
- **`prepare()`**, immediately after the set selection (`:1338-1356`), computes for each sampled TMU. The decision sits **where the TMU's set is chosen**, so it follows whatever stage→TMU assignment G12 settles on.

  ```c
  /* G92: is the set this TMU reads a projected one (include/vcr_ptex.h)? TMU0 samples
   * stage 1 when two stages are on (above), TMU1 stage 0 */
  w->d.ptex = w->d.ptex_seen = 0;
  if (w->d.textured) {
      unsigned q, kind = vcr_ptex_kind(c->regs.textured1 ? c->tss1[D3DTSS_TEXTURETRANSFORMFLAGS]
                                                         : c->tss[D3DTSS_TEXTURETRANSFORMFLAGS],
                                       w->set_n[s0], &q);   /* the header is Win32-free: unsigned */
      ptex_note(c, c->regs.textured1 ? 1 : 0, kind);           /* Part A */
      if (kind == VCR_PTEX_DIVIDE) {
          w->d.ptex_seen |= 1;
          w->d.q0 = q;
          if (c->pd->d3d_ptex)
              w->d.ptex |= 1;
      }
      if (w->d.textured1) {
          kind = vcr_ptex_kind(c->tss[D3DTSS_TEXTURETRANSFORMFLAGS], w->set_n[i0], &q);
          ptex_note(c, 0, kind);
          if (kind == VCR_PTEX_DIVIDE) {
              w->d.ptex_seen |= 2;
              w->d.q1 = q;
              if (c->pd->d3d_ptex)
                  w->d.ptex |= 2;
          }
      }
  }
  ```
- **Bounds.** q is read at `uv[q]`, with `q ≤ nset - 1 ≤ 3`, inside the vertex: `fvf_layout`'s offsets and stride already cover the whole set. The walker's index checks (`tri()`, `:1367-1374`) bound the vertex itself, so no read moves past what `uv[0..1]` already trusts.

#### 5.2.4 `VcrDd3dTriangle` and `vertex()` (`KMD/display/vcrdd_3d.c`)

```c
#define QOF(v, off, i)  (((const float *)((v) + (off)))[i])

BOOL VcrDd3dTriangle(VCR_PDEV *pd, const vcr3d_draw *d, const UCHAR *a, const UCHAR *b,
                     const UCHAR *c)
{
    float pk[2] = { 0.0f, 0.0f };          /* 0: this TMU is drawn as today */
    if (d->ptex_seen)
        ptex_scales(d, a, b, c, pk);       /* k per TMU where d->ptex; Part A's ratio and bad-q
                                              counts where d->ptex_seen (integers via ptex_cnt) */
    if (!vertex(pd, d, a, pk))
        ...                                /* the rest unchanged: sBeginTriCMD, sDrawTriCMD x2 */
}

static BOOL vertex(VCR_PDEV *pd, const vcr3d_draw *d, const UCHAR *v, const float *pk)
{
    ...                                    /* x, y, colour, z, Wfbi: unchanged */
    if (d->textured) {
        const float *uv = (const float *)(v + d->tex_off);
        if (pk[0] != 0.0f) {               /* G92: TMU0's set is projected (D3DFeat PTEX) */
            float o[3];
            vcr_ptex_vertex(uv[0], uv[1], uv[d->q0], oow, d->s_scale, d->t_scale, pk[0], o);
            wf(pd, V3D_SOOW0, o[0]);
            wf(pd, V3D_SSOW0, o[1]);
            wf(pd, V3D_STOW0, o[2]);
        } else {                           /* today's three writes, verbatim */
            wf(pd, V3D_SOOW0, oow);
            wf(pd, V3D_SSOW0, uv[0] * d->s_scale * oow);
            wf(pd, V3D_STOW0, uv[1] * d->t_scale * oow);
        }
    }
    /* TMU1: the same with tex1_off, q1, s_scale1/t_scale1, pk[1], V3D_SOOW1/SSOW1/STOW1 */
    return TRUE;
}
```

**What stays as it is:**
- the `VcrDdRoom` count;
- the write order;
- the registers.

**`pk[i]` is set only where `d->ptex` has bit i AND `vcr_ptex_scale` returned non-zero.** A bad q draws that triangle as today, and Part A counts it.

#### 5.2.5 Setup mode and W sharing

- **No new `sSetupMode` bit.** One stage already sets `SM_W0|SM_ST0`, two stages `SM_W1|SM_ST1` too (`KMD/display/vcrdd_d3d.c:1021-1022`).
- **Two stages, one of them projected.** TMU0 gets W0 = its value; TMU1 gets W1 = its own value, because `SM_W1` stays set.
- **One stage.** W0 reaches TMU1 too ("TREX0 & TREX1 W"), but its output is not used: TMU0's combine is REPLACE.
- **G58.** Its bit 4 (TMU1 takes W0, `SM_W1` cleared) and Part C (TMUs take Wb) must not apply to a draw with `d->ptex`. G58's `vcr_vtx_facts.tmu_own_w` already exists for this: `f.tmu_own_w = w->d.ptex != 0` (G58 §3.2-3.3).

#### 5.2.6 tclampw and LOD

- **`TM_CLAMPW` stays set**, as it is on every textureMode today (`:787`, `:825`). Where q < 0 inside a triangle, the TMU samples texel (0,0), which is the spec's intended "behind the projector" answer. D3D's reference would back-project (inferred); applications clip. This divergence is documented, not tested for equality.
- **LOD** is invariant under k (§3.3). A mipmapped projected texture picks its level with the same approximation the ordinary perspective path uses.

#### 5.2.7 What Part B does not do

It does not handle:
- 1-D projection (`COUNT1/2|PROJECTED`);
- back-projection;
- projected coordinates on lines and points. G16's quads inherit Part B for free, since they go through the same `VcrDd3dTriangle`.
- a projected set on a stage the HAL does not draw (stage 2+; stage 1 without a stage-0 texture, G12).

#### 5.2.8 The fallback if U3 fails (`tmu_w_ignored` / `w1_ignored` on silicon)

If the hardware does not divide by W0/W1, Part B's per-pixel path cannot work. The same switch then selects a CPU divide per vertex:

    W = rhw,  S = (s/q)·scale·rhw,  T = (t/q)·scale·rhw

- **Quality.** That is exactly the runtime's documented fallback quality: right at the vertices, a defined approximation inside the triangle.
- **Range.** A triangle with a bad q is drawn as today.
- **Cost.** One divide per vertex per projected TMU.

This keeps the gap fixable even in the worst hardware outcome (a "(b)" runtime): unprojected becomes per-vertex correct.

### 5.3 Part C: the cap (`D3DFeat` bit PTEXCAPS, default OFF, ignored without PTEX)

In `VcrDdD3dHalInfo`, after `prim_caps(&d->dpcTriCaps); prim_caps(&d->dpcLineCaps);` (`KMD/display/vcrdd_d3d.c:2071-2072`):

```c
    /* G92: projected texture coordinates divided per pixel by the TMU's own 1/W
     * (Diag\\D3DFeat PTEXCAPS, only with PTEX): the runtime then hands us (s, t, q) */
    if (pd->d3d_ptexcaps) {
        d->dpcTriCaps.dwTextureCaps |= D3DPTEXTURECAPS_PROJECTED;
        d->dpcLineCaps.dwTextureCaps |= D3DPTEXTURECAPS_PROJECTED;
    }
```

- **What D3D8 then reports.** TextureCaps `0x00004407`: the runtime adds MIPMAP from `DDSCAPS_MIPMAP` itself, as today's `00004007` shows.
- **Why at boot.** Like D3DBigTex, the bit is read at boot by the miniport, so the caps an application reads at its desktop equal the device's (`KMD/miniport/vcrmp.c:242-244`, the D3DBigTex comment).

### 5.4 The switch

**`HKLM\SYSTEM\CurrentControlSet\Services\vcrmp\Diag\D3DFeat`** is the word G05 §4 designs, read at boot into an appended `vcr_info.d3dfeat`. Whichever D3DFeat item lands first creates `KMD/include/vcr_d3dfeat.h` and the transport.

**The bits.** `VCR_D3DFEAT_PTEX` and `VCR_D3DFEAT_PTEXCAPS` are provisionally **bit 20 (0x100000)** and **bit 21 (0x200000)**. No sibling design claims them (bits 0-15 are contested); the plan owner assigns them.

**`VcrDd2dInit`** (`KMD/display/vcrdd_2d.c:432-475`):
- `pd->d3d_ptex = (info.d3dfeat & VCR_D3DFEAT_PTEX) != 0`;
- `pd->d3d_ptexcaps = pd->d3d_ptex && (info.d3dfeat & VCR_D3DFEAT_PTEXCAPS)`;
- one INFO event when armed: "armed (Diag\D3DFeat %x): projected tex coords per pixel %s, PROJECTED cap %s".

**Chip-generic, not gated on `napalm`.** The Banshee/Voodoo3 setup unit has the same W0/W1 parameters (GPL `h3regs.h`), so the 86Box Voodoo3 bed can run Part B. Only `.124` arms it.

### 5.5 What happens on the old path

**With both bits clear:**
- `prepare()` computes the kinds and counts them (integers, Part A).
- `d->ptex` stays 0, so every `pk[i]` is 0.
- `vertex()` runs its unprojected branch, which holds today's three lines verbatim.
- The caps are today's.

Part A's only effect on the draw path, for triangles whose set carries q, is that the FPU file reads three more floats to bucket the ratio. **No register value, write count or order changes.**

**With PTEX set:** only triangles whose sampled set carries q under PROJECTED change, and they are the ones drawn wrong (or per-vertex) today.

**With PTEXCAPS set:** the caps change, and the runtime's output for projected stages changes, under (a), from 2 floats to 3/4.

## 6. The d3dprobe tests (`KMD/tools/d3dprobe.c`, explicit list only; never in the default gate)

### 6.1 Textures

- **RAMP:** a 32x32 R5G6B5 texture in which **every texel names itself**: red = its column (5 bits), green = 2 × its row (6 bits), blue = 0.
- **PLAIN:** a 32x32 texture with red = green = 0 and blue = its column.

Both are point sampled, with CLAMP and MIPFILTER NONE.

Colour can be read back exactly:
- at a 16 bpp target the 565 values come back as they are;
- at 32 bpp, `col = R8 >> 3` and `row = G8 >> 3`;
- dithering is off.

### 6.2 Geometry

**The band:** x from 32 to 224, y from 96 to 160, a triangle strip, inside the 256x256 readback window.
- Left vertices: (s, t, q) = (0, 0.5, 1).
- Right vertices: (4, 2, 4).
- So `s/q` runs 0 → 1, and `t/q = 0.5` everywhere.

## 9. Risk to proven paths

| path | risk | why |
|---|---|---|
| default 16 bpp D3D (bits clear) | **none** | register values, counts and order unchanged (§5.5; pinned by `q1_is_todays_values_bit_for_bit` and the verbatim-branch source test; boot A re-runs the matrices) |
| with PTEX | low, and confined | only triangles whose set carries q under PROJECTED change, and they are wrong today. The W magnitude never exceeds that triangle's own largest rhw (k), so no new iterator range. A bad q draws as today. |
| with PTEXCAPS | low-medium | a cap changes what titles and the runtime choose. UE2 never reads it (§3.1). D3D9 titles are unknown; boot C watches Halo and NewDark (U5). Bigger vertex sets for projected stages under (a) cost negligibly. |
| Glide/OpenGL coexistence | none | no new register; `sSetupMode` bits unchanged; the TMU W values are per-vertex parameters that Glide re-sends itself |
| SLI, flip, 2D, DirectDraw | none | untouched (D3D renders on chip 0) |
| draw-path cost | negligible | Part A: integer work per state change, one increment per triangle, three float reads per triangle that carries q. Part B: ~10 FP operations per projected vertex. |
| textured vertex fog | **already at risk today, unproven** | it relies on the TMU taking W0 rather than Wb (§1). Boot B's verdicts settle that as a side effect; `tmu_w_ignored` would expose a live defect, not one this item causes. |

## 13. Open questions

1. **What does XP SP3's `d3d8.dll` (5.03.2600.5512) send our DX7 HAL** for a COUNT3|PROJECTED stage under software vertex processing, without the cap and with it? This is U1, settled on the 86Box bed first. And does `d3d9.dll` (Halo, NewDark) behave the same? Part A in their sessions shows it; d3dprobe is D3D8-only.
2. **Does the VSA-100 divide by W0/W1 rather than Wb on our direct-register path** (U3)? The answer also decides whether today's textured vertex fog is right (§1, §9).
3. **Which UE2 projector classes set the flag UE2 tests before OR-ing in PROJECTED** (material `+0xb8` and `+0xd4`), and how far does q vary inside their triangles? These are U2 and U6, from Part A's census. The UnrealScript defaults (decal FOV, ShadowProjector FOV) were not read.
4. **Should PTEXCAPS graduate together with PTEX,** or stay off if U1 = (b) makes the cap unnecessary? Advertising it only matters under (a).
5. **Does the raw MesaFX form** (`W = q·oow`, no rescale) ever exceed the TMU W iterator's range on this silicon? This is U4's debug build. If it never does, the rescale can be dropped, which simplifies G49. The OpenGL lane may also want the rescale (the clean-room ICD lane, not this item).
6. **Bit numbers.** `D3DFeat` bits 20/21 are provisional; the plan owner assigns them.
7. **G73's census cell c21** uses `COUNT2|PROJECTED`, which this design counts as 1-D. Should the cell use `COUNT3|PROJECTED` with a 3-float set, so it exercises `.drawn`?
8. **Back-projection.** `TM_CLAMPW` gives texel (0,0) where q < 0, while D3D's reference mirrors (inferred). If a title is ever seen depending on the mirrored image, the per-vertex fallback (§5.2.8) cannot reproduce it either. No staged title is known to.
