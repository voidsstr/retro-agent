## 1. Verdict

1. **The gap is real, and every format but A8 is fixable in one pass.**
   - The TMU samples all of them natively: RGB332 (format 0), I8 (3, = L8), AI44 (4, = A4L4), ARGB8332 (8), AI88 (13, = A8L8). The X formats are ARGB8888/1555/4444 (15/11/12) with alpha forced to 1.0 (H3DEFS:265-292; SPEC §8.76 L3867-3886).
   - The XP D3D8/D3D9 runtimes convert every one of them from a DX7 `DDPIXELFORMAT`, **provided the flags and masks are exactly the ones the converter compares** (§2.1, read from the binaries in this session).
   - **A8 is not offered**, for three independent reasons:
     - the converter has no `DDPF_ALPHA` case, so D3D8/9 games can never see it (§2.1);
     - no staged title asks for it;
     - the TMU's A8 returns RGB = alpha, which is not D3D's semantics.

     3dfx's own DX7 A8 entry was broken anyway: the list publishes `DDPF_ALPHA`, but the sampler only recognises `DDPF_ALPHAPIXELS` with a zero red mask, so the surface falls through to "565" (§2.6).
2. **No staged `.124` title is measured to need any format G34 still owns.**
   - **Halo needs none of them.** The A8/Y8/AY8/A8Y8 reading in `games.md` §4.2 and `runtime.md` §4.4-4.5 is refuted, by two facts:
     - `halo.exe` maps `a8`/`y8`/`ay8`/`a8y8`/`p8-bump` to "no D3D format" (its table at VA `0x65e040` holds `-1` there);
     - all 30 maps hold **0** monochrome bitmaps (§2.4).

     Halo's one missing format is **X8R8G8B8**: 1,419 2D bitmaps across the 30 maps, among them lens flares, the sky's stars, `rasterizer\default 2d` and the bump maps. **G17 owns that row** (`Diag\D3DBigTex` bit 3).
   - **UE2 (UT2003/UT2004)** probes only DXT1/3/5, A8R8G8B8 and R5G6B5 (§2.5).
   - **Max Payne and Thief II** ask for none of them directly. They load through D3DX helpers that take the "closest supported" format, so offering more formats *changes* their choices rather than fixing anything.
   - **Hidden & Dangerous Deluxe** carries its own converter for every D3D8 format. It is a candidate consumer, and equally a candidate regression.
   - **DX5/DX6 enumerators:**
     - Shogo picks its 8-bit format by `DDPF_PALETTEINDEXED8` only (P8 is G38).
     - AvP takes the *first* enumerated format with enough colour depth, so an RGB332 entry could replace a 16-bit one for its 256-colour art.
3. **So G34 is P3.** The plan below is complete and implementable, sequenced so the money is spent only where measurement says it pays:
   - **Phase 0** (log only, default on): find out who creates or asks for which texture formats.
   - **Phase 1:** X1R5G5B5/X4R4G4B4 and A8L8. Cheap once G17's plumbing exists, and no new storage kind.
   - **Phase 2:** L8/A4L4, with a new 8-bit storage kind.
   - **Phase 3:** the 3-3-2 pair. Only for a measured consumer.
4. **Four hazards any implementation must handle.** Each was found while reading for this design, and none is in the reports:
   - **The Thief II launcher reads `D3DBigTex` with `findstr /c:"0x[57df]$"`** (`LIB/Thief2/Play Thief 2.bat:18`).
     - Any value of 0x10 or more fails that pattern, and the title silently drops to its DX6 path at 640x480.
     - `tests/python/test_newdark_display.py:254-261` only tries 0-15.
     - **So G34 cannot use `D3DBigTex` bits 4+.** It gets its own switch, `Diag\D3DTexFmt`.
   - **8-bit textures add texBaseAddr "phases".**
     - The TMU drops texBaseAddr bits 3:0, so a top level must start at (size of the absent levels) mod 16.
     - That is 4 bytes for an 8-bit 1x1 and 8 for an 8-bit 2x1/1x2. G21 covers only the 16 bpp 1x1 (8).
     - G21's `SF_PAD8` flag cannot express 4 (§3.6).
   - **`Dd_Blt` takes a texture's bytes per pixel from the desktop.**
     - It does so whenever `DDRAWISURF_HASPIXELFORMAT` is clear (`KMD/display/vcrdd_ddraw.c:389-394`), and the HAL itself records that NT leaves it clear on D3D textures (`vcrdd_d3d.c:162-170`).
     - An 8-bit texture at a 16/32 bpp desktop would be blitted 2-4x past its rows. It must go to the HEL (§3.8).
   - **The flush's texture-port write-back** is proven only for textureMode formats 10/11/12. AI88, ARGB8332 and every 8-bit format must not get it (§3.8).

## 2. Evidence

### 2.1 What the XP runtime will convert, exactly

**The converter.** `XPRT/d3d8.dll` `0x6d9b6850-0x6d9b6d48` is the DDPIXELFORMAT→D3DFORMAT converter for DX7 drivers. `XPRT/d3d9.dll` carries the same cases (luminance at `0x4fe05d7f-0x4fe05df9`).
- `dwFlags` is compared **for equality** (`cmp $0x40,%ecx`, `cmp $0x20001,%ecx`), not as a bit test.
- So an entry with an extra flag is a different format, or no format at all.
- Offsets: `+0xc` bit count, `+0x10` R/luminance mask, `+0x14` G, `+0x18` B, `+0x1c` alpha mask.

| `dwFlags` (exact) | bits | masks the code compares | D3DFORMAT |
|---|---|---|---|
| `0x40` RGB | 8 | R `e0`, G `1c`, B `03` | **27 R3G3B2** (`0x6d9b6898`). Any *other* 8-bit RGB entry becomes 41 P8 (`jne 0x6d9b6ab4`) |
| `0x40` | 16 | `7c00/3e0/1f` / `f00/f0/f` | **24 X1R5G5B5** / **30 X4R4G4B4** (`0x6d9b68e9`, `0x6d9b6908`) |
| `0x40` | 32 | `ff0000/ff00/ff` | **22 X8R8G8B8** (`0x6d9b6964`; G17) |
| `0x41` RGB+ALPHAPIXELS | 16 | A `ff00` + `e0/1c/03` | **29 A8R3G3B2** (`0x6d9b69db`) |
| `0x20000` LUMINANCE | 8 | L `ff` | **50 L8** (`0x6d9b6c1f`) |
| `0x20001` LUMINANCE+ALPHAPIXELS | 8 | L `0f`, A `f0` | **52 A4L4** (`0x6d9b6c62`) |
| `0x20001` | 16 | L `ff`, A `ff00` | **51 A8L8** (`0x6d9b6c77`) |
| `0x2` ALPHA | any | (no case) | 0: the op builder **deletes** the entry (`0x6d9af147` → `0x6d9af32e`) |

**The op builder** (`0x6d9af134-0x6d9af464`) gives each converted entry `D3DFORMAT_OP_TEXTURE`:
- Render-target-texture ops come only from the PCI-id table (`runtime.md` §4.3). `121a:0009` = `0x4580` grants R5G6B5 and A8R8G8B8 only, so **no G34 format can become a render-target texture**. G34 needs none to.
- Display-mode entries are appended as **separate** entries (`0x6d9af53c-0x6d9af6b5`).
- The lookup `0x6d9ac790(format, list, count, ops)` matches only an entry whose format is equal **and** whose ops contain every requested bit.
- So the validation pass (`0x6d9af710-0x6d9af7e2`) cannot be tripped by a texture-only entry:
  - its "R5G6B5 and X1R5G5B5 must not both be display modes" check asks for op `0x400`;
  - a texture-only X1R5G5B5 carries op `0x1`.
- **Existence proof:** R5G6B5 is already in both the texture list and the display entries today, and the 16 bpp device works.

### 2.2 What the TMU returns, and the layout it walks

SPEC §8.76 L3867-3886 (`textureMode` tformat, expansion to 32-bit ARGB); codes H3DEFS:265-292:

| code | format | alpha | R, G, B | D3D format it serves |
|---|---|---|---|---|
| 0 | RGB 3-3-2 | `0xff` | `{r,r,r[2:1]}`, `{g,g,g[2:1]}`, `{b,b,b,b}` | R3G3B2 |
| 2 | Alpha 8 | a | a, a, a | (A8: colour is not D3D's 0) |
| 3 | Intensity 8 | **`0xff`** | i, i, i | **L8** = (L, L, L, 1) |
| 4 | Alpha-Intensity 4-4 | `{a,a}` | `{i,i}` | A4L4 (nibble order: see below) |
| 8 | ARGB 8-3-3-2 | a8 | 3-3-2 as above | A8R3G3B2 |
| 13 | Alpha-Intensity 8-8 | a8 | i8 | A8L8 |
| 10 / 11 / 12 / 15 | 565 / 1555 / 4444 / 8888 | as today | | + X1R5G5B5 / X4R4G4B4 / X8R8G8B8 with alpha forced to 1 |

**Byte and nibble order:**
- **AI88 is alpha-high**, which matches D3D's A8L8 (L `0x00ff`, A `0xff00`). Our own ICD on this card packs `MESA_FORMAT_AL88` as `(alpha << 8) | luminance` and hands it to Glide as `GR_TEXFMT_ALPHA_INTENSITY_88` (`MESA/main/texstore.c:1421-1426`, `MESA/main/colormac.h:212-213`, `MESA/drivers/glide/fxddtex.c:1177-1178`).
- **AI44 nibble order: no file states it** (inferred: alpha in bits 7:4).
  - ARGB4444 and ARGB8332 both put alpha high.
  - 3dfx publishes A4L4 as L `0x0f` / A `0xf0` (`VH5/D3GLOBAL.H:989-990`) and samples it as AI44 with no swizzle (`VH5/D3TXTR.C:1994-1999`).
  - `a4l4_decode1` (§5) settles it on silicon.

**Layout: the TMU walks texel-exact levels.**
- Glide's `_grMipMapOffset` (`GL5/ditex.c:1063-1135`) is in texels, with a 1x1 level counted as 1 texel.
- `_grTexCalcBaseAddress` (`:1708-1786`):
  - multiplies by `_grBitsPerTexel` (`:232-258`: 8 for RGB332, A8, I8 and AI44);
  - rounds the sum **down** to 16, "otherwise we'll be on the wrong 'side' of the minimum aligned allocation unit".
- So a top level sits `(sum & 15)` bytes past an aligned start.
- `_grMipMapSize` ("4 is the minimum", `:840-897`) is Glide's allocation rule, not the walk.
- Glide writes a 1-texel-wide 8-bit level at a byte stride of 1, with byte masks for small levels at unaligned addresses (`GL5/xtexdl_def.c:166-240`). The 8-bit rows are therefore `w` bytes, with no padding.

**Phases.** These come from a model of `vcr_texlod_compute_ext`'s "absent levels" sum, run for every storage kind, power-of-two size to 2048, aspect at most 8 (DXT1 at least 8 wide):

| kind | shapes | non-zero phase |
|---|---|---|
| RGB16 | 72 | 1x1 → **8** (G21) |
| ARGB32, DXT1, DXT35 | 72, 57, 72 | none |
| **B8 (new)** | 72 | **1x1 → 4, 2x1 → 8, 1x2 → 8** |

G21's exhaustive check ("273 shapes, exactly one non-zero") becomes 345 shapes, exactly four non-zero.

### 2.3 What we offer today, and where

- `VcrDdD3dHalInfo` (`KMD/display/vcrdd_d3d.c:2081-2099`) lists:
  - 565/1555/4444, always;
  - A8R8G8B8 with `tex_32`;
  - DXT1-5 with `tex_dxt`.
- `g_texfmt[9]` (`:1984`).
- The format list depends only on boot-read switches, never on `pd->bpp`. `runtime-22` requires that this stay so: the D3D8 runtime reads the list at the desktop mode and builds fullscreen devices from it (`runtime.md` §11).
- Classification: `pf_kind` (`:293-310`) and `pf_tmfmt` (`:312-332`), applied through `ext_layout` (`:349-361`) and `tex_view_ext` (`:806-837`). Placement: `mipchain_ext` (`:367-466`). Copies: `texblt_level` (`:1424-1453`). Flush: `flush_written` (`:1287-1320`).
- **Latent today:** `pf_tmfmt` keys 16-bit formats on the red mask alone and never looks at `DDPF_ALPHAPIXELS`.
  - So an *unlisted* X1R5G5B5 or X4R4G4B4 surface that a DX5/6 application creates anyway is sampled as ARGB1555/4444.
  - Its undefined X bits then become alpha.
  - D3D8/9 cannot create such a surface (the runtime validates the format); DX5/6 can (`Dd_CanCreateSurface` accepts any texture format, `KMD/display/vcrdd_ddraw.c:610-631`).

### 2.5 The other titles

- **UT2003/UT2004.** `LIB/UT2004/System/D3DDrv.dll` calls `IDirect3D8::CheckDeviceFormat` (vtable `+0x28`) at `0x10010bee-0x10010cb9` for DXT1, DXT3, DXT5 (adapter X8R8G8B8), A8R8G8B8 and R5G6B5, and for nothing else.
  - Its `L8`/`A8L8` immediates (`0x10039834`, `0x1003a3de`, `0x1003ab77`) sit in D3DX's statically linked image-file loader (masks/TGA type → format), not in the texture path.
- **Max Payne.** `e2driver/e2_d3d8_driver_mfc.dll` imports `D3DXCreateTextureFromFileInMemoryEx`.
- **Thief II (NewDark).** `Thief2.exe` uses `d3dx9_43.dll` `D3DXLoadSurfaceFromSurface`.
- For both, D3DX picks the closest format the device lists (inferred), so more entries means different choices.
- No G34 format immediate feeds a D3D create/check call in `e2_d3d8_driver_mfc.dll`, `RF.exe` or `Thief2.exe`. The format tables that do appear in them are D3DX's descriptor tables, in D3DFORMAT enum order.
- **Hidden & Dangerous Deluxe.** `Bin/igraph2.dll` has its own masks→D3DFORMAT converter covering every D3D8 format (`0x1000a0ff-0x1000a1db`) plus the `D3DFMT_*` name strings. Whether it picks a newly offered format is unknown.
- **Shogo.** `d3d.ren` `0x10019dde-0x10019e2c` takes its "8 bit texture format" only with `DDPF_PALETTEINDEXED8` (`test $0x20`). RGB332 and L8 cannot be mistaken for it.
- **AvP.** `avp.exe` `0x5167ab-0x51682a` walks its enumerated list and takes the first entry with `1 << bits` at or above the image's colour need (field mapping inferred).
  - An appended RGB332 entry does not displace a 16-bit entry that comes first.
  - A "smallest that fits" ordering inside AvP would. That is unknown, and AvP has not yet reached a device on `.124` (G71).

## 3. Design

### 3.1 Scope after G17

| format | DDPIXELFORMAT entry (exact) | D3D8/9 | TMU format | storage kind | alpha | `D3DTexFmt` bit |
|---|---|---|---|---|---|---|
| X8R8G8B8 | `0x40`, 32, `ff0000/ff00/ff`, A 0 | 22 | 15 ARGB8888 | ARGB32 | forced 1 | **G17** (`D3DBigTex` bit 3) |
| X1R5G5B5 | `0x40`, 16, `7c00/3e0/1f`, A 0 | 24 | 11 ARGB1555 | RGB16 | forced 1 | **0 (1)** |
| X4R4G4B4 | `0x40`, 16, `f00/f0/f`, A 0 | 30 | 12 ARGB4444 | RGB16 | forced 1 | 0 |
| A8L8 | `0x20001`, 16, L `ff`, A `ff00` | 51 | 13 AI88 | RGB16 (2 bytes) | texel | **1 (2)** |
| L8 | `0x20000`, 8, L `ff` | 50 | 3 I8 | **B8 (new)** | `0xff` by the TMU | **2 (4)** |
| A4L4 | `0x20001`, 8, L `0f`, A `f0` | 52 | 4 AI44 | B8 | texel | 2 |
| A8R3G3B2 | `0x41`, 16, A `ff00`, `e0/1c/03` | 29 | 8 ARGB8332 | RGB16 | texel | **3 (8)** |
| R3G3B2 | `0x40`, 8, `e0/1c/03`, A 0 | 27 | 0 RGB332 | B8 | `0xff` by the TMU | 3 |
| A8 | not offered (§1.1) | never | (2) | | | path only via G94 (TMU `SST_TC_ZERO` for RGB = 0) |
| P8, A8P8 | G38 | | | | | |

The grouping follows plumbing and risk:
- **bit 0:** reuses G17's `alpha_one` only;
- **bit 1:** one new TMU code, same storage;
- **bit 2:** the new 8-bit storage kind;
- **bit 3:** the quality-reducing 3-3-2 pair, which a "fewest bits that fit" chooser could prefer over 16-bit (§2.5). Bit 3 is not to be armed without a measured consumer.

### 3.2 The switch: `Diag\D3DTexFmt`, not more `D3DBigTex` bits

- `HKLM\SYSTEM\CurrentControlSet\Services\vcrmp\Diag\D3DTexFmt`, DWORD, bits 0-3 as in §3.1.
  - **Absent = 0 = off.**
  - Read **once at boot** in `FindAdapter`, beside `D3DBigTex` (`KMD/miniport/vcrmp.c:244`). The list must be the same at the desktop and the fullscreen PDEV (`runtime-22`; the `vcrmp.c:240-243` comment).
  - Masked `& 0xf`, and zeroed on anything but a VSA-100.
- It is **honoured only on the VSA-100 texture path** (`pd->tex_ext`, i.e. any `D3DBigTex` bit; G20 makes 7 the default).
  - The new formats need the ext views, the 26-bit base and the driver's own placement.
  - The default path (`tex_view`, DirectDraw placement, `vcrdd_d3d.c:754-799`) is never touched.
- **Why not `D3DBigTex` bits 4-7:** the Thief II launcher's `findstr /c:"0x[57df]$"` (§1.4) would read 0x17 as "BigTex off".
- **Transport:**
  - Append `vcr_u32 d3d_texfmt;` to `vcr_info` (`KMD/include/vcr_ioctl.h:63-108`), which is append-only by design ("older tools read a shorter struct"), instead of taking four more bits of the crowded `flags` word (bits to `0x4000` used; G01, G02, G05, G07, G08, G09, G16 and G17 all propose bits at `0x8000` and up). G05 already proposes the same pattern for `Diag\D3DFeat` (an appended `info.d3dfeat`, with `info` zeroed first, `G05.md:297`); the two fields should land together.
  - `VcrDd2dInit` (`KMD/display/vcrdd_2d.c:432-472`) must `memset(&info, 0, sizeof info)` before the IOCTL and honour the field only when the returned byte count covers it. Today `info` is an uninitialised stack variable, so a shorter reply from an older miniport would hand it garbage.
  - If the implementer prefers flags for consistency, four positive `VCR_INFO_F_*` bits work too. `test_vcr_kmd_abi.c::every_vcr_info_flag_owns_one_bit` then guards them.
- **Display driver:** `pd->tex_fmt = pd->napalm && pd->tex_ext ? (info.d3d_texfmt & 0xf) : 0;`
  - New `ULONG tex_fmt;` in `KMD/display/vcrdd.h:70-75`.
  - One INFO event, "armed (Diag\\D3DTexFmt): X1R5G5B5/X4R4G4B4 %s, A8L8 %s, L8/A4L4 %s, 3-3-2 %s". Codes 24-31 of event 513 are already claimed by sibling designs: take the next free ones, proposed **40/41/42**, and re-check at implementation.

### 3.3 The list (append-only)

`VcrDdD3dHalInfo` builds the list through G17's `vcr_texfmt_list(armed, …)` (`include/vcr_texfmt.h`, created by G17). G34 extends `armed` with `VCR_TFA_X16 0x10`, `VCR_TFA_AL88 0x20`, `VCR_TFA_L8 0x40` and `VCR_TFA_332 0x80`. These are internal bits of `armed`, not Diag bits.

**Order:**

```
565, 1555, 4444 | 8888 (tex_32) | DXT1..DXT5 (tex_dxt) | X8R8G8B8 (G17) |
X1R5G5B5, X4R4G4B4 (bit 0) | A8L8 (bit 1) | L8, A4L4 (bit 2) | A8R3G3B2, R3G3B2 (bit 3)
```

- **Append-only.** Every DX5/6/7 title that takes the *first* match from `EnumTextureFormats` keeps the entry it takes today.
- R3G3B2 is last of all.
- `g_texfmt` becomes `g_texfmt[VCR_TEXFMT_MAX]` with `VCR_TEXFMT_MAX` = 17. G38's P8/A8P8 would append after these.
- Luminance entries need a `texfmt_lum()` helper: `DDPF_LUMINANCE | (a ? DDPF_ALPHAPIXELS : 0)`, `dwLuminanceBitCount`, `dwLuminanceBitMask`, `dwLuminanceAlphaBitMask`. All of these are in the DX8 DDK headers the build uses (`~/retro3dfx-toolchain/devtools/dx8ddk/inc/ddraw.h:710, 720, 748, 4011`).
- 8-bit RGB332 must carry `dwRGBBitCount = 8`. `texfmt()` hard-codes 16 (`vcrdd_d3d.c:1994`).
- **No cap bit changes:**
  - TextureCaps keeps ALPHA. No ALPHAPALETTE (that is G38).
  - Only the format list grows.

### 3.4 Classification (`include/vcr_texfmt.h`, G17's `vcr_texfmt_classify`)

**New cases, each only with its `armed` bit.** The test on `dwFlags` is for **equality**, like the runtime's:

| pf | → kind, tmfmt, `alpha_one` |
|---|---|
| `0x40`, 16, R `7c00` | RGB16, `TM_FORMAT(11)` = `0xb00`, **1** (X16) |
| `0x40`, 16, R `0f00` | RGB16, `0xc00`, **1** (X16) |
| `0x20001`, 16, L `ff`, A `ff00` | RGB16, `TM_FORMAT(13)` = `0xd00`, 0 (AL88) |
| `0x20000`, 8, L `ff` | **B8**, `0x300`, 0 (L8) |
| `0x20001`, 8, L `0f`, A `f0` | B8, `0x400`, 0 (L8) |
| `0x41`, 16, A `ff00`, R `e0` | RGB16, `0x800`, 0 (332) |
| `0x40`, 8, R `e0`, G `1c`, B `03` | B8, `0x000`, 0 (332) |

**Unarmed, every result is today's.**
- The new formats are refused (`KIND_NONE` → drawn untextured with the existing once-per-handle 513/7 "texture refused" WARN).
- An off-list `0x40`/16/`7c00` surface still classifies as ARGB1555 with `alpha_one` 0, the §2.3 latent behaviour. It changes only when bit 0 is armed, which is then a fix for DX5/6 titles that create unlisted X formats.

**Two helpers for later items:**

- `vcr_texfmt_port_ok(tmfmt)`: true only for `0xa00`/`0xb00`/`0xc00` (§3.8).

**New TMU codes** in `KMD/include/vcr_3dregs.h` beside `TF_RGB565`: `TF_RGB332 0`, `TF_I8 3`, `TF_AI44 4`, `TF_ARGB8332 8`, `TF_AI88 13`. `TF_A8 2` and `TF_P8 5` are documented, unused. `test_vcr_kmd_bigtex.py::test_register_codes_are_the_gpl_h5_headers` pins them against H3DEFS.

### 3.5 The 8-bit storage kind (bit 2 / 3 only)

In `KMD/include/vcr_texlod.h` and `KMD/common/vcr_texlod.c`:
- `#define VCR_TEXK_B8 4u /* 1 byte a texel: RGB332, I8, AI44 (VSA-100 path only) */`.
- `vcr_tex_level_bytes(B8, w, h) = w * h`, with no minimum (§2.2).
- `vcr_texlod_compute_ext`:
  - accepts `kind <= VCR_TEXK_B8`;
  - B8 only with `VCR_TEXF_NAPALM`;
  - pitch must equal `w` (the 16/32-bit rules stay as they are);
  - TBIG works unchanged: its absent-level loop already calls `vcr_tex_level_bytes(kind, …)`.
- `vcr_tex_chain_usable` returns `have` for B8, as for every non-DXT1 kind.
- **New helper `vcr_tex_row_bytes(kind, w)`** (2w, 4w, w, 0 for compressed). It replaces the two ternaries in `mipchain_ext` (`vcrdd_d3d.c:415-416` for the layout check and `:454-455` for `lPitch`), so no site can miss the new kind.
- `vcr_tex_writeback_addr` is unchanged: B8 is not RGB16, so it gets no write-back.

### 3.6 Placement: the phase, generalised

- G21 defines `vcr_tex_chain_pad(kind, w, h)` = the absent levels' size mod 16 (or the negated value with TBIG), applied to the **top** only. A per-level call for a chain's sub-level gets no pad: that is G21's `mip_level` guard, since G07 owns contiguity. For B8 it returns 4/8/8 (§2.2) with no new code.
- **The flag must become a count.**
  - G21 stores `SF_PAD8 0x8` in the surface-local `dwReserved1`, and `VcrDdD3dFreeMipChain` (`vcrdd_d3d.c:586-601`) frees `fpVidMem − 8`.
  - G34 needs `SF_PAD(n)` = `(n & 0xf) << 8` (bits 11:8, beside `SF_MIP_TOP 1`, `SF_MIP_LVL 2`, `SF_DIRTY 4`), and the free path subtracts `SF_PAD_OF(s)`.
  - Freeing an address that is not the block's start corrupts DirectDraw's heap, so this is a correctness requirement, not tidiness.
  - If G21 lands first with `SF_PAD8`, G34 converts it. Better: G21 adopts the 4-bit count from the start.
- **Without G21:** G34 carries `vcr_tex_chain_pad` itself and applies it **to kind B8 only**, so the 16 bpp 1x1 placement stays exactly today's.
- The block is `total + pad`, and the top goes at `base + pad`. 16-byte start alignment is unchanged (`vcrdd_d3d.c:438-440`).
- **Mip chains:** XP sends one `CreateSurface` per level (`runtime.md` §7.1). Separately placed levels of under 16 bytes are therefore not contiguous:
  - an 8-bit 2x2 (4 bytes) is followed by its 1x1 at +16, where the TMU expects +4;
  - a 4x2 (8 bytes) by its 2x1 at +16, where it expects +8;
  - the 16 bpp 2x2→1x1 has the same problem today.

  So B8 chains lose their last one or two levels until **G07**'s whole-chain reservation lands. `mipl8` (§5) asserts only levels down to 4x4 until then.

### 3.7 The combine: alpha read as 1 for X1R5G5B5 and X4R4G4B4

This is G17's mechanism (`G17.md` §4.3), reused unchanged. `tmu_view.alpha_one` is set by `tex_view_ext` from `vcr_texfmt_classify`. Then, at the three sites in `compute_regs`:

| site | today | X16 texture |
|---|---|---|
| one texture, TMU0 (`vcrdd_d3d.c:962`) | `TM_TC_REPLACE \| TM_TCA_REPLACE` = `0x41000 \| 0x08200000` | `TM_TC_REPLACE \| TM_TCA_ONE` = `0x41000 \| 0x24000000` |
| two textures, TMU1 = stage 0 (`:951`) | `TM_TCA_REPLACE` | `TM_TCA_ONE` |
| two textures, TMU0 = stage 1 local (`:954`) | `stage1_combine` TCA | `vcr_tca_alpha_one`: REPLACE → ONE, MULT → PASS, ADD → ONE, PASS → PASS |

- `TM_TCA_ONE` = `SST_TCA_MZERO | SST_TCA_INVERT_OUTPUT` = `(1<<26)|(1<<29)` (H3DEFS:374, confirmed this session).
- Everything downstream (`CP_ASEL_TMU`, `CC_M_ATMU`, the alpha test, SRCALPHA) then reads 1.0. RGB is untouched.
- **Single pass, no multipass.** L8, A4L4, A8L8, R3G3B2 and A8R3G3B2 need no combine change: the TMU already returns D3D's values (§2.2).
- **Constraint for G12/G13/G14.** A future combine that reads a TMU's *local texel alpha* directly must treat `alpha_one` formats as alpha = 1. That covers `combineMode` LOCAL_TA muxes and `tc_mselect` 3. It can rewrite the op, as 3dfx rewrote the muxes for alpha-less textures (`VH5/D6MT.C:4829-4850`). The TCA override covers only the TCA's *output*.

### 3.8 Copies, flush, Blt, Lock

- **TEXBLT** (`vcrdd_d3d.c:1424-1453`) copies `surf_bpp/8` bytes a texel. `surf_bpp` reads `dwRGBBitCount`, which is the same union field as `dwLuminanceBitCount`, so 8- and 16-bit luminance copy correctly with no change. `has_pixfmt` (`:166-170`) is true for them for the same reason.
- **Flush.** `flush_written` (`:1310-1311`) passes `vcr_texfmt_port_ok(tmfmt) ? fpVidMem : ~0u` into `vcr_tex_writeback_addr`.
  - The texture-port write-back stays on textureMode formats 10/11/12, the ones it was proven on.
  - X1R5G5B5 and X4R4G4B4 keep it (formats 11/12, identical storage). AI88, ARGB8332 and every B8 format do not.
  - The base-flip that silicon needs is unchanged (`vcrdd_3d.c:253-270`).
- **`Dd_Blt` guard.**
  - Beside the FOURCC guard (`vcrdd_ddraw.c:485`) and before `if (p->IsClipped)`: while `pd->tex_fmt != 0`, a source or destination that is a texture carrying its own `dwRGBBitCount` different from `pd->bpp` returns `DDHAL_DRIVER_NOTHANDLED`.
  - The HEL then copies with the surface's real format, as it already does for DXT.
  - Without the guard, `surf_bytespp` (`:389-394`) would blit an L8 texture at 2 or 4 bytes a texel when `DDRAWISURF_HASPIXELFORMAT` is clear. Whether NT sets that flag on DX6-created textures is unknown (§10); the guard is correct either way.
  - With G34 off, nothing changes.
  - The same desktop-depth assumption may affect 16 bpp textures at a 32 bpp desktop today. That latent case is outside G34; it is noted for G56/G61's owner.
- **Lock/Unlock:** unchanged. The runtime computes the pointer from `fpVidMem` and `lPitch` = `w` (B8).

### 3.9 Phase 0: measurement (default on, log only, no register change)

## 4. Gating

- **Default OFF.** `Diag\D3DTexFmt` absent = 0. Each bit is armed alone, **one bit per clean boot**, under supervision. Arming needs:
  - an activation check, then `scripts/fleet/safe-reboot.py`;
  - `REGWRITE HKLM SYSTEM\CurrentControlSet\Services\vcrmp\Diag D3DTexFmt REG_DWORD <n>`, read back.
- **Not safe to land default-on.** Offering a format changes what titles may choose (§2.5, §8), and the B8 kind, AI44 and AI88 have never run on this silicon. Even after proof the bits should stay opt-in unless a consumer is measured. G20's default (`D3DBigTex`=7) deliberately stays below bit 3 and does not touch `D3DTexFmt`.
- **Safe to land default-on now:**
  - Phase 0's two log events. No register traffic, and not on the drawing path.
  - The new d3dprobe tests and caps rows. They are explicit-only, change no driver state, and a named test that is skipped fails (`2991448`).
  - The refactors, provided the native test pins today's list and registers:
    - `vcr_tex_row_bytes`;
    - the `vcr_info` zeroing in `VcrDd2dInit`;
    - the `SF_PAD` count. Pads are written only for B8, or for G21's bit.

**What would raise the priority.** No game scene is expected to change, because no consumer is known; the on-box game check is a **no-regression** check. Two outcomes change that:
- **A consumer.** If boot A's 513/42 or 513/7 shows a DX5/6 title creating L8/A8L8/A4L4/332 textures that are refused today, it is drawn untextured now. That title's own scene, fullscreen at its staged mode, becomes the proof for the matching bit, and G34 rises to P1/P2.
- **A regression.** If an armed boot changes a working title's frame (H&D, Thief II, Max Payne), that bit stays opt-in, and the title's choice is recorded in the README's Findings.

## 8. Risk

- **Proven paths:**
  - Fresh install, no `D3DBigTex`: untouched.
  - `D3DBigTex`=7 with `D3DTexFmt` absent: the list, classification, registers and placement are byte-for-byte today's, pinned by the native list test and `test_off_the_hal_is_the_proven_one`. Only two deduplicated INFO events are added, outside the drawing path.
- **Glide/OpenGL coexistence, SLI, flip:** no new registers. The changes are textureMode format codes and the TCA bits inside the same writes. No `combineMode`, `chipMask` or `sliCtrl`, and no flip-path code.
- **Behaviour change when armed (the main risk).** Titles that choose formats themselves may switch. None of these is a crash, but each is a visible change in a title that works today:
  - H&D's LS3D converter;
  - Max Payne's and Thief II's D3DX loaders;
  - DX5/6 enumerators with "best match" rules (AvP; JK/MotS for luminance entries).

  Mitigations: append-only order; one bit at a time; 513/41 shows exactly who switched; bit 3 (3-3-2) is not recommended without a consumer.
- **Memory safety:**
  - Without the Blt guard, an 8-bit texture is overrun 2-4x by an engine blit.
  - Without the pad *count*, freeing a padded 8-bit tiny texture hands DirectDraw's heap a pointer that is not a block start.
  - Without `port_ok`, the write-back writes a dword through the texture port of an unproven format.

  All three are in §3 and pinned by tests.
- **The Thief II launcher:** avoided by design (`D3DTexFmt`, not `D3DBigTex` ≥ 0x10).
- **Silicon unknowns:** AI44 nibble order, AI88 and B8 on the VSA-100. The decode tests settle each before any game runs with the bit.

## 9. Effort, dependencies, priority, games

- **Effort: M overall.**
  - Phase 0: S.
  - Phase 1 (bits 0-1, given G17's plumbing): S.
  - Phase 2 (bit 2: B8 kind, pad count, Blt guard, 7 probe tests): M.
  - Phase 3 (bit 3): S.
- **Depends on:**
  - **G17** (`vcr_texfmt.h`, `alpha_one`, `TM_TCA_ONE`, `vcr_tca_alpha_one`, the append order; X8R8G8B8 itself);
  - **G21** (`vcr_tex_chain_pad`, the per-level guard; the pad must be a count);
  - **G07** (whole-chain packing, for B8 chains' last levels);
  - **G20** (the ext texture path on by default; G34 is honoured only with it);
  - **G74** (d3dprobe caps rows and test infrastructure);
  - **G01** (a clean FIFO before any on-box probe).
- **Provides for:**
  - G08: `vcr_texfmt_has_alpha` for the legacy MODULATE rule;
  - G12/G13/G14: the `alpha_one` constraint (§3.7);
  - G09: a colour key on these formats must expand from their own layout, or be refused;
  - G38: append after G34's entries;
  - G94: the only route to A8.
- **Games unblocked: none measured.**
  - Halo's missing format is X8R8G8B8, which is G17's.
  - Candidates, unmeasured: Hidden & Dangerous Deluxe (LS3D converter); DX5/6 titles found by Phase 0 creating off-list formats.
  - Max Payne and Thief II would *change* format choices, not gain anything.
- **Priority: P3.** Phase 0 is worth landing now because it is free and turns every "(inferred)" consumer above into a measurement. The rest waits for a consumer or for parity work.

## 10. Open questions

1. **AI44 nibble order on the VSA-100.** Alpha high is inferred; `a4l4_decode1` decides.
2. **Does NT set `DDRAWISURF_HASPIXELFORMAT` on DX6-created textures?** If not, `surf_bytespp`'s desktop-depth fallback also mis-blits today's 16 bpp textures at a 32 bpp desktop. That is outside G34 (G56/G61), but the same measurement answers it: a DX6 test, or the 513/42 field logging `dwFlags`.
3. **Does any staged title ask for these formats?** Phase 0 answers it for DX5-7. D3D8/9 titles need the optional API-level proxy (§3.9), worth building only if a decision depends on it.
4. **Will H&D, Max Payne (D3DX) or Thief II (D3DX) switch formats when offered**, and does the switch look the same? Boots B-D.
5. **The pad encoding:** G21's `SF_PAD8` versus a 4-bit count. G07, G21 and G34 should settle on the count before the first of them lands.
6. **`vcr_info` field or four flag bits** for the switch? The flags word is filling (§3.2).
7. **Does the DX6 runtime validate a bound texture's format against the enumerated list** (`d3dim.dll`)? If it does, off-list X formats in DX6 titles cannot happen, and the §2.3 latent case is moot.
8. **A8:** only via G94's DX8 DDI. If that is ever built, the TMU's A8 must have its RGB zeroed (`SST_TC_ZERO` in the TMU colour combine). No staged title needs it today.
