## 0. Verdict

1. **The gap is real, and it is larger than "one image".**
   - The 11-08 strip (`SWP/sweep_1108_fixed/RainbowSix_intro_then_menu_z16in32.png`) shows only that
     `CreateDevice` now succeeds. In it, the intro plays (Smacker) and the main menu appears.
   - Both of those are very likely **DirectDraw, not Direct3D triangles**. `.123`'s compat row records the
     same menu as `renderer ddraw` (measured 2026-09-01). The cursor in the strip is a clean arrow, with no
     key-colour box around it, and our HAL draws no texture colour key (section 3.1).
   - So **no Rainbow Six triangle has ever been seen on vcr-kmd, and the 16-over-32 Z (be58b7d) has never
     depth-tested a pixel in this game.**
   - The compat row for `.124` still says `runs: untested`.
2. **Static evidence says R6's in-game scenes hit three HAL gaps for certain** (section 2). None of them can
   show in a menu:
   - **Texture colour key (G09).**
     - `Surface::SetTransparentValue` calls `IDirectDrawSurface::SetColorKey(DDCKEY_SRCBLT)` (VA 0x46ad9a).
     - The renderer has a `SetRenderState(COLORKEYENABLE)` setter (VA 0x47ab62/0x47ab74).
     - `R6/data/texture/Sherman.CXP` declares **294 colour-keyed materials**: glass, tree lines, shrubs,
       vines, chain-link, railings, grills, chandeliers, bullet holes, muzzle flashes, smoke, map icons and
       **the HUD reticle** (`reticule.bmp colorkey 0 0 0`).
     - Our HAL advertises `D3DPTEXTURECAPS_TRANSPARENCY` (`KMD/display/vcrdd_d3d.c:2035`) and ignores the
       key, so every one of these should draw its key colour opaque.
   - **Lines (G16).** The renderer's only `DrawIndexedPrimitive(D3DPT_LINELIST, D3DVT_LVERTEX)` wrapper
     (VA 0x474140) is called six times from one class (VA 0x461a00-0x461b80). That class sits right after the
     loader of `stairUpIcon.sob`, `stairDownIcon.sob`, `ladderUpIcon.sob` and `ladderDownIcon.sob`.
     It is very likely the **planning map** (inferred). The DP2 walker parses and skips every line opcode
     (`vcrdd_d3d.c:1690-1715`), so the map's floor plans and team paths would be invisible.
   - **Legacy render states (G08).** There are setters for TEXTUREMAG/TEXTUREMIN (all six values),
     TEXTUREMAPBLEND (all eight), WRAPU/V and SHADEMODE (Appendix A). R6 draws through
     `IDirect3DDevice2::SetRenderState` + `DrawPrimitive`, not execute buffers. Our HAL stores these states
     and never applies them.
3. **The Z pairing itself is very likely fine.** This is a code review, not a measurement.
   - 3dfx's own V5 driver did the same thing at attach time: "16bpp render target, 32bpp zbuffer: silently
     substitute 16bpp zbuffer". It kept the 32-bit allocation and its pitch (`VH5/DDSURF.C:2243-2260`,
     `FX_ORIGINALLY_Z32`).
   - Our chain is `vcr_rt_format(1,16,32)` = 16, then aux stride = the Z's own 4-byte pitch
     (`KMD/include/vcr_3dseq.h:73-74`). The depth scale and the clear scale both follow the target format
     (`KMD/display/vcrdd_3d.c:153, 292`).
   - R6 clears through `IDirect3DViewport2::Clear(TARGET|ZBUFFER)` (VA 0x4712e6), which reaches our Clear2/DP2
     CLEAR. It does not go through a DirectDraw depth fill.
   - The risks left are the ones only a running game can show: the Z handle dropped at a re-target, and the
     clear route (section 6, outcomes B and C).
4. **What this design delivers:**
   - (a) a supervised in-game investigation of R6 on the deployed build, with captures that cannot be the
     wrong buffer (R6's own F2 screenshot, section 2.5);
   - (b) the full D3D re-sweep 95678704 never had;
   - (c) the compat row;
   - (d) a native regression test that pins R6's whole pairing chain, not just `vcr_rt_format`;
   - (e) a lab test of R6's exact Z path, `z16in32`, which needs the DX5 probe G75 adds (D3D8 cannot create
     this pair at all);
   - (f) one optional log-only line that makes the 16-over-32 path visible in every future ring.
5. **Priority P1.**
   - G69 is a measurement prerequisite for P0 work: the R6 scenes are how G09 and G16 become P0 for a staged
     title, and how they are verified.
   - G10 and G20 also lean on 16-over-32 as "proven" (`designs/G10.md` section 7, `designs/G20.md` boot C), and
     it is not yet proven in any game.
   - No driver behaviour changes here, so nothing needs a Diag switch.

## 2. New static evidence: what R6 will ask of the HAL in game

### 2.1 Its Z pick is the DX5 SDK's D3DApp, deepest first

- R6 carries the D3DApp error strings verbatim: "Unsupported Z-buffer depth requested by device.", "Could not fit
  the Z-buffer in video memory for this hardware device.", "CreateZBuffer() : AddAttachedSurface()",
  "PickDriverAndMode()", "Cannot find a Direct3D device driver which is compatible with the current display
  depth." (`strings` lines 4796-4826).
- D3DApp's rule is to take `dwDeviceZBufferBitDepth` deepest first: DDBD_32, then 24, then 16 (inferred from
  the DX5 SDK sample this code is built from).
- Our HAL reports `DDBD_16 | DDBD_32` (0x500) when `rt32` is set (`vcrdd_d3d.c:2053-2080`). That is
  where the 32-bit Z comes from.
- The request is the legacy `DDSD_ZBUFFERBITDEPTH = 32`, not a pixel format. The 09-28 ring shows the surface:
  0x12c000 bytes for 640x480, i.e. 4 bytes a pixel.
- On a fresh install (D3D32 off) the list is DDBD_16 alone, so R6 takes plain 16/16 (`vcr_rt_zlist(0)`).

### 2.2 Render-state setters (the Renderer class; the device pointer is the global 0x8bb8dc = Renderer 0x8bb690 + 0x24c)

All of these go through `IDirect3DDevice2::SetRenderState` (vtable +0x5c) with immediate state and value
arguments. The full table is in Appendix A. The ones that matter here:

| state | values the setter can send | our HAL today | gap |
|---|---|---|---|
| COLORKEYENABLE (41) | 0, 1 (game mode 0 → TRUE) | stored, never applied | **G09** |
| TEXTUREMAG / TEXTUREMIN (17/18) | 1-6 (NEAREST ... LINEARMIPLINEAR) | stored, never applied: point sampling | **G08** |
| TEXTUREMAPBLEND (21) | 1-8 (DECAL ... ADD) | stored, never applied: MODULATE + texture alpha | **G08** |
| WRAPU / WRAPV (5/6) | 0, 1 | ignored | G86 (hardware) |
| SHADEMODE (9), FILLMODE (8) | 1-3 | ignored | G24 (R6 sends FLAT only for a software device, `designs/G24.md` App. A) |
| SPECULARENABLE (29) | 0, 1 | ignored | G25 |
| STIPPLEENABLE (39) | 0, 1 | ignored | G90 |
| FOGENABLE (28), FOGCOLOR (34, dynamic) | 0/1 | vertex fog through the synthetic 1/W | G32 (no FOGTABLEMODE setter: vertex fog, as `designs/G31.md:157` found) |
| SRCBLEND (19) / DESTBLEND (20) | src 1, 2, 5, 6, 9, 11, 12, 13; dst 1-6 | all in our caps and mapped | - |
| ZENABLE+ZWRITEENABLE (7+14), ZFUNC (23) | 0/1; 1-8 | mapped (ZENABLE=TRUE only) | - |
| TEXTUREHANDLE (1) | the texture object's stored handle (VA 0x473818; 0 to unbind at 0x47382c) | mapped | - |

- The setters expose the whole enumeration of each state, so **which values R6 actually sends on the HAL
  device is not settled statically**. G76's counters settle it (Phase 2).
- R6 is also the cleanest title on the fleet for runtime.md §14's open inference: does `d3dim.dll` pass the
  legacy states raw for `IDirect3DDevice2::SetRenderState` callers, and not only for execute buffers? R6
  never executes a buffer (2.4).

### 2.3 Texture colour key: certain, and everywhere

- `Surface::SetTransparentValue` (VA 0x46ad70) is
  `lpDDS->SetColorKey(DDCKEY_SRCBLT /*8*/, {key, key})`, with the error string at VA 0x89e08c. More
  `SetColorKey(8, ...)` sites are at VA 0x458f6e, 0x459042 and 0x495ca4.
- So a keyed material gets `DDRAWISURF_HASCKEYSRCBLT`, and with COLORKEYENABLE set, G09's AND rule holds.
- `Sherman.CXP` (17,694 bytes, plain text) sets `colorkey r g b` on 294 materials, by section:
  - Glass: black key.
  - Training levels: tree line, shrub line, grass, cargo net, bed springs.
  - M01 Embassy: chain-link `01_chain` (224,224,160), vines (88,120,88), flowers, railings, chandelier
    (white), fire escape.
  - M02 Congo: tree limbs and tree tops.
  - Effects: muzzle flash, sparks, breach charge, smoke, fire, propeller.
  - `reticule.bmp`, `reticuleCenter.bmp`: black key.
  - "Map Icons": `stairdn.bmp` (57,130,151) and the rest.
- 21 materials add `textureformat 0 4 4 4 4`, an ARGB4444 request: the .tga effects and `shadow2.tga`,
  several of them keyed as well.
- **No material says `mipmap`**, so R6's textures are single-level. On `.124`'s D3DBigTex path that means
  driver-placed and 16-byte aligned (481acfd), so G07, G26 and G27 do not concern this title.
- The 1998 readme describes what a driver without the key looks like: "my mouse is a large black box"
  (`R6/readme.txt` Trouble Shooting, written for 3dfx reference drivers).

### 2.4 How it draws

- **Calls through `IDirect3DDevice2`:**
  - `DrawPrimitive` (+0x74):
    - `TRIANGLEFAN` of `D3DVT_LVERTEX` (VA 0x469f28);
    - 4-vertex fans of LVERTEX, i.e. quads (VA 0x7bbd95, 0x7bc9dc, 0x7bf606);
    - a `TRIANGLESTRIP` of `D3DVT_TLVERTEX` (VA 0x7adcd4).
  - `DrawIndexedPrimitive` (+0x78):
    - `TRIANGLELIST` of LVERTEX (VA 0x474537, 0x48c8ba, 0x7bd29f ...);
    - TRIANGLELIST of TLVERTEX for 2D quads (VA 0x5b95da, 0x5b9608);
    - **`LINELIST` of LVERTEX** at VA 0x474163, through the wrapper at VA 0x474140.
- No execute buffer is executed. `IID_IDirect3DExecuteBuffer` is present only because the whole DX5
  `dxguid` table is linked: every DX5 IID sits contiguous at file 0x4408b8-0x440a28.
- D3D transforms and clips the LVERTEX geometry, so the DP2 stream carries TLVERTEX (FVF 0x1c4: XYZRHW, DIFFUSE,
  SPECULAR, TEX1) (inferred).
- **The line lists:**
  - 0x474140 is called only from VA 0x461a35, 0x461a75, 0x461ab4, 0x461af3, 0x461b3a and 0x461b79, in pairs per
    method.
  - The index count passed is 2 x the line count.
  - Each call is preceded by a material select (VA 0x473860).
  - The class's loader, immediately before it (VA 0x4615xx-0x4618a0), loads the four stair and ladder icon
    `.sob` models.
  - `pmplan.txt` names four team colours (BLUE/RED/GREEN/GOLD), waypoints and "PREVIEW".
  - Reading: **these are the planning map's floor plans and team paths** (inferred). On our HAL they draw
    nothing.

### 2.5 A capture that cannot be the wrong buffer: R6's own screenshot (F2)

- VA 0x404d50 finds the first free `ShermanScreenShot%d.BMP` (`sprintf` plus an existence loop). It then calls
  the renderer (VA 0x473bd0), which `Lock`s the Surface at Renderer+0xe48 and writes a 24-bit BMP. It converts
  from the surface's own masks and handles PALETTEINDEXED8 separately.
- It is reached only from case 0x71 of the key switch at VA 0x40f720: `lea -0x8(%eax)`, `cmp $0xd6`, byte table
  0x40fda0, jump table 0x40fcac.
- That switch covers 8..0xDE, the virtual-key range, so **0x71 = VK_F2** (inferred: the argument is read as a
  WM_KEYDOWN VK). PrintScreen (0x2c) falls to the default.
- The file lands in the current directory, which the launcher sets: `cd /d "%~dp0"` in `R6/Play Rainbow Six.bat`.
- What makes it valuable:
  - It reads video memory through our DirectDraw `Lock` from inside the game, at its own resolution, with no
    GDI back-buffer ambiguity (G79) and no `vcrctl`/ExtEscape (the project rule).
  - It is a complete frame (inferred: taken between frames from the message loop).

### 2.6 Options and registry names (for planning the runs)

- **VIDEO options:** FORCE SOFTWARE, SHOW FOG, BRIGHTNESS and RESOLUTION "320X240 LOW / 640X480 MED / 800X600 HIGH"
  (`R6/data/text/interface/english/options.txt`). **800x600x16 is R6's highest mode.**
- **Value names:** `VideoResolution`, `ShowFog`, `GammaValue`, `SoftwareOnly`, `FullScreen`,
  `UsePrimaryDisplay`, `DisplayDeviceGuid`, `PromptForDefaultPlan`, `PromptForGameStart` (strings 3878-3983).
  - Their key is `Software\Red Storm Entertainment\Tom Clancy's Rainbow Six`. The staged `install.reg:83-87`
    writes `FullScreen=1` and `SoftwareOnly=0` under HKLM.
  - Whether the in-game options write HKLM or HKCU is not settled.
- **v1.02 readme:** "Will now force software if R6 cannot initialize your hardware card". **A run must prove
  that our HAL drew the scene, not R6's software path** (section 4, check P).
- Its own log is `Sherman.log` in the game directory. On 11-08 it named the failure: "CreateDevice ... Generic
  failure", `PLAN:163`.
- The fallback error text is "We are sorry, but we are unable to initialize the renderer at 640x480x16 either"
  (strings 3810-3811). R6 retries 640x480x16 after a failed mode, so a refused device costs extra CRT switches
  (G11).

## 4. The investigation

### 4.1 Preconditions (every session)

- **Build:** the deployed `vcrdd.dll`.
  - Record its md5. It is expected to be 95678704; if it has moved on, every new D3D Diag bit must be OFF, which
    by the project's default-off contract reproduces 95678704's paths.
  - `vcrmp.sys`: as deployed.
  - `D3D32`=1 and `D3DBigTex`=7, as armed today: that is R6's configuration on `.124`.
- **Boot:**
  - a **cold boot with no Glide/OpenGL session since** (G01: a stale `cmdFifo0` erases every D3D triangle while
    clears still work), or G01's reset landed and verified;
  - the activation check (`LICSTATUS` / `wmic Win32_WindowsProductActivation`), then
    `scripts/fleet/safe-reboot.py 192.168.1.124`.
- **Ring:** `Diag\LogLevel`=2 and `Diag\LogEntries`=8192, set before that boot (read at boot,
  `KMD/miniport/vcrmp_log.c:279-283`).
  - These are logging values, not behaviour switches. They match `designs/G04.md` §4.4 Boot 1, so one boot can
    serve both. If G04's `D3DBeat` is armed in that boot, R6 gets a beat too.
  - At LogLevel 3 the per-DP2 DEBUG events wrap the ring within seconds of play (`reports/onbox.md` §6).
  - Read back each value after writing it (REGREAD of the key).
- **Desktop:** at 1280x1024x32@85, screensaver dismissed (`UIKEY SHIFT`), and the benchmark quiesce
  (`AI_DISABLE`, `rotate_wall`, `wuauclt`, `daemon.exe`, as `driver-bench` preflight does).
- **Rules:**
  - no `vcrctl`/ExtEscape while R6 runs; read the ring **after** it exits (`KMD/tools/vcrlog.py fetch`);
  - mode switches at least 5 s apart (R6 makes one at start and one at exit);
  - vsync on, no AA, stock clock;
  - **attended for the first in-game run.** It is a first D3D game session on this path, and if R6 ever needs
    a kill, use the `gamerun.py` order: WM_CLOSE by pid, then a forced kill by pid.
- **Never press ESC during the intro: it quits R6** (`.123` compat row). Let `intro.smk` (28.6 MB, about 90 s)
  run out. In the action phase, ESC opens the quick menu (`R6/readme.txt` known issues).

### 4.2 Phase 0: lab (before any game; needs G75's DX5 probe)

Run `z16in32` (section 8) at fullscreen 640x480x16 from the 32 bpp desktop, in the same boot, before R6.

| result | meaning | then |
|---|---|---|
| pass | the R6 pair draws and depth-tests in the lab, across a flip | go on to Phase 1 |
| device refused, ring 513/12 or 513/15 | be58b7d has regressed, or Z pitch/size was refused | stop; do not launch R6 (each failed device costs 2+ CRT switches); new gap |
| `zcolumns` fails on odd columns | the clear wrote 32-bit words over the 16-bit rows | see outcome C; G61's depth-fill item |
| `zorder_*` fail only after the flip | the Z handle is dropped at SETRENDERTARGET | outcome B3 |

If G75 has not landed, Phase 1 still runs. Its outcomes B and C (section 6) catch the same faults in game, at the
cost of the CRT if the device is refused.

### 4.3 Phase 1: baseline in game (one boot, about 1.5 h attended plus the sweep)

## 5. Instrumentation (optional, log only)

**What:** one INFO line per context, emitted only when a 16 bpp target is accepted over a 32-bit Z:

```
513 what <next free, assigned by the integrator> (INFO):
  "context %u: 16 bpp target over a 32-bit Z: 16/16 in its rows, aux stride %u"   a=ctx b=z pitch c=z offset
```

**Where:**
- `D3d_ContextCreate` (`vcrdd_d3d.c:1163-1208`), after the target is accepted: `target.fmt == VCR_RT_16`,
  `zb`, and `surf_zbits(zb) == 32`.
- The `SETRENDERTARGET` case (`:1725-1751`), with a per-context `z16in32_logged` flag so it fires once.
- The message is under 95 characters (`VCR_LOG_MSG_LEN` 96).
- Document it in `KMD/include/vcr_events.h:75`.

**Why:**
- Today's 513/1 shows the Z offset but not its pitch or depth. At LogLevel 2 the DEBUG CreateSurfaceEx lines that
  would reveal the 32-bit Z are gone.
- With this line, R6's ring proves which path ran, and so does any future sweep, G10's promoted-Z cases and
  G20's boot C. That is the project's "make it visible" rule.

**Old path:** byte-identical register traffic. The only new cost is one log IOCTL per context, which is
negligible (G52).

**Optional, not required:** Phase 1 can deduce the path from 513/1 plus `Sherman.log`.

## 8. The lab test: `z16in32` (in G75's DX5/DX6 probe; D3D8 cannot reach this pair)

**Why not d3dprobe:**
- The D3D8 runtime refuses R5G6B5 + D24X8/D24S8 itself (`caps_124.txt` zmatch 0; 8876086a before the driver,
  `PLAN:172-174`).
- So no D3D8 test can create R6's pair. d3dprobe's `caps` keeps pinning that refusal: zmatch R5G6B5/D24X8 = 0.
- If that ever becomes 1 (for example a DX8 DDI with ZSTENCIL_WITH_ARBITRARY_COLOR_DEPTH, G94),
  `d3dprobe render --full --bpp 16 --zfmt d24x8` then runs the whole 40-test matrix on 16-over-32 and must pass.

**The probe:**
- It is the legacy-interface probe G75 adds. `designs/G09.md` calls it `tools/d3d7probe.c`, and
  `designs/G08.md` §6.3 its DX5/DX6 mode.
- The mingw toolchain has `IDirect3D2`/`IDirect3DDevice2` (`/usr/i686-w64-mingw32/include/d3d.h:34-78`) and
  `libddraw.a`/`libdxguid.a`.
- This test uses R6's own interfaces, so it goes through `d3dim.dll` exactly as R6 does.

**Setup, R6's path step for step:**

1. **At the 32 bpp desktop:** `DirectDrawCreate`, then QI `IDirectDraw2` and `IDirect3D2`.
   - Call `EnumDevices`. The HAL description's `dwDeviceZBufferBitDepth` is recorded: expected 0x500
     (DDBD_16|DDBD_32) with D3D32 and 0x400 without.
   - Take the deepest, as D3DApp does.
2. **The mode:** `SetCooperativeLevel(EXCLUSIVE|FULLSCREEN)`, then `SetDisplayMode(640,480,16)`, paced through
   `vcr_pace.h` (one switch).
3. **The surfaces:**
   - a primary flip chain with one back buffer (`COMPLEX|FLIP|3DDEVICE`);
   - the Z through `DDSD_ZBUFFERBITDEPTH` = the chosen depth, `DDSCAPS_ZBUFFER|VIDEOMEMORY`,
     `AddAttachedSurface` to the back buffer;
   - `GetSurfaceDesc(Z)`: the pitch is recorded, expected 2560 at 32 and 1280 at 16.
4. **The device:** `CreateDevice(IID_IDirect3DHALDevice, backbuffer)`, then a viewport of 640x480 set current.
5. **State:** `DITHERENABLE` FALSE, `ZENABLE` TRUE, `ZWRITEENABLE` TRUE, `ZFUNC` LESSEQUAL, `TEXTUREHANDLE` 0,
   `CULLMODE` NONE.
6. **Each test:** `IDirect3DViewport2::Clear(TARGET|ZBUFFER)` (background black), `BeginScene`, `DrawPrimitive(D3DPT_TRIANGLELIST, D3DVT_TLVERTEX)`,
   `EndScene`, `Lock(back buffer, READONLY|WAIT)`, compare, `Unlock`, `Flip(WAIT)`.
   - **Consecutive tests therefore draw into alternate buffers, after a re-target.** That catches a Z
     dropped at SETRENDERTARGET.

**Tests:**

| test | scene | pass (565, exact: dither off) | old-buggy reference |
|---|---|---|---|
| `zclear_far` | after the clear, a full-screen red quad at sz 0.999 (65469 of 65535) | **every pixel of row 240 (640 px) and of column 320 (480 px) = 0xF800**: the clear left 0xFFFF in every 16-bit slot | pre-be58b7d (b63ea6a5/13256e46, D3D32=1): CreateDevice refused, ring 513/12 → the test FAILS with `device: refused`. A 32-bit-word clear: the odd columns read 0x0000 |
| `zorder_nearfirst` | green quad z 0.25 at (100..300, 100..300), then red z 0.75 at (200..400, 200..400) | (250,250) = 0x07E0 green; (350,350) = 0xF800; (150,150) = 0x07E0; (450,450) = 0x0000 | refused, as above |
| `zorder_farfirst` | the same quads in the other order (red first) | (250,250) = 0x07E0 | refused; with no depth test: 0x07E0 here but 0xF800 in `nearfirst`, hence both orders |
| `zcolumns` | a quad at z 0.5 over x 0..639, then a red quad at z 0.75 over it | all 640 pixels of row 100 = the z-0.5 quad's colour | a 32-bit-word clear or a 24-bit fill leaves alternate columns red or black |
| `zprecision` (record only) | quads at z 0.50000 and 0.500005 (< 1/65535 apart), far first, ZFUNC LESS | reported: equal at 16 bits means the second fails, so the first colour stays | documents the depth precision: 16-bit, as a 16 bpp target always had |
| `zlayout` (record only) | Lock the Z (READONLY) after `zclear_far` | reported: bytes 0..1279 of row 0 hold 0xFFBD x 640; bytes 1280..2559 are whatever the heap held | documents what an application that locked R6's Z would see (`vcr_rtfmt.h:76-78`) |

**RESULT:** JSON with `zbits_chosen`, `z_pitch`, `device` (`ok|refused`), the pass/fail per test and the record-only
values. The runner must pace (`--pace 5000`, as `EV/d3dplan_1112/onbox/d3dprobe_paced.py` does).

**Controls:**
- **D3D32 off:** `zbits_chosen` 16, pitch 1280, every test passes. That is the plain 16/16 lane, and it shows the
  test does not depend on 16-over-32 to pass.
- **86Box Voodoo3 bed:** no D3D32 there (Banshee/Voodoo3 refuse 32-bit Z, `Dd_CanCreateSurface`,

**Never in a default list:** run it explicitly (`--tests z16in32`) in the boots that touch Z or targets: G10,

## 11. Risk to proven paths

- **Default 16 bpp path, Glide/OpenGL coexistence, SLI state, flip path: none from the code.** Only a host test
  and an optional log line.
- **Session risks, and how each is handled:**
  - **CRT mode switches.** R6 makes two per session; session B adds one at the action phase. A refused device
    would add R6's 640x480x16 retry plus the runtime's revert. Phase 0's `z16in32` comes first, and a failing
    device stops the session before R6 is launched.
  - **G01.** A Glide/OpenGL session earlier in the boot erases every triangle, and that would read as a
    16-over-32 failure. Hence the cold, Glide-free boot. The sweep runs after R6, and with no Glide title.
  - **G43.** Session B's in-game resolution change re-creates the device across a mode change. That is normal R6
    behaviour, but the PDEV-lifetime hazard is unproven, so it is attended and last.
  - **A freeze (G04-class):** attended; a by-pid kill; the ring read after.
  - **ESC during the intro quits R6:** wait for the intro to finish.
  - **Synthetic input:** R6 reads window messages and `GetCursorPos` (no DirectInput in its imports), so `UIKEY`
    and `UICLICK` should reach the shell (inferred; step 1 confirms with F2 and a menu click). The mouse look
    re-centres with `SetCursorPos`, so the action phase is driven with keys only.
- **Evidence risk:**
  - R6's software fallback would produce correct-looking frames that are not ours. Check P guards against it.
  - GDI frames can be the back buffer (G79). The F2 shots are the reference, and GDI is kept only for timing and
    the agent's view.
