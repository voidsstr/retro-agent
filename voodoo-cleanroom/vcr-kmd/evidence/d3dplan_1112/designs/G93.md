## 0. Verdict

1. **The hardware half of the gap is right.** renderMode[1:0] = 1 renders ARGB1555 (SPEC L3291, L3304); renderMode[16:15]
   picks the stored alpha bit: 0 = force 0, 1 = force 1, 2 = the MSB of the alpha after alpha blending (L3294, L3308).
   At 15 bpp the 1-bit destination alpha is automatic, shares fbzMode[9] (the RGB write enable) and FASTFILL with the
   colour planes, and fbzMode[18] must stay clear (§21.5, L6229-6232; L3256). The aux buffer is the 16-bit depth
   buffer, exactly as at 16 bpp (L3258, L3513). Single pass, one register value.

2. **The plan's wording hides a correctness hole that exists today.** `vcr_rt_format` "accepts only 565 and 8888" is not
   quite what happens: `target_of` classifies a target by its **bit count only** (`surf_bpp`, `KMD/display/vcrdd_d3d.c:172-177,
   1055-1057`). Every 16-bit target, A1R5G5B5, X1R5G5B5 and A4R4G4B4 included, becomes `VCR_RT_16` and is drawn with
   renderMode `0x001e0000` (565). A grey clear `0x808080` lands as the word `0x8410`, which a 1555 reader decodes as
   alpha 1, colour (8, 0, 132). Nothing refuses it and nothing logs it. 3dfx's Win9x HAL had the same bug
   (`V9X/D3GLOBAL.H:816-858`: `case 15` on a bit count that is never 15); 3dfx's NT HAL fixed the 1555 half by testing the
   red mask (`VH5/D3GLOBAL.H:806-888`) but still drew 4444 as 565 and never set renderMode[16:15], so every 1555 target it
   drew stored alpha 0.

3. **Nobody on `.124` is known to reach a 1555 target, and Direct3D 8/9 titles never can through this DDI.**
   - The XP SP3 d3d8/d3d9 runtimes decide render-target formats for a DX7-DDI driver from a PCI-id table. The VSA-100's
     entry, `121a:0009`, is `0x00004580` in both DLLs (re-read here: d3d8.dll file offset `0xc40`, d3d9.dll `0x1410`). The
     per-format test (d3d8 VA `0x6d9af2e7`-`0x6d9af319`) grants an A1R5G5B5 render target only with flag `0x800` and an
     X1R5G5B5 one only with `0x2000`; neither is set, and the registry override can only switch flags **off**
     (`RPT/runtime.md` §4.3). No driver change can alter that short of a DX8-level DDI (G94).
   - No display mode is 15 bpp: the miniport builds 8/16/32 bpp modes only, and 16 bpp is 565
     (`KMD/common/vcr_modes.c:162-166`, `KMD/miniport/vcrmp.c:358-372`). So no back buffer is ever X1R5G5B5.
   - What remains is a DirectX 3-7 title rendering into a surface it created itself in a 555 format (a render-target
     texture, or an off-screen `DDSCAPS_3DDEVICE` surface). `Dd_CanCreateSurface` accepts any such surface
     (`KMD/display/vcrdd_ddraw.c:610-631`), and the DX7 texture list offers A1R5G5B5 and A4R4G4B4
     (`vcrdd_d3d.c:2081-2084`).
   - A case-insensitive string scan of the staged DX5-7 binaries on `.124` (`avp.exe`, `JK.EXE`, `JKM.EXE`,
     `RainbowSix.exe`, Shogo `d3d.ren`, `THIEF.EXE`, `carma2.exe`, Descent 3 `main.exe`, the `D3DDrv.dll` of Deus Ex, Unreal
     Gold and UT 436, `Turok2English.exe`) finds no render-target string at all. That is weak evidence (a call needs no
     string), so the design adds a once-per-surface record that answers it on the box.

4. **Design.** One `Diag\D3DFeat` bit, **`RT15`**, default OFF:
   - targets are classified by pixel **layout**, not bit count (`vcr_rt_layout16`, Win32-free, in `vcr_rtfmt.h`);
   - armed, A1R5G5B5 draws with renderMode `0x001f0001` (15 bpp, alpha = MSB), X1R5G5B5 with `0x001e8001` (15 bpp,
     alpha forced to 1), and a 16-bit layout the 3D engine cannot write (4444, 8332, BGR, luminance...) is refused with
     `DDERR_INVALIDPIXELFORMAT`, the HAL's existing "refused, not drawn wrong" rule;
   - a 15 bpp colour clear stores the clear colour's alpha MSB through zaColor[31];
   - no caps change (DX7 `DDBD_16` already covers 555 surfaces; D3D8/9 cannot be changed);
   - off, every register write and every decision is today's, byte for byte; the only always-on change is a once-per
     (context, surface) log record when a 16-bit target is not 565, which the proven path never produces.

5. **Tests.** Native and python host tests (old and fixed values side by side); a hosted DX7 lab set in G75's
   `d3d7probe` (D3D8 cannot create the target, so d3dprobe cannot draw this test); a D3D8 `caps` row that pins the
   runtime's refusal so nobody expects a D3D8/9 title to benefit.

6. **Priority P3, effort M.** No staged title needs it. It becomes worth more only if the on-box record finds a title
   rendering into a non-565 16-bit target, or if G94 ever exposes 1555 render-target ops (which would need this to be
   honest).

## 1. What the VSA-100 does at 15 bpp (hw-35, re-read)

| fact | source |
|---|---|
| renderMode[1:0]: 0 = 16 bpp (565), **1 = 15 bpp (1555)**, 2 = 32 bpp | SPEC L3291, L3304; `VINC/H3DEFS.H:129` `SST_RM_15BPP`; `G5/incsrc/h3defs.h:120` |
| renderMode[16:15]: 0 force 0, 1 force 1, 2 the alpha MSB *after alpha-channel blending*; used only at 15 bpp | SPEC L3294, L3308; `VINC/H3DEFS.H:134-138`; `G5/incsrc/h3defs.h:125-129` |
| renderMode[20:17] (per-channel masks) are used only at 32 bpp | SPEC L3295-3298 |
| 15 bpp: 1-bit destination alpha is automatic, fbzMode[18] must be clear | SPEC §21.5 L6230 |
| 15 bpp: the alpha bit is written whenever RGB is (fbzMode[9]); no separate mask | SPEC L6231, L3256 |
| 15 bpp: fbzMode[10] enables the **depth** buffer, as at 16 bpp | SPEC L3258 |
| FASTFILL at 15 bpp: RGB from color1[23:0] (dither by fbzMode[8] on SDRAM), alpha bit = zaColor[31] if [16:15] = 2, else the forced value; Z from zaColor[15:0] | SPEC L2694-2701, L4049-4055, L3513 |
| 15/16 bpp alpha-channel blend factors: ZERO and ONE only | SPEC L2974-2983; rev history L6549 |
| 2 pixels per clock is allowed at 15/16 bpp | SPEC L6238 |
| 2D engine: commandExtra[28] "preserve 1-bit alpha" must stay **clear** for blits to overwrite whole 1555 pixels | SPEC L1553-1562 (we never set it) |

**Nobody ever drove renderMode[16:15] != 0.** Our h5 Glide renders `GR_PIXFMT_ARGB_1555` with `SST_RM_15BPP` and leaves
[16:15] at its shadow's 0 (`G5/glide3/src/gsst.c:4166-4223`); 3dfx's NT and Win9x D3D HALs OR in `SST_RM_EN15BPP_RGBA`
only (`VH5/D3GLOBAL.H:831-888`, `V9X/D3GLOBAL.H:816-858`); a case-insensitive search of `VH5` and `H5/Win9x` for
`SST_RM_ALPHA_ONE`/`SST_RM_ALPHA_MSB` finds the definitions and nothing else. **The MSB mode is a documented but
never-exercised silicon path**: the lab test checks all three values (§6).

## 2. What happens today (read 2026-11-12)

### 2.1 The decision

- `target_of` (`vcrdd_d3d.c:1047-1085`): `rtb = surf_bpp(c->pd, c->rt)` (the surface's `dwRGBBitCount`, or the desktop's
  depth when it carries no format, `:166-177`), then `fmt = vcr_rt_format(c->pd->rt32, rtb, zb)`.
- `vcr_rt_format` (`KMD/include/vcr_rtfmt.h:79-87`) looks at sizes only: 16 → `VCR_RT_16`, 32 → `VCR_RT_32` (with
  `rt32`), anything else refused. **No mask is read anywhere on the target path.**
- `vcr_rt_rendermode` (`vcr_rtfmt.h:174-177`) → `RM_16BPP | RM_RGBA_WRITE` = `0x001e0000` for every non-32 format.
- `vcr_3d_target_seq` (`KMD/include/vcr_3dseq.h:56-77`) writes it, then colBufferAddr/Stride, auxBufferAddr/Stride and the
  clip (7 writes on a VSA-100). `VcrDd3dClear` (`KMD/display/vcrdd_3d.c:136-175`) writes `zaColor = zv` (depth only,
  bit 31 always 0).
- The same `target_of` runs at ContextCreate (`:1189`), DP2 `SETRENDERTARGET` (`:1737`), the start of every DP2 (`:1852`) and
  Clear2 (`:1884`), so all four agree.

### 2.2 The old path's pixels (what the probe will pin as "old")

| target layout | D3D colour | correct 16-bit word | what today's HAL stores (565) | that word read as the target's format |
|---|---|---|---|---|
| A1R5G5B5 | `0x80808080` (grey, A ≥ 0x80) | `0xc210` | `0x8410` | A1, (0x08, 0x00, 0x84) |
| A1R5G5B5 | `0x7f00ff00` (green, A < 0x80) | `0x03e0` | `0x07e0` | A0, (0x08, 0xff, 0x00) |
| X1R5G5B5 | `0x00808080` | `0xc210` (X forced 1) | `0x8410` | (0x08, 0x00, 0x84) |
| A4R4G4B4 | `0xffff0000` | `0xff00` | `0xf800` | A15, (0x88, 0x00, 0x00) |
| R5G6B5 (control) | `0x808080` | `0x8410` | `0x8410` | unchanged |

The 565 control is the whole proven lane; it stays identical in every mode of this design.

## 4. The design

### 4.1 Classify a target by layout (`KMD/include/vcr_rtfmt.h`, Win32-free)

```c
/* DDPIXELFORMAT.dwFlags bits, by value (ddraw.h) - this header stays Win32-free */
#define VCR_DDPF_ALPHAPIXELS    0x00000001u
#define VCR_DDPF_NOT_RGB        (0x00000002u /* ALPHA */ | 0x00000004u /* FOURCC */ | \
                                 0x00000008u /* PAL4 */  | 0x00000020u /* PAL8 */   | \
                                 0x00000400u /* ZBUFFER */ | 0x00020000u /* LUMINANCE */ | \
                                 0x00080000u /* BUMPDUDV */)

#define VCR_RT_L565     0u      /* R5G6B5 - or no masks at all: the desktop's own 16 bpp format, 565 here */
#define VCR_RT_L1555    1u      /* A1R5G5B5: 7c00/03e0/001f, alpha 8000 */
#define VCR_RT_LX555    2u      /* X1R5G5B5: 7c00/03e0/001f, no alpha */
#define VCR_RT_LOTHER   3u      /* any other 16-bit layout: 4444, 8332, BGR, luminance, bump, FOURCC */

static __inline unsigned vcr_rt_layout16(unsigned flags, unsigned r, unsigned g, unsigned b, unsigned a)
{
    if (!r && !g && !b && !(flags & VCR_DDPF_NOT_RGB))
        return VCR_RT_L565;                     /* nothing positive to go on: as today */
    if (flags & VCR_DDPF_NOT_RGB)
        return VCR_RT_LOTHER;
    if (r == 0xf800u && g == 0x07e0u && b == 0x001fu)
        return VCR_RT_L565;
    if (r == 0x7c00u && g == 0x03e0u && b == 0x001fu) {
        if (!(flags & VCR_DDPF_ALPHAPIXELS) || !a)
            return VCR_RT_LX555;
        return a == 0x8000u ? VCR_RT_L1555 : VCR_RT_LOTHER;
    }
    return VCR_RT_LOTHER;
}
```

**Refuse only on positive evidence**, the project's gate rule: a 16-bit surface with no masks keeps today's answer (565),
and 565 is recognised by its masks whatever stray flag bits it carries. So a proven 565 target cannot be misread as
"other" when the bit is armed.

### 4.2 The decision, with `vcr_rt_format` untouched

```c
#define VCR_RT_15       15u     /* the 3D engine's 1555 mode (renderMode[1:0] = 1); VSA-100 with RT15 only */

/* renderMode[16:15] (h3defs.h SST_RM_ALPHA_ZERO/ONE/MSB) */
#define VCR_RT_A1_ZERO  0u
#define VCR_RT_A1_ONE   1u
#define VCR_RT_A1_MSB   2u

/* fmt: vcr_rt_format's answer for the SIZES (the Z pairing is decided there, for 15 exactly as for 16).
 * rt15 = napalm AND Diag\D3DFeat RT15. Off, the answer is fmt itself - today's decision for every input. */
static __inline unsigned vcr_rt_format_layout(unsigned fmt, unsigned rt15, unsigned lay)
{
    if (!rt15 || fmt != VCR_RT_16 || lay == VCR_RT_L565)
        return fmt;
    return (lay == VCR_RT_L1555 || lay == VCR_RT_LX555) ? VCR_RT_15 : VCR_RT_REFUSED;
}

static __inline unsigned vcr_rt_a1mode(unsigned lay)
{
    return lay == VCR_RT_L1555 ? VCR_RT_A1_MSB : lay == VCR_RT_LX555 ? VCR_RT_A1_ONE : VCR_RT_A1_ZERO;
}
```

- A1R5G5B5 → **MSB**: the rendered alpha survives, which is what makes a 1555 render-target texture usable with an alpha
  test or alpha blend later.
- X1R5G5B5 → **ONE**: D3D treats a target without alpha as alpha 1.0 for DESTALPHA, and our texture path samples any
  `0x7c00` surface as ARGB1555 (`vcrdd_d3d.c:316-318, 764-769`), so a forced 1 also keeps an X1R5G5B5 render target
  opaque when it is later used as a texture. 3dfx forced 0 for both (§2.3).
- The existing helpers already treat any format but 32 as 2 bytes a pixel with a 16-bit aux buffer, so `vcr_rt_rtcheck`,
  `vcr_rt_zcheck`, `vcr_rt_zmax` (`0xffff`) and `VcrDd3dDrawTarget`'s `z_scale` (65535) are right for `VCR_RT_15` as they
  stand. The 16/16-in-a-32-bit-Z rule (Rainbow Six's case, `vcr_rtfmt.h:70-83`) carries over unchanged, because the size
  decision is still `vcr_rt_format`'s.

### 4.3 Register programming (`vcr_3dregs.h`, `vcr_3dseq.h`, `vcrdd_3d.c`)

New constants in `vcr_3dregs.h`, from the GPL header (`G5/incsrc/h3defs.h:120, 125-129`):

```c
#define RM_15BPP                1u
#define RM_A1(m)                ((unsigned)(m) << 15)   /* renderMode[16:15], 15 bpp only */
```

A separate sequence, so `vcr_3d_target_seq` (the proven 16 bpp writes, pinned write for write by
`tests/native/test_vcr_kmd_d3dseq.c`) is not edited at all:

```c
static __inline unsigned vcr_rt_rendermode15(unsigned a1)
{   return RM_15BPP | RM_A1(a1 & 3u) | RM_RGBA_WRITE;  }  /* [20:17] are ignored at 15 bpp; 3dfx and Glide set them too */

static __inline unsigned vcr_3d_target_seq15(unsigned napalm, unsigned rt15, unsigned a1,
                                             unsigned rt_off, unsigned rt_pitch, unsigned z_off,
                                             unsigned z_pitch, unsigned width, unsigned height, vcr_regw *w)
{
    unsigned n = 0;
    if (!napalm || !rt15 || a1 > VCR_RT_A1_MSB)
        return 0;                                   /* a Banshee/Voodoo3 has no renderMode: never 15 */
    w[n].off = V3D_RENDERMODE;      w[n++].val = vcr_rt_rendermode15(a1);
    w[n].off = V3D_STENCILMODE;     w[n++].val = 0;  /* a new lane: no stale Glide stencil can touch it */
    w[n].off = V3D_STENCILOP;       w[n++].val = 0;
    w[n].off = V3D_COLBUFFERADDR;   w[n++].val = rt_off;
    w[n].off = V3D_COLBUFFERSTRIDE; w[n++].val = BS_LINEAR_STRIDE(rt_pitch);
    w[n].off = V3D_AUXBUFFERADDR;   w[n++].val = z_off;
    w[n].off = V3D_AUXBUFFERSTRIDE; w[n++].val = BS_LINEAR_STRIDE(z_pitch ? z_pitch : rt_pitch);
    w[n].off = V3D_CLIPLEFTRIGHT;   w[n++].val = width & 0xfff;
    w[n].off = V3D_CLIPBOTTOMTOP;   w[n++].val = height & 0xfff;
    return n;                                       /* 9 = VCR_3D_TARGET_MAX */
}
```

- Values: A1R5G5B5 `renderMode = 0x001f0001`, X1R5G5B5 `0x001e8001`. Today both get `0x001e0000`.
- The stencil pair: the "16 bpp ignores stencilMode" premise is unproven (`vcr_3dseq.h:34-50`). A new lane does not need to
  inherit it, and two zero writes per target setup cost nothing. 16 bpp keeps its proven seven writes.
- `vcr3d_target` (`KMD/display/vcrdd_3d.h:27-35`) gains `ULONG a1;`. `VcrDd3dTarget` (`vcrdd_3d.c:45-69`) calls
  `vcr_3d_target_seq15(pd->napalm, pd->rt15, t->a1, ...)` when `t->fmt == VCR_RT_15`, else the existing call, unchanged.
  `VcrDdRoom(pd, n > 7 ? n : 7)` already covers 9.

### 4.4 Clears

`VcrDd3dClear` writes `zaColor = vcr_rt_fill_za(t->fmt, t->a1, zv, argb)`:

```c
/* the FASTFILL's stored alpha bit at 15 bpp is zaColor[31] when [16:15] = 2 (SPEC L2696-2699); every other
 * format keeps zaColor = the depth value, as today */
static __inline unsigned vcr_rt_fill_za(unsigned fmt, unsigned a1, unsigned zv, unsigned argb)
{   return fmt == VCR_RT_15 && a1 == VCR_RT_A1_MSB ? (zv | (argb & 0x80000000u)) : zv;  }
```

- Clearing an A1R5G5B5 target to `0x80808080` with Z 1.0 writes zaColor `0x8000ffff`; today `0x0000ffff`.
- X1R5G5B5 needs nothing: [16:15] = 1 forces the bit in the fill.
- The clear's fbzMode carries no dither bit (`vcrdd_3d.c:140-160`), so the RGB is truncated to 5:5:5: exact words.
- zaColor is rewritten by the next state flush anyway, so G22's z-bias (zaColor[15:0] at 15/16 bpp) is unaffected.

### 4.5 Wiring in the HAL (`vcrdd_d3d.c`) and the always-on record

`target_of`:

```c
rtb = surf_bpp(c->pd, c->rt);
zb = c->zb ? surf_zbits(c->zb) : 0;
fmt = vcr_rt_format(c->pd->rt32, rtb, zb);                 /* unchanged line (pinned by test_vcr_kmd_d3d.py) */
lay = rtb == 16 ? rt_layout(c->pd, c->rt) : VCR_RT_L565;   /* four compares; masks from ddpfSurface */
fmt = vcr_rt_format_layout(fmt, c->pd->rt15, lay);        /* rt15 off: fmt unchanged */
if (lay != VCR_RT_L565)
    note_layout(c, lay, fmt);                              /* once per (context, surface) */
if (fmt == VCR_RT_REFUSED) {
    c->target_why = lay != VCR_RT_L565 && c->pd->rt15 ? VCR_RT_WHY_LAYOUT : VCR_RT_WHY_FORMAT;
    ...                                                    /* as today */
}
...
t->fmt = fmt;
t->a1 = fmt == VCR_RT_15 ? vcr_rt_a1mode(lay) : 0;
```

- `rt_layout` reads `c->rt->lpGbl->ddpfSurface` when `has_pixfmt` (`:166-170`), else returns `VCR_RT_L565` (a 16-bit
  surface with no format of its own is the 16 bpp desktop's, 565 on this driver).
- **`note_layout`** logs one event 513 record per (context, surface): `b` = layout (1 A1R5G5B5, 2 X1R5G5B5, 3 other),
  `c` = `R mask | (A mask << 16)`, `d` = outcome (0 "drawn as 565 - Diag\D3DFeat RT15 off", 1 "drawn 1555", 2 "refused").
  A new `what` code (the integrator assigns it; sibling designs have proposed 24-46), appended to `VCR_EV_DD_D3D`'s text
  in `include/vcr_events.h`, and to `tools/vcrlog.py` if it decodes per code. The per-context field
  `PDD_SURFACE_LOCAL layout_noted` stops the per-DP2 repeat. **A 565 or 32 bpp target never reaches `note_layout`**, so
  the proven lane's log stream is unchanged. This record is the investigation: it answers "does any staged title render
  into a non-565 16-bit target?" on every later sweep, armed or not.
- `target_refused` gains the `VCR_RT_WHY_LAYOUT` text: "%s refused: a 16 bpp target laid out R %x G %x B %x A %x (the 3D
  engine writes 565, 1555 or 8888)".
- ContextCreate's INFO line already prints `target.fmt` as "%u bpp 3D", so an armed 1555 context reads "15 bpp 3D".
- `VCR_PDEV` (`KMD/display/vcrdd.h:68-75`) gains `ULONG rt15;`. `VcrDd2dInit` (`vcrdd_2d.c:443-470`) sets
  `pd->rt15 = pd->napalm && (info.d3dfeat & VCR_D3DFEAT_RT15)` beside `rt32`.

### 4.6 Caps: no change, on purpose

- **DX7 DDI:** `dwDeviceRenderBitDepth = DDBD_16 | (rt32 ? DDBD_32 : 0)` (`vcrdd_d3d.c:2079`). `DDBD_16` is the depth of every
  555 surface; there is no "15" flag. Nothing to add.
- **DirectDraw:** `ddCaps.ddsCaps` already carries `DDSCAPS_3DDEVICE | DDSCAPS_TEXTURE`; `Dd_CanCreateSurface` is not changed.
  (3dfx refused off-screen 555 surfaces and render-target textures in 4444; refusing at CreateSurface would also catch
  surfaces that carry `3DDEVICE` but are never drawn to. ContextCreate/SETRENDERTARGET is where it matters, and that is
  where `vcr_rt_rtcheck` already refuses.)
- **D3D8/D3D9:** unchangeable through this DDI (§3). G75's DX7 caps golden and `d3dprobe caps` must be byte-identical with
  RT15 armed and off; the bit is declared "not caps-relevant" in `include/vcr_d3dfeat.h` so G75's golden lookup ignores it.

### 4.7 Precision and semantics (single pass)

- Colour: 8 → 5 bits by truncation without dither, ordered dither with DITHERENABLE (allowed at 15 bpp; G30's 32 bpp rule
  does not apply).
- Alpha (A1R5G5B5): one bit, the MSB of the alpha the colour path produces, after alpha-channel blending. Our alpha
  factors are ONE/ZERO whenever blending is on (`vcrdd_d3d.c:991-999`), and 15 bpp only allows ZERO/ONE anyway
  (SPEC L2974), so the stored bit is `As >= 0x80`. D3D's own formula (`As*Fs + Ad*Fd` per channel) can differ when an
  app blends into the alpha with SRCALPHA/INVSRCALPHA (e.g. As = 0.6 over Ad = 0 gives 0.36, bit 0; we store 1). That is
  a 1-bit format's limit, not a bug to chase.
- DESTALPHA / INVDESTALPHA as RGB factors read the real stored bit at 15 bpp (SPEC L6230), 0x00 or 0xff. Today's
  `blend_src`/`blend_dst` already map them (`:636-637, 659-660`); whether they are advertised is G28's call.

### 4.8 Interactions

- **G28 (destination alpha):** its `rt_alpha` needs the 1-bit case this design creates (DSN/G28.md §3.8): DESTALPHA
  readable, alpha-channel factors ZERO/ONE only at 15 bpp.
- **G50 (2 ppc):** counts 15 bpp as EN16 (DSN/G50.md "G93 (1555 targets): 15 bpp counts as EN16"; SPEC L6238).
- **G35 (stencil):** 32 bpp only. A 15 bpp target over a D24S8 Z (16/16-in-32) has no stencil, like 16.
- **G22 (z-bias), G23 (W-buffer):** 16-bit depth formats, same as 16 bpp.
- **G30 (dither at 32 bpp):** no effect on 15.
- **G36 / G21 / G37 (render to texture):** a 1555 *render-target texture* that is later sampled needs G21's 16-byte
  placement (`D3DTexPlace`; DirectDraw's heap can put a `3DDEVICE` texture on a 4-byte boundary and colBufferAddr /
  texBaseAddr drop bits 3:0, `vcrdd_d3d.c:381-391`, DSN/G36.md §1) and G37's TMU flush after the 3D engine writes a
  texture. The 1555 drawing itself does not.
- **G94 (DX8 DDI):** the only route to D3D8/9 titles. It would publish `OP_OFFSCREEN_RENDERTARGET` on A1R5G5B5/X1R5G5B5
  only if this item draws them right.
- **G34 (X texture formats):** samples X1R5G5B5 with alpha forced to 1; this design's forced-1 X target agrees with it.
- **G51 (SLI):** a render target must be drawn with SLI off for that target (`RPT/hw.md` Q12); same as 16 bpp.
- **Glide/OpenGL:** both sides write renderMode whole (Glide's `_grRenderMode` from its own shadow,
  `G5/glide3/src/gsst.c:4175-4223`), so a 15 bpp D3D target cannot leak into a Glide session or the reverse.
- **2D engine:** DirectDraw Blt / COLORFILL into a 555 surface move raw pixels; commandExtra[28] stays clear (§1).

### 4.9 What this item does not do

- No 15 bpp display mode (no back buffer X1R5G5B5): that would need 555 entries in the mode list, GDI at 555, the
  video processor's RGB1555 desktop format (SPEC L4254-4261) and 2D-engine format work, for no known consumer.
- No 555 conversion of a 555 off-screen surface blitted to the 565 primary: DirectDraw does not convert pixel formats in
  Blt, and an app that relies on it is wrong on any driver.

## 5. Gating

- **`Diag\D3DFeat` bit `RT15`**, default OFF, a positive bit in the shared feature word (DSN/G05.md §4.2: the miniport
  reads `Diag\D3DFeat` at boot into an appended `vcr_info.d3dfeat`; bits are allocated in `include/vcr_d3dfeat.h`; the
  ABI test pins the appended field). Proposed bit 16 (`0x10000`), above the 0-15 that earlier designs claim; the
  integrator assigns the number. If this item lands before any other D3DFeat item, it lands the plumbing by that recipe.
- Read at boot (one mechanism for the whole word), VSA-100 only (`pd->napalm`), never on a Banshee/Voodoo3.
- **Off:** `vcr_rt_format_layout` returns its input, `vcr_3d_target_seq15` is unreachable, `vcr_rt_fill_za` returns `zv`
  for 16/32 bpp: every register write and every ContextCreate answer is today's. The always-on part is the
  once-per-surface log record for non-565 16-bit targets, which no proven run produces (no register write, no extra event
  on a 565/8888 target).
- **On:** 565 and 8888 targets unchanged; A1R5G5B5/X1R5G5B5 drawn 1555; other 16-bit layouts refused at ContextCreate
  (`DDERR_INVALIDPIXELFORMAT`) and at SETRENDERTARGET ("not drawn"). The refusal is the only behaviour an application
  could notice, and only for targets that are drawn wrong today.
- **Not safe to land default-on.** The MSB mode has never run on any VSA-100 software, and the refusal changes an answer
  an application gets. Arm it alone in one supervised clean boot (§8). **Graduation** (absent = on) after: the lab set
  passes on silicon, and the record (§4.5) has run through one sweep of the DX5-7 titles. If the record shows a title
  creating a 4444 (or other) target, graduate the 1555 half first and decide the refusal with that title in front of you.

## 11. Effort, priority, dependencies, games

- **Effort M**: the driver change is small (about 120 lines with comments), the host tests about 200, the seven probe
  scenes about 250 in G75's frame, plus two supervised boots.
- **Priority P3**: no staged title needs it, D3D8/9 titles cannot reach it, and the latent misrender affects only
  targets nobody is known to create. It rises to P2 if the record (§4.5) finds a title drawing into an A1R5G5B5/X1R5G5B5
  target (that title then misrenders today), and is a prerequisite only for G94.
- **Depends on**: **G75** (the DX7 lab frame; the only way to drive the target in a lab); **G21/G36** (16-byte placement of
  render-target textures) and **G37** (TMU flush after rendering into a texture) for the `d7_rt1555_rtt` sampling half
  only. The `Diag\D3DFeat` plumbing is shared (DSN/G05.md §4.2): whoever lands first builds it.
- **Games unblocked**: none known on `.124`.

## 12. Open questions

1. Does any staged DX5-7 title, or a dormant D3D renderer of a Glide/OpenGL title, create a non-565 16-bit render target?
   The static scan says probably not; the §4.5 record answers it on the next sweep.
2. Does renderMode[16:15] = 2 store the alpha MSB on silicon? No 3dfx software ever set it. If it does not, ship
   X1R5G5B5 (forced 1) and refuse A1R5G5B5 rather than store a wrong bit.
3. With alpha blending off (alphaMode[4] = 0), is the stored MSB the colour path's alpha, as SPEC L3308 reads? `d7_rt1555`
   quads A-D answer it.
4. Does d3dim700 hand a 555 `3DDEVICE` surface to ContextCreate (inferred: it checks the bit depth only), and does dxg
   accept a 16-bit 3D off-screen surface on the 32 bpp desktop (G75's `offscreen16`)?
5. Should an armed driver also refuse a 4444/other `TEXTURE | 3DDEVICE` surface at `Dd_CanCreateSurface`, as 3dfx did, so an
   application learns it at creation? Not in this item: it would also refuse surfaces that are never drawn to.
6. X1R5G5B5's stored bit: forced 1 (chosen: D3D's alpha-1.0 rule for alpha-less targets, opaque when sampled) or MSB
   (keeps whatever alpha the pixel had)? Revisit only if a title is found that reads it.
7. Does the D3D8 caps row really read 0 for A1R5G5B5/X1R5G5B5 render targets on `.124`'s own d3d8.dll (only the fleet image's
   copy was read)? `d3dprobe caps` answers it.
