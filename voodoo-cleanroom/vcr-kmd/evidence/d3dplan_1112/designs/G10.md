## 0. Summary

- **The failure (measured).**
  - The D3D8 runtime on `.124` reports `CheckDepthStencilMatch(X8R8G8B8, D16)` = match (`caps_124.txt`).
  - `ContextCreate` then refuses the pair, because `vcr_rt_format(rt32, 32, 16)` is `VCR_RT_REFUSED` (`KMD/include/vcr_rtfmt.h:84-85`).
  - `CreateDevice` returns `8876086c` (D3DERR_INVALIDCALL).
  - While cleaning up, the runtime makes two CRT mode switches 156 ms apart (`ONBOX/d3dprobe_render_640x480x32_d16.txt`; `ONBOX/ring_after_probe_i_decoded.txt` seq 24713).
- **New evidence: one staged title fails this way for certain.**
  - `rf.exe` (Red Faction) hard-codes `AutoDepthStencilFormat = D3DFMT_D16` for PCI vendor 0x121a at every colour depth (section 2).
  - Red Faction's launcher stages a bit depth of 32 (`LIB/RedFaction/Play Red Faction.bat:58`).
  - Today it starts only because that setting never lands (G66): it runs at 640x480x16.
  - Once G66 makes the setting land, Red Faction stops starting with "Unable to initialize DirectX 8.0 -- Device creation failed!".
- **The fix (3dfx's method, our code).**
  - `Dd_CreateSurface` gives a 16-bit Z that is created in a 32 bpp mode, while D3D32 is armed, a driver-owned block of **32 bits a pixel**.
  - The block is 16-byte aligned, comes from DirectDraw's own heap, and is marked in `dwReserved1`. `surf_zbits` then reports 32.
  - Nothing else changes: `vcr_rt_format`, the register sequence, the clears, the caps and the Z list stay as they are.
  - Behind a 32 bpp target such a Z is an ordinary 24+8 aux buffer, drawn exactly like D24X8. Behind a 16 bpp target it is the proven 16/16-in-32 layout (be58b7d).
- **Gate.**
  - A new `Diag\D3DSafe` **bit 3**, default 0, read by the miniport at boot. It acts only with `D3D32` on a VSA-100.
  - With the bit off, the old path runs unchanged, including the refusal.
  - After one supervised clean boot proves it, it should become default-on wherever D3D32 is on. It is a prerequisite of G20 (D3D32 default-on).
- **Priority: P0.** It blocks a staged title's staged configuration, and it must land before G66 changes Red Faction's depth. Effort: **M**.

## 1. The failure, end to end (measured on `.124`, 2026-11-12)

| step | evidence |
|---|---|
| The runtime lists D16, D24X8 and D24S8 at the 32 bpp desktop, and pairs D16 with X8R8G8B8 (`match 1`). R5G6B5 with D24X8/D24S8 gets `match 0`. | `caps_124.txt` `zmatch` |
| `d3dprobe render --full 640x480x32 --zfmt d16`. The runtime sets mode 144 (640x480x32@85) and only then creates the surfaces. The Z is `CreateSurface` caps `0x00024000` (ZBUFFER, VIDEOMEMORY), and DirectDraw places it at 0x258000 with 16 bits a pixel. | `ONBOX/ring_after_probe_i_decoded.txt` seq 24654-24712 |
| `ContextCreate refused: 32 bpp target with a 16-bit Z on a VSA-100 (16/16 or 32/32 only)`, event 513 what 12 (b=0x20, c=0x10). | seq 24713 |
| `CreateDevice 8876086c`. The runtime then puts the desktop back (mode 159), 156 ms after setting mode 144. | `ONBOX/d3dprobe_render_640x480x32_d16.txt:8-9`; seq 24714-24733 |

The code path:

- `Dd_CanCreateSurface` refuses a Z other than 16-bit only when rt32 is off (`KMD/display/vcrdd_ddraw.c:610-631`).
- `Dd_CreateSurface` leaves Z placement to DirectDraw (`:633-645`).
- `target_of`, via `surf_zbits`, reads 16 (`KMD/display/vcrdd_d3d.c:185-194, 1047-1088`). `vcr_rt_format(1, 32, 16)` is 0, and `D3d_ContextCreate` returns `DDERR_INVALIDPIXELFORMAT` (`:1189-1196`).
- The same pair reached through `SETRENDERTARGET` is refused silently, and that context draws nothing (`:1733-1749`).

Which calls fail:

- (a) a fullscreen D3D8/9 device at X8R8G8B8 or A8R8G8B8 with D16;
- (b) a windowed device on `.124`'s 32 bpp desktop with D16;
- (c) `SetRenderTarget` of a D16 to a 32 bpp target (silent);
- (d) a DX6/7 application that attaches a 16-bit Z to a 32 bpp back buffer.

Why the runtime says "match":

- d3d8.dll carries a built-in table keyed by PCI id. Its entry `121a:0009 = 0x4580` has no 0x10 bit ("Z with arbitrary colour depth"), and it keeps D16 as `D16_LOCKABLE` (bit 0x80) (`reports/runtime.md` §4.3).
- The rule that still pairs D16 with a 32-bit target is not visible; only its outcome is measured.
- A DX7 driver cannot turn the pairing off. The runtime's registry override can only switch flags OFF, and the 0x10 bit is already off.
- Removing D16 from the Z list would break the proven 16 bpp fullscreen lane. The runtime checks Z formats against the list it read at the desktop mode, and 4a9793b broke exactly that once (`vcr_rtfmt.h:179-198`; `reports/runtime.md` §11).
- **So the pair has to be made to draw.**

## 3. What the hardware, 3dfx and the runtime say

**Hardware.**
- `renderMode[1:0]` is the only pixel-size field, and the aux buffer follows it: 16 bits at 16 bpp, and at 32 bpp 24 of depth under 8 of stencil (`reports/hw.md` Q5; `vcr_rtfmt.h:13-25`).
- SPEC L4872: "AuxBufferAddr must be 16 byte aligned, so auxBufferAddr[3:0] are unused".
- SPEC L4881: the linear aux stride is 16-byte aligned, in `[13:0]` (at most 0x3fff).
- SPEC L4475: "the 16-bit incoming depth value is converted to a 24-bit depth value by ... MSB bit replication". This is the right 16-to-24 conversion for depth fills (section 4.7).

**3dfx (guidance only).** 3dfx never refuses the pair; it resizes the Z.
- On Napalm, a 16-bit Z created on a 32 bpp primary is allocated and labelled 32-bit, mask `0x00FFFFFF` (`VH5/DDSURF.C:592-627`, the substitution at `:619-626`).
- At attach, a 16 bpp desktop reallocates the Z and relabels it (`:2211-2347`).
- A depth fill on a promoted Z copies the low word into the high word, `(c << 16) | c`, "to pass the Blt-Exotic 3D Depth Fill test" (`VH5/DDBLT32.C:938-948`). That is right only for 0 and 0xFFFF; MSB replication is right.
- ContextCreate's mismatch check was removed in 2000 ("Removed error code for zbuffer and render targer depth mismatch", `VH5/D3CONTXT.C:33-34`).
- 3dfx's never-built DX8 list carries D16 with `ZSTENCIL_WITH_ARBITRARY_COLOR_DEPTH` (`VH5/D3INIT.C:2553`).
- `DdLock` does not look at the promotion: a locked promoted D16 returns 24-bit words. 3dfx accepted that.

**Our allocator precedent.**
- `mipchain_ext` already places every D3DBigTex texture itself. It uses `HeapVidMemAllocAligned` on DirectDraw's own heap (`pd->pvmList`), 16/16 alignment, `lpGbl->dwReserved1 = heap`, `s->dwReserved1 = MIP_TOP` (`vcrdd_d3d.c:367-461`).
- It frees in `Dd_DestroySurface` through `VcrDdD3dFreeMipChain` (`:586-600`).
- Silicon proof:
  - the 83/0 and 37/3 texture matrices (`ONBOX/d3dprobe_textures_*`);
  - four game sessions, one of them UT2004 killed by pid with every texture in such blocks;
  - no instability (`reports/onbox.md` §6, §8).

## 4. The change

### 4.1 Gate: `Diag\D3DSafe` bit 3 (value 8), default 0

- **Miniport.** `x->d3dsafe = VcrDiagGet(L"D3DSafe", 0);` beside `D3DBigTex` (`KMD/miniport/vcrmp.c:244`), read at boot. `vcrmp.h` gains `ULONG d3dsafe`.
- **Info flag.** `IOCTL_VCR_INFO` sets the positive flag `VCR_INFO_F_D16_STORE32` when `x->d3dsafe & 8` (`vcrmp.c:445-466`).
  - Proposed convention for every D3DSafe bit: flag `0x10000 << bit`, so bit 3 is **0x80000**.
  - If G01, G02 or G03 adds the carrier first, use theirs. `test_d3d32_is_a_default_off_switch` already fails when two flags share a bit.
- **Display driver.** `VcrDd2dInit` zeroes `pd->d16_store32` with the other defaults, then sets `pd->d16_store32 = pd->rt32 && (info.flags & VCR_INFO_F_D16_STORE32) ? 1 : 0;` after `pd->rt32` (`KMD/display/vcrdd_2d.c:442-457`).
  - The 513/16 "armed" text adds "D16 in 32 bpp modes stored 32-bit ON/off (Diag\D3DSafe bit 3)". Its `d` field (`info.flags`) already carries the bit.
- **The bit is inert without D3D32, and it must be.**
  - `vcr_rt_format(0, 16, 32)` is REFUSED.
  - So a D16 promoted on a box without rt32 would break today's working case of a DX7 16 bpp offscreen 3D target at the 32 bpp desktop.
- **Deploying it needs `vcrmp.sys` as well as `vcrdd.dll`.** The miniport is the only reader of Diag.
  - `.124` runs `vcrmp.sys` fda1b8c9 (late September). The current miniport tree also carries 1667afa (10-07, `SliOffAaCtrl`, default 0).
  - List every miniport change since the deployed build in the deploy note. Each must be a default-off switch.
  - If G01's miniport change goes in the same binary, it must also be default-off.

### 4.2 Allocation: `VcrDdD3dCreateZSurface` (new, `vcrdd_d3d.c`, beside `mipchain_ext`)

`Dd_CreateSurface` calls it first: `if (VcrDdD3dCreateZSurface(pd, p)) return DDHAL_DRIVER_HANDLED;`. The mip-chain and compressed-texture calls follow, unchanged.

```c
#define SF_Z32      0x8u    /* a 16-bit Z stored 32 bits a pixel; the block is ours (D3DSafe bit 3) */
#define SF_ZLOCKED  0x10u   /* ... and its first Lock has been logged */
/* SF_MAGIC/SF_IS and these move ABOVE surf_zbits (today they are defined after it, :204-212) */

int VcrDdD3dCreateZSurface(VCR_PDEV *pd, PDD_CREATESURFACEDATA p)
{
    if (!pd->d16_store32 || p->dwSCnt != 1 || !pd->pjRegs || !pd->g2d_ok || pd->d3d_disabled)
        return 0;                                  /* bit off: the old path, untouched */
    z = p->lplpSList[0];
    if (!z || !z->lpGbl || !(z->ddsCaps.dwCaps & DDSCAPS_ZBUFFER))
        return 0;
    /* bits asked: the surface's own DDPF_ZBUFFER format (NT fills it - VH5/DDSURF.C:546),
     * else the request's DDSD_PIXELFORMAT / DDSD_ZBUFFERBITDEPTH (Dd_CanCreateSurface's rule);
     * stencil bits from DDPF_STENCILBUFFER */
    if (vcr_rt_zstore(pd->d16_store32, pd->rt32, pd->bpp, zbits, stencil,
                      !(z->ddsCaps.dwCaps & DDSCAPS_SYSTEMMEMORY)) != 32)
        return 0;                                  /* DirectDraw places it as asked */
    pitch = vcr_rt_zstore_pitch(z->lpGbl->wWidth); /* (w*4 + 15) & ~15, 0 past 0x3fff */
    if (!pitch || !z->lpGbl->wHeight || !vm || !vm->lpHeap)
        return 0;
    al.dwStartAlignment = al.dwPitchAlignment = 16;            /* SPEC L4872, L4881 */
    /* 0 is "no memory" OR the heap's block at offset 0, which the heap manager hands
     * out as 0 and loses (include/vcr_ddheap.h): one retry tells them apart - DirectDraw's
     * own second pass does the same; with Diag\DdHeapFloor the retry never runs */
    for (i = 0; i < 2 && !base; i++)
        base = HeapVidMemAllocAligned(vm, pitch * h, 1, &al, &np);
    if (!base) {     /* WARN 513 what 24, b=0 */
        p->ddRVal = DDERR_OUTOFVIDEOMEMORY;        /* honest: the pair needs this memory */
        return 1;
    }
    z->lpGbl->fpVidMem = base;
    z->lpGbl->lPitch = pitch;
    z->lpGbl->dwReserved1 = (ULONG_PTR)vm->lpHeap;
    z->dwReserved1 = SF_MAGIC | SF_Z32;
    z->ddsCaps.dwCaps = (caps & ~DDSCAPS_SYSTEMMEMORY) | DDSCAPS_VIDEOMEMORY | DDSCAPS_LOCALVIDMEM;
    /* INFO 513 what 24: b=offset c=w<<16|h d=pitch */
    p->ddRVal = DD_OK;
    return 1;
}
```

The decision itself lives in Win32-free helpers in `KMD/include/vcr_rtfmt.h`, which the host tests compile:

```c
/* the bits a pixel a Z surface is STORED with when created: 32 for a 16-bit,
 * stencil-less, video-memory Z created in a 32 bpp mode with Diag\D3DSafe bit 3
 * AND rt32; VCR_ZS_ASKED (0) = DirectDraw places it as asked */
static __inline unsigned vcr_rt_zstore(unsigned promote, unsigned rt32, unsigned mode_bpp,
                                       unsigned z_bits, unsigned stencil_bits, unsigned vidmem);
static __inline unsigned vcr_rt_zstore_pitch(unsigned width);   /* 16-aligned 4*w, 0 if > 0x3fff */
```

Notes on the allocation:

- **Why `pd->bpp`, the mode the Z is created in.** The runtime sets the fullscreen mode before it creates the Z (§1 ring order). A windowed device's Z is created in the desktop PDEV. A DX6/7 title sets its mode and then creates its Z, because surfaces do not survive a mode change. So every realistic route to "D16 with a 32 bpp target" creates the Z in a 32 bpp PDEV.
- **Why not DDHAL_PLEASEALLOC_BLOCKSIZE.** DirectDraw's linear heap places blocks on 4-byte boundaries (UT2003's font pages at `...d6b4`, FINDINGS 11-08). The aux buffer ignores address bits 3:0, so a Z placed that way would be read up to three pixels off.
- **The label stays D16.** The DD_SURFACE_GLOBAL pixel format is not rewritten the way 3dfx did. The runtime's view and GetSurfaceDesc stay consistent, and only the driver knows the storage, through `SF_Z32`. If a HEL (DirectDraw's software layer) depth fill saw a 32-bit label, it would write a 16-bit 0xFFFF as depth 0x00FFFF, about 0.004 of the range, and nothing would draw. That would be worse than a 16-bit label.

### 4.3 The one reader that changes: `surf_zbits`

`if (SF_IS(z, SF_Z32)) return 32;` becomes its first test (`vcrdd_d3d.c:185`). Everything downstream already exists and is pinned:

- `vcr_rt_format(1, 32, 32)` gives VCR_RT_32, and `vcr_rt_zcheck` accepts the pitch (≥ 4·w, 16-aligned, ≤ 0x3fff) and the size.
- `vcr_3d_target_seq` writes the 32/32 sequence write for write as for D24X8 (`test_vcr_kmd_d3dseq.c`):
  - renderMode `0x001e0002`;
  - stencilMode = stencilOp = 0;
  - auxBufferAddr = the 16-aligned base;
  - auxBufferStride = `BS_LINEAR_STRIDE(pitch)`.
- `VcrDd3dDrawTarget` scales Z by 2^24-1 (`vcrdd_3d.c:292`). `VcrDd3dClear` takes depth from the target's format, `z * 16777215` into zaColor[23:0] (`:136-179`). So Clear2 and DP2 CLEAR, both float depths, need no conversion.
- The same Z behind a 16 bpp target gives `vcr_rt_format(1, 16, 32)` = 16: the 16/16-in-32 rows of be58b7d.

**There are no new register writes, no new register values, a single pass, and no caps change.**

### 4.4 Free

`VcrDdD3dFreeMipChain` (`:586`) frees `SF_Z32` blocks the way it frees `SF_MIP_TOP`: `VidMemFree` on the heap saved in `lpGbl->dwReserved1`, then `dwReserved1 = 0`, returning HANDLED. `Dd_DestroySurface` already calls `VcrDdD3dSurfaceGone` (contexts drop the Z) before it.

The lifecycle is the mip-chain blocks' own: Release, a mode change, a killed process.

### 4.5 Visibility (the project's "a tolerated failure must say so")

- **513 what 24, INFO**, per promoted Z: offset, w/h and pitch. With b=0 and WARN it means out of video memory.
- **513 what 25, WARN, once per surface.** `Dd_Lock` calls the new `VcrDdD3dSurfaceLocked(s)`. The message is: "a D16 stored 32 bits a pixel was LOCKED (pid %u): it holds 24-bit depth words at pitch %u; a 16-bit reader, or DirectDraw's own (HEL) depth fill, gets other values (Diag\D3DSafe bit 3)". This makes the accepted Lock caveat, and the HEL depth-fill case of 4.7, show up in the flight recorder ring.
- **513/12** keeps its format string; `test_32bpp_targets...` pins it. Its `%s` names the remedy:
  - bit off, 32/16: "... ; Diag\D3DSafe bit 3 stores a D16 made in a 32 bpp mode at 32 bits";
  - bit on, 32/16: "... ; this D16 was made in a 16 bpp mode". That is the residual case in 4.8.
- `vcr_events.h`'s description string for event 513 gains what 24 and 25.

### 4.6 What does NOT change

- `vcr_rt_format`: an unpromoted 32/16 pair is still REFUSED, and the existing tests keep asserting it.
- `vcr_rt_zlist`, the `GUID_ZPixelFormats` answer, DDBD, `dwZBufferBitDepths`, and every D3D and DirectDraw cap. `d3dprobe caps` after the fix must equal `caps_124.txt` field for field. That is the runtime-22 rule: caps stay independent of the mode.
- The 16 bpp lane: a D16 created in a 16 bpp PDEV is never promoted.
- The D24X8/D24S8 lane: a 32-bit Z is never promoted.
- The flip path, SLI state, the Glide/OpenGL paths, and the miniport mode set.

### 4.7 Step 2, conditional: DirectDraw depth fills on a promoted Z (lands with G61's DEPTHFILL item)

- Today the HAL caps (`04020041`) have no `DDCAPS_BLTDEPTHFILL`, and the HEL caps (`f4c08241`) do. Measured in `KMD/evidence/86box_v3/int_20260927/04_d3d/e9_zsurf_z16.txt`. So an application's `Blt(DDBLT_DEPTHFILL)` is done by the HEL.
- On a promoted Z in 32/32 use, the HEL writes 16-bit values across half of each row.
- In 16/16-in-32 use it is right, if it honours `lPitch` (to be measured, 6.3).
- D3D clears never take this route: Clear2 and DP2 CLEAR are ours.
- A claimed blit cannot be declined: "a HAL that claims DDCAPS_BLT and declines gets the application E_NOTIMPL" (`KMD/README.md:690-692`). So the fix is all-or-nothing, and it belongs to **G61**:
  - **in 32 bpp PDEVs only**, with the bit, advertise `DDCAPS_BLTDEPTHFILL`;
  - in `Dd_Blt`/`clipped_blt`, handle every `DDBLT_DEPTHFILL` into a video-memory Z through the existing `VcrDd2dFill` (plus the CPU fallback) at bpp 4;
  - the value is `vcr_rt_z16_to_z24(dwFillDepth)` = `((d & 0xffff) << 8) | ((d & 0xffff) >> 8)` for `SF_Z32` (SPEC L4475), and `dwFillDepth & dwZBitMask` for D24X8/D24S8.
- The 16 bpp lane keeps the HEL, because the cap depends on the PDEV and is absent there.
- **This is required before G10 goes default-on only if** 513/25 appears in any title, or `ddlab zsurf --depthfill` shows the HEL writing a promoted Z (6.3).
- None of the staged titles that run at 32 bpp uses the DirectDraw interfaces this way (inferred: they are D3D8/9). The DX5/6 titles run at 16 bpp.

### 4.8 Cases this does not cover, and the alternative rejected for now

1. **A D16 created in a 16 bpp mode, then bound to a 32 bpp target.**
   - The targets: an A8R8G8B8 render-target texture (the runtime's table grants 0x400), or a DX7 offscreen 32-bit 3D surface.
   - It is still refused at SETRENDERTARGET/ContextCreate, now logged with the hint.
   - 3dfx reallocated at `DdAddAttachedSurface` (`VH5/DDSURF.C:2270-2338`). We export no AddAttachedSurface, and D3D8 `SetRenderTarget` never calls one.
   - Whether any title does this is G36's question. Halo runs with `DisableRenderTargets`.
2. **A locked promoted Z in 32/32 use returns 24-bit words.** This is accepted, as 3dfx did, and visible through 513/25.
   - It is no regression: before the fix that device could not exist.
   - The 16/16-in-32 layout reads correctly through the lock pitch.
3. **A DirectDraw SRCCOPY between Z surfaces.** `surf_bytespp` reads the 16-bit label. No title is known to do this, and D3D8 forbids it.
4. **Rejected alternative: a hidden 32-bit aux buffer** allocated at ContextCreate/SETRENDERTARGET for each 16-bit Z / 32 bpp target pair ("the 16-over-32 trick the other way round", `reports/onbox.md` §3).
   - It would cover case 1.
   - It costs 3x the memory per Z.
   - It allocates inside D3D callbacks, which is untested.
   - The application's Z and the hidden buffer diverge for Lock and Blt.
   - Its lifetime is keyed to two surfaces and to every context that shares the Z.
   - Keep it as the fallback if G36 finds a title in case 1.

### 5.1 Native: `WT/tests/native/test_vcr_kmd_d3dseq.c`, `TEST(a_d16_made_in_a_32bpp_mode_is_stored_32_bits)`

### 5.3 d3dprobe (`KMD/tools/d3dprobe.c`): new explicit tests

These join the default list only when G10 goes default-on, so that "40/40" keeps its meaning until then.

- **`d16_32`**: a D16 bound to the device's target with SetRenderTarget. It runs in any run, windowed or fullscreen, at 16 or 32 bpp, while the device keeps its own Z.
  - Steps:
    1. `GetRenderTarget` and `GetDepthStencilSurface` (z0).
    2. Skip if `CheckDepthStencilMatch(adapter, target, D16)` fails.
    3. `CreateDepthStencilSurface(w, h, D16)`.
    4. `Clear(TARGET, 0xff00ff)` with z0. This is the sentinel: a refused target keeps it.
    5. `SetRenderTarget(bb, d16)`.
    6. Draw the `ztest` scene: Clear target+Z to black/1.0; green at z 0.25 over the quad, red at 0.75, blue at 0.10 on the left half.
    7. Read back, then restore z0 and release.
  - Reference values, ±8:

    | point | expected |
    |---|---|
    | (180,128) | 0x00ff00 |
    | (64,128) | 0x0000ff |
    | (8,8) | 0x000000 |

  - **The current build at 32 bpp reads 0xff00ff at all three points**: SETRENDERTARGET is refused (513/12) and neither the clear nor the draw lands.
  - At 16 bpp the D16 is not promoted and passes on both builds. That is the control.
- **`zprec`**: the aux buffer's precision behind the current target.
  - Clear Z to 1.0 and set ZFUNC LESS. Draw red at z = 0.5 + 6/2^24 (exact in float), then green at z = 0.5. Read (128,128).
  - Expected: **0x00ff00 at a 32 bpp target**. The values are 24-bit, 8388607.5 against 8388613, and the nearer quad wins.
  - Expected: **0xff0000 at 16 bpp**. Both values quantize to 32767, so LESS fails and the first quad stays.
  - This pins the documented meaning: a D16 behind a 32 bpp target has 24-bit precision.
- **`zleak`**: 64 times, create a 1024x1024 D16 (4 MB when promoted), bind it, clear Z, unbind it, release it.
  - One check: all 64 are created. The heap holds about 60 MB, so a block the driver never freed fails by about the 16th.
  - It passes on the current build too: it guards the new free path.
- **`zlock`** (informational, never gating): `CreateDepthStencilSurface(D16_LOCKABLE)` (skip if not offered), bind it, `Clear(ZBUFFER, 1.0)`, unbind it, `LockRect(READONLY)`.
  - It records `Pitch` and the first 4 dwords, so the runtime's pitch for a promoted D16 (4·w, or w·2) is measured.
  - Expected: low 24 bits 0xffffff in each dword at 32 bpp; 0xffff words at 16 bpp.

The existing full lists with **`--zfmt d16 --bpp 32`** run unchanged: fullscreen must be **40/40**, windowed on the desktop **42/42**. On the current build, fullscreen gives `CreateDevice 8876086c` (measured) and windowed is expected to give the same.

### 5.4 ddlab (`KMD/tools/ddlab.c`): the DirectDraw 7 view, with no mode switch

`ddlab zsurf` gains two options:

- **`--report`** adds GetSurfaceDesc's `lPitch` and `dwZBufferBitDepth` to its RESULT.
  - 256-wide D16 at the 32 bpp desktop: lPitch 512 today, **1024 with the bit**, and the label stays 16.
- **`--depthfill V`** does `Blt(DDBLT_DEPTHFILL)`, then Lock, and dumps the first 4 dwords of rows 0 and 255 together with the lock pitch. This measures what the HEL does to a promoted Z and settles section 4.7.

## 7. Risk to proven paths

- **Default 16 bpp path: none.**
  - Promotion needs a 32 bpp PDEV and rt32.
  - The caps and Z list are byte-identical; step 2 checks this.
  - The 16 bpp target sequence is unchanged.
- **D24X8/D24S8 32 bpp path: none.** A 32-bit Z is never promoted.
- **The one previously working case that changes.**
  - It is a D16 made in a 32 bpp mode and used with a 16 bpp target: a D3D8 R5G6B5 render-target texture, or a DX7 16-bit offscreen 3D surface at the 32 bpp desktop.
  - It moves from plain 16/16 to 16/16-in-32 (be58b7d, proven on silicon by one Rainbow Six image).
  - No title on `.124` is known to do this. G36's `rtt` test should cover it.
- **Memory.** A promoted Z takes 2x: 7.5 MB at 1600x1200 against a heap of about 60 MB.
- **Allocation.**
  - It uses the mip-chain allocator's mechanics, which are proven on silicon (section 3), with the offset-0 retry added.
  - It is new for Z surfaces: the CreateSurface → ContextCreate → DestroySurface lifecycle through a driver-owned block, including a killed process. `zleak` and step 8 exercise it.
- **Glide/OpenGL coexistence, SLI state, flip path: none.** There are no new register writes, and the heap is DirectDraw's, rebuilt at every mode set as before.
- **Lock and HEL fills:** only for the newly enabled 32/32 use (4.7, 4.8). Visible as 513/25.
- **The miniport rebuild** carries unrelated changes made since fda1b8c9 (1667afa's `SliOffAaCtrl`, default 0). They must all be default-off.
- **A double mode switch if the fix fails** at fullscreen: hence run windowed first, keep the runs paced and attended.

## 9. Open questions

1. Does XP hand the driver's `lPitch` for a Z to user mode? Measured by `ddlab --report` (DX7) and `zlock` (D3D8). D3D8 computes its own lock pitch for DXT (`ONBOX/d3dprobe_textures_a_1024x768x32.txt:66`), so it may do the same for D16.
2. Does the HEL depth fill use that pitch (`ddlab --depthfill`), and does any title Lock or Blt-fill a promoted Z (513/25 in the in-game sweep)? Together these decide whether step 2 (G61) gates default-on.
3. Does any title bind a D16 made in a 16 bpp mode to a 32 bpp render-target texture (case 1 in 4.8)? This is G36; if one does, build the hidden-aux alternative.
4. Does the DX7 runtime (d3dim700) accept a 16-bit Z attached to a 32 bpp back buffer before it reaches ContextCreate? This needs G75's DX7 probe.
5. Does D3D9 (Halo, NewDark) answer the same "match"? Only matters if a D3D9 title asks for D16 at 32 bpp.
6. After the proof, should the bit be default-on (active wherever D3D32 is)? Decide it together with G20; it is the user's call.
7. Which hive does rf.exe read its resolution from (G66)? And what else does its flag `0x1cd4462` change? It is set at `0x544cc8` when the device id is 5 (a Voodoo 3), among other conditions. On the Z path both of its branches end at D16; its other uses were not read.
