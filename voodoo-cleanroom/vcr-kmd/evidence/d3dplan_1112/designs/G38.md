## 1. Verdict

- **The gap is real, it is fixable, and it is worth little.** It is **P3**. No staged title is blocked.
  - Shogo looks for an 8-bit palettized format and falls back to 16-bit formats without one. The fallback is not fatal: "Couldn't find suitable 8 bit texture format" is printed and the code carries on. Only the absence of any usable 16-bit format is fatal (`LIB/Shogo/d3d.ren` 0x10019de0-0x10019eaf; flag test `test $0x20` = `DDPF_PALETTEINDEXED8`).
  - Aliens vs Predator's loader also has both paths: "chosen %u-bit palettized texture format" and "chosen %u-bit %u%u%u%u texture format" (`avp.exe` strings).
  - Both games render into 16 bpp targets (Shogo `screendepth 16`, AvP 640x480x16). Those targets hide most of the extra precision a 24-bit palette lookup gives over 565 textures (inferred).
- **"P8 has never been shown to draw on this silicon" is not true for the Glide path.**
  - Quake II on our ICD 0.1.75, over **our** h5 Glide (md5 2df2f969), on vcr-kmd, 4 chips, used `GL_EXT_shared_texture_palette`.
    - Log: `KMD/evidence/v5-7_q2_allours/quake2-allours_1024x768_16_cfg5.log:19` "...using GL_EXT_shared_texture_palette", 2026-09-28, 173.6 fps.
    - Frame of the same stack: `KMD/evidence/sli_shots/q2_vcrkmd_cfg5_1024x768_16.png` (2026-09-26).
    - The box's Quake II config had `gl_ext_palettedtexture "1"` until `v56k_tune.py` switched it off on 2026-10-02 (`RA/scripts/benchmarks/v56k_tune.py:43-45`; `KMD/evidence/gametune_1001/README.md:16`).
  - What that run proves: on this board, world textures were uploaded as `GL_COLOR_INDEX8_EXT` and became `GR_TEXFMT_P_8` (`MFX/fxddtex.c:1115-1122`, `:1175-1176`). The palette went through `grTexDownloadTable(GR_TEXTABLE_PALETTE)` (`MFX/fxddtex.c:540-623`), which writes `nccTable0[4..11]` with bit 31 set and broadcasts to TMU0|TMU1 (`GL5/gtexdl.c:441`, `:457`, `:476-513`). The frame shows a correctly coloured, bilinear-filtered world with lightmaps on the other TMU.
  - It is strong evidence, not a controlled test: there is no exact readback. §7 E1 makes it exact.
- **The vintage lane's "P8 samples white" is confounded, so it counts for nothing either way.**
  - The same commit (`R3` `cf3ab3e`, 2026-07-28, box `.143`) found and fixed the real cause of GoldSrc's white world: mip sub-level downloads were silently dropped (`R3/VINTAGE-FIXES.md:86-104`).
  - It switched P8 off at the same time (`VINTAGE-FIXES.md:145-156`; `VH5/D3INIT.C:521-530`), and the two changes were never A/B'd.
  - 3dfx's own history points at driver logic, not silicon:
    - revs 24/25 disabled, then re-enabled, palettized formats on W2K (`VH5/D3INIT.C:75-78`);
    - PRS 13607 removed A8P8 with no recorded reason (`:64-65`);
    - PRS 11174 was the colour key through an alpha palette (`VH5/D6DP2.C:6880-6893`);
    - PRS 14371 loaded the wrong palette with two stages (`VH5/D6MT.C:4955-4988`).
- **`FX_NO_PALETTED_TEXTURE=1` for Counter-Strike is not evidence about P8 on this card.**
  - It dates from the Voodoo 3 era (2026-07-18/23).
  - The same day's isolation ruled paletted textures out: "removed that banner line but hl.exe still exited" (`RA/voodoo-cleanroom/DEBUGGING-NOTES.md:152-156`).
  - The source comment that still blames palettes (`MFX/fxdd.c:1932-1937`) is stale. It also says Quake II uses the RGBA path, which the log above contradicts (doc drift, G80).
- **Four new findings, each one a trap this design closes:**
  1. **The XP SP3 D3D8 and D3D9 runtimes append palette records with a 4-byte hole (§4.2).** Today's walker skips SETPALETTE as 12 bytes per record. It would mis-step 4·(k−1) bytes on a d3d8/d3d9 command carrying k ≥ 2 records. hal-27's proposed fix, "parse exactly one UPDATEPALETTE record", is wrong for the same streams.
  2. **A `PALETTEENTRY` is bytes R, G, B, flags, so as a DWORD it is `R | G<<8 | B<<16 | A<<24`.** The chip wants R in bits 23:16. Copying the DWORD's low 24 bits swaps red and blue.
  3. **The base rounding in `vcr_texlod_compute_ext` mis-places tiny 8-bit textures.**
     - A P8 1x1 texture would be sampled 12 bytes before its texel; a 2x1 or 1x2 texture 8 bytes before.
     - The cause: the TMU sums the missing levels byte-exact, and the sum is not a multiple of 16.
     - G07 found the 16 bpp 1x1 twin (8 bytes early).
  4. **`Dd_Blt` takes a D3D texture's bytes per pixel from the desktop.** `surf_bytespp` (`KMD/display/vcrdd_ddraw.c:389-394`) reads `ddpfSurface` only when `DDRAWISURF_HASPIXELFORMAT` is set, and NT does not set that flag on D3D textures (`vcrdd_d3d.c:161-169`). A colour-fill or video-to-video Blt into a P8 texture at a 16 bpp mode would therefore write 2x the row width, and at 32 bpp 4x.

## 3. The hardware, in register terms

### 3.1 Formats (SPEC §8.76, L3875, L3876, L3885; `GL5/glide.h:357-377`)

| `textureMode[11:8]` | texel | colour | alpha | D3D |
|---|---|---|---|---|
| **5** `P8` | 8-bit index | palette R, G, B [7:0] | 0xFF | P8, with a palette that has no alpha |
| **6** `P8_ARGB6666` | 8-bit index | the 24 stored palette bits reread as A6 R6 G6 B6; each 6-bit value is expanded `x8 = x6<<2 | x6>>4` | A6 expanded | P8 with an alpha palette (`D3DPTEXTURECAPS_ALPHAPALETTE`); RGB drops to 6 bits |
| **14** `AP88` | 16-bit: alpha in [15:8], index in [7:0] | palette R, G, B [7:0] (the 888 layout) | texel [15:8] | A8P8 (`dwRGBAlphaBitMask` 0xFF00) |

- **Bilinear filtering works:** "four texels are looked up simultaneously, each an independent 8-bit address" (SPEC §8.82 L4037).
- **Texel sizes:** level sizes are `w·h` bytes for P8 and `2·w·h` for AP88. The TMU walks levels with these sizes (`_grMipMapOffset` in texels × bits per texel, `GL5/ditex.c:1063-1130`, `:1790-1793`).
- **Spec caveat:** the feature overview's "palette offset register" and "load the palette from texture memory" (L567) have no register in the register map. §8.82 says the palette "is loaded with register writes". Treat L567 as stale planning text.

### 3.2 Palette write (SPEC §8.82 L4038-4039; L2390; L2225)

- **Where:** "written through the NCC table 0 I and Q register space when the MSB of the register write data is set". Those are registers `nccTable0[4..11]`, offsets **0x334 + 4·(i & 7)**.
- **Word for entry *i*:** `0x80000000 | ((i & 0xFE) << 23) | payload`. Bits 30:24 hold i[7:1]; the register's parity supplies i[0].
  - **888 payload:** `R<<16 | G<<8 | B`.
  - **6666 payload:** `(A>>2)<<18 | (R>>2)<<12 | (G>>2)<<6 | B>>2`.
  - Glide uses these words (`GL5/gtexdl.c:476`, `:536-546`), and so does 3dfx's D3D (`VH5/D3TXTR.C:4185-4300`).
  - A full palette is 256 writes, in 32 groups of 8.
- **Register flags** (register table L2390, column meanings at L2225):
  - `nccTable0` is **`TREX*`**: a TMU takes the write only when the chip address names it, so each TMU can hold its own palette.
  - It is **Sync = Yes**: "the graphics processor will flush the data pipeline before loading the register". A palette write therefore cannot recolour pixels of earlier triangles that are still in flight.
  - Glide and 3dfx broadcast one palette to TMU0|TMU1 (`GL5/gtexdl.c:457`; `VH5/D6DP2.C:6788`). Our fork is built without `GLIDE_POINTCAST_PALETTE` (no Makefile defines it).

### 3.3 Where the TMU reads a texture: the 16-byte rule for small textures

- **Base:** `texBaseAddr` is 16-byte granular. The TMU reads level 0 at `base + prefix`, where `prefix` is the byte-exact size of the absent larger levels.
- **Glide's rule:** Glide subtracts `prefix & ~15` and lets the data land at `start + (prefix & 15)` (`GL5/ditex.c:1782-1793`, "it always starts from an aligned baseAddr").
- **Our rule:** we round `offset − prefix` down. With the data at a 16-aligned `o`, the TMU therefore reads at `o − (16 − skew)` whenever `skew = prefix mod 16` is not 0.

Computed for every shape up to 256 (scratch script, 8/16/32-bit):

| kind | shapes with a skew | skew | today's read |
|---|---|---|---|
| P8 (1 byte) | 1x1 | 4 | 12 bytes early |
| P8 | 2x1, 1x2 | 8 | 8 bytes early |
| AP88 / RGB16 (2 bytes) | 1x1 | 8 | 8 bytes early (the RGB16 case is G07's) |
| ARGB32 | none | — | — |

- 3dfx adds 8 to **every** 1x1 texture "(a hw feature I guess)" (`VH5/D3TXTR.C:877-889`), whatever its texel size.
  - By the arithmetic above, that is right for 16 bpp, wrong for P8 (which needs 4) and wrong for 32 bpp (which needs 0).
  - 3dfx applies nothing to 2x1 or 1x2 P8 textures.
  - So small palettized textures would come out wrong on 3dfx's own HAL as well (inferred; one more candidate for its P8 trouble).

## 4. How the XP runtimes deliver palettes (read from `XPRT`)

### 4.1 Who sends what

| runtime | used by | SETPALETTE / UPDATEPALETTE |
|---|---|---|
| **d3dim.dll** (DX5/6 interfaces) | Shogo, AvP, Thief Gold, SS2, Rainbow Six, JK (games.md §1) | Emitters at 0x6d91b0c3 / 0x6d91b01a. Each always opens a new command with wStateCount 1. They are called **eagerly** from DirectDraw's palette notifications, at SetPalette/SetEntries time, not at draw time (0x6d9174e1, 0x6d91753a). The record carries DirectDraw's (start, count). |
| **d3dim700.dll** (DX7) | none on the list (inferred) | 0x73956b0a / 0x73956a55: always a new command, wStateCount 1 |
| **d3d8.dll** | H&D, Halo-era D3D8 titles | **At draw time** (`UpdatePalette`, 0x6d9da9ea-0x6d9daa76). SETPALETTE(n+1, flags, texture handle) when the texture's palette changed. UPDATEPALETTE(n+1, 0, **256**, entries) only when the palette is dirty. Flags are **0x201** (`256 | ALLOW256`) or **0x2201** (+`DDRAWIPAL_ALPHA`); A8P8 (`D3DFMT` 0x28) always gets 0x201. |
| **d3d9.dll** | Halo, NewDark | The same logic (0x4fe55de2-0x4fe55e4e). 0x2201 only when a device flag byte (`0x17c`) has its top bit set (inferred: the ALPHAPALETTE cap). |

### 4.2 The append bug in d3d8/d3d9

- **What appends:** both runtimes append a record to the **open** command when the previous opcode is the same:
  - d3d8 UPDATEPALETTE: 0x6d9e194c-0x6d9e19ae;
  - d3d8 SETPALETTE: 0x6d9e4606-0x6d9e466a;
  - d3d9 SETPALETTE: 0x4fe7b216-0x4fe7b27a;
  - d3d9 UPDATEPALETTE: 0x4fe78bec-0x4fe78c4e.
- **What goes wrong:** each append reserves and accounts for a **new command's** size but writes no header:
  - SETPALETTE adds 16 (`addl $0x10`) for a 12-byte record;
  - UPDATEPALETTE adds 12 + 4n (`lea 0xc(,%esi,4)`) for an 8 + 4n record.
  - So **every appended record is followed by a 4-byte hole of stale bytes**. In SETPALETTE terms the records sit at P+4, P+16, P+32, …, P+16(k−1), and the command ends at P+16k.
- **Control:** the RENDERSTATE append in the same object (0x6d9e10f8-0x6d9e113c) adds exactly 8 per state. So the field meanings are right, and the palette paths are the odd ones out.
- **Reachable:**
  - **SETPALETTE:** two P8 stages re-associated with a clean palette in one pass give S,S → k = 2.
  - **UPDATEPALETTE:** U,U needs two dirty updates with no other command between them. That is unlikely in d3d8's draw-time path, but the code permits it.
  - **Neither can happen today:** without a P8 format, D3D8/9 cannot create a palettized texture.
- **Consequence for the plan:**
  - Today's skip (`12·k`; `Σ(8 + 4n)`) is right for k = 1 (every stream that can reach us today) and wrong by 4(k−1) bytes for k ≥ 2.
  - hal-27's "exactly one UPDATEPALETTE record regardless of wStateCount" is the DDK's sentence (`W2KDDK` d_grafx.chm `D3DNTHAL_DP2UPDATEPALETTE`; `VH5/D6DP2.C:4067-4071` asserts it). It would read record 2 of an appended command as a command header.
  - 3dfx's SETPALETTE loop (`VH5/D6DP2.C:4012-4042`, contiguous `NEXTINSTRUCTION`) has the same flaw under DX8 runtimes (inferred).

### 4.3 What a PALETTEENTRY contains

- **Byte order:** the runtimes copy the application's `PALETTEENTRY` array with `rep movsl` (d3d8 0x6d9e1a17). In memory that is bytes peRed, peGreen, peBlue, peFlags.
- **Which byte is alpha:** with `DDRAWIPAL_ALPHA` set, peFlags is the alpha. Without it, peFlags holds GDI's `PC_*` flags and must be ignored.
- **The DDK's wording:** it calls the entry "a DWORD with an ARGB color for each byte" (d_grafx.chm). 3dfx reads the struct fields (`VH5/D3TXTR.C:4262-4277`), and so must we.

## 5. Design

The design has four layers:
- **Phase 0** is CPU-only and lands default-on. It is byte-for-byte today's behaviour for every stream XP can send now.
- **Phases 1-3** sit behind a default-OFF switch.

### 5.0 Phase 0: parse correctly, count (default-on)

1. **New `KMD/include/vcr_pal.h`** (pure, host-tested): `vcr_dp2_pal_body(op, k, body, avail, &len, &rec_off[])`. It walks SETPALETTE/UPDATEPALETTE bodies in the runtimes' layout:
   - record 0 at body+0, record 1 right after it;
   - every record after the first is followed by a 4-byte hole, so record i ≥ 2 starts 4 bytes after the end of record i−1, and the body ends 4 bytes after the last record;
   - SETPALETTE body length **16k − 4**; UPDATEPALETTE body length **Σ(12 + 4n_i) − 4**;
   - every record and every entry block is bounds-checked against `avail`.
   - For k = 1 this gives exactly today's 12 and 8 + 4n.
   - k = 0 is SETPALETTE 0 bytes (as today) and UPDATEPALETTE one record (the DDK); both are logged as an anomaly.
2. **Defensive layout check.** When k ≥ 2, the end must land on the buffer end or on a byte that is a known DP2 opcode. If it does not, but the contiguous layout (`12k`, `Σ(8 + 4n)`) does, use the contiguous one, set a counter, and log once: `513 what P2 "palette command layout: contiguous"`.
   - This guards against a misreading of §4.2.
   - The native test pins the choice.
3. **`walk()`** sends both opcodes through the helper: SETPALETTE leaves `rec_size`, and the UPDATEPALETTE case calls it. With the switch off, the records are only counted.
4. **Counters in `vcr_d3dctx`**:
   - palette commands seen (S/U), records, the largest k, contiguous fallbacks;
   - with the switch: palettes stored, palette loads, P8/AP88 binds, binds refused for lack of a palette.

   They are reported once at "context gone" (`vcrdd_d3d.c:1210-1216`) as a second event line, because a ring message holds 95 characters. Event numbers are given in §5.9.

### 5.1 The switch

- **The value:** `HKLM\SYSTEM\CurrentControlSet\Services\vcrmp\Diag\D3DPal`, REG_DWORD, **absent = 0 = off**. It is a bit field:
  - **bit 0 (1):** P8 textures + palettes, format 5 (888) only;
  - **bit 1 (2):** `D3DPTEXTURECAPS_ALPHAPALETTE` + the 6666 layout. Ignored without bit 0;
  - **bit 2 (4):** A8P8 (format 14). Ignored without bit 0.
- **Read at boot by the miniport, next to `D3DBigTex`** (`KMD/miniport/vcrmp.c:238-244`). The reason is the same as BigTex's: the format list an application reads at the desktop must equal the one its fullscreen PDEV has. Reported as positive flags `VCR_INFO_F_PAL8`, `_PALA`, `_A8P8`; the bit numbers are the integrator's (several designs already claim 0x8000-0x20000).
- **Armed in `VcrDd2dInit`** (`KMD/display/vcrdd_2d.c:450-472`):
  - `pd->tex_p8 = napalm && F_PAL8 && tex_ext`;
  - `pd->tex_p8a` and `pd->tex_a8p8` likewise.
  - Armed without the BigTex path, it is logged as "ignored: needs Diag\D3DBigTex" and stays off. P8 rides that path's kinds, 26-bit base and placement.
- **Logged** as `513 what P0 "armed (Diag\D3DPal): P8 on/off, alpha palette on/off, A8P8 on/off"`.
- **Documented** in the `KMD/README.md` Diag table (`:88-151`), next to the `D3DBigTex` row (`:111`).

### 5.2 Formats and caps (`VcrDdD3dHalInfo`, `vcrdd_d3d.c:2049-2113`)

- **Size the array** with `VCR_TEXFMT_MAX` instead of `[9]`; G34 also adds entries.
- **Format entries:**
  - with `tex_p8`, append `{DDPF_RGB | DDPF_PALETTEINDEXED8, dwRGBBitCount 8, masks 0}` (3dfx: `VH5/D3INIT.C:2109-2116`);
  - with `tex_a8p8`, append `{DDPF_RGB | DDPF_PALETTEINDEXED8 | DDPF_ALPHAPIXELS, 16, alpha 0xFF00}` (`VH5/D3INIT.C:2177-2185`; `ALPHA_P8_AMASK` 0xFF00, `VH5/D3GLOBAL.H:995`).
  - The D3D8/9 converter maps these to `D3DFMT_P8` / `D3DFMT_A8P8` (runtime.md §4.1).
- **Caps:** with `tex_p8a`, `dwTextureCaps |= D3DPTEXTURECAPS_ALPHAPALETTE` in both `prim_caps` calls.
- **No DirectDraw palette caps or callbacks.** 3dfx's NT build keeps `ENABLE_PALETTE_CAPS 0` and still exported P8 (`VH5/DDINIT.C:64-82`); on NT, texture palettes reach the driver through DP2 only (d_grafx.chm §4.6.2, "Paletted Textures").
- **Expected caps on `.124` once fully armed:** TextureCaps `00004087`, `texP8 1`, `texA8P8 1`.

### 5.3 Surfaces

1. **Kinds:** add `VCR_TEXK_P8` and `VCR_TEXK_AP88` (`KMD/include/vcr_texlod.h`).
   - `vcr_tex_level_bytes` returns `w·h` and `2·w·h`.
   - The pitch rule in `vcr_texlod_compute_ext` (`KMD/common/vcr_texlod.c:89-146`) becomes `w` and `2w`.
   - Both kinds need `VCR_TEXF_NAPALM`.
2. **`pf_kind`:** test `DDPF_PALETTEINDEXED8` **before** the 16-bit RGB test. An 8-bit index gives P8 if `tex_p8`; 16 bits with alpha 0xFF00 gives AP88 if `tex_a8p8`; anything else gives `KIND_NONE`.
   - `pf_tmfmt` returns `TM_FORMAT(5)` for P8 and `TM_FORMAT(14)` for AP88.
   - The 5→6 switch for an alpha palette happens at bind (§5.5).
3. **Skew placement:** new `vcr_tex_skew(kind, w, h)` = `prefix mod 16` (non-TBIG).
   - In `mipchain_ext`, **for P8/AP88 only**, allocate `total + skew` and place the top at `block + skew`. The rounded base `(block + skew − prefix) & ~15` is then exact.
   - `vcr_texlod_compute_ext` **refuses** a P8/AP88 surface whose `(offset − prefix) & 15 ≠ 0`. A DirectDraw-placed one is never sampled at a wrong address.
   - RGB16 keeps its rounding unchanged; its 1x1 fix belongs to G07.
4. **Free:** `VcrDdD3dFreeMipChain` (`vcrdd_d3d.c:586-600`) must free `fpVidMem − skew`. The skew is recomputed from the top's kind and size, so nothing extra is stored. Freeing `fpVidMem` itself would hand `VidMemFree` an address it never allocated (a heap corruption trap the Python test pins).
5. **Blt guard:** in `surf_bytespp` (`vcrdd_ddraw.c:389-394`), if `ddpfSurface.dwFlags & DDPF_PALETTEINDEXED8`, return `dwRGBBitCount / 8` (1 or 2), whatever the flag says.
   - Only palettized surfaces take this branch, and they exist only with the switch. Every other surface keeps today's answer.
   - The general bug (a 565 texture at a 32 bpp mode) is recorded for G61/G37.
   - 2D-engine bases off 16 bytes are already handled (`vcrdd_2d.c:163-168`).
6. **TEXBLT, Lock, Unlock and the dirty flag are unchanged.** `surf_bpp` already uses `has_pixfmt`, so a P8 copy is byte-wise. The texture-port write-back stays RGB16-only (`vcr_tex_writeback_addr`).

### 5.4 Palette store (new `KMD/display/vcrdd_pal.c`, integer-only)

- **Records:** `vcr_pal_rec { PDD_DIRECTDRAW_LOCAL ddlcl; DWORD handle, flags; ULONG serial; ULONG alpha; DWORD e[256]; }`.
  - Allocated with `EngAllocMem` (paged, tag `VCRD`), about 1 KB each.
  - Found through an open-addressed table of `VCR_PAL_MAX = 1024` pointers keyed (ddlcl, handle), using the `hslot` hash (`vcrdd_d3d.c:90-93`).
  - **When full:** one WARN, a counter, and a later bind of an unknown palette is refused. The cap is 1 MB of paged pool.
- **Texture → palette association:** a separate table (ddlcl, **surface handle**) → palette handle, 4096 entries.
  - It survives `handle_forget`, because d3d8 does not repeat a SETPALETTE for a texture whose palette it believes the driver already knows. Its palette word lives at `texture+0x4e`, written before the emitter (0x6d9e4602).
  - A later SETPALETTE overwrites the entry.
- **SETPALETTE(handle, flags, surf):**
  - `surf == 0` is ignored and counted. The runtime attaches palettes to system-memory surfaces this way (`VH5/D7DP2.C:1018-1029`, PRS 12730).
  - `handle == 0` detaches.
  - Otherwise set the association, create the record if needed, and store the flags.
- **UPDATEPALETTE(handle, start, n, entries):**
  - Create the record if needed; d3dim can send it before SETPALETTE.
  - Clamp `start + n ≤ 256` (count any excess).
  - Copy, bump `serial` from a global `++g_pal_serial`, and recompute `alpha` = (flags & `DDRAWIPAL_ALPHA`) && any `peFlags ≠ 0xFF`.
- **After any palette command:** `c->dirty = 1`, `w->prepared = 0`.
- **`Dd_DestroyDDLocal`** (`vcrdd_d3d.c:1971-1978`): free that local's records and associations. Serials are never reused, so no PDEV cache can match a freed record.

### 5.5 Binding and the load (`compute_regs` `:921-1029`, `prepare` `:1322-1365`)

**Bind.** For each TMU that samples a P8/AP88 texture (TMU0 = stage 0 with one stage, TMU1 = stage 0 and TMU0 = stage 1 with two; `:948-966`):
1. Look up the association and the record. With none, the texture is **refused**: the existing once-per-texture 513/7 line with reason "no palette", and a counter. It draws untextured, never in random colours.
2. Choose the layout:
   - AP88 is always 888 (format 14).
   - P8 is 6666 (format **6**) only if `tex_p8a && (flags & DDRAWIPAL_ALPHA) && alpha`; otherwise 888 (format **5**). d3d8 flags every P8 palette 0x2201 (§4.1), so the flag alone would cost 2 bits of RGB for nothing.
3. Set `c->pal_need[tmu] = serial << 1 | layout`, and the `textureMode` format to match.

**Load.** In `prepare()`, before `VcrDd3dTarget/VcrDd3dState`:
- if both TMUs need the same word, load it broadcast (chip field **0x1800**);
- otherwise load each differing TMU point-cast (**0x800** / **0x1000**);
- skip any TMU whose `pd->pal_tmu[t]` already equals the need.

The load is a new `VcrDd3dPalette(pd, chip, e, layout)` in `vcrdd_3d.c`. It is integer-only, but that file owns the register writes:

```c
for (g = 0; g < 32; g++) {                       /* 32 groups of 8, as Glide */
    if (!VcrDdRoom(pd, 8)) return FALSE;
    for (k = 0; k < 8; k++)
        w3(pd, chip + vcr_pal_reg_off(8 * g + k), vcr_pal_reg(8 * g + k, e[8 * g + k], layout));
}
if (!VcrDdRoom(pd, 2)) return FALSE;
w3(pd, chip + V3D_TEXBASEADDR, ~cur_base & 0x00fffff0u);   /* point away: the TMU cache forgets */
w3(pd, V3D_NOPCMD, 0);                                     /* (3dfx D6DP2.C:6709-6714 does this every state send) */
/* VcrDd3dState then writes each TMU's real texBaseAddr */
```

- `vcr_pal_reg(i, pe, layout)` takes R from `pe & 0xFF`, G from `>> 8`, B from `>> 16` and A from `>> 24` (§4.3), and builds the §3.2 word.
- **Cost:** 256 PIO writes + 34 room checks. At the ~0.15-0.2 µs per write implied by perf.md §0 (5-8 µs for a 36-write triangle), that is about 50-100 µs per load (inferred). A title that reloads 100 palettes a frame pays 5-10 ms; the counters measure it.
- **The cache flush** is kept unconditionally: 2 writes. Whether the TMU cache holds indices or colours is not worth a switch.

### 5.6 Invalidation (shared with G41)

One function, `VcrDd3dStateLost(pd)`, clears both `fog_valid` (G41) and `pal_tmu[0..1]`. It is called at:
- `HWCSETEXCLUSIVE` and `HWCRLSEXCLUSIVE` (`KMD/display/vcrdd_escape.c:126-131`, `:189-200`): Glide writes the same palette RAM;
- the `DrvAssertMode` re-assert (`KMD/display/vcrdd.c:580-595`);
- `VcrDdGlideReset3d`, whatever its outcome;
- G02's engine-reset paths.

A new PDEV (a mode change) starts zeroed.

### 5.7 Hooks into other gaps

- **G15:** `ValidateTextureStageState` answers `D3DERR_CONFLICTINGTEXTUREPALETTE` for two P8 stages with different palettes until point-cast palettes are proven (§7 E4). A palettized texture whose palette is missing answers `D3DERR_WRONGTEXTUREFORMAT`.
- **G09:** a colour key on a P8 texture is a palette **index**. The FBI chroma key must be `palette[index]`, and with an alpha palette the 6-bit expanded value (PRS 11174's fix, `VH5/D6DP2.C:6880-6893`). `vcr_pal.h` exports `vcr_pal_sampled()` for it.
- **G26** (trilinear on both TMUs) loads one palette broadcast. **G50** (2 ppc) must include P8 in its probe matrix (unknown, inferred). **G51** (D3D SLI) must write palettes to every chip. **G47** (CMDFIFO) turns the load into four packet-4 groups like Glide's.

### 5.8 With the switch off

These are byte-identical to today:
- the texture list and every cap;
- `pf_kind`/`pf_tmfmt` for every format the runtime can create;
- placement and free;
- register traffic: no `nccTable0` write is reachable without `tex_p8`;
- `Dd_Blt` for every surface that exists.

What changes: SETPALETTE/UPDATEPALETTE with k = 1 are consumed as today (k ≥ 2 cannot occur without palettized textures), plus counters. `VcrDd3dStateLost` also clears an unused field.

## 8. Risks to proven paths

- **The default 16 bpp path:** none with the switch off (§5.8). The only always-on code is a parser that is identical for every stream XP can send today, plus counters.
- **With the switch on, titles change texture path.** Shogo and AvP, and possibly others (E5), move from 565/4444 to P8. A palette bug would then show in titles that render correctly today. That is why E3/E5 compare frames and why the recommendation is to **keep `D3DPal` opt-in** even after proof: nothing needs it.
- **Performance:** per-texture palettes (AvP's loader keeps one palette per image, inferred) cost about 50-100 µs per switch on the PIO transport. The counters and the A/B decide.
- **Glide/OpenGL coexistence:**
  - D3D overwrites the palette RAM; Glide titles download their own palette after open.
  - The only exposure is a Glide title that set a palette once, lost the chip, and resumed without reloading. On `.124` the P8 Glide users (Quake II, SiN) were switched to full-colour textures on 2026-10-02.
  - In the other direction, §5.6 drops our cache at every Glide acquire and release.
- **SLI:** D3D runs on chip 0 only; the palette writes go to chip 0. Glide's SLI broadcast is untouched.
- **Flip path:** untouched.
- **Memory:**
  - The palette store is at most 1 MB of paged pool, freed per process.
  - A wrong free of a skewed texture would corrupt DirectDraw's heap. It is pinned by test and reviewed explicitly.
- **Stability:** a load is 256 bounded register writes. Each one makes the chip drain its pipeline (Sync = Yes), which costs chip time but cannot wedge it. The CPU waits only through `VcrDdRoom`.

## 10. Open questions

1. Is §4.2 right on `.124`? It was read from the fleet image's runtimes, not `.124`'s system32 copies (hash them), and nothing has run yet. `p8_2stage_switch` plus the 513/P1 `kmax` field settle it.
2. Do point-cast (per-TMU) palettes work on Napalm? `TREX*` says yes, and Glide warns "will not work on future hardware". Only the DX7 probe (G75) or a point-cast glidelab build can show it.
3. Which titles create P8 when it is offered?
   - Strings: Shogo and AvP yes.
   - H&D and Halo name the formats only.
   - Rainbow Six's `CheckForPalettized` concerns its front and back buffers ("FrontBuffer SetPalette()"), not textures.
   - Thief Gold's "color (palettized)" is a particle property.
   - E0 and E5 measure it.
4. How many palettes does AvP keep, and how often does it switch per frame (the cap and the cost)?
5. Why did 3dfx drop A8P8 (PRS 13607)? `a8p8_decode1` decides for us.
6. Does XP's DirectDraw let a DX6 title attach a palette to a video-memory texture without `DDCAPS_PALETTE`? 3dfx's NT build shipped P8 without it (`VH5/DDINIT.C:64-82`), so this is inferred yes. The E3 counters show SETPALETTE arriving.
7. Does a D3D8 device Reset re-send SETPALETTE for re-created managed textures? §5.4's persistent association assumes it may not.
8. Should the 6666 decision also require that the alpha actually varies across the entries in use, not just across all 256 entries? This is a refinement only, if Shogo shows banding.
9. Does 2 ppc (G50) support P8 lookups? Add P8 to G50's matrix.
