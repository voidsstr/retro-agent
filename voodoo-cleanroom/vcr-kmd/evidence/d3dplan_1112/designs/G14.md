## 0. Verdict

- **The gap is real**, confirmed in code (section 1). Whenever stage 0 pairs `D3DTA_TFACTOR` with the texture,
  the HAL draws the iterated (diffuse) colour in TFACTOR's place, in RGB and in alpha. A TFACTOR alpha fade
  does not fade. No TMU stage can ever see TFACTOR.
- **D3D has no cap for TFACTOR.** Every DX6+ driver must support it, so games never check for it and never fall
  back (inferred from the D3D6+ caps model; nothing in `D3DPRIMCAPS`/`D3DDEVICEDESC7` names it). Each title that
  uses it is wrong today, with nothing to tell it so.
- **The fix splits into two parts:**
  - **Part A, stage 0 on the FBI (the common case).** It needs **no new register**. The FBI's legacy colour
    combine already has a constant *local* input: `color0`, selected by fbzColorPath[4] (`cc_localselect`) and
    [6:5] = 1 (`cca_localselect`). We write `c0 = 0` at every state flush and never select it. 3dfx's own
    legacy-combine D3D tables do exactly this for every "Texture + Factor" entry. It is about a day of work (S),
    and it may go default-on after one supervised boot.
  - **Part B, TFACTOR inside a TMU.** This covers TFACTOR at stage 1, and at stage 0 when two textures are bound
    and the op is not a MODULATE chain. It needs the extended combine (G12): each TMU's
    `chromaKey`/`chromaRange` holds the constant while that TMU's `combineMode[30]` is set. It lands with G12,
    under G12's switch, with a strict write order and a restore. A TFACTOR left in a TMU's `chromaRange` turns
    into **texture chroma substitution** as soon as that TMU's `combineMode[30]` is 0 again (section 4.3).
- **Single pass in every case.** A constant is a free input to all three combine units.
- **No caps change** for Part A or Part B. Widening TextureOpCaps (for example BLENDFACTORALPHA) is G12's work.
- **vendor-26 is already met by our architecture.** It asks that TFACTOR be re-uploaded after a FASTFILL. Here a
  clear marks the context dirty, and the whole state, `c1` included, is re-sent before the next triangle. This
  design pins that with a d3dprobe check and a source test, so a future register-shadowing change (G53) cannot
  silently lose it.

## 1. What the code does today (verified at `e3056d1`)

- **`ARG_KIND(a) = a & D3DTA_SELECTMASK`** (`KMD/display/vcrdd_d3d.c:671`). TFACTOR is kind 3. The COMPLEMENT
  and ALPHAREPLICATE modifiers are dropped (that is G13).
- **`color_path`** (`:676-745`) is stage 0's FBI combine on the legacy fbzColorPath:
  - **SELECTARG.** `SELECTARG1/2(TFACTOR)` selects `CP_RGBSEL_C1` / `CP_ASEL_C1` (`:693-694`, `:728-729`). This
    is **right**: `c1` holds TFACTOR.
  - **Two-argument ops** (`:698-717`, alpha `:733-740`). "other" is the texture if either argument is the
    texture, else TFACTOR (`c1`) if either is TFACTOR, else diffuse (`:699-700`). "local" is **always** the
    iterated colour, because `CP_LOCAL_C0`/`CP_ALOCAL_C0` are never set.
  - **The consequences:**
    - `MODULATE(TEXTURE, TFACTOR)` draws texture × diffuse.
    - `ADD(TEXTURE, TFACTOR)` draws texture + diffuse. With an FVF that has no diffuse, the vertex colour is
      0xffffffff (`KMD/display/vcrdd_3d.c:187`, D3D's own default), so this draws **white**.
    - The alpha op `MODULATE(TEXTURE, TFACTOR)` gives texA × diffuseA: the fade is lost.
    - `op(TFACTOR, DIFFUSE)` with no texture is **right**: TFACTOR is "other" (`c1`) and diffuse is "local".
- **`compute_regs`** writes `r->c0 = 0` and `r->c1 = TEXTUREFACTOR` (`:1019-1020`).
  - `CP_LOCAL_C0 (1u<<4)` and `CP_ALOCAL_C0 (1u<<5)` are defined (`KMD/include/vcr_3dregs.h:80-81`) and used
    nowhere.
  - The default TFACTOR is 0xffffffff (`ctx_defaults :1137`).
  - A TFACTOR change marks the context dirty (`set_rs :1402-1405`). The whole state is re-sent at the first
    triangle of every DP2 call and after any change (`prepare :1322-1365`).
- **Stage 1 has no TFACTOR path.**
  - `stage1_combine` (`:849-874`) maps only REPLACE/PASS/ADD/MULT onto the legacy `textureMode` TC fields.
  - Two stages need two textures (`two`, `:928`), so a texture-less "tint" stage 1 is dropped.
  - No TMU constant register is ever written. `combineMode` is written only by `Diag\Reset3D`, as 0
    (`KMD/include/vcr_3dseq.h:193`).
- **Clears.**
  - `VcrDd3dClear` writes `c1 = clear colour` (`KMD/display/vcrdd_3d.c:159`). The FASTFILL colour *is* `color1`
    (SPEC L3497).
  - Its own comment says the HAL re-sends state afterwards (`:133-135`). `clear_rects` sets `c->dirty = 1` and
    `w->prepared = 0` (`vcrdd_d3d.c:1419-1420`, "the clear rewrote fbzMode and c1").
- **`ValidateTextureStageState`** answers "1 pass, DD_OK" to everything (`:1905-1910`).
- **Logging.** `log_combo` (`:882-919`, event 513 what 21-23, LogLevel 2) logs stage 0's ops *and* arguments,
  so a TFACTOR argument shows as 3 (or 0x13/0x23 with a modifier). Stage 1's arguments are not logged.
- **The ring loses this evidence.** The on-box rings of 2026-11-12 contain no game combine lines: at LogLevel 3
  a game session overruns the 1024-entry ring many times (`onbox/README.md`). **No measurement exists of which
  staged title uses TFACTOR.**

## 2. What the hardware offers, and what 3dfx did

### 2.1 Where a constant colour lives on the VSA-100

| unit | constant registers | how a combine input selects it |
|---|---|---|
| FBI, legacy (`combineMode[31]=0`, our path) | `c0` 0x144, `c1` 0x148 (ARGB) | other: fbzColorPath[1:0]=2 → `c1` RGB, [3:2]=2 → `c1` A (SPEC L2735-2736). **local: fbzColorPath[4]=1 → `c0` RGB (L2737), [6:5]=1 → `c0` A (L2738).** Blend factor: `cc_mselect` 2/3 = a_other/a_local (L2742); `cca_mselect` 6 = color1 alpha (L2749) |
| FBI, extended (`combineMode[31]=1`) | the same `c0`/`c1` | `CC_OTHERSELECT` 2 = C1_RGB / 6 = C1_A; `CC_LOCALSELECT` 1 = C0_RGB / 4 = C0_A; `cc_mselect` 7 + `CC_MSELECT_7` 1 = C1_RGB / 3 = C1_A; `CCA_OTHERSELECT` 2, `CCA_LOCALSELECT` 1 (`GL5/incsrc/h3defs.h:387-462`; SPEC mux table L2826-2834) |
| each TMU (`combineMode[30]=1` in that TMU) | that TMU's `chromaKey` 0x134 and `chromaRange` 0x138; alpha in [31:24] | `TC_OTHERSELECT` 6 = CR_RGB / 7 = CR_A; `TC_LOCALSELECT` 6 = CK_RGB / 7 = CK_A; `tc_mselect` 7 + `TC_MSELECT_7` 6 = CR_RGB / 7 = CR_A; `TCA_OTHERSELECT` 3 = CR_A; `TCA_LOCALSELECT` 3 = CK_A; `tca_mselect` 7 = chromaRange alpha (`h3defs.h:468-545`, `:333-334`; SPEC L3839, L3847). A TMU's other/local/mselect_7 "always come from the combineMode register" (L2836) |

SPEC on the TMU constants:

- **Bit 30.** "When combineMode[30]=1, then the chromaRange register is used to store constant color values in
  the texture units ... The chip fields are used to store different constant color values into each texture
  unit" (L2825, L3534).
- **chromaKey.** It is "also used to store constant color values in the texture units" (L3522), and its
  [31:24] is "Constant Alpha (used by texture units only)" (L3528).
- **chromaRange [31:24]** reads "Constant Alpha" **only when `combineMode[30]=1`** (L3550-3551). With
  `combineMode[30]=0` the same bits are the range modes [27:24], the range enable [28] and **texture chroma
  substitution [30:29]=3** (L3540-3547; `h3defs.h:988-990` SST_ENCHROMARANGE / ENCHROMAKEY_TMU /
  ENCOLORSUBSTITUTION). Section 4.3 rests on this.
- **The spec contradicts itself here.** Its register table lists `chromaKey`/`chromaRange` with chip column
  "FBI" (L2316-2317), while §8.37/§8.38 and the change log ("Added description in chromaRange and chromaKey for
  specifying constant colors into the texture units", L6552) describe TMU copies. Both vendor code bases write
  TMU copies by chip field: Glide `grTexChromaRange` (`0x02 << tmu`, `GL5/glide3/src/gtex.c:3435`) and 3dfx's
  D3D (chip field 6, below). Part B follows the newer text. It is unproven on our silicon (section 13).
- **Chip fields.** Address bits [13:10] select the unit: 0x400 = FBI, 0x800 = TMU0, 0x1000 = TMU1,
  0x1800 = both TMUs (`h3defs.h:2087-2088` SST_CHIP; `GL5/glide3/src/fxcmd.h:584-587`).

### 2.2 What 3dfx's D3D did

- **Legacy combine (non-Napalm: Voodoo2/3, Banshee).** This is exactly Part A.
  - `singleStage_s0_colorOp` (`VH5/D6MT.C:1046`) puts TFACTOR on `c0` as the combine's **local** with
    `SST_LOCALSELECT` in every Texture/Factor entry: MODULATE "11 Texture + Factor" `:1120` and
    "14 Factor + Texture" `:1123`, ADD `:1143/1146`, SUBTRACT `:1166`, BLENDDIFFUSEALPHA `:1187`,
    BLENDTEXTUREALPHA `:1206`.
  - `singleStage_s0_alphaOp` (`:1270`) uses `SST_ALOCAL_C0`: MODULATE `:1344/1347`, ADD `:1367/1370`.
  - SELECTARG of Factor is `ZERO_OTHER | ADD_CLOCAL | LOCALSELECT` (`:1083-1086`).
  - `c0 = TFACTOR` is loaded by the non-Napalm branch of the TEXTUREFACTOR flush (`VH5/D6DP2.C:7029-7036`).
- **Napalm (extended combine everywhere).**
  - `combineMode = USE_COMBINE_MODE | DISABLE_CHROMA_SUBSTITUTION` on the FBI, T0 and T1 at every stage setup
    (`VH5/D6MT.C:4412-4414`, `:4454-4456`, `:4891-4893`).
  - The flush writes TFACTOR to **both TMUs' chromaKey and chromaRange (chip field 6)** and to **FBI c0 and c1**
    (`VH5/D6DP2.C:7014-7027`).
  - FBI tables: Factor = OTHER C1_RGB, LOCAL C0_RGB, M7 C1_RGB; alpha C1_A/C0_A (`CCU_mini_arg_c0_of_0` /
    `_a0_of_0`, `VH5/D6MT.C:603-636`).
  - TMU tables: Factor = OTHER CR_RGB, LOCAL CK_RGB, M7 CR_RGB; alpha CR_A/CK_A, `tca_mselect` MCR
    (`mini_arg_c0_of_0` ... `mini_arg_a1_of_0_to_1`, `VH5/D6MT.C:748-845`).
- **The TMU chroma registers are reserved for TFACTOR.** The texture colour key uses the FBI's `chromaKey`
  only: "Don't write the TMU chromakey (its used for texturefactor)" (`VH5/D6DP2.C:6943`, again at `:7131`,
  `:7173`, `:7243`).
- **When TFACTOR is re-uploaded:**
  - on a change (`VH5/D3RSTATE.C:2376-2382`);
  - after a colour FASTFILL (`VH5/D7DP2.C:745`, vendor-26);
  - on a context switch (`VH5/D6DP2.C:6375`);
  - after an SLI blit (`VH5/DDSLIBLT.C:2128`).

## 3. Part A — stage-0 TFACTOR on the FBI's legacy combine

### 3.1 The rule

The structure of `color_path` stays as it is. One rule is added to each two-argument branch, RGB and alpha:

- **the partner** is the argument that is not "other": `partner = (ARG_KIND(arg1) == other) ? ARG_KIND(arg2) : ARG_KIND(arg1)`.
- **If the partner is TFACTOR**, the combine's local becomes `c0`, and `c0` is loaded with TEXTUREFACTOR:
  - RGB: set `CP_LOCAL_C0` (fbzColorPath[4] = 1);
  - alpha: set `CP_ALOCAL_C0` (fbzColorPath[6:5] = 1);
  - in either case `r->c0 = TEXTUREFACTOR` (`c0`'s RGB feeds `c_local`, its [31:24] feeds `a_local`, SPEC L3489).
- **One conflict, resolved to "never worse than today".**
  - If the RGB op uses the alpha local as its blend factor (`CC_M_ALOCAL`, i.e. BLENDDIFFUSEALPHA), the alpha
    path keeps the iterated local, exactly as today. The context's conflict counter is incremented.
  - Switching it would make today's correct RGB factor wrong, to fix an alpha that is wrong today.
  - When it lands, G15 should report this pair (the helper's `conflict` output) as unsupported, unless Part B or
    G12 is armed.
- **Nothing else changes:**
  - the SELECTARG mapping (`c1`, already right);
  - the "no texture bound but an argument is TEXTURE" fallback (`:690`, `:725`);
  - the "other" choice;
  - BLEND* argument polarity (G12's: hal-09 `:708-713`);
  - every op that is drawn as MODULATE today (G12/G05). With a TFACTOR partner such an op now multiplies by
    TFACTOR instead of by diffuse. That is still the approximated op, now with the right operand.

| stage 0 combination | today | Part A |
|---|---|---|
| `SELECTARG1/2(TFACTOR)`, RGB or alpha | `c1` | unchanged (right) |
| `op(TFACTOR, DIFFUSE/CURRENT)`, no texture argument | `c1` × or + iterated | unchanged (right for MODULATE/ADD) |
| `op(TEXTURE, TFACTOR)` / `op(TFACTOR, TEXTURE)`, op ∈ {MODULATE, ADD, BLENDTEXTUREALPHA, BLENDDIFFUSEALPHA} | texture op **diffuse** | texture op **`c0` = TFACTOR**. Right, except for BLEND* with TFACTOR as arg1 (polarity, G12) |
| `op(TFACTOR, TFACTOR)` | TF op diffuse | TF op TF |
| ALPHAOP `MODULATE(TEXTURE, TFACTOR)` (the fade) | texA × diffuseA | **texA × TF.a** |
| the same, while COLOROP is BLENDDIFFUSEALPHA | texA × diffuseA | unchanged, counted as a conflict |
| two textures: stage 0 `MODULATE(TEXTURE, TFACTOR)`, stage 1 `MODULATE(TEXTURE, CURRENT)` (the TMU0 MULT path) | tex0·tex1·diffuse | **tex0·tex1·TF** (right) |
| two textures with a non-MODULATE stage-0 TFACTOR op, or any TFACTOR argument at stage 1, or a texture-less tint stage | wrong / dropped | unchanged; **counted** (Part B / G12) |

### 3.2 Registers

There is no new register and no new write. The 12-entry state flush (`VcrDd3dState`, `KMD/display/vcrdd_3d.c:74-129`,
room 12 at `:76`) writes the same eight FBI registers in the same order. Only two values change:

- `fbzColorPath` gains bit 4 and/or bits [6:5] = 1;
- `c0` becomes TEXTUREFACTOR instead of 0.

Both change **only** for combinations whose partner is TFACTOR. `c0` stays 0 everywhere else, so every other
combination writes byte-identical words. `c1` stays TEXTUREFACTOR, as today. Part A is chip-independent: the
Banshee/Voodoo3 legacy combine is the same, and 3dfx shipped this mapping for non-Napalm parts.

### 3.3 Code

- **New `KMD/include/vcr_d3dcomb.h`.** Win32-free and integer-only, like `vcr_3dseq.h`/`vcr_rtfmt.h`.
  - It holds today's `color_path` body as `vcr_cc_stage0(op, a1, a2, aop, b1, b2, tex, feat)`.
  - It returns `{ cp, c0_tfactor, tf_pair, conflict }`.
  - It defines the D3D values it needs as `VCR_D3DTOP_*`/`VCR_D3DTA_*`, with the numbers from `d3dtypes.h`
    (`DISABLE 1`, `SELECTARG1 2`, `SELECTARG2 3`, `MODULATE 4`, `ADD 7`, `BLENDDIFFUSEALPHA 12`,
    `BLENDTEXTUREALPHA 13`; `D3DTA_SELECTMASK 0xf`, `DIFFUSE 0`, `TEXTURE 2`, `TFACTOR 3`). A Python test pins
    them against the toolchain's header.
  - `feat & VCR_CC_TFACTOR_C0` arms the rule of 3.1. With 0, the function is today's `color_path`, word for word.
- **`KMD/display/vcrdd_d3d.c`:**
  - `color_path(c, tex)` becomes a thin wrapper that calls the helper. It keeps its name and signature, so the
    existing pin `r->fbzColorPath = color_path(c, tex) | CP_PARMADJUST;` (`tests/python/test_vcr_kmd_d3d.py:198`)
    still holds. It stores `c->c0_tf` and adds to the context's counters (section 6).
  - `compute_regs :1019` becomes `r->c0 = c->c0_tf ? c->rs[D3DRENDERSTATE_TEXTUREFACTOR] : 0;`. `:1020` is
    unchanged.
- **Switch plumbing:**
  - `KMD/miniport/vcrmp.c` reads `VcrDiagGet(L"D3DFeat", 0)` at boot, beside D3D32/D3DBigTex (`:238-244`).
  - It passes the switch to the display driver through `vcr_info` (`KMD/include/vcr_ioctl.h`). The preferred
    form is an **appended** `d3d_feat` field: appended fields are the struct's established extension, and a
    bit-field switch with a dozen planned bits would exhaust the 32 `VCR_INFO_F_*` flags. If `D3DFeat` already
    exists when this lands, take its next free bit.
  - `KMD/display/vcrdd_2d.c:442-470` copies it to `pd->d3d_feat` and logs the armed bits (a new 513 what code;
    see section 6).
  - Part A is armed on **every** chip, so the 86Box Voodoo3 bed can prove it before silicon.

### 3.4 Caps

Unchanged. Part A adds no op and no format; TFACTOR has no cap bit. ValidateTextureStageState is unchanged here
(that is G15).

## 4. Part B — TFACTOR inside the TMUs (lands with G12)

Part B is the **TFACTOR column of G12's extended-combine tables**, plus the loading discipline those tables need.
It is VSA-100 only. It is armed only together with G12's switch, because a TMU constant is unreadable without
`combineMode` selects.

### 4.1 Selects that G12's tables must use for a TFACTOR argument

| unit (stage) | TFACTOR as "other" | as "local" (subtract/add term) | as blend factor | alpha unit |
|---|---|---|---|---|
| FBI (single stage, or the last op) | `CC_OTHERSELECT_C1_RGB` (2) / `C1_A` (6) | `CC_LOCALSELECT_C0_RGB` (1) / `C0_A` (4) | `cc_mselect` = 7 + `CC_MSELECT_7_C1_RGB` (1) / `C1_A` (3) | `CCA_OTHERSELECT_C1_A` (2), `CCA_LOCALSELECT_C0_A` (1), `cca_mselect` 6 (`SST_CCA_MAC1`) |
| TMU1 (stage 0 with two textures), TMU0 (stage 1) | `TC_OTHERSELECT_CR_RGB` (6) / `CR_A` (7) | `TC_LOCALSELECT_CK_RGB` (6) / `CK_A` (7) | `tc_mselect` = 7 (`SST_TC_MCMSELECT7`) + `TC_MSELECT_7_CR_RGB` (6) / `CR_A` (7) | `TCA_OTHERSELECT_CR_A` (3), `TCA_LOCALSELECT_CK_A` (3), `tca_mselect` 7 (`SST_TCA_MCR`) |

- **Required bits.** Both TMUs' `combineMode` carry bit 30 (`DISABLE_CHROMA_SUBSTITUTION`) **whenever G12's
  extended combine is armed, used or not**. This is 3dfx's rule (`VH5/D6MT.C:4412-4414`).
- **The FBI.** Its `combineMode` bit 31 is G12's decision. Part A's legacy `c0` select then becomes the
  extended `CC_LOCALSELECT_C0_RGB` / `CCA_LOCALSELECT_C0_A`, with the same `c0` load.
- **Stage-1 cases that need this:**
  - `BLENDFACTORALPHA(TEXTURE, CURRENT)`: lerp the stage-1 texture over stage 0 by TF.a. TMU0 `tc_mselect` 7 +
    `CR_A`; both texture-alpha selects as G12's table has them. Only once G12 advertises BLENDFACTORALPHA
    (TextureOpCaps 0x2000).
  - `ADD(TEXTURE, TFACTOR)` at stage 0 under a stage-1 lightmap MODULATE. This must be done in TMU1, because
    folding it into the FBI gives (tex0·tex1)+TF instead of (tex0+TF)·tex1.
  - The texture-less tint stage `MODULATE(CURRENT, TFACTOR)`. This is G12's texture-less stage-1 work; the
    constant comes from here. If G12 folds that stage into the FBI, it is Part A's `c0`.

### 4.2 Loads and their order (`VcrDd3dState`, `KMD/display/vcrdd_3d.c:74-129`)

1. **G12's three combineModes first:** FBI (chip field 0 or 1, G12's choice), then TMU0 and TMU1, each with
   bit 30.
2. **Then the TMU constant, chip field 6 (both TMUs, never the FBI):**
   - `w3(pd, V3D_TMU0 + V3D_TMU1 + V3D_CHROMAKEY, tf)`
   - `w3(pd, V3D_TMU0 + V3D_TMU1 + V3D_CHROMARANGE, tf)`
3. **Then the FBI's `c0`/`c1`**, as today.

The flush's `VcrDdRoom` budget grows by 2 (plus G12's 3). The sequence is built by a new
`vcr_3d_tmuconst_seq()` in `KMD/include/vcr_3dseq.h`, so the host test can pin it write for write.

**Why this order.**

- If the flush is cut short after the combineModes, a TMU has bit 30 set over an old `chromaRange`. That is a
  harmless constant, and nothing draws, because a give-up clears `g2d_ok`.
- If it were cut short after the chroma writes, with the combineModes still old, a TMU would be left holding
  TFACTOR under `combineMode[30]=0`. That is the hazard in 4.3.

`V3D_CHROMARANGE 0x138` is new in `vcr_3dregs.h`; `V3D_CHROMAKEY 0x134` exists (`:32`). The offset test gains
both (section 9).

### 4.3 The hazard, and the restore

- **What a stale TFACTOR does.** `chromaRange[30:29] = 3` is texture chroma substitution whenever that TMU's
  `combineMode[30] = 0` (SPEC L3534, L3547). Those bits are TFACTOR's alpha bits 6:5. Any TFACTOR alpha in
  0x60-0x7f or 0xe0-0xff, **including the default 0xffffffff**, therefore reads as "substitution ON, range ON,
  all channels exclusive, union" (L3540-3547) once the TMU leaves the extended mode. What exactly the substitution
  then does is (inferred) a texel replacement around the key colour. Either way it is a misrender of the next
  client's textures.
- **Who could inherit it.**
  - **Our own legacy D3D path, while G12 is off.** It never writes `combineMode`, and the D3D path would not
    re-load a constant it does not use.
  - **A later Glide/OpenGL session.**
    - At its default state our h5 Glide writes TMU0's `chromaRange` from its own shadow only
      (`GL5/glide3/src/gsst.c:910-911`).
    - It also forces a 2ppc-off transition (`gsst.c:916-917`), which invalidates both TMUs' chroma state
      (`GL5/glide3/src/gtex.c:1015-1023`). Each TMU's chroma is then rewritten before that TMU is used
      (`distate.c:1568`, `:1655-1672`).
    - So the analysis says Glide cleans up after us. That is not proven on the box.
- **Restore** (defence in depth, VSA-100, Part B armed):
  - When: in `ctx_free` (`KMD/display/vcrdd_d3d.c:1210-1221`), after its `VcrDd2dSync`, only when this PDEV's
    flag `pd->tmu_const_live` is set and the engine is ours (`pd->g2d_ok && !pd->exclusive_pid`).
  - What: **chromaKey = chromaRange = 0 on both TMUs (chip field 6) first, then both TMU `combineMode` = 0**
    (`vcr_3d_tmuconst_off_seq()`, pinned).
  - Zero is Glide's own disabled value (`grTexChromaMode` DISABLE, `gtex.c:3322-3368`).
  - Other live contexts are not disturbed: every DP2 call re-sends the full state before its first triangle
    (`prepare`, `:1335-1363`).
- **Not restored:**
  - **At a Glide owner's acquire.** We may not touch the chip then. The residual risk is a D3D application still
    alive in the background when a Glide game takes the chip; the Glide analysis above covers it.
  - **By `Diag\Reset3D`.** It writes `combineMode = 0` but not the chroma registers (`vcr_3dseq.h:185-198`). If
    G03's D3D-owned baseline adds chroma writes, they must also follow "chroma before combineMode".

### 4.4 Chip-field ownership (coordination with G09)

The TMU `chromaKey`/`chromaRange` belong to TFACTOR. The texture colour key (G09) must use the **FBI's**
`chromaKey`/`chromaRange` through **chip field 1** (0x400), as 3dfx did (`VH5/D6DP2.C:6943`). Neither item may
write those offsets with chip field 0 (broadcast):

- a G09 broadcast key would overwrite both TMUs' TFACTOR;
- a G14 broadcast TFACTOR would put TF.a into the FBI's chroma-range enable [28] and the mode bits, and break
  G09's keying.

A source test pins this rule.

### 4.5 Interactions

- **2ppc (G50).** In 2ppc, "writes to either texture unit will be received by both" (L2838). TFACTOR is
  identical in both TMUs anyway. G50's bit 29 must be OR-ed into the same combineMode words, and its 12-NOP exit
  rule applies before bit 29 is cleared.
- **SLI (G51).** D3D draws on chip 0 only today. Under a future D3D SLI, broadcast plus chipMask ALL replicates
  the constant to every chip with no change.
- **CMDFIFO (G47).** The pair becomes one PK4 packet (chip field 6, mask R0|R1), as `VH5/D6DP2.C:7020-7022` does.
- **Vertex colour (G58).** TFACTOR in a TMU needs no iterated colour. A TMU stage that uses DIFFUSE does, and
  that is G58's trap.

## 5. Clears and other `c1` clobbers (vendor-26)

- **FASTFILL takes its colour from `color1`** (SPEC L3497). `VcrDd3dClear` writes it (`vcrdd_3d.c:159`), and
  `clear_rects` marks the state dirty (`vcrdd_d3d.c:1419`), so the next triangle re-sends `c1` (and, with Part A,
  `c0`). No change is needed.
- **The TMU constants (Part B) are not touched by FASTFILL.** The 2D engine and the texture flush (`VcrDd3dTexFlush`:
  texBaseAddr and nopCMD only) do not touch them either.
- **The rule this design pins for later work.**
  - Any future register shadowing (G53) must treat `c1` as clobbered by every 3D clear, and by any future
    DirectDraw use of the 3D fastfill (G61 DEPTHFILL).
  - It must treat `c0`, `c1` and the TMU constants as unknown after a Glide session, a mode set or an engine
    reset.
  - d3dprobe `tfactor_clear` and the source test in section 9 fail otherwise.

## 7. Gating

- **Part A: `Diag\D3DFeat` bit "TFACTOR"** (the plan's bit-field switch).
  - Allocate the next free bit when it lands. If `D3DFeat` does not exist yet, this item creates it: read at
    boot, a positive value, default 0, any chip.
  - **Off:** every register word is today's. This is pinned by an exhaustive native comparison against a
    verbatim copy of `color_path` (section 9).
  - **On:** only combinations with a TFACTOR partner change. Each of those is wrong today by construction,
    because the operand is replaced. Only `fbzColorPath` bits 4 and 5, and `c0`'s value, change. Every flush
    already writes both registers.
  - **It may go default-on** (absent = 1, 0 = off, as `Accel2DPattern` did) **after one supervised clean boot on
    `.124`** in which d3dprobe's `tfactor_*` pass and the default list is unchanged. That is a pure correctness
    fix proven by d3dprobe. Not before that boot.
- **Part B: under G12's extended-combine bit,** VSA-100 only, default OFF. It is never default-on before the
  attended coexistence check of section 10 (D3D TFACTOR → Quake III on our ICD/Glide → D3D).
- **The counters of section 6 have no switch.** They are logging only.

## 9. Regression tests

### 9.1 Native — `tests/native/test_vcr_kmd_d3dcomb.c` (new; TRUE-SOURCE of `KMD/include/vcr_d3dcomb.h`)

**`old_color_path()`** is a verbatim copy of `vcrdd_d3d.c:676-745` at `e3056d1`, written with the header's
constants. It follows the `old_target()` pattern of `test_vcr_kmd_d3dseq.c`.

1. **`off_is_the_old_colour_path_for_every_input`.**
   - The space is exhaustive: COLOROP and ALPHAOP 1..24; arguments
     {DIFFUSE, CURRENT, TEXTURE, TFACTOR, SPECULAR, and TEXTURE/TFACTOR with COMPLEMENT and ALPHAREPLICATE} for
     each of the four; `tex` ∈ {0,1}. That is about 15 M cases, about one second.
   - With `feat` 0: `cp == old_color_path()` and `c0_tfactor == 0`.
2. **`on_changes_only_tfactor_partners`.** Over the same space with the bit on:
   - if neither the RGB nor the alpha partner is TFACTOR, the result equals the old one;
   - otherwise it differs **only** in `CP_LOCAL_C0` / `CP_ALOCAL_C0`, and `c0_tfactor == 1`;
   - in the BLENDDIFFUSEALPHA case, `CP_ALOCAL_C0` is absent and `conflict == 1`.
3. **`the_fbi_model_draws_the_d3d_result`.** This is the first host test that *executes* the state→register
   translation (part of G77).
   - **The model.** A software model of the legacy FBI combine per SPEC §8.20:
     - selects from bits [1:0], [3:2], [4], [6:5];
     - `x = (zero_other ? 0 : other) - (sub_clocal ? local : 0)`;
     - `f = reverse ? m : 255 - m`, `x = x*(f+1) >> 8`;
     - `+ local` or `+ alocal`, then clamp, then invert.
     - The 8-bit rounding is inferred from the Voodoo spec and 86Box, not measured; tolerance ±2.
   - **The comparison.** A D3D reference for the seven advertised ops, with inputs iterated = 0x00ff00 / A 0xff,
     texel = 0xff0000 / A 0xff, TF = 0x808080 / A 0x80. Assert the fixed **and** the old value:
     - `MODULATE(TEXTURE, TFACTOR)`: fixed **0x800000**, old **0x000000**;
     - the same with arguments swapped: the same values;
     - alpha `MODULATE(TEXTURE, TFACTOR)`: fixed **0x80**, old **0xff**;
     - `ADD(TEXTURE, TFACTOR)` with iterated 0x000000 and TF 0x004000: fixed **0xff4000**, old **0xff0000**;
     - `BLENDTEXTUREALPHA(TEXTURE, TFACTOR)` with texA 0x80 and TF 0x0000ff: fixed **0x80007f**, old **0x807f00**.
4. **`c0_is_tfactor_only_when_selected`.** `compute_regs`' rule: `c0 = TF` iff the helper set `c0_tfactor`;
   `c1 = TF` always.
5. **Part B, when it lands: `the_tmu_constant_is_tmus_only_after_bit30` and `the_way_back_zeroes_chroma_first`.**
   - `vcr_3d_tmuconst_seq` emits exactly `{0x1934, tf}, {0x1938, tf}` (chip field 6). Neither offset is ever
     emitted with chip field 0 or 1.
   - The off sequence emits the two zero writes **before** the TMU `combineMode` writes.
   - The old-buggy order, chroma after combineMode, is asserted to be refused by an order check.

## 11. Risk to proven paths

- **The default 16 bpp path.**
  - Bit off: no change. The exhaustive native test compares every input against the old function.
  - Bit on: changes only TFACTOR-partner combinations. None of the 40/40 default probe tests uses TFACTOR.
  - The refactor of `color_path` into a header is itself guarded by the same test.
- **Glide/OpenGL coexistence.**
  - Part A: none new. `c0`/`fbzColorPath` are FBI state that Glide rewrites at its default state
    (`grConstantColorValue`, `gsst.c:912`) and at every validation.
  - Part B: the stale-chromaRange hazard of 4.3, mitigated by the write order, the `ctx_free` restore and the
    Glide invalidation analysis, and to be proven by step 5.
- **SLI.** None. D3D is chip 0 only, and Part B's chip-field writes stay inside chip 0's TMUs.
- **The flip path and DirectDraw.** None. FASTFILL's `c1` handling is unchanged and now pinned.
- **Performance.**
  - Part A: zero extra writes. Part B: +2 PIO writes per state flush.
  - The counters cost one compare per triangle and add no logging on the draw path.
- **The trap to remember.** A TFACTOR-heavy title changes TFACTOR per object, and each change is a full state
  flush, as with any state change today (G53).

## 13. Open questions

1. Which staged titles actually pair TFACTOR with a texture at stage 0, or use it at stage 1? Section 6's
   counters and event 25 settle this. Today it is unmeasured: the rings wrapped.
2. Is Halo's "glow drawn as a translucent square" (`onbox` run #17 at 60 s, G17) a
   `MODULATE(TEXTURE|ALPHAREPLICATE, TFACTOR)` drawn as texture RGB × diffuse? If so, G13 + G14 Part A fix it on
   the legacy path: `c1` × texture alpha via `CC_M_ATMU` is expressible without combineMode.
3. Is UE2's solid-white sky/horizon (G18) an `ADD(TEXTURE, TFACTOR)` in a vertex format without diffuse? That
   would draw texture + 0xffffffff = white today. Event 22's arguments for those draws answer it.
4. Does VSA-100 silicon honour fbzColorPath[4] and [6:5] = 1 with `combineMode[31]=0` exactly as the
   Banshee/Voodoo3 do? The SPEC says yes (L2737-2738), 86Box reproduces the Voodoo3, and 3dfx shipped it for
   non-Napalm parts. Boot 2 of section 10 is the proof.
5. The SPEC's register table puts `chromaKey`/`chromaRange` on the FBI only (L2316-2317), against §8.37/§8.38,
   L6552 and both vendor code bases. Part B relies on the TMU copies. G12's first probe run proves or refutes
   them.
6. What exactly does a TMU do with `chromaRange[30:29]=3` under `combineMode[30]=0`: substitute with black, or
   with something else? It matters only if the restore of 4.3 fails; step 5 observes it.
7. Should Part A also fix BLEND* argument polarity, which today is right only with TEXTURE as arg1? G12 owns it
   (hal-09 `:708-713`). The fix (clear `CP_CC_REVERSE` when "other" is arg2) applies to diffuse partners too, so
   it is not folded in here.
8. The `D3DFeat` bit number: coordinate with G08, G16, G22, G25 and G12's designs (`reports/hal.md` §10 numbers
   Phase 2 as bits 0-5 and Phase 3 as bits 6+, but Part A is in neither list).
9. Should G12's texture-less tint stage (`MODULATE(CURRENT, TFACTOR)` with no stage-1 texture) be folded into the
   FBI with Part A's `c0` when stage 0 leaves the local input free? This is cheaper than a TMU pass-through stage,
   and is G12's decision.
