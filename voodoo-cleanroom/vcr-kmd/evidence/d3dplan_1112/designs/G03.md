# G03: a Direct3D-owned 3D baseline (`Diag\D3DSafe` bit 1)

**Gap.** The HAL relies on 3D state that Glide leaves behind. combineMode, the
2PPC exit, clip rect 1, chroma, stipple, aaCtrl and (at 16 bpp) stencil are never
written. `Diag\Reset3D` is default off, has never run on silicon, and cannot cover
a killed client.

**Lane:** clean-room (`vcr-kmd`, `vcrdd.dll` D3D HAL). This is a design only:
nothing was built, deployed or run, and no box was contacted.

**Sources read:**
- the reports hal-02 (`reports/hal.md` R2), history-26/27 (`reports/history.md`
  §3.1 and §7), hw-39/41 (`reports/hw.md` §5 item 3 and §6 S2) and visual-05
  (`reports/visual.md` V-05);
- the HAL (`KMD/display/vcrdd_3d.c`, `vcrdd_d3d.c`, `vcrdd_2d.c`, `vcrdd.c`,
  `vcrdd_escape.c`; `KMD/include/vcr_3dseq.h`, `vcr_3dregs.h`, `vcr_rtfmt.h`,
  `vcr_ioctl.h`; `KMD/miniport/vcrmp.c`, `vcrmp_hw.c`);
- the vendor HAL (`VH5/D6DP2.C`, `HWCEXT.C`, `DDFXNT.C`);
- 3dfx's C simulator (`.../H5/CSIM/GO.C`);
- our h5 Glide (`GL5/glide3/src/gtex.c`, `distate.c`, `gglide.c`, `gsst.c`,
  `diget.c`, `minihwc/minihwc.c`);
- our MesaFX ICD (`build/retro3dfx-gl/src/mesa/drivers/glide/fxapi.c`,
  `fxsetup.h`, `fxsetup.c`, `fxdd.c`);
- the VSA-100 register spec (SPEC).

**SPEC line numbers.** Lines `Lnnnn` are lines of

**Marks.** "(inferred)" marks what comes from reasoning, not from a file or a

## 0. Verdict

**The gap is real and fixable.** It is a single-pass correctness fix with no
caps change. Reading the spec and the code changes the picture in four ways:

1. **It is worse than the gap says for the TMUs.**
   - The spec says that for the texture combine units, *"the 'other', 'local'
     and 'mselect_7' ... always come from the combineMode register"* (SPEC §8.21,
     L2836). This holds whatever bit 31 says.
   - The HAL's legacy TMU combine (`TM_TC_REPLACE/MULT/ADD/PASS`,
     `vcr_3dregs.h:164-175`) therefore reads whatever inputs the last
     combineMode chose.
   - Our MesaFX ICD on `.124` programs its combines through Glide's COMBINE
     extension:
     - `diget.c` `NAPALM_EXT_STR` carries `COMBINE`;
     - `fxapi.c:575` sets `HaveCmbExt`;
     - `fxsetup.h:574-606, 637-700, 828-838` call
       `grColorCombineExt`/`grTexColorCombineExt`.

     The one legacy call is `fx_sh_grTexCombine` in the TMU1-source path
     (`fxsetup.h:665`).
   - A clean Glide close clears only combineMode bit 29 (`gsst.c:3295-3303`;
     `gtex.c:986-1092` `_grTex2ppc`).
   - So after **any OpenGL title**, the FBI and both TMUs keep MesaFX's last
     extended combine. The next D3D context draws through it.
   - Whether that combine is harmless depends on what the GL title drew last
     (inferred). That would explain why visual-05 is "correlation only".
2. **The fix as listed would arm a trap.**
   - Texture chroma substitution switches on when TMU
     `chromaRange[30:29] = 3` and TMU `combineMode[30] = 0` (SPEC L2825, L3534).
   - While Glide uses a TMU constant colour it sets `combineMode[30]`
     (`gtex.c:1931-1932`), and the TMU chroma registers then hold that constant
     colour (`distate.c:1656-1666`).
   - Writing combineMode = 0 alone clears bit 30. That re-arms substitution from
     the constant colour's alpha bits 6:5.
   - So the baseline must write **TMU chromaRange = 0 (chip field TMU0|TMU1)
     before combineMode = 0**.
3. **Two items on the list are not live hazards today.** They are written or
   pinned anyway, at no risk:
   - **Clip rect 1** acts only with `clipLeftRight1[31]` (secondary-rect mode) or
     with `renderMode[21]` (guard band) (SPEC §8.45 L3624-3642; CSIM
     `GO.C:64-86, 132-145`).
     - Glide's clip1 value never has bit 31 set (`gglide.c:3349-3357`).
     - The HAL writes renderMode in full with bit 21 = 0
       (`vcr_rt_rendermode`, `vcr_rtfmt.h:174-177`).
   - **Stipple and FBI chroma** act only through `fbzMode[2]` and `fbzMode[1]`.
     The HAL writes fbzMode in full and never sets either bit
     (`vcrdd_d3d.c:978-986`).
4. **Correction to hal-02.** "combineMode, aaCtrl and chipMask read 0, so they
   were not today's cause" does not hold.
   - All three (and sliCtrl, chromaKey and chromaRange) are **write-only**
     (SPEC register table L2316-2317, L2344-2347).
   - *"Reading from a register which is 'write only' returns undefined data"*
     (L2225).
   - The 11-12 dump therefore neither convicts nor acquits them. Only
     stencilMode/stencilOp (R/W, L2334-2335) and clip1 (R/W, L2342-2343) can be
     checked by reading, and clip1 was not read.

**The fix.** When `Diag\D3DSafe` bit 1 is set, every DrawPrimitives2/Clear2 call
that draws writes a fixed 22-write sequence before its first target write. The
sequence sets every 3D register the D3D path depends on but never writes to the
value the legacy path assumes. It is VSA-100 only and pinned write-for-write in
`vcr_3dseq.h`. 3dfx's own HAL does more than this: it writes all three
combineModes at every hardware-state flush (`VH5/D6DP2.C:6404-6452`), and stencil
"disable" at every depth (`D6DP2.C:5459-5469, 6107-6129`).

## 2. The design

### 2.1 The sequence (`KMD/include/vcr_3dseq.h`, new `vcr_3d_d3d_baseline_seq`)

Win32-free, like `vcr_3d_glide_reset_seq`, so the host test compiles the writes
the driver makes.

New offsets go into `vcr_3dregs.h`:
- `V3D_CHROMARANGE 0x138`;
- `V3D_CLIPLEFTRIGHT1 0x200`;
- `V3D_CLIPBOTTOMTOP1 0x204`;
- `V3D_TMU01 0x1800` (chip field TMU0|TMU1 = 0x6 << 10). This is the field
  `vcrdd_3d.c:111` already writes nopCMD to before every DXT state, which
  silicon has proven.

```c
#define VCR_3D_BASE_MAX 22
static __inline unsigned vcr_3d_d3d_baseline_seq(unsigned napalm, vcr_regw *w)
{
    unsigned n = 0, i;
    if (!napalm)                                  /* Banshee/Voodoo3: reserved registers */
        return 0;
    w[n].off = V3D_CHIPMASK;   w[n++].val = VCR_3D_CHIPMASK_ALL;   /* 1: chip 0 takes the rest */
    w[n].off = V3D_SLICTRL;    w[n++].val = 0;                     /* 2: behind the mask, as Reset3D */
    for (i = 0; i < VCR_3D_RESET_NOPS; i++) {                      /* 3-14: the 2PPC exit (L2840) */
        w[n].off = V3D_TMU01 + V3D_NOPCMD; w[n++].val = 0;         /*   TMUs only, not the FBI */
    }
    w[n].off = V3D_TMU01 + V3D_CHROMARANGE; w[n++].val = 0;        /* 15: no TMU substitution ... */
    w[n].off = V3D_COMBINEMODE; w[n++].val = 0;                    /* 16: ... before bit 30 clears */
    w[n].off = V3D_AACTRL;      w[n++].val = 0;                    /* 17 */
    w[n].off = V3D_STENCILMODE; w[n++].val = 0;                    /* 18: every depth */
    w[n].off = V3D_STENCILOP;   w[n++].val = 0;                    /* 19 */
    w[n].off = V3D_CHROMARANGE; w[n++].val = 0;                    /* 20: FBI range enable off */
    w[n].off = V3D_CLIPLEFTRIGHT1; w[n++].val = 0;                 /* 21: rect 1 off */
    w[n].off = V3D_CLIPBOTTOMTOP1; w[n++].val = 0;                 /* 22 */
    return n;
}
```

**Never written:**
- renderMode, the buffers and the clip (the target's);
- fbz*, alpha, fog, c0/c1 and the TMU texture registers (the state's);
- any non-zero sliCtrl, which stays the miniport's.

**Why it differs from Reset3D's 18 writes:**
- The NOPs go to the TMUs only, as the spec and the vendor do (`D6DP2.C:6420-6428`,
  chip field 0x6). Reset3D sends them broadcast, which flushes the whole pixel
  pipeline 12 times. That is fine once at a release, wasteful on every call.
- It adds the TMU and FBI chromaRange and clip1 writes.

### 2.2 Where it runs (`KMD/display/vcrdd_d3d.c`)

- `dp2walk` (`:1244`) gains `int based;`. DP2 and Clear2 already `memset` the
  walk at entry (`:1835`, `:1882`), so it starts at 0 on every call.
- A new helper `baseline(w)`:
  - returns TRUE at once if `w->based || !w->c->pd->d3d_base`;
  - otherwise sets `based = 1` and calls `VcrDd3dBaseline(pd)`;
  - counts it in a new `c->baselines`.
- It is called in two places, and these cover every 3D register write the HAL
  makes:
  - **`prepare()`** (`:1322`): right after `if (!w->drawable) return FALSE;`.
    That is before `flush_written` (`:1331`, which writes texBaseAddr and
    nopCMD) and before `VcrDd3dTarget`/`VcrDd3dState` (`:1361`). If the
    baseline fails, prepare returns FALSE, the path the HAL already has for a
    failed state write.
  - **`clear_rects()`** (`:1408`): after the `!w->drawable || !what` return and
    before `VcrDd3dTarget` (`:1416`). This also covers Clear2 and DP2's CLEAR op.
- **Once per DP2/Clear2 call that draws.** No foreign writer can run inside one
  call: the DDI holds the display lock, and while an exclusive owner exists
  `drawable` is 0.
- A call that never draws (state-only DP2, `!drawable`) writes nothing.

### 2.3 The writer (`KMD/display/vcrdd_3d.c`, new `VcrDd3dBaseline`)

- It uses Reset3D's proven chunking: `(i & 7) == 0 && !VcrDdRoom(pd, n - i < 8 ? n - i : 8)`.
  - So the request never exceeds 8 free entries. `g2d_fifo_full` is learned,
    not assumed, and asking for 22 at once could spin into a give-up on a FIFO
    that reports fewer.
  - That is 3 status reads.
- Then `w3()` each write and set `pd->g2d_busy = 1`.
- No idle pre-check: unlike Reset3D at a release, this runs on a chip the HAL is
  about to draw on anyway, with the same transport and the same give-up path
  (G02).

### 2.4 Evidence: residue read, log-only, same bit (optional; can be dropped without changing the fix)

At the **first** baseline of each context:
1. `VcrDd2dSync(pd)`.
2. Read the R/W FBI registers: renderMode, fbzMode, stencilMode, stencilOp,
   clipLeftRight1 and clipBottomTop1. That is 6 reads, about 6 µs, once per
   context.
3. Then write the baseline.
4. Log 513/25 at WARN once per context when any shows foreign state:
   - stencil enable or wmask non-zero;
   - clip1 non-zero;
   - renderMode bit 21 (our Glide's default guard band, `gsst.c:4177-4179`; the
     HAL writes it 0) or bit 25;
   - fbzMode bits 1, 2 or 12.

This is the field evidence for hw-41 S2 and for which titles leave what. The
write-only registers cannot be read, so for them rendering is the only evidence.

### 2.5 The switch

- **Miniport** (`KMD/miniport/vcrmp.c:239-244`): `x->d3dsafe = VcrDiagGet(L"D3DSafe", 0);`
  - Read at boot, like D3D32 and D3DBigTex: the HAL a fullscreen PDEV offers
    must match the desktop's.
  - `v->flags |= (x->d3dsafe & 2) ? VCR_INFO_F_D3DBASE : 0`.
- **`include/vcr_ioctl.h`**: `VCR_INFO_F_D3DBASE 0x10000`. This proposes
  `0x8000 << bit` for D3DSafe bits 0-3: bit 0 (G01) = 0x8000, bit 1 = 0x10000,
  bit 2 (G02) = 0x20000, bit 3 (G10) = 0x40000. It is a positive flag, so an
  older miniport never arms it.
- **Display** (`KMD/display/vcrdd_2d.c:454` area):
  - `pd->d3d_base = pd->napalm && (info.flags & VCR_INFO_F_D3DBASE) ? 1 : 0;`
  - when armed, the INFO event 513/24 "armed (Diag\D3DSafe): D3D baseline ON".
- The context-gone event (513/2, `vcrdd_d3d.c:1212`) adds "%u baselines" to its
  text.
- `vcr_events.h` 513 gains what 24 and 25. The next free code today is 24 (1-23
  are used); coordinate with G01, G02, G10 and the Phase 0 counters.

### 2.6 Caps, passes, the old path

- **Caps:** nothing changes. **Single pass.**
- **Old path (bit 1 clear, the default):**
  - `baseline()` returns at its first test, no reads, `based` unused;
  - register traffic is **byte-for-byte the proven sequence**: Voodoo3 6 target
    writes, VSA-100 16 bpp 7, plus the 12 state writes;
  - pinned by the native model below.
- **Banshee/Voodoo3:** a no-op even when set (`napalm` 0, so the sequence is
  empty).

### 2.7 Cost (inferred; measured in §5)

- Per call: 22 posted writes at about 45-150 ns, plus 3 status reads at about
  1 µs, so **about 4-6 µs per drawing DP2/Clear2 call** (perf report §4.1 cost
  model).
- The sync registers among them (chipMask, sliCtrl, aaCtrl, stencil, clip1,
  chromaRange: "Yes" in L2316-2347) drain the pipeline. `prepare()` already
  causes that drain at every call through renderMode, the buffer addresses and
  the clip, so there is no new serialisation.
- Measured DP2 rates:

  | title | DP2 calls / frame (from the 11-12 counts) | baseline cost / frame |
  |---|---|---|
  | UT2004 | ~35 (26145 over ~750 frames) | ~0.2 ms (~1%) |
  | Halo | ~4 | negligible |
  | DX5 execute-buffer titles (JK, MotS) | **unmeasured** | open question 6 |

- The vendor writes more: three combineModes at every state change, not once
  per call.

### 2.8 Relation to existing switches and later gaps

- **Reset3D:** the baseline does everything Reset3D does, at the point of use.
  It also covers killed clients and display-reset ends, which Reset3D cannot
  (`vcrdd.c:592-603`).
  - Once bit 1 is default-on, Reset3D is redundant for D3D. Propose retiring it
    then; the README row and `test_the_glide_release_reset_is_exactly_this`
    change.
- **SliOffAaCtrl:** stays relevant for the **slave** chips, which only matter to
  G51. The baseline touches chip 0 only.
- **G41 (fog cache):** the one residue a per-call rewrite of uncached registers
  cannot reach. Land G41 alongside (CPU-only, default-on).
- **The baseline becomes "D3D owns these registers" for later work:**

  | later gap | what changes in the baseline |
  |---|---|
  | G05/G12/G13/G14 (extended combine) | write combineMode per state after it |
  | G14 (TFACTOR) | rewrites the TMU chromaRange (combineMode[30] = 1) |
  | G50 (2PPC) | the NOPs become "only when leaving 2PPC", as the vendor's WINNT branch does (`D6DP2.C:6409-6416`) |
  | G09 (colour key) | takes chromaKey/chromaRange ownership |
  | G57 (guard band) | writes clip1 = viewport |
  | **G51 (D3D SLI)** | **must** replace sliCtrl = 0 and chipMask = ALL with D3D's own SLI values. A comment and a test name this |

### 2.9 Follow-up, only if §5 measures a cost: a generation gate

- Write the baseline only when `pd->base_gen != pd->foreign_gen`.
- Bump `foreign_gen` at:
  - PDEV creation (it starts "unknown");
  - HWCSETEXCLUSIVE and HWCRLSEXCLUSIVE;
  - DrvAssertMode (both directions);
  - every register-touching escape/IOCTL path.
- A hardware variant: one renderMode read per call, where bit 21 set means
  Glide wrote it last.
- Keep the per-call path as the reference. Ownership living in the PDEV is lost
  across a PDEV swap (`FINDINGS.md:93-97`), which is why per-call is the first
  design.

## 3. Gating

- **`Diag\D3DSafe` bit 1, default OFF** (absent = 0). VSA-100 only. Read at
  boot; arm with REGWRITE, read back, then `safe-reboot.py`.
  `test_vcr_kmd_integration.py` `NEW_DIAG` gains `"D3DSafe": "0"`.
- **When off, the proven path is byte-for-byte unchanged.**
- **Default-on is justified after one supervised clean boot** (§5, boot 2), not
  at landing. All of these must hold:
  - the no-harm gate passes: default d3dprobe matrix at 16 and 32 bpp, windowed,
    perf within noise;
  - the residue A/B passes;
  - one game A/B passes.

  The values are the clean or power-on state (chipMask all 1s L3449-3456,
  aaCtrl 0 L3433-3440, renderMode 0 L3288), and the vendor ran stricter traffic
  on every flush.
- **The flip:** the miniport resolves "absent ⇒ default bits" with bit 1 in the
  default. That needs a `MOVED_DIAG` entry and a README note that an explicit
  D3DSafe value replaces the defaults (write e.g. 3 to arm bit 0 too).
  Alternative: open question 9.

## 4. Tests

### 4.1 Native: `tests/native/test_vcr_kmd_d3dseq.c` (extend; compiles `vcr_3dseq.h`)

1. **`the_d3d_baseline_is_exactly_this`**
   - n == 22 == `VCR_3D_BASE_MAX`.
   - The order and values are those of §2.1.
   - The NOPs and the TMU chromaRange use chip field `0x1800`: TMU0|TMU1, **not**
     broadcast (asserts the difference from Reset3D's `0x120`).
   - Everything else uses chip field 0.
   - chipMask comes first and equals 0xFFFFFFFF (not 4a9793b's 1).
   - sliCtrl comes only directly behind chipMask, and its value is 0.
   - All 12 NOPs precede combineMode, and the TMU chromaRange precedes
     combineMode.
   - No renderMode, colBuffer*, auxBuffer*, fbz*, alpha, fog or texture
     register; every offset is inside the 3D block.
2. **`the_baseline_is_nothing_on_a_banshee_or_voodoo3`**: napalm = 0 gives 0
   writes.
3. **`glide_residue_survives_the_proven_sequence_and_not_the_baseline`**
   (register-file model, the old-buggy and fixed values side by side).
   - **The model:** a 3-unit register file (FBI, TMU0, TMU1) with chip-field
     routing:
     - field 0 → all three units;
     - bit 0 → FBI;
     - bit 1 → TMU0;
     - bit 2 → TMU1;
     - chipMask always taken; any other write dropped while `chipMask & 1 == 0`.
   - **Seeded residue:**
     - FBI combineMode `0x8000_00c9`;
     - TMU0/TMU1 combineMode `0x4000_0124` (bit 30 + selects);
     - TMU chromaRange `0xffffffff`;
     - stencilMode `0x01ffff00` (enable, func NEVER, wmask ff, mask ff: what
       glidelab's stencil class writes);
     - aaCtrl `0x1000_0011` (AA enable + offsets);
     - sliCtrl `0x0500_0301` (SLI on);
     - chipMask `0x2` (chip 0 masked out);
     - clip1 `0x8000_0100`.
   - **Old-buggy:** apply the proven first-prepare at 16 bpp (`old_target()`'s
     7 writes + the 12 state writes). The test asserts:
     - colBufferAddr did **not** land (chip 0 masked out: nothing drawn);
     - FBI bit 31, the TMU selects, the 16 bpp stencil enable, AA enable and
       SLI enable all remain.
   - **Fixed:** apply baseline + the same writes. The test asserts:
     - every predicate is clear;
     - TMU chroma substitution is off (`(chromaRange>>29 & 3) == 3 && !(combineMode & 1<<30)` false);
     - the target registers landed.
4. **`a_baseline_without_the_tmu_chroma_write_arms_substitution`**: the gap's
   literal list (combineMode = 0, FBI chroma off) applied to `{TMU combineMode
   bit 30, TMU chromaRange 0xffffffff}`. The predicate is **true** before our
   fix and false with our sequence.
5. **`two_ppc_is_never_cleared_without_twelve_tmu_nops`**: the model counts TMU
   nopCMDs since 2PPC was last seen on. A sequence with combineMode before the
   NOPs is flagged; ours is not.
6. **`the_off_path_is_the_proven_sequence`**: with `d3d_base = 0` the modelled
   first prepare equals `old_target()` + state, write for write.

### 4.3 d3dprobe: new explicit test `residue` (`KMD/tools/d3dprobe.c`, `--tests residue`)

**What it draws:** one frame in the 256x256 readback window. Clear colour
`0x000040`, Z = 1. It is analytic like every d3dprobe test, and each check is
named after the residue class that would break it.

| check | what is drawn | expected (16 bpp tol 12, 32 bpp tol 8) | fails under |
|---|---|---|---|
| `fbi combine` | untextured flat quad, diffuse `0x40a0e0`, ZFUNC ALWAYS | `40a0e0` | FBI combineMode bit 31 / outshift |
| `tmu0 white/red/green/grey` | 64x64 R5G6B5, four 32x32 cells (`ffffff`, `ff0000`, `00ff00`, `808080`), MODULATE × white, point sampling, 1:1 | each cell's texel | TMU selects; TMU chroma substitution (any channel ≠ ff gets keyed under the hostile key); 2PPC |
| `tmu1 two-stage` | stage 0 solid red, stage 1 MODULATE × solid grey `808080` | ≈`800000` (tol 16) | TMU1 combineMode; 2PPC (TMU1 = TMU0: ≈`404040`) |
| `depth pass` / `depth reject` | yellow quad, z 0.25, LESSEQUAL with Z write; then magenta, z 0.75, LESSEQUAL, overlapping | yellow, then still yellow | a stale stencil honoured at 16 bpp (nothing draws); a broken Z |
| `row y` ×24 | green band x 8..248, y 160..167; sampled at x 16/128/240 on each row | `00ff00` | SLI residue (missing bands); aaCtrl bit 30 |
| `cover` ×5 | second frame: one quad over the whole window (-0.5..255.5) | 4 corners + centre drawn | aaCtrl primary offset (a shifted edge); an enabled clip1 |

**Pass criterion:** 0 failed checks, against the computed values above.

- On a clean chip it must pass at 16 and 32 bpp. This is its control; if it
  fails there, the test is wrong.
- After a hostile residue with bit 1 **off**, the class's named checks must
  fail. That is the negative control, proving the test can fail.
- After the same residue with bit 1 **on**: 0 failures.

### 4.4 The residue generator: `glidelab residue` (`KMD/tools/glidelab.c` + `glidelab_run.py`)

d3dprobe is D3D8 and cannot create Glide state, so this new mode does it
deterministically. It is safer and more conclusive than replaying GLQuake, whose
last combine is whatever its last frame drew.

```
glidelab residue --cfg 0 --res 640x480 --bpp 32 --leave fbi|tmu|tmuconst|stencil|all --close clean [--pace 5000]
```

**Setup:** cfg 0 (one chip: no SLI, no AA). It opens with a 24/8 aux buffer for
the stencil class.

**What each class leaves:**

| class | Glide calls |
|---|---|
| fbi | `grColorCombineExt` / `grAlphaCombineExt` with all-ZERO inputs, so the FBI outputs 0 |
| tmu | `grTexColorCombineExt` / `grTexAlphaCombineExt` with ZERO on both TMUs |
| tmuconst | `grConstantColorValueExt(TMU0/TMU1, 0xffffffff)` with a TCCU input of the TMU constant colour (`gtex.c:1931` sets bit 30) |
| stencil | `grEnable(GR_STENCIL_MODE_EXT)`, `grStencilFuncExt(GR_CMP_NEVER, 0, 0xff)`, `grStencilMaskExt(0xff)`, `grStencilOpExt(REPLACE ×3)` |

**The run:**
1. Draw one triangle; Glide validates its state lazily, so this writes the
   registers.
2. `grFinish`.
3. Hold the mode for the pace.
4. **Close cleanly.** The clean close turns the FIFO off, which keeps G01 out of
   the experiment.

`--close abandon` (2PPC, chipMask and AA residue) is allowed only after G01
lands. The RESULT names the classes left.

**Runner** (new `KMD/tools/residue_ab.py`, evidence to
`KMD/evidence/d3d_residue_<date>/`). Each step is paced at ≥5 s:
1. `vcrctl reg 0x80024` (cmdFifo0 off, or stop: G01).
2. `vcrctl reg` of the R/W registers 0x2001e0, 0x200110, 0x2001e4, 0x2001e8,
   0x200200, 0x200204.
3. `d3dprobe render --full --res 640x480 --bpp 16 --tests residue` (control).
4. `glidelab residue --leave <class>`.
5. The two `vcrctl reg` reads again. This is the post-condition that the residue
   is really there: after the stencil class, stencilMode should read
   `0x01ffff00` (Glide: func NEVER = 0 << 25, mask ff << 8, wmask ff << 16,
   ENABLE).
6. `d3dprobe residue` at 16 bpp, then at 32 bpp.
7. The `vcrctl reg` reads again (after a bit-1 run, the R/W ones read 0).
8. A ring pull at the end (513/24, 513/25, context-gone baselines).

## 6. Risks to proven paths

| area | risk |
|---|---|
| **Default 16 bpp path** | None while off (pinned). On: +22 writes per call with clean-state values, and the TMU-only NOP form is already silicon-proven traffic (`vcrdd_3d.c:111`). The one unknown is the power-on value of combineMode. The 40/40 runs were made from cold boots, so if it were not 0, writing 0 would change the proven environment. The boot-2 no-harm gate catches that |
| **Glide/OpenGL coexistence** | None expected. Glide programs all of this itself at open (`vcrdd_2d.c:384-386`). The baseline leaves chipMask ALL and combineMode 0, Glide's own defaults. It runs only when `!exclusive_pid` |
| **SLI** | It writes sliCtrl 0 and chipMask ALL on chip 0 only. SLI is live only under an exclusive Glide owner, when D3D draws nothing. `DrvAssertMode(TRUE)` clears a stale owner and re-programs the mode (VcrSliOff) in the same DDI call (`vcrdd.c:589-591`), so no DP2 can fall between the two. **G51 must change this** (pinned by name in the tests) |
| **Flip path** | None: the flip writes no 3D register (vidDesktopStartAddr by IOCTL) |
| **G01 (stale FIFO)** | Not fixed by this: the baseline goes through the same PIO path as the draws it precedes. With G01 armed, `drawable` = 0 and the baseline never runs. Until G01 lands, every on-box step checks cmdFifo0 off first |
| **The 11-12 attribution** | The 40/40 after the busy-at-mode-set reset cannot separate G01 from G03. The miniport's reset also pulses the graphics core (`vcrmp_hw.c:180-200`), and whether that restores 3D registers is unknown. G01's planned fix (cmdFifo0.baseSize = 0 with no core reset) will separate them |
| **Performance** | About 4-6 µs per drawing call (inferred). It could matter only for titles with hundreds of DP2 calls per frame. §2.9 is the fallback |

## 8. Open questions

1. Does a broadcast (chip field 0) write reach the TMU copies of
   chromaKey/chromaRange (the register table says "FBI")? The design writes both
   forms. A silicon check could drop the broadcast or the 0x6 write.
2. Is combineMode's power-on value 0? The no-harm gate answers it indirectly.
3. Does the miniport's engine reset (miscInit0 GRX/FBI-FIFO/2D +
   miscInit1 command-stream reset) restore 3D registers to defaults? This
   decides what the 11-12 "40/40 after reset" means. Test: stencil residue, then
   a forced busy reset, then read stencilMode.
4. hw-41 S2: does the VSA-100 honour a stale stencil enable at 16 bpp? Boot 1
   step 3 answers it.
5. Which MesaFX end states are hostile and which benign? The per-class runs
   answer it, and so explain why visual-05 is intermittent.
6. DP2 calls per frame of the DX5 execute-buffer titles (JK DF2, MotS). If they
   reach hundreds per frame, implement §2.9.
7. Is chipMask really always taken when chip 0's own bit is clear? SPEC L3482
   does not say. Glide's SLI teardown depends on it (inferred). It cannot be
   tested safely; the abandon class after G01 shows it indirectly.
8. The D3DSafe flag allocation (`0x8000 << bit`) and the 513 what codes 24/25
   are shared with the G01, G02 and G10 designs. Agree them in whichever lands
   first.
9. Bitfield default semantics, once bit 1 goes default-on: an explicit value
   replaces the defaults. The alternative is a dedicated `D3DBaseline` switch
   (absent = 1 later, like `Accel2DPattern`). Pick one before the flip.
10. Retire Reset3D once bit 1 is default-on? Its writes and more run at the
    point of use.

## 9. Corrections to the record (for the README/FINDINGS update that lands with this)

1. **The hal-02 reading is not evidence.** combineMode, sliCtrl, aaCtrl,
   chipMask, chromaKey and chromaRange are write-only; their reads are undefined
   (SPEC L2225, L2316-2347). Only stencilMode/stencilOp, clip1, stipple,
   renderMode and fbzMode read back.
2. **The TMU's combine inputs always come from combineMode** (L2836). "Glide
   says some bits act with USE_COMBINE_MODE clear" is the spec's rule, not a
   quirk.
3. **Zeroing combineMode alone re-arms texture chroma substitution** from a
   leftover TMU constant colour (L2825, L3534). Clear TMU chromaRange first.
4. **Clip rect 1 and stipple are inert for the current HAL** (bit 31 /
   renderMode[21]; fbzMode[2]). They are written or pinned for future gaps, not
   as causes of today's symptoms.
5. **aaCtrl's offsets apply even with AA off** (L3442). A killed AA client
   shifts every D3D vertex and can double-write a stale secondary buffer.
