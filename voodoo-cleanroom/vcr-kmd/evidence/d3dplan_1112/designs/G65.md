## 0. Verdict

The gap is **half real, a quarter inert and a quarter wrong**. Each part has its own answer.

| claim in the gap | finding | action |
|---|---|---|
| UT2003/UT2004 `UseVSync=False` makes them present without vsync | **Real (read).** D3DDrv puts `UseVSync ? D3DPRESENT_INTERVAL_ONE : D3DPRESENT_INTERVAL_IMMEDIATE` into `FullScreen_PresentationInterval` (§1.1). The runtime turns IMMEDIATE into `DDFLIP_NOVSYNC`, which vcr-kmd honours (`KMD/display/vcrdd_ddraw.c:102-105, 319-357`). | Per-box launcher block: `UseVSync=True` on the campaign box. |
| `DesiredRefreshRate=60` runs them at 60 Hz, "far below the CRT's 85-120 Hz" | **Wrong.** D3DDrv uses the value only when it is **above 60** or `OverrideDesktopRefreshRate=True`. At 60 it passes `FullScreen_RefreshRateInHz = 0` (`D3DPRESENT_RATE_DEFAULT`) (§1.1). The XP D3D8 runtime's default on `.124` was **85 Hz** in every measured case (§1.4). | **Do not write it.** Above 60, D3DDrv takes an *exact* match or else the **lowest** rate of the mode, which would make the result worse. |
| Red Faction `Vsync=0` (HKCU) | **Real (read).** rf.exe reads `HKCU\Software\Volition\Red Faction\Vsync` into `FullScreen_PresentationInterval` the same way (§1.2). | Per-box line in the generated launcher's spec: HKCU `Vsync` = 1 on the campaign box. |
| Thief II `multisampletype 8` against the user's no-AA choice | **Real in the file, inert on `.124` (read, and inferred for the runtime).** NewDark steps the type down through `CheckDeviceMultiSampleType` until one is offered, else NONE (§1.3). vcr-kmd's DX7-level HAL offers none (no AA raster cap, and no multisample formats through a DX7 DDI). `d3d_disp_enable_atoc 1` needs MSAA too. | Hygiene: per-box `multisampletype 0` and `d3d_disp_enable_atoc 0`. A `d3dprobe caps` check pins "no MSAA offered". |
| "so they tear" | **Mechanism corrected (on the driver's model).** vcr-kmd's flip model takes `vidDesktopStartAddr` as latched at the next vsync (`KMD/include/vcr_flip.h:9-16`; `designs/G54.md:98`). The spec does not say so for that register (`designs/G55.md:243`), and G55's E4 would measure it. On that model a `NOVSYNC` write never switches mid-scan. What a `NOVSYNC` title gets instead is **superseded frames** and **drawing into the buffer still on screen** (G55's hazard). | G55's fix waits only on *vsync'd* flips (`designs/G55.md:201`: "A NOVSYNC flip is never pending ... any immediate-present title are untouched"). **So until G65 lands, G55 cannot protect UT2003, UT2004 or Red Faction.** |

**What to do:**
- **Part A, the fix:** three generated launcher blocks and one spec line. They are gated per box on
  `FR_UE1DEV == GlideDrv.GlideRenderDevice`, the established "the 3dfx card drives the screen" idiom
  (`SF:620, 654, 684, 706, 1008`; `FRC:806-814`), which today is true on `.124` alone.
  - No driver change.
  - Every other box keeps the library's values: its launcher gains lines that do nothing there.
- **Part B, guard and measurement (d3dprobe):**
  - `caps` reports multisampling and `PresentationIntervals`;
  - the shared `vsync` mode (`designs/G59.md` §7) gains `--hz 0` (the refresh the runtime picks when a
    title asks for none) and `--immediate` (an IMMEDIATE present is not held).
- **Part C, triple buffering:** UE2 `UseTripleBuffering`, NewDark `single_display_mode 3`. It is the
  config-only way to a hazard-free vsync'd present on today's HAL. It is staged **only after** G55's E1
  shows the hazard in these titles and `d3dprobe vsync --bb 2` passes on silicon.
- **Part D, audit:** classify every other D3D title on `.124` (Halo, Max Payne, H&D, the DX5/DX6 titles)
  from the session-end flip counters during G59-E2/G73's sweep. A title with a setting gets a Part-A line.
- **Part E, conditional:** a default-off `Diag\D3DVsync` driver policy. It is built only if Part D finds a
  title that presents IMMEDIATE and has no setting a launcher can reach.

**Priority P1.** No title stops or renders worse because of this item alone, so it is not P0. But it
contradicts a stated user choice in three staged titles. G55's fix cannot help those titles until it
lands. And G59-E2, G73 and G78 all measure "vsync on" and assume it. The Thief II half is P3 hygiene.
**Effort M**: Part A is S; the probe work and the on-box session make it M.

## 1. What the staged titles ask for

### 1.1 Unreal Engine 2 `D3DDrv.dll` (UT2003 2225 and UT2004 3369): identical logic in both builds

**Config fields.** These are read from each `StaticConstructor`'s `U*Property(CPP_PROPERTY(...), "Options",
CPF_Config)` registrations. All four are full 32-bit `UBOOL`/`INT` fields: the code compares whole
dwords, not bit masks.

| key | D03 offset (registration) | D04 offset (registration) |
|---|---|---|
| `UseVSync` | `+0x40e8` (`0x1000bed3-0x1000bee6`) | `+0x4120` (`0x1000dc89-0x1000dc9c`) |
| `UseTripleBuffering` | `+0x4108` (`0x1000bf1d-0x1000bf2c`) | `+0x4140` (`0x1000dcc9-0x1000dcdc`) |
| `OverrideDesktopRefreshRate` | `+0x4134` (`0x1000c16d-0x1000c17e`) | `+0x416c` (`0x1000dec9-0x1000dedc`) |
| `DesiredRefreshRate` | `+0x4158` (`0x1000c24b-0x1000c25e`) | `+0x4190` (`0x1000df89-0x1000df9c`) |

**`UD3DRenderDevice::SetRes`, fullscreen.** D03 is at `0x100100b7-0x100103c7`. D04 is at
`0x10011909-0x10011b9e`. The `D3DPRESENT_PARAMETERS` struct is at `+0x46c8` in D03 and `+0x4700` in D04.

```
target = (DesiredRefreshRate > 60  ||  OverrideDesktopRefreshRate) ? DesiredRefreshRate : 0
                                             ; D03 0x100100b7-0x100100e0, D04 0x10011909-0x10011930
for each adapter mode i (EnumAdapterModes order):           ; D03 0x100100e5-0x10010158
    score = |W-reqW| + |H-reqH| + |bpp(fmt)-reqBpp|
    take i if bpp(fmt) == reqBpp and
          (score < best  ||  (score == best && (target == 0 || mode.Refresh == target)))
FullScreen_RefreshRateInHz      = target ? chosen.Refresh : 0   ; D03 0x100101f2-0x10010200 -> +0x2c
FullScreen_PresentationInterval = UseVSync ? 1 : 0x80000000      ; D03 0x100103a1-0x100103c7, D04 0x10011b7a-0x10011b9e
                                  (neg/sbb/and 0x80000001/add 0x80000000 = ONE or IMMEDIATE)
BackBufferCount                 = UseTripleBuffering ? 2 : 1     ; D03 0x10010356-0x10010374, D04 0x10011b4b-0x10011b5e
log "Best-match display mode: %ix%ix%i@%i" with chosen.Refresh   ; D03 0x1001022e, D04 0x10011a4e
```

**What each `DesiredRefreshRate` / `OverrideDesktopRefreshRate` setting does:**

| staged values | refresh UE2 asks for | result on `.124` |
|---|---|---|
| **60 / False (staged today)** | **0 = `D3DPRESENT_RATE_DEFAULT`** | the runtime's default: 85 Hz in every measured case (§1.4) |
| 85 / any | 85 if the mode lists exactly 85 at that W×H×bpp, else the **first** equal-score entry of the runtime's list: the **lowest** rate if the list is in ascending order (inferred; the measured "@120" below is the last entry) | 85 at 1280x960 today; the lowest listed rate on any mode without an 85 entry |
| 60 / True | 60 Hz explicitly (where listed) | the CRT at 60 Hz: a real regression |

The UE2 log line is not the refresh it asks for. `UT2003.log:101` "`Best-match display mode:
640x480x16@120`" prints the matched list entry. With `target == 0` that is the **last** equal-score entry
(the highest rate, as the measured 120 shows), but the device is created with refresh 0. So the "@120" in `designs/G46.md:87` and
in the session log is UE2's log text, not the scan rate (§1.5).

### 1.2 Red Faction `rf.exe`: `Vsync`, and the hive it reads

- **Present parameters.** The fullscreen branch at `0x544634` calls `os_config_read_uint(NULL, "Vsync",
  &v, 0)`: `call 0x52b7d0` with the string at `0x5a99cc` (also `designs/G10.md:101`). Then
  `neg/sbb/and 0x80000001/add 0x80000000` sets `[0x1cd42e0]` = `FullScreen_PresentationInterval`, which is
  `+0x30` of the `D3DPRESENT_PARAMETERS` at `0x1cd42b0`. 0 gives IMMEDIATE and 1 gives ONE.
  - Three fields keep the 0 of the `rep stos` at `0x5445fd`. No instruction in rf.exe names their
    addresses (searched):
    - `FullScreen_RefreshRateInHz` (`0x1cd42dc`): `RATE_DEFAULT`;
    - `BackBufferCount` (`0x1cd42bc`): 1. Red Faction has no triple buffering;
    - `MultiSampleType` (`0x1cd42c0`): NONE. Red Faction never asks for AA.
- **The hive.** `0x52b4a0` is the reader: `RegOpenKeyExA` at `0x52b4fd`, then `RegQueryValueExA` at
  `0x52b53d`. It gets its root and subkey from `0x52b2a0`. That function starts with `mov ebp,
  0x80000001` (**HKEY_CURRENT_USER**), and for a NULL section copies the base path built at init by
  `0x52b570` (`"Software\"` at `0x5a6d98` + `"Volition"` + `"Red Faction"`, pushed at `0x4b2323-0x4b2381`).
  An explicit `hkey...` prefix is the only way to another root, and no caller here uses one.
- **By-product for G66 (read).** The resolution reads (`0x4b1480-0x4b14c4`: `"Resolution Bit Depth"`
  default 16, `"Resolution Width"` 640, `"Resolution Height"` 480) also pass section NULL. **rf.exe reads
  HKCU only.** The launcher's and GAMERES's HKLM writes (`LIB/RedFaction/Play Red Faction.bat`;
  `WT/agent/shared/gameres.h` RedFaction rows) are never read. That settles G66's and
  `designs/G10.md:483`'s open question. G10 must still land before G66 makes Red Faction 32 bpp
  (`designs/G10.md:29-30, 461`).
- **The staged value.** `LIB/RedFaction/install.reg:43` stages `"Vsync"=dword:00000000` under HKCU.
  GAMESYNC merges it at every sync.

### 1.3 Thief II (NewDark): already vsync'd; the MSAA request is inert on our HAL

- **Vsync.** `vsync_mode` is left at its default: `LIB/Thief2/cam_ext.cfg:27-31` says "default is 3 which
  means enabled", and line 31 is commented out. That already matches the user's choice.
  `framerate_cap 100.0` (`:37`) sits above 85 Hz.
- **MSAA.** `multisampletype 8` (`:211`). NewDark's step-down at `ND 0x682f10-0x682fb6`
  (`KMD/evidence/newdark_thief2/excerpts.asm:1447`):
  1. It clamps the type to 16.
  2. It calls `IDirect3D9::CheckDeviceMultiSampleType` (vtable `+0x2c`), decrementing until one succeeds.
  3. If none does, it returns 0 = NONE.

  vcr-kmd is a DX7-DDI driver. Its RasterCaps (`00100191`, `KMD/evidence/d3dplan_1112/caps_124.txt`) carry
  no AA bit, and a DX7 DDI has no multisample format operations, so every check fails and Thief II runs
  without AA (**inferred for the runtime; Part B measures it**).
- **ATOC.** `d3d_disp_enable_atoc 1` (`:259`). The file's own comment says it "requires multisampling to be
  enabled". So it is inert too.
- **Not AA, not in scope.** `tex_filter_mode 16`, `tex_filter_trilinear` and
  `d3d_disp_enable_distortionfx` are feature requests that fall back (G26, G85, G36). They do not
  contradict a user choice.
- **One-line launcher context.** `LIB/Thief2/Play Thief 2.bat` (md5 `f38f3e8e…`) is: FLEETRES call →
  `cam.cfg` `-setline` → `cd /d "%~dp0"` → the ND_DX6 block (`SF:767`) → `start "" Thief2.exe`.

### 1.4 What the runtime and our HAL do with these values

- **IMMEDIATE.** The runtime sends `DDFLIP_NOVSYNC` because vcr-kmd advertises `DDCAPS2_FLIPNOVSYNC`
  (`vcrdd_ddraw.c:102-105`). `Dd_Flip` then does not wait for the previous flip (`:324-333`), and
  `vcr_flip_begin` marks the flip **never pending** (`KMD/include/vcr_flip.h:132-144`).
  - Measured: `d3dprobe perf --novsync` 151 fps at 85 Hz (`WT/docs/v56k-benchmark-plan.md:1097`).
- **ONE.** A vsync'd flip is pending until the latch is seen.
  - Measured on `.124`, 2026-11-12: 640x480x16 at 85.1 fps (297 of 300 flips by retrace) and 1024x768x32
    at 84.4 fps (`ONBOX/d3dprobe_perf_*_vsync.txt`; ring `ONBOX/ring_after_probes_decoded.txt:192-193,
    962-963`).
- **RATE_DEFAULT.** d3dprobe never sets `FullScreen_RefreshRateInHz` (`KMD/tools/d3dprobe.c:1419-1455`:
  `memset`, then only the interval). Every d3dprobe device on `.124` came up at the desktop's 85 Hz:
  - `mode 144: 640x480x32@85` (`ONBOX/ring_after_probe_i_decoded.txt:30`);
  - `mode 153: 1024x768x32@85` (`ONBOX/ring_after_probe_ii_decoded.txt:27`, `ring_after_probes_decoded.txt:282`).

  The desktop was `1280x1024x32@85` (`FR_HZ=85`, `ONBOX/games/halo/fleetres_cmd.txt:5`). **Inferred:**
  UE2's and Red Faction's `RATE_DEFAULT` devices get the same 85 Hz, because the runtime and the call are
  the same. Part B measures it at UE2's own 1280x960x16.
- **A contrast worth keeping.** A Glide/OpenGL session's own mode set came up at `1280x960x32@60` and was
  re-set to `@85` 2.3 s later (`ONBOX/ring_start_decoded.txt:183, 320`). A refresh of 0 does not mean
  85 on every path. That is why Part B measures the D3D path at the titles' modes rather than assume it.

   The UE2 and Halo sessions' 511/12 lines were simply overwritten. That UT2003/UT2004 presented IMMEDIATE

## 2. Approach

### 2.1 The gate: who gets the campaign's choices

The user's choices (vsync on, no AA) are for the Voodoo 5 6000 campaign on `.124`. The library is one
tree for every box, so they go in **per-box launcher logic**. That is how this campaign already did UE1's
Glide device and refresh (`SF:651-693`), Descent 3's renderer (`SF:596-626`), Hexen II's uncap
(`SF:695-706`) and Serious Sam's `ogl_bExclusive` (`SF:1008`). All of them use one test:

```
if /i "%FR_UE1DEV%"=="GlideDrv.GlideRenderDevice" ...
```

- **What sets it.** FLEETRES.EXE prints `FR_UE1DEV=GlideDrv.GlideRenderDevice` only when
  `HKLM\Software\RetroAgent\GlideRender` = 1 **and** 3dfx silicon is enumerated (`FRC:806-814`,
  `1051-1052`).
- **Where it is true.** `.124` today: `ONBOX/games/halo/fleetres_cmd.txt:33`.
- **Where it is false:**
  - a box without the flag or the card;
  - a box whose FLEETRES.EXE is missing: the BAT's fallback is `D3DDrv.D3DRenderDevice`, `SF:177`.

  Each of those keeps the library's values.
- **Why not `sc query vcrmp`.** That is the test for "vcr-kmd's HAL limits apply", as in `halo_novideo`
  and `newdark_display_swap`. Vsync is the owner's choice for the box and its monitor. It should survive a
  rollback to the vendor driver, so it is keyed to the card driving the screen, not to the driver.
- **Glide/OpenGL on the same box** already run vsync'd through the system `FX_GLIDE_SWAPINTERVAL=1`
  (`WT/docs/v56k-benchmark-plan.md:373, 500-501`). After G65 every API on `.124` presents vsync'd.

### 2.2 Part A: the per-box blocks (the fix)

All lines are **single-line `if`s**. cmd expands `%VAR%` in a `( )` block at parse time (`SF:580-583`).
The marker is in the first `rem` line, as `post_block` (`SF:3023-3073`) keys off it.

**A1. UE2: `UT2003/Play UT2003.bat`, `UT2004/Play UT2004.bat`, `UT2004/Join fleet UT2004 server.bat`.**

New helper in `SF` beside `ue1_glide_device`, plus a `post` entry per launcher (marker `UE2_VSYNC`). The
anchor is `cd /d "%~dp0System"`, so the block runs after FLEETRES and after UT2004's player-name block,
before the game. The helper `campaign_ue2_vsync("System\\UT2004.ini")` emits:

```bat
rem ---- per-box VSYNC - UE2_VSYNC, see stage-fleetres.py campaign_ue2_vsync ----
rem The 3dfx campaign box presents with vsync on. D3DDrv reads UseVSync at SetRes:
rem True is one flip per retrace, False is immediate flips, which vcr-kmd honours.
rem DesiredRefreshRate stays 60 on purpose: at 60 or less D3DDrv asks the runtime's
rem default rate, above 60 it takes an exact match or else the mode's LOWEST rate.
if /i "%FR_UE1DEV%"=="GlideDrv.GlideRenderDevice" if exist "%~dp0FLEETRES.EXE" "%~dp0FLEETRES.EXE" -ini "%~dp0System\UT2004.ini" D3DDrv.D3DRenderDevice UseVSync True
```

- **Section.** Only `[D3DDrv.D3DRenderDevice]`, the device both inis select (`UT2004.ini:21`).
  `[D3D9Drv...]` and `[OpenGLDrv...]` are not used.
- **Write.** `-ini` is `WritePrivateProfileStringA` (`FRC:653-663`). Both inis are ANSI.
- **Post-block isolation.** UT2004's existing `UE_USERINI` block anchors before the FLEETRES call
  (`SF:1996-2007`), so refreshing either block cannot swallow the other.

**A2. Red Faction: `provisioning/discmount/specs/RedFaction.json` `fleetres_block`.**

`Play Red Faction.bat` is **generated** by `scripts/fleet/make-mount-launcher.py` from that spec, and
`tests/python/test_mount_launcher_template.py::test_shipped_launcher_matches_its_spec` reads the share. So
the line goes into the spec, never into the shipped file by hand. Append after the block's `)`:

```bat
rem per-box VSYNC - RF_VSYNC: rf.exe reads HKCU Vsync into its present interval, 1 = one flip per retrace
if /i "%FR_UE1DEV%"=="GlideDrv.GlideRenderDevice" if exist "%~dp0FLEETRES.EXE" "%~dp0FLEETRES.EXE" -reg HKCU "SOFTWARE\Volition\Red Faction" Vsync dword 1
```

- **Write.** `-reg` creates the key if needed and writes a REG_DWORD (`FRC:557-597`). It is used rather
  than `reg.exe`, which Win9x lacks (`SF:461-473`).
- **Generator.** Regenerate the launcher with `make-mount-launcher.py --spec ... --out <LIB path>`
  through `libwrite` (one verified write).
- **One source for the text.** A helper `campaign_rf_vsync()` in `SF` returns the line, and the
  regression test pins the spec's copy to it.
- **G66** rewrites the three resolution lines of the same block, HKLM → HKCU. It must keep this line.
  Landing both in one publish saves a push.

**A3. Thief II: `Thief2/Play Thief 2.bat`, a new `post` block `ND_NOAA` from `newdark_noaa()`.**

```bat
rem ---- per-box NO AA - ND_NOAA, see stage-fleetres.py newdark_noaa ----
rem The 3dfx campaign box runs without anti-aliasing. NewDark steps multisampletype down to the
rem first type the device offers and vcr-kmd offers none, so this pins the choice, not a frame.
if /i "%FR_UE1DEV%"=="GlideDrv.GlideRenderDevice" if exist "%~dp0cam_ext.cfg" if exist "%~dp0FLEETRES.EXE" "%~dp0FLEETRES.EXE" -setline "%~dp0cam_ext.cfg" multisampletype multisampletype 0
if /i "%FR_UE1DEV%"=="GlideDrv.GlideRenderDevice" if exist "%~dp0cam_ext.cfg" if exist "%~dp0FLEETRES.EXE" "%~dp0FLEETRES.EXE" -setline "%~dp0cam_ext.cfg" d3d_disp_enable_atoc d3d_disp_enable_atoc 0
if /i "%FR_UE1DEV%"=="GlideDrv.GlideRenderDevice" if exist "%~dp0cam_ext.cfg.d3d9" if exist "%~dp0FLEETRES.EXE" "%~dp0FLEETRES.EXE" -setline "%~dp0cam_ext.cfg.d3d9" multisampletype multisampletype 0
if /i "%FR_UE1DEV%"=="GlideDrv.GlideRenderDevice" if exist "%~dp0cam_ext.cfg.d3d9" if exist "%~dp0FLEETRES.EXE" "%~dp0FLEETRES.EXE" -setline "%~dp0cam_ext.cfg.d3d9" d3d_disp_enable_atoc d3d_disp_enable_atoc 0
```

- **Anchor: `cd /d "%~dp0"`, NOT ND_DX6's `start "" Thief2.exe`.** `post_block` refreshes a stale block by
  replacing everything from its first line to its anchor (`SF:3043-3057`). Two blocks on one anchor
  would let a refresh of ND_DX6 delete ND_NOAA. The block therefore runs before ND_DX6's move. It
  edits both `cam_ext.cfg` and the aside copy, so the right values follow whichever file ND_DX6 leaves
  in place.
- **Never creates a file.** `-setline` returns 1 on a missing file (`FRC:505-506`), and the `if exist`
  guards stop the call anyway. A stub `cam_ext.cfg` would be fatal: on a vcr-kmd box without the
  switches, ND_DX6's `move /y` would carry it over the real aside copy.
- **Lines it cannot touch.** The commented `;d3d_disp_enable_atoc 2` (`:262`) and `; if "d3d_disp_enable_atoc"
  ...` (`:263`) have the first token `;...`, which `first_token` (`FRC:466-476`) never matches.
- **Line endings.** The file is CRLF, so sizes do not change.

**A4. What is deliberately not changed:**
- the library constants (`UseVSync=False`, `DesiredRefreshRate=60`, `OverrideDesktopRefreshRate=False`,
  RF `Vsync`=0, `multisampletype 8`). Every other box keeps today's behaviour, and changing the fleet
  default is the user's call (open question 1);
- `DesiredRefreshRate` and `OverrideDesktopRefreshRate` on the campaign box (§1.1). If Part B shows the
  runtime default is not the desktop rate at 1280x960x16, the fallback is `DesiredRefreshRate=%FR_HZW%`.
  FLEETRES's best rate at FR_W×FR_H is 85 on `.124` and is listed there, per `fleetres_cmd.txt:7`;
- `vsync_mode` (already on), and Thief II's filtering and distortion options;
- no GAMERES rule. The gate cannot be expressed in `gr_rules`, and the precedent blocks (UE1_GLIDE,
  D3_RENDERER) are launcher-only too. GAMERES owns none of these keys, so the two writers cannot fight

### 2.4 Part C: triple buffering, the config-only route to a correct vsync'd present (after G55 E1)

With one back buffer, a vsync'd title draws its next frame into `flip_from` while that buffer is still
scanned out (G55 §1). With two back buffers the target is never `flip_from`
(`designs/G55.md:116, 327`). Engines that offer it:

| title | setting | read |
|---|---|---|
| UT2003/UT2004 | `UseTripleBuffering=True` | `BackBufferCount = 2` in D3DDrv (§1.1) |
| Thief II | `single_display_mode 3` | `cam_ext.cfg:16-17` |
| Max Payne | a "Triple" option in its startup dialog | `MaxPayne.exe` UTF-16 strings; registry value name not found |
| H&D Deluxe | "Triple buffering" | `Bin/IConfig.exe` strings |

**Gate (all three):**
1. G55's E1 shows `raf_hazard` in the title's sessions.
2. `d3dprobe vsync --bb 2` passes on silicon at the title's mode. A 3-buffer D3D chain has never run on
   vcr-kmd.
3. A VRAM and hitch check in one scene. One more 1280x960x16 buffer is 2.4 MB of the ~27 MB per-chip
   heap.

**Block.** Then a sibling block, `UE2_TRIPLE` (same gate, same anchor rules), with
`-ini ... UseTripleBuffering True` and the Thief II `-setline single_display_mode`.

**Costs.** One more frame of latency (the user decides, open question 3). With G54's swap queue or G55's
F1, it also restores the overlap that correct double buffering loses (`designs/G54.md:394-397`).

### 2.5 Part D: audit of the other D3D titles on `.124`

**How.** In G59-E2/G73's sweep boot, which carries `Diag\LogEntries` = 16384 as its one Diag change
(`designs/G59.md:365-369`), read per session after a clean exit:
- 511/6 `DrvDisableDirectDraw` field c, all flips;
- 511/12 `flips F: retrace R, deadline D`, vsync'd flips only;

**Verdict per title:** `F ≈ c` means vsync'd. `F = 0` with `c > 0` means IMMEDIATE. The second is a

| Red Faction | D3D8 | HKCU `Vsync` (§1.2) | 0 | IMMEDIATE until A2 |
| Thief II | D3D9 | `vsync_mode`, default 3 | default | vsync'd |
| Halo | D3D9 | "Framerate throttle" in the per-user profile (inferred from `halo.exe` "Framerate throttle= No Vsync", a timedemo report line); `-vidmode` asks 85 explicitly (`LIB/Halo/Play Halo.bat:13`) | not staged | unknown: measure |
| Max Payne | D3D8 (e2) | unknown; `REFRESHRATE_DEFAULT`, `MULTISAMPLE_NONE` symbols | — | measure. Its launcher is spec-generated (`MaxPayne.json`) |
| H&D Deluxe | D3D8 (LS3D) | unknown | — | measure |

### 2.6 Part E (conditional): `Diag\D3DVsync`, a driver-side present policy

Build this only if Part D finds an unconfigurable IMMEDIATE title. Sketch:
- **The switch.** `Diag\D3DVsync` REG_DWORD, read at every mode set into `vcr_info` flags, like
  `FlipDeadline`/`Accel2D*`. Absent or 0 = the application decides (today, byte-for-byte). 1 = every flip
  vsync'd. 2 = every flip `NOVSYNC`; this is `reports/perf.md:854`'s `D3DNoVsync` diagnostic, so one
  switch serves both.
- **The decision.** A pure helper in `vcr_flip.h`, `vcr_flip_novsync(app_flag, policy)`, called in
  `Dd_Flip` where `novsync` is computed today (`vcrdd_ddraw.c:324`).
- **Caps stay.** Keep `DDCAPS2_FLIPNOVSYNC`. Removing it would drop `D3DPRESENT_INTERVAL_IMMEDIATE` from
  D3D9's caps, and a title that asks for IMMEDIATE could then fail `CreateDevice`.
- **Tests.** `tests/native/test_vcr_kmd_flip.c` covers policy 0 (the app's flag passes, the old value),
  1 (pending and counted in `flips`) and 2.
- **Probe.** `d3dprobe_run.py` records the Diag value with every `perf --novsync` result, so a forced
  vsync can never pass for a slow chip.
- **The vendor never forced vsync on.** `SSTH3_SWAPINTERVAL` (`VH5/DDINIT.C:796-800`) only turned it off,
  and an application's `DDFLIP_NOVSYNC` won (`VH5/DDFLIP.C:150-153, 171-176`). So policy 1 is our own
  behaviour, and it overrides an application. That is why it stays a fallback.

## 4. d3dprobe test

`KMD/tools/d3dprobe.c` and `d3dprobe_run.py`. The `vsync` mode is specified by `designs/G59.md` §7 (test
key `vsync_rate`). "Whichever item lands first owns it". G65 adds only what is below; if G65 lands
first, it writes that mode.

**4.1 `d3dprobe caps`: new fields `msaa` and `PresentationIntervals`; test key `msaa_none`.**
- **What it does.** No device and no mode switch. For `R5G6B5` and `X8R8G8B8`, fullscreen and windowed,
  call `IDirect3D8_CheckDeviceMultiSampleType(d3d, 0, D3DDEVTYPE_HAL, fmt, windowed, t)` for t = 2..16.
  - Report one 17-bit mask per (format, windowed): `"msaa":{"R5G6B5":{"full":"00000","win":"00000"},
    "X8R8G8B8":{...}}`.
  - Also print `caps.PresentationIntervals`.
- **Pass.** Every mask is 0. Reference: the HAL offers no AA (RasterCaps `00100191`, no ANTIALIAS bit;
  user choice "no AA"; `reports/hal.md:310`), and NewDark's step-down (§1.3) then runs NONE.
- **Fail meaning.** Some driver or runtime change made a multisample type available. Every staged title
  that asks for AA would then get it.
- **`PresentationIntervals`.** Recorded and pinned after the first silicon run. Expected `80000001`
  (ONE | IMMEDIATE) for a DX7 HAL without `DDCAPS2_FLIPINTERVAL` (inferred). Losing IMMEDIATE would
  break any title that asks for it (§2.6).

**4.2 `d3dprobe vsync --hz 0`: what a title gets when it asks for no rate; test key `rate_default`.**

`FullScreen_RefreshRateInHz = 0`, as UE2 (staged), Red Faction and Max Payne pass it. Before
`CreateDevice` the probe records:
- `desktop_refresh` (`GetAdapterDisplayMode`);
- `desktop_rate_listed`: does `EnumAdapterModes` list the test W×H×fmt at that rate.

After `CreateDevice` it records `refresh_chosen` (`IDirect3DDevice8_GetDisplayMode`). `d3dprobe_run.py`
reads the session's `MODESET_BEGIN` "mode N: WxHxBPP@Hz" line from the ring after the run; that is the
authoritative value.
- **Pass.** If listed, ring Hz == `desktop_refresh`. Reference: 85 on `.124` (`mode 159: 1280x1024x32@85`;
  the measured `mode 144`/`153` d3dprobe devices at 85). If not listed: "skipped", with the rate
  reported.
- **Runs:** 1280x960x16 (UE2's mode) and 640x480x16 (Red Faction's mode until G66).
- **Then G59's `vsync_rate` checks hold with R = the ring Hz.** Pass: 0.98 ≤ present/raster ratio ≤
  1.02; `slow_frames + two_frame` ≤ 3/600; `fast_frames` ≤ 1.

**4.3 `d3dprobe vsync --hz 0 --immediate`: what `UseVSync=False` / `Vsync=0` get; test key
`immediate_not_held`.**

`FullScreen_PresentationInterval = D3DPRESENT_INTERVAL_IMMEDIATE`. G59's scene and loop, at 1280x960x16
and 640x480x16.
- **Pass.** The median Present-to-Present interval ≤ 0.85 × (1000 / R) ms. Reference:
  `perf --novsync` 151 fps = 6.6 ms against 11.76 ms at 85 Hz. The scene (a fastfill and one 64x64
  quad) costs well under one refresh at 1280x960x16 (inferred: about 1.2 Mpixels of fastfill).
- **Skipped** if `PresentationIntervals` lacks IMMEDIATE.
- This pins both halves of what a staged config chooses between: §4.2 shows the vsync'd present is paced
  at the refresh; this shows the immediate one is not held.

**4.4 `--bb N` (G55's option name): `BackBufferCount = N` for `vsync`.** Part C's gate: `vsync --hz 0
--bb 2` at the title's mode must pass `vsync_rate` with `fast_frames` ≤ 1.

**Runner.** `d3dprobe_run.py` passes `--hz`, `--immediate` and `--bb` through. It computes the three
verdicts and refuses `--immediate` without `--full`. `tests/python/test_vcr_kmd_d3d.py` gains:
- argument-passthrough cases;
- the verdict logic over synthetic RESULTs: an 11.8 ms median under ONE passes; a 5 ms median under ONE
  fails `vsync_rate`; a 12 ms median under `--immediate` fails `immediate_not_held`; a RESULT without
  the new fields still parses, which is the old probe.

## 7. Risk to proven paths

- **HAL, kernel, Glide/OpenGL coexistence, SLI state:** none. No driver code changes in Parts A-D.
- **Flip path.** The two titles move from the NOVSYNC path to the vsync'd one, which is the proven path:
  85.1 and 84.4 fps, 297/300 by retrace on 11-12. At UE2's current 4-9 fps (G46) each flip finds the
  previous one long done, so vsync costs nothing measurable. Red Faction is capped at 85 fps by design
  (the user's choice).
  - G59's open question about positive-vsync modes (1280x960@85) is the one place a vsync'd title could
    fall to R/2 once UE2 is fast enough. §6 step 4 reads it.
- **Every launcher of these titles changes on every box.** A malformed line could stop a game starting
  fleet-wide. Mitigations:
  - single-line `if`s only, executed in the cmd model for every box state;
  - `stage-fleetres.py --check`, the validator, and the spec round-trip test;
  - a real launch on one non-3dfx box (§6 step 8).
- **G55.** Vsync on does not remove the render-after-flip hazard (§0). Part C or G55's F1 does, and F1
  needs G65.
- **Diagnostics that relied on `UseVSync=False`** (G46's vsync-off runs, `designs/G46.md:426-429`).
  UE2's `Core.dll` parses `INI=` and `USERINI=` (UTF-16 strings in both builds' `Core.dll`). So a
  vsync-off diagnostic runs the exe with `ini=` pointing to a copy carrying `UseVSync=False`, never a
  library edit. That answers G46's open question 4 statically; a run confirms it.
