# G16: Direct3D lines and points on vcr-kmd (design)

2026-11-12. Design only: nothing was built, edited, deployed or run on a fleet box.
Paths: `KMD` = `voodoo-cleanroom/vcr-kmd`, `VH5` = 3dfx's W2K H5 display driver,
`W9X` = `retro-3dfx/3dfx Driver Code/H5/Win9x/DX/D3D`, `G5` = our h5 Glide fork
(`voodoo-cleanroom/build/retro3dfx-glide/glide3x/h5/glide3/src`), `DDK` =
`~/retro3dfx-toolchain/devtools/w2kddk/src/video/displays` (Microsoft's sample drivers).
Sources: the plan reports hal-16, vendor-22, hw-10 (Q9), games-25 (5.2), history-15,
runtime-16 (8.3) and visual-15 (V-15), plus the code read for this design.

## 1. Verdict

**The gap is real and fixable. There are two defects, not one.**

1. **The gap as filed.** The HAL reports `D3DDD_LINECAPS` with `dpcLineCaps` copied from the
   triangle caps (`KMD/display/vcrdd_d3d.c:2063, 2072`). The DP2 walker then parses every line and
   point opcode and draws nothing: POINTS, LINELIST, LINESTRIP, INDEXEDLINELIST, INDEXEDLINELIST2,
   INDEXEDLINESTRIP and LINELIST_IMM (`:1690-1715`, "not drawn yet").
2. **New, found while designing: LINELIST_IMM is skipped with the wrong length.** The walker skips
   `2 * n * stride` bytes of inline vertices (`:1690-1694`). The record is a connected strip of
   **n + 1** vertices, drawn V[i] to V[i+1]. Four independent parsers agree:
   - 3dfx W2K `VH5/D6DP2.C:3732` (limit check) and `:3748` (advance);
   - 3dfx Win9x `W9X/D6DP2.C:3561` and `:3577`;
   - Microsoft's 3dlabs sample, `DDK/3dlabs/driver/d3ddx6.c:1124, 1143`;
   - Microsoft's S3 Virge sample, `DDK/s3virge/d3ddx6.c:1024`.

   For n = 1 the two lengths are equal (2 = 1 + 1), so one clipped line parses correctly today.
   For any n >= 2 the walker skips n - 1 vertices too far. It then either returns
   `D3DNTERR_COMMAND_UNPARSED`, which is the D3DIM fallback path that crashed Jedi Knight before
   the EXIT fix (`:1773-1782`), or it executes vertex floats as opcodes. Whether the runtime ever
   sends n >= 2 has not been measured (open question 1).

**Hardware.** The VSA-100 has no line or point primitive. SPEC section 3.3 (L550): *"spans and lines
are rendered as special case triangles"*. Its setup unit draws strips: `sBeginTriCMD` after the
first vertex, then `sDrawTriCMD` after each later one, and *"after D2's data has been sent, and the
2nd write to sDrawTriCMD has been completed Napalm will begin to render triangle 1"* (SPEC section
8.60; sSetupMode bit 16 strip/fan, bit 17 cull enable, bit 18 cull sign, section 8.59). Everyone
who drove this chip drew lines and points as quads through that unit:
- Glide: `G5/gdraw.c:831`, *"the triangle pair as a strip of 4 vertices"*, ±0.5 in the minor
  axis, `kSetupCullDisable`;
- 3dfx's D3D HAL: `VH5/D6LINE.C:382-990`, `VH5/D6POINT.C:127-365`.

So the fix is a CPU-side decomposition through the path every triangle already uses. It needs no
new register and no new hardware mode.

## 4. Design

### 4.1 Step 0: default ON, no register traffic (lands with the next driver build)

These parts change no register write. They correct the walk and measure what titles send.

**(a) LINELIST_IMM consumes n + 1 vertices.**
- Pad to DWORD exactly as today; this is the same rule as TRIANGLEFAN_IMM (`:1678-1689`).
- `NEED((n + 1) * w->stride)` and `p += (n + 1) * w->stride`, in place of `2 * n`.
- A `w->stride` of 0 means `fvf_layout` refused the FVF, so the record's length is unknown. Hand
  that command to `g_parse_unknown`, as the default case does, rather than advance by 0. This is
  defensive only: a non-T&L DX7 HAL is never sent untransformed vertices.

**(b) Per-context line and point counters.** These are the measurement G76 asks for, scoped to
this item; if G76 lands first, use its counter block.
- New `vcr_d3dctx` fields:
  - `lines_seen`, `points_seen`, `lines_drawn`, `points_drawn`;
  - `imm_lines` and `imm_max` (the largest n of any LINELIST_IMM);
  - `prim_ops`, a 7-bit mask of the line/point opcodes seen (bit 0 POINTS, 1 INDEXEDLINELIST,
    2 LINELIST, 3 LINESTRIP, 4 INDEXEDLINESTRIP, 5 LINELIST_IMM, 6 INDEXEDLINELIST2; the
    opcode numbers themselves reach 27 and would not fit beside `imm_max`);
  - `prim_logged`.
- **Event 513 what 26, once per context**, at the first line or point opcode: the opcode, n, the
  DP2 ordinal, and "drawn" or "skipped: Diag\D3DFeat bit 4 off". This dates the scene that sends
  them.
- **Event 513 what 24, at `ctx_free`, only when non-zero:** b = lines, c = points,
  d = `prim_ops << 16 | min(imm_max, 0xffff)`. The message carries drawn/seen and the IMM count,
  within the ring's 95 characters.
- Document what 24/25/26 in the 513 comment in `KMD/include/vcr_events.h`.
- Cost: two `VcrDd` calls per context lifetime and integer increments per command.

**(c) d3dprobe:** the seven tests of section 7, and two more `caps` fields: `LineCaps` and
`MaxPointSize`.

### 4.2 Step 1: draw them (behind `Diag\D3DFeat` bit 4, default OFF)

**Geometry.** This is new `KMD/include/vcr_d3dprim.h`: floats, Win32-free, included only by
`display/vcrdd_3d.c` and the host test. Coordinates are the setup unit's, which means D3D's plus
`xy_bias` (0.5); pixel n is sampled at n + 0.5.

```c
typedef struct vcr_quad { float x[4], y[4]; } vcr_quad;   /* a 4-vertex STRIP */

/* 0: zero length - nothing (Glide gdraw.c:822). x-major when |dx| >= |dy|. */
static __inline int vcr_line_quad(float ax, float ay, float bx, float by, vcr_quad *q)
{
    float dx = bx - ax, dy = by - ay, ox = 0.0f, oy = 0.0f;
    if (dx == 0.0f && dy == 0.0f)
        return 0;
    if ((dx < 0.0f ? -dx : dx) >= (dy < 0.0f ? -dy : dy)) oy = 0.5f; else ox = 0.5f;
    q->x[0] = ax - ox; q->y[0] = ay - oy;     /* A-  BEGIN */
    q->x[1] = ax + ox; q->y[1] = ay + oy;     /* A+  DRAW  */
    q->x[2] = bx - ox; q->y[2] = by - oy;     /* B-  DRAW: triangle (A- A+ B-) */
    q->x[3] = bx + ox; q->y[3] = by + oy;     /* B+  DRAW: triangle (A+ B- B+) */
    return 1;
}
static __inline void vcr_point_quad(float x, float y, vcr_quad *q)   /* VH5/D6POINT.C order */
{ q->x[0] = x - 0.5f; q->y[0] = y - 0.5f;  q->x[1] = x + 0.5f; q->y[1] = y - 0.5f;
  q->x[2] = x - 0.5f; q->y[2] = y + 0.5f;  q->x[3] = x + 0.5f; q->y[3] = y + 0.5f; }
```

What this geometry draws:
- **Integer endpoints.** The minor-axis edges land on pixel boundaries (5.0 and 6.0 for D3D row
  5), so each column (x-major) or row (y-major) gets exactly one pixel, on the line's own row or
  column. The NT tree's -1..0 lands a row high. So would leaving out the bias.
- **Integer point.** It covers exactly pixel (x, y). A fractional point covers the pixel nearest
  to it.
- **Ends.** The quad's ends sit at the endpoints. A line drawn left-to-right or top-to-bottom
  draws [first, last), which is D3D's half-open rule. A line drawn right-to-left or bottom-to-top
  draws (first, last]. That is 3dfx's shipped behaviour as well: its endpoint swap does not move
  the quad.
- **D3DRENDERSTATE_LASTPIXEL is ignored**, as 3dfx and Microsoft's samples ignore it.

The register writer, in `display/vcrdd_3d.c` (the one FPU object):
- **`vertex_at(pd, d, v, x, y)`:** today's `vertex()` body, with sVx = x and sVy = y. It keeps the
  same room reservation and the same writes in the same order.
- **`vertex()`** becomes `return vertex_at(pd, d, v, p[0] + d->xy_bias, p[1] + d->xy_bias);`.
  - It is the same float expression, rounded once at the call boundary, so every triangle's writes
    are identical in value and order.
  - Declare `vertex_at` before `vertex()` and define it between `vertex()` and
    `VcrDd3dTriangle`. Then the existing Python tests pass unmodified:
    - `test_vertex_colour_goes_to_the_setup_unit_as_floats_not_packed_sargb` slices
      `static BOOL vertex(` .. `BOOL VcrDd3dTriangle(`;
    - `test_vertices_get_the_half_pixel_centre_offset` looks for `p[0] + d->xy_bias` in
      `vertex()`.
- **`quad(pd, d, v0, v1, v2, v3, q)`:** `vertex_at` v0, BEGIN, then v1, v2 and v3 each followed by
  DRAW. Then `g2d_busy = 1`.
- **`BOOL VcrDd3dLine(pd, d, a, b)`:** `vcr_line_quad(a + bias, b + bias)`, then `quad(a, a, b, b)`.
  Each corner carries its own endpoint's colour, Z, W or fog, and S/T for both TMUs.
- **`BOOL VcrDd3dPoint(pd, d, v)`:** `vcr_point_quad(v + bias)`, then `quad(v, v, v, v)`.
- **`BOOL VcrDd3dSetupMode(pd, mode)`:** room 1, then `w3(V3D_SSETUPMODE, mode)`.
- Prototypes go in `display/vcrdd_3d.h`.

**Culling.** D3D culls triangles only, and a quad's winding follows the line's direction. A quad
is also a 4-vertex **strip**: in fan mode the same four vertices would leave a gap. So, in
`display/vcrdd_d3d.c`:

```c
#define SM_NOT_FOR_QUADS (SM_CULL | SM_CULL_NEGATIVE | SM_FAN)   /* SM_FAN: a guard for G49 */
static BOOL quads_begin(dp2walk *w)          /* before each quad, after prepare() */
{ if (w->quads || !(w->c->regs.setupMode & SM_NOT_FOR_QUADS)) return TRUE;
  if (!VcrDd3dSetupMode(w->c->pd, w->c->regs.setupMode & ~SM_NOT_FOR_QUADS)) return FALSE;
  w->quads = 1; return TRUE; }
static void quads_end(dp2walk *w)            /* at the end of every line/point command */
{ if (w->quads) VcrDd3dSetupMode(w->c->pd, w->c->regs.setupMode); w->quads = 0; }
```

- `prepare()` sets `w->quads = 0` after a successful `VcrDd3dState`, because the full state write
  has just put the context's setupMode back.
- The cost is one write before the first quad of a command and one after the command, and only
  when the context culls (CULLNONE costs nothing).
- `tri()` and `imm_tri()` are untouched.
- This matches 3dfx clearing `SST_SETUP_EN_CULLING` for every line and point.

**Walker.** New `KMD/include/vcr_dp2prim.h`: integer, Win32-free, so the -mgeneral-regs-only HAL
may include it. It provides:
- `vcr_dp2_prim_bytes(op, n, stride, pad)`, the record bytes after the 4-byte header:

| opcode | record bytes |
|---|---|
| POINTS | 4n |
| INDEXEDLINELIST | 4n |
| LINELIST, LINESTRIP | 2 |
| INDEXEDLINELIST2 | 2 + 4n |
| INDEXEDLINESTRIP | 2 + 2(n + 1) |
| LINELIST_IMM | pad + (n + 1)·stride |

- `vcr_dp2_line(op, rec, i, &a, &b)`, line i's two vertex indices:
  - LINELIST: s + 2i, s + 2i + 1;
  - LINESTRIP: s + i, s + i + 1;
  - INDEXEDLINELIST: rec[i].wV1, rec[i].wV2 (absolute);
  - INDEXEDLINELIST2: s + wV1, s + wV2;
  - INDEXEDLINESTRIP: s + idx[i], s + idx[i + 1].
- `vcr_dp2_points(rec, i, &start, &count)`.

The record sizes match `VH5/D6DP2.C:2926-3760` and `d3dnthal.h` `D3DNTHAL_DP2POINTS/LINELIST/INDEXEDLINELIST/LINESTRIP/INDEXEDLINESTRIP`.
Execute-buffer `D3DOP_POINT` (`{wCount, wFirst}`) and `D3DOP_LINE` (`{wV1, wV2}`) are DP2 opcodes 1
and 2 byte for byte, so Jedi Knight's and MotS's streams decode through the same cases (runtime
section 6.1).

`walk()` keeps **one case per opcode**, each with its own `NEED(`. The Python test names every
case label and wants at least 20 `NEED(` in `walk()`; today there are 25, and folding the six line
cases into one would leave exactly 20, the floor. Each case does three things:
1. `NEED(vcr_dp2_prim_bytes(...))`, then `prim_seen(w, op, n)` (the counters);
2. when `w->lines_on`, loop through `line_ix()` (the `tri()`-style bounds check
   `a, b < w->nverts`), `line()` for the IMM's inline vertices, or `points()`;
3. `quads_end(w)`, then advance.

`line()` and `points()` do `prepare()`, then `quads_begin()`, then `VcrDd3dLine` or
`VcrDd3dPoint`. A context's existing state applies to its lines and points unchanged: textures and
both TMUs, blend, alpha test, Z, fog and the fog ramp carrier.

**Switch plumbing.** It follows the `Accel2DLine` pattern: a positive flag, read at every
`IOCTL_VCR_INFO`. It changes no caps, so a new PDEV picks it up at the next mode change, and 0 kills
it without a reboot.
- `KMD/miniport/vcrmp.c` `hwinfo()`: `(VcrDiagGet(L"D3DFeat", 0) & 0x10) ? VCR_INFO_F_D3DLINES : 0`.
- `KMD/include/vcr_ioctl.h`: `#define VCR_INFO_F_D3DLINES 0x8000` (D3DFeat bit 4; the next free
  flag bit).
- `display/vcrdd_2d.c` `VcrDd2dInit`: `pd->d3d_lines = 0` with the other resets, then set it from
  the flag; log 513 what 25 "armed: Direct3D lines and points (Diag\D3DFeat bit 4)".
- `display/vcrdd.h`: `ULONG d3d_lines;`.
- `D3d_DrawPrimitives2`: `w.lines_on = c->pd->d3d_lines;`.

The switch covers every chip, because the code uses only registers that Banshee, Voodoo3 and
VSA-100 share. That lets the 86Box Voodoo3 bed prove it before silicon.

**Cost per primitive at today's PIO transport.**
- A line or point is 4 vertices x (8 + 3 per TMU) writes, plus 4 commands and 4 room checks:
  about 4/3 of a triangle, or roughly 7-11 µs when textured (perf.md: 5-8 µs per textured
  triangle, inferred).
- Points and the two ends of a line repeat their parameters. Sending them once and only x/y for
  the other corners relies on the s* registers holding their values. That is untested, and it is
  a follow-up for G48/G49.
- Under the command FIFO (G47) a quad becomes one packet-3 BDDD whose own setupMode field drops
  the cull bits, so `quads_begin`/`quads_end` go away.

## 5. Caps

**No change.** With this item, the copy of the triangle caps becomes true: lines and points go
through the same state, so TEXTURE, ZTEST, BLEND, ALPHACMP and FOG all hold for them. With the
switch off the caps are the proven HAL's, byte for byte.

Removing line caps while the switch is off would change the proven path's caps, and an
application can change its code path on that. That is why the switch gates drawing and not caps.

3dfx's DX7 `dpcLineCaps` is the same full set (`VH5/D3INIT.C:2686-2780`). Its DX8-DDI
`LineCaps = 0` (`D3INIT.C:3544-3550`) belongs to a DDI we do not use.

## 6. Gating and promotion

- **Step 0** (the IMM length, the counters, the probe): **default ON**.
  - It writes no register.
  - For n = 1 the IMM length is unchanged; for n >= 2 the old length is a walker desync.
  - Pinned by the native test, both values.
- **Step 1** (drawing): **default OFF**, `Diag\D3DFeat` bit 4 (0x10).
  - The bit number follows hal.md section 10, Phase 2 item 5; coordinate with the other D3DFeat
    designs.
  - Off, the register stream is today's byte for byte:
    - the draw loops do not run, so `quads_begin` is never called and `quads_end` writes nothing;
    - `vertex()` produces the same writes;
    - `tri()` and `imm_tri()` are untouched.
- **Promotion to default ON** (absent = 1, 0 = kill): a one-line `VcrDiagGet` default plus a
  README row, **after one supervised clean boot on `.124`** (section 9, boot B) in which:
  - the seven line/point tests pass at 640x480x16 and 1024x768x32;
  - the 14-test default set still passes;
  - one game A/B shows the element appearing.

  This item is a good candidate for quick promotion. The ON path only touches command streams
  that draw nothing today, and the triangle path is unchanged. It still lands OFF first because
  it is new register traffic: a cull-bit toggle and quads at screen edges.

## 7. d3dprobe tests (`KMD/tools/d3dprobe.c`)

All seven tests are explicit (`--tests ...`), like `mip` and the D3DBigTex set. Add them to the
default list only when the switch defaults on.

Common setup:
- vertices are `VC`/`VT` XYZRHW;
- `untextured()` unless stated otherwise;
- **CULLMODE is left at D3D's default CCW on purpose**, so a missing cull disable loses whole
  directions;
- background 000000, flat-colour tolerance 8, gouraud tolerance 24;
- every coordinate stays inside the 256x256 readback window.

End pixels are recorded as **notes**, neither pass nor fail. D3D's end rule (LASTPIXEL, diamond
exit) differs between drivers, and a probe that also serves as the reference must not fail a
correct one.

**Old-buggy value.** With today's driver, or the switch off, every "lit" check reads 000000. The
exception is `lineclip`'s sentinel, which passes once Step 0 is in.

## 10. Risk to proven paths

- **Default 16 bpp path, switch off.**
  - Register stream identical.
  - `vertex()` has the same writes, values and order; the 14-test set in boot A is the silicon
    check.
  - The only behaviour change is the IMM length, which only changes what the walker skips, and
    only for n >= 2, where today it desyncs.
  - Counters cost two log calls per context.
- **Switch on.**
  - New traffic only in DP2 streams that contain line or point opcodes: the quads, plus one
    sSetupMode write before a command's first quad and one after the command, when the context
    culls.
  - Triangles in the same DP2 get the context's setupMode back before they draw.
  - Coordinates are bounded the way triangles' are: the runtime clips because we report no guard
    band, and quads at the edge are trimmed by `FZ_RECTCLIP` and the target's clip rectangle.
  - A title sending thousands of points a frame pays about 7-11 µs each (4.2). That is a frame-time
    cost, not a stability risk.
- **Glide/OpenGL coexistence.** Unchanged. Lines inherit whatever 3D state Glide left, exactly as
  triangles do (G03). sSetupMode is rewritten by Glide per packet anyway.
- **SLI.** None: D3D draws on chip 0 (G51). **Flip path:** none.
- **Fill rule.** A pixel centre exactly on a quad's end edge (integer endpoints) is assumed to be
  decided top-left. Only the first and last pixel depend on this, and the probe records them as
  notes.

## 12. Open questions

1. Does XP's D3D8 (and DX5-DX7) runtime ever send LINELIST_IMM with n >= 2? Which opcode carries a
   clipped line at all? `lineclip` and 513/24's `imm_max` answer it.
2. Which staged titles send lines or points, and how many per frame? Is JK's map overlay drawn
   with D3D lines or blitted by DirectDraw? Boot A's Phase-0 pass answers it.
3. Is the VSA-100's tie rule top-left for a pixel centre exactly on a quad edge? This only affects
   end pixels; see the probe notes and the 86Box reference.
4. Do any titles depend on D3D's end-pixel rule (LASTPIXEL, reverse-direction lines)? Fix only on
   evidence, with parameter extrapolation (4.3).
5. Does D3D8 report MaxPointSize = 1.0 for this DDI and expand point sprites itself? The caps
   print answers it.
6. D3DFeat: bit allocation across G08, G15, G22, G24, G25 and others. Is it one flag per bit, or
   one appended `vcr_info` field for the whole DWORD (then `memset` the info struct before the
   IOCTL)? Caps-changing bits must be latched at boot; this bit need not be.
7. The IMM vertex data is aligned relative to `cmds` (ours, also TRIANGLEFAN_IMM). The vendor and
   the DDK samples align the absolute address. The two agree while `fpVidMem + dwCommandOffset`
   is DWORD-aligned; log once if it ever is not.
8. Can a point's or line end's second corner skip its parameter writes, given that the s*
   registers keep their values? This is perf only and needs a bed and silicon check (G48/G49).
