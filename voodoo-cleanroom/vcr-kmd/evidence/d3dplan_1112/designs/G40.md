## 0. Verdict

1. **The code path is real.** `rec_size` skips STATESET by size (`KMD/display/vcrdd_d3d.c:1562`). RENDERSTATE and TEXTURESTAGESTATE records are applied as soon as they are parsed (`:1585-1611`; `set_rs :1393-1406`, which also writes the runtime's `lpdwRStates` mirror).
   - If a runtime ever sent `STATESET BEGIN … END`, the recorded states would become current at record time.
   - `EXECUTE`, `CAPTURE` and `DELETE` would do nothing.
2. **No XP SP3 runtime ever sends STATESET to vcrdd.** Static analysis of all three runtimes settles this (section 2):
   - **D3D8/D3D9** emulate state blocks for any driver of DDI type ≤ 5. The `EmulateStateBlocks` knob is read only above 5. This is runtime-19's reading, re-checked here byte for byte. vcrdd is a DX7-level driver, so DDI ≤ 5.
   - **d3dim700 (DX7)** is the case runtime-19 called "the exception", and it is not one. Its DX7 device classes contain a working emitter:
     - BEGIN, the recorded states, END, plus EXECUTE/CAPTURE/DELETE.
     - Every emission is gated on a per-block "driver buffer" being non-empty.
     - A recorded state goes into that buffer only when bit 31 of `CStateSets::m_dwFlags` is set.
     - That word is copied once, at device init, from the device's runtime-flags word `+0x1a6c`.
     - **No instruction in the image sets bit 31 of `+0x1a6c`.** The full disassembly and a raw byte scan of every encoding that could set it both find none. The same scan finds its positive control: the one write of bit 30, in the T&L device's Init.
     - Result: the driver buffers are always empty, and d3dim700 emulates state blocks for every driver.
   - **d3dim (DX6)** has no state blocks at all: there is no opcode-39 store and no method names for them.
3. **What reaches us when a title uses state blocks.** `ApplyStateBlock` replays the block as ordinary `RENDERSTATE (8)` and `TEXTURESTAGESTATE (25)` records in the next DP2, which the walker applies. While recording, `SetRenderState`/`SetTextureStageState` return without reaching the driver.
   - So the hal-07 "over-promise" does not exist.
   - hal-07's per-title list (Halo, UT2003, UT2004) and the gap's list (UE1 D3DDrv, Tribes 2) are not exposed.
   - The only staged renderer that uses state blocks at all is Tribes 2's `OpenGL2D3D.dll`: 27 `ApplyStateBlock` call sites. UE1's D3DDrv has none. Both renderers are dormant on `.124`.
4. **Keep `D3DDEVCAPS_DRAWPRIMITIVES2EX`.** It is what makes d3dim700 build its DX7 device class (DDI 4) for vcrdd and what D3D8/9 classify us by. Dropping it would change everything else and fix nothing.
5. **The work is small and mostly evidence.**
   - **Step 0** (default-ON, log-only, register traffic byte-for-byte unchanged):
     - count STATESET records by operation per context, and report the counts at context destroy;
     - raise a once-per-context WARN tripwire if a STATESET ever arrives;
     - add `d3dprobe stateblock` and `d3d7probe stateblock` (the replay must draw at Apply time, not record time);
     - add a host test that pins the runtime evidence.
   - **Step 1** implements record/execute/capture/delete in the driver, default-OFF behind `Diag\D3DFeat` bit `SBLK`. It is designed below (section 3.2) and **not to be built unless Step 0 ever counts a STATESET**.
6. **Priority P3, effort S** (Step 1, if ever needed: M). Raise it only if the tripwire fires on `.124`.

## 1. What the HAL does today

| piece | code | behaviour |
|---|---|---|
| caps | `vcrdd_d3d.c:2066-2070` | `dwDevCaps` includes `D3DDEVCAPS_DRAWPRIMITIVES2 \| D3DDEVCAPS_DRAWPRIMITIVES2EX` (live DevCaps `0008ae50`, `caps_124.txt`) |
| opcode 39 | `rec_size :1552-1567` (STATESET at `:1562`), consumed in `walk()`'s `default:` (`:1789-1795`) | `NEED(n * 12)`, then `p += n * 12`. Byte-aligned and bounds-checked; nothing counted, nothing logged |
| RENDERSTATE | `:1585-1590` → `set_rs :1393-1406` | applied now: `c->rs[st]` plus `lpdwRStates[st]` |
| TEXTURESTAGESTATE | `:1591-1611` | applied now: stages 0/1, with `D3DTSS_TEXTUREMAP` the stage's texture handle |
| record size | `KMD/out/ddi/d3dnthal.h:734-741` | `{DWORD dwOperation; DWORD dwParam; D3DSTATEBLOCKTYPE sbType;}` = 12 bytes; operations 0 BEGIN, 1 END, 2 DELETE, 3 EXECUTE, 4 CAPTURE (`:727-732`); 5 CREATE is DX8-DDI only (`:959-960`) |

**The hypothetical failure, if a runtime did forward state blocks.** Take an app that does `Begin; Set(ALPHABLENDENABLE, TRUE); End; Draw A; Apply; Draw B; Set(FALSE); Capture; Set(TRUE); Apply; Draw C`.
- A runtime that forwards sends `BEGIN, RS(…TRUE), END` at EndStateBlock time. We apply the RS at once, so **A blends (wrong)**.
- `EXECUTE` is skipped, so B blends only by accident.
- `CAPTURE` and the second `EXECUTE` are skipped, so **C blends (wrong)**.

The probe tests in section 4 draw exactly this sequence, so the signature (A and C purple) is recognisable.

**The DDK's expectation.** d_grafx.chm 4.7.4, "Accelerated State Management", describes BEGIN/END recording, DELETE, EXECUTE and CAPTURE ("only states that are already in the state block are captured"). Microsoft's sample has `#define D3D_STATEBLOCKS 1` (`W2KDDK/.../d3dhw.h:59-62`), and 3dfx implemented it (`VH5/D7DP2.C:1375-2420`). The question was always whether the XP runtime actually uses that driver path. Section 2 answers it.

## 2. What the XP SP3 runtimes send

### 2.1 D3D8 and D3D9 (runtime-19, re-checked)

- **d3d8, `0x6d9e8bb0`** (the device's DDI-info setup):
  - `+0x50` = DDI ∈ {5, 7, 0xb} (the T&L types).
  - `+0x58` = DDI ≥ 6 (a DX8 driver).
  - **`+0x54` (emulate state blocks)**: `cmpl $0x5,0x28(%eax); jle` → `movl $0x1,0x54(%esi)` (`0x6d9e8c05`: `83 78 28 05 7e 27`; `0x6d9e8c32`: `c7 46 54 01 00 00 00`).
  - Above 5 only, it reads the registry value named at `0x6d9a949c`, which is **`EmulateStateBlocks`**.
- **d3d9, `0x4fe6fbf0`**: the same rule. `cmpl $0x5,0x28(%ebx); jle` → `movl $0x1,0x54(%edi)` (`0x4fe6fc25` / `0x4fe6fc5a`). The T&L types are 5/7/9/0xb.
- **vcrdd's DDI type is ≤ 5.** It never sets `DDHALINFO_GETDRIVERINFO2`, and no `GUID_GetDriverInfo2` was ever sent (runtime.md §2). It is therefore not a DX8 driver.
  - The numbering is the one d3dim700 uses (2.2): 3 = DX6 DP2, 4 = DX7 DP2EX, 5 = DX7 T&L.
  - Whether d3d8 puts vcrdd at 3 or 4 does not matter: both emulate. The registry knob cannot switch the emulation off for vcrdd, because it is never read at DDI ≤ 5.

The binary carries no symbols. The API names come from its own strings; `CStateSets`, `CStateSet`, `InsertRenderState`, `GetDeviceBufferInfo`, `DIRECT3DDEVICEI::Init` and the other internal names are labels **(inferred)** from what each function does. The addresses and instructions are what the file holds.

| what Apply does instead | Apply `0x73950bc5` → class vtable `+0x14c` = `0x7394f470` (the same in all three classes) → `CStateSets::Execute` → `CStateSet::Execute 0x739517b6` on the front-end buffer | the block is replayed through the device's own state path, so the driver receives `RENDERSTATE` / `TEXTURESTAGESTATE` records in the next DP2 |

**Conclusion:** XP SP3's DX7 runtime emulates state blocks for every driver. The driver path is present in the binary but cannot be reached: the bit that would enable it is never set. Why Microsoft left it in is not known and does not matter here (open question 3).

### 2.3 d3dim.dll (DX6: IDirect3D, IDirect3D2, IDirect3D3)

There is no `movb $0x27` store and no state-block method name in the image. DX6 interfaces have no state blocks (they arrived with IDirect3DDevice7). JK, MotS, Rainbow Six, AvP, Thief Gold, SS2 and Shogo cannot produce a STATESET.

### 2.4 No title brings its own runtime

`find LIB -maxdepth 7 -iname 'd3dim*.dll' -o -iname d3d8.dll -o -iname d3d9.dll` finds nothing (the search is case-insensitive). The only game-local DirectDraw-family DLL is `RedAlert2/ddraw.dll`, a 2D wrapper. Every D3D title loads the system runtimes analysed above.

## 3. Design

### 3.1 Step 0: measure, and a tripwire (land default-ON)

**Why default-ON is right.** It writes no register and does not change what Direct3D sees. The 12-byte skip stays byte-for-byte the same. The only addition is one INFO event per context lifetime and a WARN that fires only if section 2 is wrong. This is hal.md's "Phase 0: log-only" class, pinned by source tests.

1. **New Win32-free header `KMD/include/vcr_dp2stateset.h`.** It follows the pattern of the other `vcr_*.h` headers so a native test compiles the code the driver runs.

   ```c
   #define VCR_SS_REC   12u    /* sizeof(D3DNTHAL_DP2STATESET): dwOperation, dwParam, sbType */
   #define VCR_SS_KINDS 6u     /* 0 BEGIN 1 END 2 DELETE 3 EXECUTE 4 CAPTURE, 5 other (DX8 CREATE, junk) */
   typedef struct vcr_ss_tally {
       unsigned long n[VCR_SS_KINDS];
       unsigned long seen;                         /* records counted */
       unsigned long first_op, first_handle, first_type;  /* the first record ever counted */
   } vcr_ss_tally;
   /* n records at p, avail readable bytes: 1 = all counted (n * VCR_SS_REC consumed),
    * 0 = they do not fit - nothing counted, the walker's NEED reports the stream */
   static int vcr_ss_count(vcr_ss_tally *t, const unsigned char *p, unsigned long n,
                           unsigned long avail);
   /* two counts in one event field, each saturating at 0xffff */
   static unsigned long vcr_ss_pack16(unsigned long lo, unsigned long hi);
   ```

2. **Changes to `KMD/display/vcrdd_d3d.c`:**
   - **`vcr_d3dctx`** (`:49-74`): add `vcr_ss_tally ss;` (zeroed by ContextCreate's `memset`).
   - **`walk()`**: add an explicit `case D3DNTDP2OP_STATESET:` before `default:`. It does `NEED(n * VCR_SS_REC)`, then `vcr_ss_count(&c->ss, p, n, end - p)`, then `p += n * VCR_SS_REC`.
     - The first record a context ever sees (`c->ss.seen` was 0) raises **one** WARN: `VcrDd(VCR_LV_WARN, VCR_EV_DD_D3D, 25, op, handle, sbType, "context %u: STATESET op %u arrived - the runtime is not emulating state blocks (G40)")`.
     - Nothing else is logged on this path (G52).
     - The case never calls `set_rs` and never touches `c->rs`, `c->tss*`, `c->tex_handle*` or `c->dirty`. Behaviour is identical to today: the records are skipped.
   - **`rec_size()`**: remove the `D3DNTDP2OP_STATESET` line (`:1562`). It would be dead code behind the explicit case.
   - **`ctx_free()`** (`:1210-1221`): after the existing "context gone" event, **always** emit one more INFO event, so that zero is a printed number and not the absence of a line:

     `VcrDd(VCR_LV_INFO, VCR_EV_DD_D3D, 24, pack16(BEGIN, END), pack16(EXECUTE, CAPTURE), pack16(DELETE, other), "context %u: STATESET %u/%u/%u/%u/%u/%u (begin/end/exec/capture/delete/other)")`.

     It is a separate event because the existing message is already at the 96-character limit (`VCR_LOG_MSG_LEN`, `KMD/include/vcr_log.h:32`).
   - **Coordination with G76.** If G76's per-context counter record lands first, these six counts become a row of it, and 513/24 is not added.
   - **Numbering.** 24 and 25 are the next free 513 sub-ids at the time of writing (1-23 are used). The implementer must check them against G76 and the other designs.
3. **`KMD/include/vcr_events.h:75`**: add `24 STATESET counts: b=begin|end<<16 c=exec|capture<<16 d=delete|other<<16; 25 STATESET arrived: b=op c=handle d=sbType` to the 513 description, which is what `vcrlog.py` decodes.
4. **Caps:** no change. `DRAWPRIMITIVES2EX` stays (verdict 4), and a Python test pins it.
5. **Old path:** unchanged register traffic, unchanged parse alignment, unchanged answers to the runtime.

**What each Step 0 outcome means:**

| outcome | meaning | next |
|---|---|---|
| 513/24 reads `0/0/0/0/0/0` for every context; no 513/25; the probe pixels pass | section 2 holds on silicon | close G40 as not a defect; drop hal-07 from the per-title matrix; keep the tripwire |
| a 513/25 appears | the box's runtime is not the analysed build (or a runtime from another OS/redistributable) | read op/handle/type/pid; md5 the box's `d3dim700.dll`; re-run the appendix scan on it; build Step 1 behind `SBLK`; raise to P2 if a staged title is the sender |
| probe pixels fail with STATESET = 0 | not G40. The replay went through RS/TSS and something else drew wrong (G01's stale FIFO, a blend gap, …) | file it under the gap whose state failed |

### 3.2 Step 1: state blocks in the driver (parked; default-OFF; build only if Step 0 counts a STATESET)

**Gate.** `Diag\D3DFeat` bit `SBLK`, read at boot and cached in the PDEV like `D3D32`/`D3DBigTex`. The bit number is assigned by whoever lands the `D3DFeat` register. When armed, the driver reports `vcr_info.flags` and raises a "513/16-style armed" event. With the bit clear, Step 0's skip stays byte-for-byte as it is.

**Pure logic in a Win32-free `KMD/include/vcr_stateblk.h`.** Allocation is passed in by the caller (EngAllocMem in the driver, malloc in the test).
- **The block.** Each block holds:
  - `rs_mask[RS_MAX/32]` and `rs[RS_MAX]` (256 states);
  - `tss_mask[2]` and `tss[2][TSS_MAX]` (stages 0/1; `D3DTSS_TEXTUREMAP` = 0 is the stage's texture handle).

  That is about 1.3 KB per block, uncompressed. Last writer wins inside a block.
- **The table.** One per context, indexed by the runtime's handle. It grows in steps of 32 and is capped at 1024 handles. A handle past the cap is refused once with a WARN and its records are skipped. Handle 0 is refused.
- **The walker, when armed.**
  - **Recording.** While `c->sb_rec != NULL`, RENDERSTATE and TEXTURESTAGESTATE records are recorded into the block and **not applied**. `lpdwRStates` is **not** written either, as Microsoft's sample does (`W2KDDK/.../d3dstate.c:1903-1929` mirrors only when not recording).
  - Stage ≥ 2 records stay dropped, as today. Draws, clears, TEXBLT and SETRENDERTARGET are unaffected.
  - A triangle drawn while recording increments a "drawn while recording" counter, and that counter's first increment logs one WARN.
  - **STATESET operations:**

    | op | action |
    |---|---|
    | BEGIN h | if already recording, the open block is ended first (logged once) — never an error that aborts the batch; then a fresh block is made for h (replacing any old one) and `c->sb_rec` is set |
    | END | `c->sb_rec = NULL`; an empty block is freed |
    | DELETE h | the block is freed |
    | EXECUTE h | every recorded RS goes through `set_rs(w, st, v, rstates)` (so the mirror is updated, as for any RS); every recorded TSS goes through the existing TSS path (TEXTUREMAP → `tex_handle`/`tex_handle1`); then `c->dirty = 1` |
    | CAPTURE h | every recorded entry is overwritten with the current value: `c->rs[st]`, `c->tss[st]`/`c->tss1[st]`, `c->tex_handle`/`c->tex_handle1` |
    | any other op (DX8 `CREATE` = 5 included) | counted, one WARN, skipped |

  - ContextDestroy and DestroyAll free every block. ContextCreate starts with none.
- **Vendor behaviour not to copy (G95):**
  - **Capture zeroes what it does not track.** 3dfx's `CaptureStateBlock` captures any render state it keeps no RC field for as **0**: `RenderStateOffsetInRC[i] == -1 → data = 0` (`VH5/D7DP2.C:2046-2057, 2098-2099`). Capture-then-Execute therefore resets MIPMAPLODBIAS, WRAP2-7, the stipple patterns, RANGEFOGENABLE and ANISOTROPY. We keep `c->rs[256]` for every state, so capture reads the real value.
  - **Off-by-one in the block table.** `AddStateBlockToTable` grows only when `dwHandle > ppSBTable[0]` (`:2237`), while `FindStateBlock` finds only `dwHandle < ppSBTable[0]` (`:2202`). The release loop stops at `< ppSBTable[0]` (`:2160`). A handle equal to the last index is stored but never found or freed: its EXECUTE is a silent no-op and the block leaks.
  - **A protocol error drops the whole batch.** A STATESET error aborts the entire DP2 batch. A nested BEGIN returns `D3DERR_INBEGINSTATEBLOCK`; `if (D3D_OK != hr) break;` leaves the record loop without advancing (`VH5/D6DP2.C:4236-4245`), and the stream loop then exits on the error (`:4972-4980`). Every later command in the frame is dropped. Ours logs and continues.
  - 3dfx's DCT-50 workaround (texture handle `0xFFFFFFFF` → 0, `VH5/D7DP2.C:1587, 1717`) is unnecessary: `handle_get` already returns NULL for an unknown handle (`vcrdd_d3d.c:118-131`).
- **Not a fix:** setting `EmulateStateBlocks=1` on the box changes nothing. D3D8/9 never read it at DDI ≤ 5, and d3dim700 has no such value.

### 4.1 d3dprobe `stateblock` (D3D8; explicit, not in the default list)

## 6. Risk

**Step 0 to proven paths: none measurable.**
- No register write is added or changed. The default 16 bpp D3D sequence, the 32 bpp D3D32 path, Glide/OpenGL coexistence, SLI state and the flip path are untouched.
- Opcode 39 is still consumed as `n * 12` bytes under the same `NEED` bound, so the walk cannot lose its place. The native test pins the size and the all-or-nothing bound.
- The one new event costs one IOCTL per context lifetime, never per draw (G52). The WARN costs one per context, and only if section 2 is wrong.
- The single realistic way Step 0 breaks something is a typo in the new case that mis-sizes the records. Today's runtimes never send the opcode, so even that would be invisible. The native test exists so it cannot ship.

**The evidence test.**
- It depends on the share. It skips loudly when the share is absent and never silently.
- Its md5 pins fail when the fleet image's runtime changes. That is intended: the conclusion is only valid for the analysed build.

**Step 1 (parked).**
- Record mode stuck on (a BEGIN with no END) would swallow every later RS/TSS, and the frames would draw with stale state.
- Mitigations:
  - END, ContextCreate and ContextDestroy clear it;
  - a draw while recording is counted and logged;
  - the block table is capped;
  - the gate is default OFF.
- Proven one clean boot at a time, as the project rule requires.

## Appendix: re-deriving the d3dim700 evidence

```sh
d=$(mktemp -d) && cd "$d"                # an empty directory of its own
7z x -y /mnt/retro-share/Files/OS/XPSP3-FLEET/I386/D3DIM700.DL_ >/dev/null
md5sum d3dim700.dll                      # 56adb11f7d4d0816c0be1e701c1b5e52
i686-w64-mingw32-objdump -d d3dim700.dll > d3dim700.dis
grep -n -F 'movb   $0x27,' d3dim700.dis                     # 0x7395661e, 0x73956673 (WriteStateSetToDevice)
grep -n -E 'push +\$0x27$' d3dim700.dis                     # 0x73951588 is the EXECUTE/CAPTURE/DELETE helper
grep -n -E ',0x1a6[cdef]\(%e[a-z]+\)$' d3dim700.dis | grep -v -E 'test|cmp'   # 65 writes: none sets bit 31
grep -n -F 'testb  $0x80,0x5f(%ecx)' d3dim700.dis            # 0x739521f4, the only driver-buffer gate for RS
```

The raw byte scan (python3 -I, stdlib only) looks at every encoding with a 32-bit displacement and no SIB:

```python
import struct, sys
d = open(sys.argv[1], 'rb').read(); hits = []
for i in range(len(d) - 10):
    op, m = d[i], d[i + 1]
    if op == 0x0f and m == 0xba:                                  # bts r/m32, imm8
        mm = d[i + 2]
        if mm >> 6 == 2 and (mm >> 3) & 7 == 5 and mm & 7 != 4 and \
           struct.unpack_from('<I', d, i + 3)[0] == 0x1a6c and d[i + 7] == 31:
            hits.append((i, 'bts'))
        continue
    if op not in (0x81, 0x83, 0x80, 0xc7) or m >> 6 != 2 or m & 7 == 4:
        continue
    reg, disp = (m >> 3) & 7, struct.unpack_from('<I', d, i + 2)[0]
    imm32 = struct.unpack_from('<I', d, i + 6)[0]
    if (op == 0x81 and reg == 1 and disp == 0x1a6c and imm32 >> 31) or \
       (op == 0x83 and reg == 1 and disp == 0x1a6c and d[i + 6] & 0x80) or \
       (op == 0x80 and reg == 1 and disp == 0x1a6f and d[i + 6] & 0x80) or \
       (op == 0xc7 and reg == 0 and disp == 0x1a6c and imm32 >> 31):
        hits.append((i, 'SETS BIT 31'))
    if op == 0x80 and reg == 1 and disp == 0x1a6f and d[i + 6] == 0x40:
        hits.append((i, 'control: bit 30'))
print(hits)   # 5.03.2600.5512: [(89869, 'control: bit 30')] and nothing else
              # (file offset 0x15f0d = VA 0x73956d0d, the T&L Init's orb $0x40,0x1a6f(%ecx))
```

The staged DX7 renderers were scanned by counting `call *0x9c(%e..)` (Apply), `*0xa0` (Capture), `*0xa4` (Delete) and `*0xa8` (Create) in `objdump -d` of `LIB/{UnrealGold,UnrealTournament436,DeusEx}/System/D3DDrv.dll` (0 each) and `LIB/Tribes2/GameData/OpenGL2D3D.dll` (27/3/6/0). Each count was then checked against the object loaded for that file's `SetRenderState` (`*0x50`) calls.
