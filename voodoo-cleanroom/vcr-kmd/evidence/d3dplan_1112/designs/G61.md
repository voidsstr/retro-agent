# G61 design: DirectDraw caps under-report the 2D engine (colour key, depth fill, stretch; overlay excluded)

- **Lane:** clean-room `vcr-kmd` (`vcrdd.dll` DirectDraw HAL over the 2D engine, plus one miniport Diag read), Voodoo 5 6000 in `.124`. DirectDraw only; Direct3D is touched through two read-only helpers and through D3D9 `StretchRect` / D3D8 windowed `Present`, which reach `DdBlt`.
- **Kind as filed:** fixable, "low risk, mainly CPU cost and capture limits". **What this design found:**
  1. The gap is real. The fix as filed ("report what `Dd_Blt` implements") is **not safe on its own**. On XP a HAL that claims a blit class and answers `DDHAL_DRIVER_NOTHANDLED` gives the application `E_NOTIMPL` (= `DDERR_UNSUPPORTED`). It does **not** fall back to the HEL (`/home/voidsstr/development/retro-3dfx/FINDINGS.md:1294-1296`, `KMD/README.md:690-692`, measured in the VM bed on 2026-09-26). The comments in `vcrdd_ddraw.c:370-375, 404-407, 545` and the test `test_a_blit_we_cannot_do_goes_back_to_the_hel` say the opposite. Their NOTHANDLED branches only "work" because the runtime never sends those classes to us: the caps do not claim them, so ddraw routes them to the HEL before the HAL is called. A claimed cap is a **contract**: every blit of that class must be drawn, by the engine where it is exact and by the CPU otherwise.
  2. The staged titles **do** use these classes. A static scan of the binaries (§2.4) shows:
     - Jedi Knight DF2 clears its Z buffer with `Blt(DDBLT_DEPTHFILL)` from its frame code (`JK.EXE` `0x42ae80`, called at `0x443f87`). Today the HEL does that on the CPU through the write-combined mapping, plus an engine drain in `Dd_Lock`.
     - Aliens vs Predator clears its Z the same way, twice (`avp.exe` `0x537380`, `0x5373e0`).
     - Rainbow Six, JK, MotS and AvP issue source-keyed blits (`DDBLT_KEYSRC`).
     - Halo's Bink intros do a `StretchRect` 640x480 → 1280x960 per frame. G56 traced their 14-20x slowdown to that stretch, which the runtime does on the CPU by reading video memory (G56 §0.3-0.5). The staged launcher hides this with `-novideo`.
  3. The DirectDraw-only titles named in the gap gain **nothing**, and the design says so.
     - Red Alert 2 / Yuri run DirectDraw **emulation-only** on XP: the tree's aqrit `ddraw.dll` has `ForceDirectDrawEmulation = 1` (`LIB/RedAlert2/aqrit.cfg`, kept on XP by `Launch Red Alert 2.bat`).
     - StarCraft and Warcraft II (Storm) issue plain `DDBLT_WAIT` copies only.
     - Tiberian Sun issues copies and fills. Its `DSurface::AllowStretchBlits` is `DDCAPS_BLTSTRETCH`, which would let it stretch movies, but its staged `StretchMovies=no` keeps them unstretched.
- **Priority P1.** The stretch bit fixes a visible defect in a staged title: Halo's intro and ending movies are disabled by a workaround and run 14-20x slow without it. G56 hands that fix to this item. The depth-fill bit takes a per-frame CPU Z clear out of Jedi Knight. Without those two consumers this item would be P2.
- **Effort L.** Step 0 (instrumentation, ddlab caps) is S. The contract layer, three caps, two probes and tests are L.
- **Written:** 2026-11-12. Read-only design. Nothing was built, deployed or run, and no fleet box was contacted. The only commands run were host-side reads: the code, the vendor tree, the spec as text (`soffice --convert-to txt:Text`, the same line numbers as `reports/hw.md`), the W2K DDK help, and `i686-w64-mingw32-objdump -d` of staged binaries, all in the scratchpad.
- **Sources:**
  - hal-31 (`reports/hal.md` §8, §11);
  - games-34 (`reports/games.md` §2 DirectDraw row, §3b);
  - history-50 (`reports/history.md` §3.6);
  - G56 (Halo's `StretchRect`), G10 §4.7 (depth fills on a promoted Z ride on this item), G37 (blits into textures).

| request | today | reachable today? |
|---|---|---|

| stretch | `NOTHANDLED` (`:529-532`, clipped `:429-430`) | no: HEL |

| 24 bpp surfaces, a ROP other than SRCCOPY | `NOTHANDLED` | ROPs: no (DDK: "the only ROP passed to the driver is SRCCOPY") |

### 1.3 A latent hardware bug in the keyed path

`VcrDd2dCopy` sets `CMD_XDIR` (right to left) for an overlapping copy inside one surface that moves right on the same rows (`vcrdd_2d.c:193-197`), **and** it enables the source key. SPEC §7.2.2 L1517: *"destination and source color keying, along with color conversions, cannot be used with right to left blits."* 3dfx's HAL routes exactly that case through a scan-line bounce buffer (`VH5/DDBLT32.C:1302-1430`, "HW doesn't directly support right-to-left chromakey, stretch, or conversion blits").

Unreachable today (§1.2). **Reporting `DDCAPS_COLORKEY` naively would make it reachable.**

## 2. Evidence

### 2.1 The runtime contract

- **Measured (VM bed, 2026-09-26):** *"A HAL that claims `DDCAPS_BLT` and declines a blit gets the application `E_NOTIMPL` - there is no HEL fallback for that case"* (`FIND:1294-1296`). The decline was `DDHAL_DRIVER_NOTHANDLED` (commit `b5058d2`, the ROP compare that missed `0x00CC0000`).
- **The W2K DDK agrees** for compressed surfaces: returning NOTHANDLED *"will cause DirectDraw to propagate a DDERR_UNSUPPORTED error code to the application"* (quoted in `VH5/DDINIT.C:113-118`). `DDERR_UNSUPPORTED` is `E_NOTIMPL`.
- **DDK `DdBlt` page** (`ddfncs_7lpj.htm`):
  - the driver sees only the `*OVERRIDE` colour-key flags;
  - "the only ROP passed to the driver is SRCCOPY";
  - `DDBLTFX_NOTEARING` / `MIRRORLEFTRIGHT` / `MIRRORUPDOWN` "will never be passed to the driver";
  - `IsClipped` "On Windows 2000 ... always FALSE". On XP, D3D's windowed present does arrive clipped (`KMD/README.md` d3dprobe `present`).
- **Consequence for the design:**
  - every class we claim must end `DDHAL_DRIVER_HANDLED`: drawn, or a real error such as `DDERR_WASSTILLDRAWING` or `DDERR_INVALIDRECT`;
  - `NOTHANDLED` stays only for classes we do not claim, which the runtime routes to the HEL before it calls us;
  - every such NOTHANDLED is counted and logged once (§3.1), so an unforeseen flag from a runtime shows up instead of failing silently.

### 2.2 The hardware (SPEC chapter 7)

| fact | SPEC |
|---|---|
| source/destination colour keys: inclusive ranges; 8 bpp compares the index; 16/24/32 bpp compare R, G, B **per channel**; **the top byte at 32 bpp is ignored** | §7.2.11 L1781-1793 |

| **screen-to-screen stretch blt** = command 2, `srcSize` 0x58 (w [12:0], h [28:16]); top-down, left-to-right only | §7.2.2 L1498, §7.2.7 L1634-1648, §7.3.2 L1945-1946 |

## 3. The design

### 3.0 Principles

1. **A cap is a contract.** For every class it claims, the HAL draws, with the engine where the result is exact and the CPU otherwise. It never answers NOTHANDLED for a claimed class.
2. **One decision, host-tested.** A new Win32-free header, `KMD/include/vcr_ddblt.h`, owns:
   - the caps per switch bit;
   - the classification and route of a request;
   - the colour-key rule;
   - the stretch sampling;
   - the depth-fill layout;
   - the CPU drawers;
   - the engine's stretch register list.

   It follows the pattern of `vcr_flip.h`, `vcr_rtfmt.h` and `vcr_ddheap.h`.
3. **The switch off is today's code.** With `Diag\DdBltCaps` absent, `DrvGetDirectDrawInfo` and the existing `Dd_Blt` / `clipped_blt` bodies run unchanged. The only change on that path is counter increments (Step 0). The new path is a separate function, entered only when armed.

### 3.1 Step 0: instrumentation (default ON, log only, no register change)

**What it measures:** what each title sends us today, and what the HEL does instead.

- **Counters** in `VCR_PDEV`: a `vcr_dd_bltstats` struct, zeroed after each log. Coordinate with G46/G56: if `Diag\D3DStats`'s `vcr_d3dperf` has landed, these become its fields.
  - **Blts received, by class:** copy, keyed copy, fill, depth fill, stretch, keyed stretch, clipped, other.
  - **Route taken:** engine, CPU, `WASSTILLDRAWING`, declined.
  - **The first decline of the session:** its `dwFlags` and reason code. Reasons: 1 unknown flag, 2 system memory, 3 FOURCC, 4 format mismatch, 5 engine refused on the old path, 6 rect.
  - **Locks by surface kind:** Z (`DDSCAPS_ZBUFFER`), texture, primary/flip chain, offscreen. Also "Lock found the engine busy". This is the before-picture: a title doing HEL depth fills shows **one Z Lock per frame**, and a HEL stretch shows a source and a destination Lock per frame.
  - `session_ms`, from the first counted event.
- **Logging:** one INFO line (event 511, two new `what` values, assigned at implementation; other designs claim 15-19) at the four points that already log flip stats:
  - exclusive end (`vcrdd_ddraw.c:589`);
  - DD local gone (`:312`);
  - mode off (`vcrdd.c:611`);
  - DD disabled (`:740`).

  Read it from the ring **after** the game exits. Never run `vcrctl` during a D3D game.
- **`ddlab caps`** also prints, for the HAL and the HEL: `dwCaps2`, `dwCKeyCaps`, `dwFXCaps`, `dwSVBCaps` and `dwZBufferBitDepths`. `dwCaps2` also shows whether the runtime set `DDCAPS2_PRIMARYGAMMA` (G74 territory; free here).

### 3.2 `KMD/include/vcr_ddblt.h` (new, integer only)

```c
#define VCR_DDBLT_ARM_KEY      0x01u  /* DDCAPS_COLORKEY + DDCKEYCAPS_SRCBLT          */
#define VCR_DDBLT_ARM_ZFILL    0x02u  /* DDCAPS_BLTDEPTHFILL                          */
#define VCR_DDBLT_ARM_STRETCH  0x04u  /* DDCAPS_BLTSTRETCH + FX STRETCH/SHRINK X/Y    */
#define VCR_DDBLT_ARM_CONTRACT 0x08u  /* the classes claimed since 09-26 never decline;
                                         implied by any of 0x07                        */
#define VCR_DDBLT_ARM_FORCECPU 0x80u  /* LAB ONLY: every blit of the new path by the CPU */
#define VCR_DDBLT_ARM_MASK     0x8fu

/* what DrvGetDirectDrawInfo ORs in; nothing unless armed AND the engine is usable */
void vcr_ddblt_caps(unsigned arm, unsigned engine_ok,
                    vcr_u32 *caps_or, vcr_u32 *ckey_caps, vcr_u32 *fx_caps);

unsigned vcr_ddblt_class(const vcr_ddblt_req *q, unsigned arm);    /* VCR_BC_* */
unsigned vcr_ddblt_route(const vcr_ddblt_req *q, unsigned cls, unsigned arm,
                         const vcr_ddblt_env *e);                    /* VCR_BR_* */
int      vcr_ck_match(unsigned bytespp, vcr_u32 px, vcr_u32 lo, vcr_u32 hi);
long     vcr_stretch_src(long i, long s, long d);   /* floor((2i+1)s / 2d), integer */
void     vcr_zfill_plan(unsigned label_bits, unsigned store_bits, unsigned use_fmt,
                        vcr_u32 v, unsigned *bytespp, vcr_u32 *val);
unsigned vcr_2d_stretch_seq(vcr_regw *w, /* bases, formats, skews, sizes, key, clip1 */ ...);
/* CPU drawers over byte views (1-4 bytes a pixel): copy (overlap-safe),
 * keyed copy (overlap-safe), stretch (from a temp copy when the rects overlap),
 * fill */
```

(The functions are `static __inline`, the header's existing convention.)

**The rules:**

| item | rule | why |
|---|---|---|
| `vcr_ck_match` | 8 bpp: index in [lo, hi]. 16 bpp: R, G and B of the 565 split each in range. 32 bpp: R, G and B each in range, **bits 31:24 ignored**. lo == hi (the only form we claim) is therefore whole-value equality at 8/16 bpp and 24-bit equality at 32 bpp | the engine's rule (SPEC L1786), so the engine and CPU paths agree pixel for pixel. Key values are masked to the pixel size first |
| `vcr_stretch_src` | centre sampling, integer | exact for 2x and 0.5x. The engine's own Bresenham phase may differ by one source pixel; `ddlab bltx` records the engine's map and the CPU rule is aligned to it if it differs (§8 Q3) |
| `vcr_zfill_plan` | D16 (store 16): 2 bytes, `v & 0xffff`. D24X8/D24S8 used 32/32: 4 bytes, `v` as given (byte-identical to the HEL; stencil is never read). D24 used **16/16** (a 16 bpp target over a 32-bit Z, `vcr_rtfmt.h:70-87`): 2 bytes at the Z's pitch, `(v & 0xffffff) >> 8`. G10's promoted D16 (`SF_Z32`): 32/32 gives 4 bytes, `vcr_rt_z16_to_z24(v)`; 16/16 gives 2 bytes, `v & 0xffff` | the engine reads 16/16 as the first half of each 4-byte row. A 32-bit fill there reads back as alternating words: `0x00FFFFFF` gives `0xFFFF`, `0x00FF`, ... (the old, HEL, value; §4) |

**Route for a claimed request:**

1. **Pending flip.** Destination == `flip_from` and the flip is not done → `WAIT` (`DDERR_WASSTILLDRAWING`, HANDLED). Unchanged.
2. **Geometry.** A rect outside its surface, or empty → `INVALID` (`DDERR_INVALIDRECT`, HANDLED). Today this is NOTHANDLED; the runtime validates first, so this is not expected to be reached.
3. **Unclaimed** → `DECLINE` (NOTHANDLED), counted, WARN once per reason per PDEV:
   - a source or destination in system memory;
   - a FOURCC surface (as today, `:485-486`);
   - different pixel sizes;
   - a ROP other than 0xCC;
   - a destination key;
   - mirror DDFX;
   - a flag outside §3.3's set.
4. **ENGINE** when all of these hold:
   - the engine is usable: `g2d_ok && pjRegs && !exclusive_pid`;
   - not `FORCECPU`;
   - 1, 2 or 4 bytes a pixel;
   - strides 1..0x3fff;
   - coordinates within 13 bits, and within 12 bits for a clip1 rectangle;
   - the class rule:
     - **copy:** as today;
     - **keyed copy:** not (same surface **and** overlapping rects). This removes §1.3;
     - **stretch:** not (same surface and overlapping);
     - **fill / depth fill:** as today's fill.
5. **CPU** otherwise: `VcrDd2dSync`, then the header's drawer over `pd->pvRamBase`. Also when the engine accepted nothing (`VcrDdRoom` gave up before the first write); an engine command is all or nothing.

### 3.3 `vcrdd_ddraw.c`

- **`Dd_Blt`:** after the existing TRACE line, `if (pd->dd_blt_arm) return blt_v2(pd, p);`. The old body follows unchanged, plus counters.
- **`blt_v2`** normalizes the flags before classifying:
  - `DDBLT_WAIT`, `ASYNC`, `DONOTWAIT`, `PRESENTATION`, `LAST_PRESENTATION`: dropped (hints);
  - `DDBLT_EXTENDED_FLAGS` with only `EXTENDED_LINEAR_CONTENT`: dropped;
  - `DDBLT_DDFX` whose `dwDDFX` has no bit but `DDBLTFX_NOTEARING`: dropped. Rainbow Six sends exactly this with KEYSRC (§2.4);
  - `DDBLT_ROP` with ROP byte 0xCC: a plain copy;
  - `DDBLT_KEYSRCOVERRIDE` / `KEYSRC`: the key from `bltFX` / `ddckCKSrcBlt`, as today's `:536-539`;
  - `DDBLT_COLORFILL`: fill;
  - `DDBLT_DEPTHFILL` (only with ZFILL armed): depth fill.

  Then it routes as in §3.2. Every HANDLED + `DD_OK` exit goes through one `blt_done(pd, d, route)`: counters, `pd->dd_blts++`, and **G37's texture mark** (a keyed or stretched blit into a texture must invalidate the TMU cache too).
- **`clipped_blt_v2`** (IsClipped; in practice D3D8/9 windowed `Present` and possibly `StretchRect`):
  - per clip rectangle ∩ `rOrigDest`, the same route;
  - **an engine stretch is programmed once per rectangle over the whole `rOrigSrc → rOrigDest` with clip1 = that rectangle** (command bit 23), so every rectangle is pixel-identical to the unclipped stretch. The vendor clips the same way;
  - a source == destination clipped blit is CPU, its rectangles ordered so that none reads pixels another has already written: by `dy`, then `dx`, as memmove;
  - a clipped stretch within one surface goes through a temporary copy of the source rectangle (`EngAllocMem`; out of memory → `DDERR_OUTOFMEMORY`, HANDLED).
- **`DrvGetDirectDrawInfo`:** when `pd->dd_blt_arm` and `pd->g2d_ok && pd->pjRegs`, OR in `vcr_ddblt_caps(...)` and log the caps once (511, INFO). No engine at enable time → no new caps. A later give-up is covered by the CPU route.
- **Comments** at `:370-375`, `:404-407` and `:545` are corrected to say NOTHANDLED means `E_NOTIMPL` for a claimed class (FIND:1294-1296).

### 3.4 `vcrdd_2d.c`: one new engine primitive, nothing changed in the proven ones

`VcrDd2dCopy`, `VcrDd2dFill` and the text/pattern paths are **not edited**: the router never sends them a case they draw wrongly.

New `VcrDd2dStretch(pd, dst_off, dst_stride, src_off, src_stride, bytespp, sx, sy, sw, sh, dx, dy, dw, dh, const RECTL *clip1, key, ck_lo, ck_hi)` writes, after `VcrDdRoom(pd, 19)`, the list `vcr_2d_stretch_seq()` builds:

| reg | offset | value |
|---|---|---|
| `clip0Min`/`clip0Max` or `clip1Min`/`clip1Max` | 0x08/0x0c or **0x4c/0x50** | 0 / `0x1fff1fff` (as the copy), or `(top<<16) \| (left+dsk)` / `(bottom<<16) \| (right+dsk)` |
| `dstBaseAddr`, `dstFormat` | 0x10, 0x14 | 16-byte base + skew (`base_of`), `stride \| fmt_bits<<16` |
| `srcBaseAddr`, `srcFormat` | 0x34, 0x54 | the same for the source; **same format only** |
| `commandEx` | 0x38 | key ? `CMDEX_SRC_CKEY` : 0 |
| `rop` | 0x30 | `ROP_KEYED` (as the copy) |
| `srcColorkeyMin/Max` | 0x18/0x1c | only when keyed, masked to the pixel size |
| **`bresError0`, `bresError1`** | **0x28, 0x2c** | **0**: bit 31 clear, so the engine makes its own initial error terms. Written every time, so nothing earlier can leave bit 31 set |
| **`srcSize`** | **0x58** | `(sh<<16) \| sw` |
| `srcXY`, `dstSize`, `dstXY` | 0x5c, 0x68, 0x6c | with the skews |
| `command` | 0x70 | **2** (screen-to-screen stretch) \| GO \| ROP0 0xCC \| (clip1 ? bit 23 : 0) |

Then `g2d_busy = 1`, `g2d_ops++`, as the copy. No direction bits (SPEC L1946).

The registers it leaves behind (`srcSize`, `bresError` = 0, `clip1`) are ignored by every later command: non-stretch commands do not read `srcSize`, and clip select 0 does not read clip1.

### 3.5 `vcrdd_d3d.c`: one read-only helper

`VcrDdD3dZFillPlan(pd, z, v, &bytespp, &val)`:

- **use:**

  - else the surface `z` is attached to (`lpAttachListFrom`; which list holds it is to be confirmed by `ddlab bltx zfill_1616`), through `vcr_rt_format(pd->rt32, its bpp, storage)`;
  - else the Z's own layout.
- Calls `vcr_zfill_plan`.

**No draw path changes.**

### 3.6 The caps, exactly

| `DdBltCaps` | `dwCaps` (with D3D's 3D bit) | `dwCKeyCaps` | `dwFXCaps` |
|---|---|---|---|
| absent / 0 (**today**) | `0x04020041` | 0 | 0 |
| 0x8 (contract only) | `0x04020041` | 0 | 0 |
| 0x1 | `+0x00400000` = `0x04420041` | `0x00000200` (SRCBLT) | 0 |
| 0x2 | `+0x10000000` = `0x14020041` | 0 | 0 |
| 0x4 | `+0x00000200` = `0x04020241` | 0 | `0x00015400` (SHRINKX 0x400, SHRINKY 0x1000, STRETCHX 0x4000, STRETCHY 0x10000) |
| **0x7** | **`0x14420241`** | **0x200** | **0x15400** |

The caps are the same at every depth. The runtimes cache caps read at the desktop (the runtime-22 rule), so the caps do not depend on the PDEV's bpp. This departs from G10 §4.7, which proposed the depth-fill cap at 32 bpp only. The fill plan is right at every depth, and JK, the main consumer, runs at 16 bpp.

**Deliberately not claimed:**
- `COLORKEYHWASSIST`;
- `SRCBLTCLRSPACE` and the destination keys (the engine has them, SPEC L1784, but no title needs them);
- `CANBLTSYSMEM` and every SVB cap (the vendor itself turned them off on Napalm);
- `ZBLTS`;

- `BLTFOURCC` and format conversion;
- `CANCLIP` / `CANCLIPSTRETCHED`;
- `WIDESURFACES`;
- `PALETTE`;
- **overlay** (§3.9).

### 3.7 Gating

- **`Diag\DdBltCaps`** (DWORD, absent = 0). The miniport reads it at **every `IOCTL_VCR_INFO`**, like `Accel2DText` and `DdHeapFloor` (`miniport/vcrmp.c:453-466`), masked with `VCR_DDBLT_ARM_MASK`. The next mode change picks it up, with no reboot: the runtime re-reads the DirectDraw caps at every DirectDraw enable.
- **Transport:** an **appended `vcr_info.dd_blt_caps` field** rather than new flag bits. The 32 `VCR_INFO_F_*` bits are contested: this plan's designs already claim 0x8000-0x20000 several times over. `VcrDd2dInit` then `memset`s `info` before the IOCTL (`vcrdd_2d.c:443`), so an older miniport yields 0. Positive flags are the fallback if the integrator prefers them.
- **The display driver:**
  - `pd->dd_blt_arm = info.dd_blt_caps & MASK`;
  - any of 0x07 also sets 0x08;
  - one INFO line when armed.
- **Chip-independent.** The 2D engine is the same on Banshee/Voodoo3/VSA-100, so the 86Box bed exercises it. Only the 16/16 depth layout needs `rt32` (VSA-100 + `D3D32`).
- **Default OFF** until §6 passes: the three bits, the CPU fallbacks and the stretch primitive have never run on silicon. **One Diag change per clean boot** (§6).
- **Moving the default to 0xF** needs a `MOVED_DIAG` entry with the evidence path (`tests/python/test_vcr_kmd_integration.py:86-91`).
- **`FORCECPU` (0x80)** is for a lab boot only: in-game it would run 1280x960 stretches on the CPU under the display lock.

### 3.8 What does NOT change

- The register traffic of every proven path, with the switch absent: the copy, fill, text and pattern commands, the 3D sequences, the flip, the vblank, the heap and `CanCreateSurface`.
- Direct3D: drawing, `Clear2`, TEXBLT and the D3D caps. `d3dprobe caps` must equal `caps_124.txt` field for field.
- Glide/OpenGL coexistence. The engine is used only while `!exclusive_pid`; while a Glide client owns the chip every claimed blit takes the CPU path, as unkeyed copies already do.
- SLI: DirectDraw blits use chip 0's 2D engine in a non-SLI desktop.

### 3.9 Out of scope, with reasons

- **Overlay** (`DDCAPS_OVERLAY`, YUY2/UYVY, `UpdateOverlay`): new scan-out programming on the 1998 CRT and the V5 6000's SLI video path, which 3dfx itself bent into a 3D-flip mechanism (`VH5/DDFXNT.C` overlay promotion, vendor-28). The only consumers are DOSBox `output=overlay` titles, which PASS through SDL's software YUV path (`reports/games.md` §3b). If wanted, it is a separate item, P3.
- **Capture limits** (GDI cannot photograph 8 bpp exclusive surfaces): G79.
- **8 bpp palettes:** `DrvSetPalette` works (StarCraft/WC2 PASS). `DDCAPS_PALETTE` is not needed.

### 5.3 d3dprobe: `present_stretch` and `present_shrink` (windowed)

## 8. Open questions

1. **`StretchRect` without the cap.** Does XP's d3d9 call `DdBlt` for `StretchRect` when `DDCAPS_BLTSTRETCH` is absent, and does it fall back after NOTHANDLED? G56 E3 (TRACE ring) answers it. The design is the same either way.

3. **The engine's stretch phase** against `vcr_stretch_src` (±1). Align the CPU rule to the measured map if it differs.
4. **32 bpp keys.** Does the HEL compare bits 31:24 (`key_xbyte`)? If it does, we keep the engine's rule, which matches real 3dfx hardware, and document it.

8. **Destination colour keys.** Should they be added later? The engine has them (`commandEx` bit 1, `dstColorkeyMin/Max`, ROP0 = 0xAA, rop[7:0] = 0xCC); no staged title needs them.
9. **Tiberian Sun's movies.** Should the library stage `StretchMovies=yes` in `SUN.INI` once the stretch is proven? Boxes without a hardware stretch force it off themselves (`AllowStretchBlits`). This is a library change outside this item.
