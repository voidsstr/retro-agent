## 0. Verdict

**G64 is not a driver defect.** Set it to P3. Don't change the driver. The remaining work is one cheap confirmation run
on `.124` and a guard test. The guard matters because a later allocator change could turn this into a fatal error for
two staged titles.

1. **What the Dark engine reads.** It reads `IDirectDraw4::GetAvailableVidMem` with
   `DDSCAPS_TEXTURE | VIDEOMEMORY | ALLOCONLOAD | LOCALVIDMEM`, before and after it loads a texture. It never reads
   `DDCAPS.dwVidMemFree`. If the free count does not drop, the result is **fatal**, not a warning: an `ERROR:` message
   box at exit and `exit(1)` (THIEF.EXE disassembly, section 1).
2. **Where XP SP3 gets that number.** `dxg.sys` computes it itself. It walks every DirectDraw heap's free list and alloc
   list, then **adds** whatever a driver's `GetAvailDriverMemory` reports. The `DD_HALINFO.ddCaps.dwVidMemFree` that
   `vcrdd_ddraw.c:109-110` sets is never read on that path (section 2).
3. **Why our HAL passes.** Every video-memory texture comes from that same heap:
   - the runtime places it; or
   - `mipchain_ext` / `VcrDdD3dCreateMipChain` call `HeapVidMemAllocAligned` on the heap's own `VIDEOMEMORY` entry.

   We pass a `SURFACEALIGNMENT` whose `dwFlags` is 0, so each block is non-discardable, and dxg subtracts it from "free"
   (section 3). We answer no `GUID_MiscellaneousCallbacks`, so nothing is added or double-counted.
4. **The constant is right.** `dwVidMemTotal == dwVidMemFree == he - hs` is exactly true when `DrvGetDirectDrawInfo`
   runs, because dxg builds the heap after that call returns. 3dfx's own NT driver never sets either field (a
   case-insensitive search of the H5 tree finds no `VidMemTotal`/`VidMemFree` assignment).
5. **The measurements on file agree** (section 4). In the 86Box Voodoo 3 bed, free memory sits below total by exactly
   one surface's size when a surface is outstanding. UT2003 on `.124` logs the heap size to the MiB.
6. **One trap is worth writing down** (section 5). The same fatal message appears when the **D3D HAL is missing**
   (G01/G02). In that case the Dark engine has no video-memory texture pool to measure. So on `.124` this error box
   points at the 3D engine's give-up first, not at memory accounting.

What to do: add `ddlab texmem` and a `d3dprobe` `texmem` test, add the guard test
`tests/python/test_vcr_kmd_vidmem_report.py`, and run the probe once on `.124` with no reboot, no Diag change and no
mode switch. Land the guard with or before the first of G07, G21 and G63, because those change the paths this answer
depends on.

## 1. What the Dark engine does with free texture memory (THIEF.EXE, static analysis)

### 1.1 Choosing the pool at init

`lgd3d\d6Sts_s.cpp`: the file name string is at VA 0x61adb0 and is pushed at 0x573664.

- **0x5736d7.** `IDirect3DDevice3::GetCaps` (vtable +0xc) fills two `D3DDEVICEDESC`s of 0xfc bytes. `[esp+0x98]` is the
  HAL desc's `dwDevCaps`.
- **0x57370c-0x573774.** If `dwDevCaps & D3DDEVCAPS_TEXTURENONLOCALVIDMEM` (0x1000) is set, it creates a 256x256 texture
  with caps 0x24005000 (`TEXTURE|VIDEOMEMORY|ALLOCONLOAD|NONLOCALVIDMEM`). Success sets `this+0x28 = 1` (AGP pool).
- **0x573777-0x5737cb.** If `dwDevCaps & D3DDEVCAPS_TEXTUREVIDEOMEMORY` (0x200) is set, it creates a 256x256 texture
  with caps **0x14005000** (`TEXTURE|VIDEOMEMORY|ALLOCONLOAD|LOCALVIDMEM`). Success sets `this+0x24 = 1` (local pool) and
  `this+4 = 0x14005000`.
- **No pool.** With neither, `this+4 = 0x04001800` (system-memory textures).
- **0x5737e7.** It starts on local: `this+0x20 = this+0x24`.

**On our HAL the result is local only.** `dwDevCaps` is 0x0008ae50: it has `TEXTUREVIDEOMEMORY`
(`vcrdd_d3d.c:2066-2070`) and not `TEXTURENONLOCALVIDMEM`. The HAL also lists `DDSCAPS_TEXTURE` (`vcrdd_d3d.c:2110`).

### 1.2 The query

The helper at 0x576cd0 takes two pointers, `pFreeLocal` and `pFreeAgp`.

- For each non-NULL pointer it calls `GetAvailableVidMem` on the DirectDraw object at `[0x6a6624]` (vtable +0x5c).
  The local call is at 0x576d08 with caps 0x14005000, set at 0x576cf7. The AGP call is at 0x576d2e with caps 0x24005000.
- It keeps **only the free count**. The total goes into a scratch slot.
- These are the only `GetAvailableVidMem` calls on that object in the executable.
- THIEF.EXE does call `IDirectDraw4::GetCaps` (0x56f524, 0x56f9d3). No read of `dwVidMemTotal`/`dwVidMemFree` was found
  near either call; that was not traced further.

### 1.3 The check (0x574140)

This is vtable slot 4 of all three texture-manager classes; the vtables are at VA 0x5da800, 0x5da8c8 and 0x5da988.

1. It reads the free count of each pool in use (0x574185-0x5741a6).
2. It refuses the load (returns -1, not fatal) if the current pool's free count is below the texture's recorded cost. It
   switches to AGP when that pool is allowed (0x5741ad-0x5741dc).
3. It loads the texture through the method at vtable +0x2c (0x574360). That method:
   - fills a system-memory surface (`DDSURFACEDESC2`, flags 0x1007, caps 0x1800);
   - creates the video-memory texture with the pool's caps from `this+4`;
   - locks the surface, copies, unlocks;
   - calls `IDirect3DTexture2::Load`.
4. **Measuring a new size.** If the texture's cost has not been recorded yet (the lookup at 0x574153-0x574166 gives 0),
   it reads the free counts again (0x574217-0x574238). Then:
   - local `before > after`: it records `before - after` as the cost (0x574250 / 0x574268) and succeeds;
   - otherwise, AGP pool in use and `before != after`: it records that (0x574275-0x574294);
   - **otherwise (0x574297):** `0x52e370(1, "Direct3d device driver does not accurately report texture memory usage.\n
     Contact your 3d accelerator vendor for updated drivers.")`.
5. **That call is fatal.** It is the engine's level-3 `ERROR:` path:
   - 0x52e400 picks the prefix from the table at 0x6154a8: 1 = `WARNING: `, 2 = `WARN USER: `, 3 = `ERROR: `;
   - 0x52e3a0 handles level 3: 0x52e4b0 registers an `atexit` handler (0x52e500) that calls `MessageBoxA` through IAT
     slot 0x5b626c;
   - then `exit(1)` runs (0x59ec20 calls 0x59ec60, which is `doexit(code, 0, 0)`).

So **a driver whose reported local free memory does not drop when a texture is created stops Thief Gold at the first
in-game texture of each new size.** There is a second trap: if `GetAvailableVidMem` fails, the "after" slot `[esp+0x18]`
was never initialised (only `[esp+0x10]` and `[esp+0x14]` are zeroed at 0x57414b-0x574156). The result is then
undefined, so the HRESULT matters too.

### 1.4 Which titles carry it

| title | carries the check? | evidence |
|---|---|---|
| Thief Gold | **yes** | THIEF.EXE: the string at VA 0x61add8 (file 0x2189d8) is pushed only at 0x574297 |
| Thief II retail | **yes** | `backup/thief2.exe`: the string at file 0x27cf18; caps 0x14005000 at 0x5bd7a7. Not on the play path: the staged `Thief2.exe` is NewDark |

## 2. Where `GetAvailableVidMem` gets its numbers on XP SP3 (dxg.sys, static analysis)

**The call chain.** On NT, `GetAvailableVidMem` goes through `NtGdiDdGetAvailDriverMemory` into
`DxDdGetAvailDriverMemory` **(inferred: the user-mode half was not traced)**. dxg's function table is at file offset
0xfc10: 92 `{index, function}` pairs. Index 0x1c is 0x16350; it is the only function that sums the heaps (below). The
structure it copies and writes back is `DD_GETAVAILDRIVERMEMORYDATA` exactly: `lpDD`, `DDSCaps`, `dwTotal`, `dwFree`,
`ddRVal`, `GetAvailDriverMemory`.

**What the function does:**

1. **0x16378-0x16392.** It copies the caller's 0x18 bytes and zeroes `dwTotal`, `dwFree` and `ddRVal` in the copy.
2. **0x163ad-0x163e1.** For each `VIDEOMEMORY` of the DirectDraw global (count at `+0x30`, array at `+0x34`):
   - it skips the heap if `dwFlags & VIDMEM_HEAPDISABLED` (0x20);
   - it skips the heap if `ddsCapsAlt.dwCaps & requested caps` is non-zero;
   - otherwise it adds two sums for that heap.

   | sum | helper | linear-heap routine | what it counts | where it goes |
   |---|---|---|---|---|
   | free | 0x1166e | 0x12324 | free-list bytes plus **discardable** allocated blocks | `[ebp-0x1c]` |
   | allocated | 0x1164a | 0x122fc | **non-discardable** allocated blocks | `[ebp-0x20]` |
3. **0x163e3-0x16405.** It calls the driver's `GetAvailDriverMemory` (global `+0x4e8`) only if the driver registered one.
   That is `MiscellaneousCallBacks.dwFlags & 1`, and 1 is `DDHAL_MISCCB32_GETAVAILDRIVERMEMORY` (`DDK8/ddrawint.h:346`).
   A DirectDraw object that is lost at that point gets `DDERR_SURFACELOST` instead of the call.
4. **0x16426-0x16469.** It writes back:
   - `dwTotal = driver total + free sum + allocated sum`;
   - `dwFree = driver free + free sum`.

   **The driver's numbers are added to dxg's own sums; they do not replace them.**
5. 0x1166e/0x1164a are called from nowhere else in dxg. Nothing in dxg recomputes `HalInfo.ddCaps.dwVidMemFree`.

**When a block counts as free.** The linear allocator is at 0x1212e (`linVidMemAlloc`; `HeapVidMemAllocAligned` lands
here):

- **Discardable flag.** A block is marked discardable (`VMEML.bDiscardable`, node `+0xc`, written at 0x12266) only when
  the caller's `SURFACEALIGNMENT.Linear.dwFlags & SURFACEALIGN_DISCARDABLE` (0x1, `DDK8/dmemmgr.h:63`) is set
  (0x12164-0x1216a).
- **Block size.** It is `(h - 1) * pitch + w`, rounded up to 4 (0x12196-0x121a6). A leftover of 15 bytes or less is
  absorbed into the block (0x12256-0x1225f).
- **Alignment gap.** The gap in front of the block goes back on the free list (0x12291-0x122ba).
- **A block at offset 0 is allocated and returned as 0** (0x122ef). The caller reads that as failure, so the block stays
  on the alloc list until the heap is rebuilt. That is G63's offset-0 loss (`KMD/include/vcr_ddheap.h:13-25`).

## 3. Our HAL against that rule

| path | where | the block comes from | counted by dxg as |
|---|---|---|---|
| a single-level texture with no `D3DBigTex` | runtime (`Dd_CreateSurface` returns NOTHANDLED, `vcrdd_ddraw.c:633-645`) | the DirectDraw heap, the runtime's own allocation | allocated, non-discardable **(inferred: the runtime path was not traced)** |
| every texture with `D3DBigTex` (`.124` today: 7) | `mipchain_ext`, `vcrdd_d3d.c:367-469` | `HeapVidMemAllocAligned(vm, total, 1, &al, &pitch)` at `:441`, where `vm = pd->pvmList`, the array dxg built its heap in (`vcrdd_ddraw.c:74-80`); `al` is memset at `:438` and only the alignments are set | allocated, non-discardable |
| a DXT surface `mipchain_ext` declined | `VcrDdD3dCreateTexSurface` `:473-511` | `DDHAL_PLEASEALLOC_BLOCKSIZE` (`:491`): the runtime allocates our size | allocated (inferred, as row 1) |
| a mip chain with no `D3DBigTex` | `VcrDdD3dCreateMipChain` `:522-584` | `HeapVidMemAllocAligned` at `:562`, with `al` memset at `:559` | allocated, non-discardable |
| freeing a chain | `VcrDdD3dFreeMipChain` `:586-600` | `VidMemFree` on the heap saved at allocation (`:592`) | back to free |

**Supporting facts:**

- **Every placement in the display DLL is one of three.** There are exactly three `fpVidMem =` assignments in
  `display/*.c`: `base + vcr_tex_chain_offset(...)` (`:452`), `DDHAL_PLEASEALLOC_BLOCKSIZE` (`:491`) and
  `base + mip_offset(...)` (`:572`).
- **No caps exclusion.** The heap's `ddsCaps` and `ddsCapsAlt` are 0 (`vcrdd_ddraw.c:74`, memset), so no requested caps
  exclude it.
- **No `GUID_MiscellaneousCallbacks` answer.** `DdGetDriverInfo` (`vcrdd_ddraw.c:683-706`) and `VcrDdD3dDriverInfo`
  (`vcrdd_d3d.c:2129-2235`) answer NTCallbacks, D3DCallbacks3, D3DExtendedCaps, ZPixelFormats, Miscellaneous2Callbacks
  and ParseUnknownCommandCallback. They do not answer `GUID_MiscellaneousCallbacks` (efd60cc0-...).

So every texture Thief Gold creates on `.124` lowers the local free count by its block size. On the `D3DBigTex` path
that is `vcr_tex_level_bytes(kind, w, h)` (`common/vcr_texlod.c:40-58`) rounded to 4, plus at most 15 bytes. Release
returns it. The check in 1.3 therefore passes.

**The current code is already right.** This design changes no driver code, so there is no "old path" to keep: the HAL
already gives the runtime what it needs.

## 5. The trap: the same message from a missing HAL

When the HAL is down, Thief Gold shows the same error message even though memory accounting is fine.

**How it happens.** Suppose the 3D engine has given up (G01's stale FIFO escalating, or G02's silent give-up):

- `VcrDdD3dHalInfo` returns early (`vcrdd_d3d.c:2058-2059`), so there is no D3D HAL and no `DDSCAPS_TEXTURE`.
- The Dark engine then has no device with `TEXTUREVIDEOMEMORY`, so 1.1 picks neither pool: `this+0x24` = `this+0x28` =
  0.
- At 0x574140 both pool pointers are NULL. The "after" branch has nothing to compare, so it falls through to 0x574297
  at the first texture whose cost is unknown. That is the same fatal message.

This is read from the disassembly. Whether THIEF.EXE ever reaches its texture manager on a software device, rather than
failing earlier, was not traced. So if `.124` ever shows **"ERROR: Direct3d device driver does not accurately report
texture memory usage"**, check in this order:

1. the ring for the engine give-up or a `d3d_disabled` PDEV;
2. `d3dprobe caps` `hal` / `DevCaps`;
3. only then memory accounting.

Record this in `KMD/README.md` Findings when the guard lands.

## 6. What is still worth doing

### 6.1 Probe 1: `ddlab texmem`, the Dark engine's calls replayed

Add a mode to `KMD/tools/ddlab.c` next to `caps`/`vidmem`/`zsurf`. It uses no window, no exclusive mode and no
`SetDisplayMode`, so nothing switches and it needs no pacing.

**Runner change.** In `tools/ddlab_run.py`, add `texmem` to `choices` (`:218`). Leave it out of `FULLSCREEN` and
`SWITCHES`. Read `HKLM\SYSTEM\CurrentControlSet\Services\vcrmp\Diag` (`D3DBigTex`, `D3D32`, `DdHeapFloor`) with
`REGREAD` and put it in the RESULT, so each run names the allocator path it measured.

**Steps:**

1. **Objects.** `DirectDrawCreate`, then `QueryInterface(IID_IDirectDraw4)`, the interface THIEF.EXE uses; its
   `DDSURFACEDESC2` is 0x7c bytes. Then `SetCooperativeLevel(NULL, DDSCL_NORMAL)`.
2. **Device caps.** `QueryInterface(IID_IDirect3D3)`, then `EnumDevices`. Take the HAL device's `dwDevCaps` and record
   `texvidmem` (0x200) and `texnonlocal` (0x1000). Derive the pool by the 1.1 rule (expected: `local`). No device is
   created.
3. **Warm-up.** Create and keep one 4 KB `OFFSCREENPLAIN | VIDEOMEMORY` surface. A runtime allocation survives G63's
   offset-0 block (its second pass takes the next block), just as a fullscreen game's back buffer does. Record
   `offset0_lost` = the free drop minus the warm-up's own block. Expected values:

   | heap state | `offset0_lost` |
   |---|---|
   | fresh heap, no `DdHeapFloor` | 4096 |
   | heap already used | 0 |
   | `Diag\DdHeapFloor = 1` | 0 |

   This doubles as a G63 readout.
4. **Init replay.** One 256x256 R5G6B5 `CreateSurface` with caps 0x14005000 and `DDSD_CAPS|HEIGHT|WIDTH|PIXELFORMAT`.
   Record its HRESULT, then release it.
5. **Per-texture check.** Formats: 565, 1555 and 4444 always; 8888, DXT1 and DXT5 when offered. Sizes: 1, 8, 32, 64,
   128, 256, 256x128, 256x32 (8:1); add 512, 1024 and 2048 when `D3DBigTex` bit 0 is set. Cap the total at 16 MB.
   For each texture:
   - `before = GetAvailableVidMem(0x14005000)` (keep the HRESULT and the total);
   - create it with caps 0x14005000 and **keep it**, as a game loading a level does;
   - `after` (same call);
   - `GetCaps(&hal).dwVidMemFree` before and after.
6. **Other queries** (informational). `GetAvailableVidMem` with:
   - `DDSCAPS_VIDEOMEMORY` alone;
   - 0x24005000, the AGP query;
   - `DDSCAPS_ZBUFFER | VIDEOMEMORY`.
7. **One mip chain** (informational, G07). 256x256 565 with `TEXTURE|MIPMAP|COMPLEX`, 9 levels: the total drop against
   the packed chain size.
8. **Release.** Release everything, read free again, and compare it with the value right after the warm-up.

**Verdict per texture.** It comes from a new Win32-free header, `KMD/tools/vcr_texmem.h`, shared with the native test
(the same pattern as `tools/vcr_pace.h`). The call is `vcr_texmem_verdict(before, after, d3d_bytes, alloc_bytes)`:

| verdict | condition | meaning |
|---|---|---|
| `PASS` | `d3d <= before - after <= round4(max(d3d, alloc)) + 15` | — |
| `NO_DROP` | `after == before` | **THIEF.EXE 0x574297, fatal** |
| `ROSE` | `after > before` | also fatal in 1.3 |
| `SHORT` | `0 < drop < d3d` | Thief passes, but records too small a cost |
| `OVER` | larger than the bound | another allocation in the window, or a create that failed with the G63 block lost |

`d3d` is what DirectDraw needs: `w*h*bytes`, or DXT blocks. `alloc` is the larger of that and the TMU layout,
`vcr_tex_level_bytes`. The bound is dxg's own: rounding to 4, plus a leftover of at most 15 bytes (section 2).

**Shapes the bound covers.** The bound is exact for the shapes listed, all of them at least as wide as tall:

- `mipchain_ext` asks for `total x 1` bytes (`:441`), so the pitch never enters;
- the runtime's `(h - 1) * pitch + w * bytes` equals `d3d` whenever a row is a whole number of DWORDs.

A texture narrower than it is tall at 16 bpp (1x256, for example) would carry the runtime's row padding **(inferred:
the pitch the runtime asks for was not traced)**, so the list leaves such shapes out.

**RESULT** (one JSON line):

```
{"mode":"texmem","diag":{...},"devcaps":"...","pool":"local","init_hr":"00000000",
 "offset0_lost":N,"textures":N,"created":N,"create_fail":[...],"pass":N,"no_drop":0,"rose":0,
 "short":0,"over":0,"gav_hr_bad":0,"caps_free_moves":true|false,"vidmem":{...},
 "nonlocal":{"hr":"...","total":N,"free":N},"zbuf":{...},"mipchain":{"bytes":N,"drop":N},
 "start_free":N,"end_free":N,"leak":N,"dark_check":"pass"|"FAIL"}
```

**Pass criterion:**

- `init_hr` is DD_OK;
- every `GetAvailableVidMem` HRESULT is DD_OK;
- every created 16-bit texture is `PASS`;
- `leak == 0`, i.e. free after release equals free after the warm-up.

`dark_check` is `pass` exactly when those hold for the 16-bit sizes, which are the ones the Dark engine uses.
`caps_free_moves`, `nonlocal`, `zbuf` and `mipchain` are recorded, not judged (section 9).

### 6.2 Probe 2: `d3dprobe` test `texmem`, the D3D8 analogue

Add it to `tools/d3dprobe.c` as a render-mode test: `d3dprobe render --tests texmem`. It runs windowed in a 256x256 back
buffer, so there is no switch and no pace.

**What it does:**

1. Reads `IDirect3DDevice8::GetAvailableTextureMem` into `m0`.
2. Creates **64 R5G6B5 textures of 256x256**, one level, `D3DPOOL_DEFAULT`; that is 8,388,608 B. It fills each by
   `LockRect`, and the last one is a 4-quadrant colour checker.
3. Reads the value again into `m1`.
4. **Draws** one full-window point-sampled quad with the last texture and checks the four quadrant colours with
   `expect()`. This shows that a texture placed by the counted path also samples.
5. Releases everything and reads the value into `m2`.

**Reference value: 8,388,608 B.** Pass when:

- `|(m0 - m1) - 8,388,608| <= 1 MiB`. The tolerance allows for the runtime rounding to whole MBs **(inferred)** and for
  the allocator slack, at most 64 x 18 B;
- `|m2 - m0| <= 1 MiB`;
- all four pixels match within the existing tolerance.

The test passes on both texture paths: 565 at 256x256 is in the default list. It covers what D3D8 titles see (UE2's
"Video memory on board", Halo's texture budgeting), through the same dxg function **(inferred: `d3d8thk` path not
traced)**.

## 8. Regression tests

### 8.1 `tests/python/test_vcr_kmd_vidmem_report.py` (new): the guard

Source assertions, in the style of `test_vcr_kmd_ddraw.py`. The docstring carries the evidence above: md5s, addresses,
and the dxg rule "free = free list + discardable; driver figures are added".

1. **`test_halinfo_reports_the_empty_heap_as_free`.**
   - `DrvGetDirectDrawInfo` assigns `dwVidMemTotal = he - hs;` and `dwVidMemFree = he - hs;`.
   - The heap entry uses the same `hs`/`he` (`vm->fpStart = hs`, `vm->fpEnd = he - 1`).
   - `dwVidMemFree` is assigned nowhere else in `display/*.c`. A "fix" that reported a smaller, fake value would make it
     disagree with `GetAvailableVidMem`.
2. **`test_no_getavaildrivermemory_is_registered`.**
   - Neither `0xefd60cc0` (`GUID_MiscellaneousCallbacks`) nor `DDHAL_MISCCB32_GETAVAILDRIVERMEMORY` appears in
     `display/*.c`.
   - The checker function is also run on a synthetic snippet that registers the callback, and must flag it. This
     asserts the forbidden shape as well as the current one.
   - Why: dxg adds a driver's figures to its own heap sums, so a callback that walks the DirectDraw heaps (as
     `VH5/DDMEMMGR.C:737` does) counts the memory twice. Such a callback may report only memory *outside* those heaps.
3. **`test_every_texture_placement_comes_from_the_directdraw_heap`.**
   - The right-hand sides of `fpVidMem =` in `display/*.c` are exactly the three in section 3.
   - Each `base` is assigned from `HeapVidMemAllocAligned(vm, ...)` in the same function, with
     `vm = (VIDEOMEMORY *)pd->pvmList`.
   - The free uses `VidMemFree((PVOID)s->lpGbl->dwReserved1, ...)`, and `dwReserved1` holds `vm->lpHeap`.
4. **`test_heap_blocks_are_never_discardable`.**
   - Every function that calls `HeapVidMemAllocAligned` memsets its `vcr_surfalign` and never assigns `.dwFlags`.
   - `SURFACEALIGN_DISCARDABLE` appears nowhere in `display/*.c`.
5. **`test_dark_engine_rule_model`.** A small Python model of the two disassembled rules:
   - `dxg_free(free_blocks, allocs)` = sum of free blocks + sum of discardable allocations;
   - `thief_texture_ok(before, after)` = `before > after`.

   The model must give:

   | case | result |
   |---|---|
   | our shape (non-discardable block of `s` bytes) | `after = before - s`, ok |
   | **the old-buggy / forbidden shapes**: a discardable block, a private pool outside the heap, or a constant report | `after == before`, **fatal** |
   | a device with no video-memory texture pool (section 5) | **fatal** |

### 8.2 `tests/native/test_vcr_kmd_texmem.c` (new): the probe's verdict

It compiles `KMD/tools/vcr_texmem.h` and `KMD/common/vcr_texlod.c` and asserts:

- **`PASS`** for `drop = round4(alloc)` and for `drop = round4(alloc) + 15`;
- **`NO_DROP`** for `drop = 0`, the value that stops THIEF.EXE;
- `ROSE` for a negative drop;
- `SHORT` for `drop = d3d - 4`;
- `OVER` for `drop = round4(alloc) + 16`;
- the header's TMU size formula equals `vcr_tex_level_bytes()` for every kind at sizes 1..2048 and aspects up to 8:1,
  so the bound cannot drift from the allocator.

## 10. Risk to proven paths

**None.** No driver code changes:

- the default 16 bpp HAL, the flip path, SLI state and Glide/OpenGL coexistence are untouched;
- the guard test only constrains future changes.

**The probes:**

- `ddlab texmem` allocates at most about 16 MB of textures in the desktop heap and frees them. It makes no mode switch
  and no ExtEscape.
- On a fresh heap without `DdHeapFloor`, the warm-up loses one 4 KB block at offset 0 until the next mode set (G63). That
  is harmless and is reported.
- `d3dprobe texmem` uses the windowed device every `render` run already uses.

**Who must honour the guard.** Any later change to these must keep "every video-memory texture is a non-discardable block
of the DirectDraw heap, or is reported through a callback that counts only memory outside the heaps":

- the texture allocator: G07 whole-chain reservation, G21 default-path placement, G63 heap floor;
- render-target texture placement (G36);
- any private texture pool.

Otherwise Thief Gold and SS2 exit at their first in-game texture. The guard test is what makes that visible.

## 12. Open questions

1. **Does XP's `GetCaps` return a live `dwVidMemFree`, or the snapshot from `DrvGetDirectDrawInfo`?** dxg never
   recomputes it, so it is live only if user-mode `ddraw.dll` refreshes it through `GetAvailDriverMemory`; that was not
   traced. `ddlab texmem`'s `caps_free_moves` answers it. No driver fix is possible either way. It matters only if a
   staged title reads it:
   - THIEF.EXE's memory logic does not;
   - UE1 `D3DDrv.dll` logs `D3D Device %iK vram, %iK free` (Unreal Gold, UT 436, Deus Ex), but those renderers are
     dormant on `.124` (G82) and their source call was not traced.
2. **Does a `DDSCAPS_NONLOCALVIDMEM` query count our local heap?** The dxg loop at 0x163b7 tests only
   `VIDMEM_HEAPDISABLED` and `ddsCapsAlt`. User-mode `ddraw` may answer non-local queries itself. UT2003 logs "no AGP
   support detected" and 58 MB, not about 117, so D3D8 at least does not double the figure.

   If the probe shows the local heap answering an AGP query, a one-line, default-OFF fix exists: put
   `DDSCAPS_NONLOCALVIDMEM` in our heap's `ddsCaps` and `ddsCapsAlt` (`vcrdd_ddraw.c:74-78`), which says "this heap
   cannot hold non-local surfaces". Do it only if a staged title is shown to misread it; THIEF.EXE queries AGP only with
   `TEXTURENONLOCALVIDMEM`, which we never report.
3. **Does `SHOCK2.ICD` carry the same check?** It is encrypted (SafeDisc v1), so this is inferred from Thief Gold and
   retail Thief II. The in-game run settles it.
4. **Can the agent drive the Dark-engine menus** (`UICLICK`/`UIKEY`) to reach a mission unattended, or does the in-game
   half need a person? Sweeps so far only reached the menu and force-closed Thief Gold. SS2 was quit "via its menu" on
   09-29.
5. **The vintage lane** (not this lane's change, but found here). `VH5/DDFXNT.C:1634-1641` says that once
   `GETAVAILDRIVERMEMORY` is registered "DirectDraw asks US and publishes nothing of its own". XP SP3 dxg **adds** the
   driver's figures to its own heap sums (0x16405-0x16469).
   - Its measured 0/0 fits the degenerate heaps of `V56K-256MB-READINESS.md:261` better.
   - Its heap-walking `memMgr_queryAvailMemory` (`VH5/DDMEMMGR.C:737`) would double-count once those heaps are real.
   - Someone working in `retro-3dfx` should add a `FINDINGS.md` note.
6. **If a private texture pool is ever needed** (G07, G36), how should it be reported? Under dxg's rule, a pool carved
   from the heap is already counted as allocated. Its callback should therefore report `dwTotal = 0` and
   `dwFree = the pool's unused bytes`. A pool outside the heap reports both. The guard test's checker would need that
   exception written into it.
