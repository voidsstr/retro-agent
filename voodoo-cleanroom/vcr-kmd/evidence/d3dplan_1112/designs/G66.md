## 0. Verdict

The gap is real for all three titles. Its two "very likely / inferred" statements are now settled from the
binaries, and one of them turns out to be wrong in a way that matters.

1. **Red Faction reads its mode from HKCU and has never read HKLM (read).**
   - `rf.exe`'s registry wrapper (`vsdk\os\registry.cpp`) starts every lookup with root
     `0x80000001` = `HKEY_CURRENT_USER` (`mov ebp, 0x80000001` at VA `0x52b2b3`).
   - The five video reads pass a NULL subkey (VA `0x4b1480`-`0x4b14f5`), which keeps that root and the base path
     `Software\Volition\Red Faction`.
   - The launcher (`LIB/RedFaction/Play Red Faction.bat:55-59`, rendered from `SPECS/RedFaction.json`) and the agent
     (`GR:1041-1043`) both write **HKLM**. So every box runs `rf.exe`'s built-in defaults, **640x480 at 16 bpp**
     (the default arguments at `0x4b1480`, `0x4b149d`, `0x4b14b3`).
   - That is exactly what every measurement shows: both 11-08 sweeps (640x480), the 09-29 scan-out (640x480x16@85),
     and every compat row that records a game mode (`.124`, `.133`, `.246`: 640x480).
2. **Writing the staged 32 bpp where it is read would stop Red Faction starting on `.124` (read + measured).**
   - For PCI vendor `0x121a`, `rf.exe` hard-codes `AutoDepthStencilFormat = D3DFMT_D16` at every colour depth
     (`0x544756` → `0x5446f6`). At 32 bpp it asks for an `A8R8G8B8` back buffer (`0x5446a1`-`0x5446b5`).
   - vcr-kmd refuses a 32 bpp target over a 16-bit Z (`KMD/include/vcr_rtfmt.h` `vcr_rt_format`,
     `KMD/display/vcrdd_d3d.c:1195`). The refusal was measured on 11-12: `CreateDevice 8876086c`
     (`ONBOX/README.md` run #4). This is G10.
   - So the depth must be chosen **per box**: 16 where the vcr-kmd miniport runs (until G10 is proven), 32 elsewhere.
     The agent must **not** own the depth.
3. **Thief Gold and System Shock 2 are not "incapable" (read).** `FR/PER-TITLE-STATUS.md` and `GR` `gr_incapable[]`
   say "`game_screen_size` is a NewDark cvar; vanilla Dark is 640x480". Both halves are wrong:
   - **The variable exists.** Vanilla `THIEF.EXE` builds `"%sscreen_size"`, `%sscreen_depth`, `%sscreen_flags`,
     `%sfull_screen` and `%shardware` from a prefix: `""` for the default mode (the menus) and `"game_"` for the
     in-game mode.
   - **SS2's own `shock.cfg` uses the same family:** `screen_size 640,480` and `game_screen_depth 16`
     (`LIB/SystemShock2/shock.cfg:25-29`).
   - **The limit is real, but it is a mode table, not an absence.** A size is accepted only if it is in the
     engine's fixed table (`THIEF.EXE` VA `0x615f40`). Its 4:3 sizes are 640x480, 800x600, 1024x768 and 1600x1200,
     plus 1280x1024 (5:4). It has **no 1280x960 and no 16:9 mode**.
   - **So the answer is a ladder:** the largest of 640x480 / 800x600 / 1024x768 that the box's 4:3 target reaches.
     That is **1024x768 on `.124`** and on the four 1080p boxes, and 800x600 on `.171`.
   - **The menus stay 640x480 by the engine's design.** That is why the 11-08 sweeps, which only reached the
     menus and the intro, could not have shown the in-game mode either way.
4. **No HAL change, so no Diag switch.** The fix lands through the project's staged-game loop:
   - fix the generators;
   - purge and redeploy on `.124`;
   - check fullscreen **in game**, attended;
   - then push to every box.

   **P1**, effort **M**. G10 owns raising Red Faction to 32 bpp on `.124`. This design hands it the exact lines
   (4.5).

## 2. Red Faction: what `rf.exe` reads (read)

Binary: `LIB/RedFaction/rf.exe`, md5 `0ba3b15d64a702333a4d9a0815f782b7`, 1,773,568 bytes (the build G10 analysed).
In this PE a `.text`/`.data` VA is the file offset + `0x400000`.

### 2.1 The registry path

| VA (file offset) | bytes / code | meaning |
|---|---|---|
| `0x4b2420`-`0x4b2554` | four command-line options set 640x480 / 800x600 / 1024x768 / 1280x1024 directly; **none present → `[0x7d938c] = -1`** | the staged launcher passes no switch |
| `0x4b10ff`-`0x4b1109` | `[0x7d938c] == -1` → `call 0x4b1480` | the registry is read |
| `0x4b1480` (`0xb1480`) | `6a10 6898947d00 68f4145a00 6a00 ... e8→0x52b7d0` | `Resolution Bit Depth`, default **16**, subkey **NULL** (`6a 00`) |
| `0x4b149d` | `6880020000 ... 680c155a00 6a00 e8→0x52b7d0` | `Resolution Width`, default **640**, subkey NULL |
| `0x4b14b3` | `68e0010000 ... 6820155a00 6a00 e8→0x52b7d0` | `Resolution Height`, default **480**, subkey NULL |
| `0x4b14c9` / `0x4b14df` | same shape | `Resolution Backbuffer Format` (default -1), `Selected Video Card` (default 0) |
| `0x52b7d0` → `0x52b4a0` | `RegOpenKeyExA(root, path, 0, KEY_QUERY_VALUE)` + `RegQueryValueExA`; on failure the default is stored | a missing value = the default |
| `0x52b2a0`-`0x52b2b8` (`0x12b2b3`) | `bd 01 00 00 80` = `mov ebp, 0x80000001`; `test ebx, ebx`; `0f 84` → `0x52b39e` | **root = HKEY_CURRENT_USER**; a NULL subkey takes the base path with that root |
| `0x52b2be`-`0x52b2ce` | `_strnicmp(subkey, "hkey", 4)` | only a subkey that **starts with `hkey`** can name another root (parsed at `0x52b3e0`; `0x80000002` is returned only there, `0x52b43e`) |
| `0x4b2322`-`0x4b232c` | `0x52b570("Volition", "Red Faction")` | base path = `Software\` + `Volition` + `\` + `Red Faction` |

So `rf.exe` reads `HKCU\Software\Volition\Red Faction\{Resolution Width, Resolution Height, Resolution Bit Depth,
Resolution Backbuffer Format, Selected Video Card}`. These are the same key and hive as `UpdateRate` and `Vsync`, which
`install.reg:37-43` already writes and which are proven to work (the multiplayer fix, `README-FLEET.txt`).
A failed read logs `Couldn't find registry key '%s', using default value.` (`0x52b548` → `0x5a6d60`). That is the
line `install.reg:8-9` reports seeing, so the defaults path is also the observed one.

**Why HKLM was believed.** `FR/PER-TITLE-CHANGES.md:65` named HKLM and added "Confirm the hive on a box that has run
the game". That was never done. The hive matches the `InstallPath` key that the vendor launcher `RedFaction.exe` builds
with an explicit `"hkey_local_machine\software\"` prefix (`install.reg:5-6`). That is a different call. The resolution
reads carry no such prefix. The value names were read from `rf.exe` (correct); the root was not.

### 2.2 What `rf.exe` does with the depth: `gr_d3d_init`, VA `0x5444b0`

The `D3DPRESENT_PARAMETERS` are at `0x1cd42b0`; 13 dwords are zeroed at `0x5445fd`.

| VA | what | result |
|---|---|---|
| `0x5444da`-`0x5444f3` | bit depth other than 16 or 32 | forced to 16 |
| `0x544634`-`0x544668` | `Vsync` (HKCU, same wrapper) | `FullScreen_PresentationInterval` = ONE when non-zero, IMMEDIATE when 0 (`install.reg:43` stages 0; G65) |
| `0x544664`-`0x5446b5` | 4th argument = `Resolution Backbuffer Format` (passed as `gr_init`'s 10th argument from `[0x5a127c]`; default -1) | if ≥ 0 it is used as is; otherwise **16 → R5G6B5 (23), anything else → A8R8G8B8 (21)** |
| `0x544756`-`0x54476f` → `0x5446f6` (`0x1446f6`: `c705 d442cd01 50000000`) | VendorId `0x121a` (both of its flag branches) | **`AutoDepthStencilFormat = D3DFMT_D16` (80) at 16 AND 32 bpp** |
| `0x5447b4`-`0x5447c1` | VendorId `0x10de` | D24S8 (75) at 32 bpp, D16 at 16 |
| `0x544784`, `0x5447d7` | VendorId `0x102b` | D32 (71) |
| other vendors | | D16 |
| `0x54471d` | `CreateDevice(adapter, HAL, hwnd, SOFTWARE_VERTEXPROCESSING, &pp)`, `Flags = LOCKABLE_BACKBUFFER`, refresh 0 | failure → `"Unable to initialize DirectX 8.0 -- Device creation failed!"` (`0x5a99d4`), handed to the fatal-error routine `0x50b1d0` (the code loops back to the call, so it does not return) |

(G10's section 2 says the format is overridden "by a matching adapter mode's format (`0x544694`)". On this reading,
`0x544694` is the branch for the `Resolution Backbuffer Format` registry value. Pinning that value (4.1) removes the
question either way.)

What a 32 bpp setting does on each kind of box:

| box | VendorId | 32 bpp asks for | outcome |
|---|---|---|---|
| `.124` today (vcr-kmd, any Diag state) | `0x121a` | A8R8G8B8 + D16 | **refused**: `vcr_rt_format(rt32, 32, 16) = VCR_RT_REFUSED`, `ContextCreate` → `DDERR_INVALIDPIXELFORMAT`, then `CreateDevice` fails (measured with the d3dprobe replay, `ONBOX` run #4). Red Faction would then show "Device creation failed!", and the runtime's revert costs the CRT two re-syncs 156 ms apart (G11). |
| a V4/V5 on 3dfx's own HAL (AmigaMerlin, vintage H5) | `0x121a` | A8R8G8B8 + D16 | works: 3dfx stores such a Z at 32 bits (`VH5/DDSURF.C:592-627`, cited by G10 §3) (inferred for this title) |
| NVIDIA | `0x10de` | A8R8G8B8 + D24S8 | works (inferred) |
| Intel / ATI / other | | A8R8G8B8 + D16 | mixed depths; usually supported (inferred). Verify in the push (8.4). |
| any box at 16 bpp | | R5G6B5 + D16 | the proven pair; on `.124` d3dprobe `render --full 640x480x16` is 40/0 on vcrdd 95678704 (`ONBOX` run #18) |

## 3. The vanilla Dark engine: the variable exists; the size is checked against a table (read)

Binary: `LIB/ThiefGold/THIEF.EXE`, md5 `8dd515df75176bcd1caaf65a93f47d81`, 2,240,000 bytes. Its window title is
`Thief  1.37` (sweep).

| VA | code | meaning |
|---|---|---|
| `0x415c86`-`0x415cb7` | `0x43b190(&mode, "")` (prefix at `0x6261c0` is an empty string), then `0x43adb0` | the **default** mode, used by the menus/metagame: `screen_size`, `screen_depth`, `screen_flags`, `full_screen`, `hardware` |
| `0x41081a`-`0x410836`, `0x4fd120`-`0x4fd135` | `0x43b190(&mode, "game_")` (`0x5e1a10`, `0x60e138`); merged over the default by `0x43b140`, field by field (flag bits 1/2/4) | the **in-game** mode: `game_screen_size`, `game_screen_depth`, ... |
| `0x43b190`-`0x43b20b` | `sprintf("%sscreen_size")` (`0x5ea4b8`), then `0x54a190` reads a **2-int array** | `game_screen_size W H` |
| `0x54a190`-`0x54a28a` | tokens end at whitespace (ctype mask 8) **or `,`** | `1024 768` and `1024,768` both parse (SS2 ships the comma form) |
| `0x43b320` (`0x5ea508`) | writes `game_screen_size` / `game_screen_depth` back into the config | the options screen persists a choice (where it is saved to is unread: open question 2) |
| built-in defaults `0x5ea460` / `0x5e1a40` | flags 7, 640, 480 | 640x480 when no cfg sets a size |
| `0x43a380` → `0x537380` → `0x5373b0` | the requested (w, h, depth, flags) must match an entry of the static table `0x615f40` that is in the runtime list `0x742784`; otherwise -1, and `0x43b10f` returns failure | **a size not in the table is never set.** What the engine falls back to is unread; the ladder never asks for such a size. |
| `0x615f40` (file `0x213b40`), 12-byte records | 87 entries | 4:3: 320x240, 400x300, 512x384, **640x480, 800x600, 1024x768, 1600x1200**; also 1280x1024 (5:4), and the non-square-pixel VGA/EGA modes 640x350/400, 320x200/400/480, 360x200/240/400. **No 1280x960, and nothing wider than 640 that is not 4:3 or 5:4 (no 16:9).** The sizes from 640x480 up exist at 8, 15, 16, 24 and 32 bpp, so the depth the engine picks at 640x480 also exists at 1024x768. |

**System Shock 2.** `SHOCK2.ICD` (md5 `9ba459f03ff6853cbdb2b91831434f6e`) is SafeDisc v1. Its `.text` has entropy
7.99 and its strings are encrypted, so its code and table cannot be read statically. Two facts tie it to the same
engine code:
- `shock.cfg:25-29` (shipped by Looking Glass) sets `edit_screen_depth 16`, `game_screen_depth 16`,
  `screen_depth 16`, `screen_size 640,480` and `hardware 1`. Those are the same variables with the same `""` /
  `game_` / `edit_` prefixes.
- The `.133` row shows SS2 in game at 640x480x16 with no `game_screen_size` set, which is the behaviour of the
  default-plus-game merge above.

Its table is inferred to match Thief Gold's at 640/800/1024. The on-box run confirms it (8.3).

**NewDark is different, which is why Thief II already works.** NewDark 1.26's `Thief2.exe` table contains 1280x960
and 16:9 sizes (1280x720, 1360x768, 1366x768, ...). That is why `Play Thief 2.bat` hands it `%FR_W% %FR_H%`. A
vanilla engine handed the same values would be asked for a size it does not have.

**In-game only.** `game_screen_size` changes the mission view. The menus, briefings and loadout run in the default
mode (640x480). On every box today game mode = menu mode = 640x480, so the engine never switches modes between menu
and mission. After this change it does (risk, section 9).

## 4. Approach

### 4.1 Red Faction: write HKCU, choose the depth per box, pin the back-buffer format

**(a) The launcher block, one source of truth in `SF`.** The disc-mount launcher's text comes from
`SPECS/RedFaction.json` `fleetres_block`. `SF`'s `TITLES["RedFaction"]` record stages `FLEETRES.EXE`/`.BAT`
(`patch_launcher` skips a launcher that already calls the block). This is the Serious Sam arrangement. Add to `SF`:

```python
def redfaction_mode():
    r"""Red Faction keeps its mode in HKCU\Software\Volition\Red Faction - rf.exe's
    registry wrapper starts at HKEY_CURRENT_USER (mov ebp,0x80000001 at 0x52b2b3) and
    the five video reads pass a NULL subkey (0x4b1480). HKLM was written here until
    2026-11 and is never read: every box ran rf.exe's defaults, 640x480x16.

    THE DEPTH IS PER BOX. rf.exe asks D3DFMT_D16 on every 3dfx card at ANY depth
    (0x544756 -> 0x5446f6) and an A8R8G8B8 back buffer at 32 bpp (0x5446a1); vcr-kmd
    draws a 32 bpp target only over a 32-bit Z (vcr_rtfmt.h vcr_rt_format, G10), so
    there "Device creation failed!". 16 where the vcrmp miniport RUNS (the newdark /
    halo test: a key left behind by a rollback must not count), 32 everywhere else.
    WIDEN THIS WHEN G10 IS PROVEN (Diag D3DSafe bit 3 with D3D32 -> 32).

    Resolution Backbuffer Format = 0xffffffff (-1: derive from the depth, rf.exe's own
    default) so a format left by the vendor launcher's Setup cannot override the
    depth chosen here (0x544694)."""
    return ([
        'rem ---- per-box D3D COLOUR DEPTH - see stage-fleetres.py redfaction_mode ----',
        'set RF_BPP=32',
        'sc query %s 2>nul | find /i "RUNNING" >nul && set RF_BPP=16' % VCRKMD_SERVICE,
    ] + reg_cfg("HKCU", "SOFTWARE\\Volition\\Red Faction",
                [("Resolution Width", "dword", "%FR_W%"),
                 ("Resolution Height", "dword", "%FR_H%"),
                 ("Resolution Bit Depth", "dword", "%RF_BPP%"),
                 ("Resolution Backbuffer Format", "dword", "0xffffffff")]))
```

- `TITLES["RedFaction"]` becomes `rec('cd /d "%~dp0"', [CALL] + redfaction_mode())`.
- `SPECS/RedFaction.json` `fleetres_block` becomes exactly `"\r\n".join([CALL] + redfaction_mode())`. A test pins the
  two together (7.1). Update its `_note`.
- Regenerate with `make-mount-launcher.py --spec SPECS/RedFaction.json --out "LIB/RedFaction/Play Red Faction.bat"`.
  It writes through `libwrite`, one verified file at a time.
- `%RF_BPP%` is set before the `( ... )` block, so the parse-time expansion inside the block sees it.
- No value contains `(` or `)`.
- `FLEETRES -reg` parses `0xffffffff` with `strtoul(.., 0)`, so it stores `0xFFFFFFFF`, which `rf.exe` reads as -1
  (`cmp eax, 0; jl`).

**(b) The agent rows (`GR:1041-1043`):**

```c
/* Red Faction: rf.exe's registry wrapper (vsdk registry.cpp) starts at HKEY_CURRENT_USER
 * (0x52b2b3) and reads the mode with a NULL subkey (0x4b1480). These rows wrote HKLM until
 * 2026-11, which rf.exe never opens - every box ran its defaults, 640x480x16. The colour
 * depth is deliberately NOT here: the launcher chooses it per box (16 where vcr-kmd runs,
 * G10), and a second writer with a constant would fight it - and a constant 32 makes
 * rf.exe ask A8R8G8B8 + D16, which vcr-kmd refuses. */
{ "RedFaction", GR_OP_REG, "HKCU", "SOFTWARE\\Volition\\Red Faction", "Resolution Width",  "dword:%W%" },
{ "RedFaction", GR_OP_REG, "HKCU", "SOFTWARE\\Volition\\Red Faction", "Resolution Height", "dword:%H%" },
```

**(c) Why the agent must not own the depth.**
- **The right answer depends on the running display driver**, which `gameres.h` (Win32-free, decided from the
  monitor) does not see.
- **Two writers with different answers rewrite each other** on every GAMERES pass after a launch. That is the
  project's signature fault (`CLAUDE.md`, "A file BOTH writers touch must get the SAME number from each").
- **The old row's constant 32 is exactly the value that breaks `.124`** once HKCU is the target. The safe outcome
  when the launcher never ran is no value at all, which `rf.exe` reads as its default of 16.

**(d) The two halves can land in either order (read from the code above):**

| agent rows | launcher | what `rf.exe` gets on `.124` |
|---|---|---|
| old (HKLM) | old (HKLM) | defaults 640x480x16 (today) |
| old | **new** | 1280x960 at 16 (the launcher's values; the agent's HKLM writes are inert) |
| **new** | old | 1280x960 (agent) at 16 (no depth value: the default) |
| **new** | **new** | 1280x960 at 16 (vcr-kmd), and 1280x960 / 1920x1080 at 32 on other boxes |

**(e) The HKLM values the old rows left on every box are inert.** `rf.exe` opens HKLM only for a subkey that starts
with `hkey`, and its video reads never do. GAMESYNC never deletes, so they stay. The test box's purge removes them
(8.2). Nothing else needs to.

### 4.2 Thief Gold and System Shock 2: one 4:3 ladder, both writers

**(a) The ladder lives in `GR` as data,** so the C, the Python generator and the tests read one list:

```c
/* THE VANILLA DARK ENGINE (Thief Gold 1.37 THIEF.EXE; System Shock 2 1.15, whose SHOCK2.ICD
 * is encrypted - inferred to share the table). game_screen_size sets the IN-GAME mode only
 * (prefix "game_", 0x41081a/0x4fd120); the menus keep the default screen_size (640x480).
 * The size must be an entry of the fixed mode table (THIEF.EXE 0x615f40, searched at
 * 0x5373b0): its 4:3 sizes are 640x480, 800x600, 1024x768 and 1600x1200 - NO 1280x960 and
 * nothing 16:9 - so %W43% (1280x960 on .124 and the 1080p boxes) asks for a size the engine
 * does not have. 1600x1200 is left out: no box's 4:3 target reaches it and SS2's own table
 * cannot be read. NewDark (Thief2) has a different table and keeps %W% %H%. */
GR_DATA const gr_res_t gr_dark_ladder[] = { {640, 480}, {800, 600}, {1024, 768} };
#define GR_DARK_LADDER_N ((int)(sizeof(gr_dark_ladder) / sizeof(gr_dark_ladder[0])))

GR_FN gr_res_t gr_dark_res(int w43)
{
    gr_res_t r = gr_dark_ladder[0];
    int i;
    for (i = 1; i < GR_DARK_LADDER_N; i++)
        if (w43 >= gr_dark_ladder[i].w)
            r = gr_dark_ladder[i];
    return r;
}
```

- **New tokens in `gr_expand`:** `%DARKW%` → `gr_dark_res(t->w43).w`, and `%DARKH%` → `.h`. Document them in the
  token list beside `%T2SEL:W%`.
- **Rows:**

## 9. Risk to proven paths

- **vcr-kmd code: none.** The default 16 bpp HAL path, Glide/OpenGL coexistence, SLI state and the flip path are not
  touched. No Diag value changes.
- **Red Faction on `.124`.** It moves from 640x480x16 to 1280x960x16 on the same proven 16/16 path.
  - Buffers grow from about 1.8 MB to about 7.4 MB (front, back and Z); the heap is about 60 MB.
  - Fill per frame grows 4x on one VSA-100 (G50/G51).
  - The 16 bpp flip rate (G59, 42-47 flips/s at 85 Hz) and the per-vertex PIO cost (G47/G48) apply as before. Red
    Faction stages `Vsync=0` (G65), so it presents immediately.
  - If it turns out unplayable at 1280x960, that is a G46 performance finding to raise with the user, not a reason to
    pin a lower staged resolution (open question 5).
- **Red Faction on other boxes.** It moves from 640x480x16 to `FR_W x FR_H` at 32 bpp, a path no box has run (the
  value never landed).
  - The GeForce path (D24S8) is ordinary.
  - The Intel/ATI path (A8R8G8B8 + D16) depends on the driver.
  - 8.4 measures one box per family before the claim is made.
- **Dark titles, everywhere.**
  - **A new mode switch.** Menu (640x480) ↔ mission (1024x768) switches now happen in every session; until now the
    two modes were equal, so the engine never switched.
  - **On `.124`** each switch tears down and rebuilds a DX6 device across a mode change: the territory of G43 R1
    (`DestroyDDLocal` after `DrvDisablePDEV`), G39 (stale VRAM at the new mode) and G41.
  - **Precedent that bounds it:** Jedi Knight switches between its 8 bpp DirectDraw menus and its 16 bpp D3D game at
    1280x960 and played on vcr-kmd on 09-28.
  - **Mitigation:** the run is attended and the ring is saved after each title (8.3).
- **Agent release.** The GAMERES half is data rows, two tokens and one VERIFY kind, plus tests. It ships with the next
  release and applies at each box's next agent start. The order-independence table (4.1 d) shows no mixed state is
  worse than today.
- **Churn.** A launch makes the next GAMESYNC re-copy `CAM.CFG` / `cam.cfg` once (the same as Thief 2). The
  steady-state signals ("0 files written", "0 values changed" on quiet runs) are unaffected.
- **The disc mount.** Red Faction and SS2 already mount through their launchers on `.124` (09-29, 11-08). Running SS2
  last limits a possible locked-unit side effect to the end of the session.

## 11. Open questions

1. **Red Faction at 16:9.** On the 1080p boxes it gets 1920x1080. `rf.exe` sets its fullscreen pixel-aspect factor to
   1.0 (`0x50ba1e`), so the picture is probably stretched rather than hor+ (inferred). Measure it in 8.4. If it is
   stretched, the choice between `%FR_W%` (fills the panel) and `%FR_W43%` (correct shape) is the user's, under the
   "1080p where configurable" directive.
2. **Does the vanilla Dark engine persist `game_screen_size` at exit?** If so, where (`USER.CFG`, or the file named by
   `include_user_cfg`)? This only affects re-copy churn; 8.3 #4 checks it.
3. **SS2's mode table** cannot be read (encrypted). The ladder assumes it shares 640/800/1024 with Thief Gold's (same
   engine, and its `shock.cfg` uses the same variables). 8.3 #3 confirms it.
4. **What the vanilla engine does with a size not in its table** (search fails at `0x5373b0`/`0x43b10f`) is unread.
   The ladder never asks for one. The NewDark DX6 path's 640x480 at 1280x960 on `.124` (09-28) is not evidence
   either way: NewDark's table has 1280x960.
5. **Red Faction's in-game frame rate at 1280x960x16 on one chip** is unknown. If it is unplayable while 1024x768 is
   playable, should `.124` get a per-title cap until G47-G51 land? That is the user's decision, and it should be
   measured first.
6. **A Voodoo 3 as the primary adapter** (on any driver) has no 32 bpp 3D, so Red Faction at 32 would fail there too.
   No such box exists today. The `vcrmp` test would not catch it.
7. **`-level L1S1.rfl`**: the argument form is inferred from the switch table and `levels1.vpp`; confirm it in 8.3
   #2b.
8. **Optional, separate:** `FLEETRES -setline` always rewrites the file. Making it a no-op when the line is already
   right would end the per-launch re-copy for every `-setline` title, but it means a `FLEETRES.EXE` rebuild and
   re-stage everywhere.
