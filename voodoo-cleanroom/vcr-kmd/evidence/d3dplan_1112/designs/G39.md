# G39: a mode change never clears the new primary

Design for one item of the Direct3D plan for the Voodoo 5 6000 on `.124` (vcr-kmd, clean-room lane).
Written 2026-11-12. It reads code, docs, vendor source and committed evidence only. Nothing was
built or deployed, and no fleet box was contacted.

Path shorthands: `KMD` = `voodoo-cleanroom/vcr-kmd`, `WT` = the `v56k-bench` worktree root,
`ONBOX` = `KMD/evidence/d3dplan_1112/onbox`, `SWP` = `KMD/evidence/d3dtune_1014`,
`VH5` = 3dfx's H5 W2K display driver (`retro-3dfx/3dfx Driver Code/H5/W2K/Src/Video/Displays/H5`),
`VMP` = its miniport (`.../W2K/Src/Video/Miniport/H5`), `VINC` = `.../W2K/Src/Video/Inc`,
`SPEC` = the VSA-100 register spec (`.../H5/DOCS/avenger_spec.doc`, line numbers of the
`soffice --convert-to txt` text, as in `hw.md`), `PLAN` = `WT/docs/v56k-benchmark-plan.md`.
"Measured" means a ring, a log, a frame or a probe result says it. "Inferred" means nothing measured does.

## 0. Verdict

**The gap is real, fixable, small, and P1.** No title is blocked by it, but it has already cost
a misdiagnosis: on 2026-10-14 the user at the box reported *"the half life game is all garbled"*
while no box was running `hl.exe`. The screen was AvP's 640x480x16 mode showing the old
1280x1024x32 desktop, and the Half-Life lambda in it was a desktop icon (`PLAN:201-206`). The same
stale picture covers the loading period of every title that switches mode. It also makes a title
that never presents look like corrupted rendering instead of a stall, and a luma check reads it as
content (UT2004's 45 s frame: luma mean 40.3, extrema 0..255, `ONBOX/games/UT2004_botmatch/run.json`).

**The fix:** one 2D-engine rectangle fill, colour 0, over the visible primary. It runs in
`DrvEnableSurface`, right after `VcrDd2dInit`, and it is waited for before `DrvEnableSurface` returns.
It sits behind a new `Diag\ModeClear`, read at every mode change and **default OFF**. After one
supervised clean boot, the default moves to ON with 0 as the kill switch, as `Accel2DPattern` did.
No caps change and no D3D code changes.

Facts this design adds to the brief:

1. **The DDK contract is not inferred. It is written in the header 3dfx shipped.**
   `VINC/NTDDVDEO.H:618-623` says: *"High order bit of the mode determines if the set mode should (0)
   or should not (1) cause the video memory to be zeroed out simultaneously to the set mode
   operation."* Our display DLL never sets the bit (`KMD/display/vcrdd.c:472`,
   `vm.RequestedMode = pd->ulMode`). The pair therefore owes a cleared screen at every mode set, and
   neither half provides one.
2. **There is a vendor reference; the gap's "vendor_ref: none" is wrong.** 3dfx's display driver
   clears the desktop itself. `bAssertModeHardware(TRUE)` does it right after the mode set:
   *"First thing we do is set the default registers and clear the desktop"* (`VH5/ENABLE.C:1371-1373`).
   The clear is `vClearDesktopSurface` (`VH5/MISC.C:195-215`): one 2D RECTFILL with `colorFore` 0,
   ROP 0xCC, `dstSize` = cxMemory x cyMemory, at `dstXY` 0,0 from `dstBaseAddr` = the screen
   offset. 3dfx's miniport does not clear either. Its BIOS path calls VBE 4F02 with BX bit 15 clear,
   which makes the BIOS clear (`VMP/H3MODES.C:519-569`). But `DMT_ENABLED` (`VMP/H3.H:62`) forces the
   register mode set (`VMP/H3.C:859`), and `h3modeset.c` writes no frame-buffer memory. **In 3dfx's
   own Win2K/XP stack, the display driver owns the clear.** Our layering puts the 2D engine in the
   same place.
3. **Every application mode switch on vcr-kmd is a new PDEV, so one call site covers them all.** The
   ring shows the order: `DrvAssertMode(FALSE)` on the old PDEV, then `DrvEnablePDEV`, the miniport
   mode set, "2D engine on", `DrvEnableSurface`, and the DirectDraw HAL. The old PDEV's
   `DrvDisableSurface` comes after (`ONBOX/ring_after_probe_i_decoded.txt:26-76`, both directions).
   A same-mode `CDS_RESET` is only `DrvAssertMode(FALSE/TRUE)` (`KMD/README.md:133-139`), and it
   leaves the content alone. `DrvEnableSurface` is therefore reached by every switch: a D3D8/9
   CreateDevice, a DirectDraw SetDisplayMode, ChangeDisplaySettings, Glide's DirectDraw switch-in,
   the desktop restore, and the boot.
4. **A smaller new primary always lies entirely inside the old desktop.** The desktop sits at the
   top of video memory in every mode (`KMD/common/vcr_modes.c:380-384`), so a smaller new primary
   overlaps the old desktop completely. From `.124`'s 1280x1024x32 desktop (`0x3b00000-0x4000000`,
   64 MB per chip):

   | title | new mode | new primary | old desktop rows it shows | stale pixels |
   |---|---|---|---|---|
   | AvP | 640x480x16 | `0x3f6a000-0x4000000` | 904-1023 | 307,200 of 307,200 |
   | UT2004 | 1280x960x16 | `0x3da8000-0x4000000` | 544-1023 | 1,228,800 of 1,228,800 |

   The rows are the taskbar and the bottom icon rows, which is exactly what both frames show.
5. **Why no test bed ever showed it (inferred).** QEMU's std-vga clears VRAM itself at a DISPI
   enable without `VBE_DISPI_NOCLEARMEM`, and `bochs_program` never sets that bit
   (`KMD/miniport/vcrmp_hw.c:644`). 86Box's Voodoo3 and the silicon are programmed by register and
   clear nothing, so the 86Box bed can reproduce it off silicon.

## 2. Why (the code, read 2026-11-12)

- `IOCTL_VIDEO_SET_CURRENT_MODE` passes `RequestedMode & ~VIDEO_MODE_NO_ZERO_MEMORY` and nothing
  else (`KMD/miniport/vcrmp.c:671-676`).
- `VcrHwSetMode` (`KMD/miniport/vcrmp_hw.c:652-721`) and `voodoo_program` (`:564-627`) program
  registers only. They move `vidDesktopStartAddr` to the new top-of-memory offset (`:699-701`, `:606`).
  The one video-memory write they make is the cursor pattern, one page **under** the desktop
  (`KMD/miniport/vcrmp_cursor.c:16-50`).
- The miniport has no mapping of the frame buffer. It maps the cursor page alone (`vcrmp_cursor.c:37`).
- `DrvEnableSurface` (`KMD/display/vcrdd.c:482-545`) maps the frame buffer and builds the surfaces.
  `VcrDd2dInit` (`:540`) learns the engine. Nothing writes the primary until GDI repaints, and a
  fullscreen game's window has no background brush, so GDI does not repaint it.
- No BIOS runs: the mode set is ours, by register.

## 3. The hardware and the references

- **Engine limits (SPEC §7.2.6-7.2.9, `L1615-1740`).** `dstSize` takes 13-bit width and 13-bit
  height. `dstFormat` takes a 14-bit stride and bpp codes 1/3/4/5 for 8/16/24/32. `dstBaseAddr`
  takes **26 bits** on Napalm (*"Increased address width in 2D srcBaseAddr and dstBaseAddr to 26
  bits to access 64 MBytes"*, `L6495`). RECTFILL uses `colorFore` as its source (`L2013`), the
  lesson `KMD/README.md:649-651` records. One fill therefore covers every primary we list
  (the largest listed mode is 1920x1440x32: stride 0x1e00, 1440 lines, 10.5 MB), at the top of a 64 MB chip.
- **Our fill is proven.** `VcrDd2dFill` (`KMD/display/vcrdd_2d.c:222-243`) does GDI's solid fills and
  DirectDraw colour fills, 0 bad on `.124` at 16 and 32 bpp and on the 86Box bed at 8/16/32
  (`KMD/README.md:642-647`, `:116-119`). The desktop offsets it reaches (e.g. 0x3b00000) are the ones
  it writes every day.
- **Vendor**: see §0 item 2. The vendor clears at **every** `bAssertModeHardware(TRUE)`: at enable,
  at `DrvAssertMode(TRUE)` (`VH5/ENABLE.C:920`), and at Glide's release (`VH5/HWCEXT.C:1612`). It
  clears all GDI-addressable memory (cxMemory x cyMemory, up to 0xfff lines), not just the screen.
  This design takes less, on purpose (§4.6).

## 4. Design

### 4.1 Where: `DrvEnableSurface`, after `VcrDd2dInit`, before it returns

- It is the one point that every mode change passes through (§0 item 3), with the engine mapped
  and its FIFO depth learned.
- It is new-PDEV time. No DirectDraw object, D3D context or flip exists yet for this PDEV, and no
  Glide client can be in exclusive mode on it (`exclusive_pid` starts 0). A Glide title's switch-in
  reaches `HWCSETEXCLUSIVE`/`GETLINEARADDR` only later, and both already call `VcrDd2dSync` first
  (`KMD/display/vcrdd_escape.c:102`, `:127`).
- SLI is already off: `VcrSliOff(x, "mode set")` runs at the top of the mode set
  (`vcrmp_hw.c:674`). Chip 0 alone scans out.
- The primary sits at the top of memory, never inside Glide's command-FIFO window
  (96 KB-1116 KB; `KMD/README.md:81-87`). The fill cannot touch a stale `cmdFifo0` (G01).
  In that state `onbox-01` measured fastfill clears still working, and the desktop's 2D engine
  ran on until a surface landed inside the FIFO window.

### 4.2 What: `VcrDd2dClearPrimary` (new, `KMD/display/vcrdd_2d.c`)

```c
/* G39: the new primary is cleared at the mode change - NTDDVDEO.H's contract
 * (VIDEO_MODE_NO_ZERO_MEMORY clear = zero video memory at the set mode), met
 * where 3dfx's own driver meets it (VH5 ENABLE.C:1371, MISC.C:195
 * vClearDesktopSurface). Only the visible primary: never the cursor page under
 * it, the DirectDraw heap or Glide's FIFO window below. Waited for here, so no
 * flip, Lock, GDI punt or 3D triangle meets it in flight. Diag\ModeClear. */
void VcrDd2dClearPrimary(VCR_PDEV *pd)
{
    ULONG bpp = pd->bpp / 8, off, how, y, us = 0;
    LONGLONG t0 = 0, t1 = 0, f = 0;
    if (!pd->mode_clear || !pd->pjScreen || !pd->pvRamBase)
        return;                         /* off: the path before G39, write for write */
    off = (ULONG)(pd->pjScreen - (PUCHAR)pd->pvRamBase);
    how = vcr_modeclear_how(1, pd->pjRegs != NULL, pd->g2d_disabled, pd->g2d_ok,
                            vcr_modeclear_one_fill(off, pd->cx, pd->cy, (ULONG)pd->lDelta, bpp));
    EngQueryPerformanceCounter(&t0);
    if (how == VCR_MC_ENGINE) {
        if (!VcrDd2dFill(pd, off, pd->lDelta, bpp, 0, 0, (LONG)pd->cx, (LONG)pd->cy, 0))
            how = pd->g2d_ok ? VCR_MC_CPU : VCR_MC_SKIP;   /* refused unwritten / FIFO never drained */
        else {
            VcrDd2dSync(pd);                    /* bounded; a give-up logs 512/9 */
            if (!pd->g2d_ok)
                how = VCR_MC_SKIP;
        }
    }
    if (how == VCR_MC_CPU) {
        VcrDd2dSync(pd);
        for (y = 0; y < pd->cy; y++)
            memset(pd->pjScreen + (SIZE_T)y * (ULONG)pd->lDelta, 0, (size_t)pd->cx * bpp);
    }
    EngQueryPerformanceCounter(&t1);
    EngQueryPerformanceFrequency(&f);
    if (f > 0)
        us = (ULONG)((t1 - t0) * 1000000 / f);
    VcrDd(how == VCR_MC_SKIP ? VCR_LV_WARN : VCR_LV_INFO, VCR_EV_DD_2D, 12, how, off, us,
          "new primary %ux%ux%u at %x %s (%u us)", pd->cx, pd->cy, pd->bpp, off,
          how == VCR_MC_ENGINE ? "cleared by the 2D engine" : how == VCR_MC_CPU
          ? "cleared by the CPU" : "NOT cleared - the 2D engine is unusable", us);
}
```

**The registers it writes are `VcrDd2dFill`'s nine, unchanged.** Per mode on `.124` (64 MB per chip):

| mode | `dstBaseAddr` | `dstFormat` | `dstSize` | `clip0Min/Max` | `commandEx` | `colorFore` | `dstXY` | `command` |
|---|---|---|---|---|---|---|---|---|
| 640x480x16 | 0x03f6a000 | 0x00030500 | 0x01e00280 | 0 / 0x1fff1fff | 0 | 0 | 0 | 0xcc000105 |
| 1280x960x16 | 0x03da8000 | 0x00030a00 | 0x03c00500 | " | 0 | 0 | 0 | " |
| 1024x768x32 | 0x03d00000 | 0x00051000 | 0x03000400 | " | 0 | 0 | 0 | " |
| 1280x1024x32 | 0x03b00000 | 0x00051400 | 0x04000500 | " | 0 | 0 | 0 | " |

The command is RECTFILL (5) | GO (bit 8) | ROP 0xCC. Colour 0 is black at 16/32 bpp and palette
index 0 at 8 bpp, which `make_palette` makes black (`vcrdd.c:255-274`; the vendor also fills 0).

**Single pass, synchronous.** The fill takes about 1 pixel per clock, so 2-8 ms from 640x480 to
1280x1024 at the stock clock (inferred; the 512/12 event measures it). The mode set itself took
15-31 ms in the ring, and the CRT re-sync takes far longer. The wait removes every ordering question:
2D against 3D (the HAL does not sync the 2D engine before triangles), CPU against 2D, and flip
against fill.

**The CPU branch runs only where there is no engine by design**: no register window (the VM bed's
Bochs backend), or `Diag\Accel2D = 0`. That is where GDI already draws with the CPU, and it costs
about 25-50 ms of write-combined stores (inferred). It also covers a geometry that one fill cannot
take, which never occurs for a listed mode (the native test proves it). An engine that is present
but unusable is **never written** (`VCR_MC_SKIP`): neither the FIFO reading full at init, nor a
give-up. A wedged chip gets no new traffic from this feature.

### 4.3 The decision, host-testable: `KMD/include/vcr_modeclear.h` (new, Win32-free)

```c
#define VCR_MC_OFF     0u   /* Diag\ModeClear not armed: nothing written (the path before G39) */
#define VCR_MC_ENGINE  1u   /* one 2D RECTFILL of the visible primary, colour 0, then the sync */
#define VCR_MC_CPU     2u   /* no engine by design (no register window, Diag\Accel2D = 0) or a
                             * geometry one fill cannot take: rows of zeros by the CPU */
#define VCR_MC_SKIP    3u   /* the engine is there but unusable: nothing written by us */

/* one RECTFILL covers the primary: SPEC 7.2.6-7.2.9 field widths and vcrdd_2d.c's limits */
static __inline unsigned vcr_modeclear_one_fill(vcr_u32 off, vcr_u32 w, vcr_u32 h,
                                                vcr_u32 stride, vcr_u32 bytespp)
{
    return (bytespp == 1 || bytespp == 2 || bytespp == 4) && w && h && w <= 8191 &&
           h <= 8191 && stride && stride <= 0x3fffu && w * bytespp <= stride &&
           (off & 15u) == 0 && off < (1u << 26) && h * stride <= (1u << 26) - off;
}

static __inline unsigned vcr_modeclear_how(unsigned armed, unsigned have_regs,
                                           unsigned accel2d_off, unsigned engine_ok,
                                           unsigned one_fill)
{
    if (!armed)
        return VCR_MC_OFF;
    if (!have_regs || accel2d_off || !one_fill)
        return VCR_MC_CPU;
    return engine_ok ? VCR_MC_ENGINE : VCR_MC_SKIP;
}
```

### 4.5 Caps, passes, and the old path

- **Caps:** none change, DirectDraw or Direct3D. **Passes:** one fill per mode change, nothing per frame.
- **Old path:** with `Diag\ModeClear` absent or 0, the flag is never set. `VcrDd2dClearPrimary`
  returns on its first line, before any read, write or log, so `DrvEnableSurface`'s register traffic
  and memory writes are today's, byte for byte. A new DLL with an older miniport, or the reverse, is off.
- **Not touched:** `DrvAssertMode` (either direction), `IOCTL_VCR_RESTORE_MODE`/`HWCRLSEXCLUSIVE`,
  the miniport's mode set, the flip path, DP2, Clear2, textures.

### 4.6 Considered and not taken

- **A clear in the miniport (honouring the bit there).** The miniport has no frame-buffer mapping.
  It would need a new uncached mapping of up to 10.5 MB of system PTEs, CPU stores over PCI (slow, on every mode
  set), or a copy of the 2D engine code. `VcrHwSetMode` is also the `RESTORE_MODE` path at Glide's
  release, so a miniport clear would run there too.
- **A clear at primary creation (DirectDraw `CreateSurface` with `PRIMARYSURFACE`).** It misses a
  switch that never creates a primary, and the boot. It also runs when a windowed client creates its
  primary on the live desktop, which must **not** be cleared.
- **The vendor's full clear (cxMemory x cyMemory, the heap included).** A DirectDraw title that
  flipped an undrawn back buffer would show stale heap memory, but no frame shows that. Clearing
  about 59 MB needs several fills, takes about 10x longer, and runs over Glide's FIFO window. That
  last part is what the top-of-memory layout exists to avoid. Open question 4.
- **`DrvAssertMode(TRUE)` and Glide's release (the vendor clears there too).** No defect has been
  seen there, because GDI repaints the whole screen on both paths. `DrvAssertMode(TRUE)` is also how an alt-tabbed
  DirectDraw-exclusive Glide game comes back while its command stream lives
  (`vcrdd.c:592-605`). Writing there is exactly what `Reset3D` was taken back out for. Open question 3.
- **An asynchronous fill (no wait).** It saves a few ms per mode change but leaves 2D-against-3D
  ordering unproven, and the HAL does not sync 2D before 3D.
- **A 3D fastfill.** It is faster, but it depends on 3D state Glide leaves behind (G03). The 2D fill
  is self-contained.
- **A diagnostic non-black colour,** so a stall can be told from a black game frame. The contract
  says zero, and a player would see it. The 512/12 event plus `DestroyDDLocal: flips of 0` already
  name a stall.

## 5. Gating

- **`Diag\ModeClear`, DWORD, absent or 0 = off** (the default when it lands). It is read at every
  `IOCTL_VCR_INFO`, that is at every new PDEV, so arming it needs no reboot: the next switch to
  another mode picks it up. A same-mode reset does not (`KMD/README.md:133-139`). Register it in
  `tests/python/test_vcr_kmd_integration.py` `NEW_DIAG` as `"ModeClear": "0"`.
- **Do not land it default-on blind.** It is a pure correctness fix built on a proven primitive.
  But it adds 2D traffic at every mode change, including the boot's first `DrvEnableSurface` and
  every Glide/OpenGL title's switch-in. That is new kernel-side behaviour at a sensitive point, so
  the project rule applies: one supervised clean boot first (§8).
- **After that boot passes,** move the default: `VcrDiagGet(L"ModeClear", 1)`, absent = on,
  0 = kill switch. This is a separate commit. The switch moves from `NEW_DIAG` to `MOVED_DIAG` with the
  evidence path, the README row says "default ON since <date>", and the Python test asserts the new
  default. This is the precedent of `Accel2DPattern`/`Accel2DLine` on 2026-09-28. The user decides
  the flip, per the project rule.
- **Deploy:** `vcrmp.sys` **and** `vcrdd.dll` (the flag is the miniport's). Use
  `KMD/tools/deploy_box.py install` after its activation preflight, then `scripts/fleet/safe-reboot.py`.
  Make no Diag change in the deploy boot other than this one.

## 6. d3dprobe test: `d3dprobe modeclear` (new mode, `KMD/tools/d3dprobe.c`)

The test needs a mode switch and a seed painted **before** `CreateDevice`, so it is a mode like
`caps`/`render`/`perf`, not a `--tests` entry. It is driver-agnostic: any correct driver passes.

```
d3dprobe modeclear [--res WxH] [--bpp 16|32] [--pace MS]     (fullscreen by definition)
```

1. **Refuse a no-op.** If WxHxbpp is the desktop's mode, the RESULT is the error "no mode change to
   test", and no switch is made.
2. **Seed.** A `WS_POPUP | WS_VISIBLE`, `WS_EX_TOPMOST | WS_EX_TOOLWINDOW` window covers the whole
   desktop. Its `WM_ERASEBKGND` fills with the seed RGB(0x5A,0xC3,0xA5) while `g_seed = 1`. At a 32 bpp
   desktop that is the dword 0x005AC3A5, and its 16-bit halves (0xC3A5 and 0x005A) are both non-black.
   Do `UpdateWindow`, `GdiFlush`, a 300 ms wait, and `pump()`. Then `GetPixel(GetDC(NULL))` at the
   4 corners (2 px in) and the centre must read the seed (±8 per channel at a 16 bpp desktop).
   Otherwise the RESULT is the error "seed not on screen" and no switch is made. The screensaver must be
   dismissed beforehand, as `onbox` found.
3. **Stop painting.** Set `g_seed = 0`: `WM_ERASEBKGND` then returns 1 without painting and `WM_PAINT`
   only validates. Call `ShowCursor(FALSE)` (a software cursor would sit in the frame buffer).
4. **Switch.** `vcr_pace_before_switch()`, then `CreateDevice(HAL, this window, fullscreen, WxH,
   X8R8G8B8 or R5G6B5, 1 back buffer, D3DSWAPEFFECT_FLIP)` with **no depth buffer** (it keeps G10's
   X8R8G8B8+D16 refusal out of the test), then `vcr_pace_after_switch()`.
5. **Read the front buffer, with no Clear and no Present.** `CreateImageSurface(W, H, A8R8G8B8)`,
   `GetFrontBuffer`, `LockRect`. Count `nonblack` (RGB != 0), the `first_nonblack` (x, y, value), and
   `seedlike` (pixels within ±8 of the seed or of its two 16-bit misreads, a diagnostic).
   Before any flip, the front buffer is the primary at `fpPrimary`, the one the mode set left.
   `Dd_Lock` syncs the engine first (`vcrdd_ddraw.c:658`). If `GetFrontBuffer` fails, fall back to a
   GDI `BitBlt` from `GetDC(NULL)` into a 32-bit DIB and set `"readvia":"gdi"`.
6. **Read again after 500 ms** (`nonblack_500ms`). Nothing may paint the primary later either.
7. **Release the device (paced),** destroy the window, and restore the cursor.

```
RESULT {"mode":"modeclear","res":"640x480x16","desktop":"1280x1024x32","seed_ok":1,
        "readvia":"frontbuffer","pixels":307200,"nonblack":0,"nonblack_500ms":0,
        "first_nonblack":null,"seedlike":0,"pass":1,"focus_lost":false}
```

## 7. Regression tests

**`WT/tests/native/test_vcr_kmd_modeclear.c`** (new). It includes `KMD/include/vcr_modeclear.h` and
`KMD/common/vcr_modes.c` (as `test_vcr_kmd_modes.c` does) and runs the code the driver runs:
- `off_writes_nothing`. **The old path:** `vcr_modeclear_how(0, ...)` is `VCR_MC_OFF` for all 16
  combinations of the other inputs.
- `an_engine_clears_with_one_fill`: `how(1,1,0,1,1)` is `VCR_MC_ENGINE`.
- `no_engine_by_design_clears_by_cpu`: `how(1,0,0,0,1)` (no register window, the VM bed) and
  `how(1,1,1,0,1)` (`Diag\Accel2D = 0`) are both `VCR_MC_CPU`.
- `a_wedged_engine_is_never_written`: `how(1,1,0,0,1)` is `VCR_MC_SKIP`, never CPU. This pins the
  promise that a chip whose FIFO reads full or which gave up gets no stores from this feature.
- `every_listed_mode_is_one_fill_at_the_top`: for every `vcr_timings[]` entry × {8, 16, 32} that
  `vcr_mode_check` accepts, on 64 MB and on 32 MB per chip, with `off = vcr_desktop_offset(fb, w·B, h)`:
  - `vcr_modeclear_one_fill(off, w, h, w·B, B)` is 1;
  - `[off, off + w·B·h)` lies inside `[0, fb)`;
  - the cursor page `[off - 0x1000, off)` is **outside** the cleared range;
  - `off >= 0x118000` (Glide's reserved FIFO area, `vcrmp_hw.c:360`) whenever the mode fits above it.
  
  Also: stride 0x4000 gives 0 (so the CPU branch is used, never a partial engine fill), and so does an
  `off` not 16-byte aligned.
- `the_stale_desktop_avp_and_ut2004_saw` asserts **the old-buggy value and the fixed value**. From
  the 1280x1024x32 desktop on 64 MB (`0x3b00000`):
  - AvP's 640x480x16 primary `[0x3f6a000, 0x4000000)` overlaps it by 614,400 bytes: old rows
    904-1023, **all 307,200 pixels stale without the clear**.
  - UT2004's 1280x960x16 `[0x3da8000, 0x4000000)` overlaps it by 2,457,600 bytes: rows 544-1023,
    **1,228,800 stale**.
  - With the clear (the cleared range equals the new primary) the stale count is **0** for both.

## 9. Risk to proven paths

| path | risk | why |
|---|---|---|
| default 16 bpp D3D path | none off; negligible armed | Off, the code returns before anything. Armed, it changes only `DrvEnableSurface`, before any D3D context exists on the PDEV. The HAL code is untouched. |
| Glide/OpenGL coexistence | very low | The fill runs on chip 0, through the PCI FIFO, over the top-of-memory primary only. It never touches the FIFO window. It is waited for before `DrvEnableSurface` returns, and `GETLINEARADDR`/`HWCSETEXCLUSIVE` sync again. It never runs at `DrvAssertMode`/`RESTORE_MODE`, so a live, alt-tabbed or killed Glide stream is never written under. A Glide switch-in pays a few ms. |
| SLI | none | It runs after the mode set's `VcrSliOff`. SLI is enabled only by Glide after `HWCSETEXCLUSIVE`. |
| flip path | none | It completes before DirectDraw is enabled on the PDEV. The scan-out offset (`dd_scan`) is the primary it clears. |
| boot | low | A bounded fill+sync at the first `DrvEnableSurface`: at worst a give-up (acceleration off, logged), never a hang. `BootAttempts` and `Diag\Disable` still cover the boot. Default off until the supervised boot. |
| cursor | none | Its page is one page under the desktop and outside the range. The native test pins this. |
| wedged chip | none new | `VCR_MC_SKIP` writes nothing. The first GDI blit would have met the same state. |
| timing | negligible | 2-8 ms per mode change (inferred, measured by 512/12). A refused CreateDevice's double switch (G11) pays it twice. |
| measurement | intended | Titles that never present now give **black** sweep frames instead of plausible garbage, so AvP's baseline changes. Do not read that as a regression. |

## 10. Effort, dependencies, games, priority

**Effort: S.** About 45 lines in `vcrdd_2d.c`, 3 in `vcrdd.c`, 1 flag in the miniport and the header,
a 30-line pure header, about 120 lines of native test and 40 of Python, about 150 lines for the
d3dprobe mode (plus the ddlab field), and docs. One supervised boot, about 45 minutes.

**Dependencies: none hard.**
- G01 is a verification precondition only: probe before any Glide session in the boot. Its
  mode-set guard (if armed) runs earlier in the same mode set and leaves a cleaner engine.
- G02: its "give-up made visible" work covers this item's SKIP case too.
- G71 is AvP's own stall. This item only changes what that stall looks like.
- G74, G79: this item brings its own probe check, and a front-buffer frame before the first flip is
  valid GDI evidence.

**Games.** Nothing is blocked. The loading period of every title that switches mode on `.124` stops
showing garbage, and so does the whole session of one that never presents:
- **AvP** (whole session today) and **UT2004** (loading): both measured;
- **UT2003** (640x480x16 from the 1280x1024x32 desktop) and **Halo** (1280x960): the same mechanism;
- every other staged D3D/DirectDraw title that switches mode: Battlefield 1942, Hidden and Dangerous
  Deluxe, Jedi Knight DF2 / MotS, Red Faction, Shogo, System Shock 2, Thief Gold, Thief II,
  Rainbow Six, Max Payne, Red Alert 2 / Yuri's Revenge, Tiberian Sun, StarCraft, Warcraft II.

**Priority: P1.** It is a visible defect in every mode-switching staged title. It has already caused
a phantom report, and it disguises stalls (AvP) as rendering corruption in the frames the sweeps
judge.

## 11. Open questions

1. **Does XP's D3D8 runtime clear the front buffer itself at CreateDevice?** UT2004's 45 s frame
   says no, but only if UT2004 had created its device by then. Step 2 of §8 settles it. If the
   runtime clears, `ddlab flip`'s front field is the discriminating test.
2. **How long does the VSA-100's 2D engine take to fill 5 MB?** The estimate is 2-8 ms, about
   1 px/clock (inferred). The 512/12 event measures it on the first armed boot.
3. **Should `DrvAssertMode(TRUE)` and Glide's release clear too, as the vendor's does?** Not
   without evidence of a defect there: GDI repaints on both paths, and `DrvAssertMode(TRUE)` is where
   an alt-tabbed Glide game resumes. If ever wanted, it should be a second value of the same switch,
   default off.
4. **Should the DirectDraw heap be cleared too, as the vendor's cxMemory x cyMemory fill does?**
   Only if a title is seen flipping an undrawn back buffer. It costs several fills over Glide's
   FIFO window.
5. **Which `VCR_INFO_F_*` bit?** 0x8000 is free today and claimed by eight sibling designs. The
   integrator assigns it; the tests pin the name.
6. **Does DOSBox `output=ddraw` (Descent 1/2, G62) change?** Its unused borders should turn black
   instead of stale. This is unrelated to G62's failing setup call, but the frames will differ.
7. **When does the default move to ON?** After the supervised boot, by the user's decision (§5).
