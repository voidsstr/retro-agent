## 1. Verdict

1. **Neither a combine-unit bug nor a missing luminance format causes the square.** The cause is **X8R8G8B8**, the one format Halo asks for that we do not offer.
   - **Both frames show an additive quad of one flat colour** (§2.1):
     - the timedemo square adds (47,92,105) to whatever lies behind it;
     - the 09-28 menu's three squares each add (38,53,36).
   - **Our HAL draws an untextured stage in the vertex colour.** A stage whose texture handle is 0 but whose op reads `D3DTA_TEXTURE` is drawn in the vertex colour (`KMD/display/vcrdd_d3d.c:690-691`, `:725-726`), as 3dfx's own HAL does (`VH5/D6MT.C:4378-4409`). A flat additive square is exactly what "an additive sprite whose texture does not exist" looks like.
   - **Halo creates every 2D bitmap through one function, with no fallback** (`0x523fa0`):
     - it maps the bitmap's format through a constant table at **VA `0x65e040`** straight to a `D3DFORMAT`;
     - it calls `CreateTexture(..., D3DPOOL_MANAGED)`;
     - if that fails, the bitmap's texture slot stays NULL.
   - **This table has caused this exact failure once already.** With DXT2/DXT4 unlisted, Halo's menu drew white until `4ef226e` listed them (`KMD/display/vcrdd_d3d.c:264-269`, `retro-3dfx/FINDINGS.md:435-441`).
   - **Table index 10, `x8r8g8b8`, maps to `D3DFMT_X8R8G8B8` (0x16).** With `D3DBigTex`=7, `.124` offers every other entry of the table, but not this one (§2.5).
   - **Every one of Halo's 30 level maps holds 2D X8R8G8B8 bitmaps** (§2.4). Among them:
     - **every lens flare** (`flares_generic`, `flares_generic2`, `soft flares`, the weapon and vehicle flares);
     - Halo's own fallback textures (`rasterizer\default 2d`);
     - the menu's starfield;
     - a30's dusk-sky gradient;
     - the multiplayer join-list icons.
   - **No map holds an `a8`/`y8`/`ay8`/`a8y8` bitmap,** and `halo.exe` maps those formats to "no D3D format" anyway. The luminance/alpha-only reading (`runtime.md` §4.5, `games.md` §4.2) is refuted for Halo.
2. **X8R8G8B8 is exposable through our DX7 DDI, and the VSA-100 can sample it.**
   - The runtime's converter turns a 32-bit `DDPF_RGB` entry without alpha into `X8R8G8B8` with `OP_TEXTURE` (`runtime.md` §4.1, read from `d3d8.dll`/`d3d9.dll`).
   - The TMU samples it as ARGB8888 (format 15).
   - D3D requires the X byte to read as alpha 1.0. The TMU's own alpha combine does that: `SST_TCA_ONE` = `0x24000000` (`H3DEFS:374`).
   - It is a single pass, with no multipass and no new hardware feature.
3. **The fix: offer X8R8G8B8 behind a new `Diag\D3DBigTex` bit 3 (8), off by default.** Read its alpha as one on whichever TMU samples it (§4).
   - With the bit off, the proven path is unchanged byte for byte: the same format list, the same registers.
   - This is the X8R8G8B8 row of G34, pulled forward. G34 keeps the rest of the format family.
4. **What remains to investigate is cheap** (§3):
   - **Phase 1**, no driver change and no reboot: d3dprobe shows our combine and blend draw a Halo-style flare correctly from an A8R8G8B8 texture, and reproduces the square with no texture bound.
   - **Phase 2:** one clean boot with the new DLL (bit off; untextured-draw counters as the baseline), then one with the bit on (the A/B).
5. **G13 (ALPHAREPLICATE), G12 (stage order), G14 (TFACTOR) and G28 (alpha blend) are demoted.** They are residual checks after the A/B, used only if the glow then shows the right shape but the wrong tint or intensity.
   - G13's own design already ranked itself unlikely for this artefact (`G13.md` §1.4).
6. **visual-12's attribution to the alignment bug is wrong.**
   - An unaligned DXT read produces colour noise (UT2003's menu text, V-02).
   - The 09-28 squares are flat additive colour, the same untextured-sprite signature.
   - That frame was taken at 23:46, after `4ef226e` (13:28) had listed DXT2/DXT4.
7. **Priority P1, effort M.** Raise it to P0 if the A/B shows a common-scene surface also depends on X8R8G8B8, such as the a30 sky (§11, question 2).

### 2.2 What our HAL draws when a stage reads TEXTURE but no texture is bound

`compute_regs` (`vcrdd_d3d.c:921-1029`) sets `tex = c->tex_handle && view_of(...)`. Then `color_path` (`:676-745`):
- RGB: `op == DISABLE || (!tex && (a1 == TEXTURE || a2 == TEXTURE))` gives `CP_RGBSEL_ITER | CP_CC_M(CC_M_ONE)`, i.e. the iterated diffuse colour (`:690-691`);
- alpha: the same rule gives the iterated alpha (`:725-726`).

A NULL texture is `D3DTSS_TEXTUREMAP` = 0 (`:1597-1604`). The sprite is then drawn in its vertex colour through the blend Halo set. That is a flat square with ONE/ONE.

This is the convention 3dfx's HAL used: a stage with `textureHandle == 0` whose op reads the texture ends the stage list, and `numStages == 0` is drawn "flat shading or gouraud shading" (`VH5/D6MT.C:4378-4409`). It is also what textureless D3D applications rely on when they leave the default `MODULATE(TEXTURE, CURRENT)`. **(inferred from common practice; not changed by this design)**

### 2.3 `halo.exe`: one creation path, one format table, no fallback

**The table.** VA `0x65e040` (file `0x25e040`, `.rdata`) holds 18 dwords indexed by Halo's bitmap-format enum, whose names `halo.exe` stores at `0x25f790`-`0x25f820`:

| index | Halo format | D3DFORMAT | offered on `.124` (D3DBigTex=7) |
|---|---|---|---|
| 0-3 | a8, y8, ay8, a8y8 | `0xffffffff` (no D3D format) | - |
| 4, 5, 7, 12, 13 | unused | `0xffffffff` | - |
| 6 | r5g6b5 | 0x17 R5G6B5 | yes |
| 8 | a1r5g5b5 | 0x19 A1R5G5B5 | yes |
| 9 | a4r4g4b4 | 0x1a A4R4G4B4 | yes |
| **10** | **x8r8g8b8** | **0x16 X8R8G8B8** | **no** |
| 11 | a8r8g8b8 | 0x15 A8R8G8B8 | yes (bit 2) |
| 14 | dxt1 | DXT1 | yes (bit 1) |
| 15 | dxt3 | **DXT2** | yes (bit 1, since `4ef226e`) |
| 16 | dxt5 | **DXT4** | yes (bit 1, since `4ef226e`) |
| 17 | p8-bump | `0xffffffff` | - |

An identical copy sits at VA `0x657210`. No absolute reference to that copy was found.

**The consumer** is the only absolute reference to `0x65e040`, at `0x523fc0`. The function `0x523fa0`-`0x5240eb`:
- reads `format = *(short *)(bitmap + 0xc)` and looks it up: `mov ebp, [0x65e040 + format*4]`;
- on `-1`, sets `bitmap+0x28` (the texture pointer) to NULL and returns;
- switches on `type = *(short *)(bitmap + 0xa)`:
  - **type 0 (2D):** `IDirect3DDevice9::CreateTexture` (vtable `+0x5c`) with Usage 0 and **Pool 1 = `D3DPOOL_MANAGED`**;
  - **type 1 (3D):** `CreateVolumeTexture` (`+0x60`), only if `TextureCaps & 0x2000` (VOLUMEMAP);
  - **type 2 (cube):** `CreateCubeTexture` (`+0x64`), only if `TextureCaps & 0x800` (CUBEMAP). The caps word is `[0x7c10fc]`.
- If a create fails, the slot stays NULL and the function returns false. **Nothing retries with another format.**

The bitmap block offsets match Halo's `bitmap_data_block`: +4 width, +6 height, +0xa type, +0xc format, +0x14 mipmap count.

### 2.5 What we offer, and what the runtime can expose

- **Our DX7 list** (`vcrdd_d3d.c:2081-2097`):
  - R5G6B5, A1R5G5B5 and A4R4G4B4 always;
  - A8R8G8B8 with `tex_32` (bit 2);
  - DXT1-5 with `tex_dxt` (bit 1).
  - There is no 32-bit `DDPF_RGB` entry without alpha. `pf_tmfmt` refuses one anyway (`:320-321` requires alpha mask `0xff000000`).
- **The runtime** maps a 32-bit `DDPF_RGB` entry with masks ff0000/ff00/ff and no `DDPF_ALPHAPIXELS` to `D3DFMT_X8R8G8B8` with `OP_TEXTURE` (`runtime.md` §4.1, d3d8 `0x6d9b6850`, d3d9 `0x4fe059b0`).
  - Only an X8R8G8B8 *render-target* texture is impossible on this PCI id (`runtime.md` §4.3). Halo runs with `DisableRenderTargets` (`LIB/Halo/config.txt:115-118`), so that does not matter here.
- **3dfx** offered X8R8G8B8 on Napalm only in its DX8 list (`VH5/D3INIT.C:2496-2507`). Its DX7 list stops at ARGB8888 (`:2188-2197`).
  - Its ARGB8888 row has no forced alpha (`VH5/D3TXTR.C:2954`). Whether it ever read an X8 texel's alpha as 1 was not found **(not to copy blindly, G95)**.
- **`d3dprobe caps` does not ask.** Its format table has no X8R8G8B8 row (`KMD/tools/d3dprobe.c:1325-1329`), so `caps_124.txt` is silent on it.

### 3.3 Instrumentation: why was a draw untextured? (log only; lands with the fix, default on)

`vcr_d3dctx` (`vcrdd_d3d.c:48-74`) gains:
- `ULONG untex[5]`: state flushes drawn untextured while an op read a texture, by reason:
  1. stage 0 reads TEXTURE and its handle is 0. **This is Halo's case.**
  2. a handle is bound but `view_of` refused it (already a once-per-handle WARN 513/7).
  3. the texture was accepted, but its texcoord set is beyond the vertex's sets (`prepare`, `:1339-1356`).
  4. stage 1 has an op and a handle but is dropped (G12's "stage 1 dropped when stage 0 has no texture"; `two` = 0).
- `ULONG untex_seen[8], untex_n`: the first 8 distinct set-ups. The hash covers the reason, both stages' COLOROP/ARG1/ARG2/ALPHAOP, SRCBLEND and DESTBLEND **as the application set them**, and ALPHABLENDENABLE.
  - Each is logged once at INFO as 513/*next*:
    `untextured %u: why %u s0 %u %x %x a %u %x %x blend %u %u/%u` (<= 95 characters, `VCR_LOG_MSG_LEN`).
  - Optional, if cheap: the first triangle's integer screen bounding box, computed in `vcrdd_3d.c` inside the FPU bracket. This maps a record to the square in a frame.
- At `ctx_free` (`:1210-1215`), one INFO summary line right before "context gone":
  `context %u untextured: none %u refused %u texcoord %u stage1 %u (%u set-ups logged)`.
  - It survives the ring wrap that lost Halo's 11-12 session, because it is written last (`ONBOX/games/Halo_timedemo/ring_decoded.txt` kept "context 1 gone").

These are counters only: no register changes. The event codes are the next free ones under 513 when this lands; G13 holds 24-27 provisionally (`G13.md` §4.1), so this would take 28-29. Document them in `include/vcr_events.h:75`. This is a first instance of G76's per-context counters.

## 4. The fix: X8R8G8B8 textures, alpha read as one

### 4.1 The format list

`VcrDdD3dHalInfo` (`vcrdd_d3d.c:2049`) appends **one entry, last** (after DXT1-5), only when `pd->tex_x8`:

```c
texfmt(&g_texfmt[n], 0, 0x00ff0000, 0x0000ff00, 0x000000ff, 0);   /* DDPF_RGB only */
g_texfmt[n++].ddpfPixelFormat.dwRGBBitCount = 32;
```

- **Last**, so DX6/DX7 titles that pick the first match from `EnumTextureFormats` still find the entries they find today.
- `g_texfmt[9]` (`:1984`) becomes `g_texfmt[VCR_TEXFMT_MAX]` (10 today; G34 grows it).

### 4.2 Classification moves to a Win32-free header

Create `include/vcr_texfmt.h`, so a host test runs the code the HAL runs. It holds today's `pf_kind`/`pf_tmfmt` (`:293-332`) plus:

```c
#define VCR_TFA_BIG 0x1   /* D3DBigTex bit 0 */
#define VCR_TFA_DXT 0x2   /* bit 1 */
#define VCR_TFA_32  0x4   /* bit 2 */
#define VCR_TFA_X8  0x8   /* bit 3: X8R8G8B8, honoured only with VCR_TFA_32 */
typedef struct { unsigned flags, bits, r, g, b, a, fourcc; } vcr_texfmt_desc;  /* DDPF_* values */
unsigned vcr_texfmt_list(unsigned armed, vcr_texfmt_desc *out, unsigned max);   /* the offered list, in order */
int vcr_texfmt_classify(unsigned armed, const vcr_texfmt_desc *pf,
                        unsigned *kind, unsigned *tmfmt, unsigned *alpha_one);  /* 0 = sampleable */
unsigned vcr_tca_alpha_one(unsigned tca);  /* a TCA as it reads with the local alpha = 1.0 */
```

`vcr_texfmt_classify` returns:
- **X8R8G8B8** (32 bits, `DDPF_RGB` without `DDPF_ALPHAPIXELS`, R `0xff0000`, A 0) with `VCR_TFA_32|VCR_TFA_X8`: kind `VCR_TEXK_ARGB32`, tmfmt `TM_FORMAT(TF_ARGB8888)` = `0xf00`, **`alpha_one` = 1**. Without `VCR_TFA_X8`: refused, which is today's behaviour.
- every format accepted today: unchanged, with `alpha_one` = 0.

`pf_kind`, `pf_tmfmt` and `ext_layout` (`:349-361`) become thin wrappers that pass `armed` built from `pd->tex_*`. `ext_layout` returns `alpha_one`.

Every later reader goes through `ext_layout`, so all of them accept the format at once:
- sampling: `tex_view_ext` (`:806`);
- the TMU flush: `flush_written` (`:1301-1311`);
- chain placement: `mipchain_ext` (`:367`). It already gives a 32-bit chain kind ARGB32 when `tex_32` is set, so an X8 chain is packed, 16-byte aligned, exactly like an A8R8G8B8 one.

TEXBLT copies by bytes per pixel (`texblt_level`, `:1424`) and needs no change.

### 4.3 Alpha read as one: the TMU's own alpha combine

`tmu_view` (`:750`) gains `ULONG alpha_one`. It is set by `tex_view_ext` and is always 0 in `tex_view` (the default 16 bpp path). `compute_regs` applies it at the three places a TMU's alpha combine is written (`:951`, `:954`, `:962`):

| site | today | with `alpha_one` |
|---|---|---|
| one texture, TMU0 (`:962`) | `TM_TC_REPLACE \| TM_TCA_REPLACE` (`0x41000 \| 0x08200000`) | `TM_TC_REPLACE \| TM_TCA_ONE` (`0x41000 \| 0x24000000`) |
| two textures, TMU1 = stage 0 (`:951`) | `TM_TCA_REPLACE` | `TM_TCA_ONE` |
| two textures, TMU0 = stage 1's local (`:954`, `stage1_combine`) | REPLACE / MULT / ADD / PASS (`0x08200000` / `0x04800000` / `0x08000000` / `0`) | `vcr_tca_alpha_one`: REPLACE -> ONE, **MULT -> PASS** (other x 1), ADD -> ONE (saturates), PASS -> PASS |

- `TM_TCA_ONE` is new in `include/vcr_3dregs.h`: `((1u << 26) | (1u << 29))`. That is `SST_TCA_MZERO | SST_TCA_INVERT_OUTPUT`, Glide's own `SST_TCA_ONE` (`H3DEFS:374`): (other x 0) inverted = 1.0, whatever the texel's X byte holds.
- **Everything downstream then reads alpha 1.0:**
  - the FBI's alpha select (`CP_ASEL_TMU`);
  - BLENDTEXTUREALPHA's factor (`CC_M_ATMU`);
  - the alpha test;
  - the source alpha of the blend.
- RGB is untouched. That is D3D's definition of X8R8G8B8.

It is the same mechanism G34 needs for X1R5G5B5 and X4R4G4B4 (formats 11 and 12): `vcr_tca_alpha_one` is shared.

## 5. Gating

- **The format: `Diag\D3DBigTex` bit 3 (8), a positive flag, default off (absent = 0).**
  - It needs bit 2. It is read once at boot, like the other bits (`README.md:111`).
  - The NewDark launcher's test (`tests/python/test_newdark_display.py:254-261`, `(v & 5) == 5`) already treats 0xd/0xf as armed, so 15 changes nothing there.
- **It is not safe to land default-on.** Offering a format changes what every D3D title may choose (§9).
  - It must be proven in one supervised clean boot in which bit 3 is the only change (boot C, §3.2).
  - It then joins the D3DBigTex default-on decision (G20). That decision applies to all of D3DBigTex's bits, which are default off and therefore inert on a fresh install today.
- **Safe to land default-on now:**
  - the untextured counters (§3.3: log only);
  - the new d3dprobe tests (explicit-only; they change no register);
  - the `include/vcr_texfmt.h` move, provided the native test pins today's list and registers.

## 9. Risk

- **The default 16 bpp path** (no D3DBigTex): untouched. X8 needs `tex_32`, and `tex_view` never sets `alpha_one`; native test (1) pins the 3-entry list.
- **The armed path with bit 3 off** (`.124` today): format list and registers byte-for-byte unchanged (native test 1, Python site checks). The only addition is the counters' INFO lines.
- **With bit 3 on:**
  - **Titles may change format.** UE2, NewDark, Max Payne, Red Faction or DX6 titles that enumerate formats may now pick X8R8G8B8 for opaque textures. That is more video memory where they used to fall back to 565, and more managed-pool uploads, each of which drains the engine (G56). It is measured by the regression row in §8 and stays opt-in until then.
  - **Halo's video memory grows.** Halo creates more textures: 2D X8R8G8B8 bitmaps are 0.8-26 MB a map, mostly bump maps, if they are created eagerly **(unknown; §11, question 1)**.
    - They are `D3DPOOL_MANAGED`, so the runtime evicts rather than fails **(inferred)**.
    - The heap is 27 MB, `dwVidMemFree` is constant (G64), and the heap-floor question is open (G63).
    - Watch for 513/10 "out of video memory".
  - **`alpha_one` touches TCA bits of X8 textures only.** The native model test covers every TCA value our HAL emits.
- **Glide/OpenGL coexistence, SLI state, the flip path:** no interaction. D3D state is rewritten per state flush, and nothing here touches chip masks, `sliCtrl` or the swap path. G01's stale-FIFO hazard is a precondition for every on-box step, not a risk this change adds.
- **Box stability:** no new register traffic beyond values the TMU already takes (`SST_TCA_ONE` is a Glide constant); no new IOCTL. Low.

```python
# Bitmap formats in a Halo PC map: header @0x10 = tag index offset; the index starts
# with {tag array VA, scenario, ?, tag count}; 32-byte tag entries; VA base 0x40440000;
# 'bitm' tag + 0x60 = {count, VA} of 48-byte bitmap data blocks (+4 w, +6 h, +0xa type,
# +0xc format, +0xe flags (0x100 = pixels in bitmaps.map), +0x12 mips, +0x18 offset, +0x1c size)
import struct, collections, sys
FMT = {0:'a8',1:'y8',2:'ay8',3:'a8y8',6:'r5g6b5',8:'a1r5g5b5',9:'a4r4g4b4',
       10:'x8r8g8b8',11:'a8r8g8b8',14:'dxt1',15:'dxt3',16:'dxt5',17:'p8-bump'}
d = open(sys.argv[1], 'rb').read()
io = struct.unpack_from('<I', d, 0x10)[0]
tp, _, _, n = struct.unpack_from('<IIII', d, io)
off = lambda a: a - 0x40440000 + io
for i in range(n):
    c1, _, _, _, pp, dp, _, _ = struct.unpack_from('<8I', d, off(tp) + 32 * i)
    if struct.pack('>I', c1) != b'bitm':
        continue
    name = d[off(pp):d.index(b'\0', off(pp))].decode('ascii', 'replace')
    cnt, ptr = struct.unpack_from('<II', d, off(dp) + 0x60)
    for k in range(cnt if 0 < cnt < 4096 else 0):
        w, h, dep, typ, fmt = struct.unpack_from('<HHHHH', d, off(ptr) + 48 * k + 4)
        print(name, w, h, typ, FMT.get(fmt, fmt))
```

For a flare's pixels: `flags & 0x100` means read `size` bytes at `offset` in `MAPS/bitmaps.map`. Level 0 is `w*h*4` bytes, in BGRX order.
