## 0. Summary

- **The gap is real, exactly as filed.** Three separate defects share the blend code:
  1. **Targets without alpha** (every 16 bpp target, and every 32 bpp flip-chain back buffer, which is
     X8R8G8B8): `DESTALPHA`, `INVDESTALPHA` and `SRCALPHASAT` are passed to the chip, which reads whatever
     the alpha byte holds. Direct3D defines that alpha as 1.
  2. **Targets with alpha** (an A8R8G8B8 render-target texture or offscreen target at 32 bpp): the alpha
     channel is always blended ONE/ZERO, so a blended draw stores unblended source alpha.
  3. **Caps**: `SRCALPHASAT` is advertised and has never been checked on silicon. `DESTALPHA`/`INVDESTALPHA`
     are not advertised, yet the code sends them to the hardware.
- **The fix, in three parts:**
  - **A. The no-alpha substitution, default ON.** On a target without alpha, the RGB factors `DSTALPHA` →
    `ONE`, `1-DSTALPHA` → `ZERO`, `SATURATE` → `ZERO`. This is what 3dfx did on every Napalm draw (PRS 8373),
    restricted here to the targets where it is correct. Any draw that names none of the three factors writes
    the same `alphaMode` as today. That covers every logged game combine and every d3dprobe test.
  - **B. Real destination alpha, default OFF** (`Diag\D3DFeat` bit `DSTALPHA`). On a 32 bpp target whose
    format has 8 bits of alpha, `alphaMode[23:16]` takes the alpha component of the application's two
    factors. Only the six codes the 32 bpp alpha table allows are used.
  - **C. Caps, default OFF** (`D3DFeat` bit `DSTALPHA_CAPS`, which needs B). It adds `DESTALPHA` and
    `INVDESTALPHA` to both blend caps: `SrcBlendCaps` `0x1f33` → `0x1ff3`, `DestBlendCaps` `0x3f` → `0xff`.
    `SRCALPHASAT` stays advertised only if the new `srcalphasat` probe passes on a target with alpha.
- **One header holds the whole mapping**: `KMD/include/vcr_blend.h`, Win32-free. It is executed by a new host
  test, `WT/tests/native/test_vcr_kmd_blend.c`, over all 225 factor pairs. This is the first host test that
  runs the HAL's state-to-register translation for blending (G77).
- **Four d3dprobe tests:** `destalpha`, `srcalphasat`, `destalpha_rt`, `alphachan_rt`, plus three `caps` fields.
- **Game exposure:**
  - Halo is the one staged title shown to name `D3DBLEND_DESTALPHA`: six `SetRenderState` sites in `halo.exe`.
  - Five of them are behind pixel-shader-1.1+ guards, which `.124` (PixelShaderVersion 0) never passes.
  - The sixth sits in a pass reached through a pointer check, and Halo's own `config.txt` documents
    `DisableAlphaRenderTargets`.
  - UT2003's logged combines name none of these factors.
- **Priority P2** (correctness and caps hygiene). Part B becomes **P1** on the day Halo's
  `DisableRenderTargets` is lifted for `0x121a:0x0009` (G36/G67).
- **Effort M.** Depends on G01 (precondition for any on-box D3D verification), G29 (same functions, same
  header) and G36 (targets with alpha are render targets).

## 2. Hardware and reference facts the design rests on

| fact | source |
|---|---|
| `alphaMode[11:8]`/`[15:12]` are the RGB source and destination factors; `[19:16]`/`[23:20]` are the **alpha-channel** source and destination factors. "RGB color components and the alpha components may have different associated alpha blending functions" | SPEC L2895-2899, L2907, L2940-2953 |
| RGB factor codes: 0 ZERO, 1 SRCA, 2 COLOR, 3 DSTA, 4 ONE, 5 1-SRCA, 6 1-COLOR, 7 1-DSTA, 8/9 SAMECOLOR, 0xF ASATURATE `MIN(As, 1-Ad)` as a source and COLORBEFOREFOG as a destination | SPEC L2955-2972; `VINC/H3DEFS.H:913-934` |

| **15/16 bpp alpha-channel factors: ZERO and ONE only**, "only relevant when the auxiliary buffer is setup to be an alpha buffer, fbzMode bit(18)=1" | SPEC L2974-2983 |
| At 32 bpp the destination alpha planes are always on (`fbzMode[18]` must be 0). `renderMode[20]` gates alpha writes and `fbzMode[9]` is the master write enable | SPEC L3266, L3298, L3312, L6224-6226 |
| At 16 bpp the aux buffer is an alpha buffer only with `fbzMode[18]`, and then depth cannot be used. The HAL never sets bit 18 | SPEC L3266; `vcr_3dregs.h:117` (`FZ_ALPHABUFFER`, unused) |
| Glide restricts the alpha-channel factors the same way: at `grPixelSize == 4` it keeps the six legal codes and maps others to ONE (source) or ZERO (destination); below 32 bpp it keeps ZERO/ONE only | `GL5/gglide.c:682-720` |
| 3dfx's matrix: destination alpha and inverse destination alpha "Destination surface must be 32bpp" (Napalm column) | `D3DXLS` rows 255-256, 269-270 |
| 3dfx maps every D3D factor to an RGB **and** an alpha code: SRCCOLOR → (SAMECOLOR, SRCA); DESTCOLOR → (COLOR, DSTA); SRCALPHASAT → (SATURATE, ONE); BOTH* overrides the destination | `VH5/D3RSTATE.C:3054-3174` (`srcBlend`), `:3183-3302` (`dstBlend`) |
| 3dfx's Napalm caps add SRCCOLOR, INVSRCCOLOR, DESTALPHA, INVDESTALPHA and SRCALPHASAT to both sides. The base lists have them commented out, so `REP/hal.md`'s "3dfx did not advertise SRCALPHASAT" is half right | `VH5/D3INIT.C:2945-2977`, `:3131-3158` |
| …and then `setDX6state` rewrites the RGB factors **on every Napalm draw at any depth**: DSTALPHA → ONE; 1-DSTALPHA, SATURATE and COLORBEFOREFOG → ZERO. So 3dfx shipped no real destination alpha in D3D | `VH5/D6DP2.C:6233-6313`; revision note "PRS 8373 fix - conditionally modify the source and/or destination alpha blend mode" (`VH5/D6DP2.C:307-308`, `W9X/D6DP2.C:314-315`) |
| D3D's definition of a target without alpha: destination alpha reads as 1, so SRCALPHASAT's `f = min(As, 1-1) = 0` | (inferred: the DX8 reference rasterizer and OpenGL both define it so; 3dfx's substitution values match it exactly) |

**Consequence.** The chip can do everything D3D's DX7/DX8 blend needs on a 32 bpp target with alpha, alpha
channel included. On a target without alpha, the correct answer is a factor substitution. The vendor applied
that substitution everywhere. It is copied here only where it is correct (`REP/vendor.md` §13 item 2).

## 3. Design

### 3.1 Scope

- **In:**
  - `SRCBLEND`/`DESTBLEND` (D3D render states 19/20, the same values in DX5-DX9) → `alphaMode[23:4]`;
  - the `BOTHSRCALPHA`/`BOTHINVSRCALPHA` overrides;
  - the target's alpha;
  - the blend caps.
- **Out:**
  - **SAMECOLOR** for SRCCOLOR as a source and DESTCOLOR as a destination: G29. It uses the same function;
    see 3.8.
  - **BLENDOP and COLORWRITEENABLE**: G91.
  - **D3D9 separate alpha blend** (`SEPARATEALPHABLENDENABLE`/`SRCBLENDALPHA`/`DESTBLENDALPHA`): a DX7 DDI cannot
    report `D3DPMISCCAPS_SEPARATEALPHABLEND` (G91/G94). The hardware's separate alpha factors are used here only
    to carry D3D's *joint* factors' alpha component.
  - **1555 targets' 1-bit alpha**: G93; see 3.8.

### 3.2 The decision, per target

| target | `D3DFeat.DSTALPHA` | RGB `DESTALPHA` / `INVDESTALPHA` / `SRCALPHASAT` | alpha-channel factors | vs today |
|---|---|---|---|---|
| 16 bpp (any chip) | either | **ONE / ZERO / ZERO** (Part A) | ONE / ZERO | changed only for draws naming the three factors |
| 32 bpp, no 8-bit alpha (X8R8G8B8) | either | **ONE / ZERO / ZERO** (Part A) | ONE / ZERO | same |
| 32 bpp A8R8G8B8 | off | DSTA / 1-DSTA / SATURATE (as today) | ONE / ZERO (as today) | **byte-identical** |
| 32 bpp A8R8G8B8 | **on** | DSTA / 1-DSTA / SATURATE | **the application's** (table 3.3) | changed for every blended draw on such a target |

`rt_alpha`, "the target has 8-bit alpha", is true only when all of these hold:
- `vcr_rt_format` chose `VCR_RT_32`;
- the target carries its own pixel format (`has_pixfmt`);
- `ddpfSurface.dwFlags & DDPF_ALPHAPIXELS`;
- `dwRGBBitCount == 32`;
- `dwRGBAlphaBitMask == 0xff000000`.

A flip-chain buffer has no pixel format of its own, and uses the display format, which has no alpha mask
(`fill_pixfmt`). So it is never `rt_alpha`.

### 3.3 `KMD/include/vcr_blend.h` (new; integer only, Win32-free)

```c
/* D3D blend states (d3dtypes.h D3DBLEND_*: 1..13, the same in DX5-DX9) and caps
 * (d3dcaps.h D3DPBLENDCAPS_*), by number: the HAL static-asserts them against
 * the DDK headers, the host test cannot include those */
#define VCR_BL_ZERO 1u
#define VCR_BL_ONE 2u
#define VCR_BL_SRCCOLOR 3u
#define VCR_BL_INVSRCCOLOR 4u
#define VCR_BL_SRCALPHA 5u
#define VCR_BL_INVSRCALPHA 6u
#define VCR_BL_DESTALPHA 7u
#define VCR_BL_INVDESTALPHA 8u
#define VCR_BL_DESTCOLOR 9u
#define VCR_BL_INVDESTCOLOR 10u
#define VCR_BL_SRCALPHASAT 11u
#define VCR_BL_BOTHSRCALPHA 12u
#define VCR_BL_BOTHINVSRCALPHA 13u

#define VCR_BL_RT_ALPHA   1u   /* the target stores 8-bit alpha (32 bpp A8R8G8B8) */
#define VCR_BL_DSTALPHA   2u   /* Diag\D3DFeat DSTALPHA: blend that alpha with the app's factors */

/* RGB factors: blend_src/blend_dst of 95678704, moved here unchanged
 * (SRCCOLOR/INVSRCCOLOR as a source and DESTCOLOR/INVDESTCOLOR as a
 * destination stay ONE until G29) */
static __inline unsigned vcr_bl_rgb_src(unsigned b);
static __inline unsigned vcr_bl_rgb_dst(unsigned b, unsigned src);

/* the alpha component of the same D3D factor, in SPEC's 32 bpp alpha-channel
 * codes {0,1,3,4,5,7}: ZERO 0, ONE 4, SRCCOLOR/SRCALPHA 1, INVSRCCOLOR/INVSRCALPHA 5,
 * DESTALPHA/DESTCOLOR 3, INVDESTALPHA/INVDESTCOLOR 7, SRCALPHASAT 4 (its factor
 * is (f,f,f,1)), BOTHSRCALPHA src 1 / dst 5, BOTHINVSRCALPHA src 5 / dst 1;
 * anything else ONE - the RGB side's fallback, and Glide's for a source */
static __inline unsigned vcr_bl_a_src(unsigned b);
static __inline unsigned vcr_bl_a_dst(unsigned b, unsigned src);

/* does the pair read destination alpha in its RGB factors? (the counter's test) */
static __inline unsigned vcr_bl_reads_dst_alpha(unsigned src, unsigned dst)
{
    return src == VCR_BL_DESTALPHA || src == VCR_BL_INVDESTALPHA || src == VCR_BL_SRCALPHASAT ||
           ((dst == VCR_BL_DESTALPHA || dst == VCR_BL_INVDESTALPHA) &&
            src != VCR_BL_BOTHSRCALPHA && src != VCR_BL_BOTHINVSRCALPHA);
}

/* alphaMode's blend bits: AM_BLEND and the four factor fields */
static __inline unsigned vcr_blend_alphamode(unsigned src, unsigned dst, unsigned flags)
{
    unsigned rs = vcr_bl_rgb_src(src), rd = vcr_bl_rgb_dst(dst, src), as = BF_ONE, ad = BF_ZERO;
    if (!(flags & VCR_BL_RT_ALPHA)) {
        /* no alpha planes the app can own: D3D reads its alpha as 1 (PRS 8373's values) */
        rs = rs == BF_DSTALPHA ? BF_ONE
           : (rs == BF_INVDSTALPHA || rs == BF_SATURATE) ? BF_ZERO : rs;
        rd = rd == BF_DSTALPHA ? BF_ONE : rd == BF_INVDSTALPHA ? BF_ZERO : rd;
    } else if (flags & VCR_BL_DSTALPHA) {
        as = vcr_bl_a_src(src);
        ad = vcr_bl_a_dst(dst, src);
    }
    return AM_BLEND | AM_RGBSRC(rs) | AM_RGBDST(rd) | AM_ASRC(as) | AM_ADST(ad);
}

/* the caps, built from here so the host test pins them */
#define VCR_BL_SRCCAPS        0x1f33u   /* 95678704's: incl. SRCALPHASAT (0x400) until srcalphasat decides */
#define VCR_BL_DSTCAPS        0x003fu
#define VCR_BL_CAPS_DSTALPHA  0x00c0u   /* DESTALPHA | INVDESTALPHA, both sides */
```

### 3.4 `KMD/display/vcrdd_d3d.c`

- **`blend_src`/`blend_dst`** (`:630-662`) are deleted; `vcr_bl_rgb_src`/`_dst` are the same switch. A
  compile-time check ties the numbers to the DDK: `typedef char vcr_bl_chk[(VCR_BL_SRCALPHASAT ==
  D3DBLEND_SRCALPHASAT && VCR_BL_BOTHINVSRCALPHA == D3DBLEND_BOTHINVSRCALPHA && …) ? 1 : -1];`
- **`target_of`** (`:1047-1088`) clears `c->rt_alpha` at entry, because a refused target must not keep a
  stale flag. After `t->fmt = fmt` it sets `c->rt_alpha = fmt == VCR_RT_32 && surf_alpha8(c->rt)`.
  - `surf_alpha8` is the five-condition test of 3.2.
  - SETRENDERTARGET already sets `dirty` and clears `prepared` (`:1741-1742`), and every DP2 re-runs
    `compute_regs` before its first triangle (`prepare`, `:1335-1337`), so the flag can never be stale in
    `alphaMode`.
- **`compute_regs`** (`:995-999`) becomes:

  ```c
  if (c->rs[D3DRENDERSTATE_ALPHABLENDENABLE]) {
      DWORD s = c->rs[D3DRENDERSTATE_SRCBLEND], d = c->rs[D3DRENDERSTATE_DESTBLEND];
      ULONG fl = (c->rt_alpha ? VCR_BL_RT_ALPHA : 0) | (c->pd->bl_dstalpha ? VCR_BL_DSTALPHA : 0);
      r->alphaMode |= vcr_blend_alphamode(s, d, fl);
      if (vcr_bl_reads_dst_alpha(s, d))
          blend_seen(c, s, d, fl);          /* 3.6: counters, one event per context */
  }
  ```
- **Caps** (`prim_caps :2025-2031`) are built from `VCR_BL_SRCCAPS`/`VCR_BL_DSTCAPS`, which are the same
  numbers. In `VcrDdD3dHalInfo`, after the two `prim_caps` calls, both the triangle and the line caps OR in
  `VCR_BL_CAPS_DSTALPHA` when `pd->bl_dstalpha_caps`.
- **PDEV flags.** These go in `KMD/display/vcrdd_2d.c:451-470`, beside `rt32` and `tex_32`, from whichever
  `D3DFeat` transport the plan adopts (§4.3):
  - `pd->bl_dstalpha = pd->rt32 && (feat & VCR_D3DFEAT_DSTALPHA)`. VSA-100 only, because `rt32` already
    implies `napalm`, and no Voodoo3 target has alpha.
  - `pd->bl_dstalpha_caps = pd->bl_dstalpha && (feat & VCR_D3DFEAT_DSTALPHA_CAPS)`.
  - One "armed" INFO line: `armed (Diag\D3DFeat): destination alpha ON|off, DESTALPHA caps ON|off`.
- **Struct fields.** `KMD/display/vcrdd.h` gets the two PDEV fields. `vcr_d3dctx` gets `rt_alpha`,
  `bl_as1`, `bl_real`, `bl_logged`.

### 3.5 What the hardware sees, and what is never written

- **Registers.** No new register is written. `alphaMode` is still one full write per state flush
  (`vcrdd_3d.c:80`). Part A uses only `BF_ONE` and `BF_ZERO`, the RGB values the proven path writes on every
  opaque draw. Part B writes only the six legal 32 bpp alpha codes.
- **At 16 bpp** the alpha-channel fields stay exactly `ONE`/`ZERO` whatever the switch says. SPEC reserves
  everything else there, and the native test asserts it for all pairs.
- **SATURATE (0xF)** is never written as a destination factor, where it means COLORBEFOREFOG. As a source it
  is written only on an alpha target.

### 3.6 Logging and measurement (cheap, default on)

- **Counters per context**, bumped in `compute_regs` (once per state flush, not per triangle):
  - `bl_as1`: state flushes where Part A read a target's alpha as 1;
  - `bl_real`: state flushes that read real destination alpha on an alpha target.
- **One INFO event per context**, on the first use, both factors raw. Proposed `513` what 30 (24-27 are taken by
  other drafts); the message is at most 95 characters:
  `blend 7/1 on a 32 bpp target without alpha: its alpha read as 1`.
- **At context free, only when non-zero**, proposed what 31:
  `context 3 blend: 512 flushes read alpha as 1, 0 read real dest alpha`.
- **Why it is needed.** `log_combo`'s `am` (513/21) will show the *substituted* factors after Part A. This
  event keeps the application's request visible.
- **LogLevel.** Both are INFO, so LogLevel 2 keeps them. That is the per-title measurement §7.1 needs.

### 3.7 The old path, byte for byte

- **Switch off (the default).** Only draws that name one of the 65 pairs change, and only on targets without
  alpha.
  - No d3dprobe test names them, and no logged game combine names them.
  - The 16 bpp lane (40/40), the 32 bpp lane and the windowed desktop lane therefore write identical register
    streams.
  - Caps are unchanged: `1f33`/`3f`.
- **Every chip.** Part A also applies to the Banshee/Voodoo3 86Box bed: 16 bpp there, so no target has alpha.
  The same 65 pairs change; nothing else does.

### 3.8 Interactions

- **G29 (SAMECOLOR).** It changes `vcr_bl_rgb_src`/`_dst` for four values behind its own flag.
  - The alpha side is already right here: SRCCOLOR's alpha component is SRCA, DESTCOLOR's is DSTA.
  - Whichever item lands first creates `vcr_blend.h` and `test_vcr_kmd_blend.c`; the other extends them.
- **G91 (COLORWRITEENABLE).** Halo's alpha-only pass at `0x520806` needs both G91 and Part B. It is
  shader-gated off on `.124`.
- **G93 (1555 targets).**
  - Today `vcr_rt_format` accepts any 16-bit target, including A1R5G5B5/A4R4G4B4 render textures, and draws
    them as 565. That is G93's bug, not this one.
  - If G93 adds 15 bpp rendering, `rt_alpha` must grow a 1-bit case: RGB DSTALPHA readable; alpha-channel
    factors ZERO/ONE only (SPEC L2974); `renderMode[16:15]` = 2.
- **G36 (render-to-texture).** Every alpha target a D3D8/9 game can own is a render target. The D3D8 runtime
  grants A8R8G8B8 render-target textures on `121a:0009` while D3DBigTex bit 2 lists the format
  (`REP/runtime.md` §4.3). The `destalpha_rt` probe is also the first draw into an offscreen 32 bpp target on
  this HAL; G36 should read its result.
- **G30 (no dither at 32 bpp)** and **G03 (3D state baseline):** no interaction. `fogMode` blend-op bits and
  `alphaMode` are rewritten in full at every flush.

## 4. Gating

### 4.1 Part A: safe to land default ON

The project rule allows new HAL behaviour default-on when the proven path stays byte-for-byte unchanged. This
qualifies:
- **What changes:** only draws that name `DESTALPHA`, `INVDESTALPHA` or `SRCALPHASAT` on a target with no
  alpha.
- **What they get:** `ONE`/`ZERO`, values already proven on silicon.
- **Who agrees on the answer:** Direct3D's own definition and 3dfx's shipping driver.
- **Its proof** is the deploy boot itself (§7.2): the full default d3dprobe matrix unchanged, plus `destalpha`
  and `srcalphasat` passing at 16 and 32 bpp. If the plan adopts a `D3DFeatOff` kill mask for graduated items
  (G05 §4.1), Part A gets a kill bit there. Otherwise it gets none, as the change has nothing to re-arm.

**The one behaviour risk.** A title that relied on a stale X8R8G8B8 alpha byte (for example `SRCALPHASAT`
behaving like `SRCALPHA` after a clear to alpha 0) loses that accidental effect. No staged title is known to
do this, and §7.1 measures it before the deploy.

### 4.2 Parts B and C: default OFF, then graduate

- **Switch:** `HKLM\SYSTEM\CurrentControlSet\Services\vcrmp\Diag\D3DFeat`, read at boot (FindAdapter), like
  `D3D32` and `D3DBigTex`. The caps an application reads at its desktop must match its fullscreen PDEV's.
- **Bit `VCR_D3DFEAT_DSTALPHA`** (provisional bit 12, `0x1000`): Part B.
  - It changes registers only on 32 bpp targets with 8-bit alpha.
  - It needs `rt32`; render-target textures in A8R8G8B8 also need D3DBigTex bit 2.
- **Bit `VCR_D3DFEAT_DSTALPHA_CAPS`** (provisional bit 13, `0x2000`): Part C. It is ignored unless
  `DSTALPHA` is also set.
- **Why two bits.** B can be proven with d3dprobe while no game changes path, since the probe names
  DESTALPHA whatever the caps say. C is the part that can move a game onto a dest-alpha technique: a title
  that sees the cap may then use it on an X8R8G8B8 back buffer, where D3D answers 1. So C gets its own boot,
  with a game A/B.
- **Graduation:** after §7.3 (B) and §7.4 (C) pass, flip each default in its own commit with its own test.

### 4.3 Transport

`vcr_info.flags` is full: `0x7fff` is pinned by `WT/tests/native/test_vcr_kmd_abi.c:113-138`. Use the plan's
`D3DFeat` word: G05 §4.2 proposes the raw DWORD in an appended `vcr_info.d3dfeat`, with bits allocated in
`include/vcr_d3dfeat.h` and a one-bit-each test. The bit numbers above are provisional; they sit above every
number the other drafts claim (0-8). If G29 is gated separately, it takes the next bit.

### 4.4 SRCALPHASAT: decided by silicon, no switch

- **The cap stays (`0x1f33`) when both hold:**
  - `srcalphasat` (§5) part a passes: a target without alpha gives `f = 0`. That is exact by construction
    after Part A.
  - Part b passes: an A8R8G8B8 target gives `min(As, 1-Ad)`.
- **If part b fails**, a follow-up commit sets `VCR_BL_SRCCAPS` to `0x1b33`. Its test asserts the new and the
  old value, and Findings record why. The mapping stays as designed, because no exact single-pass substitute
  exists.
- **If part b cannot run** (the runtime grants no A8R8G8B8 target), the cap stays. Every target a D3D8/9 game
  could then own is alpha-less, where Part A makes the answer exact.

## 5. d3dprobe tests (`KMD/tools/d3dprobe.c`)

### 5.1 Shared machinery

- **`readback_argb(IDirect3DSurface8 *s)`** locks any lockable surface, the back buffer or an offscreen target,
  and keeps the alpha byte. Today's `expand()` masks it off (`d3dprobe.c:273-289`).
- **`expect_argb(test, what, x, y, want, tol_rgb, tol_a)`** compares four channels; `tol_a < 0` skips alpha.
- **`ref_blend(src, dst, sb, db, dst_has_alpha)`** is D3D's blend as the probe's reference. Every expected value
  is computed, not hard-coded:
  - factor vectors as the D3D8 documentation defines them; `Ad = dst_has_alpha ? A(dst) : 255`;
  - `SRCALPHASAT = (min(As, 255-Ad), …, 255)`;
  - `out = min(255, (s·Fs + d·Fd + 127) / 255)`.
- **Diagnosis.** Each cell also logs the value today's mapping would give ("old"), so a FAIL says which
  mapping the chip ran.
- **Tolerance:** RGB 8 at 32 bpp, 16 at 16 bpp (565 quantisation); alpha 8.
- **Recording.** The RESULT records `SrcBlendCaps`/`DestBlendCaps` so a run says which caps it ran under.
- **Explicit only at first** (`--tests …`). `destalpha` and `srcalphasat` join the default list after the
  deploy boot; the RT tests join after B graduates.

- The device's own target and Z are restored after each RT test (`GetRenderTarget`/`GetDepthStencilSurface`,

### 5.3 `caps` additions (no device, no mode switch)

`"rt_a8r8g8b8": {"surface": n, "texture": n}`: `CheckDeviceFormat` with `D3DUSAGE_RENDERTARGET`.

`"bb_a8r8g8b8": {"full": n, "windowed": n}`: `CheckDeviceType(X8R8G8B8 display, A8R8G8B8 back buffer)`.

They measure what `REP/runtime.md` §4.3 read from the binaries: which targets with alpha a D3D8 game can own
on this PCI id. They also matter to G36.

### 5.4 Validate the reference first

d3dprobe is "for any other driver, as the reference" (`d3dprobe.c:1-3`). Run the four tests once on a fleet box
whose D3D8 driver advertises DESTALPHA: any DX8-class NVIDIA box in `WT/docs/fleet-inventory.md`.

- `destalpha` there tests this design's premise that an X8R8G8B8 target reads alpha 1.
- If that driver reads the stored byte instead, stop and decide before landing Part A default-on: D3D's
  definition against what period hardware did.

### 5.5 Modes

- Fullscreen 640x480x16 (D16) and 1024x768x32 (D24X8), `--pace 5000`.
- Windowed on the 32 bpp desktop.
- Never a refused pair (no `--zfmt d16` at 32 bpp: G10/G11).
- A named test that skips is not a pass (`d3dprobe_run.py:201-216`).

## 10. Open questions

1. **What does the VSA-100 read as destination alpha at 15/16 bpp with `fbzMode[18]` = 0?** SPEC is silent.
   §7.1 measures it, and Part A makes it moot.
2. **Does XP's D3D8 runtime grant a lockable A8R8G8B8 offscreen render target on `121a:0009`?** It is inferred
   from the driver-flag table (`REP/runtime.md` §4.3), and the new `caps` fields settle it. If not, the RT tests
   would need a render-target texture plus a sampling readback, which G21/G36/G37 confound.
3. **Does DirectDraw place that target 16-byte aligned?** `colBufferAddr` drops bits `[3:0]`. The probe's edge
   cells detect a misplacement; the fix is G36's.
4. **Is ASATURATE exact on silicon?** Part b of `srcalphasat` decides it, and with it the cap.
5. **Is Halo's `0x525720` pass reachable under `DisableRenderTargets`, and what does `0x69ddb0` hold?** §7.1's
   combine log decides.
6. **Does any staged title choose a path from `DestBlendCaps & DESTALPHA`?** Boot 3 decides.
7. **Does a period DX8 driver (NVIDIA) read X8R8G8B8 destination alpha as 1, or the stored byte?** §5.4 tests
   the premise of Part A.
8. **What are the `D3DFeat` transport, the bit numbers, and the graduation convention?** These are plan-level,
   shared with G05/G08/G15/G16 and others.
9. **Should the X byte of a 32 bpp target without alpha be held at `0xFF` instead of substituting factors?**
   That would mean `renderMode[20]` = 0 plus clears forced to alpha `0xFF`. Rejected:
   - it is new traffic on the proven 32 bpp path;
