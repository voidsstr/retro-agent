# G35: stencil at 32 bpp - D24S8 honoured (`Diag\D3DFeat` STENCIL / STENCILCAPS)

**Gap.** D24S8 is listed in the Z formats, but its stencil is never written or tested. StencilCaps is 0, the
stencil render states are dropped, and so is `D3DCLEAR_STENCIL`.

**Lane:** clean-room (`vcr-kmd`, the `vcrdd.dll` D3D HAL). This is a design only: nothing was built, deployed
or run, and no fleet box was contacted.

## 0. Verdict

**The gap is real and fixable, at 32 bpp only, in a single pass.** Every claim was checked in the code:

| claim | where (today, 95678704's source) |
|---|---|
| D24S8 is listed | `vcrdd_d3d.c:2204-2212` (`DDPF_ZBUFFER \| DDPF_STENCILBUFFER`, 32 bits, stencil mask `0xff000000`); reaches D3D8 as D3DFMT_D24S8 (`caps_124.txt` `z24s8: 1`, X8R8G8B8 match 1) |
| `dwStencilCaps` is never set | `VcrDdD3dDriverInfo` memsets the extended caps and never names the field (`:2150-2172`) |
| `compute_regs` reads no stencil state | `:921-1029`; `c->rs[52..59]` are stored by `set_rs` (`:1393-1406`) and never read |
| `D3DCLEAR_STENCIL` is dropped | `clear_rects` builds `what` from TARGET and ZBUFFER only (`:1408-1421`). The DP2 CLEAR record's `dwFillStencil` (offset 12, `d3dnthal.h:810-817`) is never read (`:1754-1758`), nor is Clear2's (`:1873-1903`). A stencil-only clear returns before any write (`!what`). |
| 32 bpp targets write stencilMode = stencilOp = 0 | `vcr_3dseq.h:56-77`, at every target setup |

**Three refinements to the gap text:**

1. **D3D's Clear needs no masked stencil fill.**
   - FASTFILL cannot mask stencil bits one by one (SPEC §21.4 L6227, §8.83.3 L4056).
   - But Direct3D's Clear writes every stencil bit, whatever STENCILWRITEMASK says. 3dfx's own D3D FastFill
     always writes `SST_STENCIL_MODE_CLEAR | value` (`VH5/D7DP2.C:862-874`; `VH5/H3DEFS.H:164-170`).
     Wine's D3D also sets a full stencil mask before a clear (inferred: recalled, not read).
   - So the 2D "hot WAX" byte-mask path that Glide needs for OpenGL (`GL5/gglide.c:2270-2296`) is not needed
     here. A d3dprobe check against a reference driver settles it (§5.4).
2. **Stencil writes do not depend on the depth write enable.**
   - At 32 bpp, fbzMode[10] enables DEPTH writes only, and the stencil follows stencilMode[23:16] alone (SPEC
     §21.4 L6226-6227, L3258, L3312).
   - So ZWRITEENABLE FALSE (every shadow-volume pass) keeps the stencil ops working. 3dfx's HAL clears
     `SST_ZAWRMASK` whenever Z is off, with no stencil exception (`VH5/D3RSTATE.C:1156-1189`).
3. **The Halo evidence is weaker than the gap says.**
   - halo.exe's `CCW_STENCILFAIL/FUNC/PASS/ZFAIL` strings sit inside a complete D3D9 render-state name table
     (strings 14330-14440, beside COLORWRITEENABLE1-3, TWOSIDEDSTENCILMODE and ADAPTIVETESS_*). That is the
     D3DX effect-state table. It does not show that Halo uses two-sided stencil.
   - The Halo-specific hint is the rasterizer global `rasterizer_stencil_mask` (string 17711). Its use is
     unmeasured.

**Who needs it today: no staged `.124` title is shown to use stencil.** The case-insensitive scan, title by
title:

| title | stencil strings | reading |
|---|---|---|
| UT2003/UT2004 | `D3DDrv.dll` `SetStencilOp` | stencil only with `UseStencil=True` (D24S8, `G19.md`); staged `UseStencil=False` (`onbox/games/ut2003/UT2003.ini_before:258,279,290`) |
| Max Payne | `e2_d3d8_driver_mfc.dll`: `P_D3D::getStencilMask(D3DFORMAT)` | a depth-format helper; use unmeasured |
| Hidden & Dangerous | `igraph2.dll` | a caps dump that prints the stencil cap names |
| Thief II | `D3DX9_43.dll` only | D3DX's effect table |
| BF1942 | `SStencilEnable/Func/PassOp` | blocked by SafeDisc 2.80 before D3D (G72, not ours) |
| Red Faction, Rainbow Six, Shogo, System Shock 2, Thief Gold, AvP, JK DF2, MotS | 0 hits | none |

Render states are numbers, so a title can use stencil with no string at all. The step-0 counter (§4.10) is the
measurement that matters.

**Priority P3.** Escalate it to P1 if the counters (this item's step 0, or G76) show a staged title enabling
stencil or clearing it on D24S8, or if boot C (§7) shows a title taking a stencil path.

**Not possible on this chip:**
- stencil at 16 bpp (SPEC §8.27 L3358);
- two-sided stencil in one pass: there is one stencilOp register. It is not offered: no `D3DSTENCILCAPS_TWOSIDED`.

| fact | source |

## 2. The design in one paragraph

Behind `Diag\D3DFeat` bit **STENCIL**, read at boot, VSA-100 with `D3D32` only:
- `target_of` records whether the Z surface carries the 8 stencil bits (D24S8 as we list it), at a 32 bpp target;
- `compute_regs` turns the eight D3D stencil states into stencilMode/stencilOp through a new Win32-free header,
  and `VcrDd3dState` writes the pair when stencil is live;
- `D3DCLEAR_STENCIL` becomes part of the FASTFILL (stencilMode = 0x00ff0000 | value before the fills, 0 after);
- the target sequence writes the disable pair at 16 bpp too, so no stencil state of ours outlives a 32 bpp
  context.

A second bit, **STENCILCAPS**, reports `dwStencilCaps = 0xff`, so the caps change can be proven apart from the
drawing. With D3DFeat absent, every register write and every caps byte is today's.

## 3. The header: `KMD/include/vcr_stencil.h` (new, Win32-free)

Integer only, like `vcr_rtfmt.h`. The HAL (`-mgeneral-regs-only`) and the native test compile the same code.

```c
#ifndef VCR_STENCIL_H
#define VCR_STENCIL_H

#define VCR_SM_REF(v)       ((unsigned)(v) & 0xffu)              /* stencilMode [7:0]  */
#define VCR_SM_MASK(v)      (((unsigned)(v) & 0xffu) << 8)       /* [15:8] read mask   */
#define VCR_SM_WMASK(v)     (((unsigned)(v) & 0xffu) << 16)      /* [23:16] write mask */
#define VCR_SM_ENABLE       (1u << 24)
#define VCR_SM_FUNC(f)      (((unsigned)(f) & 7u) << 25)
#define VCR_SO_FAIL(o)      ((unsigned)(o) & 0xfu)               /* stencilOp [3:0]  */
#define VCR_SO_ZFAIL(o)     (((unsigned)(o) & 0xfu) << 4)        /* [7:4]  */
#define VCR_SO_ZPASS(o)     (((unsigned)(o) & 0xfu) << 8)        /* [11:8] */

/* D3DSTENCILCAPS_KEEP .. DECR (0x01 .. 0x80), as VH5/D3INIT.C:3243-3255.
 * Never D3DSTENCILCAPS_TWOSIDED (0x100): one stencilOp serves both faces */
#define VCR_STENCIL_CAPS    0xffu

/* D3DSTENCILOP_* 1..8 -> 0..7 (SPEC 8.28, "ordering ... to match D3D"); else KEEP */
static __inline unsigned vcr_stencil_op(unsigned d3d)
{
    return d3d >= 1u && d3d <= 8u ? d3d - 1u : 0u;
}

/* D3DCMP_* 1..8 -> stencilMode[27:25]; else ALWAYS (the HAL's cmp() rule) */
static __inline unsigned vcr_stencil_func(unsigned d3d)
{
    return d3d >= 1u && d3d <= 8u ? d3d - 1u : 7u;
}

/* the Z surface's stencil bits from its DDPIXELFORMAT: 8 only for the layout
 * GUID_ZPixelFormats lists (DDPF_STENCILBUFFER, 8 bits, mask 0xff000000 = the
 * aux word's top byte); anything else 0 */
#define VCR_DDPF_STENCILBUFFER 0x4000u
static __inline unsigned vcr_stencil_zbits(unsigned flags, unsigned bits, unsigned mask)
{
    return (flags & VCR_DDPF_STENCILBUFFER) && bits == 8u && mask == 0xff000000u ? 8u : 0u;
}

/* live: armed (Diag\D3DFeat STENCIL), a 32 bpp target, a Z it accepted, 8 stencil bits */
static __inline unsigned vcr_stencil_live(unsigned armed, unsigned fmt, unsigned z_on,
                                          unsigned z_stencil)
{
    return armed && fmt == 32u && z_on && z_stencil == 8u;
}

/* the pair for a draw. Not live, or STENCILENABLE FALSE: 0/0 (DISABLE + KEEP),
 * whatever the other seven states hold - an enable bit cleared alone is
 * ALWAYS + REPLACE under the write mask (H3DEFS.H:157-162) */
static __inline void vcr_stencil_draw(unsigned live, unsigned enable, unsigned func,
                                      unsigned ref, unsigned mask, unsigned wmask,
                                      unsigned fail, unsigned zfail, unsigned pass,
                                      unsigned *mode, unsigned *op)
{
    if (!live || !enable) {
        *mode = *op = 0u;
        return;
    }
    *mode = VCR_SM_REF(ref) | VCR_SM_MASK(mask) | VCR_SM_WMASK(wmask) | VCR_SM_ENABLE |
            VCR_SM_FUNC(vcr_stencil_func(func));
    *op = VCR_SO_FAIL(vcr_stencil_op(fail)) | VCR_SO_ZFAIL(vcr_stencil_op(zfail)) |
          VCR_SO_ZPASS(vcr_stencil_op(pass));
}

/* stencilMode for a FASTFILL: write mask all set (a fill has no per-bit mask,
 * and D3D's Clear writes every bit), the value in [7:0], enable clear (as
 * SST_STENCIL_MODE_CLEAR, D7DP2.C:867). clear 0: 0 - the fill leaves it alone */
static __inline unsigned vcr_stencil_clear_mode(unsigned clear, unsigned v)
{
    return clear ? VCR_SM_WMASK(0xffu) | VCR_SM_REF(v) : 0u;
}
#endif
```

## 4. The changes, function by function

### 4.1 `vcr3d_target` and `target_of` (`vcrdd_3d.h:27-34`, `vcrdd_d3d.c:1047-1088`)

- `vcr3d_target` gains `ULONG z_stencil;`. It is 8 when the accepted Z has the 24+8 layout and the target is
  32 bpp, else 0.
- At the end of `target_of`:
  `t->z_stencil = t->z_on && fmt == VCR_RT_32 ? surf_zstencil(c->zb) : 0;`
  - `surf_zstencil` returns `vcr_stencil_zbits(f->dwFlags, f->dwStencilBitDepth, f->dwStencilBitMask)` over
    `c->zb->lpGbl->ddpfSurface`.
  - It is recomputed at every DP2/Clear2 call and every SETRENDERTARGET, because `target_of` already runs there.
- Interaction with G10:
  - a D16 promoted to 32-bit storage keeps its D16 label (`G10.md` §4.2), so it has no stencil;
  - a 16 bpp target over a D24S8 (Rainbow Six's 16/16 rows) is `fmt` 16, so it has no stencil. That is
    correct: the chip has none at 16 bpp.

### 4.2 `compute_regs` (`vcrdd_d3d.c:921-1029`)

`vcr3d_regs` gains `ULONG st_live, stencilMode, stencilOp;`. Before `log_combo`:

```c
    r->st_live = 0;
    r->stencilMode = r->stencilOp = 0;
    if (c->rs[D3DRENDERSTATE_STENCILENABLE]) {
        unsigned live = vcr_stencil_live(c->pd->d3d_stencil, c->target.fmt, c->target.z_on,
                                         c->target.z_stencil);
        c->st_enabled++;                                   /* step 0 counter, every build */
        c->st_ops |= (1u << vcr_stencil_op(c->rs[D3DRENDERSTATE_STENCILFAIL])) |
                     (1u << vcr_stencil_op(c->rs[D3DRENDERSTATE_STENCILZFAIL])) |
                     (1u << vcr_stencil_op(c->rs[D3DRENDERSTATE_STENCILPASS]));
        c->st_funcs |= 1u << vcr_stencil_func(c->rs[D3DRENDERSTATE_STENCILFUNC]);
        if (live) {
            vcr_stencil_draw(1, 1, c->rs[D3DRENDERSTATE_STENCILFUNC],
                             c->rs[D3DRENDERSTATE_STENCILREF], c->rs[D3DRENDERSTATE_STENCILMASK],
                             c->rs[D3DRENDERSTATE_STENCILWRITEMASK],
                             c->rs[D3DRENDERSTATE_STENCILFAIL], c->rs[D3DRENDERSTATE_STENCILZFAIL],
                             c->rs[D3DRENDERSTATE_STENCILPASS], &r->stencilMode, &r->stencilOp);
            r->st_live = 1;
            c->st_drawn++;                         /* live state computations */
        }
    }
```

- Enabled but not live means one of three things: STENCIL is not armed, the target is 16 bpp, or the Z has no
  stencil bits. That draw is today's draw: the target's 0/0 stands.
- In D3D10 and OpenGL, an enabled stencil test with no stencil buffer passes, and 3dfx strips the enable below
  32 bpp. That D3D8/9 has the same rule is (inferred).
- Depth is untouched: stencil works with ZENABLE FALSE (only the fail and pass ops) and with ZWRITEENABLE FALSE
  (§0 refinement 2).
- `st_live` is also the flag G25's specular second pass reads ("pass 2 must not run stencil ops twice",
  `G25.md:394`).

### 4.3 `ctx_defaults` (`vcrdd_d3d.c:1126-1158`)

Set D3D's defaults, so a runtime that does not send every default still starts from D3D's state:
- STENCILENABLE FALSE;
- FAIL, ZFAIL and PASS = `D3DSTENCILOP_KEEP`;
- FUNC = `D3DCMP_ALWAYS`;
- REF 0;
- MASK and WRITEMASK `0xffffffff`.

This touches only `c->rs[]`, which nothing reads unless STENCIL is armed.

### 4.4 `VcrDd3dState` (`vcrdd_3d.c:74-129`): the live pair, last

After the TMU1 block, before `pd->g2d_busy = 1`:

```c
    if (r->st_live) {               /* Diag\D3DFeat STENCIL, 32 bpp over D24S8, STENCILENABLE */
        if (!VcrDdRoom(pd, 2))
            return FALSE;
        w3(pd, V3D_STENCILMODE, r->stencilMode);
        w3(pd, V3D_STENCILOP, r->stencilOp);
    }
```

- It goes **last**, with its own FIFO room, so that every existing `VcrDdRoom` count (12, the fog chunks, 5, 4)
  covers exactly what it covers today.
- `prepare()` always sends the target before the state (`:1361`). Stencil therefore goes 0/0 (the target) then
  live (the state). When STENCILENABLE goes FALSE, the next re-send leaves only the target's 0/0. The chip never
  keeps a stale enable inside a context.

### 4.5 The target sequence: the disable pair at 16 bpp too, when armed (`vcr_3dseq.h:56-77`)

`vcr_3d_target_seq(napalm, rt32, fmt, ...)` gains a parameter `st16` ("write the disable pair at 16 bpp too").
`VcrDd3dTarget` passes `pd->d3d_stencil`; every existing test call passes 0.

```c
    if (napalm) {
        w[n].off = V3D_RENDERMODE;  w[n++].val = vcr_rt_rendermode(fmt);
        if (fmt == VCR_RT_32 || st16) {
            w[n].off = V3D_STENCILMODE; w[n++].val = 0;
            w[n].off = V3D_STENCILOP;   w[n++].val = 0;
        }
    }
```

Why it is needed:
- With stencil live, a 32 bpp context can end with an enabled stencilMode on chip 0.
- A later 16 bpp context writes no stencil today. The proven 16 bpp lane would then draw under our own stale
  enable, and whether the chip ignores it at 16 bpp is exactly the unproven premise (hw S2, `PLAN:888-892`, G03).
- With STENCIL armed, a 16 bpp target writes 0/0 and that path is closed. The values are the vendor's: its NT
  HAL writes DISABLE/0 on every state send at any depth (`VH5/D6DP2.C:6107-6130`).

Cost and coverage:
- 16 bpp armed: 9 writes, exactly 4a9793b's sequence. That sequence was rejected only because it ran with no
  switch (`test_vcr_kmd_d3dseq.c:62-82`). `VCR_3D_TARGET_MAX` stays 9.
- Glide after D3D is covered by Glide itself (§1, `gsst.c:956`).
- Reset3D and G03's baseline write the same 0/0. G03 runs at every depth when its own switch is armed, and is
  harmless next to this.

### 4.6 Clears (`vcrdd_d3d.c:1408-1421, 1754-1758, 1873-1903`; `vcrdd_3d.c:136-179`)

1. **The value reaches `clear_rects`:**
   - `clear_rects(w, flags, color, zbits, stencil, r, n)`;
   - the DP2 CLEAR passes `rd(p + 12)`, the record's `dwFillStencil`. `NEED(16 + n * sizeof(RECT))` already
     covers it;
   - Clear2 passes `p->dwFillStencil`.
2. **The flag, only where it can be honoured:**
   ```c
   if (flags & D3DCLEAR_STENCIL) {
       c->st_clears++;                                         /* step 0 counter */
       if (c->pd->d3d_stencil && c->target.z_stencil)
           what |= VCR3D_CLEAR_STENCIL;                        /* else dropped, as today */
       /* st_clears_done++ once VcrDd3dClear has run with the bit */
   }
   ```
   A stencil-only clear now passes the `!what` return only when it can be done.
3. **The register writes move into `vcr_3dseq.h`, so the host test pins them** (recommended; an inline edit of
   `VcrDd3dClear` works too):
   - `VCR3D_CLEAR_COLOR/Z/STENCIL` (1/2/4) move from `vcrdd_3d.h:60-61` into `vcr_3dseq.h`;
   - `vcr_3d_clear_head(what, z_on, argb, zv, stencil, w)`:
     - fbzMode = `FZ_RECTCLIP` plus `FZ_RGBWRITE` and/or `FZ_ZAWRITE`, as today;
     - c1 and zaColor;
     - **plus `stencilMode = vcr_stencil_clear_mode(1, stencil)` when `what & VCR3D_CLEAR_STENCIL`**;
   - `vcr_3d_clear_tail(what, width, height, w)`:
     - the full-target clip, as today (`:173-176`);
     - **plus `stencilMode = 0` after a stencil clear**, so no fill mode is left on the chip;
   - `VcrDd3dClear(pd, t, what, argb, zbits, stencil, rc, n)`:
     - still does the float→depth conversion;
     - calls `VcrDdRoom(pd, nhead)` (3 or 4), writes the head, then does the per-rectangle clip + fastfill loop
       unchanged;
     - then `VcrDdRoom(pd, ntail)` (2 or 3) and the tail.
   - Without the stencil bit, the counts are 3 and 2 and the writes are today's, byte for byte.
4. **Why the stencil value goes into stencilMode, never zaColor:**
   - zaColor[31:24] is the alpha field (`vcr_rtfmt.h:45-47`, pinned by `a_depth_clear_never_touches_the_top_byte`);
   - G22's Z bias owns zaColor[23:0]. A stencil clear changes neither.
5. **What a clear leaves:**
   - the target sequence before it wrote stencilMode 0 (32 bpp, and 16 bpp when armed). So a TARGET or ZBUFFER
     clear without the stencil flag never touches the stencil byte, which is D3D's rule;
   - stencil-only: fbzMode = `FZ_RECTCLIP` (0x001), so neither colour nor depth is written, only stencil;
   - the clip rectangle limits the stencil fill like the others, so a rect-limited Clear works.

### 4.7 Caps (`vcrdd_d3d.c:2150-2172`)

`x.dwStencilCaps = pd->d3d_stencil_caps ? VCR_STENCIL_CAPS : 0;`

- It is the only assignment of the field.
- The Z list, `DDBD_*`, the misc caps and the format list do not change.
- Caps are global, so a 16 bpp device also sees 0xff. D3D8 refuses R5G6B5 with D24S8 itself (`caps_124.txt` zmatch
  `R5G6B5/D24S8 match 0`). A D3D8/9 title at 16 bpp therefore finds no stencil format, as today.
- A DX6/7 title that pairs a D24S8 with a 16 bpp target gets no stencil: a hardware limit, logged (§4.10).

### 4.8 The switch: two positive bits of `Diag\D3DFeat`, read at boot

- **`VCR_D3DFEAT_STENCIL`** (provisional bit 14, `0x4000`): §4.1-§4.6. The register traffic and the counters'
  "live" path.
- **`VCR_D3DFEAT_STENCILCAPS`** (provisional bit 15, `0x8000`): §4.7. It is ignored unless STENCIL is set.

Why the numbers:
- `reports/hal.md` §10 gives Phase 2 bits 0-5 and Phase 3 bits 6+;
- the siblings propose 0 (G15), 1 (G08), 2 (G22), 4 (G16), 6-8 (G12, with G05/G13), 10-11 (G26) and 12-13 (G28);
- 14/15 sit above all of them. The final numbers belong to whichever item lands `include/vcr_d3dfeat.h`
  first.

**Transport** (shared; created by whichever D3DFeat item lands first, `G15.md` §5, `G26.md` §4.6):
- the miniport reads `VcrDiagGet(L"D3DFeat", 0)` **at boot**, beside `D3DBigTex` (`vcrmp.c:238-244`). The caps
  a title reads at its desktop must equal its fullscreen PDEV's;
- it reports the word in an appended `vcr_info.d3dfeat`, pinned by `test_vcr_kmd_abi.c`;
- `VcrDd2dInit` (`vcrdd_2d.c:432-475`) zeroes `info` before the IOCTL, so an older miniport reads as 0, and
  resets both fields to 0 with the other D3D flags:
  ```c
  pd->d3d_stencil = pd->rt32 && (info.d3dfeat & VCR_D3DFEAT_STENCIL) ? 1 : 0;    /* rt32 implies napalm */
  pd->d3d_stencil_caps = pd->d3d_stencil && (info.d3dfeat & VCR_D3DFEAT_STENCILCAPS) ? 1 : 0;
  ```
- one INFO event, 513 at the next free `what` (24-26 are proposed by siblings): "armed (Diag\D3DFeat %x):
  stencil ON, stencil caps ON|off". The 513 description string in `vcr_events.h` gains the new `what` values.

**Why it is not safe default-on:**
- it is new register traffic whose silicon behaviour is unproven: the triangle stencil ops, the FASTFILL stencil
  on SDRAM, and the 16 bpp disable pair;
- the caps change can move titles onto stencil paths never seen on this HAL (Halo, Max Payne).

It stays OFF until boot C (§7) passes. Graduation then follows the plan's D3DFeat convention (an open question
for the plan; G05 Q4).

### 4.9 Exact traffic, off against armed

| path | D3DFeat absent (today) | STENCIL armed |
|---|---|---|
| 16 bpp target setup | renderMode + 6 (7 writes) | renderMode, **stencilMode 0, stencilOp 0**, + 6 (9) |
| 32 bpp target setup | renderMode, 0, 0, + 6 (9) | unchanged |
| state send, stencil off or not live | 8 + fog + TMU writes | unchanged |
| state send, stencil live | n/a (the states are ignored) | + **stencilMode, stencilOp** (live values), last |
| clear without `D3DCLEAR_STENCIL` | fbzMode, c1, zaColor; (clip, clip, fastfill) × n; clip, clip | unchanged |
| clear with it, 32 bpp over D24S8 | the stencil part is dropped (a stencil-only clear writes nothing) | + **stencilMode = 0x00ff0000\|v** before the fills, **stencilMode 0** after |
| caps | `dwStencilCaps` 0 | 0 (STENCIL) / **0xff** (+STENCILCAPS) |
| Z list, DDBD, texture formats | unchanged | unchanged |
| Banshee / Voodoo3 | n/a | never armed (needs `rt32`) |

### 4.10 Step 0: measure (log-only, every build, no register write)

This is G76's STENCILENABLE counter, carried here so the measurement does not wait for G76. If G76 lands first,
its counter block is reused.

- **Context fields:**
  - `st_enabled`: state computations with STENCILENABLE TRUE;
  - `st_drawn`: of those, the ones where stencil was live (armed, 32 bpp, 8 stencil bits);
  - `st_clears`: clears with `D3DCLEAR_STENCIL`;
  - `st_clears_done`: of those, the ones executed with `VCR3D_CLEAR_STENCIL`;
  - `st_ops`, `st_funcs`: bit masks of the ops and compares seen;
  - `st_twosided`: `c->rs[185]` (D3DRS_TWOSIDEDSTENCILMODE) set non-zero. That shows a D3D9 title expecting
    two-sided stencil despite the caps.
- **`ctx_free`** (`:1210-1221`): when any field is non-zero, one INFO line, 513 at the next free `what`.
  It is written at the context's end, so a ring that wraps during the game still holds it:
  `context %u stencil: enabled %u, live %u, clears %u (done %u), ops %x, funcs %x, two-sided %u`.
- **`ContextCreate`** (`:1163-1207`): when the Z has `DDPF_STENCILBUFFER`, one INFO line:
  `ContextCreate %u: Z flags %x stencil %u bits mask %x - stencil %s`, where %s is "live-capable", "not armed",
  "16 bpp target" or "layout refused".
  - If the runtime ever hands us a D24S8 whose format fields differ from our list, this line names the fields,
    so `vcr_stencil_zbits` can be corrected rather than guessed.
  - The 513/1 line itself is left as it is.

### 4.11 Deliberately not done

- **Two-sided stencil.** `D3DSTENCILCAPS_TWOSIDED` cannot be offered in one pass. A driver-side split is possible
  (inferred, not proposed): the HAL knows each triangle's winding, so it could switch stencilOp between CW and
  CCW runs. But it is unclear whether a DX7-DDI driver's caps or render states 185-189 even reach the D3D9 path.
  No staged title is shown to need it.
- **Stencil at 16 bpp.** It is a hardware limit (SPEC L3358).
- **The 2D byte-mask stencil clear.** D3D does not need it (§0). If the reference run (§5.4) shows that Windows
  drivers honour STENCILWRITEMASK in a Clear, a clear under a write mask other than 0xff becomes a follow-up.
  - Only a 2D rectangle fill of the aux buffer can do it: colorFore = value << 24 with a bit mask on the top
    byte, Glide's "hot WAX" (`GL5/gglide.c:2270-2312`).
  - Glide's other route, the aux buffer as a colour target with an alpha-only renderMode write enable
    (`GL5/gglide.c:2314-2422`), writes the whole byte too: that enable is per channel, not per bit.
- **SLI.** D3D draws on chip 0 (G51). If G51 lands, a stencil FASTFILL has the same SLI bugs as a Z fill (SPEC
  L2705-2709) and needs the 2D path the spec prescribes.

## 5. The d3dprobe tests (`KMD/tools/d3dprobe.c`)

They are explicit, never in the default list, like the big-texture tests.

**The pattern:**
- each test locks the back buffer and compares pixels with analytic colours, with no goldens;
- a test is **skipped, not failed**, when the device cannot hold the case. `d3dprobe_run.py` fails a run whose
  explicit `--tests` were skipped, which is wanted: a skipped stencil check is not a pass;
- every check is within the 256 × 256 readback (Q0 = 32, Q1 = 224);
- colours are flat, and at 32 bpp the tolerance is 8, as in `flat`.

**New plumbing:**
- `g_zused` = `pp.AutoDepthStencilFormat`;
- `frame_begin_s(colour, z, s)`: `Clear(TARGET|ZBUFFER|STENCIL)` then BeginScene;
- `st(en, func, ref, mask, wmask, fail, zfail, pass)` sets the eight states;
- `readout(x0, y0, x1, y1, v)`: Z off, a green quad with `EQUAL v`, then a red quad with `NOTEQUAL v`, then stencil
  off. **Green means the stencil is exactly v. Red means another value, or a stencil test that does nothing.
  Black means a test that never passes.**
- every stencil test ends with STENCILENABLE FALSE and Z off, so the tests after it run as before.

**When it runs:** `StencilCaps & 0xff == 0xff`, a 32 bpp back buffer and `g_zused == D3DFMT_D24S8`; otherwise

**How to run it on `.124`:**
- windowed on the 32 bpp desktop: `render --bpp 32 --zfmt d24s8 --tests stencil`. That needs no mode switch;
- once fullscreen at `--full --res 1024x768 --bpp 32 --zfmt d24s8`.

### 5.2 `stencil_nocaps` (the A/B)

- The same nine frames, gated only on a 32 bpp back buffer with D24S8; the caps are not asked.
- On the off build it **fails**: that is today's no-op stencil, recorded. With STENCIL armed it passes.
- If the D3D8 runtime strips `D3DCLEAR_STENCIL` for a HAL with StencilCaps 0 (inferred not to; unmeasured), F1,
  F7 and F8's clear checks fail in boot B while the draw checks pass, and the counter line shows 0 clears done.
  That outcome table is §7. The full verdict then belongs to boot C.

### 5.3 `stencil_nostencil` (the guard)

- **When it runs:** a Z **without** stencil (D16 at 16 bpp, or `--zfmt d24x8` at 32 bpp); otherwise skipped.
- **Scene:** Clear(TARGET|ZBUFFER); `st(1, NEVER, 0x44, ff, ff, REPLACE ×3)`; Z off; a green quad.
- **Pass:** (128,128) green on every build. Stencil without stencil bits must never be live; a red or black
  pixel there means the new code armed the test on a Z that has none.

### 5.4 `stencil_clearmask` (informational, never gating)

- **Scene:** clear S = 0; STENCILWRITEMASK 0x0f, enable off; `Clear(STENCIL, 0xff)`; readout with 0xff.
- **Recorded as a `note`** (the `texhigh` pattern): "clear ignored the write mask" (green, our design and the
  vendor's) or "honoured it" (red: the value is 0x0f).
- **Run it once on a reference D3D driver first** (a GeForce box from `docs/fleet-inventory.md`), together with
  `stencil`. That checks the probe's own expectations against a known-good driver before `.124` is judged.
  `d3dprobe` is built to run on any driver (header, `:1-3`).

### 5.5 `caps`

The JSON gains `"StencilCaps":"%08lx"`. Expected: `00000000` off and with STENCIL alone; `000000ff` with
STENCILCAPS. G74 wants the same field; whichever lands first adds it.

## 8. Risk to proven paths

| path | with D3DFeat absent | with STENCIL armed |
|---|---|---|
| default 16 bpp D3D | byte-for-byte: no new write, same `VcrDdRoom` counts (pinned by §6.2 `st16 = 0`) | +2 writes of 0 per target setup: 3dfx's own per-state-send values. Covered by the 16 bpp runs in boots B and C |
| 32 bpp D3D | byte-for-byte | unchanged unless a title enables stencil on D24S8. A title that set stencil states believing them ignored (StencilCaps 0) now gets them honoured, which is correct D3D. Boot B's title checks would show such a title |
| clears | byte-for-byte (`what` never carries STENCIL) | +2 writes only for a stencil clear |
| Glide/OpenGL coexistence | unchanged | Glide's window open writes stencilMode 0 (`gsst.c:956`, `distate.c:2265-2284`), and our next target writes 0/0 at any depth. No D3D stencil state survives into either API. Reset3D and G03 write the same pair |
| SLI | none: D3D is chip 0 only, no sliCtrl or chipMask write | none |
| flip path | none | none |
| caps-driven title behaviour | none | only with STENCILCAPS (boot C), watched per title |
| CPU cost | counters: a few adds per state change; two log lines per context | +1 test per state computation |

**Code risks:**
- **A D24S8 surface whose `ddpfSurface` lacks `DDPF_STENCILBUFFER` on NT.** Stencil then stays off, which is safe
  and is today's behaviour. The ContextCreate line names the fields (§4.10).
- **G53's register shadowing.** When it lands, it must treat stencilMode/stencilOp as written by three writers:
  the target, the state and the clear. That is noted for G53.

## 10. Open questions

1. **Does XP's D3D8 runtime pass `D3DCLEAR_STENCIL` and the stencil render states to a DX7 HAL whose StencilCaps
   is 0?** Inferred yes for the states, unknown for the clear. Boot B's outcome table answers it.
2. **Does a Windows D3D driver's Clear honour STENCILWRITEMASK?** The design follows 3dfx's HAL: it does not.
   `stencil_clearmask` on a GeForce box answers it.
3. **Does the native FASTFILL stencil write work on `.124`'s SDRAM?** Glide avoids it on SDRAM: it uses the
   aux buffer as a colour target (`gglide.c:2314-2422`, inside the windowed-or-SDRAM branch that the SGRAM-fullscreen test at `:2182` sends it to, `:2228-2245`), while 3dfx's D3D HAL uses the native fill. F1 and F7 answer it.
   **Fallback:** Glide's trick, which needs renderMode alpha-only write enables and a second fastfill per
   rectangle.
4. **Does any staged title use stencil once caps are reported?** Halo (`rasterizer_stencil_mask`) and Max Payne
   (`getStencilMask`) are the candidates. Boot C's counters answer it.
5. **Are the D3DFeat bit numbers (14/15), the transport (appended word or flags) and the graduation convention
   right?** These are plan-level questions, shared with every D3DFeat item.
6. **Should boots B and C merge?** It saves a reboot but breaks the one-change rule. It is the user's call.
7. **Should D24S8 stay listed while STENCIL is off?** Recommendation: yes, as today. `vcr_rtfmt.h` explains why:
   apps that name it would otherwise find no 24-bit Z.
