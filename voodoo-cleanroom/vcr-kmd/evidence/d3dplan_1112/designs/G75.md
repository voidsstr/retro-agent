## 0. Verdict

1. **The gap is real and fixable: it is tooling, with no driver change.**
   - d3dprobe is Direct3D 8 only. It calls `Direct3DCreate8` (`KMD/tools/d3dprobe.c:1307`) and links `-ld3d8`
     (`KMD/Makefile:102`); `out/d3dprobe.exe` imports `d3d8.dll`.
   - Every HAL path that only a DirectX 3-7 client reaches therefore has no lab test (section 1).
   - The `D3DOP_EXIT` fix that let Jedi Knight run (`c6a3e93`) is pinned only by a source-text test. Nothing
     replays an execute buffer.
2. **The plan's wording is half wrong, and the design changes because of it: a DX7 probe cannot send the legacy
   states.**
   - XP's DX7 runtime refuses render states 1, 3, 17, 18, 21, 43-46 and 49 with `E_INVALIDARG` and never emits
     them (F1 below).
   - So the legacy tests G08 needs must go through the DX6 runtime, `d3dim.dll`: `IDirect3DDevice3`,
     `IDirect3DDevice2` and `IDirect3DDevice` with execute buffers. That runtime is what Jedi Knight, MotS, Rainbow
     Six, AvP, Thief Gold, System Shock 2 and Shogo talk to.
   - The design is **one probe, `d3d7probe`, with two families:**
     - `dx7`: `IDirect3DDevice7` on `d3dim700.dll` (colour keys, state blocks, DX7 texture loads, primitives);
     - `legacy`: `IDirect3DDevice3`, `IDirect3DDevice2` and execute buffers on `d3dim.dll` (legacy states, texture
       handles, `D3DOP_EXIT`, edge flags, lines and points).
3. **Five runtime facts, read in the disassembly for this design.** The probe is built around them (section 2):
   - **F1.** `d3dim700` keeps a 51-entry table of retired render states. Its `SetRenderState` stores their value
     and answers `0x80070057`, with no token.
   - **F2.** `d3dim`'s `SetRenderState` forwards every state 1-255 raw, but drops a value equal to the runtime's
     stored copy (when the device field +0xf50 >= 2), and its `SetTextureStageState` always drops an unchanged
     value. **A test must never rely on re-sending the runtime's current value.** G08's `legacy_order`, as
     written, would be filtered and would fail against a correct HAL.
   - **F3.** `IDirect3DDevice7::SetRenderTarget` either emits a DP2 `SETRENDERTARGET` or destroys and re-creates
     the driver context, depending on the device class. One class then re-sends render states 2-135 with no
     retired-state filter and no TSS. That is the one way a DX7 context could carry `TEXTUREMAPBLEND`, which is
     G08's open hazard.
   - **F4.** The input `dwhContext` of ContextCreate: `d3dim700` passes 3; `d3dim` passes `[device+4] - 1` at one
     site and 0 at another.
   - **F5.** Both runtimes carry Microsoft's RGB software rasterizer. It is a reference that needs no 3D hardware
     and no mode switch.
4. **The pieces.**
   - `tools/d3d7probe.c`.
   - `tools/d3d7probe_ref.h`: Win32-free. It holds the analytic expected values, the execute-buffer encoder and
     the test catalogue.
   - `tools/d3d7probe_run.py`: the runner. It runs a read-only pre-flight (including G01's stale-FIFO
     condition), attributes the HAL's flight-recorder events to each test, and grades each check three ways:
     `ok` / `old` / `bad`.
   - Caps goldens.
   - 30 core tests, and room for the tests G08, G09, G16, G38, G40 and others add.
5. **Gating.**
   - The probe changes no driver byte and no Diag switch. It is safe to land default-on, because it runs only when
     invoked.
   - Running it on `.124` follows the lab rules:
     - offscreen by default, with **no mode switch**;
     - `--full` paced through `vcr_pace.h` at 5 s;
     - read-only pre- and post-flight;
     - the first run of each family supervised.
6. **Priority P1. Effort L** (the frame, the DX7 core and the execute-buffer core are an M).
   - It is the prerequisite for verifying G08 and G09, both P1 quality fixes in staged DX5/DX6 titles.
   - It is the only lab gate for the `D3DOP_EXIT` fix. A regression there crashes Jedi Knight on `.124`.

## 2. The runtimes the probe drives (read for this design)

### 2.1 Which DLL serves which interface

A scan for the interface GUIDs (`uuid.bytes_le` in each file) gives:

| file | interfaces carried |
|---|---|
| `d3dim.dll` | IID_IDirect3D, IDirect3D2, IDirect3D3, IDirect3DDevice, IDirect3DDevice2, IDirect3DDevice3, IDirect3DExecuteBuffer, IDirect3DTexture, IDirect3DTexture2; device GUIDs HAL, RGB, MMX, Ref, Null, Ramp |
| `d3dim700.dll` | IID_IDirect3D7, IDirect3DDevice7; device GUIDs HAL, TnLHal, RGB, MMX, Ref, Null, Ramp |

This confirms the split that `RPT/runtime.md` §1 inferred: the DX3/5/6 interfaces are served by `d3dim.dll`, and
the DX7 interface by `d3dim700.dll`. A DirectDraw 7 object cannot supply `IDirect3D3` **(inferred)**, so the
probe makes one DirectDraw object per family.

### 2.2 F1: `IDirect3DDevice7` cannot reach the HAL with a legacy state

- **The table.** 51 dwords at 0x739482a8 (file offset 0x74a8):
  1, 3, 5, 6, 11, 12, 13, 17, 18, 21, 31, 32, 39, 43, 44, 45, 46, 49, 51, 64-95. These are TEXTUREHANDLE,
  TEXTUREADDRESS, WRAPU/V, MONOENABLE/ROP2/PLANEMASK, TEXTUREMAG, TEXTUREMIN, TEXTUREMAPBLEND,
  SUBPIXEL(X), STIPPLEENABLE, BORDERCOLOR, TEXTUREADDRESSU/V, MIPMAPLODBIAS, ANISOTROPY,
  TRANSLUCENTSORTINDEPENDENT and the stipple pattern.
  - The table is loaded into a per-device bitmap at +0x31d0 (`0x7394a350-0x7394a377`).
  - A second, 81-entry table at 0x73948160 (special states plus the same 51) fills +0x31b0.
- **The validator** `0x7394f442` returns 0 for a state in the +0x31d0 bitmap.
- **The public `SetRenderState`** is `0x7394f8c9`. It is at slot +0x50 of all four device vtables (0x73948448,
  0x739485a0, 0x739486f8, 0x739494f0).
  - While a state block records, it validates first and returns 0x80070057 for these states
    (`0x7394f903-0x7394f939`). The branch is taken on bit 0x1000 of +0x1a6c and calls the state-set recorder
    `0x739521df`, whose gate G40 read at `0x739521f4`; so that bit is "recording" **(inferred)**.
  - Otherwise it calls vtable +0x10c, `0x73951237`, in every class.
- **The internal setter** `0x73951237`:
  - Takes states in the +0x31b0 bitmap down a slow path.
  - That path calls `0x739504e2`, which ends by **storing the value** in the runtime's state array
    (`0x73950822-0x73950828`, `[+0x2998]`).
  - It then validates (`0x739512bf`) and returns **0x80070057** (`0x739512d6`) **without emitting a token**. That
    holds for a state below the device's limit at +0x31ac (`0x739512b7`); at or above it the call returns `S_OK`,
    also without a token.
- **Other states.** `COLORKEYENABLE` (41) is in neither table. Like any ordinary state it is stored and emitted
  when it changes (`0x73951266-0x739512d2`).

### 2.3 F2: the DX6 runtime forwards raw, but filters unchanged values

- **`SetRenderState`** is `0x6d921737`. `IDirect3DDevice3` reaches it directly; `IDirect3DDevice2` goes through the
  this-adjusting thunk `0x6d9161cd`.
  - States 0 and 256 or above get 0x80070057 (`0x6d921758-0x6d921768`).
  - 50 (FLUSHBATCH) is a flush (`0x6d92176e`).
  - WRAPU/V (5/6) and WRAP0 (128) are cross-mapped (`0x6d9217b7-0x6d921879`).
  - Everything else is stored and emitted through vtable +0x80, the RENDERSTATE writer G08 found at `0x6d91a6d8`
    (`0x6d9218a8-0x6d9218ba`).
- **The redundancy filter.** A value equal to the stored copy is dropped when the device field +0xf50 >= 2
  (`0x6d92187f-0x6d9218a4`).
  - +0xf50 is compared with 2 and 3 elsewhere (`0x6d914f5c`, `0x6d922f7e`), which fits the interface version
    **(inferred)**.
  - So `IDirect3DDevice2/3` drop a repeat of the current value.
- **`SetTextureStageState`** is `0x6d91b516`, named `CDirect3DDeviceIDP2::SetTextureStageState` by its own
  string (0x6d911e04): the DP2 device class our driver gets. It compares with the stored copy and returns `S_OK`
  without a token when they are equal (`0x6d91b548-0x6d91b54c`), with no version test.
- **Execute buffers are not filtered (inferred).** The stream reaches the HAL as written: the 47 "unparsed" EXITs in
  JK's run were 4 bytes before the end of each stream (`vcrdd_d3d.c:1773-1782`, `c6a3e93`). That its STATERENDER
  records are passed through rather than re-filtered follows from that, and was not read in d3dim's Execute path.
- **Consequences for the probe:**
  1. **Forced delivery.** A test that needs a state token to arrive sets a different legal value first whenever
     the target value equals the runtime's current one: `rs_force()` and `tss_force()`, which read the runtime's
     current value with `GetRenderState`/`GetTextureStageState`. The HAL then receives the alternate value and then
     the target, so the last writer wins.
  2. **G08's `legacy_order` must be re-sequenced** (section 4.2, test 18). Step 2's `ALPHAOP SELECTARG1` equals the
     runtime's stored default, and step 3's second `MODULATE` equals its stored rs[21]. On `IDirect3DDevice3` both
     would be dropped, and a correct HAL would read (32,0,0) where G08's table expects (128,0,0).
  3. **G08's "map on every receipt" choice** (`DSN/G08.md` §4.2 item 1) still matters for execute buffers. From
     `IDirect3DDevice2/3` an identical re-send never arrives. `d6_rs_redundant` (section 4.2, test 19) measures
     which.

### 2.4 F3: what `IDirect3DDevice7::SetRenderTarget` does to the driver

`SetRenderTarget` is `0x7394feea`, at slot +0x20 of all four device vtables. After its surface checks it calls
vtable +0x118 (`0x739500cb`):

| device vtable | +0x118 (re-target) | +0xec (re-send) | what the HAL sees |
|---|---|---|---|
| 0x73948448 | `0x7394f2bf`: ContextDestroy, then ContextCreate with **`dwhContext` = 3 on input** (`0x7394f3ac`), then +0xec | `0x7394f28c`: render states **2-135, every one, no retired filter, no TSS** | a new context, then `TEXTUREMAPBLEND`/`TEXTUREMAG`/... with whatever the runtime holds. **This includes a value an F1-refused call stored.** |
| 0x739485a0 | `0x7394f2bf` (the same) | `0x73955040`: an 87-state list at 0x739ff320, then every stage's TSS | a new context. The list **excludes** 1, 3, 17, 18, 21, 43-46 and 49, and the TSS follow the RS |
| 0x739486f8, 0x739494f0 | `0x73956b99`: one DP2 token **0x29 (`SETRENDERTARGET`)**, 8 bytes | `0x73955040` | the same context, a SETRENDERTARGET record (`vcrdd_d3d.c:1725-1751`) |

- **Which class vcrdd gets is not settled here.** G40 places our driver at DDI 4 by its own reading; the mapping
  from class to DDI is **(inferred)**.
- **Why the first row matters to G08.** A DX7 title on a vcrdd device of class 0x73948448 hands the HAL the legacy
  texture states AFTER its TSS, at every `SetRenderTarget`. With G08's mapping armed, stage 0 would then be
  re-mapped behind the title's back. That is G08's check 3 (`lgc_misc` 0x100).
- **The probe settles both questions on silicon.** `d7_retarget` counts one context (a token) or two (a re-create)
  in the ring. `d7_retarget_legacy`, hosted for G08 (section 4.4), shows whether the hazard is live.

### 2.5 F4: ContextCreate's input `dwhContext`

- `d3dim700`'s re-create path writes 3 (`0x7394f3ac`, the record built at `0x7394f38d-0x7394f3b9`).
- `d3dim` writes `[device+4] - 1` at one ContextCreate site (`0x6d918204-0x6d918219`, after `GetCurrentProcessId`
  at `0x6d9181ea`). At its DP2 creation site it zeroes the record and writes no handle (`0x6d922280-0x6d92228b`,
  call at `0x6d92231b`).
- G08's open question 3 (scope its mapping by interface version) is therefore half settled. DX7 contexts are
  recognisable. DX6-runtime contexts are recognisable only at the first site, and only if `[device+4]` is the
  interface version **(inferred)**.
- The probe makes **one device per test, of a known interface** (section 3.3), so every context in the ring has a
  ground-truth label. G08's `lgc_hctx_in` counter can be calibrated against it.

### 2.6 F5: a Microsoft reference in the same runtimes

- Both DLLs carry the RGB software rasterizer: the device GUID scan in 2.1, and the strings "Microsoft Direct3D RGB
  Software Emulation" and "RGB Emulation" in each.
- It implements the legacy blend semantics itself (`DSN/G08.md` §2 item 3: d3dim `0x6d927f66`, the legacy pixel
  routine `0x6d946d40`).
- Run on it, with a system-memory target, every probe scene gets Microsoft's answer **with no 3D hardware and no
  mode switch**:
  - on the QEMU chassis bed (Bochs VGA, no D3D HAL; agent on 127.0.0.1:19910);
  - and on `.124` itself, in the same process and runtime as the HAL run.
- The 86Box bed adds a vendor DX7 HAL: XP's in-box 3dfx Voodoo3 driver, `3dfxvs.dll` 5.0.2489.28, "a full DX7 HAL
  at 16 and 32 bpp" (`KMD/tools/86box/README.md`, "The reference driver is already on it").
- So the probe's expected values are checked twice, independently, before they ever judge our HAL. Where the two
  references disagree, for example DECAL's alpha on an RGB texture (`DSN/G08.md` open question 5), the
  disagreement is recorded, not guessed.

### 3.2 Command line

```
d3d7probe caps                                   no device, no mode switch: IDirect3D7 and IDirect3D3
                                                 EnumDevices (HAL desc), EnumZBufferFormats
d3d7probe dx7    [--offscreen | --full] [--res WxH] [--bpp 16|32] [--device hal|rgb]
                 [--tests a,b,...] [--pace MS] [--log PATH]
d3d7probe legacy [same]  [--iface dev3,dev2,dev1]
```

- **`--offscreen` is the default.** The render target is a 256x256 `DDSCAPS_OFFSCREENPLAIN | DDSCAPS_3DDEVICE |
  DDSCAPS_VIDEOMEMORY` surface with an explicit pixel format, plus an attached Z. The cooperative level is NORMAL,
  and **no display mode is ever changed**.
  - `--bpp` defaults to the desktop depth.
  - `--bpp 16` on `.124`'s 32 bpp desktop asks DirectDraw and our `Dd_CanCreateSurface` for a 16 bpp 3D surface.
    The latter accepts any non-Z format (`vcrdd_ddraw.c:610-630`). That gives the legacy 16 bpp lane without a
    mode switch.
  - **Whether dxg accepts it is unverified.** A refusal is reported as `"offscreen16":"refused <hr>"`, and
    `--full` covers that lane.
- **`--full`** is exclusive fullscreen: a primary plus one back buffer with `DDSCAPS_3DDEVICE`, and a Z attached
  to the back buffer.
  - **Exactly two mode switches per run** (in at the start, out at the end), both through `vcr_pace.h`.
  - The default pace is raised to 5000 ms by the runner, as `ONBOX/d3dprobe_paced.py` did.
- **`--device rgb`** creates the same scenes on `IID_IDirect3DRGBDevice`, on a system-memory target. It needs no 3D
  hardware, never switches, and refuses `--full`.
- Z format: 16-bit at 16 bpp. At 32 bpp it is 32-bit with a 24-bit depth mask (D24X8). The HAL lists a 32-bit Z
  (D24X8, D24S8) only with `Diag\D3D32` (`vcr_rtfmt.h`). Without D3D32 a 32 bpp run reports
  `"device":"refused 32 bpp (Diag\\D3D32 off)"` and stops cleanly.

### 3.3 Session model

- **One DirectDraw object and one cooperative level per run (family).**
  - `dx7`: `DirectDrawCreateEx` → `IDirectDraw7` → `IDirect3D7`.
  - `legacy`: `DirectDrawCreate` → `IDirectDraw`, queried for `IDirectDraw2`/`IDirectDraw4`, then `IDirect3D`,
    `IDirect3D2` and `IDirect3D3` from it.
  - The render targets are created once, through `IDirectDraw4` in `legacy` and queried down to
    `IDirectDrawSurface` where Device1/2 need it.
- **A fresh device per test.**
  - Each test creates its device on the shared target and textures of the interface its scene uses. It releases
    them all before the next test.
  - Interfaces per test: `CreateDevice(IID_IDirect3DHALDevice)` for 7, 3 and 2; for 1, a QueryInterface of the
    back-buffer surface for the HAL device GUID (the DX3 route).
  - Each test therefore owns exactly one HAL context, or the number its catalogue entry declares (`d7_retarget`:
    1 or 2). Tests cannot inherit each other's state, and the runner can attribute the ring's per-context counters
    to the test.
  - Creating a device switches no mode in DX3-7: the application owns the mode. So a refused ContextCreate costs no
    CRT re-sync here, unlike D3D8's two switches (G11).
- **Scene conventions, d3dprobe's:**
  - readback window 256x256 at the top left;
  - the quad covers [32, 224);
  - TL vertices with z = 0.5, rhw = 1, specular 0xff000000 (fog factor 255, so the HAL's vertex-fog carrier stays
    neutral);
  - clear black unless stated;
  - dither off, Z off, CULLNONE and GOURAUD unless stated.
- **Readback.**
  - `Lock(DDLOCK_READONLY | DDLOCK_WAIT)` on the target after `EndScene`. Our `Dd_Lock` drains the engine first
    (`vcrdd_ddraw.c` `VcrDd2dSync`), so the pixels are final.
  - The pixels are expanded as d3dprobe's `expand()` does (`d3dprobe.c:273-289`).
  - In `--full` mode the probe flips after the readback, as d3dprobe presents, so a person at the screen sees
    progress.
- **Clears.**
  - `dx7`: `IDirect3DDevice7::Clear`.
  - `legacy`: `IDirect3DViewport3::Clear2` for Device3 tests, which reaches the HAL's clear (Clear2, or a DP2
    `CLEAR` record). For Device1/2:
    `IDirectDrawSurface::Blt(DDBLT_COLORFILL)` (the 2D engine), the way DX5 titles clear. A Z clear for a
    Device1/2 test goes through a Device3 viewport on the same target, because `DDBLT_DEPTHFILL` is refused by our
    HAL (G61) and would run in the HEL.
- **RESULT.** The last log line is `RESULT {json}`, as in every lab. Per check it carries:
  `{"test", "iface", "ctx", "at", "x", "y", "got", "want", "old", "old_kind", "gap", "tol", "verdict"}`.
  For an HRESULT check `got`/`want` are HRESULTs.
  - Per test: `{"test", "iface", "contexts_expected", "t0", "t1"}` (`GetTickCount` at start and end, for
    attribution).
  - The totals: `pass`, `old`, `fail`, `skipped`, plus `pid`, `device`, `target`, `fmt`, `z`, `offscreen16` and
    `focus_lost`.
  - The JSON buffer is 64 KB; d3dprobe's is 16 KB (`d3dprobe.c:138`).

### 3.4 Safety rules, carried over and added

- `SetErrorMode(SEM_FAILCRITICALERRORS | SEM_NOGPFAULTERRORBOX)` (`d3dprobe.c:1265`). A crash dies at once instead
  of holding a fullscreen mode behind a Watson box.
- Every step is flushed to the log before the next, so a hang leaves the step it hung in.
- **Every mode change goes through `vcr_pace.h`:**
  - `IDirectDraw7_SetDisplayMode`, `IDirectDraw2_SetDisplayMode` and `IDirectDraw4_SetDisplayMode`;
  - `..._RestoreDisplayMode`;
  - the release of the exclusive object.

  The probe follows ddlab's `restore_mode()` / `restore_mode2()` pattern (`ddlab.c:201-210, 359-370`): a switch the
  gate refuses is not made, and the mode is left for the exit hold. `WM_ACTIVATEAPP` focus loss is handled as in
  d3dprobe (`d3dprobe.c:103`, `pump()` after it).
- **The canary stop.** Each family starts with a clear and an untextured triangle (`d7_clear`/`d7_flat`; `d6_tex`
  and `exec_exit` lead the legacy groups). The stop condition: the clear passes and **no** triangle pixel differs
  from the clear colour. The run then ends with `"suspect":"no triangle reached the target - stale Glide command
  FIFO (G01) or a silent engine give-up (G02)"`. That is the 11-12 signature: "Clears still work and every
  triangle vanishes" (`RPT/hal.md` §0 item 1). The run does not go on to record 30 unrelated failures.
- **Ordering inside a family: proven paths first, first-time-on-silicon paths last.** The first-time paths are DX7
  `Load`, managed textures, SetRenderTarget, the execute buffer's lines and points, and offscreen 16 bpp on a 32 bpp
  desktop. If one of them stalls the engine, the log names it and everything before it has its verdict.
- The probe writes nothing but `C:\vcr\d3d7probe\*` (exe and logs): no registry, no Diag, no driver file.

### 3.5 `d3d7probe_ref.h`: the pure part

The header is integer-only, `<stdint.h>` only, and host-compilable.

- **Scene constants:** `D7_BB` 256, `D7_Q0` 32, `D7_Q1` 224, and `d7_tpx(t, size)` (= d3dprobe's `tpx`).
- **Reference functions.** Each takes 8-bit channel values and returns 0x00RRGGBB:
  - `d7_ref_blend_srcalpha(src, a, dst)`;
  - `d7_ref_legacy_blend(mode, tex_argb, tex_has_alpha, diffuse_argb, dst)`, the DDK formula with the
    implementations' choices for DECAL/ADD alpha (`DSN/G08.md` §3.1);
  - `d7_ref_old_hal_blend(...)`, today's HAL: stage-0 defaults MODULATE with texture alpha (`vcrdd_d3d.c:1138-1143`);
  - `d7_ref_bilinear_2x2(x)`, which gives 255 * clamp(2u - 0.5, 0, 1) with u = (x + 0.5 - 64)/128 (`DSN/G08.md`
    §6.2);
  - `d7_ref_clamp_wrap(x, clamp)`;
  - `d7_ref_565_expand(v)`: MSB replication, so 0xF81F → 0xFF00FF and 0xF81E → 0xFF00F7 (`DSN/G09.md` §4).
- **`d7_verdict(got, want, old, old_kind, tol)`** returns `D7_OK`, `D7_OLD` or `D7_BAD`. `old_kind` is one of:
  - `NONE`: no gap; only `want` passes;
  - `PINNED`: today's value is known; reading it is `OLD`;
  - `EITHER`: the runtime may already do the work, so `want` or `old` are both accepted until a measurement pins it.

  When `old` equals `want` within the tolerance, the verdict is `OK`, never `OLD`.
- **The execute-buffer encoder.** It writes into a caller's buffer, little-endian, in the DX5 layout:
  - `D3DINSTRUCTION` = {bOpcode, bSize, wCount}, 4 bytes;
  - `D3DPROCESSVERTICES` = {dwFlags, wStart, wDest, dwCount, dwReserved}, 16 bytes;
  - `D3DSTATE`, 8 bytes;
  - `D3DTRIANGLE` = {v1, v2, v3, wFlags}, 8 bytes;
  - `D3DLINE`, 4 bytes, and `D3DPOINT`, 4 bytes;
  - plus an `OP_NOP` (a `D3DOP_TRIANGLE` with `wCount` 0, as `d3dmacs.h` did) before any triangle data that would
    not start on an 8-byte boundary.

  Functions: `d7_eb_begin`, `d7_eb_process_copy`, `d7_eb_state`, `d7_eb_tris`, `d7_eb_line`, `d7_eb_point` and
  `d7_eb_exit`. Each returns 0 when the buffer is too small, never a partial record.
- **The catalogue:** `static const d7_test_t d7_tests[]` = {name, family, iface, contexts_expected, gap, flags}.
  Checks are generated by each test's code from the reference functions.

### 3.6 Expectations: `want`, `old`, verdict

- Each check states:
  - **`want`**: the specification value, from the analytic reference;
  - **`old`**: what today's HAL draws, for a check in a known gap (`gap` = "G08", "G09", "G16", ...);
  - **`old_kind`**.
- The runner chooses what each check must read:
  - **`--expect spec`**: every check must read `want`. For the RGB device and for the in-box 3dfx driver on
    86Box. This validates the goldens.
  - **`--expect old`**: every gap check must read `old`. This proves each test detects its defect today.
  - **`--expect auto`** (default on vcr-kmd):
    - a gap whose fix is armed on the box must read `want`;
    - an unarmed gap must read `old` where `PINNED` (either is accepted where `EITHER`).

    So a fix that silently stops working fails, and so does behaviour that changes without its switch. That is
    the default-off rule enforced on silicon.
- **Which fixes are armed** comes from `vcrctl info`'s `"flags"` (`vcrctl.c:190-197`), read in the pre-flight
  before anything runs.
  - The flag-to-gap map lives in `d3d7probe_run.py` (`ARMED_BY_FLAG`). At G75 it is empty and every gap is listed
    in `NOT_SWITCHABLE_YET`.
  - Each fix's landing commit moves its gap into the map, with its own evidence.
  - Section 6 pins that every gap tag in the catalogue is in exactly one of the two.
  - Integration note: G08 proposes `VCR_INFO_F_D3DLEGACY` 0x8000 (`DSN/G08.md` §4.3), and G09 proposes 0x8000/0x10000
    (`DSN/G09.md` §5.2). The integrator must give them distinct bits before either lands.
- **`EITHER` becomes `PINNED`** after the first measured runs: on the 86Box bed with vcr-kmd, then `.124`. A commit
  with that evidence changes the catalogue.

### 3.7 The runner, `d3d7probe_run.py`

1. **Refusals before any connection.**
   - `--device rgb --full`;
   - `caps` with `--full`;
   - `--res` without `--full`;
   - an unknown family or test;
   - `--accept-stale-fifo` without `--full` or `--offscreen` named.

   Each answers rc 2 with a RESULT-shaped line, as `d3dprobe_run.refused` does.
2. **Read-only pre-flight.** No D3D is running at this point, so escapes are allowed:
   - PROCLIST: no `d3d7probe.exe` already running (the `spare` rule of `d3dprobe_run.py`).
   - `vcrctl info`:
     - `flags` gives the armed fixes;
     - `log_next_seq` gives the ring's start for this run;
     - `exclusive_pid` must be 0: no Glide owner. A `null` means the display driver did not answer, and is a
       refusal, never "no owner" (vcrctl's own rule, `vcrctl.c:217-231`);
     - the EDID, for the `--full` gate.
   - **G01's condition.** `vcrctl reg` of `cmdFifo0.baseSize` (0x80024, as the 11-12 session read it). If enable
     bit 8 is set and there is no owner, the run is refused with a banner and the remedy: one paced
     `vcrctl modeseq`, or a reboot (`ONBOX/README.md` runs 7-10). `--accept-stale-fifo` exists for G01's own A/B.
3. **`--full` only:** `ms.fullscreen_gate` against the EDID at the highest listed refresh, and
   `ms.execw_budget(2, timeout)`.
4. **Run.** Upload `out/d3d7probe.exe` to `C:\vcr\d3d7probe\`. Then
   `EXECW <budget> cmd /c start "d3d7probe" /wait ... --pace 5000 --log C:\vcr\d3d7probe\<family>.log`.
5. **Read the log** with `DOWNLOAD`, never `type` through EXEC. The RESULT is the last `RESULT` line.
6. **Post-flight, only after the probe has exited.**
   - `vcrctl log <log_next_seq>`: the entries of this run (`vcrlog.parse_tsv`). Each entry carries a `pid`.
   - Keep the probe's pid, which the probe logs at start.
   - Attribute 513/1 (ContextCreate) and 513/2 (`context N gone: ... DrawPrimitives2, ... triangles, ... clears,
     ... unparsed, ... texture flushes`, `vcrdd_d3d.c:1210-1215`) to tests:
     - in order, cross-checked against the tests' `t0`/`t1` tick windows;
     - a count mismatch makes every HAL assertion of that test `unattributed`. It is reported, never passed.
   - A 513/2 message cut at the ring's 95 characters (`vcr_log.h:32`) is `unknown`, **never 0**.
   - A first returned sequence above the start means `"ring_wrapped":true`, and the HAL-side checks are skipped
     with that reason.
7. **HAL-side assertions** (section 4.5):
   - per test: triangles, clears, unparsed, texture flushes;
   - per run: no 513/5 (opcode unparsed), 513/6 (stream ends inside a command) or 513/9 (handle table full);
   - no "2D engine never went idle ... acceleration off".
8. **Exit codes:**

   | rc | meaning |
   |---|---|
   | 0 | every check as `--expect` requires and every HAL-side assertion holds |
   | 1 | a `bad`; a gap read against its expectation; a named test skipped (the `named_skips` rule); a failed HAL assertion; `error`; `focus_lost` |
   | 2 | refused before running |
   | 3 | the canary stopped the run (suspected G01/G02) |
9. **Cleanup of an uncivil end** (timeout, no RESULT): `ms.reap` (PROCLIST, pace-kill by PID, confirm it is gone,
   the pace stamp), as `d3dprobe_run.py` does.
10. **`--save DIR`** writes the log, the RESULT, the ring slice and the pre-flight to the evidence directory, in the
    repo tree, never the scratchpad.

## 5. Gating

- **No driver change, no Diag switch, no reboot, no deploy.** The HAL's code, caps and register traffic stay
  byte-for-byte as they are. The default 16 bpp path, D3D32, BigTex, SLI, the flip and the Glide hand-over are
  untouched.
- **Safe to land default-on.** It is a lab program run on demand, like d3dprobe, and is part of no boot path.
- **Running it on `.124`:**
  - **Offscreen by default:** no mode switch at all. `--full` makes two switches, paced at 5 s, behind the EDID
    gate.
  - **Not after an unclean Glide/OpenGL close.** The pre-flight refuses while `cmdFifo0` is enabled with no owner,
    until G01 lands.
  - **No `vcrctl`/ExtEscape during a run.** Pre- and post-flight only.
  - **The first run of each family on `.124` is supervised.** Several paths run on silicon for the first time
    (section 8). Later runs need nobody at the box.
  - **No game running.** Vsync stays on (the default), and nothing touches AA or the clock.
- **The fixes this probe verifies keep their own gating** (default-off Diag bits). `--expect auto` checks both
  states, armed or not, against the same catalogue.

## 10. Open questions

1. **Does d3dim strip every runtime-handled execute-buffer op before DP2?** These are `PROCESSVERTICES`,
   `MATRIX*`, `STATETRANSFORM`, `STATELIGHT`, `TEXTURELOAD`, `BRANCHFORWARD` and `SETSTATUS`.
   - Today's evidence is MotS's 0 unparsed (`RPT/runtime.md` §6.1), which covers only what MotS uses.
   - An explicit-only `exec_ops` (a stream with each op, `unparsed` read from the ring) would settle it.
   - It is kept out of default lists because a parse-unknown failure there is the JK crash class.
2. **Is d3dim's +0xf50 the interface version?** If so, `IDirect3DDevice2/3` filter redundant render states (F2).
   `IDirect3DDevice` (v1) has no `SetRenderState` method; its states arrive only in execute buffers.
   `d6_rs_redundant` with G08 armed answers it.
3. **Which d3dim700 device class does vcrdd get?** It is the class that decides whether `SetRenderTarget`
   re-creates the context and re-sends retired states (F3). `d7_retarget`'s context count answers it.
4. **Do dxg and our HAL accept a 16 bpp 3D offscreen surface on the 32 bpp desktop?** `offscreen16` in the first
   run answers it. If not, the 16 bpp lane needs `--full` (2 switches per run).
5. **Do the RGB rasterizer and the in-box 3dfx driver agree with the analytic values everywhere?** Expected
   exceptions are bilinear precision, colour-key-after-filter in a 3dfx HAL (`VH5/D6DP2.C:6818-6822`) and
   DECAL/ADD alpha (`DSN/G08.md` Q5). Each exception is recorded per reference, never folded into `want`.
6. **Does `d3dim`'s first ContextCreate site carry the interface version?** That is `[device+4] - 1` (F4). G08's
   `lgc_hctx_in`, read with the probe's per-test labels, answers it.
7. **Does the 1024-entry ring hold one family run at LogLevel 3?** `--save` records `ring_wrapped`. If it wraps,
   run families at LogLevel 2 or split `--tests`.
