# G50: two pixels per clock (2PPC), its band height and the column band, for the vcr-kmd Direct3D HAL

**The gap.** Nothing in the HAL writes `combineMode`, `renderMode[24:22]` or `fbzColorPath[31:30]`. As a
result, Direct3D fills at about one textured pixel per clock per chip. The VSA-100 does two for
single-textured and untextured triangles.

**Verdict.** The gap is real and fixable. The hardware supports 2PPC, and our own h5 Glide already uses it
on `.124`'s chip 0 at 1.98 px/clk (section 1.5).

| | |
|---|---|
| Priority | **P2**: performance with a measurable gain. It stops no title from running and causes no visible defect |
| Effort | **M** |
| Gating | A new boot-read switch, `Diag\D3D2ppc`, **default OFF**. With the switch off, the register traffic is the proven traffic, byte for byte (pinned by tests). One supervised armed boot proves the switch. After that, value `0x221` (16 bpp only) may become the default. 32 bpp comes on only after its own measurement |

Design written 2026-11-12. This was read-only work: no fleet box was contacted, and nothing was built or
deployed.

## 0. The design in brief

**The switch.** A new boot-read switch, `Diag\D3D2ppc`. The recommended armed value is `0x221`, which
matches 3dfx's own D3D defaults: 2PPC for 16 bpp targets, 4-line TMU bands, iterator columns of 32.

**What the HAL does when armed.** The HAL owns chip 0's `combineMode`, and a per-PDEV tracker records
whether the chip is in 2PPC (UNKNOWN, OFF or ON).

- **Which flushes run 2PPC.** A state flush runs 2PPC when at most one texture unit is in use (one stage,
  or no texture) on a 16 bpp target.
  - It does the same on a 32 bpp target only with bit `0x2`. The spec advises against 2PPC at 32 bpp
    (SPEC L6238), while both 3dfx stacks shipped it on.
  - Above 1600x1200 it stays off unless bit `0x8` is set; that is where 3dfx's own Glide table turned it
    off.
- **Write order in each flush.** Before any other 3D register:
  - leaving 2PPC (ON, or UNKNOWN, going to 1PPC): 12 `nopCMD` addressed to the TMUs only (chip field
    `0x6`), then `combineMode` = 0. This is the hardware-bug rule, SPEC L2840.
  - entering 2PPC: one broadcast `combineMode` write with bit 29 set.
  - after a foreign owner (UNKNOWN): the TMUs' `chromaRange` is first cleared, so that the write does not
    re-arm a stale texture chroma substitution.
- **TMU state.** In 2PPC the TMU block writes **the same single-texture state to TMU0 and then TMU1**, as
  3dfx's HAL does. An untextured flush writes a 1x1 idle state to both TMUs.
- **Band and column band.** `renderMode` carries the band height on targets whose depth runs 2PPC.
  `fbzColorPath` carries the column band.

**What does not change.** No caps, no passes, no vertex traffic.

**Verification:**

- `d3dprobe render --tests ppcband` is an analytic test. It checks every row of eight 32-pixel strips that
  walk through every 1PPC/2PPC transition, inside one DP2 call and across a Present.
- `ppcexact` checks the armed frame bit for bit against the switch-off boot's frame.
- `d3dprobe perf --mode fill` measures Mpix/s.
- A native test models the chip's TMU write mirroring. It catches the wrong write orders, including the
  "stale 2PPC green world" that `.143`'s vintage ICD once had (FIND:11628-11636).
- On `.124`:
  - fill A/B at 640x480, 1024x768, 1280x960 and 1280x1024 at 16 bpp (32 bpp in its own boot);
  - Mysteries of the Sith in game at 1280x960x16 (single texture, DX5): no band stripes, and the flip
    rate;
  - the UT2004 botmatch at 1280x960x16.

**Expected gain (inferred).** Up to 1.5-2x fill for single-textured and untextured triangles at 16 bpp.
None for two-stage triangles. Little or none at 32 bpp. In-game, the gain shows only where a title is
fill-bound: high resolution, low geometry, single texture (JK, MotS, Shogo, Thief Gold/SS2 once at
resolution). It does not show yet in UE2, which is bound by the transport (UT2003: 116.7 of a 123 ms
frame inside DrawPrimitive, `ONBOX/session_log.md`, 10:23 entry). G47/G48/G49 and G51 are the larger
levers there.

## 1. Facts this design rests on

### 1.1 The registers

| field | where | values | source |
|---|---|---|---|
| 2PPC enable | `combineMode[29]` (0x208), in the FBI and in each TMU (chip field) | 1 = two pixels per clock | SPEC L2819 (bit table), L2838; `GL5/../incsrc/h3defs.h` `SST_CM_ENABLE_TWO_PIXELS_PER_CLOCK` BIT(29) |
| `combineMode` access | **write-only**, not a sync register, FBI+TREX* | a read returns undefined data | SPEC L2344 (`W`, `No / Yes`), L2223 ("Reading from a register which is 'write only' returns undefined data") |
| band height | `renderMode[24:22]` (0x1e0, R/W, sync) | log2 of the scanlines each TMU renders in 2PPC | SPEC L3300, L3316; `h3defs.h` `SST_RM_TWO_PIXELS_PER_CLOCK_BAND_SELECTION_SHIFT` 22 |
| column band | `fbzColorPath[31:30]` (0x104, R/W, FBI+TREX%) | 0 = column of 8 (legacy), 1 = 16, 2 = 32, 3 = 4. It applies at 1 ppc too | SPEC L2758, L2800, L6250; `h3defs.h` `SST_TRIANGLE_ITERATOR_COLUMN_BAND_CONTROL_SHIFT` 30 |
| chip field | address bits [13:10] of a 3D register | `0000` = FBI + every TREX; `0110` = TREX0 + TREX1; `0010` = TREX0; `0100` = TREX1 | SPEC L2203-2221; `KMD/include/vcr_3dregs.h:9-18` |
| TMU 0 setup parameters | `sWtmu0`, `sS/W0`, `sT/W0` | reach **TREX0 & TREX1**; the TMU1-only ones are `sWtmu1`..`sT/Wtmu1` | SPEC L2367-2372 |
| TMU chroma substitution | TMU `chromaRange` (0x138 at a TMU chip field) | **armed when `chromaRange[30:29]` = 3 and `combineMode[30]` = 0** | SPEC L2825, L3534 |

### 1.2 The hardware rules (SPEC §8.21, §21.6)

1. **Only one texture.** 2PPC "is only allowed to be enabled when a single texture is being applied per
   triangle ... must be disabled when dual-texturing is being utilized" (L2838, L6233).
2. **TMU writes are mirrored.** With 2PPC on (and `miscInit1[18]` = 0), "any write to either TMU unit will
   be received by both ... regardless of the chip field value" (L2838, L6236). Our miniport never sets
   bit 18 (only CMDSTREAM_RESET, CLUT_INVERT and POWERDOWN_DAC: `KMD/miniport/vcrmp_hw.c:189-195, 574`).
3. **TMU state must be identical.** "Each texture unit is used to generate pixels in scanline bands ...
   it is required that each TMU's state be identical (and each setup for single texture-per-pixel
   rendering operation)" (L6237).
4. **The exit is a hardware bug workaround.**
   - Leaving 2PPC needs "at least 12 NOP commands with the chip field set to select both TMUs prior to
     the write to combineMode register clearing bit(29)".
   - The NOPs must not select the FBI: chipField `0x6`. Selecting the FBI flushes the whole pixel
     pipeline (L2840, L6235).
   - Entering 2PPC needs no NOPs (L2840).
5. **Performance warning.** 2PPC helps only "when extra memory bandwidth is available". It should "only be
   enabled for 15/16 bpp ... not ... 32bpp (except possibly for some very low resolutions)". It may need
   disabling "for very high resolutions or high refresh rates". The band height and the column band "will
   need" tuning "once actual silicon is available" (L6238-6239, L6250).

### 1.3 3dfx's own D3D HAL (NT tree; the Win9x tree agrees)

- **On by default.**
  - `TwoPpc = SST_CM_ENABLE_TWO_PIXELS_PER_CLOCK` (`VH5/D3INIT.C:1046-1061`);
  - band log2 = 2 (`:1063-1082`);
  - column band = 2, "column-of-32" (`:955-963`);
  - the change log: "Modified Column Band Control to 2, and 2PPC Band Height to 2. This bought us
    6 MTexels/s in 3DMark 2000's fill rate test Single Textured" (`:66-68`).
- **At every depth, in both trees.**
  - NT: `_FF(ModeUses2PixPerClkRender)` is set unconditionally on Napalm (`VH5/DDFXNT.C:790-791`).
  - Win9x: the mode flag `REND2PIX_PER_CLK` is set for `dwBPP <= 16 || dwBPP == 32`
    (`DD16/MODE.C:1602-1606`, read at `DD16/H3.C:3407-3409`).
  - So the shipped drivers did **not** follow the spec's 16-bpp-only advice. The comment that does
    follow it (`VH5/D6MT.C:4411`, `:4453`) is not what the code does.
- **When it is used:**
  - untextured (`numStages == 0`, `VH5/D6MT.C:4405-4415`) and one stage (`:4450-4456`): bit 29 in all
    three combineModes;
  - **off** for two stages (`:4888-4895`) and for trilinear (`:5671-5687`: "We can't do trilinear and 2ppc
    so disable 2ppc").
  - In 2PPC the single-stage texture goes to `HOME_BOTH_2PIX_PER_CLOCK`, "textures into both TMUs
    independently (tmu1 does not pass texture to tmu0)" (`:5672-5677`; tables `:5453-5490`).
- **The exit** (`VH5/D6DP2.C:6402-6452`, again at `:7189-7224`):
  1. 12 `nopCMD` to chip field `0x6`, "Send to TMU0 and TMU1 only". They go out when the tracked state
     `NapalmIsIn2ppc` was on and the new state is off, **or when the context changed**: in that case the
     state is unknown.
  2. Then "we need to write combineMode before all other 3D regs" (FBI, TMU0, TMU1).
- **Band and column** are written into `renderMode`/`fbzColorPath` at every buffer change, whether 2PPC is
  on or not (`VH5/D6DP2.C:6343-6355`).
- **TMU state is written TMU0 then TMU1**, each with its own chip field, at every texture flush. In 2PPC
  both get the same values (`VH5/D6DP2.C:6647-6766`).

### 1.4 Our h5 Glide (GL5), which runs 2PPC on `.124` today

- **Forced on.** `FX_GLIDE_2PPC` defaults to 1, "always enabled" (`gpci.c:1874-1876`). That overrides the
  original table in `gsst.c:2040-2128`, which:
  - enabled 2PPC at 15/16 bpp except 1600x1200 and above;
  - at 32 bpp, only at 1600x1024.
- **Band and column.** Band = `FX_GLIDE_2PPC_BAND` 2 (`gpci.c:1877`, written at `gsst.c:4182-4183`). Column
  width 32 (`gpci.c:1801`; bits at `gsst.c:3925-3966`).
- **When it is used.** When TMU1 is not needed by a downstream unit, so untextured draws too (the
  `TMU0:r -> TMU1:r` branch, `distate.c:1720-1750`). It is turned off whenever a TMU is needed downstream
  (`distate.c:1568-1580`) or a palettized texture is bound (`:1532`, `:1568`).
- **Clone, then enable** (`distate.c:1734-1749`):
  - TMU0's real register state is copied into TMU1 and written;
  - the W/S/T setup parameters of the unused TMU are disabled, "otherwise bad things happen because when
    2PPC mode is enabled, any writes that go to one TMU will get sent to both" (`:1836-1847`);
  - then `_grTex2ppc(TRUE)` (`:1848`).
- **`_grTex2ppc`** (`gtex.c:986-1093`):
  - on disable, 12 `nopCMD` to `eChipTMU0 | eChipTMU1`;
  - then `combineMode` **broadcast**, then TMU0, then TMU1.
- **Every open leaves 2PPC by the book.** `assertDefaultState` sets the shadow to 2PPC and calls
  `_grTex2ppc(FXFALSE)` (`gsst.c:914-917`). A D3D session that leaves 2PPC on therefore cannot hurt the
  next Glide session.

### 1.5 Silicon evidence

- **One chip, our Glide, 2PPC on.** Flat fill at 1024x768x16 (untextured, no depth) runs at
  **330.2 Mpix/s**, and blended at 315.8 (`EV/glidelab/vcrkmd-paced-2.jsonl:1-2`; glidelab's fill is flat
  colour, no Z, no texture: `KMD/tools/glidelab.c:8-12, 672-711`). At the stock 166.8 MHz
  (`KMD/include/vcr_clock.h:9`) that is **1.98 px/clk**. This is direct evidence that 2PPC works on this
  board's chip 0 under our kernel driver. It is stronger than the 4-chip arithmetic in the gap text
  (1124.6 Mpix/s = 281 per chip, `:4-8`).
- **D3D today.** `d3dprobe perf` (640x480x16, novsync) runs at 151 fps (`EV/silicon/vcrkmd-v5-7.jsonl:14`),
  which fits ~1 textured px/clk (the perf report's model: 6.9 ms against 3.9 ms at 2 px/clk).
- **The live register values** (`ONBOX/regs/regs_after_windowed_1009.txt`):
  - `renderMode` 0x001e0002 (band field 0);
  - `fbzColorPath` 0x0c002401 (column field 0);
  - `combineMode` "0". That last value is **not evidence**: the register is write-only (1.1).
- **A stuck 2PPC was not present on 11-12.** A chip left in 2PPC mirrors every TMU write, so a two-stage
  draw gets the same state in both TMUs. On `.143`'s vintage ICD that produced a green CS world
  (FIND:11628-11636). On 11-12, `tex2mod` and `tex2add` passed in the 40/40 runs at 10:12 and 10:39
  (`ONBOX/session_log.md`). The UT2004 run between them therefore did not run under a stuck 2PPC (inferred
  from the mirroring rule), and **G06's block noise is not a 2PPC residue**.

## 2. Design

### 2.1 The switch: `Diag\D3D2ppc` (REG_DWORD, absent = 0 = off, read at boot)

The value is made of fields. In each field, 0 means today's behaviour.

| bits | name | effect when set (VSA-100 only) |
|---|---|---|
| `0x001` | EN16 | 2PPC for **16 bpp** targets (and 15 bpp, once G93 offers 1555 targets) |
| `0x002` | EN32 | 2PPC for **32 bpp** targets too. The spec advises against it (L6238); both 3dfx stacks did it. Measured in its own boot (section 6.3) |
| `0x008` | NOCEIL | 2PPC also when the target has 1600x1200 pixels or more. Glide's original table turned it off at 1600x1200 at 16 bpp (`GL5/gsst.c:2063-2064`). `.124`'s titles run at 1280x960/1280x1024 |
| `0x070` | BAND [6:4] | written to `renderMode[24:22]` on targets whose depth has 2PPC enabled: log2 of the scanlines per TMU band (0 = 1 line ... 7) |
| `0x300` | COL [9:8] | written to `fbzColorPath[31:30]` on every VSA-100 target: 0 = 8 wide (today), 1 = 16, 2 = 32, 3 = 4 |

The mask of known bits is `0x37b`; any other bit is ignored, with a WARN.

**Recommended armed value: `0x221`** (EN16, band 2 = 4 lines, column 2 = 32 wide). These are 3dfx's D3D
defaults (1.3) and our Glide's (1.4).

**Why fields rather than the perf report's "1 = 2PPC, 2 = band, 4 = column band":**

- the band and the column band are multi-valued tuning knobs, and the spec says games may want different
  values (L6239, L6250);
- 32 bpp must be separable, because the spec and the bandwidth arithmetic (section 7) say it may lose.

**Why it is read at boot** (like `D3D32` and `D3DBigTex`, `KMD/miniport/vcrmp.c:238-244`):

- Within one boot the value is constant, so a PDEV never inherits a chip that an earlier armed PDEV left in
  2PPC while the HAL is no longer watching `combineMode`.
- It also matches the project rule of one Diag change per clean boot.

No caps depend on it.

**Plumbing:**

- **Miniport.**
  - `KMD/miniport/vcrmp.h:153` area: `ULONG d3d2ppc;`.
  - `vcrmp.c:244` area: `x->d3d2ppc = VcrDiagGet(L"D3D2ppc", 0);`.
  - In the info fill (`vcrmp.c:443-466` area): `v->d3d2ppc = x->backend == VCR_HW_VOODOO ? x->d3d2ppc : 0;`.
- **`KMD/include/vcr_ioctl.h`.**
  - Append `vcr_u32 d3d2ppc;` to `vcr_info` after `mon_src` (`:107`), or after G05's `d3dfeat` if that
    lands first. The struct only grows at its end.
  - `IOCTL_VCR_INFO` already copies `min(OutputBufferLength, sizeof v)` (`vcrmp.c:789-799`).
  - It is a field, not flag bits: the designs G01-G10 already contend for `vcr_info.flags` bits 0x8000+.
- **Display.**
  - `KMD/display/vcrdd_2d.c` `VcrDd2dInit` (`:430-474`): `memset(&info, 0, sizeof info)` before the IOCTL,
    so that an older miniport's shorter answer reads 0. Then
    `pd->ppc_cfg = vcr_ppc_cfg(pd->napalm, info.d3d2ppc); pd->ppc = VCR_PPC_UNKNOWN;`.
  - When the switch is armed, log one INFO event 513 (`VCR_EV_DD_D3D`) with a new `what` code: "armed
    (Diag\D3D2ppc %x): 2PPC 16 bpp %s, 32 bpp %s, bands of %u lines, columns of %u". The next free codes
    are 24+; G03 and G05 also claim 24/25, so the code is assigned when this lands.
  - `KMD/display/vcrdd.h`: `ULONG ppc_cfg, ppc;` beside `rt32`/`tex_ext` (`:68-75`).
- **Deploy.** A deploy of this item swaps **both** `vcrmp.sys` and `vcrdd.dll`: the miniport is what reads
  the Diag.
- **`KMD/tools/vcrctl.c` `info`.** Print `d3d2ppc` when `v.size` covers it, the same pattern as `mon_src`
  (`vcrctl.c:213`). That is the pre-run check that the box is armed as intended.

### 2.2 Which flushes run 2PPC

`want = vcr_ppc_want(cfg, target.fmt, tmu1_used, width, height)`. It is evaluated in `prepare()` **after**
the coordinate check that may drop the textures (`vcrdd_d3d.c:1339-1356`), so the decision is about what
is actually drawn.

| draw | today | armed `0x221`, 16 bpp | armed `0x221`, 32 bpp | armed `0x223`, 32 bpp |
|---|---|---|---|---|
| untextured (incl. TFACTOR/diffuse only) | 1 ppc | **2 ppc** + idle TMU state | 1 ppc | 2 ppc |
| one texture stage | 1 ppc | **2 ppc** | 1 ppc | 2 ppc |
| two stages (`regs.textured1`) | 1 ppc | 1 ppc | 1 ppc | 1 ppc |
| target with 1600x1200 pixels or more | 1 ppc | 1 ppc (2 with `0x8`) | 1 ppc | 1 ppc (2 with `0x8`) |
| future: single-stage trilinear (G26), a paletted texture (G38) | n/a | must pass `tmu1_used = 1`: 1 ppc | | |
| Banshee/Voodoo3 (the 86Box bed) | 1 ppc | inert: `vcr_ppc_cfg` returns 0 when `!napalm` | | |

**Untextured draws are included**, as in both 3dfx stacks (1.3, 1.4). This keeps "2PPC whenever TMU1 is
idle" a single rule, and spares a scene that alternates textured world and untextured HUD/shadow quads an
exit (12 NOPs and a TMU drain) at each switch.

The TMUs are parked identically on a 1x1 level, which satisfies L6237 to the letter:

- `textureMode = TM_FORMAT(TF_RGB565)`;
- `tLOD = TL_LODMIN(8) | TL_LODMAX(8)` = **0x820**, the value 3dfx's HAL uses for an unused TMU,
  `VH5/D6MT.C:5663-5669`; Glide forces 1x1 the same way, `GL5/distate.c:1596-1601`;
- `tDetail 0`, `texBaseAddr 0`.

3dfx's HAL itself wrote no TMU state for untextured 2PPC. Whether the idle state is needed is open
question 4. It costs 8 writes per untextured flush.

### 2.3 Who owns `combineMode`: the per-PDEV tracker

`pd->ppc` is what the HAL knows of chip 0's `combineMode[29]`:

- `VCR_PPC_UNKNOWN`: someone else may have had the chip; 2PPC may be on;
- `VCR_PPC_OFF`;
- `VCR_PPC_ON`.

The register cannot be read (write-only), so the tracker is the only truth. It is reset to **UNKNOWN**
wherever anything other than this HAL may have written the 3D block, or the engine was reset:

| event | where |
|---|---|
| a new PDEV (mode change, boot) | `VcrDd2dInit`, `KMD/display/vcrdd_2d.c:430-474` |
| Glide takes the chip | `VCR_HWC_HWCSETEXCLUSIVE`, `KMD/display/vcrdd_escape.c:126-132` |
| Glide gives it back, released or refused | `VCR_HWC_HWCRLSEXCLUSIVE`, `vcrdd_escape.c:134-200` (next to `pd->exclusive_pid = 0`) |
| GDI re-asserts or leaves (a mode change, alt-tab, a killed Glide client's owner cleared, device reset) | `DrvAssertMode`, both branches, `KMD/display/vcrdd.c:570-618` |
| the Glide release reset ran | `VcrDdGlideReset3d`, `vcrdd_2d.c:400-428` |
| a write of the transition failed (FIFO give-up) | `VcrDd3dPpc` itself |

**UNKNOWN is treated as "possibly ON".** 3dfx's HAL does the same: it sends the NOPs whenever the context
changed, `VH5/D6DP2.C:7194-7202`. The first flush after any of these events therefore writes `combineMode`
explicitly, with the 12-NOP exit if it wants 1 ppc.

This also clears a 2PPC that a **killed** Glide client left behind. Today that residue mirrors every D3D
TMU write and breaks every two-stage draw: the class of FIND:11628-11636, and part of G03.

### 2.4 The writes, in order

Each state flush (a `prepare()` that writes) on an armed VSA-100:

```
[1] transition (only when pd->ppc differs from want, or is UNKNOWN), BEFORE any other 3D write:
      leaving / unknown -> 1 ppc : 12 x nopCMD @ V3D_TMU0+V3D_TMU1 (chip field 0x6, 0x1920)   SPEC L2840
      unknown only               : TMU chromaRange = 0 @ 0x6 (0x1938)       before the bit-30-clearing write
      always                     : combineMode = want ? 0x20000000 : 0   @ broadcast (0x208)
[2] target   (VcrDd3dTarget)     : renderMode | (EN for this depth ? band << 22 : 0), the rest as today
[3] state    (VcrDd3dState)      : fbzColorPath | col << 30, fbzMode ... sSetupMode, [fog table], [DXT nop]
                                   want ? TMU0 x4 then TMU1 x4, identical single-texture state
                                          (or the 1x1 idle state when untextured)
                                        : TMU0 x4 [+ TMU1 x4]   <- today's code, untouched
```

**Why this order:**

- `combineMode` goes first, as the vendor does ("before all other 3D regs", `VH5/D6DP2.C:6443-6444`).
  Above all, the 2PPC exit must precede the two-stage TMU1 writes. While 2PPC is still on, a TMU1 write
  also lands in TMU0 (L2838), and stage 0's texture would overwrite stage 1's. That is the green-world
  defect.
- Entering needs no NOPs (L2840).
- The broadcast `combineMode` write is Glide's own first write in `_grTex2ppc` (`GL5/gtex.c:1056-1063`). It
  sets all three units in one write. With no extended combine, the FBI and TMU words are identical; G05
  later splits them (2.8).
- **The TMU chromaRange write (UNKNOWN only).**
  - Texture chroma substitution is armed when `chromaRange[30:29]` = 3 and `combineMode[30]` = 0
    (L2825, L3534).
  - A Glide session that used a TMU constant colour (`combineMode[30]` = 1, the constant in TMU
    chromaRange; alpha 0xff gives bits 30:29 = 3) leaves exactly that.
  - Our `combineMode` writes clear bit 30. So the first one after a foreign owner must clear TMU
    chromaRange first. This is the same rule and order the G03 design specifies (`designs/G03.md`, section
    2.1, writes 15-16).
  - One write, at most once per PDEV activation or Glide handoff.
- **TMU state in 2PPC is written TMU0 then TMU1 with identical values.**
  - This is the form 3dfx's HAL writes (`VH5/D6DP2.C:6647-6766`), and the same chip fields the HAL's
    proven two-stage path already uses (`0x800`, `0x1000`).
  - It is correct whether or not the hardware mirrors (`miscInit1[18]`) and whatever order the
    `combineMode` write lands in.
  - A single chip-field-`0x6` write would halve it to 4. That is spec-valid (L2212), but texture registers
    have never been written that way here, so it is left as a later trim.

**Write counts added per flush** (armed):

| transition | added writes |
|---|---|
| no change, 1 ppc | 0 |
| OFF -> ON | 1 (+4 TMU1 clone textured; +8 idle untextured, where today's untextured flush writes no TMU register) |
| ON -> ON | +4 (clone) or +8 (idle) |
| ON -> OFF | 13 |
| UNKNOWN -> ON / OFF | 2 / 14 (once per PDEV activation or Glide handoff) |

Against the ~22 writes plus 2-4 status reads a flush already costs (perf report §1.4, inferred), this is
small. The counters (2.7) measure the real transition rate.

### 2.5 Code

**New `KMD/include/vcr_2ppc.h`.** Win32-free, so the native test compiles exactly what the driver writes.

```c
#include "vcr_3dseq.h"                  /* vcr_regw, VCR_3D_RESET_NOPS, vcr_3d_target_seq */
#define VCR_PPC_EN16      0x001u
#define VCR_PPC_EN32      0x002u
#define VCR_PPC_NOCEIL    0x008u
#define VCR_PPC_BAND(c)   (((c) >> 4) & 7u)
#define VCR_PPC_COL(c)    (((c) >> 8) & 3u)
#define VCR_PPC_KNOWN     0x37bu
#define VCR_PPC_VENDOR    0x221u        /* 3dfx's D3D defaults (D3INIT.C) */
#define VCR_PPC_CEIL_PX   (1600u * 1200u)
#define VCR_CM_2PPC       (1u << 29)    /* h3defs.h SST_CM_ENABLE_TWO_PIXELS_PER_CLOCK */
#define VCR_RM_BAND(b)    ((unsigned)(b) << 22)
#define VCR_CP_COL(c)     ((unsigned)(c) << 30)
#define VCR_PPC_IDLE_TM   TM_FORMAT(TF_RGB565)
#define VCR_PPC_IDLE_TLOD (TL_LODMIN(8) | TL_LODMAX(8))     /* 0x820: one 1x1 level */
#define VCR_PPC_UNKNOWN 0u
#define VCR_PPC_OFF     1u
#define VCR_PPC_ON      2u

static __inline unsigned vcr_ppc_cfg(unsigned napalm, unsigned diag)
{ return napalm ? diag & VCR_PPC_KNOWN : 0u; }
static __inline unsigned vcr_ppc_armed(unsigned cfg)
{ return (cfg & (VCR_PPC_EN16 | VCR_PPC_EN32)) != 0u; }
static __inline unsigned vcr_ppc_depth(unsigned cfg, unsigned fmt)
{ return fmt == VCR_RT_16 ? (cfg & VCR_PPC_EN16) != 0u : fmt == VCR_RT_32 ? (cfg & VCR_PPC_EN32) != 0u : 0u; }
static __inline unsigned vcr_ppc_want(unsigned cfg, unsigned fmt, unsigned tmu1_used, unsigned w, unsigned h)
{ return vcr_ppc_depth(cfg, fmt) && !tmu1_used && ((cfg & VCR_PPC_NOCEIL) || w * h < VCR_PPC_CEIL_PX); }
static __inline unsigned vcr_ppc_rendermode(unsigned rm, unsigned cfg, unsigned fmt)
{ return vcr_ppc_depth(cfg, fmt) ? (rm & ~VCR_RM_BAND(7u)) | VCR_RM_BAND(VCR_PPC_BAND(cfg)) : rm; }
static __inline unsigned vcr_ppc_colpath(unsigned cp, unsigned cfg)
{ return VCR_PPC_COL(cfg) ? (cp & ~VCR_CP_COL(3u)) | VCR_CP_COL(VCR_PPC_COL(cfg)) : cp; }

#define VCR_PPC_SEQ_MAX (VCR_3D_RESET_NOPS + 2)
static __inline unsigned vcr_ppc_seq(unsigned cur, unsigned want, vcr_regw *w)
{
    unsigned n = 0, i;
    if (cur == (want ? VCR_PPC_ON : VCR_PPC_OFF))
        return 0;                                       /* already there */
    if (!want)                                          /* SPEC 8.21: >= 12 NOPs, TMUs only */
        for (i = 0; i < VCR_3D_RESET_NOPS; i++) {
            w[n].off = V3D_TMU0 + V3D_TMU1 + V3D_NOPCMD; w[n++].val = 0;
        }
    if (cur == VCR_PPC_UNKNOWN) {                       /* no stale texture chroma substitution */
        w[n].off = V3D_TMU0 + V3D_TMU1 + V3D_CHROMARANGE; w[n++].val = 0;
    }
    w[n].off = V3D_COMBINEMODE; w[n++].val = want ? VCR_CM_2PPC : 0u;   /* broadcast */
    return n;
}
/* the TMU block of a 2PPC flush: TMU0 then TMU1, the same single-texture (or idle) state */
#define VCR_PPC_TMU_MAX 8
static __inline unsigned vcr_ppc_tmu_seq(unsigned textured, unsigned tm, unsigned tl, unsigned tb,
                                         vcr_regw *w)
{
    static const unsigned unit[2] = { V3D_TMU0, V3D_TMU1 };
    unsigned n = 0, u;
    if (!textured) { tm = VCR_PPC_IDLE_TM; tl = VCR_PPC_IDLE_TLOD; tb = 0; }
    for (u = 0; u < 2; u++) {
        w[n].off = unit[u] + V3D_TEXTUREMODE; w[n++].val = tm;
        w[n].off = unit[u] + V3D_TLOD;        w[n++].val = tl;
        w[n].off = unit[u] + V3D_TDETAIL;     w[n++].val = 0;
        w[n].off = unit[u] + V3D_TEXBASEADDR; w[n++].val = tb;
    }
    return n;
}
/* the target sequence with the band OR-ed into its renderMode write (VSA-100) */
static __inline unsigned vcr_3d_target_seq_ppc(unsigned napalm, unsigned rt32, unsigned cfg,
        unsigned fmt, unsigned rt_off, unsigned rt_pitch, unsigned z_off, unsigned z_pitch,
        unsigned width, unsigned height, vcr_regw *w)
{
    unsigned n = vcr_3d_target_seq(napalm, rt32, fmt, rt_off, rt_pitch, z_off, z_pitch,
                                   width, height, w), i;
    for (i = 0; napalm && i < n; i++)
        if (w[i].off == V3D_RENDERMODE)
            w[i].val = vcr_ppc_rendermode(w[i].val, cfg, fmt);
    return n;
}
```

`KMD/include/vcr_3dregs.h` gains `V3D_CHROMARANGE 0x138`, as G03 adds it too. Comments name the chip
fields used.

**`KMD/display/vcrdd_3d.c`:**

- **New `BOOL VcrDd3dPpc(VCR_PDEV *pd, ULONG want, ULONG *made)`.**
  - It returns TRUE at once, **writing and reading nothing**, when `!vcr_ppc_armed(pd->ppc_cfg)`.
  - Otherwise it writes `vcr_ppc_seq(pd->ppc, want, w)`. It checks room in chunks of at most 8, as Reset3D
    does (`vcrdd_2d.c:418-423`): the FIFO free count is learned, not assumed.
  - On a failed room check: `pd->ppc = VCR_PPC_UNKNOWN`, return FALSE. This is the existing give-up path
    (G02).
  - On success: `pd->ppc = want ? ON : OFF`, `g2d_busy = 1`, and `*made` = 0 (no change), 1 (entered) or
    2 (left).
- **`VcrDd3dTarget` (`:45-70`)** calls `vcr_3d_target_seq_ppc(pd->napalm, pd->rt32, pd->ppc_cfg, ...)`.
  With `ppc_cfg` = 0 it returns exactly `vcr_3d_target_seq`'s writes.

**`KMD/display/vcrdd_d3d.c`:**

  This is unchanged with COL = 0. `color_path` never sets bits 31:30, and `prepare()`'s

- **`ctx_free` (`:1210-1221`):** a second INFO line when the switch is armed (the 95-character ring

**`VcrDd3dTexFlush` (`:253-270`) is mode-independent.**

- Its `texBaseAddr` writes are broadcast, so both TMUs are invalidated, as both TMUs' caches must be in
  2PPC.
- Its TMU0-only write-back `texBaseAddr` is mirrored to TMU1 in 2PPC, with the same value.
- The state flush that follows rewrites both TMUs either way.

### 2.6 Caps, passes, the old path

- **Caps: none change.** 2PPC is invisible to the application. No new capability is claimed and no
  `ValidateTextureStageState` answer changes.
- **Single pass.** Nothing is split or re-drawn.
- **Old path: the switch absent or 0, any Banshee/Voodoo3, the 86Box bed.**
  - `vcr_ppc_cfg` returns 0, `VcrDd3dPpc` returns before any access, and `vcr_3d_target_seq_ppc` equals
    `vcr_3d_target_seq`.
  - `vcr_ppc_colpath(cp, 0) == cp`, `regs.ppc == 0`, so `VcrDd3dState` takes today's branch.

### 2.7 Counters and log lines

These are the per-context numbers that make the effect measurable without a tool attached.

- **Event 513 "armed"**: once per PDEV.
- **Context-gone line**: 2PPC triangles out of all triangles, enters and exits. Enters and exits are the
  real transition rate; the triangle share says which titles can gain (UE2's two-stage world cannot).
- **Optionally**, the first 2PPC flush of a context, once (INFO).

Nothing per draw (G52).

If the G76/P0 (`D3DStats`) counters land, these fold into them.

### 2.8 Interplay with other gaps

| gap | what changes |
|---|---|
| **G03** (the HAL owns its 3D state; D3D baseline) | The two share `combineMode` ownership, the TMU-only NOP form and the chromaRange-before-combineMode rule. Whichever lands first owns the helper. With both armed, the G03 baseline must **not** write its own 12 NOPs + `combineMode = 0` per DP2: it would force an exit at every DP2 call. It sets `pd->ppc = VCR_PPC_UNKNOWN`, or leaves `combineMode` to this tracker. G03's own table already anticipates this: "G50 (2PPC): the NOPs become only when leaving 2PPC" |
| **G05/G12/G13/G14** (extended combine) | `combineMode` words become `ext \| (pd->ppc == ON ? VCR_CM_2PPC : 0)`, written per unit (FBI, TMU0, TMU1). | **G26** (trilinear) | Single-stage trilinear needs both TMUs: pass `tmu1_used = 1`. 3dfx turned 2PPC off for it (`VH5/D6MT.C:5679`) |

| **G47/G53** (CMDFIFO, register shadows) | `vcr_ppc_seq` becomes packet 1 (`PK1CHIP` 12 x `nopCMD` @ `0x6`, as `VH5/D6DP2.C:6424-6430`). The tracker is the shadow; shadows invalidate at the same events as 2.3 |
| **G19** (UE2 at 16 bpp) | Today UE2 benefits because it runs at 16 bpp. Fixed to 32 bpp, it benefits only if bit `0x2` proves out |
| **G59** (16 bpp flips at half rate) | It can mask a 16 bpp fps gain under vsync. Measure fill with novsync, and record flip intervals |
| **G93** (1555 targets) | 15 bpp counts as EN16 |
| **G06** (block noise) | Not a 2PPC residue (1.5). This item neither causes nor fixes it |

## 3. Gating

- **Default OFF, behind `Diag\D3D2ppc`** (boot-read, VSA-100 only). Off is the proven path byte for byte
  (2.6, pinned in section 5).
- **Not safe to land default-on now.** This is new register traffic on the proven 16 bpp lane. It relies on
  a documented hardware-bug workaround (the exit), and the spec itself warns that 2PPC can be slower when
  bandwidth is short. None of that has run under our HAL.
- **Proof.** One supervised clean boot armed with `0x221` (section 6.2): `ppcband` passes, `ppcexact` is
  identical to the off boot, render is 40/40 at 16 and 32 bpp, the fill gain is measured, and the in-game
  frames are free of band stripes.
- **Default flip** (its own commit, with the evidence): the miniport default becomes `0x221`
  (`VcrDiagGet(L"D3D2ppc", 0x221)`), and `D3D2ppc = 0` is the kill switch. The tests flip their
  default-value assertions in the same commit.
- **EN32 (`0x2`) stays off** unless boot C (6.3) shows a gain of at least 10 % at 1024x768x32 and no loss at
  1280x1024x32.
- **NOCEIL (`0x8`) stays off**: no `.124` title runs at or above 1600x1200.

## 4. d3dprobe tests (`KMD/tools/d3dprobe.c`)

All three are explicit-only (`--tests ...` / `--mode`), like `mip` and the BigTex checks. The default
40/40 gate list does not change. Each is valid on any correct driver, which is what lets the
switch-off boot validate it.

### 4.1 `ppcband`: every row, through every transition (the correctness gate)

**What it draws.** Eight vertical strips, 32 px wide x 256 rows, filling the 256x256 readback window
(`BB`, `d3dprobe.c:149`). Each strip is checked at its centre column on **every row 0-255**. Any band
height from 1 to 128 lines therefore shows: a TMU-state mismatch is wrong in every other `2^band` rows.

| kind | set-up | expected at row y |
|---|---|---|
| `A` single | 32x256 R5G6B5 texture, row v = `rowc(v)`, 1:1 (-0.5 offsets, as `test_cells`), point, `SELECTARG1(TEXTURE)` | `rowc(y)`, tolerance 12 |
| `C` single, **a different texture** (a different `texBaseAddr`: catches a TMU1 still on A) | the same with row v = `rowc(255 - v)` | `rowc(255 - y)`, tolerance 12 |
| `TWO` two-stage (1 ppc, needs the exit) | stage 0 = A `MODULATE(TEX, DIFFUSE white)`, stage 1 = 16x16 grey 0x808080 `MODULATE(TEX, CURRENT)`, coordinate sets 0/1, as `tex2mod` | `rowc(y) x (0x84, 0x82, 0x84) / 255`, tolerance 14 (the `tex2mod` constants, `d3dprobe.c:1065`) |
| `U` untextured (2 ppc with the idle TMU state) | gouraud, top `0x000000` to bottom `0xff8040` | linear in `(y + 0.5)/256`, tolerance 24 (as `gouraud`) |

`rowc(v) = (32(v&7)+16, 32((v>>3)&7)+16, 64(v>>6)+32)`. It is exact in 565, unique per row, and
neighbours differ by at least 32 in a channel, so tolerance 12 cannot alias.

**Order.**

- **Frame 1** (one DP2 batch: in-call transitions): `A@0 C@1 TWO@2 U@3 TWO@4 A@5 U@6 C@7`. This covers
  2->2 with a texture change, 2->1, 1->2 untextured, 2(untextured)->1, 1->2 textured, 2->2
  untextured, and untextured->textured.
- **Frame 2** (after Present, so a new DP2 call): `TWO@2 U@3 TWO@4 A@5 U@6 C@7 A@0 C@1`. Its **first draw
  is two-stage while the chip was left in 2PPC by frame 1's last strip**. That tests the cross-call
  tracker, the exact case a per-call or per-context tracker would get wrong.

Dither off (as `main` sets, `d3dprobe.c:1495`). Depth off.

**Pass.** 0 wrong rows in all 8 strips x 256 rows x 2 frames (4,096 checks). The JSON per strip gives the
wrong rows, the first 6 failures with `y`, `y & 15` and got/want, so a band pattern reads at a glance.
Expected to pass with the switch off (validating the test) and armed.

### 4.2 `ppcexact`: armed frame = off frame, bit for bit

**What it draws.** One deterministic frame that uses everything the FBI and TMUs do, at the run's depth,
**dither ON** (`D3DRS_DITHERENABLE TRUE`):

- a bilinear 64x64 checker quad rotated 30 degrees (minified and magnified);
- the 64x64 mip chain of the `mip` test on a perspective quad (rhw varying, `MIPFILTER POINT`);
- table-fogged quads;
- two intersecting z-tested quads (`LESSEQUAL`);
- an alpha-blended gouraud triangle;
- a `tex2mod` quad (1 ppc mid-frame);
- an untextured gouraud triangle;
- at 32 bpp with BigTex, a DXT5 and an A8R8G8B8 quad.

**Output.**

- `"crc"` (CRC32 of the 256x256 readback) and a CRC per 16-row band in the RESULT.
- The raw readback is written to `C:\vcr\d3dprobe\ppcexact_<W>x<H>x<bpp>.raw` (256 KB) for the host.

**Pass (cross-boot).** The armed boot's raw is **identical** to the off boot's at the same mode. The
reasoning: 2PPC and the column band change only which TMU, and in what order, renders a pixel. The
iterators are fixed-point DDAs and the dither matrix is indexed by screen x,y (inferred), so the values
should not change.

**If not identical**, the comparator says how:

- differences confined to rows of alternating `2^band` groups = **fail** (TMU state not identical);
- a uniform ±1 LSB scatter = iterator rounding; open question 2, the analytic `ppcband` is then the gate;
- anything else = fail.

### 4.3 `perf --mode fill`: Mpix/s (the KPI)

The existing `perf` mode (`d3dprobe.c:1497-1530`) is kept for continuity (151 fps). A new
`perf --mode fill [--layers L] [--variants t0,t1,t1z,t1zb,t2] [--frames F]` runs, in **one device**
(one pair of mode switches per resolution, paced), for each variant:

1. 10 warm-up frames;
2. F (150) frames of a target clear plus L (8) full-screen quads, each quad its own diffuse colour;
3. F frames of the clear alone.

Mpix/s = `W*H*L*F / (t_L - t_0)`, so the clear and the flip cancel out.

| variant | set-up | 2PPC? |
|---|---|---|
| `t0` | untextured | yes |
| `t1` | 256x256 R5G6B5 bilinear `MODULATE`, ~1 texel/pixel, wrap | yes |
| `t1z` | t1 + `ZENABLE`, `ZFUNC ALWAYS`, `ZWRITE` (Z read and write, no rejection) | yes |
| `t1zb` | t1z + `SRCALPHA/INVSRCALPHA` | yes |
| `t2` | t1 + a stage-1 `MODULATE` 64x64 | **no**: the control, must not move |

- `--full --novsync` measures the chip.
- A vsync-on run records nothing beyond the refresh cap unless G78/P0 headroom counters exist.
- The RESULT carries `mpix_s` per variant.
- The host adds `px_clk` from the core clock it read with `vcrctl clock` **before** the run (never during
  a D3D run).
- If G78 has landed its `fill` mode first, reuse it.

### 4.4 Harness (`KMD/tools/d3dprobe_run.py`)

- It DOWNLOADs the `ppcexact` raw after a run.
- `--compare-to <ref.raw>` prints JSON: `identical`, `max_delta` per channel, `px_diff`, and differing rows
  split by `(y >> b) & 1` for b = 0..3.
- References and runs are kept under `EV/silicon/d3d2ppc/<boot>/`.
- Pass `--pace 5000` to every fullscreen run: the CRT pacing rule, at least 5 s.

### 4.5 Proving the tests before silicon

On the 86Box Voodoo3 bed (`napalm` = 0, so the switch is inert), run `render --tests ppcband,ppcexact`,
windowed and `--full` at 16 bpp, under vcr-kmd and under XP's in-box Voodoo3 driver:

- `ppcband` must pass on both;
- `ppcexact` must give the same CRC on two runs.

That settles the expected values with no hardware at stake.

### 5.1 Native: new `tests/native/test_vcr_kmd_2ppc.c`

     write.
   - So the 16 bpp `renderMode` stays **0x001e0000** and 32 bpp **0x001e0002**.
   - `vcr_ppc_colpath(0x0c002401, 0)` = **0x0c002401** (the on-box value).
2. **`armed_values_reach_the_fields`**
   - `0x221`: 16 bpp `renderMode` **0x009e0000** (old 0x001e0000: the band "never programmed");
     `fbzColorPath` **0x8c002401** (old 0x0c002401).
   - 32 bpp under `0x221`: `renderMode` stays 0x001e0002; under `0x223` it is 0x009e0002.
   - `0x021` leaves `fbzColorPath` alone.
   - Unknown bits are masked: `0xffffffff` decodes to `0x37b`.
   - `VCR_PPC_VENDOR == 0x221`.
3. **`who_runs_two_pixels_per_clock`**
   - `want(0x221, 16, 0, 1280, 960)` = 1;
   - two stages = 0; 32 bpp = 0 (1 with `0x223`);
   - 1600x1200 = 0 (1 with `0x8`);
   - a refused target (fmt 0) = 0.
4. **`entering_is_one_broadcast_write`**
   - `seq(OFF, 1)` = `{0x208, 0x20000000}`;
   - `seq(ON, 1)` = no writes;
   - `seq(UNKNOWN, 1)` = `{0x1938, 0}, {0x208, 0x20000000}`.
5. **`leaving_sends_twelve_tmu_only_nops_first`**
   - `seq(ON, 0)` = 12 x `{0x1920, 0}`, then `{0x208, 0}`. Every NOP's chip field is `(off >> 10) & 0xf == 6`.
   - It is **not** the Reset3D form, a broadcast `0x120` that also flushes the FBI (L2840). It is **not**
     `combineMode` first.
   - `seq(UNKNOWN, 0)` = 12 NOPs, `{0x1938, 0}`, `{0x208, 0}` (14 writes).
   - `seq(OFF, 0)` = no writes.
6. **`the_2ppc_tmu_block_is_both_tmus_alike`**
   - `vcr_ppc_tmu_seq(1, tm, tl, tb)` = TMU0 (`0xb00`..`0xb0c`), then TMU1 (`0x1300`..`0x130c`), the same
     4 values each.
   - Untextured gives the idle state (`0xa00`, **0x820**, 0, 0) on both.
7. **`a_chip_model_catches_a_mirrored_two_stage_draw`**: the key invariant.
   - **The model.** A model of chip 0 has:
     - FBI and TMU0/TMU1 `combineMode`;
     - TMU register files;
     - TMU chromaRange;
     - a count of TMU-only NOPs since the last other write;
     - the mirroring rule: while bit 29 is set in the TMUs, a TMU-addressed write lands in both (L2838).
   - **What it replays.** The HAL's whole flush (transition, then the TMU block, `vcr_ppc_tmu_seq` or
     today's TMU0/TMU1 writes) for a script that starts **UNKNOWN with the chip actually in 2PPC and a
     stale TMU chromaRange `0x7f000000` + `combineMode[30]`** (a killed Glide), then runs: two-stage ->
     single A -> untextured -> two-stage -> single C -> two-stage.
   - **What it asserts after each flush:**
     - a 2PPC draw has TMU0 == TMU1 == the expected state;
     - a two-stage draw has TMU0 = stage 1 and TMU1 = stage 0;
     - every 1->0 change of bit 29 had at least 12 TMU-only NOPs before it;
     - texture chroma substitution is never armed (`(chromaRange >> 29 & 3) == 3 && !combineMode[30]` is
       false).
   - **Old and buggy orderings it must catch:**
     - (a) the transition after the TMU block: TMU0 overwritten with stage 0's state, the
       FIND:11628-11636 shape;
     - (b) a tracker that treats UNKNOWN as OFF: no exit before the first two-stage draw;
     - (c) single-stage state written to TMU0 only with `miscInit1[18]` = 1: TMU1 stale. Ours passes in
       both mirroring modes;
     - (d) the UNKNOWN write without the chromaRange clear: substitution armed.

## 6. On-box verification (`.124`, supervised, one Diag change per clean boot)

### 6.0 Before each boot

1. Run `bash tests/run_all.sh` green and `tools/check_imports.py` on the built binaries.
2. Swap **vcrmp.sys + vcrdd.dll** (record both md5s).
3. Check activation (`LICSTATUS`), then reboot through `scripts/fleet/safe-reboot.py`. Every boot in this
   plan is a **cold** boot with no Glide session before the D3D runs. That avoids the G01 stale-FIFO trap,
   and is the perf report's correctness gate (§5).
4. Set the Diag with `REGWRITE HKLM SYSTEM\CurrentControlSet\Services\vcrmp\Diag D3D2ppc REG_DWORD <v>`
   (five tokens) and `REGREAD` it back.
5. After the boot, check:
   - the ring shows the "armed (Diag\D3D2ppc ...)" event;
   - `vcrctl info` shows `d3d2ppc`;
   - `vcrctl reg 80024` shows `cmdFifo0.baseSize` = 0;
   - `vcrctl clock` gives the core clock;
   - all of these **before** any D3D program, never during one.
6. Quiesce as in the v56k plan.

## 7. Expected effect (inferred unless measured)

**Bandwidth arithmetic.**

- Peak per chip: a 128-bit SDR bus at 166 MHz, about 2.66 GB/s (inferred from 32 MB per chip in 2Mx32
  parts, PSEXT L182).
- At 16 bpp with Z, about 6 B per pixel. 333 Mpix/s needs ~2.0 GB/s, which fits.
- At 32 bpp with Z, about 12 B per pixel, so 1 ppc already needs ~2.0 GB/s. This is why the spec warns
  about 32 bpp.

| case | 1 ppc today | 2 ppc | basis |
|---|---|---|---|
| untextured, 16 bpp | ~166 Mpix/s | ~330 | Glide flat fill measured 330.2 on chip 0 (1.5) |
| one texture, 16 bpp, no Z | ~150-166 | 260-330 | the same pipe plus a texture cache per TMU |
| one texture + Z, 16 bpp | ~150 | 220-300 | ~2 GB/s against ~2.66 |
| + alpha blend | ~140 | 200-260 | about 8 B/px |
| two stages | ~160 | unchanged | not 2PPC (`t2` control) |
| one texture + Z, 32 bpp (`0x2`) | ~140 | 140-180, or a loss | 12 B/px; spec L6238 |
| `d3dprobe perf` (640x480x16, novsync) | 151 fps | 200-255 fps | perf report §3.2 model |

**Titles**, with vsync on at 85 Hz:

- **Fill-bound, single texture, low geometry, at 16 bpp:** MotS and JK at 1280x960x16, Shogo at
  1280x960x16, and Thief Gold, SS2 and R6 at 640x480x16.
  - 1280x960 with overdraw 2 is about 2.5 Mpix. That is ~15 ms at 1 ppc against ~8-10 ms at 2 ppc.
  - So frames can cross the 11.8 ms refresh line, and with vsync the flip rate doubles when they do.
  - The 640x480 titles probably hold 85 Hz already; for them the gain is CPU headroom only.
- **UE2 (UT2003/UT2004):** at most a few percent today. The frame is the transport (116.7 of 123 ms in
  DrawPrimitive, 29.4k primitives a frame), and the lightmapped world is two-stage. 2PPC pays off there
  after G47/G48/G49.
- **The 32 bpp titles** (H&D, Thief II, Max Payne, Halo by its own pick): nothing unless EN32 proves out.

**Nothing is unblocked:** every title runs already.

## 8. Risk to proven paths

| path | risk | why it is contained |
|---|---|---|
| **default** (switch absent) | none | No `combineMode`, NOP or chromaRange write, and no status read is added. `renderMode` and `fbzColorPath` are unchanged. Pinned by 5.1 test 1 and the 5.2 source checks |
| **16 bpp D3D, armed** | (1) a TMU-state mismatch draws stripes of another texture in alternate bands; (2) a bad exit corrupts two-stage draws (a mirrored "green world"); (3) the 2->1 hardware bug, if our exit is short, could corrupt the TMU pipeline or hang the engine; (4) a loss at high resolution | (1)-(2): the native model (5.1 test 7) and `ppcband`. (3): the exit is the spec's and both 3dfx stacks' (12 TMU-only NOPs, then `combineMode`); Glide toggles 2PPC through it continuously on this silicon; the boot is supervised; a hang is bounded by `SPIN_CAP` and surfaces as a G02 give-up. (4): measured at 1280x1024, and a ceiling exists |
| **32 bpp D3D, armed with `0x221`** | the column band and one exit (14 writes) per PDEV | boot B runs the 32 bpp render lanes in full |
| **Glide/OpenGL coexistence** | D3D leaves `combineMode[29]` = 1 for the next owner | Glide's every open runs its own 12-NOP exit (`GL5/gsst.c:914-917`). The tracker goes UNKNOWN at every handoff. Tested last in boot B |
| **stale state from others** | clearing `combineMode[30]` could re-arm a stale TMU chroma substitution | the TMU chromaRange is cleared before the first write after UNKNOWN (2.4; model test 7d). **Without this, arming 2PPC after an OpenGL session that used a TMU constant colour would key out D3D texels** |
| **SLI** | none | D3D is single-chip. Nothing touches `sliCtrl`/`chipMask`. Snooping is off, so only chip 0 sees the writes (`vcr_3dseq.h:97-99`) |
| **flip, clears, DirectDraw, 2D, texture flush** | none | not touched. FASTFILL is FBI-only. The texture flush is mode-independent (2.5) |
| **refactor** | the TMU block of `VcrDd3dState` | the 1 ppc branch is left textually untouched (5.2) |

## 9. Effort, dependencies, priority

- **Effort M.**
  - Code: about 150 lines (header, plumbing, the hook, `VcrDd3dPpc`, the branch, counters, vcrctl).
  - d3dprobe: about 350 lines (three tests) plus the harness compare (~60).
  - Tests: about 300 lines.
  - On silicon: 3 supervised boots (A, B, C), up to 6 with tuning.
- **Dependencies** (none blocks landing the code):
  - **G01**: procedural. The A/B boots are cold, so a stale Glide FIFO cannot fake a result. The
    coexistence step meets G01's failure mode if Glide's close goes wrong; that is G01's to fix.
  - **G03**: shared `combineMode` ownership and the TMU-only NOP and chromaRange rules. Whichever lands
    first owns the helper (2.8).
  - **G05**: the same register words. Bit 29 is OR-ed in, and the end-of-DP2 restore keeps it.
  - **G78**: the `fill` benchmark and a vsync-on headroom method. This design defines the fill mode
    itself if G78 has not.
- **Interplay, not a dependency:** G26 and G38 must pass `tmu1_used`. G51 must keep the band below the SLI
  band. G47/G48/G49 decide how much of the fill gain reaches UE2.
- **Priority P2.** A performance gain, measurable and cheap. It neither unblocks nor fixes rendering. It
  is the main term in the HAL's fill at 1280x960 (perf report §4).

## 10. Open questions

1. What is the real gain at 16 bpp with Z and blending? The bandwidth arithmetic predicts 1.3-1.9x, not 2x.
   The fill matrix answers it.
2. Is the 2PPC frame bit-identical to the 1 ppc frame, dither and column band included? `ppcexact` answers
   it. If not, `ppcband`'s analytic checks stay the gate.
3. Single-write TMU state: later, can the TMU state go to chip field `0x6` once (4 writes instead of 8)?
   `ppcband` would show it, and the vendor writes both TMUs.
4. Is the 1x1 idle TMU state needed for untextured 2PPC? 3dfx's HAL wrote none, and it costs 8 writes per
   untextured flush. An A/B of `ppcband` strip U plus `t0` fill, with and without it, would decide whether
   to drop it.
5. 32 bpp (hw-41 S4): a gain, nothing, or a loss? And does 2PPC at 16 bpp need a resolution or refresh
   ceiling below 1600x1200 on this CRT (spec L6238)?
6. What band height and column width suit D3D titles? 3dfx tuned 2/32 on 3DMark2000. Boots D-F.
7. Is `miscInit1[18]` (TMU write mirroring) 0 on `.124`? The design does not depend on it. A boot-time
   read logged by the miniport would settle it for G47's packet form.
8. Per title, what share of triangles is single-stage? The context counters answer it, and so which games
   gain at all.
9. G59: is the 16 bpp half-rate flip a separate limit that hides the fill gain under vsync? Flip intervals
   need to be recorded in boot B.
