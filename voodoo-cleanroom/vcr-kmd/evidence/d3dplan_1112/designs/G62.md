## 0. Verdict

**The gap is real, and its cause is not established. It is P1.**

**The record.** Of four recorded runs of the Descent DOSBox shortcut on `.124` (vcr-kmd), three dropped
to DOSBox's 640x400 surface fallback and then showed a blank DOS screen for 60-70 s. One run took the
ddraw path at 640x480 and showed the Interplay logo. The runs used the same conf and the same binaries
on the same box.

**What this reading adds.** Four facts narrow the search:

1. **Only `output=ddraw` puts a surface in the DirectDraw heap.** `surface` and `overlay` make the
   same fullscreen `SDL_SetVideoMode(640,480,...)` call and lock only the primary. Carmageddon runs the
   identical `DOSBox.exe` (md5 33294e0a) and `SDL.dll` (md5 52726f9e) with `output=overlay` and passed,
   once right after a Glide session. Daggerfall (overlay) passed too. So the steps every output shares
   are probably not the failing ones. The ddraw-only steps are: the hardware blit surface, and its
   per-frame Lock and stretched Blt.
2. **That blit surface lies at the bottom of the heap, inside Glide's default command-FIFO window.**
   The first block of a fresh heap is lost at offset 0. This was measured three times on silicon, and
   each time the real surface sat right after the lost block. So DOSBox's 640x400x32 blit surface
   should land at 0xFA000-0x1F3FFF. Its first 46 rows (0xFA000-0x116FFF) are then inside
   [0x18000, 0x117000), the window that a not-idle 4-chip GL close leaves enabled (G01). All three
   failing runs had a 4-chip OpenGL/Glide session one to three titles before them.
3. **On SDL's path our HAL almost never returns an error** (§1 fact 7). So the failing call is most
   likely an answer from the runtime or from Windows that depends on machine state. DOSBox's own log
   names the step: `-noconsole` writes it to `stdout.txt`. The DOSBox window title shows which DOS
   program runs and at what CPU speed. Neither instrument has been used yet.
4. **No setup step is known to fail because of a stale FIFO.** SDL does not write the blit surface
   while it sets it up, so the window is written only frame by frame, after setup. If the fallback does
   follow the FIFO state, the mechanism is still unknown. The design does not paper over that gap: it
   measures it.

**The deliverable** is an investigation, plus a small fix for each outcome:
- **The investigation:** one supervised session, an optional second one, and host-side tools.
- **The likely fix:** `Diag\DdHeapFloor = 2`, which puts the heap above Glide's FIFO window (default
  OFF), and/or G01's stale-FIFO guard.

**The overlay half of the gap is not a defect.** With no overlay caps, SDL takes its software YUV path,
and the four overlay titles render. A hardware YUV overlay belongs to G61.

**Why P1 and not P0.** Both titles run on `.124` through their Rebirth launchers, for single player and
UDP LAN. What is broken is the default "Descent" shortcut and the DOSBox IPX LAN launchers. Raise this
to P0 if Session A's clean-state run also falls back: the default shortcut would then be broken
outright, not only after a GL session.

The sweep called all four PASS: a black frame passes its luma check (G79).

### Fact 2. 640x400 is DOSBox's fallback (README:591-611, reconfirmed in the source)

- With `aspect=true`, the ddraw output asks SDL for 640x480: clip = 640 x (400 x 1.2).
  Sources: `DBX/src/gui/sdlmain.cpp:365-407`, `render.cpp:276, 411-423`.
- Only `goto dosurface` asks for 640x400: `SDL_SetVideoMode(640,400,32, FULLSCREEN|SWSURFACE|HWPALETTE)`
  (`sdlmain.cpp:428-451`). There are two ways in:
  - `GFX_SetupSurfaceScaled` returns NULL. This is silent: DOSBox logs nothing.
  - The blit surface comes back as software. DOSBox logs "Failed to create ddraw surface, back to
    normal surface." (`:519-525`).
- The ddraw output always asks 32 bpp. `GFX_GetBestMode` calls `SDL_VideoModeOK(640,480,0,...)`, which
  answers 0 for bpp 0, so every CAN bit survives (`:296-327`). This agrees with fbshot `fmt 3` at 640x400.

### Fact 3. SDL 1.2.13 has three routes to that fallback

**(a) `SDL_SetVideoMode` returns NULL.** No DOSBox message. Any of these can fail:
- `SetCooperativeLevel` (`SDL/SDL_dx5video.c:1272`);
- the primary (`:1325-1358`);
- its pixel-format check;
- `DX5_AllocDDSurface` on the primary: `GetCaps` must say VIDEOMEMORY (`:1722-1735`), then `Lock`
  (`:1750-1757`), then the format and size checks (`:1784-1801`).

**(b) The screen comes back as software.** DOSBox logs its message. There are two ways:
- Both `SetDisplayMode` calls fail, at SDL's rate and at 0. SDL then retries **windowed** (`:1312-1320`),
  and a windowed screen is `SDL_SWSURFACE` (`:1503-1506`).
- SDL makes a shadow surface (`SDL/SDL_video.c:869-895`).

Either way, `SDL_CreateRGBSurface(SDL_HWSURFACE)` quietly makes a software surface, because the public
screen is not hardware (`SDL/SDL_surface.c:53-74`).

**(c) The blit surface fails `DX5_AllocDDSurface`.** DOSBox logs its message. The steps that can fail:
- `CreateSurface` with OFFSCREENPLAIN | VIDEOMEMORY, and DDSD_PITCH | DDSD_PIXELFORMAT;
- `GetCaps` (if the surface is not in video memory: "No room in video memory");
- `Lock`;
- the size and format checks.

`ddlab sdlddraw` replays routes (a) to (c) for **one** `GFX_SetSize` (`KMD/tools/ddlab.c:214-251, 372-760`).

### Fact 4. Only the ddraw output touches the heap

- All three outputs make the same fullscreen `SDL_SetVideoMode(640,480, 32 or 0, FULLSCREEN|HWSURFACE)`.
  Overlay passes bpp 0, and SDL takes the screen's 32.
- They then make the same primary and the same COLORFILL clear.
- Only ddraw then allocates an OFFSCREENPLAIN video-memory surface from our heap.
- Overlay asks for a DDSCAPS_OVERLAY surface (`SDL/SDL_dx5yuv.c:64-75`). That is refused, because we
  report no overlay caps (`KMD/display/vcrdd_ddraw.c:101-108`). SDL falls back to `SDL_CreateYUV_SW`
  (`SDL/SDL_yuv.c:56-62`), which only locks the primary.

The outputs that never touch the heap passed in every recorded run:
- **Carmageddon** (overlay, `aspect=true`): 640x480 at 23:50 on 09-29, right after Carmageddon 2's
  Glide session at 23:49 (whose close state is unknown).
- **Daggerfall** (overlay, `aspect=true`): 640x480 at 03:16 on 09-28, right after Team Fortress
  Classic's OpenGL session.
- MOO2 and Warcraft (`output=surface`).

One data point is ambiguous: Redneck Rampage Route 66 (overlay, `aspect=true`) at 640x400 with content
(09-28 03:03). It is either its own VESA mode or the same fallback; see the open questions.

### Fact 5. The lost first block, measured three times

Each time, the first block of a fresh heap is the request's own size, placed at 0 and lost. The real
surface is placed right after it:

| request | lost block | real surface | source |
|---|---|---|---|
| `ddlab vidmem`, 512 KB | [0, 512 KB) | +512 KB | `KMD/evidence/silicon/256mb/ddlab_vidmem.txt`: 120 surfaces, `from_primary_lo` -63438848 from a primary at 0x3D00000 |
| fullscreen 1024x768x32 D3D target, 0x300000 | [0, 0x300000) | 0x300000 | `ONBOX/session_log.md:9` |
| windowed 256x256x32 D3D target, 0x40000 | [0, 0x40000) | 0x40000 | `ONBOX/session_log.md:9` |

So the runtime's second pass is real (`KMD/include/vcr_ddheap.h` header), and the loss is
deterministic for a fresh heap. **Prediction, never measured:** DOSBox's blit surface is 640x400x4 =
1,024,000 = 0xFA000 bytes, and it is the first allocation in its 640x480x32 PDEV. It lands at
0xFA000-0x1F3FFF.

### Fact 6. Glide's FIFO window is the bottom of our heap

- **Where Glide puts its FIFO.** h5 Glide puts the Napalm command FIFO 96 KB in, 0xFF000 long:
  [0x18000, 0x117000). Glide's textures start at 0x117000 (`GL5/minihwc/minihwc.c:1043-1044, 2566-2592`).
- **Where our heap starts.** At 0 (`vcr_ddheap.h`).
- **What 3dfx did.** Their own driver reserves the command FIFO, the cursor and the font cache *below*
  its heaps (`VH5/ENABLE.C:2128-2143`, "cmdfifo / hw cursor / font cache / ddraw stretch blt slop /
  linear heap / tiled heap / desktop").
- **What a stale FIFO does** (measured 2026-11-12, `ONBOX` §1):
  - a not-idle 4-chip GL close leaves `cmdFifo0` enabled (baseSize 0x1fe);
  - host writes into its window make it busy (status 0xa1f, CMD0_BUSY);
  - a busy chip makes the 2D path give up, and with it the D3D HAL, for that PDEV.
- **The collision.** On the default layout, the first 118,784 bytes of DOSBox's blit surface are inside
  that window: rows 0-46 at 2560 bytes a row. DOSBox rewrites them every frame.
- **The same with `DdHeapFloor = 1`.** The surface moves to 0x1000-0xFAFFF. From 0x18000 on it would
  then sit wholly inside the window.

### Fact 7. Our HAL fails almost nothing on SDL's path

The only error returns, and they are narrow:
- `Dd_Lock` and `Dd_Blt` answer DDERR_WASSTILLDRAWING, but only for the surface a pending flip is
  taking off the screen. DOSBox never flips (`fulldouble=false`).
- `Dd_MapMemory`, `Dd_WaitForVerticalBlank` and `Dd_GetScanLine` answer DDERR_GENERIC when an IOCTL fails.
- `Dd_CanCreateSurface` refuses only a Z buffer the HAL does not offer: anything but 16-bit unless `D3D32` is armed (`vcrdd_ddraw.c:610-631`).
- Everything else returns DD_OK or NOTHANDLED, and the runtime then does the work: the heap
  placement, the Lock pointer, the stretch Blt in the HEL (`:532`).
- A 2D engine that will not go idle makes `VcrDd2dSync`/`VcrDdRoom` spin for about a second and then
  give up (`vcrdd_2d.c:83-133`). That is slow, but it is not an error.

So the failing call is most likely an answer from the runtime or from Windows. Candidates: the heap
allocation, the mode set, exclusive mode, the runtime's own surface description.

At the default level (DEBUG) our ring records only part of this:
- PDEV and mode events;
- `DirectDraw HAL: heap`;
- exclusive mode and MapMemory;
- `CreateSurface` (the count and the first surface's caps);
- `DD_FAIL` lines, 2D give-ups, and `pick_mode`'s "not listed (monitor limits?)" warning (`vcrdd.c:389-396`).

`Lock` and `Blt` are TRACE (`vcrdd_ddraw.c:650, 479`). The ring holds 1024 entries (`LogEntries`
default, `KMD/miniport/vcrmp_log.c:279-284`).

### Fact 8. DOSBox can say which step failed

- **The log.** With `-noconsole`, DOSBox writes its LOG_MSG lines to `stdout.txt` in its working
  directory (`DBX/src/gui/sdlmain.cpp:1689-1696`). The staged exe carries `-noconsole`, `stdout.txt`,
  "Failed to create ddraw surface, back to normal surface." and "DDRAW:Failed to blit, error %X"
  (`strings LIB/Descent1/DOSBOX/DOSBox.exe`).
- **Why it has never been read.** The staged launchers run DOSBox with its "DOSBox Status Window"
  console instead, and that text is lost when DOSBox exits.
- **The window title.** It reads `DOSBox 0.74, Cpu speed: max NN% cycles, Frameskip N, Program: XXXXXXXX`
  (`sdlmain.cpp:232-246`). `Program` is set whenever a DOS program starts (`dos/dos_execute.cpp:92-99`).
  The agent's `WINLIST` returns window titles.

### Fact 9. The frozen DOS screen is a second question

- **What the failing frames show.** DOSBox's blank text screen, with only the 8x2 cursor at row 0.
- **DOSBox kept drawing.** In the 06:57 run the cursor was on at 30 s and off at 70 s.
- **The DOS side made no progress.** DOS/4GW never printed its banner, which a host DOSBox prints within
  2 s (`KMD/README.md:604-606`).
- **The fallback path works elsewhere.** MOO2 and Warcraft use DOSBox's `output=surface` path on `.124`
  and pass.
- **What decides it.** Whether DESCENTR.EXE ever started, and at what CPU speed, is in the DOSBox window
  title.

### Fact 10. What `ddlab sdlddraw` does not replay

The replay starts from a fresh fullscreen setup and does one `GFX_SetSize`. DOSBox does more:
- It first sets up a **windowed** `SDL_SetVideoMode(640,400,0,0)` (`sdlmain.cpp:1152`). That means
  DDSCL_NORMAL, a clipper, and a SYSTEMMEMORY surface.
- It forces the `directx` SDL driver (`:1767-1777`).
- It runs one `GFX_SetSize` at every DOS video-mode change, for example text, then mode 13h.
- It opens its status console with `AllocConsole`.

Neither `ddlab sdlddraw` nor `DdHeapFloor` has ever run on silicon (history.md §3.6 and §7).

## 3. The investigation

### 3.1 Instruments first (host-side tools, no driver change)

These are tools, not driver behaviour, so they land default-on.

**T1. `ddlab sdlddraw` follows DOSBox more closely** (`KMD/tools/ddlab.c`). With no new flag, today's
sequence stays byte for byte as it is. The new flags:
- `--windowed-first` replays `GUI_StartUp`'s windowed `SDL_SetVideoMode(640,400,0,0)` before the
  exclusive sequence. That is `SetCooperativeLevel(DDSCL_NORMAL)`, the primary, `CreateClipper` +
  `SetHWnd` + `SetClipper`, a 640x400 OFFSCREENPLAIN | SYSTEMMEMORY surface hooked by `SetSurfaceDesc(LPSURFACE)`,
  and one clipped `Blt` to the primary (`DX5_WindowUpdate`).
- `--setsize N` repeats DOSBox's `GFX_SetSize` N times, with `--frames` frames between repeats:
  release the blit surface and the primary, then `SetCooperativeLevel`, `SetDisplayMode` (the same
  mode), the primary and its Lock, the COLORFILL clear, and a new blit surface. DOSBox does this at
  every DOS video-mode change (`render.cpp:423`).
- `--no-pitch` creates the blit surface without `DDSD_PITCH`. It tests whether the explicit pitch is
  what the runtime refuses.
- The RESULT also carries `vidmem_total` (`GetAvailableVidMem`). `blit_from_primary` already exists.
  The host computes `blit_off = 0x4000000 - roundup(pitch x h, 4 KB) + blit_from_primary`, which is
  0x3ED4000 + from_primary at 640x480x32 on `.124`'s 64 MB chip, and from it `blit_in_fifo_window`.
- `ddlab_run.py`'s `SWITCHES["sdlddraw"]` becomes `3 + 2 x (N - 1)`, so the paced budget covers the repeats.

**T2. `KMD/tools/dosbox_ddraw_run.py` (new).** One observed DOSBox launch, through the agent:

1. **Refuse** to start within 30 s of its previous launch, or past a per-boot cap of 8 DOSBox launches
   (a stamp file on the host).
2. **Before the launch**, read chip 0 with `vcrctl reg`, read-only: 0 (status), 80020, 80024, 8002c,
   80034, 8003c, 80048. This is `cmdFifo0` baseAddr, baseSize, readPtr, aMin, aMax and holeCount, the
   command used in `ONBOX/README.md:32`. Also run `vcrlog.py fetch`, which gives the starting sequence
   number, and `DISPLAYCFG get`.
3. **Launch, in one of two modes.**
   - `exact`: the staged shortcut `C:\Games\Descent1\Play Descent.bat`, as `lan_sweep.py` starts it.
   - `noconsole`: a copy of `DOSBOX\` in `C:\vcr\dosbox_g62\`, with both confs copied, the mount made
     absolute (`mount C "C:\Games\Descent1"`), and `DOSBox.exe -noconsole`.

   **Never write under `C:\Games`.** GAMESYNC never deletes, so a stray `stdout.txt` there would stay forever.
4. **At T+15 s and T+45 s:** `WINLIST` (DOSBox's title, the foreground window and pid), `PROCLIST`
   (DOSBox's CPU time), `DISPLAYCFG get`, and `SCREENSHOT 0` → PNG plus its mean and standard deviation.
5. **Close** with WM_CLOSE, then `taskkill /f` after a grace period, then confirm the process is gone.
6. **Read back at once:** `vcrlog.py fetch` and the same register reads. Fetch `stdout.txt` and
   `stderr.txt` with **`DOWNLOAD`**, never `EXEC type`. Then `DELETE` them and confirm with `DIRLIST`
   that they are gone.
7. **No `vcrctl` and no `vcrlog` while DOSBox runs.** Both take the display lock.
8. **The verdict, as JSON:**
   - `path`: `ddraw` (640x480), `fallback` (640x400), `hang-foreground` (the desktop size) or `exited`;
   - `program` and `cycles`, from the title;
   - `fifo_before` / `fifo_after`;
   - the DOSBox log lines;
   - the ring's DirectDraw events between the two sequence numbers.

**T3 (conditional). A diagnostic `SDL.dll`.** SDL 1.2.13 rebuilt from source with
`i686-w64-mingw32-gcc`. It prints `SDL_SetError` and the `DDRAW_DEBUG` lines of `SDL_dx5video.c` to
`C:\vcr\dosbox_g62\sdl_g62.log`. It is used only in that copy, and it never goes into the library. It
names the exact failing call and its HRESULT from inside the real DOSBox.

## 4. Likely fixes, by outcome

### F1 (H1): keep DirectDraw out of Glide's FIFO window, and clear the state

The state itself is G01's: the stale-FIFO guard, `Diag\D3DSafe` bit 0, at its unmap (A) and mode-set
(B) points. Point (B) runs at **every** mode set, and a DirectDraw-only program like DOSBox gets a mode
set too. So G62 needs only G01's DirectDraw-side proof (§7).

**The defence that needs no FIFO knowledge: `Diag\DdHeapFloor = 2`.** The heap starts at 0x117000,
above h5 Glide's default Napalm FIFO window. This makes G01 §3.5 concrete, and it is what 3dfx's own
layout does (fact 6). The changes:
- **`include/vcr_ddheap.h`:**
  - `#define VCR_DD_HEAP_FLOOR_GLIDE 0x117000u`, with a comment citing `minihwc.c:2566-2592` (a 96 KB
    pad plus `MAXFIFOSIZE_16MB` 0xFF000);
  - `static inline vcr_u32 vcr_dd_heap_floor_bytes(vcr_u32 v) { return v >= 2 ? VCR_DD_HEAP_FLOOR_GLIDE : v ? VCR_DD_HEAP_FLOOR : 0; }`.
- **`display/vcrdd_ddraw.c` `heap_range` (`:51-58`):** `vcr_dd_heap_floor_bytes(pd->dd_heap_floor)` in
  place of `pd->dd_heap_floor ? VCR_DD_HEAP_FLOOR : 0`. The INFO line names the floor.
- **`include/vcr_ioctl.h`:** a second positive flag, `VCR_INFO_F_DDHEAPGLIDE`. Its bit is allocated at
  integration, because several designs already claim 0x8000 and 0x10000. The unique-bit assertion in
  `test_vcr_kmd_ddraw.py:402-403` catches a clash.
- **`miniport/vcrmp.c` `fill_info` (`:463-466`):** `DdHeapFloor` = 1 sets `F_DDHEAPFLOOR`. A value of
  2 or more sets both flags, so an older DLL gets the one-page floor.
- **`display/vcrdd_2d.c` `VcrDd2dInit` (`:457`):**
  `pd->dd_heap_floor = (f & F_DDHEAPGLIDE) ? 2 : (f & F_DDHEAPFLOOR) ? 1 : 0;`.
- **The cost:** 0x117000 = 1,142,784 bytes of a heap of about 60 MB.
- **What it cures besides.** No block sits at 0 any more, so it also cures H2/G63 for DirectDraw and for
  the D3D mip-chain allocator.
- **Where it applies:** any Voodoo backend. On the VM bed the desktop sits at 0, and the floor matters
  there only below 0x117000 bytes of desktop.
- **Not done:**
  - a floor read from the live `cmdFifo` registers. A heap is built once per mode set, so a FIFO that
    appears later would not move it.
  - a per-allocation guard. The runtime places these surfaces, not us.
- **Gating.** Default OFF. When it is off, `heap_range` gets floor 0, byte for byte today's layout.
  It is read at every mode change and needs no reboot to arm, but under the convention it is armed for
  one supervised clean boot. If that boot proves it (§7), move the default with a `MOVED_DIAG` entry
  carrying the evidence (`MOVED_DIAG`, `WT/tests/python/test_vcr_kmd_integration.py:91`).

With the floor alone, a stale FIFO stays enabled but idle. For 2D that is harmless: the desktop did 10
million 2D operations in that state without a give-up (`ONBOX` §1). D3D still loses its triangles,
which is why G01's guard is needed for D3D in any case.

### F2 (H2): the floor

`DdHeapFloor` 1, or F1's 2, which includes it. The decision is G63's, and Session B is its silicon proof.

### F3 (H3): the rate SDL asks for

1. Add a host emulation of SDL's `EnumModes2` (`SDL/SDL_dx5video.c:651-709`). It keeps the first rate
   enumerated for a mode and raises it only by later rates that are no higher than the desktop's.
2. Run it over our listing order (`vcr_modeorder.h`, then the miniport's resolution-then-refresh order)
   and the EDID filter. That gives the exact `(640,480,32,rate)` SDL asks for.
3. Fix `pick_mode` or the list so that every mode DirectDraw enumerates can be set.

### F4 (H4): the runtime's primary or surface description after a mode change

Look at `DrvGetDirectDrawInfo`'s `vmiData` and the mode-change ordering. The fix depends on which check fails.

### F5 (H5): the harness, not the driver

`lan_sweep.py` waits after a title until the desktop's persisted mode is live again, then 3-5 s more,
before it starts the next one. G62 is then "not ours" for the driver. G79 owns the sweep's luma verdict.

### F6 (H6): depends on what the window title and the CPU time show

## 8. Risk to proven paths

- **The investigation changes no code and no default.** Session A changes nothing. Session B arms an
  existing switch that is unproven on silicon. Session C changes only the logging.
- **The 1998 CRT.**
  - The fallback itself can make two unpaced switches in quick succession (640x480, then 640x400).
  - Hence the cap of 8 DOSBox launches per boot, with at least 30 s between them.
  - ddlab is paced.
  - The three recorded failures already made these switches; the 06:53 run made one.
- **The post-GL state can escalate.**
  - Writes into an enabled FIFO window make the chip execute whatever the pixels decode to. It went busy
    within about 1 s on 11-12, then the 2D give-up followed and the D3D HAL was lost for that PDEV.
  - `hal.md` calls this a credible freeze mechanism (inferred).
  - So a person stays near the box for A6-A9. Stop at the first sign of trouble: the agent's PING
    fails, or the ring shows a give-up.
  - Recover with one paced `vcrctl modeseq` (proven 11-12), or with a cold boot through `safe-reboot.py`
    after the activation check.
- **`vcrctl reset-engine` (A9) has never run on silicon without a new PDEV** (G01 fact 8). Run it with
  nothing else on the engine, and fall back to `modeseq`.
- **No `vcrctl`/`vcrlog` while DOSBox runs.** Both take the display lock.
- **The library tree is never touched.** The `noconsole` and diagnostic-SDL runs use `C:\vcr\dosbox_g62`.
- **Session B's floor moves every DirectDraw and D3D allocation off 0.** So the d3dprobe matrix runs in
  that boot too. That run is G63's proof as well.
- **F1, armed:**
  - Every heap surface moves up 0x117000: D3D targets, Z, textures and mip chains.
  - Proven paths are unchanged while it is off, because `heap_range` gets floor 0, byte for byte.
  - Glide never uses the DirectDraw heap; its own map starts at its FIFO and texture memory. SLI is
    untouched.
  - Flip-chain back buffers move up too, which `ddlab flip` and d3dprobe fullscreen cover.
  - **On the default 16 bpp D3D path (no `D3DBigTex`) the move is not neutral.** That path writes the
    24-bit texBaseAddr, so a texture above 16 MB is sampled 16 MB lower (G21). Moving every surface
    up 1.1 MB pushes a few more textures over that line. `.124` runs `D3DBigTex` = 7 (26-bit
    addresses), so the deployed setup is not affected; a fresh install is. Prove F1 with `D3DBigTex`
    off as well, or land it after G21's fix.
