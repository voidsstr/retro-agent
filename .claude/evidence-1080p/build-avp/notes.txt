avp.exe facts that decide the 1080p work (addresses in the disassembly file)
----------------------------------------------------------------------------
* MENUS always run 640x480 on the primary display: SelectMenuDisplayMode 0x491e90
  stores 0x280/0x1e0 and opens DirectDraw with a NULL GUID (0x538580(0)).
  The Options > Video choice is for GAMEPLAY only (SetGameVideoMode 0x4fada0).
* Options > Video lists (device, mode) pairs; label "%dx%dx%d" (0x5596f4).
  Devices: DirectDrawEnumerateExA flags 7 (0x559668); a device needs DDCAPS_3D and a
  HAL D3D device (0x559310); max 4 devices. Modes: EnumDisplayModes dwFlags=0
  (0x559629) kept when bpp>8, w>=512, h>=384 and the HAL's dwDeviceRenderBitDepth
  has that depth (byte 0x85c569: 4=16bpp 2=24bpp 1=32bpp); cap 100.
* Measured by another session (goldsrc-halo-review/probe_{123,145,195,240}.txt):
  DirectDraw's "Primary Display Driver" (NULL GUID) enumerates 1920x1080x16 AND
  1920x1080x32 on all four LCD boxes; accepted-mode counts 30-42, under the cap.
* AvP_Video.cfg (working directory, "rb"/"wb", 32 bytes): GUID[16], DDGUIDIsSet,
  W, H, BPP. The loader 0x559810 compares ONLY the 16 GUID bytes (primary = zeros,
  because the NULL-GUID record is never written), then W/H/BPP. Device found + mode
  not listed -> mode index stays -1 and 0x55999c copies W/H/BPP from dev+0x9d4 (the
  tail of DDCAPS). Absent/unmatched device -> 640x480x16 (0x5598f8).
* The only SetDisplayMode is IDirectDraw v1 (w,h,bpp) at 0x537511: no refresh
  argument, Windows picks the mode's default refresh (for the refresh lane).
